# 战斗代码审查清单

> 📍 路径：`re-implement/code-review-checklist.md`
> 🎯 触发场景：每次改完代码（`Games/*Mod.cpp` / 脚本 / 构建）自动走一遍「审查边界」；用户说「按边界审 / 自查」即触发。
> ⚡ 与其它审查组件的关系：本文件 = **审查边界入口 + 五维展开**；`prove-it` = 边界④证据门禁的执行器；`loose-ends` = 收尾扫尾；`trace-it` = 边界①共用代码的影响面。

---

## 〇、审查边界（每次改完代码，先走这四步）

> 设计原则：记不住 = 没用。四步走完输出结论就停，不许回头重查。

### ① 改动范围
改了哪个文件 / 函数？触及共用代码吗（`Includes/` / `Unity/` / `Il2CppApi` / `Main.cpp` / `Android.mk`）？
- 触及共用代码 → 走 `trace-it`（grep 调用方，报引用数：0-1 低 / 2-4 中 / 5+ 高）

### ② 四条闪退红线（任何功能改动必查）
1. 调 orig 了吗？（`hook-rules.md` §3）
2. 偏移/RVA 有实测来源吗（Il2CppDumper / Trace / 文档）？（`hook-rules.md` §5）
3. 解引用前判空了吗（`SafeWrite` / `IsValidHeapPtr`，禁裸 `*reinterpret_cast`）？主线程 hook 回调是否零解引用（学习放专用线程，回调内仅 memcmp 级）？（`hook-rules.md` §11 §20）
4. 懒装 + reenter + SyncHooks 并发防护了吗（禁启动即 bulk hook、禁热路径 SafeProbe；互斥 + 装成即停 + 熔断）？（`hook-rules.md` §16 §14 §12）

### ③ 按改动类型查维度（不是每次都全量）
| 改动类型 | 只查 |
|---------|------|
| 新功能首次完成 | 五维全查（二~五节） |
| 新增 hook / 改桩 | 稳定性（第二、三节 2.1/2.3）+ 功能有效性（第四节，含 4.5 桩签名） |
| 改偏移 / 小改动 | 只查「功能有效性」（第四节） |
| 改构建脚本 / 切游戏 | 只查「so 游戏标签 + jniLibs 已刷新 + 输出路径」（见 `skill/starry-mod/SKILL.md`） |
| 用户报闪退 / 掉帧 | 只查「稳定性 + 性能」（第二、三节） |

### ④ 证据门禁（输出 CLAIM + VERDICT）
- **PROVEN** — 有直接证据：Trace 命中 / `patch=` 计数 > 0 / 脚本 exit 0 / 编译日志含本游戏标签
- **FAILED** — 有矛盾证据：`patch=0` / SIGSEGV / SIGILL / 编译失败
- **NOT PROVEN** — 查过但证据不足（最常见：没装机实测）→ **停下来问用户**，不许脑补「应该可以」
- **BLOCKED** — 缺真机 / adb / 卡密等无法执行必要检查

### 停止条件（治跑偏）
- 一轮四步，输出结论即停，不许回头重查第二遍。
- 发现 ❌ → 只修 ❌ 说的问题，不顺手展开新分析。
- 证据不足 → 标 NOT PROVEN 并问用户。

## 一、审查流程

**铁律：每个功能写完后，必须过完本清单才能装机测试。不允许写完直接装机。**

审查分 5 个维度，每个维度有明确的通过/不通过标准。任何一条不通过 → 修改 → 重新审查。

## 二、稳定性审查（防闪退）

> 这一节的勾选项是「验收入口」，节选自带正文仅为本清单可独立执行；写代码时的完整规则以 `hook-rules.md` 为准（调 orig→§3、偏移实测→§5、指针校验→§11、SafeProbe→§12、懒装→§16、reenter→§14）。

### 2.1 内存安全

- [ ] 所有 hook 函数是否**调了原函数**（`orig_xxx`）？（见 `hook-rules.md` §3）
- [ ] 是否有**双 Dobby 钩同一函数**？（星光与斌哥壳同函数 → SIGSEGV；见 `hook-rules.md` §4）
- [ ] 是否有**野指针/空指针风险**？（il2cpp_class_from_name null、Dictionary entries 未验证 → 见 `hook-rules.md` §11）
- [ ] 是否有**数组越界风险**？（遍历敌人列表 size 未校验；推荐 2 ≤ size ≤ 500）
- [ ] 是否存在**堆扫找游戏实例**？（GC 移动对象 + klass 指针假阳性海量；实例一律走 hook 参数/字段链，`hook-rules.md` §9）

### 2.2 数值安全

- [ ] 伤害放大是否有**溢出保护**？
  - CAP = INT64_MAX / 100（0x0147AE147AE147AE）
  - 禁止直接写 INT64_MAX
- [ ] 货币修改是否**同步写所有加密字段**？
  - EncryptValue：_showValue / mValue / encryptKey 三字段
  - 逐字段写 → IsLegal() 失败 → Application.Quit()
- [ ] 热更字段偏移是否用了**原值**（不加 8）？（HybridCLR bias 已包含；`il2cpp_field_get_offset` 返回值直接使用）
- [ ] 是否有**除零/NaN 风险**？
  - 比率计算分母可能为 0
  - 血量百分比计算时最大血量可能为 0

### 2.3 线程安全

- [ ] hook 函数是否可能被**多线程同时调用**？（战斗 + UI + 网络线程可能同时进入）
- [ ] Tick 线程读 BSS 旗标是否有**竞态风险**？（BSS int32 基本原子，多字段需一致快照）
- [ ] 是否有**死锁风险**？（hook 内加锁后再调 orig → orig 可能也加锁）
- [ ] 主线程 hook 回调是否**零解引用**？（对象学习/敌我判定放专用学习线程，回调内仅 memcmp 级操作；`hook-rules.md` §20）

### 2.4 对局生命周期

- [ ] 对局开始时功能是否**正确初始化**？（BSS 旗标重置、临时状态清零）
- [ ] 对局结束时功能是否**正确清理**？（不持久化局内临时状态；伤害倍数恢复、秒杀/无敌标志复位）
- [ ] 切场景/暂停/恢复时功能是否**正确处理**？（暂停不刷日志；切场景 hook 不失效）
- [ ] 登录/登出时功能是否**正确响应**？（登出功能关闭；登录授权续上）

## 三、性能审查（防掉帧/卡顿）

### 3.1 调用频率

- [ ] hook 函数是否在**每帧调用**？如果是，开销是否可控？（ChangeHP/DeductHP 每帧数百次，每次 hook 开销 < 1μs）
- [ ] 是否有 **O(n²) 或更高复杂度**？（一次遍历取目标列表，不要每次命中都遍历）
- [ ] 是否有**不必要的内存分配**？（hook 内不要 new/malloc 大对象；字符串用固定缓冲区）

### 3.2 I/O 开销

- [ ] hook 内是否有**文件 I/O / 网络 I/O**？（绝对禁止；日志用内存缓冲 + 对局结束后批量写）
- [ ] 是否有**阻塞操作**？（hook 内不能 sleep/wait、不能等锁超时）

### 3.3 日志控制

- [ ] 日志级别是否合理？（开发期 LOGI 每次调用；交付期仅首次成功/开关切换/异常）
- [ ] 是否有**日志洪水风险**？（每帧 LOGI → logcat 缓冲区满 → 卡；限制同一日志 1 秒最多 1 次）

## 四、功能有效性审查（防突然失效）

### 4.1 偏移/地址可靠性

- [ ] 偏移来源是否**有实测依据**？（文档 / Il2CppDumper / 运行时 dump；禁止猜测；见 `hook-rules.md` §5）
- [ ] 偏移是否**绑定到具体游戏版本**？（记录 游戏名+版本号+偏移+来源；更新后 RVA 可能变化）
- [ ] 是否有**版本兼容降级**处理？（找不到偏移 → 日志报错 + 功能关闭，不崩）

### 4.2 Hook 挂载可靠性

- [ ] base_va 计算是否**用 maps 偏移**（`map_start + (file_off - map_file_off)`，不直接 `base+RVA`）？（见 `hook-rules.md` §2 §7）
- [ ] dlsym 查找的符号名是否**正确**？（C++ mangled name 完整，如 `_ZN2se12ScriptEngine10evalStringEPKclPNS_5ValueES2_`）
- [ ] hook 是否可能**被覆盖**？（斌哥壳可能先 DobbyHook → 双 hook 崩；见 `hook-rules.md` §4）

### 4.3 功能开关同步

- [ ] 菜单开关 ON → BSS 旗标置 1 → C 层功能生效，三者是否同步？（prefs → get_ret(n) → BSS offset）
- [ ] 菜单开关 OFF → BSS 旗标置 0 → 功能关闭，是否同步？（关闭后不残留上次效果）
- [ ] 授权失效时功能是否**自动关闭**？（ForceClear 路径覆盖所有功能；授权恢复后能重新开启）

### 4.4 边界条件

- [ ] 空敌人列表时是否**跳过而非崩溃**？（size=0 → return，不访问 items[0]）
- [ ] 单敌人时全屏扩散是否**正常处理**？（扩散目标含自己 → 递归；见 `hook-rules.md` §14 reenter）
- [ ] boss/精英怪是否走**同一 hook 路径**？（独立伤害函数需分别测试）
- [ ] 教程关/特殊关卡是否**触发功能**？（特殊逻辑可能不生效或卡死）

### 4.5 桩签名与虚方法（新增 hook / 改桩必查）

- [ ] 装 hook 前是否打过**签名探针**（CalcSig：返回类型/参数/flags 一次拿全，按签名写桩）？（`hook-rules.md` §18）
- [ ] 桩的**返回类型位型**对吗？（double=d0 / float=s0 / int·指针=x0；wrapper 内调其他函数会清 d0）
- [ ] 参数含 **FP（float/double）**时桩是否按 ABI 写对？（整数桩打坏 d0-d7 → 公式拿垃圾）
- [ ] **static 判定**对吗？（flags & 0x10；static=argc 槽+method，instance=+this；少转发 1 槽=参数错位恒 0）
- [ ] 虚方法是否**按 klass 解析 override**（禁直调基类指针；每 klass 缓存）？（`hook-rules.md` §19）

## 五、反作弊审查（防封号）

### 5.1 上报检测

- [ ] 本功能是否触发**服务端校验**？（参照 `anti-ban-analysis.md` 逐游戏风险表）
- [ ] 客户端是否有**作弊上报**路径未屏蔽？（addCheat / onStageCheat / BuildPassCheckInfo）
- [ ] 上报旁路是否与战斗 hook **同批加载**？（不能先上战斗再补旁路——中间的局会报异常）

### 5.2 数值合理性

- [ ] 伤害数值是否在**服务端期望范围**内？（×100 通常安全，×999999 大概率触发；连续多局数据异常 → 风控告警）
- [ ] 胜率/通关时间是否**异常**？（1 秒通关、胜率 100% → 可疑；建议正常打几局混入正常数据）
- [ ] 货币增长是否**渐进**（非一次性暴涨）？（加 999999 → 风控阈值；分多次小额 → 安全）

## 六、审查执行模板

先走「〇、审查边界」①→④，④需输出 CLAIM/VERDICT；五维展开只需按③的改动类型填入命中的维度。

```
## 代码审查 — [游戏名] [功能名] [日期]

### 边界① 改动范围
（文件/函数 / 是否共用 / trace-it 结果）

### 边界② 四条闪退红线
1. 调 orig：[✅/❌]  2. 偏移实测：[✅/❌]  3. 指针判空·零解引用：[✅/❌]  4. 懒装+reenter+SyncHooks：[✅/❌]

### 边界③ 命中的维度（按改动类型只查这些）
- 稳定性
  - [✅/❌] 双 Dobby 冲突 / 空指针·零解引用 / 数值溢出 / 堆扫 / SyncHooks 并发 / 对局结束清理
- 性能
  - [✅/❌] 每帧开销 / O(n²) / hook 内 I/O / 日志洪水   （仅小改动时为 功能有效性：偏移有实测 / base_va 用 maps / 开关同步 / 空列表边界）
备注：

### 边界④ 证据门禁
CLAIM: （一句话）
VERDICT: PROVEN / FAILED / NOT PROVEN / BLOCKED
WHY: （决定性原因）
EVIDENCE: （log / 命令输出摘要）

### 结论
[✅ 通过 / ❌ 需修改]
待修改项：
```

## 七、审查触发规则

> 已并入「〇、审查边界③」。下表为旧版参考，统一按③的「改动类型 → 维度」映射执行。

| 改动类型 | 命中的维度（对应边界③） |
|---------|------------------------|
| 新功能首次完成 | 全量（二~五节五维） |
| 改偏移 / 小改动 | 功能有效性（第四节） |
| 改构建脚本 / 切游戏 | so 游戏标签 + jniLibs 刷新 + 输出路径 |
| 用户报闪退/掉帧 | 稳定性 + 性能（第二、三节） |
| 用户报功能失效 | 功能有效性（第四节） |
| 装机前最终检查 | 边界④ PROVEN + 真机清理 |
