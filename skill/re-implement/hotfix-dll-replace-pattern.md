# 授权热更程序集变更：加载边界项目模式

> 合并日期：2026-09-05；状态：已批准合并，非全部命题 PROVEN。
> 适用范围：有权修改与测试的 Unity IL2CPP / HybridCLR 项目及明确指定程序集。
> 这是项目经验，不是 Unity / HybridCLR 官方解法，也不是通用保护绕过方案。

## 证据与定位

- 历史来源：[无限升级运行记录](../../10_docs/无限升级/运行时dump与YAES破解_20260905.md) §七–十一。
- 案例版本：无限升级 11.266018；以下“历史观察”均来自记录，非本轮运行核验。
- 本模式只沉淀程序集变更的契约、验证与失败边界，不收录规避或作弊实施步骤。
- 参考 [hook-rules.md](hook-rules.md) 的 ABI、地址、生命周期与原调用契约。
- 参考 [HybridCLR 运行时知识](../re-extract/hybridclr-runtime.md) 区分 AOT 与解释执行。
- “已合并”表示文档经验已收录；每项运行声明仍须独立给出证据。

## 何时考虑这个模式

- 项目确有受控的程序集加载边界，并已明确允许变更的程序集与版本。
- 需要验证托管变更如何经过既有加载链，而不是假设每个业务方法都有 native 地址。
- 原生加载边界存在，不等于解释执行的业务方法具有独立 AOT 入口。
- 边界身份、实际调用关系或授权范围不清楚时，先标 NOT PROVEN，不套用案例。
- 优先使用项目支持的构建、热更和部署机制；本模式不替代正常发布与授权流程。

## 变更前的契约

1. 记录输入程序集身份、版本、依赖、目标运行时和允许修改范围。
2. 明确输出程序集身份与可回退的原始产物，避免把其他构建混入验证。
3. 核对程序集名称、类型/方法签名、引用关系与加载顺序是否仍兼容。
4. 明确共享加载入口的非目标调用必须保持原行为；不得无过滤影响其他程序集。
5. 核对加载参数、返回值、异常传播、所有权、生命周期和原调用副作用。
6. 字节容器的容量、有效长度与解析语义须一致，不把“能容纳”当作“可加载”。
7. 线程和初始化时序依目标构建验证，不从一次命中推定重启也可靠。
8. 缺失、格式错误或版本不符时应保留安全失败与可恢复路径，不能静默误用。

## Cecil 四项检查

### 1. 基础类型编码正确

- 历史记录：手工构造的 `System.Int32` 引用曾被编码为 CLASS，引发类型错误。
- 基础类型使用目标模块正确的 `TypeSystem` 表示，并核对输出签名编码。
- 这不等于所有 `TypeReference` 都用 `TypeSystem`；自定义、泛型与外部类型应正确导入/构造。
- 检查类型作用域、值/引用类型属性、泛型参数与目标依赖，而不仅看显示名称。

### 2. 实例引用与调用匹配

- 实例方法引用的 `HasThis` 必须匹配真实签名；静态方法不能机械设为 true。
- 核对调用点接收者、参数、返回类型与 `call` / `callvirt` 的实际语义。
- 历史记录曾因实例引用不匹配发生 MissingMethodException；名字相同不能证明引用正确。

### 3. 分支不能绕过必要初始化

- 新分支不得越过后续必需的局部变量、委托或对象初始化。
- 每个汇合点检查可达路径上的定义与使用，兼顾异常处理区域和原副作用。
- 历史记录曾出现绕过委托构造、后续回调为空；分支能反编译不代表业务完整。

### 4. 求值栈平衡

- 逐条计算入栈/出栈，保证各分支汇合点的栈高度和类型兼容。
- `ret`、条件跳转、异常边界和方法调用分别按签名与控制流核对。
- 不是所有问题都补 `pop`：无待消费值时补它会下溢，错误类型/路径也不会因此修复。
- 历史 QuickUpgrade 的栈修正之后仍崩，不能把一个栈问题修掉当作整体修复。

## 配置与路径契约

- 配置生产者与消费者须约定键、类型、默认值、异常回退和更新可见性。
- 明确谁有权写入、何时读取、如何避免半写内容及如何恢复原行为。
- 历史观察：本构建的 `Application.persistentDataPath` 曾返回空串，配置读取失效。
- 空串的根因 **NOT PROVEN**；不能泛化为 Unity API 不可用或解释器普遍不支持。
- 路径来源、调用时机与运行环境须分别验证，不能只凭一次替代路径生效断言根因。
- 硬编码应用私有路径不是通用推荐，会依赖包名、用户空间与具体部署环境。
- 案例中的固定路径、缓存间隔和替代处理仅见历史记录 §七–九，不作为模式默认值。
- 配置直写只能验证该输入覆盖的消费链；不能证明 UI 映射、正常授权或恢复链。

## 分层验证，不越级证明

| 层次 | 可以证明 | 不能据此证明 |
|---|---|---|
| 静态 IL / 反编译检查 | 所检查签名、分支、栈与引用关系 | 目标运行时行为与完整业务语义 |
| Mono 测试 | 测试实际覆盖的托管逻辑与断言 | 目标 HybridCLR 桥接、装载时序或原生行为 |
| 目标加载证据 | 当前产物在该次运行到达指定边界 | 所有方法生效、重启稳定或正式授权成功 |
| 行为与回归 | 覆盖场景内的开关效果和副作用 | 未覆盖场景或不同版本仍可靠 |
| 正常端到端 | 实际覆盖的 UI、授权、配置、业务和恢复链 | 未验证的发布环境和账户状态 |

- Mono 历史断言通过不能提升为“目标 IL 全部正确”；测试替身不等于目标桥接。
- 加载成功与局部日志仅是局部事实，验证时绑定确切程序集及最终包身份。
- 基线、变更开启、关闭恢复、异常输入、重启与必要回归分别记录，不合并成一个“通过”。
- 无授权或依赖用户操作的目标验证保持 NOT PROVEN，文档任务不自动恢复设备执行。

## 历史失败与不可推广项

- QuickUpgrade 在栈修正后仍出现 tagged-pointer 崩溃，最后是禁用，不是完整修复。
- “禁用后无反应不崩”只证明该避用状态，不证明原生崩溃根因已解决。
- 关于具体根因的判断须有独立证据；旧报告的确定语气不替代证明。
- 100ms 重试、约 1.5s 装载窗口等仅是记录 §九的本构建参数，不作为通用时序。
- 加载边界历史实现的大小、地址和字节容器策略仅属案例，不复制为跨版本方案。
- 最后五功能历史报告仍把后台注册与发卡列为移交项，不能证明正式授权全链路。
- 菜单映射与授权验证边界见 [星光落地](../starry-mod/SKILL.md) 的 2026-09-05 合并节。
