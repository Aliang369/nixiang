# 代码审查清单

> 路径：`re-implement/code-review-checklist.md`
> 触发场景：代码、脚本、构建改动后；用户说“按边界审 / 自查”即触发。
> 本文件为审查边界入口及按需展开项。可用检索、构建日志、测试记录执行，不依赖特定审查组件。

---

## 〇、审查边界（每次改完代码，先走这四步）

一轮四步输出结论即停。发现问题只修该问题，修复后复查修复点及直接影响面，不跳过复查，也不无限扩大审计。

### ① 改动范围

列出文件/函数、目标版本、改动意图和声明。触及共用代码时检索调用方及构建引用；引用数是范围线索，不是严重程度的证明。未改动文件仅按直接依赖需要核对。

### ② 四条闪退红线（相关功能改动必查）

1. **调用契约与副作用**：默认保留 orig 必要副作用；调用次数、时机、参数、返回值、ABI、异常和生命周期是否有依据？不调 orig 不等于必崩，调用 orig 也不等于安全。（`hook-rules.md` §3 §18）
2. **地址与身份**：偏移绑定到哪个产物、版本、架构和坐标系？ELF VA/file offset/IDA EA/load bias 是否明确，运行时确认到哪一步？（§2 §5–7）
3. **内存与对象**：判空/映射检查之外，有无类型、边界、存活期、所有权、线程与写屏障依据？memcpy/memcmp 也访存，学习线程不豁免。（§9 §11 §20）
4. **重入、并发与安装**：同线程重入和跨线程互斥分开；安装检查与发布整体同步；无热路径异常探测；懒装、失败隔离和重试范围有依据。（§4 §12 §14 §16）

不适用项写 N/A 和理由；红线是审查类别，不是“违反必 SIGSEGV”的预测。

### ③ 按改动类型查维度（不是每次都全量）

| 改动类型 | 检查范围 |
|----------|----------|
| 新功能首次完成 | 二~五节相关项，N/A 写理由 |
| 新增 hook / 改桩 | 稳定性、性能受影响项 + 第四节，含 4.5 ABI |
| 改偏移 / 小改动 | 第四节 + 实际受影响的地址、布局、生命周期项；不因改动小免查 |
| 改构建脚本 / 切游戏 | 下述输入身份、错误传播、输出身份，以及直接调用链 |
| 用户报闪退 / 掉帧 | 稳定性 + 性能；保留多根因候选 |

**构建脚本专项**（不只看标签）：
- 输入身份：APK/ELF/DEX/配置的版本、架构、路径、哈希或 build ID，依赖和 jniLibs 来源是否一致；是否可能拾取旧文件或错游戏产物。
- 错误传播：子命令、管道、后台任务、条件分支的失败是否上抛；退出码是否被覆盖；失败时是否仍复制、签名或报告旧输出。`set -e` 本身不是完整证明。
- 输出身份：输出路径与实际 APK 内容一致；核对嵌入的 so/dex、架构、包信息、签名及输入输出对应关系，防止旧缓存和复制错位。游戏标签和构建成功仅为局部线索。
- 工具链验证：记录实际执行命令、退出状态、产物检查；必要时用受控失败测试验证错误传播，不以正常 exit 0 证明失败分支正确。

### ④ 证据门禁（CLAIM + 适用范围 + 证据 + VERDICT）

每条声明独立裁决，记录版本/产物、设备/运行时、场景、测试条件和未覆盖范围：
- **PROVEN**：证据直接支持该范围内的声明；不外推到其他设备或全部行为。
- **FAILED**：有直接反证；说明反驳哪条声明，不由事故直接推定根因。
- **NOT PROVEN**：已检查但证据不足；明确缺口和下一项最小验证。
- **BLOCKED**：必要检查因设备、权限、输入或用户操作缺失而无法执行。

编译成功只证明本次构建结果；脚本 exit 0 不证明打入了正确内容；hook 安装、hit 或 `patch>0` 只证明相应路径/计数被观测，不证明目标行为、副作用或稳定性。`patch=0` 也须先确认场景确已触发，不能独立推定挂点错误。

**分阶段门禁**：
- **G1 可测试**：静态审查、可用的构建/产物检查完成；无已知阻断安全测试的问题；明确测试边界、观测、停止和恢复条件。未测试行为标 NOT PROVEN，不因此阻止首次受控测试；存在 ABI/地址/存活期等关键未知时先缩小为可安全执行的诊断实验。
- **G2 运行**：G1 后获取实际运行证据，验证目标行为、对照、关闭路径和直接副作用；安装成功/hit 不代替行为验收。未覆盖项继续标 NOT PROVEN。
- **G3 交付**：对拟交付的确切产物完成身份检查与约定运行/回归验收，列明覆盖范围和剩余限制。不能用另一个构建的 G2 结果直接宣布本包通过。

### 停止条件（治跑偏）

- 一轮输出当前门禁和逐条结论后停止扩展。
- 只修已发现问题；修后核对修复点、直接调用/数据/构建影响面，并更新对应声明。
- NOT PROVEN 不自动暂停所有工作：能在授权范围内完成的最小验证可继续；需要用户操作/决策、缺少条件或安全边界不清时说明并等待。

## 一、审查流程

首次装机测试前完成 G1，而非要求尚不存在的 G2 运行证据。按③选择维度，得到实际运行证据后再判 G2，交付前判 G3。所有结论都有适用范围，不声称一次测试证明永不崩溃。

---

## 二、稳定性审查（防闪退）

完整技术依据见 `hook-rules.md`；事故记录与原因推断分开。

### 2.1 内存安全

- [ ] orig 的必要副作用、ABI、有效跳板及发布状态已核对？（§3 §18）
- [ ] 同一入口有无重复改写、链式兼容或安装顺序问题？双 hook 不是必崩定律。（§4）
- [ ] 对象来源、类型、存活期、所有权、字段布局及边界有证据？地址检查不能替代生命周期。（§11）
- [ ] 数组 size/capacity/元素宽度和溢出有验证？允许范围按容器契约，不套统一 2~500。
- [ ] GC 实现是否明确？非移动 GC 仍有回收/复用问题；堆扫 klass 命中不证明实例。（§9）

### 2.2 数值安全

- [ ] 运算类型、范围和溢出行为明确？放大时按实际因子检查，不套固定 CAP。
- [ ] 关联字段更新是否满足目标对象的一致性和同步契约？历史 EncryptValue 多字段案例不能推广到所有对象。
- [ ] 字段偏移来源和对象表示已匹配？不无依据加减固定 bias，运行时 API 返回值也需核对适用类型。
- [ ] 除零、NaN、无穷、负值、单位/精度转换是否覆盖？

### 2.3 线程安全

- [ ] hook 可能由哪些线程调用？相关引擎 API 有无线程亲和性？
- [ ] 普通 BSS `int32_t` 无同步跨线程读写仍是 C++ data race；对齐不撕裂不等于语言层安全。所有访问端使用一致的原子或锁协议？
- [ ] 多字段快照是否一致？原子发布/读取的内存序与对象生命周期相符？
- [ ] 同线程重入用 thread_local RAII 等机制；跨线程互斥另行设计，独立 atomic load/store 不算锁？（§14）
- [ ] 持锁调 orig/回调是否可能递归或死锁？安装状态是否整体同步？
- [ ] 主线程或学习线程访问均满足生命周期和线程许可？memcpy/memcmp 也访存，attach 不等于任意引擎操作安全。（§20）

### 2.4 对局生命周期

- [ ] 初始化、结束清理、切场景、暂停/恢复和登录/登出路径是否覆盖？
- [ ] 缓存引用、元数据、方法指针在域/模块/场景变化后是否按契约失效？
- [ ] 关闭功能是否恢复应恢复的状态，不残留临时效果？

## 三、性能审查（防掉帧/卡顿）

### 3.1 调用频率

- [ ] 按目标设备实测调用频率、耗时和分配，不把“每次 <1μs”或方法名称当通用事实。
- [ ] 热路径有无重复全量遍历、O(n²)、昂贵解析或无界缓存？优化不破坏对象生命周期。

### 3.2 I/O 开销

- [ ] 热路径避免同步文件/网络 I/O、sleep/wait 和无界锁等待；诊断日志有界且测量开销。

### 3.3 日志控制

- [ ] 使用采样/限频/缓冲，开发期也不默认逐调用 LOGI；错误诊断证据不能因过度限频丢失。
- [ ] 交付日志量、线程竞争与缓冲区开销经核对？

---

## 四、功能有效性审查（防突然失效）

### 4.1 偏移/地址可靠性

- [ ] 记录版本、架构、产物哈希/build ID、偏移、坐标系和来源；区分静态候选和运行时确认。
- [ ] 更新后重新核对；解析失败时仅关闭依赖功能，清楚报告降级。

### 4.2 Hook 挂载可靠性

- [ ] ELF VA、file offset、IDA EA、load bias 及 maps 对应正确？明确定义且匹配参考点的 `base+RVA` 允许使用。（§2 §6–7）
- [ ] dlsym 的模块/符号与实际目标匹配？入口字节、架构、权限和跳板状态可核对？
- [ ] 重复 hook、被覆盖、安装/卸载顺序是否有证据，而非仅据 SIGSEGV 定因？

### 4.3 功能开关同步

- [ ] UI → 配置/旗标 → 实际分支的每一步有独立证据？跨线程同步协议正确？
- [ ] ON、OFF、恢复、授权失效路径均验证实际行为，而非仅验证数值置位？

### 4.4 边界条件

- [ ] 空/单/多对象、递归触发、不同对象类型、特殊场景分别测试？
- [ ] 对照基线、目标行为、关闭恢复和直接副作用有可比较记录？未测条件明示。

### 4.5 桩签名与虚方法（新增 hook / 改桩必查）

- [ ] 根据元数据、架构 ABI 和实际入口/调用点确认签名，不强制 CalcSig 单一工具。（§18）
- [ ] 返回值及整数/FP/聚合参数、byref、对齐、栈参数、隐藏返回缓冲区均匹配？
- [ ] this/MethodInfo/泛型或 invoker 隐含上下文核实？static flag 不足以推出通用参数槽数。
- [ ] 需要虚派发时解析实际 override；明确有意基类直调与虚调用的区别，缓存生命周期正确。（§19）

## 五、反作弊审查（合规与运行边界）

### 5.1 上报检测

- [ ] 测试是否在授权范围内，是否涉及第三方账号、线上数据或服务端约束？
- [ ] 记录可观察到的校验/拒绝响应和影响，不由退出信号推定保护机制或唯一根因。
- [ ] 无新增规避或作弊操作；未知服务端行为标 NOT PROVEN，不宣称客户端测试可证明无封禁风险。

### 5.2 数值合理性

- [ ] 数值符合目标测试契约及有效范围？不得将固定倍数、渐进增长或混入正常行为称作通用安全线。
- [ ] 异常结果与服务器响应分别记录，必要时停止受控测试，避免扩大影响。

## 六、审查执行模板

```text
代码审查 — [任务] [日期]
边界①：文件/函数、产物身份、直接影响面
边界②：调用契约 / 地址身份 / 对象生命周期 / 重入与并发
         每项 PASS / FAIL / NOT PROVEN / N/A（理由）
边界③：命中维度；构建类含输入身份/错误传播/输出身份
边界④（逐条声明）：
GATE: G1 可测试 / G2 运行 / G3 交付
CLAIM: 可被证据支持或反驳的具体声明
SCOPE: 版本/产物/架构/设备/场景/条件；未覆盖范围
EVIDENCE: 命令和退出状态 / 静态位置 / 日志 / 行为对照记录
VERDICT: PROVEN / FAILED / NOT PROVEN / BLOCKED
WHY: 证据能证明什么、不能证明什么
结论：当前门禁可否进入；需修复项；下一项最小验证
修后复查：修复点与直接影响面，更新的声明与证据
```

## 七、审查触发规则

以边界③为准，保留此节供旧链接使用。

| 改动/阶段 | 检查 |
|-----------|------|
| 新功能 | 相关维度全查，首次受控测试前 G1 |
| 改偏移 / 小改动 | 功能有效性及直接受影响项 |
| 改构建脚本 / 切游戏 | 输入身份 + 错误传播 + 输出身份 |
| 闪退 / 掉帧 | 稳定性 + 性能，候选根因与区分证据 |
| 功能失效 | 功能有效性与实际行为对照 |
| 装机前 | G1 + 用户协作/授权条件；不要求先有 G2 |
| 运行验收 / 交付 | 分别 G2 / G3；真机会话结束按工作区规则清理 |
