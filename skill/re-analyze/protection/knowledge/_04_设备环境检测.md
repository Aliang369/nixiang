# 知识库 04 · 设备环境检测（完整对抗链）

> 📍 `re-analyze/protection/knowledge/_04_设备环境检测.md`
> 🎯 校验「设备是不是被篡改/调试/模拟」的一整层。它不是校验包，是校验环境。核心原则：**别让特征被看见**，而不是见一个 patch 一个。

---

## 0. 总原则

环境检测的对抗不是「hook 掉检测函数」，而是**让检测读到的值本来就是正常值**。检测有几十个点分散在 Java/native，逐一 patch 是无穷尽的。正解：

1. 消除特征源（别装 frida、别落探针残留、KSU 隐藏 su）
2. 伪造读取结果（回灌 `TracerPid=0`、伪造 Build 特征）
3. 会话结束清理残留（铁律：`cleanup_device_re_residue.sh`）

## 1. Root 检测

### 特征（怎么认）
| 检测项 | 具体 |
|---|---|
| su 路径 | `/system/xbin/su`、`/system/bin/su`、`/sbin/su`、`/su/bin/su` 存在性 |
| busybox | `/system/xbin/busybox`、`/data/local/tmp/busybox` |
| Magisk | `magisk` 包名、`/sbin/.magisk`、`/data/adb/magisk`、init.rc 残留 |
| mountinfo | `/proc/self/mounts` 出现 `/system` rw、overlay |
| 测试签名 | 包 `test-keys` 签名 |
| SELinux | `getenforce` / 读 `/sys/fs/selinux/enforce`，返回 `Permissive` 视为异常 |
| 系统属性 | `ro.debuggable=1`、`ro.secure=0`（属性是全局，与包级 `test-keys` 签名区分） |
| 进程扫描 | `ps` / 枚举 `/proc` 找 `su`、`magiskd`、`frida-server`、`zygisk` 进程 |
| 设备指纹 | `/data/local/tmp/starry_magic` 之类公共资产被扫 |

### 对抗
- **KSU umount 隐藏**（本工作区已实战，多游戏）——隐藏 su/相关路径
- 别把工具遗留在 `/data/local/tmp`（铁律清理脚本）
- 设备指纹：星光公共资产放隐蔽路径，或跨包一致（经验：卡密设备指纹跨包一致）
- SELinux 保持 `Enforcing`，别为省事全局 `setenforce 0`（很多游戏的 root 判定直接读 enforce）
- 系统属性 `ro.debuggable`/`ro.secure` 用 magiskprops / KSU 属性侧写改回正常值

### 坑
- RootBeer 类（`libtoolChecker.so`）是 Java+native 双查，Java 层 hook 掉 Java 部分，native 部分仍死 → 必须 native 隐藏
- KSU 隐藏后仍有个别游戏扫 mountinfo/overlay → 需额外处理

### 状态
- ✅ RootBeer/libtoolChecker 已实战（`root-check.md`）
- ✅ ACE 残留污染扫描（雷霆/公主/终末地）

## 3. Frida 检测

### 特征（怎么认）
| 检测项 | 具体 |
|---|---|
| 端口 | 默认 27042 监听 |
| 文件 | `/data/local/tmp/re.frida*`、`frida-agent*.so`、`gadget*.so` |
| maps | `/proc/self/maps` 含 `frida`、`gum-js-loop`、`linjector` |
| 线程名 | `gmain`、`gum-js-loop`、`gdbus` |

### 对抗
- **本工作区铁律：别留 frida，优先自注入 Trace**（`libstarry_magic.so`）

- Florida 实测（2026-09-10 静态特征计数）：清了 gum-js-loop 线程名，但 `frida:rpc`/`frida-agent` 字串残留 → 上表「线程名/端口」初级档可挡，「maps/文件/D-Bus」类检测挡不住
- 反 frida 杀进程（如 nesec 可能反 frida）→ 换自注入

### 状态
- ✅ 多游戏已踩（ACE 扫 frida 特征、无悔 dump 需防反 frida）

## 4. ptrace / 调试器检测

### 特征
- 自己 `ptrace(PTRACE_ATTACH)` 检查能否 attach 自己（能 = 无调试，被占 = 有调试）
- 读 `/proc/self/status` `TracerPid`
- `/proc/self/mem` 访问被 EACCES
- JDWP：`ro.debuggable=1` 或应用自身 `android:debuggable="true"` 时，`/proc/self/status` 里 JDWP 线程 / `DdmHandleAppName` 可被检测
- 时间差：单步断点/逐行调试导致执行流耗时异常，校验方测「关键函数往返时间」超阈值即判调试

### 对抗
- **非 ptrace 注入**（自注入 Trace 走合法 so 加载链，不用 ptrace）
- `/proc/self/mem` 被禁（蜀汉传实锤 EACCES）→ 不能靠 ptrace 注入镜像，靠自注入
- 别开 debuggable 包跑真机调试（JDWP 一开就是满脸痕迹）

### 坑
- 蜀汉传实锤：ptrace attach → 游戏加速死亡 → 别用 ptrace 对抗反调试，陷入死循
- 反调试是通过「检测到调试」触发，而非「调试本身破坏」——先隐藏调试痕迹

### 状态
- ✅ 蜀汉传（ptrace 加速死亡、`/proc/self/mem` EACCES 已实锤）
- ⚠️ JDWP/debuggable 检测待验证；时间差检测 ⚠️ 未实测

## 6. 通用 Hook 框架检测（SandHook/EPIC/Pine/Dobby 等）

### 特征（怎么认）
| 检测项 | 具体 |
|---|---|
| 入口码比对 | 读目标函数首几字节，比对 `ldr x17,#imm`/`br x17`（类 clang 跳板）或 `0x94000000`（bl）与原始入口码，不一致即判 hook |
| 框架特征 | `SandHook` 的 `SHEnm`/`sh_entry`、`EPIC`/`Pine`/`Dobby` 的可执行映射段出现在 `/proc/self/maps` |
| GOT 重定向 | 比对 `dlopen`/`dlsym`/`__system_property_get` 等 GOT 表项与真实地址（走 plt 里的间接跳转），被改即判 hook |
| 内存页属性 | 扫描被 hook 函数的页，出现「匿名 r-x 页 + 原页被 mprotect rwx」的异常组合 |
| 回调栈 | `backtrace()` 看调用栈里出现 `hook`/`hook_entry`/`stub` 命名帧 |

### 对抗
- **hook 必调原函数**（铁律 6）——否则改代码段 + 入口码比对双重暴露
- 优先「改数据不打代码」：旗标门控改 BSS/.data，不动函数入口码（雷霆实战）
- 别在目标进程加载 Dobby/SandHook 等可识别框架（用自注入 + 手写等长跳板，尽量用 `plt` 层而非函数入口）

### 坑
- 入口码比对是「有 hook 特征就弹」的布尔判定，patch 比对函数本身也会暴露（它自己就是被 hook 的目标）
- 「调原函数」能躲过跳板被抹掉最明显的特征，但仍可能被 GOT/内存页二级检测抓到 → 数据区旗标是更干净的替代

### 状态
- ✅ 旗标门控（雷霆战机）
- ⚠️ SandHook/EPIC/Pine 显式检测待验证（本工作区自注入 Trace 未命中显式框架检测）

## 7. inotify / 文件监控 + 时间差

### 特征（怎么认）
- 游戏里 `inotify_add_watch` 监控 `/data/local/tmp`、`/sdcard`、`/data/data/<pkg>` 出现探针文件即触发
- 定时轮询某目录 mtime / 文件列表，发现新增即判环境异常
- 关键操作时间差超阈值（如加载某 so 耗时明显 > 正常值）判 hook/单步

### 对抗
- 探针文件别落在被监控的公共目录；用隐蔽私有目录
- 用完即删（cleanup 脚本）；别留日志/Dump 镜像在 `/data/local/tmp`
- 时间差检测无法「伪造成正常」——只能避免单步调试，改用行为 hook

### 坑
- inotify 检测和残留污染（§8）会叠加：文件出现 → 判环境异常 + 残留污染清单命中 → 双重死因

### 状态
- ⚠️ inotify 检测待验证（`_02` 块6 提过，本工作区未实锤命中 inotify 具体 watch 点）

## 8. 设备残留污染（ACE 特有，重点）

### 特征
- ACE 扫 `/proc/self/maps` + 特定文件路径，发现残留工具/日志/探针 → 判定篡改环境
- 雷霆经验：`ace3-14` 磁盘旁路全败，根因之一是残留污染

### 对抗（铁律）
- **每次真机会话结束/暂停必跑** `04_scripts/_common/cleanup_device_re_residue.sh`
- 残留物清单：`/data/local/tmp` 工具、探针 APK、dump 镜像、Florida server、日志文件
- 设备指纹残留：`/data/local/tmp/starry_magic`（星光公共资产）注意隐蔽

### 状态
- ✅ 雷霆战机（残留污染 ACE 教训已沉淀于`官方原包_ACE崩溃与过检候选`§13-14）

## 9. 对抗链总结（由高到低优先级）

```
1. 消除源（不装 frida/ptrace/工具残留 → 让环境本身干净）
2. 隐藏特征（KSU umount su、隐蔽公共资产路径、magiskprops 回灌属性）
3. 伪造读取（TracerPid=0、Build 值回灌、/proc 伪造）
4. 会话清理（cleanup 脚本，铁律）
```

**核心认知**：环境检测是「对不对得上正常设备」的布尔判断，不是「单个点 patch 就过」。逐点 patch 是无穷尽的；让特征不存在才是一劳永逸。
