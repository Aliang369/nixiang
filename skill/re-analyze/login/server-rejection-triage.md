# 服务端登录拒绝分流

> 路径：`skill/re-analyze/login/server-rejection-triage.md`
> 适用：登录页能进、SDK 显示成功，但游戏登录服务器返回错误码，或用户描述像“设备被检测 / root 被检测 / 数据异常”。

---

## 先做三查，再查 root

登录失败时先区分四类来源，禁止先改设备环境或直接猜 root 检测：

1. **服务端返回码**：从游戏自有日志、SDK 回调、登录服务器响应中取原始码。UI 文案不是原始证据。
2. **客户端文案存在性**：在 DEX、`resources.arsc`、assets、IL2CPP metadata、热更脚本中按字节搜用户看到的文案。搜不到时，倾向服务端下发。
3. **账号 / 设备 / 环境矩阵**：至少做同账号换设备、同设备换账号、同设备原版包 / 改签包三类对照。
4. **最后才查 root / 模拟器 / Hook 检测**：只有前 3 步指向客户端环境检测，才进入 `protection/root-check.md` 等页面。

## 最小判定流程

```text
登录失败
  |
  |-- 有服务端错误码？
  |      |-- 有：先记录码、时间、账号、设备、channel、包签名身份
  |      |      再做同账号换设备 / 同设备换账号
  |      |
  |      `-- 无：查 SDK 回调、登录页状态、网络层响应，不先归因 root
  |
  |-- 客户端是否有同文案？
  |      |-- 有：定位文案消费者和触发条件
  |      `-- 无：服务端下发概率高
  |
  |-- 同账号换干净设备能登录？
  |      |-- 能：账号级排除，转向设备/环境/服务端设备指纹
  |      `-- 不能：账号、渠道、服务端策略优先
  |
  `-- 只有客户端环境检测候选仍成立，才查 root / 模拟器 / Hook / 调试检测
```

## 设备环境实验纪律

在确认是设备/环境级问题后，每次只改一个变量，并记录：

| 变量 | 原值 | 本次值 | 恢复命令或前置快照 | 结果 | 是否已还原 |
|---|---|---|---|---|---|
| `su_compat` / `ro.debuggable` / BL 属性 / `install_id` / `android_id` | 待填 | 待填 | 待填 | 待填 | 待验证 |

- 修改前先保存原值或快照；修改后必须验证恢复。
- 不在同一轮同时改多个变量后宣称根因已定位。
- 涉及设备属性、标识文件、卸载/清数据时，按 AGENTS.md 的授权规则执行。
- 服务端拒绝若是查表式快速返回，优先考虑账号/设备指纹/策略表，不优先做实时 root 隐藏。

## 输出模板

```text
CLAIM: 登录失败发生在 <SDK / 客户端 / 服务端> 阶段
SCOPE: 游戏/版本/包名/设备/账号/渠道/时间
EVIDENCE: 原始返回码、日志行、客户端文案搜索、对照实验
VERDICT: PROVEN / REFUTED / NOT PROVEN
WHY: 证据能证明什么，不能证明什么
NEXT: 最小区分实验
```

## 潮汐守望者案例（2026-09-30）

- 用户描述：`检测到您的游戏数据异常，您的角色被限制登录`，第一反应像 root 或客户端检测。
- 实测：官方原版 6/6 次登录均为 `QuickSDK onLoginSuccess` 后 `Login_Auth` 收到服务端 `-37`。
- 客户端文案搜索：DEX、resources、assets、`liblogic.bytes`、`global-metadata.dat` 均 0 命中，提示由服务端下发。
- 对照：同账号在未 root 设备可登录，原设备不行，账号级排除。
- 环境实验：`su_compat`、`ro.debuggable`、BL 属性、`install_id`、`.gp_uuid`、`.DNA_` 均排除，仍 `-37` 后全部还原。
- 剩余候选：`android_id`（Android 8+ 按 APK 签名派生）或服务端自算设备指纹。
