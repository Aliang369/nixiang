## 2. ★改包形态：不是 Lua 替换，而是「官方壳 + 远程 WebView 菜单 + 运行时补丁表」

**崩坏3 的改法与前作伊莫完全不同**：伊莫是把 Lua 载荷明文塞进壳 `.rodata` 整份替换 `Time.lua`；崩坏3 是 **native 补丁**——壳在运行时维护一张「目标 so + 偏移」补丁表，直接改 `libil2cpp.so` 里的 IL2CPP 生成代码。

**关键事实：这张补丁表在 APK 里查无明文。**
- 全 APK 逐条目扫描：`0x5F16228` / `0x5F156A8` / `0x5F16828`、菜单域名 `menu-1255602259`、`game/38.html`、`您好`（免责声明）**均 0 命中**；表尾的 tag dword `b6 66 00 00` / `62 66 00 00` 也 0 命中。
- 表只出现在**壳进程的匿名 rw-p 内存段**（dump `seg_23_rw-p_7349938000.bin`，155,648 B）。
- ⇒ 补丁表是**运行时生成/解密/下发**的（很可能随菜单一起由 `menu-1255602259.file.myqcloud.com` 按 `game_id=38` 下发，或由壳在内存里就地解密后组装）。**此项为推断（待验证）**，但「APK 内无明文」是实测事实。

## 4. ★三个抓点：`libil2cpp.so` 补丁偏移

Shell 维护的补丁表中，指向 `libil2cpp.so` 的**偏移共 3 个**（与用户点名的 3 项功能数量一致；**一一对应关系待与原版对照后确认**）：

| # | 偏移值 | 解释 | 所属函数起点（文件偏移） | 函数体量下限 |
|---|---|---|---|---|
| 1 | `0x5F16228` | **文件偏移** | `0x5F16180` | ≥ 0xA8 |
| 2 | `0x5F156A8` | **文件偏移** | `0x5F155D8` | ≥ 0xD0 |
| 3 | `0x5F16828` | **文件偏移** | `0x5F16270` | ≥ 0x5B8 |

**偏移口径判定（实测）**：把 3 个值当**文件偏移**读 `libil2cpp.so` 时，三处都落在**连续、自洽的 ARM64 代码**中，且能向前找到正规函数头（见上表）；把同一个值当**虚拟地址**（`vaddr − 0x4000`，本 so 的 `addr = file_off + 0x4000`）去读时，`0x5F156A8` 对应字节**根本不是可解码代码**（capstone 无输出），另两处落在疑似数据区。⇒ **判为文件偏移**（`libil2cpp.so` 内有三个 PT_LOAD，`.text` `addr=0x2172cc0/off=0x216ecc0`、`il2cpp` `addr=0x24d38e0/off=0x24cf8e0 size=0xdead620`，两段 `addr−off` 均 = `0x4000`）。**此判定为强证据支持，最终口径待原版对照复核。**

三个偏移**都落在名为 `il2cpp` 的自定义段内**（`0x24cf8e0..0x10380f00` 文件范围，被 `__start_il2cpp=0x24d38e0` / `__stop_il2cpp=0x10380f00` 夹住）＝ **IL2CPP 生成的托管方法代码**，符合「改玩法逻辑（秒杀/血量/暴击）」的预期。

## 5. ★反检测 / 校验 / 上报拦截（用户点名要看的）

命中字符串：`A64_HOOK`、`mprotect failed with errno = %d, p = %p, size = %zu`、`ref_idx must be less than or equal to current_idx!`、`failed to allocate trampoline!`、`/proc/self/maps`、`libEGL.so`。

### 5.3 检测判据点（`seg_34_rw-p` 匿名 rw，16,384 B，77 串）

`/proc/self/maps`、`BW_MEMORYTOOL`（**内存修改器特征名**）、`libtprt.so`、`libtersafe2.so`、`tersafe`、`signatures`、`[Landroid/content/pm/Signature;`、`libEGL.so`、`eglSwapBuffers`、`android/widget/Toast`、`(Landroid/content/Context;Ljava/lang/CharSequence;I)Landroid/widget/Toast;`。

⇒ 检测面覆盖：**读自身 maps（找注入 so）**、**扫内存工具特征（BW_MEMORYTOOL）**、**取 APK 签名数组（`Signature[]`）做校验**、**`libEGL/eglSwapBuffers` 画面层检测**（外挂叠加层常用点）、**Toast 弹提示**。

### 5.4 签名与重签名处理（`seg_30_rw-p`，16,384 B）

- `%s/SpeedUpCCH.dat`：加速/风控缓存文件（配套组件）。

### 5.5 壳自身

- `libSDKloading.so`（3,893,752 B，md5 `f2122937a47ac14577826b43a8b54bc3`）＝ **游戏进程实际加载的壳 so**（pid 26210 maps 可见，与 `libil2cpp.so` / `libunity.so` / `libmain.so` / `libulua.so` 同列）。
- `libSDKloading.so` 在磁盘上**不含**菜单域名、免责声明、偏移表、tag dword（全 0 命中）⇒ 壳的菜单/补丁配置**运行时解密/下发**，静态改 .rodata 不可直接定位（与伊莫的明文 .rodata 完全不同）。

### 5.6 「上报拦截」现状

- **未发现**斌哥侧有独立的「上报拦截」模块（无「拦截 RPC / 屏蔽上报」类字符串命中）。
- 更可能的真实姿态是：**改包依赖 `Signature[]` 伪造（MT 签名杀手）通过官方 ACE 的签名校验**，加上 ACE 自身在改包上仍会运行/上报，而改包只改玩法数值 ⇒ 风险由官方 ACE 侧承担。**此项为推断（待验证）**；要证伪/证实需在真机上抓 ACE 的网络上报与 `libtersafe2` 的决策日志。

## 8. 星空版移植建议（等原版到手后执行）

1. **不要在改包/壳上做文章**：`libSDKloading.so` 的配置运行时解密，静态改 .rodata 不可行；走星空自己的注入路径。
2. **移植的最小闭环（3 步）**：
   - ① 拿到官方原版 `com.miHoYo.enterprise.NGHSoD` 的 `libil2cpp.so`，与斌哥包同一 so 做 **diff**，直接定位斌哥改动的 3 处字节（若斌哥包里 `libil2cpp.so` 未被重新编译，改动就是那 3 个偏移处的少量字节）。
   - ② 对照本文件 §4 的 3 个偏移（文件偏移口径）在**原版**里的对应函数（`0x5F16180` / `0x5F155D8` / `0x5F16270` 附近），确认函数语义与「秒杀/血量/暴击」的对应。
   - ③ 用星空框架在这 3 个函数上做运行时 hook/直写，**不硬编码偏移**（原版与改包版本可能不同），改用「代码特征串/函数签名」定位后再改写（`hook-rules.md` §24 指纹铁律：禁写死会被混淆改名的短标识符）。
3. **ACE/TSS 必须当作既定环境处理**：`libtersafe2.so` + `libtprt.so` 会做 ptrace/root/模拟器/inline-hook/签名/maps 检测并上报。移植时**不要**引入 frida（ACE 命中即杀）、**不要**动 `libEGL/eglSwapBuffers` 叠加层特征；优先选**不改签名即可覆盖**的装机方式。
4. **RootBeer（`libtoolChecker.so`）是官方库**，两包同 md5 —— 移植**不要**试图删它（删了反而与官方不一致）。
5. **功能优先级建议**：先做「秒杀」（单点数值/判定，最易验证）→ 再「刀刀暴击」（判定/倍率）→ 最后「无敌（超级血量）」（往往是最长的一条链路，且最可能触发服务器/ACE 侧校验）。
6. **验收走 L1/L2/L3**：先 L1 静态核对 + L2 机器自检（ACE 场景下模拟器可能不可用，需真机），人工只在 L3 出现。
