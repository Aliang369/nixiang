## 4. 漏洞面清单（静态确认）

### 4.1 免广告（广告奖励直接客户端发放）

- `MenuAdTvUI.ConfirmButtonClick()`：看广告成功后 `SoulStoneCount += 30`，每日一次。
  - Hook 点：`SDKLinker.ADLinker.PlayRewardedVideo` 直接调用 successCallback，或直接调 `Archive.PlayerArchive.SoulStoneCount += 30`。
- `ReviveWindowUI.AdDoubleConfirmClick(true)`：**在广告实际播放前**就设置 `isReborn = true` / `hasAdReborn = true` 并发复活；广告只是战斗结算时才补播。
- `GameProcess` 结算中的广告仅做埋点，不发奖。
- 广告拉取配置在 distroConfig 中明文可改（TradPlus appid / adId）。

### 4.2 免支付购买

- `IapProductIdEx.OnPurchasesSuccess(string id)`：根据商品 ID 字符串**无条件发奖**，包括：
  - `zhmr_hero_*` → `SetHeroUnlock(RealMoney)` 解锁英雄；
  - `zhmr_heroskill_*` / `zhmr_herostyle_*` → 解锁技能/风格；
  - `zhmr_jew_soulstone_988` 等 → `SoulStoneCount += 988`；
  - 皮肤、礼包、宠物、战令、鉴定券等同样直接入账。
  - 防刷只有埋点 `fake_receipt_cheat_detected`（统计触发/成功频率），没有硬性阻断。
- Android 侧 `BasePayAgent.sendPaySuccess(orderId, productId, "")` 直接把结果发给 Unity，Java 层不做票据/签名校验（真正的校验在凉屋 `Payment` 服务端 ClaimOrder 流程）。
- Frida 可直接调用 `IapProductIdEx.OnPurchasesSuccess("zhmr_jew_soulstone_988")` 或伪造 Java `sendPaySuccess` 回调。
- 新版服务端流程（`com.chillyroom.services.accounts`）：`Payment` 走 `CreateOrder → CallNativePurchase → ClaimOrder`，`ClaimOrder` 后调用 `callConfirmPaySuccess`；本地发奖点仍是 `OnPurchasesSuccess`。
- `StandaloneAPIManager.OpenConsumableIapPage`：standalone 构建下 `resultStr == "success"` 直接 `OnPurchasesSuccess`。

### 4.3 无敌 / 满血 / 锁血 / 秒杀

核心类：`Character` / `Body` / `Skill`。

- 无敌：
  - `Body.SetInvincibleTime(float)` / `Body.isInvincible` / `invincibleCountdown` / `invincibleMultiBool`。
- 免伤 / 锁血：
  - `Character.isBlockDamage`（setter 公开，为 true 时 `GetDamage/GetHealthDamage` 直接返回）；
  - `Character.LockHealthMultiBool`（`isLockHealth` 时 `GetDamage` 后把血钳制在 `healthLockValue`）；
  - `Character.currentHealth` setter 可任意设值（死亡状态除外）；
  - `Character.ResetHealthAndShieldToMax()` / `FullChargeHealth()`。
- 秒杀：
  - `Character.GetDamage(DamageMessage)` / `GetAttack` / `GetDotDamage` 全在客户端计算；
  - `Character.uDamage`（`USystem` 乘区）可整体放大伤害；
  - 直接 hook `Character.GetAttack` 把 `finalDamage` 改为极大值，或对敌人调 `ResetHealthAndShieldToGhost()`（0.1 HP）。
- 单机/本地房没有服务端数值校验；联机房内 `CmdSyncGetAttackListAdd` 等命令由房主客户端计算。

### 4.4 技能 CD

- `SkillManager.TryAddSkillExecution(SkillFlagInfo info, bool ignoreCd = false)`：已有 `ignoreCd` 参数，Hook 后传 `true` 即可无视 CD。
- `Skill.countdown`（`Ive.Countdown`）：字段 `interval`、`lastFlushTime`，方法 `CountDownOverRightNow()` / `TimeJump()`。
- `Character.coolDown`：全局 CD 倍率，`properties["Cooldown"]`；`CurMinCoolDown = 0.2f`。
- `Body.mainSkillCooldown / exSkillCooldown / weaponSkillCooldown`（`MultiFloat`）可直接清零。
- `Skill.SetCooldownFreeze(obj, val)` 可冻结 CD。

### 4.5 角色 / 皮肤 / 技能 / 风格解锁

- **（2026-08-15 实装）选人全亮**：读静态 `Archive.heroArchiveDic`，直写各 `HeroArchive._isUnlock`。勿依赖堆扫描数量；勿对 Archive 字段一律 +8。详见 `全角色解锁_dic直写_20260815.md`。
- `Archive.HeroArchive.isUnlock` setter：设 true 后可能顺带解锁技能/默认风格（静态笔记）；动态上优先直写字段，避免错误线程 `runtime_invoke` 卡死。
- 公开方法：`SetHeroUnlock(UnlockMethod, DateTime)` / `SetSkillUnlock` / `SetStyleUnlock` / `PlayerArchive.SetMenuSkinUnlock` 等（方法在，invoke 成本高，角色解锁非必需）。
- `GiftPackTools.UnpackGiftJson(json)`：静态可见；现热更下 Frida `runtime_invoke` 易失败，不作角色解锁主路径。
- 资源存储 `EncryptValue`：`_showValue`、`mValue`、`encryptKey` 三个字段，校验 `_showValue == mValue ^ encryptKey`；内存修改需同步三字段；云存档上传可能触发 `CheckForbid`。

### 4.6 存档

- 本地存档：`CryptoPrefs`（加密 PlayerPrefs）保存；字典类用 `BinaryFormatter → Base64`（`PlayerPrefsUtility`）。
  - 关键键：`EXBarmaterials`、`EXHeroSkinEquip`、`EXSixPowerConfig`、`MenuSkinUnlock`、`EXAsuraPowerPointInvest`、各 `ResourceTag` 等。
  - `CryptoPrefs` 实现在被裁剪的 corekit 程序集，静态未见实现，动态阶段用 Frida hook `CryptoPrefs.SetString/Save` 抓明文与密钥。
- 云存档：`CloudSaveClient`（`Rpc_save_upload_binary` / `Rpc_save_download_binary2`）。
  - 上传：`gzip(zlib) 压缩 gameData` → `StringHash.Hash(compressedBytes)` → 连同 uid/channel/deviceId/`GetSign()`/extra/version 上传。
  - 下载：服务端返回压缩数据 + 期望 hash，客户端 `StringHash.Hash` 比对。
  - 设备绑定：`CheckSaveMac` / `UnBindMac2`，限制换绑次数。
  - 签名盐已硬编码（见第 3 节），但由于 RPC 还带 Bearer token，完整伪造需先取得会话 token；客户端本地内存改完再上传时，hash 由客户端自己算，服务端主要靠 `CheckForbid` 与字段语义校验。
- `ZhmrCloudSaveArchive` 是纯 JSON 可序列化结构，`soulStoneCount / blueStoneCount / redStoneCount` 等直接明文可改（配合 `CloudSaveHash` 重算）。

### 4.7 反作弊现状（薄弱点）

- `EncryptValue.IsLegal()`：唯一强校验，被触发后 `isCheated = true` 并 `Application.Quit()`；但三字段可同步伪造。
- `isCheated` 实际影响面小：仅 `EntryReplace`、`MaterialExchangeUI` 等少数功能拒绝继续。
- `SignatureVerify.IsCorrect()`：用 Java `Signature.hashCode()` 与常量 `1525265668` 比较，Frida 可秒绕。
- Java `RootOrSimulatorDetectUtil`：只查 `/system/xbin/su`、`/system/app/Superuser.apk`、`Build.TAGS`；Magisk 隐藏 root 不触发。
- 支付防刷只有埋点（`fake_receipt_cheat_detected`）。
- 未发现 Frida/调试器主动检测；`debuggable=true` 降低动态分析门槛。

### 4.8 配置 / 供应链风险

- `distroConfig.bytes` 用固定 DES 密钥加密，解密后含账号体系 `accessKeySecret` 等敏感参数。
- GameLogic.dll 从固定 CDN 明文下发，若 CDN/网关被控制或证书校验被绕过，可整体替换游戏逻辑。
- 内置 SRDebugger / SROptions 调试组件，需动态确认是否可通过手势唤出调试面板。

## 6. 结论（静态）

该包为“客户端可信”设计：发奖、伤害、CD、解锁、礼包均在客户端直接落账，服务端校验覆盖面有限（支付 ClaimOrder、云存档 MAC/hash/CheckForbid）。结合 `debuggable=true`、硬编码密钥、弱反作弊，免广告、免支付、无敌、秒杀、零 CD、全解锁、改档均具备明确的可利用路径，具体可利用性需真机动态验证后定级。
