## 1. 怎么找到的（思路）

问题拆成两句，而不是先押「假支付 / 解密热更 DLL」：

1. **选人界面亮不亮，最终读的是什么？**  
   先枚举运行中已加载的类/方法（轻量 Frida，**禁止全堆扫描**），确认存在：
   - 静态类 `Archive`，字段 `heroArchiveDic`
   - `HeroArchive._isUnlock` / `get_isUnlock` / `set_isUnlock`
2. **对象够不够？**  
   读 `heroArchiveDic`：`count≈43`，Entry 里已是完整 `HeroArchive` 引用。  
   → 「只有 7 个角色有存档对象」这条旧结论是错的；缺的不是对象，是 **`_isUnlock` 标志**。
3. **怎么改最简单？**  
   对 dic 内每个 `HeroArchive` **直写 `_isUnlock=1`**（可选 `isUnlockSecondSkill=1`）。  
   不调 `SetHeroUnlock` / `OnPurchasesSuccess` / `UnpackGiftJson`（这些经 `il2cpp_runtime_invoke` 易空指针或卡死）。  
   选人界面**当场全亮且可选**。

验证顺序：只读 dic → 只写字段（不 invoke）→ 看 UI → 再写入菜单 Tick。

## 2. 有效做法（当前正式方案）

| 项 | 内容 |
|---|---|
| 入口 | `Archive.heroArchiveDic`（静态字段，`il2cpp_field_static_get_value`） |
| 布局 | IL2CPP `Dictionary`：`entries@+0x18`，`count@+0x20`；Entry stride `0x18`（hash/next/key/value*） |
| 写入 | `HeroArchive` 对象上 `_isUnlock`；offset 用 **`il2cpp_field_get_offset` 原值，不要再 +8** |
| 实测 offset | `_isUnlock@32`（旧文档写的 `@40` 是错误地加了 HybridCLR bias，会踩到 `level`） |
| 菜单行为 | 开关打开时在游戏 Tick 线程直写；不依赖假支付、不解密 DLL |

落盘：用户侧清档复测后确认**角色解锁可用**；是否每次都会进 CryptoPrefs 以实际存档为准，**不以「必须不落盘」为约束**。菜单侧仍按「开着就重放」实现，关开关不主动回滚。

## 3. 之前文档为什么没找到？

| 旧路线 / 旧结论 | 问题 |
|---|---|
| 堆扫描 `HeroArchive` 只找到 ~7 个 | 扫的是匿名堆里 klass 命中；**字典里还有大量未扫到的实例**。把「扫到几个」当成「游戏只创建了几个」。 |
| `HeroArchive` 字段 +8 bias → unlock@40 | Character 战斗字段可能要 bias；**Archive 热更类实测 offset 已是真偏移**。写错字段导致旧实现不可靠。 |
| 假 `sendPaySuccess` / `OnPurchasesSuccess` | Java 层有日志 ≠ C# 发奖；现热更里 `runtime_invoke` 该路径常 **AV 0x0**。文档一度写成「全量成功」，后虽更正但仍把精力耗在支付链。 |
| `GiftPackTools.UnpackGiftJson` / `SetHeroUnlock(UnlockMethod, DateTime)` | 方法存在，但从非主线程 / 错误装箱 invoke 会崩或卡死；不是「没有 API」，是 **调用成本高且不必要**。 |
| 解密 `GameLogic.dll` 改初始化 | 目标是「创建缺失的 HeroArchive」。dic 里对象**已经齐了**，此路对「全亮选人」是弯路（见 `战魂铭人_3.4.0_热更DLL解密任务.md`，解锁场景应降级）。 |

一句话：旧文档卡在「怎么发奖 / 怎么建档」，真实瓶颈是「**别扫堆，去读 dic，直写 bool**」。
