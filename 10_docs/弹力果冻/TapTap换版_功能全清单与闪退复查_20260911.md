## 3. 需求②：旧包闪退复查（核心）

### 3.1 先把「三个血功能」的耦合关系讲清楚

用户直觉「三个功能写的（血/伤害）有问题、代码有冲突」——**方向对，机制的归因要修正**：

```
        [ 秒杀 ]   [ 无敌 ]   [ 全屏秒杀 ]
             \        |        /
      (1) 同一份 g_playerEids / g_enemyEids 敌我缓存
             \        |        /
      (2) 同一个刷新门控 NeedDmgPatch() = kill||inv||aoe
             \        |        /
      (3) 同一条 HybridCLR 跳板 0xBAAB0C
             \        |        /
   RefreshBattleCache()   ← 跑在未 attach 的 mod 线程，5 次/秒
```

- 三者**不是互相打架**，而是**三者共同把 `NeedDmgPatch()` 拉成 true**，于是 `Tlgd_Tick` 每 tick 都调 `RefreshBattleCache()`（`TlgdMod.cpp:874-875`）。
- **只有无限技能 ON 时** `NeedDmgPatch()=false` → 缓存刷新降到 `t%4`（1.25 次/秒，`TlgdMod.cpp:874`）。
- 所以「开血三功能 → 崩得勤；只开无限技能 → 相对稳」在**代码上是有解释的**，不需要假设三者逻辑冲突。

**真正的「冲突」有三处（会造成表现诡异，不是必崩）**：

| 冲突 | 位置 | 后果 |
|------|------|------|
| 无敌分支**优先于**秒杀分支 | `PatchHpHandle` L622 先判 inv，L630 才判 kill | 同一对 atk/vic 同时命中两条规则时以无敌为准；配合 R-4 撕裂缓存 → 该秒杀的没秒、该免伤的没免 |
| **全屏秒杀隐含单发秒杀** | `WantKillStrike() = g_kill \|\| g_aoe`（L278），`PatchHpHandle` 用的是 `WantKillStrike()` 而不是 `g_kill` | 用户只开「全屏秒杀」，普通攻击也变成一击必杀（L630-L637）——**与 UI 语义不符** |
| 无敌自伤式实现 | `WriteI64Arg(handle, kOffBeAttacker, 0)`（L623） | 旧文档自己写了「orig 内 `Clamp(dmg,1,…)`，写 0 仍掉 1 血」——**这条路本来就没写对**，且把非法 victim 抛给 orig |

### 3.3 逐条展开（关键三条）

#### R-1（最高）未 attach 的 mod 线程访问热更托管对象

```cpp
// TlgdMod.cpp:508-544，由 Tlgd_Tick(:874) 在 mod_thread 上调用
static void RefreshBattleCache() {
    void* mgr = GetBattleMgr();                     // → get_Stuff() 托管方法 + StaticRefField 回退
    void* pl  = g_findTeam(mgr, TEAM_PLAYER, false, g_miFindTeam);  // → FindBattleUnitByTeam 托管方法
    void* el  = g_findTeam(mgr, TEAM_ENEMY,  false, g_miFindTeam);
    ...
}
```

- `g_getMgrStuff/g_findTeam` 是 `MethodPointer(MethodInfo)`，即热更（解释器）方法入口；`GetBattleMgr()` 的兜底还是 `il2cpp_field_static_get_value`。
- 线程是 `pthread_create(&tid, nullptr, mod_thread, nullptr)`（Main.cpp:2339）创建的**裸 pthread**，全工程没有 `il2cpp_thread_attach` 调用（只有声明 `Il2CppApi.h:46`，被 `ZhmrMod/Archero2Mod/EndfieldMod` 使用）。
- 工作区已有两条**同名机制**的实锤：
  - `战魂铭人`：「il2cpp_init Dobby 门控：mod 线程等引擎 init 完成再 **attach**+探测，根因 = **Boehm GC 未知线程 abort**」
  - 铁律四：「**未 attach 时高频 `field_static_get_value` 会随机 SIGSEGV**」
- **为什么表现为「经常」而不是「每次」**：GC 只在特定时机回收、`Thread::Current()` 只在部分调用路径被解引用、线程栈布局随机 → 典型概率型崩溃，与玩家反馈一致。
- **修复**：`mod_thread` 启动后 `api.thread_attach(api.domain_get())` 一次（参考 `EndfieldMod.cpp:384-385`）；**更彻底的做法是把缓存刷新移回游戏线程**（见 §3.5）。

#### R-2/R-3/R-9 对热更方法做 runtime_invoke（铁律二直指）

```cpp
// TlgdMod.cpp:567-581
static void InvokeHpHandle(int64_t atkId, int64_t vicId) {
    DamageHandleBlob blob{};                 // ← 栈上自造 48 字节
    blob.finalDamage  = kKillDmg;
    blob.attackerID   = atkId;
    blob.beAttackerID = vicId;
    void* args[1] = {&blob};
    void* exc = nullptr;
    api.runtime_invoke(g_miHpHandle, srv, args, &exc);   // ← exc 丢弃
}
// 由 AoeSweep(:583-596) 在 hook 内对 g_enemyN 个敌人**循环调用**
```

三重风险叠加：

1. **铁律二**：`g_miHpHandle = GetMethod(FindHotfix("BattleServer"), "HpHandle", 1)` = 热更解释器方法，`runtime_invoke` 它正是经验卡记录的崩溃形态（tombstone `#0-9 libil2cpp 解释器 / #10-12 我方线程`），且「**批量**的后面崩」——`AoeSweep` 就是批量。
   *诚实边界*：本处调用方是**游戏线程**（在解释器 dispatch 内），比经验卡的「外部线程」情形轻一档，因此**不能断言必然复现**；但经验卡记录的另一半特征（「第一个生效、批量的后面崩」）恰好就是 `AoeSweep` 的形态，而下面第 2、3 条风险与该线程无关。
2. **自造值类型**：`il2cpp_runtime_invoke` 按参数**元数据尺寸**从 `params[i]` 拷值。blob 只有 48 字节，若真实 `DamageHandle` 更大（或有引用字段），就会**读越栈帧**/把垃圾或 null 当对象指针交给 `HpHandle` → 在解释器里解引用 → SIGSEGV。旧探针记录「finalDamage + **32bit** entityId」与代码里 8 字节字段布局**互相矛盾**，说明真实布局从未被证实。
3. **`exc` 不检查**：`HpHandle` 若抛托管异常（对不存在的实体/错状态调用很容易抛），异常被留在挂起状态、代码继续跑 → 在后续任意 il2cpp 调用点被 raise → 直接 abort。

**修复方向（择一，不建议继续用 invoke）**：
- (a) **数据优先**（hook-rules §21）：无敌/免死/属性类改为 Tick 直写字段维持，零 hook、零 invoke；
- (b) 若必须行为化：在跳板内**原地改** DamageHandle 字段（不 invoke），全屏用「同一 DamageHandle 的伤害放大 + 游戏自身范围逻辑」而不是手工铺场；
- (c) 真的需要调 `HpHandle` 时：**必须**先反编译 hotfix 拿到 `DamageHandle` 完整定义与 `HpHandle` 签名，按真实尺寸构造，并检查 `exc`。

#### R-4 缓存快照撕裂（会把功能打到玩家身上）

```cpp
g_playerN.store(pn);                       // ← 先发布数量
for (...) g_playerEids[i].store(...);      // ← 后写槽位
```

游戏线程在两者之间读到的组合是**新数量 + 旧内容**（上一波/上一场的 eid）。后果直接体现在 `IsConfirmedPlayerStrike()` 上：一个**敌人→玩家**的伤害，可能因为陈旧槽位被判定为「玩家在打敌人」，于是：

- 秒杀分支把**玩家受到的伤害**写成 `kKillDmg` → 秒死（若同时没开无敌）；
- 无敌分支在该队友/召唤物身上 `vic=0` → 输出被吞。

**修复**：写入顺序反转 + 版本号/发布协议（写完整槽位 → release store `N` → 读侧 acquire load `N` 后再读槽位），或干脆双缓冲 + 世代号。**修 R-1（把刷新移回游戏线程）后，R-4 自动降级为同线程无竞争**——这也是把 R-1 和 R-4 一起修的理由。

### 3.4 区分实验矩阵（不建议直接猜，按此定因）

把三功能与 nocd 分开跑，观察崩溃率与日志；**必须先在正式 so 打开 TLGD_TRACE（修 R-12）**，否则跑完也拿不到证据。

### 3.5 修复方案（按依赖顺序，共 6 步）

### 4.1 旧版到底漏了什么

旧文档 `星光落地_2.4.0` 的「反作弊」一节全文只有 4 条且**几乎无证据**：

```
[✅] 服务端校验未证实（中危：伤害/清图可能上报）
[✅] 无已知 addCheat 旁路需求
[✅] 与战斗同批
[✅] 数值用 1e8 级非 INT64_MAX
```

对照工作区标准（`anti-ban-analysis.md` 的逐游戏检测面表、迷雾大陆 6 条上报面 R1-R6、`anti-cheat-pattern.md` 三种模式），**至少漏了 3 类共 10 项**。

> **先纠正旧文档最要命的一条结论**：`星光落地_2.4.0` 写「服务端校验**未证实**」。2026-09-11 联网调研找到**官方自己发的封号公示**（2019-11-23《近期封号名单公示》、2021-06-18《外挂封禁名单公示》、《3月11日数据异常账号封禁名单》），原文口径是「不断完善反外挂系统及外挂检测……检测到游戏数据存在**异常修改**的玩家，已**永久封禁**」「经游戏**后台数据核查**……使用过外挂」。再加上**无尽森林赛季排行按名次发奖**（1-3 / 4-300 / …）、**世界 Boss 有成绩**——**服务端/后台核查是已被官方承认的事实，不是"未证实"**。旧结论应升级为「**存在，面待定位**」，并据此把 R1/R2 提到最高优先级。

最严重的三项遗漏：

1. **签名校验面完全没查**。旧文档只记录了 `SignSpoof` 用了 4399 证书，**没有**去核实游戏自身/渠道 SDK 是否读签名（迷雾大陆的教训正是「旧文档写『游戏自身无 Java 签名校验』，后来发现 `SignCheck`/`signPrint` 把 SHA-1 塞进每个平台请求」）。
2. **客户端作弊上报通道完全没找**。没有对照 addCheat / onStageCheat / BuildPassCheckInfo / GM command 这四种常见形态去 hotfix 里搜。
3. **Root / 模拟器检测只记录存在、没记录处理**。`libtoolChecker.so`（RootBeer）+ 4399/数美 SDK 都在包里，**在 MuMu + root 环境上是否被中和、命中后行为是什么（上报/踢下线/闪退）从未验证**——这本身就是一个独立的「用户反馈闪退」候选，且与三功能无关。
