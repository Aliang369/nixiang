## 3. 4399 闪退问题边界

用户明确：4399 闪退目前只有玩家反馈，没有找到根因或可靠日志。因此本轮不能声称已经从根因上修掉 4399 闪退。

TapTap 当前实现相对 4399 历史代码已结构性移除几类已知高风险路径：

- 不在主菜单触发约 2GB 全堆扫描。
- 以程序集列表非空作为 attach 就绪条件。
- `DamageHandle` 按真实 40 字节布局传递，而非旧的 48 字节自造 blob。
- `runtime_invoke` 返回异常会被检查，不再把悬挂托管异常留到后续调用点。
- 全屏补发有 busy 去重和已击杀 EID 去重。

仍需保留的残余风险：全屏补发仍使用 `runtime_invoke(HpHandle)`，其长期压力稳定性只能靠后续多局 / 多设备反馈继续观察；不能仅凭本次单局证明“4399 闪退问题绝对不会出现在 TapTap”。

原因：旧卡 / 旧 grant 是 `tlgd` 范围，新包按设计只接受 `tlgdtt`。发布前必须在运营后台完成其中一种配置：

1. 给 `tlgdtt` 发适用卡密（`scope=game, game_id=tlgdtt`）；或
2. 使用全游戏卡（`scope=global`）。

后台 `tlgdtt` 的 bootstrap 已能返回游戏，但功能列表当前为空。客户端对空 feature 列表按“放行”处理；为了后台开关语义清楚，仍建议同步为：

| featNum | 名称 |
|---:|---|
| 1 | 秒杀 |
| 2 | 全屏秒杀 |
| 3 | 无敌 |
| 4 | 无限技能 |

在运营侧给 `tlgdtt` 配置有效票据前，这个 APK 不应宣称“拿包即用”；代码与包结构已完成，但运行门禁仍受新 ID 授权状态约束。
