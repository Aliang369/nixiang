## 二、4 功能（已 100% 提取，见 features_all4_extracted.js.txt）

全部为 JS 层 `get_ret(1..4)` 检查（`jsb.reflection.callStaticMethod("org.cocos2dx.javascript.AppActivity","get_ret","(I)Z",n)`）：

1. **百倍伤害** get_ret(1)：`KH()` 伤害结算内，玩家方单位 `o.target.damage *= 100, realDamage *= 100`
2. **无敌** get_ret(2)：同函数，`unitType === Monster` → `damage = 0, realDamage = 0`
3. **移动速度** get_ret(3)：`MoveSpeed` getter 内 `n *= 5`
4. **无限技能** get_ret(4)：`tick()` 内 `reduceAllSkillColdDown(1e9)`（主动+被动技能组件）

玩家方单位判定：`qA.Hero || Summon || Guardian || Player || ParasyteGuardian`

## 三、反作弊/封号点全清单

### A. JS 上报层（客户端可屏蔽，斌哥已做，星光必做）
| 点 | 原版行为 | 屏蔽法 |
|----|---------|--------|
| `addCheat` | 客户端把作弊**上报服务器** `SendServer("scene.playerHandler.addCheat",{type})` | 改 `return;` |
| `onStageCheat` | 服务器判定后下发，客户端弹 `FightCheat` 错误 | 置空 `{}` |
| `onDevilClear` | 恶魔关作弊回调 | 置空 |
| 聊天 md5 | 聊天内容 hash 校验 | 替换为禁聊提示 |

### B. 服务器侧联动（客户端屏蔽不了，只能"不触发"）
- `handleOnStageCheat` → `reenactInput`（**服务器战斗回放校验**，数据不同步→标记）
- 错误码 `CheatSuspect(-20009)`、`StagePassTooFast(20002)`（过关太快）、`FightCheat(8)`
- 跨战斗技能释放校验（frame/rid/skillId）
- 结论：功能量级保持斌哥同款（×100/×5/1e9），不放大，避免触发 B

### C. Native 检测库（游戏自带，原包实锤）
- `libPglbizssdk_ml`：**CRC-32 完整性校验**（改包检测）
- `libavmdl_lite`：百度环境检测（root/模拟器/hook）
- `libmaparmor`：内存防护、`libmsaoaidsec`：MSA 加固、`libtds_core`：数盟设备指纹
- 应对：root/环境类检测→装机环境规避（真机非 root 可见度低）；CRC/完整性→需实测其检测目标（文件？内存？），若校验 APK 文件 → 用 SignatureSpoof/killPath 同型 hook 绕

### D. Java/dex 层（原包 smali 逐类分析，2026-08-16 实锤）
- **xposed(58)**: 全部在 R$ 资源类（com/hortorgames/*/R$, org/cocos2d/demo/R$）—— 是资源名含 "xposed" 字符串，**不是检测代码**
- **frida(4)**: 在 PGL 等 SDK 类中（字符串引用），非主动检测
- **rootbeer(4)+magisk(2)**: 只在斌哥新增 dex（classes5-8）—— **斌哥自己的反分析，游戏原版没有**
- **checkSign(4)**: 在 `com/tencent/mm/opensdk/`（WeChat SDK 的 SSO 签名校验）—— 星光 SignSpoof 覆盖
- **getPackageInfo(11)**: PGL×7(仅读版本号,非签名校验) + OEM×3(设备ID包查询) + Cocos2dxHelper×1(引擎初始化) + org/repackage×1(查 OEM 签名) —— **游戏自身没有 Java 层签名校验**
- **verifySign(2)**: okhttp3 TLS 证书链 —— 标准库,**非游戏检测**
- **CRC(23)**: OBB expansion 文件 CRC + okio Gzip —— 标准库,**非游戏检测**
- 结论：Java 层检测面**非常薄**，星光 SignSpoof（hook PackageManager.getPackageInfo）覆盖全部；真正的重头在 native libs

## 四、星光注入方案（待确认，选一）

### 方案 A：静态 JS（复刻斌哥，推荐）
1. 底包 = 原版 APK
2. **JS 重定向**：原版 bundle 远程下载 → 需要把改好的 JS 塞进游戏加载路径。
   斌哥 = native killPath.killOpen 劫持 open；星光可用更简单方式：
   - 原版远程 bundle 下载到缓存后 evalString 执行 → 方案 A-1：直接改 `assets/zip.apk` 同名机制
     需要确认原版 bundle 的实际加载路径/文件名（`/gamecaches/code/` 下具体结构，待实测）
   - 或 方案 A-2：把改好 JS 打包成 Cocos bundle 放进 `assets/assets/main/`（本地 bundle 优先于远程？需验证 Cocos 加载优先级）
3. **开关桥**：给 `org.cocos2dx.javascript.AppActivity` 加 `get_ret(int)` 静态方法（返回星光 Toggle 状态；或用星光 ModBridge 改名替代）
4. **反作弊屏蔽**：JS 照表改（A 组 4 处）；签名 → 星光 SignSpoof；CRC/环境 → 实测后对症
5. 发版：外科组装 + 重签（星光管线）

### 方案 B：纯运行时（不塞 JS 文件）
1. hook `se::ScriptEngine::evalString` @ **0x6B0FF8**（已验证，libcocos2djs.so 原版同偏移）
2. 脚本进 evalString 时注入等价 JS（WH 模式：百倍伤害/无敌/速度/技能 + 反作弊屏蔽）
3. 优点：不碰 JS 加载链路；缺点：每脚本处理，性能/稳定性要调；热更免疫（同斌哥兜底思路）
4. 与斌哥差异：斌哥静态+运行时双保险；纯 B 方案仅运行时

### 建议：A-2 优先（本地 bundle），失败退回 B（运行时注入）。理由：B 是斌哥已验证的兜底路径，机制最确定。
