## 〇、一句话结论

1. **官方又更新了**：APK `14.0.0/vc19 → 15.0.0/vc20`（新包，非仅热更），热更 `code` bundle `6355d → a1e47`。
2. **当前 `MwdlMod` 锚点在 15.0.0 上全部失配**：4 功能里 3 项（百倍伤害 / 无敌 / 移速）**静默不拼接**，
   第 4 项（无限技能）锚点命中但拼进去引用**死符号 `jA`** → 用户一开「无限技能」就会在战斗 tick 里抛
   `ReferenceError`，**比 20260909 那次更危险**（那次只是失效，这次第四项会主动搞坏战斗循环）。
3. 复查发现 **3 类历史文档遗漏/过时的检测点**（见 §四）：
   - **`SignCheck` / `signPrint`**：游戏 SDK 自己会读签名 SHA-1 指纹并**塞进每个平台请求的公共参数上报**
     （旧文档写「游戏自身没有 Java 层签名校验」——**已过时**）。
   - **内置 `Cheat` 命令通道** `W_.command / W_.batchCommand`（含 `loot` 调试命令），服务端有
     `CheatNotFound(10101) / CheatParameterError(10102)` 校验。
   - **原生无敌/免死/斩杀机制**（`ERoleSpecialState.Infinity`、`AvoidDeath`、`damage.executed`）——
     比「伤害归零」更干净、更省事的挂点，历史文档没记录。
4. **功能可以复用**，但必须：① 按 §三 重定位 4 个锚点 + 单位/属性枚举改名；② 按 §四 补 2 项伪装
   （签名指纹 + 战报回放一致性）；③ 外科脚本 3 个补丁点（classes3/classes4/Manifest）在 15.0.0 上**仍然成立**，
   但底包与 Manifest 缓存要换新。

## 四、上报（上报面）全清单 —— 本次复查的重点

> 历史文档只列了 `addCheat`/`onStageCheat`/`onDevilClear`/聊天 md5 四个点，
> 而 15.0.0 里 `addCheat` 与聊天 md5 **已经不存在**；真正的上报面比旧文档写的**更大**，共 6 条通道。

### R1. ⭐ 战报回放上传（最重要，旧文档只写了个名字）

官方 PvE 每场战斗结束（**胜 / 败 / 退出都会**）都会上传一份**完整确定性输入记录**：

- 入口：`handleOnFightSuccess / handleOnFightFailure / handleOnExitFight / readyToOtherFight`
  → `saveFightReplay()` → `ZR.reportFightRecord(record, RandomCount, isOver)` → **`z_.stageReenact`**
- 记录结构（`_u` codec，全部实测）：
  `directs[]`、`potions[]`、`rooms[]`、`kills[]`、**`refreshAttrs[]`**、`revives[]`、`events[]`、`skills[]`
  + 结果 `Ju{ exitFrame, totalFrames, lastRandom, dPS, rank, result }`
- 另有 `initFightData`（初始状态/种子）、`fightParams`、`maxDps`、`syncFrameRate=10`
- 服务端→客户端回执：`game_stagecheatr` →（两处绑定）
  - `onStageCheat` → 弹 `EErrorTips.FightCheat=8`
  - `handleOnStageCheat` → `console.warn("===数据不同步")` + `t.reenactInput`
- **含义：客户端战斗是「锁步确定式模拟 + 输入录制」，服务端可重放对账。**

### R2. 逐杀上报（时长校验）

`killMonster(t,e)` → `ZR.stageKillMonster` → **`z_.stageKill({monsters, duration})`**；
配套 `stageEnter({stageId})`、`stageFail({})`、`stageDie({})`、`stageInteract({objects})`、
`stagePickup({lootIds})`、`stageSmash({count})`、`stageNextRoom`。
服务端错误码：**`StagePassTooFast=20002`**、`StageNeedKillBoss=20007`、`StageNeedKillMonster=20008`。

### R3. ⭐ 签名指纹上报（**旧文档漏掉**）

- `com/hortorgames/gamesdk/common/utils/SignCheck.java`：
  `getPackageManager().getPackageInfo(pkg, 64)` → `signatures[0]` → **SHA-1 指纹**
- 该指纹被塞进**所有平台请求的公共参数**：`Utils.getCommonParams()` 与
  `RequestServerManager` 的 base params，字段名 **`signPrint`**；
  同批上报还有 `androidId / oaId / oaidThirdSdk / distinctId / packageName / sysInfo(system,brand,model) / ipv6 / activeLoginMatchId`
- 目标域：`platform-apm(-test/-dev).hortorgames.com`、`platform-stat…`、`pay-app-server…`、`comb-platform…`
- **说明**：旧文档「游戏自身没有 Java 层签名校验」**已过时**。这与 20260909 的
  「10045 指纹签名无效」是同一根因面（多了平台侧 APM/统计也吃这个字段）。

### R4. 客户端埋点 / APM

- JS 侧 `mR.track(mR.ETrackEvent.XXX)`（战斗进入/击杀 Boss 等）+ `mR.apmlog(msg,data)`
- `HSDK.gameTrack / postAPMLog / trackGS / postGameInfo / business / setTGAAccountId`
  （`assets/hortor/HSDK.app.min.js`，上报 `platform-apm`）

### R5. 服务端→客户端日志推送

`game_clientlogr` → `onErrorMsg`（按 `level` 打 `console.warn`），服务器可下发警告文案。

### R6. 内置 `Cheat` 命令通道（**旧文档漏掉**）

- `W_ = V_("Cheat",{ batchCommand:Ch, command:kh })`
- 用例：`W_.command({cmd:"eclipse",parameters:["eclipse"]})`、`W_.batchCommand({commands:[{cmd:"loot",parameters:["2","300008","100000000"]}]})`
- 服务端校验错误码 `CheatNotFound(10101) / CheatParameterError(10102)`
- 相关：`StageType_Extends` 里有 `TipOff=37`（举报）、**`AntiCheat=40`**；
  玩家举报错误码 `TipOffTooFrequent=240001` 等

### 需要做的伪装（按优先级）

**1. 签名指纹伪装（必做，已部分完成，需回归确认）**
- 目标：`SignCheck.getCertificateSHA1Fingerprint()` 与 PGL 的
  `PackageManager.getPackageInfo(pkg, 0x40).signatures[]` 都必须读到**官方证书**。
- 现状：`SignSpoof.java` 已加 `MWDL_PKG=com.hortor.mwdl` + 官方 DER（20260909）。
- **15.0.0 要做的复验**：官方证书是否变化（新包 md5 已变，需重新 `apksigner --print-certs-pem` 导出比对
  SHA-1/SHA-256）；`signPrint` 是 **SHA-1 十六进制冒号分隔大写**格式，SignSpoof 返回的 `PackageInfo`
  必须让 `signatures[0].toByteArray()` 解出**官方 X.509**，否则 SHA-1 对不上。
- 注意 `SignSpoof` 清 `PackageManager.sPackageInfoCache` 依赖 hiddenapi 豁免 → MuMu 需 `hidden_api_policy=1`，
  真机原生可用。

**2. 战报回放一致性（这是「伪装」的核心，不能只改数值）**
- 硬事实：每场战斗上传 `directs/potions/kills/revives/skills/rooms/**refreshAttrs**` +
  `totalFrames/lastRandom/dPS/result`，服务端可重放。
- 因此**在结算点改伤害（如现有 `i.target.damage=E}` 乘 100）会改变模拟轨迹**，
  与「客户端声称的 totalFrames / dPS / 击杀」一起被服务端重放对账。
- **推荐伪装姿态（推断，待运行验证）**：把增益尽量做成**「记录前修改」**——
  - 改 **`refreshAttrs` / `initFightData.heroData`** 里的属性值（`AttributeComponent.getAttr` 包裹 → A9），
    让客户端在上传时**本来就记录成高属性**，服务端用同一份数据重放 → 轨迹一致；
  - 或直接走**原生机制**（A10 斩杀 / A11 `Infinity` buff），语义上「像游戏本来就允许的」。
- **量级安全线**：严格沿用斌哥已验证的 `×100 / ×5 / 1e9`，**不放大**（旧文档结论，15.0.0 不变）。
- 反作弊回调：`onStageCheat` 置空 + `handleOnStageCheat` 静默（新版后者只 `console.warn`，
  不影响功能，但留着会暴露在 logcat 里）。

**3. 时长/帧数伪装（倍速类功能）**
- fight 循环是固定步长 `S4=1/30`，`update` 里按 `fightTime` 追赶帧；
  `rw.MAX_RATE_FIGHT_TICK=!1`（生产关）、`FIGHT_TICK_RATIO=1`。
- 加速会同时抬高帧率 → `totalFrames` 与 `stageKill{duration}` 变小 → 触 `StagePassTooFast`。
- 伪装做法：倍速只做**表现层**（渲染/动画 timeScale），**不动逻辑帧计数**；或限制倍速上限并观察。

**4. 痕迹与环境**
- 不改 dex/so 原文（外科组装已保证 `resources.arsc`/`classes.dex`/`classes2.dex` 字节不变）；
- 新增 `classes5.dex`（`com/starry`）+ `lib/arm64-v8a/libstarry_magic.so` 是**新增**文件，
  但 `SignCheck` 只查签名、没有包内容枚举 → 目前无证据会被发现；
- MuMu 上 `hidden_api_policy=1` 是全局改动，**验机后按需还原**；
- 别在游戏进程里留 Frida 痕迹（旧文档实测：本游戏 **frida attach 会闪退**）；
- `DeviceFingerprint` 写 `/sdcard/Android/starry_magic/` 会 EACCES（已自动回落 `/data/local/tmp`），
  属外观告警。

**5. 登录面（沿用）**
- TapTap 旧 SDK 强制网页登录（`ActivityHandler.authorize` 抛异常）✅ 15.0.0 仍适用。
- 平台登录的「指纹签名无效 10045」根因就是 R3 → 由伪装 1 解决。
