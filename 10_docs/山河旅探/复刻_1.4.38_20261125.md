## 3 五处解锁点（运行态 dll 实测命中）

| 方法（命名空间） | 命中偏移 | patch 后字节 | 效果 |
|---|---|---|---|
| `DefaultPurchasedManager.IsChapterPurchased`（`HotFix_Project.App`） | `0x0C06BC` | `17 2A` | `ldc.i4.1; ret` ⇒ 章节恒已购 |
| `DefaultPurchasedManager.IsSkinPurchased`（同上） | `0x0C0820` | `17 17 <tok> 2A` | `ldc.i4.1; ldc.i4.1; newobj <tok>; ret` ⇒ 返回 `(inShop:true, isPurchased:true)`，服饰直接「使用」 |
| `DefaultPurchasedManager.IsActivityLimitedSkin`（同上） | `0x0C0478` | `16 2A` | `ldc.i4.0; ret` ⇒ 不挡 Tap 限定皮 |
| `SaveManager.CheckChapterStageIsUnlocked`（`HotFix_Project`） | `0x076E64` | `17 2A` | 关卡恒解锁 |
| `AchievementManager.GetAchievementUnLock`（`HotFix_Project.SaveManagerAbout.Achievement`） | `0x0ABF94` | `17 2A` | 成就皮（西装/衬衫）恒解锁 |

- `<tok>` = `ValueTuple<bool,bool>::.ctor` 的 `newobj` token，运行态实测 `73 75 0e 00 0a`（TypeSpec#308），即脚本打印的 `tuple newobj 73750e000a`。
- 按名字定位的两个坑：`DefaultPurchasedManager` 在 `HotFix_Project.App` 而非全局；`AchievementManager` 有两个，只有 `HotFix_Project.SaveManagerAbout.Achievement` 那个带真方法（`HotFix_Project.Achievement` 下只有 `.ctor`）。
- `CheckChapterIsUnlocked` 在 Android 侧恒 `true`，章节闸门只有 `IsChapterPurchased`（后者在 `UserProfile` 为空时会 NRE 并被 catch 成「未购买」）。
- 特征字节按**运行态 CDN 构建**写；每条模式在 2,184,192 B 里各只出现 1 次（命中点即方法体 IL_0000），`MemMem` 取首个命中不会误伤。若加载到 APK 内那份构建，5 条全为 0 —— 那种情况靠第 5 节的热更缓存兜底落地。

## 4 实现（钩 LoadAssembly + 开关受控）

`mod菜单/starry-mod-menu/app/src/main/jni/Games/ShltMod.cpp`：

1. 钩 `ILRuntime.Runtime.Enviorment.AppDomain.LoadAssembly`（`GetMethod(klass,"LoadAssembly",3)` + `DobbyHook`），启动加载 DLL 只进一次。**不钩 `ILIntepreter.Execute`**（每指令都进，代价与风险都不可控）。
2. 取字节走 `MemoryStream`：`_buffer @0x28`、`_origin @0x30`、`_length @0x38`，数组 `len @0x18` / `data @0x20`；先验 `MZ` 再改。
3. 原地改 IL：5 处各自 `p[0..1]` 覆写，`PatchSkinTuple` 额外在前 512 B 窗口里数出现最多的 `73 xx xx xx 0A` 拿 `newobj` token（兜底初值 `73750e000a`）。
4. 开关受控：
   - `chapter` 组 = `kChapter` + `kStage`；
   - `skin` 组 = `kLimited` + `kAchieve` + `kPatchSkinTuple`；
   - 两组都关 ⇒ 一条都不 patch（日志 `[Shlt] hotfix IL patch skipped (both OFF)`），游戏完全原样。
   - IL 在 DLL 加载那一刻定型 ⇒ **改开关后必须重启游戏**才生效（日志会带 `（需重启游戏生效）`）。

产物（`07_patched/山河旅探/hotfix_2025-02-14-1015/`）：新 bundle 2,187,187 B / md5 `825e307955d73014c567e29796202513` / crc32 `0x418f2ab5`；清单 439 B / md5 `c4ec6b38dacb885edf188ed75b52846a`；`__info` 18 B。

- **`__info` 格式**：`u16LE(8)` + CRC32 小端十六进制 8 字符 + `i64LE(size)`，定长 18 B，无引用计数/时间戳。缺字段或与清单不一致 ⇒ YooAsset 校验失败 **整目录删除**缓存，回落内置清单重新下官方 bundle（补丁失效）。生成式：`struct.pack("<H",8) + struct.pack("<I", zlib.crc32(data)).hex().encode() + struct.pack("<q", len(data))`。
- **清单三处等长改写**：该 bundle 条目的 `UnityCRC→0`、`FileHash→新 md5`、`FileCRC→新 CRC 串`、`FileSize→新字节数`；pdb 条目不动；`.version` 不碰。
- **注入脚本闸门（本地）**：bundle 头 `UnityFS` 且 >100 KB；清单内该条目恰好 1 处且 `FileHash/FileCRC/FileSize` 与实算一致；`.hash == md5(.bytes)`；`__info` 自洽。任一不符直接退出（退出码 3）。
- **`--apply` 落地**：`su mkdir` 暂存目录（root 直建目录会让 `adb push` 静默失败）→ push → 备份将被覆盖的文件到 `/data/local/tmp/shlt_hotfix_backup_<ts>` → `su cp` 到 `CacheFiles/<md5前2位>/<md5>/__data+__info` 与 `ManifestFiles/*_2025-02-14-1015.bytes+hash` → `chown` 到 app uid、目录 `2775`、文件 `664` → 回读 `ls -ln` + `md5sum`。
- **不要动** `CacheFiles/82/825e30…/` 与 `ManifestFiles/*_2025-02-14-1015.*`：删掉即重下官方 bundle。
- **CDN 发新版本号** ⇒ 清单被官方同名文件覆盖 ⇒ 注入失效；对新的运行态 bundle 重跑 `shlt_patch_hotfix.py` 再注入。

## 6 登录（TapTap 改包法）

- TapSDK **明文可达**：`classes.dex` 内 `com/taptap/sdk/*` 143 个真实 class_def（含 `ui/ActivityHandler`、`TapLoginHelper`、`LoginBlock`、`WebBlock`），未加密、未藏 payload。
- 做法：改 `com/taptap/sdk/ui/ActivityHandler.authorize`，令其抛 `starry_force_web_login` → 框架接住走 WebView。脚本 `[4/8]` 段做这步，并断言 `classes.dex` 内含该串。
- **不做签名回灌**：包内无 `TapSignKit` / `GatekeeperRepository` / `InitializerServiceImpl` / `LoginActivityImpl`（classes.dex 与 classes2.dex 均为 0），`Validate` 只有 `hasInternetPermissions/hasTapTapActivity/notNull/sdkHasInitialized` 4 个方法，不含验签 ⇒ 改包法第 4 步无对象。
- **不写 `GameHookImpl`**：本游戏走改包法（`ActivityHandler` 明文），Java SPI 那条路不需要。
- 未验证项：`libtapsdkcore.so`（6.1 MB）native 侧是否有包签名校验（装机改签后登录是否返 `1001` 未实测）。

## 7 注入宿主（决定菜单能不能看见）

- `AomiActivity` 定义在 **`classes.dex`**（`classes2.dex` 里 0 次）；`com.unity3d.player.PrivacyActivity` 才是 Manifest 里的 MAIN/LAUNCHER，启动后 `startActivity(.AomiActivity)` 自己退到后台且不 finish。
- 脚本 `[4a/8]` 段在 `classes.dex` **回编之前**（`SMALI assemble -o classes.dex` 之前、`[4/8]` WebLogin 补丁之后）给 `AomiActivity` 补两个钩子：
  1. `onCreate` 末尾 → `MenuService.start(this)`；
  2. 新建 `onResume` → `MenuService.notifyHostResumed(this)`，`invoke-super` 必须是 `Lcom/unity3d/player/UnityPlayerActivity;`（实测 `.super`，写错直接 VerifyError）。
- 顺序不能反：放到 assemble 之后会被整段覆盖，连带丢 WebLogin 补丁。
- **host 必须落在 `AomiActivity`**：框架 `resolveMenuHost` 优先用 `focusedHost`（启动时传进来的 Activity = `PrivacyActivity`），本游戏的 ACTIVITY 模式窗口继承宿主窗口 token；挂在已退后台的 PrivacyActivity 上会 `mHasSurface=false`、`isVisible=false`，表现为「悬浮球和菜单都没有」，且 `attached=true` 是粘性布尔量、不报错。


- 跨签名必须先 `uninstall` 再 `install`：同一包名不同签名的覆盖安装会被 `INSTALL_FAILED_UPDATE_INCOMPATIBLE` 拒掉。

- 后台需有 `games.game_id=shlt`（或全游戏卡），否则 bootstrap 拉不到菜单配置。

## 11 已知遗留（当前状态，未修）

- 公告窗口 `NO_SURFACE` 时 `menuHold` 不释放：bootstrap 返回公告 ⇒ `applyMenuHold()` 把 root 从窗口 `removeView`，公告本身挂同一个不可见宿主 ⇒ 用户点不到「关闭」⇒ `releaseAnnounceHold()` 永不执行 ⇒ 之后所有 `setVisible(true)` 都走 held 分支，悬浮球被公告永久 hold 隐藏。
- 位置在框架 `NativeMenuController`（`applyMenuHold` / `setVisible` held 分支 / 公告 LP 复用宿主 token），属公共框架行为，本游戏**未改**。规避：先把宿主修到 `AomiActivity`（第 7 节），公告有 surface 就能被关掉。
