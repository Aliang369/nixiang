# nixiang 仓库定制版｜会话结束全量复盘与经验进化提示词

> **性质（2026-10-27 治理）**：本文件是**执行提示词**——用来触发一次审计，**不是政策正文**。它不定义谁能改什么、什么算证据、经验怎么合并：这些一律以 `AGENTS.md`（§1.1–§1.4 规则分类与优先级、§4 授权边界、§5 证据与体量、§6 经验生命周期、§7 优化会话权限）为准；记录结构以 `10_docs/_templates/会话复盘模板.md` 为准。冲突时按 AGENTS.md 执行。
>
> **用途：** 每次完整工作会话结束时，原样复制本提示词发送给 AI。要求它回看整段对话、核对实际证据、找出问题与重复模式、比较更优路线，并把可靠经验沉淀成下一轮可直接复用的行动规则。
>
> **使用方式：** 不需要填写表单，不需要再补充一遍本轮任务。AI 应从当前会话历史、仓库和可用的会话记录中自行恢复信息；只有确实无法访问的内容，才明确列为限制。
>
> **按需执行原则：** 本文件列出的是**应检查的维度**，不是必须逐项产出的表格。某维度本轮无证据/无发现，一行写 `N/A（理由）` 即可；不为了覆盖栏目而扫描全仓或灌水。

---

## 角色与总目标

你现在是本轮工作的**独立复盘审查员、根因分析员、效率审计员和经验进化维护者**。请对**当前会话从第一条有效任务指令到现在的完整过程**进行全面复盘，而不是只总结最后几轮，也不是只复述做了什么。

唯一目标是让下一次同类任务：**少走弯路、少重复犯错、少消耗用户时间、用更少步骤获得更强证据、交付更稳定，并把经验证的经验留在正确位置。**

本次复盘必须主动检查但不限于：目标是否理解准确、用户是否被迫重复要求、路径或方法是否选错、哪里凭猜测而非证据、哪些步骤可以提前或替换、什么问题反复出现、现有规则为什么没挡住、哪些自动门禁确实创造了价值、有哪些可复用新知识、工具调用与上下文是否浪费、怎样把下一次流程做得更快更可靠。

## 0. 最高优先级：复盘边界与证据纪律

1. **先回看整段会话。** 从最初目标、用户后续修正、每次决策、工具调用、失败尝试、测试结果、用户反馈、收尾过程串成时间线。不得只根据最后一条消息判断本轮做了什么。
2. **用户意图是验收基准。** 提取用户明确提出的目标、交付形态、必须/禁止事项、验收标准，以及用户后来补充或改变的要求。指出是否偏题、越界、遗漏、让用户重复说明或过早宣布成功。
3. **证据优先于记忆和叙述。** 对重要结论核对真实文件、差异、日志、命令输出、测试、构建产物和用户原话。严格区分：`实测事实`、`仓库历史记录`、`证据支持的推断`、`待验证假设`、`无法确认`。不能拿推测冒充事实；不能只因脚本存在就声称运行过；不能只因构建通过就声称功能验证通过。
4. **不编造统计。** 会话 ID、工具调用数、耗时、返工轮数、用户配合次数、文件改动、测试通过数等，必须来自实际记录或证据。无法读取会话日志时明确说“未能取得量化数据”，不要凭感觉估算出精确数字。
5. **遵守仓库的现行唯一规则。** 先读 `AGENTS.md`，并按任务读取 `10_docs/_templates/会话复盘模板.md`、相关 `10_docs/_state/current.md`、对应游戏摘要/硬约束、相关脚本与技能。若旧文档与 `AGENTS.md` 冲突，以现行规则与脚本实际行为为准，并记录冲突。
6. **区分“本轮重复”与“历史复发”。** 历史复发须在仓库旧复盘、经验索引、规范变更日志或其他会话记录中找到依据；列出具体文件/章节/会话日期。证据不足时标记“疑似同类，尚未证实”，不能随意宣称是第几次。
7. **不要为了全面而全仓无差别通读。** 采用仓库规定的按需检索、限制输出与最小读取策略。检查与本次问题直接相关的先例、规则、脚本、日志和旧复盘即可。
8. **这条提示词本身不是危险操作授权。** 不得据此擅自清数据、卸载、覆盖不可逆产物、操作未授权设备、改动禁改文件、扩大功能范围、提交/推送或清理用户管理的目录。
9. **会话类型按真实主任务和用户授权判定。** 如果前面的主体是游戏执行任务，默认生成复盘与提案，不因用户粘贴本提示词就把它自动升级为全量规范改造；权限边界见 `AGENTS.md` §7。如环境没有文件写入能力，必须如实说明，不得假称已落盘。
10. **不以复盘之名扩大任务。** 只修正/提议有证据支持的问题；不要为了显得做了很多而重写大批文件、重复已有规则、创建内容重复的技能卡或引入没有必要的新工具。
11. **不要先停下来问我问题。** 先利用现有对话和仓库完成能完成的复盘；信息确实缺失时把未知项、影响和最低成本的补证办法列清楚。

## 1. 必须执行的证据收集与核对

### 1.1 恢复本轮目标与结果

将用户的每个实质要求按时间顺序编号，记录：

- 用户原始目标/原话锚点（必要时带消息号）；
- 交付形态与明确边界；
- 本轮采用的方法和关键决策；
- 最终结果与验收证据；
- 是否满足、部分满足、未满足或无法证明；
- 是否发生了用户纠正、重复要求、等待、额外操作或不必要配合。

用户反馈是行为证据，但需要区分“用户实际使用结果”与“机器机制验证”。不能只看主观现象，也不能用机器日志否定用户对真实体验的反馈；存在冲突时应明确区分并查出最小必要证据。

### 1.2 核对工作区与改动

按任务需要检查 `git status`、本轮相关 `git diff`、文件变更、提交/推送状态、构建产物摘要、脚本退出码、测试记录、游戏状态文档和验收证据。检查宣称完成的项目是否真的完成、有没有漏回填状态、有没有带入无关/他人改动、有没有未说明的残留或未决事项。

所有 Git 检查应限定相关路径并遵守 `AGENTS.md` 的多会话共享文件纪律；不得为了复盘而重置、清理、覆盖或推送。

### 1.3 会话效率量化（可取得时必须做，不可取得时说明）

先尝试确认本轮 DSH 会话 ID 与会话记录位置；若记录可用，依仓库现行要求运行：

```bash
python3 04_scripts/_common/session_metrics.py --session-id <真实会话ID> --gate
```

必要时进一步运行只读统计：

```bash
python3 04_scripts/_common/session_stats.py --session-id <真实会话ID>
```

命令参数以仓库脚本当前实现为准。记录真实输出与退出码，不要只抄指标名称。至少关注：工具调用/step 分布、单发占比、bash 占比与 bash 文本检索、超大工具结果、重复触达文件 Top-N、会话耗时/阶段分布、压缩与上下文浪费、关键工具是否被绕开、反复构建/装机次数、用户配合轮数、重复读写/过期读态、无信息增益的排查循环。

若会话 ID 或本机记录不可访问，写明尝试过什么、缺什么、因而哪些指标不能量化；继续完成定性分析，禁止伪造数字。`session_metrics --gate` 若返回违规，要列出具体超标项及证据；不能只写“效率一般”。

### 1.4 检查仓库中的既有经验与复发记录

至少按问题关键词定向检索：

- `10_docs/_state/规范变更日志.md`
- `10_docs/_state/pending_experience.md`
- `skill/re-lessons/SKILL.md`
- `10_docs/_state/规范优化_*会话复盘.md` 中相关旧复盘
- 相关 `10_docs/_templates/经验*.md`、`skill/**` 与 `04_scripts/_common/**`
- 如涉及框架：`10_docs/_state/框架待办.md`、`mod菜单/starry-mod-menu/CHANGELOG.md`

重点问：是不是以前就发现过？规则已经存在却没有读到、没有执行、不可发现、相互冲突，还是规则正确但缺少自动门禁？是否有人在别的会话已经修复而本轮没有复用？不得只靠“印象中有类似问题”下结论。

### 1.5 仓库五维覆盖（漏一维必须解释）

按 `10_docs/_templates/会话复盘模板.md` 的要求，逐项检查并给出 `已检查 / 有发现 / 无关(N/A+理由) / 无法检查` 状态：

1. **单游戏/当前任务链路**：从输入、分析、实施、构建、验证到交付和收尾。
2. **通用脚本与管线**：`04_scripts/_common/**`、`pipeline`、门禁、工具调用契约。
3. **Skill / 经验知识**：`skill/**`、`10_docs/_templates/经验*.md`、经验索引与状态。
4. **规则 / 模板 / BOOK**：`AGENTS.md`、复盘模板、`PLAYBOOK.md`、`WORKFLOW.md`、`TOOLBOOK.md` 及相关规范。
5. **框架源码与框架层资产**：`mod菜单/**`，尤其本仓框架入口、构建模板、公共能力、框架专属脚本与文档。

不能因为本轮没修改某个维度就直接跳过检查；但也不要为了填表强行提出改动。若框架维度有发现，至少明确证据、影响面、建议落点，按现有模板同步考虑 `10_docs/_state/框架待办.md`；已经发生的框架改动按现行约定检查 `CHANGELOG.md`。

## 2. 核心分析任务：一定要找“为什么”，而不只列现象

### 2.1 本轮目标完成度与偏航

指出哪些目标完成、未完成、部分完成、没有充分证据。对每次用户纠正、重复要求、表示困惑/不满、等待过久或额外操作，分析它暴露的是目标记忆、沟通、证据、流程还是实现问题。保持客观，不归咎用户。

### 2.2 问题分类与根因链

每个重要问题至少沿以下链条分析：

**现象 → 直接原因 → 更深层根因 → 为什么原有流程/规则/测试没有挡住 → 实际代价 → 下次具体怎么做 → 如何判定修复有效。**

适当使用但不限于这些分类：目标误读/范围偏移、凭猜测推进、未先查仓内先例、证据选择顺序错误、未设计可证伪验收、忽略已有 API/脚本、环境假设不成立、读/编辑策略低效、上下文/压缩后丢失硬约束、工具调用未并行、输出体量过大、昂贵操作缺少前置断言或保留中间产物选项、测试把“看起来正常”误当机制成功、规则冲突/不可发现、状态/交付证据未同步、跨会话协作污染等。

不要把“AI 犯错了”当根因。要追到可改变的流程机制；优先提出可自动检测、可复现、可证伪、可减少人工负担的方案。

### 2.3 黑洞与代价审计（必须写 Top-N）

从本轮挑选最值得回收成本的约 3–10 项，按“可节省成本 × 再发概率 × 风险/影响”综合排序。每项都必须写：

- **发生了什么**：具体阶段、操作、证据或输出；
- **为什么不理想**：是必要成本还是可避免的浪费；
- **根因**：不能只重复现象；
- **实际代价**：工具调用/step、重试、构建/装机、用户配合、上下文、时间或风险；没有量化数据就写定性；
- **本可怎么做**：清晰的替代路线，写出第一步应该做什么；
- **下次触发规则**：遇到什么信号时执行什么动作；
- **验收标准**：下一次如何用证据证明改进有效。

必须区分“真黑洞”与“必要投入”。为安全性、关键反证或高风险验收而付出的成本，若确实增加了重要信息或拦住事故，就不要为了追求调用数少而误判为浪费。

### 2.4 重复问题与复发层级

将重复问题拆成三个层级，不要混淆：

- **本会话内重复**：同一个错误/尝试/读取/问题重复出现几次；
- **同一游戏/同一任务跨会话复发**：指出对应复盘与日期；
- **跨游戏或通用层复发**：说明为何应升级为通用技能、规则、脚本或自动门禁。

每类列出：复发证据、共同根因、旧措施为何失效、这次有没有被成功拦截、下一步最有效的根治方式。区分“症状相似”和“根因相同”；没有足够证据时不要合并。

### 2.5 方法替代与效率优化

对关键决策和高代价步骤，比较原路线与至少一个合理替代路线，评估：

- 预计信息增益是否更高、是否更早能排除错误假设；
- 成本（工具调用/step、构建、装机、等待、人工操作、上下文）；
- 风险与可逆性；
- 所需证据和停止条件；
- 哪条路径更快得到可靠结论。

优先寻找“先检索现成能力/先看调用链/先检查输入与环境/先做静态断言/先保留中间产物/一轮只改一个变量/并行独立读操作/先小实验再昂贵操作”等可复用转变。替代路线必须基于本轮证据或仓库先例，不允许事后诸葛式的无证据断言。

### 2.6 正向收益（必填，不能只盘点失败）

明确记录哪些规则、脚本、门禁、测试、日志或人工判据**实际拦住了什么问题/避免了什么风险**，给出证据和作用链。若本轮没有机器门禁拦截问题，也要如实写“本轮未观察到可确认的拦截”，不要编造。指出哪些机制应保留、哪些门禁可能误报/漏报/形成形式主义，以及如何校准。

### 2.7 外部检索与仓内先例审计（必填）

记录是否执行了仓内先例检索（如 `prior_art.sh`）、是否按规则需要外部检索、实际关键词、命中、失败/空结果、查询次数、结果如何改变了决策、是否写入 `10_docs/_state/外部方案台账.md`。若“本轮没查”合理，解释为何仓内证据已充分；若该查未查，列出下一次应使用的精准关键词。记录空结果是为了避免之后重复付费检索。不能把没有执行的检索写成已执行。

## 3. 经验提炼与知识库进化

> 状态取值、`class` 维度、合并门槛的唯一正文是 `10_docs/_templates/经验候选卡.md`；本节只列复盘时要做的判断动作，不重复其定义。

### 3.1 每条候选要交代的四件事

- **可验证事实**：带文件路径/行号、版本、命令及输出关键行、日志/证据文件、md5/sha256、RVA/偏移等可复核锚点。
- **是不是新东西**：先检索 `skill/**`、`pending_experience.md`、该游戏文档；同义条目存在就并入，不新建文件。
- **`class` 判定**：只让 AI 更懂技术 ⇒ `tech`；会改变用户长期要求、项目政策、授权/安全边界 ⇒ `policy`（只提案，等用户当轮指令）。
- **落点**：具体文件 + 章节/行号或函数；单游戏事实落该游戏文档，跨游戏机制落通用 Skill，能机器判定的落脚本/门禁。

### 3.2 防止经验库膨胀

能并入已有章节就不新建；优先改现有段落而不是新增章节；工作流问题优先做成脚本检查而不是"请 AI 记住"的长规则。没有落点的提案不算提案。

### 3.3 复盘提示词自身的进化

检查本提示词是否遗漏了本轮反复暴露的新型问题。**只有证据表明现有提示词确实无法发现或约束该问题时**，才建议增补一条；优先修改现有段落而不是无限增加新章节。若无实质缺陷，明确写“本轮没有足够证据要求修改本提示词”，不要为了进化而进化。

## 4. 输出报告格式（按此顺序输出；没有证据的栏目明确标 N/A/未知）

报告先给一个简短总判定，再按以下章节展开。写得详尽但不灌水，每项结论都服务于“下一次怎么做更好”。

### A. 总结与会话信息

- 会话主题、日期、游戏/版本（如适用）、会话 ID（仅在真实取得时填写）；
- 复盘范围、所用证据与无法访问的材料；
- 总体完成度/可靠性判定；
- 最重要的 3 个问题、最重要的 3 个有效机制、下一轮最该优先做的 3 件事。

### B. 用户目标与交付核对表

表格字段：`# | 用户目标/原话锚点 | 验收标准 | 实际结果 | 证据 | 状态 | 遗留/偏差`。

### C. 本轮实际过程与结果

按阶段列出关键操作、目的、结果、代价和对应证据。不要逐条复述全部工具调用，只保留影响结果、风险、成本或决策的关键动作。

### D. 效率指标与成本结构

报告真实取得的 `session_metrics.py` / `session_stats.py` 数据；解释最高成本来自哪里、哪些是必要投入、哪些有优化空间。如果无法量化，明确列出缺失项和原因，然后做有证据的定性判断。

### E. 本轮黑洞 Top-N 与替代路线

按价值排序，逐项包含：`现象/证据 → 根因 → 实际代价 → 本可采取的路线 → 下一次触发动作 → 验收指标`。明确区分必要成本与可避免浪费。

### F. 重复问题与历史复发

分为“会话内”“同游戏跨会话”“跨游戏/通用层”三组；提供次数或证据锚点、历史引用、共同根因、旧措施失效原因和根治方案。没有可查历史时不要杜撰。

### G. 正向：门禁和有效做法真正拦住了什么

写具体门禁/规则、拦截证据、避免的后果，以及应保留或修正的机制。没有证据就如实说明。

### H. 外部检索与现成能力审计

列出已执行/未执行的仓内检索、外部检索和相关结果；标明值得保留的空结果关键词、遗漏的先例检索与下次补查词。

### I. 可复用的事实与新经验候选

每条写：结论、证据锚点、适用范围、反例/未知、拟落点、生命周期状态。将单游戏事实、跨游戏方法和工具/工作流经验分开。

### J. 五维覆盖审计

表格字段：`维度 | 检查状态 | 本轮发现 | 证据 | 处理方式/落点`。五维必须全部出现：单游戏链路、通用脚本/管线、Skill/经验、规则/模板/BOOK、`mod菜单/**` 框架层。

### K. 已存在规则为何没有生效

只列真正存在的规则/门禁失效案例，区分：没读到、读后没遵守、规则冲突、规则不可发现、规则写得含糊、工具/模型不可执行、门禁本身错误、例外条件缺失。提供 `文件 + 章节/脚本` 锚点；新发现但还没有现行规则的问题不要伪装成“违规”，放进优化提案。

### L. 可执行优化提案（P0 / P1 / P2）

每条必须采用以下模板：

- **ID / 优先级 / 标题**
- 问题与证据
- 根因及影响范围
- 具体方案（精确到文件、章节、函数或脚本）
- 为什么优于旧方法 / 预计节约什么成本
- 风险、适用条件与不能泛化的边界
- 验收方式（可运行的检查、对照实验或明确的行为判据）
- 状态：`已落地 / 候选 / 待验证 / 未做 / 不采纳（附理由）`

P0 = 安全/交付正确性/高概率高代价复发；P1 = 高频返工或明显效率收益；P2 = 低频、体验或整理性改进。按收益与风险排序，不要为了凑数硬列。

### M. 落地情况与下一轮行动清单

若本轮有权限且实际已实施改动，逐条列出文件、具体变化、检查/测试结果、提交 SHA（只有实际取得时填写）、是否推送、仍未做事项。未实施的提案不得写成已落地。

最后给下一次同类任务一份极短“开工前动作清单”：最先读取/检索什么、最先运行什么检查、遇到哪种信号要立刻换方法、怎样判定成功。动作必须与本轮证据对应，而不是通用口号。

### N. 复盘质量自检

在结束前逐项核对并报告 `通过 / 未通过 + 原因`：

- 是否回看了整个会话，而非只看最后几轮？
- 是否逐项核对用户目标、交付和验收证据？
- 是否识别根因，而非只列现象？
- 是否区分本会话重复和历史复发，并有可追溯证据？
- 是否给黑洞写出“本可怎么做”和可执行的下次动作？
- 是否记录了正向门禁与必要成本？
- 是否对外部检索、仓内先例和量化指标如实交代？
- 是否完成五个维度检查？
- 每条优化提案是否有明确落点、边界和验收标准？
- 是否避免重复造规则、把推断当事实或擅自扩大任务？

## 5. 实际落盘与改动规则

1. 优先沿用 `10_docs/_templates/会话复盘模板.md` 的文件命名和字段，不另造一套相冲突的复盘体系。通常落点为：
   `10_docs/_state/规范优化_{YYYYMMDD}_{主题}会话复盘.md`
   主题、日期、游戏名/版本依本轮真实内容确定，不凭空填入。
2. **会话类型与权限不由本文件定义**：游戏执行会话能改什么、优化会话能改什么、哪些文件禁改 —— 见 `AGENTS.md` §7「规范/技能优化会话全自动」与 §4 授权边界。执行会话只记录＋提案，框架侧发现落 `10_docs/_state/框架待办.md`。
3. **落地的机器关不在这里重复**：改动自查清单、`bash 04_scripts/_common/preflight.sh <改过的文件...>`、`audit_experience_registry.py`、`规范变更日志.md` 追加一行 —— 见 `AGENTS.md` §6/§7。
4. 经验升格按 `10_docs/_templates/经验候选卡.md` §4 的七项门槛执行：证据不齐或跨样本边界不清留候选；`class: policy` 一律只提案；被反证的结论要明确纠正并保留原记录。
5. 不要自动提交/推送。只有用户授权或本轮指令明确要求收尾提交时，才依 `AGENTS.md` 与仓库正式收尾脚本操作，并如实报告提交、推送和远端同步状态。
6. 完成后检查复盘文档本身的链接、路径、状态、数字和文件名，避免“复盘文档写完了，但登记与实际不一致”。

## 6. 最终回答给用户的格式

报告落盘后，用中文说明：

1. 复盘文档的真实路径；
2. 发现的最重要问题与最有价值的经验；
3. 哪些提案已实际落地，哪些只是候选/待验证；
4. 会话量化指标是否真实取得；
5. 有没有需要下一轮继续处理的高优先级事项。

**最终原则：这不是为本轮写一篇漂亮总结，而是为下一轮建立一条更短、更稳、更可验证的路径。没有证据不下结论；没有明确落点不算提案；没有验证不算修复；没有必要就不增加规则。**
