## 4. 斌哥运行时注入链

从 `libSDKloading.so` 运行态内存提取到完整 JS 补丁器原文：

- 原始内存切片：`06_dumped/燃烧纪元/binge_js_patcher_from_memory.txt`
- 清洗后的补丁器源码：`06_dumped/燃烧纪元/binge_js_patcher_source_20260918.js`
- 清洗源码：331 行 / 19,109 B
- SHA-256：`d965066a3e9dee0ee2a32bf5005e3cac11db60a5305848c1c22d838d8e823ecf`

注入器自述的关键机制：

- 壳侧给 `window.MOD` 注入状态桥；`MOD.feature1..N` 对应 `mod_sw.txt` 的 `f` 字符串。
- JS 补丁器包装 `window.__require(reg)`，在 browserify 模块真正实例化前读取工厂函数 `toString()`。
- 通过结构正则认目标函数，再用 `new Function` 重建模块工厂并写回模块表。
- 不是按方法名写死，因此对同名/混淆方法有版本自适应能力。
- 硬编码：`MOD_FORCE=false`、`MOD_SPEED=10`。
- 额外无条件功能：公告固定为“暂无公告”。

状态桥字段：

```text
MOD.feature1 .. MOD.feature15
MOD.blood / MOD.atk / MOD.spd / MOD.slider
MOD.all()
```

其中 `featureN` 读取 `f.charAt(n-1)`；数值字段读取 `mod_sw.txt`。当前注入器只使用 `feature1/2/3`，没有使用 `atk/spd/slider`。

## 5. 三项功能源码级挂点

### 5.1 伤害 + 无敌：`Unit.prototype.changeHp`

- 模块 key：`Unit`
- 解密脚本行号：`354522`
- 原始函数头（补丁器识别形状）：

```js
t.prototype.changeHp = function(t, e, n, o) {
    var a, s = t.delta, l = t.crit, c = {
        retShield: 0,
        delta: s,
        isDmg: !0,
        beKilled: !1
    }
```

- 识别正则核心：

```text
.prototype.(\w+) = function\((\w+), (\w+), (\w+), (\w+)\) \{\n
var \w+, (\w+) = \2\.delta, \w+ = \2\.crit, \w+ = \{\n
retShield: 0,\ndelta: \6,\nisDmg: !0,\nbeKilled: !1\n\}
```

- 补丁器在函数体最前面插入（语义摘要）：

```js
var _mD = this.battleCtr && this.battleCtr.handler && this.battleCtr.handler.data;
var _mSvr = _mD && ((_mD.Args && null != _mD.Args.seed) || null != _mD.seed) ? 1 : 0;
var _m0 = t.delta;

if (MOD.feature1) {
    if (!_mSvr && t.delta < 0 && e && e.group == 0 && this.group != 0)
        t.delta = t.delta * 100;
}
if (MOD.feature2) {
    if (!_mSvr && t.delta < 0 && this.group == 0)
        t.delta = 0;
}
```

- `UnitGroup.A` 由补丁器从 `GameConst` 源码动态学习，当前版本值为 `0`。
- 判定含义：
  - `this` = 挨打方；`e` = 出手方。
  - `this.group != 0` 且 `e.group == 0` 时，对敌伤害 ×100。
  - `this.group == 0` 时，我方受到的负 `delta` 清零。
- 服务端回放/多人共享种子会被跳过：
  - `handler.data.Args.seed` 或 `handler.data.seed` 存在时 `_mSvr=1`，不修改，避免“画面赢、结算输”。
- 这个函数是伤害、治疗、护盾、死亡链的统一入口，所以补丁只需插一处。

### 5.2 战斗加速：5 处倍速三元表

补丁器匹配形状：

```js
return 1 == X ? 1 : 2 == X ? 1.5 : 3 == X ? 2 : 1;
```

当前版本命中 5 处：

| 模块 key | 解密脚本行号 |
|---|---:|
| `ChapterFbBattlePanel` | 97072 |
| `OnHookBossBattlePanel` | 229248 |
| `OnHookSettingModel` | 231278 |
| `OutlandBattlePanel` | 233569 |
| `PveBattlePanel` | 261037 |

补丁器插入：

```js
if (MOD.feature3) return 10;
return 1 == X ? 1 : 2 == X ? 1.5 : 3 == X ? 2 : 1;
```

接管原因：`BattleController.update` 用 `dt += t * getBattleSpeed()` 驱动固定步长逻辑，同时 spine 动画、子弹、倒计时等也读取同一个倍速值；所以改这 5 张表能同时加速逻辑与表现，不会出现“逻辑快了动画没快”。

### 5.3 免广告（斌哥菜单没有，但游戏确实有广告奖励）

结论：**游戏有看广告领奖链路，原版移植时应新增免广告**。

广告链路：

- JS 统一入口：`AdHelper.prototype.showVideoAd(callback)`
  - 解密脚本行号：`78455`
  - 模块 key：`AdHelper`
- 广告状态枚举：

```js
AdStatus.None = 0
AdStatus.Cancel = 1
AdStatus.Reward = 2
AdStatus.Showing = 3
AdStatus.Error = 5
```

- 原生调用链：

```text
AdHelper.showVideoAd(callback)
  -> AdHelper.showAd()
  -> SDKController.showAd()
  -> SDKBase.showAd()
  -> Java com/sandglass/sdk/GameSDKProxy.showAd(...)
  -> SDKHelper.onShowAdResult
  -> cc.director.emit("onShowAdResult", true/false)
  -> AdHelper.onShowAdResult
  -> callback(AdStatus.Reward / AdStatus.Cancel)
```

- 游戏内多个奖励入口都汇到 `AdHelper.ins.showVideoAd(...)`，例如：
  - `ActDailyWelfareWin.CC_onGetClick` -> `C_ActAdTake`（9802）
  - 农场种子/施肥、钓鱼体力、抽卡、世界 Boss、挂机宝箱、魔法副本等
- 免广告候选实现：在 `AdHelper.prototype.showVideoAd` 函数头插入：

```js
setTimeout(function () { t(2); }, 0);
return;
//（或等价地：直接走 this.onShowAdResult(true)，并跳过 this.showAd()）
```

- 这个改法只跳过客户端播放，后续 `C_*` 奖励请求照常发送；服务端是否额外校验广告凭证 `NOT PROVEN`，需要原版星光包运行时验证。
- 注意：当前斌哥补丁器**没有**这条免广告逻辑；这是为下一步星空版新增的功能。

## 6. 重要差异：菜单数值与注入器不一致

菜单 `exp` 写的是：

- 超级秒杀：`1-200`
- 战斗加速：`1-50`

但当前真实注入器源码写死：

- `MOD_SPEED = 10`
- 伤害固定 `delta * 100`
- 只判定 `MOD.feature1/2/3`
- 完全没有引用 `MOD.atk`、`MOD.spd`、`MOD.slider`

因此：

- 斌哥当前包里“1-200 / 1-50”不是通过该补丁器生效的；滑条值可能只是菜单模板通用字段，当前版本未接线。
- 星空版移植时有两个可选策略：
  1. 严格复刻实际效果：伤害 ×100、无敌、速度 ×10。
  2. 按用户菜单预期实现：用滑块值替换固定 100 / 10（需确认数值上限和战斗平衡）。
- 在用户没有明确选择前，不建议擅自把滑条接到战斗逻辑。
