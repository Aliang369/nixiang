# 防御加固 · 通用路线图（跨游戏）

> 定位：**这套加固是所有游戏共用的能力**，勇士之心只是第一个落地样本 + 练兵场。
> 任何"只对勇士之心成立"的写法都算缺陷，接入新游戏前必须按本文 §3 的清单过一遍。

---

## 1. 现状分层：哪些已经是全局件，哪些还带游戏耦合

### ✅ 已经是全局件（一次做好，所有游戏复用）

| 件 | 位置 | 说明 |
|---|---|---|
| 授权链单点 | `jni/Includes/SgAuth.h` | 票解析/验签/三判据/掩码；v1 HMAC + v2 RSA + **v3（带 kx）** |
| RSA 验签 | `jni/Includes/sg_rsa_verify.h` + `sg_pubkey.h` | 纯 C，e=65537；**一把公钥服务所有游戏**（fp `25ba10e0faca3500`） |
| zip 读取 | `jni/Includes/SgZip.h` | 解压取明文给完整性/清单用 |
| 自完整性 | `jni/Includes/SgIntegrity.h` | 清单私钥签名 + 从自身 APK 取条目比对 |
| 服务端签名 build 清单 | `jni/Includes/SgBuildManifest.h` | 覆盖 so 自身（P2-1 零件） |
| **载荷解密 + 诱饵** | `jni/Includes/SgPayload.h` | keystream + Encrypt-then-MAC + 失败落诱饵 |
| 出包门禁 | `04_scripts/_common/harden_apk.py` | C1–C4 / C6 / C7 / C8 |
| 密钥与头生成 | `04_scripts/_common/sg_pki/*`、`04_scripts/勇士之心/gen_payload_enc.py`★ | ★需改成通用入口（见 §2.2） |
| 服务端 | `auth-server`：`sg_rsa.py`、`grant_service`（v1/v2/v3）、`config` | **一个服务端服务所有游戏**，v3 的 `kx` 派生与载荷 sha 相关（见 §2.3） |
| Java 侧 | `Preferences.pickGrant`（grant3>grant2>grant）、`ModBridge.setApkPath`、`NativeAccountController` 授权墙 | 菜单 dex 全游戏共用 |

### ⚠️ 还带游戏耦合（必须通用化，否则每接一个游戏都要手改）

| # | 耦合点 | 现状 | 目标形态 |
|---|---|---|---|
| 2.1 | **载荷拼接点** | 我在 `ysxz_1.0.3_menu/YsxzMod.cpp` 里写了 `GetPatchJs()`；每个游戏的 `<Tag>Mod.cpp` 各有自己的拼接处 | 抽成 `Includes/SgPayloadJs.h`：一行 `sgpayload_js::Get()` 拿到"真载荷或诱饵"，任何 Mod.cpp 接 3 行即可 |
| 2.2 | **生成头文件名** | `sg_payload_enc.h` / `sg_integ.h` 是全局单例名，编另一个游戏会被覆盖 | 改成 `<Tag>` 维度：`sg_payload_enc_<tag>.h`、`sg_integ_<tag>.h`；生成器加 `--game <tag>` |
| 2.3 | **服务端载荷 sha** | 服务端只有一个 `PAYLOAD_SHA`，是勇士之心的 | 改成"每游戏一条"：`PAYLOAD_SHA__<game_id>` 或一张表 `payload_sha`（按 game_id 查） |
| 2.4 | **出包门禁接线** | 只有 `ysxz_assemble_103.py` 调 `harden_apk.py` | 做成**共享门禁**：各游戏 assemble 末尾一行调用（或统一到 `pipeline.sh` 的出包阶段） |
| 2.5 | **诱饵 JS** | `Games/YsxzDecoyJs.h` 名字带游戏前缀 | 改名 `Games/SgDecoyJs.h`（内容与游戏无关，纯惰性 stub） |
| 2.6 | **构建前自动加密** | 只接进了 `ysxz_build_so_103.sh` | 各游戏 so 构建脚本各加一行（脚本体相同），写进接入清单 |

## 2. 新游戏接入清单（照这个走，一次全绿）

1. **框架覆盖**：该游戏的 so 构建脚本把 `MainModern.cpp`（或该游戏对应的入口）、`Includes/Sg*.h`、`Includes/sg_*` 全部用工作区现行版本覆盖（禁止用基线提交里的旧授权链）
2. **编译宏**：`LOCAL_CFLAGS/CPPFLAGS` 加 `-DSG_HAVE_ZLIB=1 -DSG_REQUIRE_INTEGRITY=1 -DSG_PAYLOAD_ENC=1`，`LOCAL_LDLIBS += -lz`
3. **完整性清单**：`gen_integ_header.py --game <tag>` 生成（条目=该游戏的菜单 dex + boot js + 证书）
4. **载荷加密**：`gen_payload_enc.py --game <tag>` 生成密文头 + 该游戏的 `K_build`
5. **载荷拼接**：在该游戏 `<Tag>Mod.cpp` 的 JS 拼接点改用 `sgpayload_js::Get()`（真载荷/诱饵）
6. **Java**：确认该游戏菜单 dex 用 `Preferences.pickGrant`（grant3>grant2>grant1）+ 调 `ModBridge.setApkPath(ctx)`
7. **服务端**：该游戏 `game_id` 的 `payload_sha` 登记进配置表
8. **门禁**：assemble 末尾调 `harden_apk.py check`，不通过拒绝交付
9. **三处自测**：`selftest_p1.py`（授权链）+ `test_payload`（解密/诱饵）+ `precheck`（装机层）

## 3. 三项待办（全局口径，见 `10_docs/勇士之心/防御加固_P2后续三项_20261027.md` 的实现细节）

这三项**天生就是全局能力**，实现时按"服务端一张表 + 客户端一次接线"来做，别写成勇士之心专用：

| 项 | 全局要点 |
|---|---|
| **每卡密水印** | 水印值由服务端按 `card_id` 算，放进票里（所有游戏同一套）；客户端只负责显示，不区分游戏 |
| **诱饵/异常上报** | 一个接口 `POST /v1/report/anomaly`，字段带 `game_id` + `build_id`；客户端上报点写在共享的 `SgPayload.h`/`SgIntegrity.h` 里 |
| **OTA 载荷下发** | `POST /v1/payload?game_id=&build_id=`，服务端按 game 取对应载荷；客户端加载链做成共享 helper |

## 4. 迁移步骤（把现有勇士之心实现通用化）

| 步骤 | 内容 | 影响 |
|---|---|---|
| 1 | 抽 `Includes/SgPayloadJs.h`（把 `GetPatchJs()` 逻辑搬进去，带缓存/重试） | 勇士之心删掉本地实现，改调共享 helper |
| 2 | 生成器加 `--game`，输出 `sg_payload_enc_<tag>.h` / `sg_integ_<tag>.h` | 勇士之心的 include 名同步改 |
| 3 | `Games/SgDecoyJs.h` 更名（去游戏前缀） | 一处 include |
| 4 | 服务端 `payload_sha` 改按 `game_id` 查表 | 服务端配置 + 勇士之心登记 |
| 5 | 各游戏 assemble 末尾接门禁 | 逐游戏一行 |

工作量：**半天到一天**（不涉及算法改动，纯结构整理 + 重出一次勇士之心的包验证不回归）。
风险：低；但必须**重出包 + 装机预检**确认勇士之心不回归。

---

## 5. 纪律（防再犯"游戏耦合"）

1. 任何加固改动，先问一句：**"这条规则对所有游戏都成立吗？"** 成立 ⇒ 写进 `jni/Includes/` 共享件或 `_common/`；不成立 ⇒ 才写进该游戏目录，并在本文 §1 表里登记。
2. 文档落点：**跨游戏的能力/路线 → 本文件**；单游戏的落地证据与坑 → `10_docs/{游戏}/防御加固_*.md`。
3. 新游戏接入后，回填 §1 表格（哪个游戏已接入哪几件），避免"以为全局其实只做了一个游戏"。
