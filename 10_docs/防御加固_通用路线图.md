## 2. 新游戏接入清单（照这个走，一次全绿）

1. **框架覆盖**：该游戏的 so 构建脚本把 `MainModern.cpp`（或该游戏对应的入口）、`Includes/Sg*.h`、`Includes/sg_*` 全部用工作区现行版本覆盖（禁止用基线提交里的旧授权链）
2. **编译宏**：`LOCAL_CFLAGS/CPPFLAGS` 加 `-DSG_HAVE_ZLIB=1 -DSG_REQUIRE_INTEGRITY=1 -DSG_INTEG_HEADER_FILE='"sg_integ_<tag>.h"'`，`LOCAL_LDLIBS += -lz`；
   **载荷型游戏**再加 `-DSG_PAYLOAD_ENC=1`；`LOCAL_LDFLAGS += -Wl,--undefined=kStarryBuildStamp`（否则构建戳被 `--gc-sections` 回收）
3. **完整性清单**：`gen_integ_header.py --game <tag>` 生成（在该游戏 `GAMES` 表里配条目：native 型＝菜单 dex + 证书；载荷型＝再 + boot js）
4. **载荷加密**（仅载荷型）：`gen_payload_enc.py --game <tag>` 生成密文头 + 该游戏的 `K_build`
5. **载荷拼接**（仅载荷型）：在该游戏 `<Tag>Mod.cpp` 的 JS 拼接点改用 `sgpayload_js::Get()`（真载荷/诱饵）
6. **Java**：确认该游戏菜单 dex 用 `Preferences.pickGrant`（grant3>grant2>grant1）+ 调 `ModBridge.setApkPath(ctx)`（`StarryInitProvider` 已内置，`MainModern.cpp:336` 收到路径即跑完整性校验）
7. **服务端**（仅载荷型）：后台 `PUT /v1/admin/games/{game_id}/payload` 登记该游戏载荷 sha（**不需要重建镜像**，下一张票即生效；见 §6）。漏做会被门禁 **C9** 在出包阶段拦下并打出操作步骤（见 §6.1）；native 型游戏 C9 记 N/A
8. **门禁**：出包脚本末尾接一行 `bash 04_scripts/_common/harden_gate.sh <成品APK> [--game <游戏名|tag>]`，不过就拒绝交付；
   构建机若在**非 git 的暂存目录**里编（中文路径机器必踩），必须从仓库根取戳再导出：`STARRY_BUILD_EPOCH="$(git -C "$NIXIANG" log -1 --format=%ct)"`（否会落兜底值 1790184000，装机闸门查8 不可信）
9. **三处自测**：`selftest_p1.py`（授权链）+ `test_payload`（解密/诱饵，仅载荷型）+ `precheck`（装机层）；
   装机后**第一优先判据**：`logcat -s V2:*` 里 `[V2] g=1`（完整性通过）—— `g=0` 时功能会全静默失效，别当成「功能没效果」

## 5. 纪律（已强制，2026-10-27）

> **强制口径**：`AGENTS.md` §6「加固门禁默认全局强制」——所有游戏出包必须过
> `harden_apk.py check`（C1–C9），PASS 写凭证 `09_test/<游戏>/harden/<apk_md5>.stamp`；
> 装机闸门 `pre_install_gate.sh` **查11** 校验凭证，缺失即 **FAIL 拦装机**。
> 下面三条是配套纪律，不再是"建议"。

1. 任何加固改动，先问一句：**"这条规则对所有游戏都成立吗？"** 成立 ⇒ 写进 `jni/Includes/` 共享件或 `_common/`；不成立 ⇒ 才写进该游戏目录，并在本文 §1 表里登记。
2. 文档落点：**跨游戏的能力/路线 → 本文件**；单游戏的落地证据与坑 → `10_docs/{游戏}/防御加固_*.md`。
3. 新游戏接入后，回填 §1 表格（哪个游戏已接入哪几件），避免"以为全局其实只做了一个游戏"。

## 6. 服务端载荷 sha：按 game_id 落库 + 后台可维护（2026-10-27 落地）

**为什么改**：原先 `PAYLOAD_SHA` 是环境变量 ⇒ 每加一个游戏就要重建镜像，运维上不可接受。

| 项 | 实现 |
|---|---|
| 存储 | `games` 表新增列 `payload_sha VARCHAR(64)`（迁移 `ALTER TABLE games ADD COLUMN IF NOT EXISTS payload_sha VARCHAR(64);` 幂等） |
| 取值 | `grant_service._game_payload_sha(game_id)`：按 game_id 查库 + **60 秒内存缓存**；改值后 `_SHA_CACHE.pop(game_id)` 立刻失效 |
| **隔离** | 库里没登记 ⇒ 该游戏**不签 v3 票**（`payload_ready=False`）。**不存在"回退全局 sha"**，避免所有游戏共用一把载荷密钥 |
| 主密钥 | `payload_master` **不进库、不进后台**，继续留文件（`chmod 600`）；库里只放 sha256 这种公开值 |
| env 兼容 | `PAYLOAD_SHA` 仅在 `game_id` 为空（内部调用）时兜底；服务器 `.env` 中该值已清空 |

### 后台接口（改完无需重建镜像 / 重启容器）
| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/v1/admin/games/{game_id}/payload` | 当前 sha、能否签 v3、`k_build` 指纹前 16 位、改动警告 |
| PUT | `/v1/admin/games/{game_id}/payload?sha=<64hex>` | 直接贴 sha；**不传 sha 时读 multipart `file` 自动算 sha256**（后台上传密文文件即可）；`sha=clear` 清空 |

### ⚠️ 改这个字段的后果（接口已内置提醒）
`payload_sha` 变化 ⇒ 该游戏 `K_build` 变化 ⇒ **所有旧包功能失效**（载荷解不出、只剩诱饵）。必须同步出新包。

### 落地验证（服务器 + 真机实测）
```
yszzx.payload_sha(db) = 165b437778c845aa…
payload_ready(yszzx)  = True
k_build(yszzx)        = d63013cd39692ddd…   ← 与出包机 ~/.starry-keys 逐字节一致
v3 mint = True | verify = True | roundtrip = True
未登记游戏 ready(hhrx) = False              ← 隔离生效，不再串用别家 sha
客户端真机：payload decrypted 117445 B + splice 各追加 117471 B（改库后功能不变）
```


### 6.1 载荷变更提醒（C9 + 生成器横幅，2026-10-27 落地）

**用户要求**：载荷变了要主动提示「去后台改」；新游戏（以后给别的游戏加防御）同样要提示。

两处提醒，覆盖"改载荷"和"新游戏"两种场景：

| 位置 | 触发条件 | 行为 |
|---|---|---|
| `gen_payload_enc.py`（构建时必跑） | 本次载荷 sha ≠ 本地 `~/.starry-keys/payload/<game_id>.last`，或无 `.last`（新游戏） | 打印**醒目横幅**：游戏名 / 新 sha / 旧 sha / 后台点击路径 / 等价 PUT 命令 / "改 sha 会让旧包全失效"警告 |
| `harden_apk.py` **C9 载荷已登记** | 出包门禁阶段 | 用 `X-Build-Key` 问服务端 `GET /v1/build/payload-status?game_id=&sha=`：<br>· `match=true` → PASS（附 `v3_ready` 与 `k_build` 指纹）<br>· 已登记但不一致 / 后台没这个游戏(404) → **FAIL 拒绝交付** + 同上横幅<br>· 未配凭证或网络不通 → PASS 但标 ⚠️ 跳过（离线出包不被卡死），横幅照打<br>· 403 → FAIL（构建机 key 配错） |

**构建机凭证**：`~/.starry-keys/build_key.txt`（与其它私钥一样**不入库**），由构建脚本导出
`SG_GAME_ID` / `SG_API_BASE` / `SG_BUILD_KEY`；服务端对应 `.env` 的 `BUILD_API_KEY`（留空即关闭该接口）。

**新游戏接入时**（对应 §2 清单第 7 步）：
1. 后台先把游戏建好（`games.game_id` 存在）
2. 首次 `gen_payload_enc.py` 运行 → 横幅给出 sha（提示"新游戏"）
3. 后台「载荷 sha」粘贴 → C9 下一轮出包转 PASS
4. 若跳过第 3 步：C9 在 assemble 阶段直接 FAIL（404 或未登记），**不会把空壳包发出去**

**实测（服务器 + 构建机）**
```
A) 已登记：C9 载荷已登记 PASS 一致 | v3_ready=True | k_fp=d63013cd39692ddd   → 门禁 8 项 FAIL=0
B) 未登记：C9 载荷已登记 FAIL 后台没有这个游戏（404：{"message":"游戏不存在：hhrx"}）→ FAIL=1 + 横幅
```
