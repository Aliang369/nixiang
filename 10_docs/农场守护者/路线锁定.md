## 六、禁止事项

1. **禁止用 ELF base + RVA 直接算地址**：本 so `va − file = 0x4000`，frida 侧要用 **VA**（`lib.base + va`），用 file offset 会差 0x4000 踩空（本轮已踩：读到 `0x34000068` 而非 `0xF81D0FFE`）。
2. **禁止只挂桩目标就断言覆盖战斗**：桩路径只证引擎→热更；C#→C# 需另行确认。
3. **禁止遍历 Config/Proto（2219+1831 类）**：只在 `QLD.Fight.Runtime.dll` 内定位。

## 七、真机动态逆向结论（2026-11-10，关键证据）

### 7.1 斌哥改包的 hook 点（内存对比法定位）

方法：装斌哥改包 → 运行时读 libil2cpp 全部可执行段 → 与官方 so 逐字节比对。
结果：**仅 2 处差异**，均为 Dobby inline hook（libSDKloading.so 导入 dlopen/dlsym/mprotect，导出 Dobby 特征符号 A0000000bxxx…）。

| VA | file | 磁盘原值 | 内存现值 | 性质 |
|---|---|---|---|---|
| **0x17E7750** | **0x17E3750** | 0xF81D0FFE | 0x16000000（b −128 MB 到 mmap 跳板） | **EnterFrame 变体 A（真实入口）** |
| 0x17E798C | 0x17E398C | 0xF81E0FFE | 0x16000000（同上） | 解释器栈操作：64 B 元素、count-1 弹栈 |

### 7.2 三个入口的覆盖差异（实测，务必区分）

| 挂点 | 时长 | 调用数 | 实测覆盖 |
|---|---|---|---|
| **0x17E7888**（本文件 §2 最初写的） | 15 s | 19,645 | **只有 UI/框架层**：90 个不同方法里无一个战斗类 |
| **0x17E7750**（斌哥挂的） | 13 s | 1,609,338 | **GameFightPlaySystem.Update** / A68PrivilegeCardSystem.Update |
| 0x17E9220（Execute） | 12 s | 17,780 | 引擎→热更顶层（Update/协程/MoveNext） |

**结论：0x17E7888 与 0x17E7750 是同型的两个不同函数，覆盖范围完全不同。实现必须挂 0x17E7750。**
（§2 表格里的 0x17E7888 保留作历史对照，不要再用。）

### 7.3 扣血不走方法调用（核心机制，别再来回试）

在 0x17E7750 上过滤 RemoveHp|CurHp|MaxHp|Hurt|Invincible|SkillCd|AddHp|Dead：**160 万次调用中命中 0**。

| 目标桩 | 地址 | 实测调用数 |
|---|---|---|
| Monster/Tower/ChildTower/Hero/SummonEntity.DoRemoveHp 共用桩 | 0x76f78bdad4 | **0** |
| MonsterEntity / EntityBase.set_CurHp 桩 | 0x76f799ccfc | **0** |
| TickAfter / TickState 桩 | 0x76f79a0e48 | **0** |

⇒ 战斗扣血是**纯 C# 到 C# 解释执行**：既不经过 methodPointer 桩，也不产生新的 EnterFrame。
⇒ 只能走「在帧更新前后改实体数据」，不能走「拦方法改参数」。旷野征途那套（ApplyHp 被 AOT 侧调用、走桩）在本作不成立。

### 7.4 下一轮实现方案

1. 挂点改为 **0x17E7750**（file 0x17E3750，序言 0xF81D0FFE），签名仍 (x0=frameGroup, x1=MethodInfo, x2=argsPkt)
2. hook 内识别 methodInfo == GameFightPlaySystem.Update 的 MI
3. 在该方法调用**前后**遍历实体改 EntityBase._curHp@88：
   - 无敌：我方实体（Tower/ChildTower/Hero/Summon）血量回填
   - 百倍伤害：怪物（Monster）额外扣 99 倍差值
4. 加速：A68PrivilegeCardSystem（月卡特权）；另需查内置最高倍速
5. 实体地址获取：在 frida 里用 klass 扫描确认对象头布局（本轮 Memory.scan 未命中，因当时已无战斗；下轮须在战斗中扫）

### 7.5 本轮踩过的坑（勿重犯）

1. **别把 file offset 当 VA 用在 frida 侧**：本 so va − file = 0x4000，用错会读到 0x34000068 这种野值。
2. **别用 Backtracer.ACCURATE 在热函数里 backtrace**：直接把游戏进程拖崩过一次。
3. **别用二进制 Manifest 字节匹配判断注入**：字符串是 UTF-16，直接搜类名恒失败，要用 aapt2 dump xmltree。
4. **斌哥包里 libil2cpp.so 与官方 md5 完全一致**（7affdf06…）⇒ 他纯运行时 hook，静态对比 so 找不到东西，必须比内存。

## 八、2026-11-10 深夜 实现落地与真机实测修正（现行方案，取代 §7.4）

### 8.1 挂点与参数约定（实测，非推断）

- 挂点 **VA 0x17E7750 / file 0x17E3750 / 磁盘序言 0xF81D0FFE**。
  在自己出的星光包上（无第三方 hook）读到该处首指令即原值，frida 实测 **28 万次/秒**（40 s / 1130 万次）。
- **参数约定（frida 实证）**：`x0 = frameGroup`、`x1 = MethodInfo*`、`x2 = argsPkt`，**`argsPkt+0 = this**`。
  - `x1` 可喂 `il2cpp_method_get_class/method_get_name` 正常取名 ⇒ 确认是 MethodInfo。
  - `argsPkt+0` 解引用后 klass 名成立 ⇒ 确认是 this。

### 8.2 ★关键事实：运行时对象是 FightCore 的子类

`argsPkt+0` 取到的对象 klass 名是 **`TrunkGamePlay`**（`TeamGamePlay` 亦同系），
**不是 `FightCore` 本身**。原因是 `il2cpp_method_get_class` 返回「方法声明类」，而运行时实例是子类。

⇒ **自检禁止严格 `klass == FightCore` 相等**（第一版装机的 `selfcheck: klass mismatch` 就是这么来的，功能全被自检挡掉）。
⇒ 正确判据：沿 `il2cpp_class_get_parent` 上溯，链上出现 FightCore 即通过。
⇒ 子类实例访问基类字段**偏移不变**（C# 基类字段先布局），可直接用 §8.3 的偏移。

### 8.4 实现（`Games/NcshMod.cpp` 现行）

| 功能 | 实现 |
|---|---|
| 百倍伤害 | 我方（Hero/Tower/Summon/ChildTower）`DmgAddRatio@264 = 100.0`（`100<<32`），伤害走游戏自身结算 ⇒ 死亡流程正常 |
| 无敌 | **只把 `_curHp@88` 回填到游戏原 `_maxHp@92`，绝不改 `_maxHp`**（2026-11-11 修正，见 §9） |
| 无限技能 | 遍历 `SkillComponent.ActiveSkillUnitList`，`SkillUnit.CurCd@96 = 0` |
| 解锁加速 | `UnityEngine.Time.set_timeScale(2.0)`（`il2cpp` 定位 + methodPointer 直调） |

**★教训（浪费一轮装的坑）：`DmgAddRatio` / `_maxHp` 是「写进去就留着」的状态字段，游戏不会自己重算。**
只改不还原 ⇒ **关掉开关后效果仍在**（用户实测「没开功能也是秒杀」）。
现行做法：每实体首次改写时记录原值（`EntRec g_rec[1024]`），`onFeatureChanged(false)` 与 `ForceClear` 时逐条还原（`SafeProbe` 兜野指针）。
`CurCd` 无需还原（游戏自己累加）。

### 8.5 ★归因陷阱：菜单会记忆开关状态

`shared_prefs/starry_magic_prefs.xml` 持久化每个开关（`<boolean name="1" value="true"/>`）。
重装/重启后菜单**自动把上次状态推给 native**（日志 `feat 1 -> 1`）。

⇒ **任何「没开也生效」的反馈，第一步先读该 prefs 与 `feat N -> M` 日志**，不要先怀疑游戏本身或默认值。
（本轮实测：用户以为没开，实际是上一轮开的被恢复，持续 44 秒。）

### 8.6 `FightCore.Tick` 未命中，但功能仍有效（备路径）

在挂点过滤 `mi == FightCore.Tick/1`：**frida 实测 0 命中**（Tick 不走该入口）。
但同一类其它方法高频命中（如 `get_IsWaitServerFrame`，28 万次/秒）⇒ 现行实现走
「**mi 的声明类属于 FightCore 继承链 ⇒ 取 argsPkt+0 作 core + 8 ms 节流**」的备路径，功能实测生效。

## 九、2026-11-11 关键修正：无敌不得抬高 `_maxHp`（否则结算异常）

### 9.1 现象

用户一局打完「没有正常结算奖励」。日志显示 `QLD.UI.UIFightLoseWindow:BackToMain()`
——**是失败窗，不是结算界面出错**（02:23:43 进战斗 → 02:25:46 失败退出，约 2 分钟）。

### 9.2 根因

无敌原实现把 `_maxHp@92` 与 `_curHp@88` 都写成 `1e8`（1 亿）。
`_maxHp` 会被结算/评分/上报读到，1 亿是明显异常值 ⇒ 战斗判定/结算异常。

**⇒ 无敌只允许回填 `_curHp`，`_maxHp` 一个字节都不能动。**

### 9.3 修正后实测（用户那局）

```
stats tower=1 hero=1 child=0 summon=0 mon(all=0,alive=0) runaway=0 tower0=800/800
```

- `tower0=800/800` ⇒ 上限是游戏原值 800（不再 1e8），且血量没掉过 ⇒ 无敌有效
- `alive=0` / `runaway=0` ⇒ 怪全清、无漏怪 ⇒ 正常胜利 + **正常结算**（用户确认）

### 9.4 顺带留下的诊断设施

`MaybeStats()` 每 5 秒落一条（不管开关是否打开）：
`stats tower= hero= child= summon= mon(all=,alive=) runaway= tower0=<cur>/<max>`

用途：下次任何「打不完 / 输了 / 没奖励」的反馈，**先看这一行**就能区分「塔被打死」「漏怪超限」「只是没打」。
