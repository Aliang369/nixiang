## 一、本轮新证据（全部实测）

### 1.1 ★Java 层签名校验链（本轮核心发现，旧会话从未定位）

`TRGame.getPackageSign()`（[TRGame.java:1379]）在**全部 Java 源码中零调用方**——它是留给 native 经 JNI 回调取签名的专用桥：

```
native 保护代码 --JNI--> TRGame.getPackageSign()
  → ApplySigningUtils.getRawSignatureStr()
  → PM.getPackageInfo(pkg, GET_SIGNATURES)
  → signatures[0].toByteArray() (证书DER)
  → MD5 → 小写hex 返回给 native
```

- `ApplySigningUtils` 为游戏自有类（`com/bantu/trgame/ApplySigningUtils.java`），仅此一处消费；其余 getSignatures 命中均为 SDK（alipay）或 androidx 框架类
- **官方证书指纹（apksigner 实测）**：
  - MD5（即 getPackageSign 官方返回值）：`0769ed9f9aab50cc4732774d74f56ff4`
  - SHA-256：`8ae4874dd88175da15852d5388da29fc1e4059108f24265c38a95d0a040d8de7`
  - DN：`O=Bantus, ST=Shanghai, C=CN`（旧 SignSpoof 伪装证书的 O=Bantus 即照抄官方）
- 包为 v2/v3-only 签名（META-INF 无 *.RSA），DER 导出需解析签名块（备用）

### 1.2 ★旧矛盾消除：20s 死亡最简解释 = 签名伪装从未稳定生效

- 挂点分析进展 §5d：18:55 版（SignSpoof 生效窗口）**存活 10+ 分钟零死亡**；§5e/f：meta-reflection 报 InvocationTargetException 后死亡回归；「denied=0」只说明没有 denied 日志，**不等于伪装成功**
- → §5e「检测不走 PM 路径」结论**不成立**（基于失效的伪装）。结合 §5d A/B（零改动重签 60s 内死），最简解释链：**重签 → getPackageSign 返回非官方 MD5 → native 比对失败 → 置检测标志 → 20s 优雅停机**
- 该假说同时解释：为什么 SignSpoof 恰好工作的窗口内游戏长稳、为什么 FairGuard/易盾跳过后死亡依旧（校验在游戏自身 native，走 JNI 桥读 PM）

## 二、突破口清单（按信息增益/成本排序）

### P0-A：Java 签名桥 patch（最小外科，绕开 PM 层，与 ColorOS 16 反射封锁无关）

smali patch `TRGame.getPackageSign()` 恒返回官方 MD5 常量：

```smali
.method public static getPackageSign()Ljava/lang/String;
    const-string v0, "0769ed9f9aab50cc4732774d74f56ff4"
    return-object v0
.end method
```

- 优点：不碰 PM/hidden-API/Dobby/seccomp；native 无论直调还是反射，取到的都是官方值；改动仅 1 个方法
- 备用加强：`ApplySigningUtils.getRawSignature()` 返回官方证书 DER 字节（覆盖字节级消费方，需导出 v2 签名块证书）
- ⚠️ 待验证：native 侧是否还有第二条独立校验（APK 文件字节 hash）。若有，由 P0-C 的 dump diff 兜底

### P0-B：A/B 实验阶梯（每次只动一个变量）

1. **AB-1**：SDK跳过（旧配方 patch_skip_protect）+ getPackageSign patch，**不带** seccomp/SignSpoof/任何 hook → 装机观察 20s 窗口。存活 ⇒ 签名桥假说实锤，20s 死亡根因关闭
2. **AB-2**：AB-1 基础上**飞行模式**对照 → 分流「服务器指令」假说（旧会话从未测过离线）
3. **AB-3**（若 AB-1 仍死）：重做内存 dump——**补齐旧 dump 两个缺口**（rel.ro gap `0x1E5B000-0x1E5F000` 与 FairGuard 置零区 `0x0-0x100000` 的解密态）+ 5/10/15/19s 多时刻分段 dump → 与早 dump diff，**新解密页=运行时检测代码本体**（0x79BACE2B 写入者在此，不在静态代码——旧 §5j 结论的另一种解释是它活在惰性解密页里）
4. **AB-4**（若 AB-3 定位到写点）：进程内 poll-and-patch——starry so 线程每秒扫自身 RWX 区，匹配 `MOVZ w?,#0xACE2B; MOVK w?,#0x79BA,LSL#16`（及 0x2AEB/0x4FAF 变体）立即数对，出现即 mprotect+patch 写点。同地址空间直写，无需 ptrace/proc/self/mem

### P1：旁路交付形态（釜底抽薪）

- **Zygisk/独立菜单**：APK 零改动（原签名原字节）+ 已装 com.starry.magic 独立菜单 + Zygisk 注入 native——签名/文件完整性检测类**整体失效**，只余 hook 检测面。设备 SukiSU root 可行
