# 动物大联盟 1.0.25 · libsecret.so 壳签名校验静态分析

- 样本：`/tmp/dwdlm_sec/lib/arm64-v8a/libsecret.so`（459344 B，源自官方 APK）。纯离线，未接触设备。
- 工具：NDK27 llvm-objdump / llvm-readelf / llvm-dwarfdump。符号表已 strip，函数边界由 .eh_frame FDE 还原（1364 条）。
- 段映射**实测**：LOAD1 文件偏移==虚拟地址（`.text` 0x24d40，`.rodata` 0xe0b0）；后续 LOAD 需 +0x4000/+0x8000。下文 `0x…` 均为 vaddr。

## ② 签名来源判定：两条互不相干的链（实测）

**链 A：sig-check = JNI 查 PackageManager（0x557f4）**。JNI 走函数表偏移间接调用，dynsym 里查不到符号名，靠 thunk 固定槽位识别：

| thunk | 指令 | JNI 槽 |
|---|---|---|
| 0x6006c | `[x8,#0xf8]; br x8` | GetObjectClass(31) |
| 0x60850 | 前导 `mov x1,x23`，`[x8,#0x108]` | **GetMethodID(33)** |
| 0x608d0 | `[x8,#0x30]` | FindClass(6) |
| 0x608f4 | `[x8,#0x538]` | NewStringUTF(167) |

方法名常量：0x103df `getPackageManager`+0x134de `()Landroid/content/pm/PackageManager;`；0xf2ef `getPackageName`+0xf8d7 `()Ljava/lang/String;`；0xf841 `getPackageInfo`+0x1156f `(Ljava/lang/String;I)Landroid/content/pm/PackageInfo;`；0x115a5 `android/content/pm/PackageInfo`；0x11e33 `hashCode`+0x146f9 `()I`。
API 分支：0x558bc `cmp w20,#0x1c`+0x558c0 `b.lt 0x55908` → ≥28 用 flags 0x8000000（GET_SIGNING_CERTIFICATES，0x558c4），<28 用 0x40（GET_SIGNATURES，0x55908）。**判据：链 A 纯 JNI，不碰文件。**

**链 B：密钥派生 = 解析内存 APK 的 v2 签名块（0x55a78，非 JNI）**
- 0x55b2c/0x55b34 取 0x17230 附近常量（`"APK Sig Block 42"`），0x55b3c `bl memcmp@plt` 比 16 字节 —— APK Signing Block v2 尾部 magic
- 0x55af8 `ldr x8,[0x786f0]`（容器长度）→ 0x55b14 `sub x0,x8,#0x18` → 0x55b24 `bl 0x4b3a0`；0x4b3a0 是**带边界检查的内存 buffer 读取**（`ldr x8,[0x786e8]; subs; ccmp`），**不是** open/pread/mmap
- 0x55a78–0x56090 整段**仅 1 处** JNI 槽位特征（0x55ccc `[x8,#0xf8]`），主体是 zip 结构解析

**结论**：sig-check 取「运行时签名」；**key-unwrap 的密钥输入取「内存 APK 文件里的 v2 签名块」**，与 PackageManager 无关。

### key-unwrap 算法（0x562e4）
1. 0x56310 `ldr w8,[0x786b0]; cbz w8,0x56338`：缓存命中则 0x56318 从 0x787a0 拷 16B(IV)、0x788a0 拷 32B(KEY)，返回 1
2. 0x56350–0x5635c：`.data` **0x6e0fe** 取 16B、**0x6e0de** 取 32B 常量
3. 0x56370 `ldrb w8,[0x6e0cd]; cbz w8,0x563ec` —— **配置字节实测 = 0x01**，强制走 0x55a78 分支
4. 0x56390 `bl 0x55a78`（sret=sp+0x70）；0x563a4 `cbz x23,0x563b0`：**串空 → 打 0x12319 → 0x56548 `mov w20,wzr` → 返回 0**
5. 正常：包名经 JNI 追加进同串（0x563ec–0x5642c，getPackageName），分别拼 `+0x4b('K')`/`+0x49('I')`（0x56450/0x56468）→ 0x61410/0x608b4（SHA-256 族）
6. 0x564a0–0x564c4：`KEY[i]=hashA[i]^const32[i]`；0x564c8–0x564f0：`IV[i]=hashB[i]^const16[i]`
7. 0x56518–0x56538 回写缓存（IV→0x787a0，KEY→0x788a0，flag 0x786b0=1），返回 1

→ **重签必然改 v2 块 → 派生串变 → KEY/IV 全错**，与「纯重签首启必崩」吻合。

## ③ 分支与后果（实测）

**key-unwrap 失败（决定性）**：0x43dd0 `bl 0x562e4` → 0x43dd4 `tbz w0,#0x0,0x440f0` → 0x440f0 打 `key unwrap failed (sig/package mismatch?)` → 0x4410c `b 0x452ac`（**不解密**）。AES 仅 0x43dec `bl 0x490c0`；解密后 0x43e60 `bl 0x585f0`（mem-load zip 校验），失败→0x44398 `no dex extracted`→0x452a8。**dex 拿不到 ⇒ Provider 类缺失 ⇒ StubProvider class missing**，与实测日志自洽。

**sig-check 失败（非致命）**：0x43108 `bl 0x557f4`→x23；0x43110 `cbz x0,0x43148`；否则 GetObjectClass→GetMethodID("hashCode","()I")（0x43138）→0x43140 `bl 0x62450`→0x47c38 取 hashCode；0x43148 `mov w0,#0x98; bl 0x48f8c` 读 **`.data:0x6e0a8` 期望值，实测 = 0xfd62fda2**；0x4317c `cbz w24,0x438f8`（掩码未置位则跳过）；0x43184 `b.ne 0x43940` → 失败打 `possible repack/theft` → 0x43974 `bl 0x48af4`("check-signature","fail") → 0x43218 "signature check failed" → 0x43220 `bl 0x48f10`。随后 0x43224 `mov w0,#0x4000; bl 0x48fb8`（掩码位测试）→ 未置位→0x432a0 上报 `"server-verify":"skip"`→0x43c18。另有 `check-signature="soft"/"pm-cross-missing"`（0x443c4/0x443c8/0x443cc）。
**判据**：sig-check 只进报告/掩码，**不参与密钥**，属「可容忍失败」项。

## ④ 兜底 patch 点评估

**先决约束（实测）**：`.text` **全段**自校验，函数 0x555f8–0x557f4：
- 0x55660 `dladdr(0x178f0 锚串 "…STXTANCH01…")` 取加载基址
- 0x5562c/0x55630 读 `.rodata` **0x17900 = 0x24d40**（偏移）、**0x17908 = 0x3d85c**（长度）
- 0x55698 `bl 0x49700`(SHA-256) → 0x556ac 与 `.rodata` **0x17910..0x17930** 逐字节 XOR 累积
- 覆盖 **0x24d40..0x6259c＝整个 .text**；期望摘要 `70b63c1e70266bc49d541eb5761e4686806398d8b17bfc002757fab67dec2020`
- 失败 → 0x55778 `self-check: .text segment tampered (possible patch)`，返回 1；调用点 0x42a7c/0x42a80 → `phase self-text fail`

| # | 地址 | 改法 | 字节 | 风险 | 难度 |
|---|---|---|---|---|---|
| A | .rodata 0x17900/0x17908/0x17910 | 把校验区间改为不随 patch 变化的常量（offset=0x17930、len=0x20），重算 SHA-256 写回 | 48 | **零 .text 改动**；该表实测仅 0x55660–0x556ac 一处引用 | 低 |
| B | 0x43184 `b.ne` | NOP(`1F 20 03 D5`)→sig-check 恒过 | 4 | 只让报告变绿，不解密 | 低·无效 |
| C | 0x563a4 `cbz x23` | NOP→空串也继续 | 4 | KEY 由空串派生仍错 | 低·无效 |
| D | 0x43dd4 `tbz` | NOP→失败也 AES | 4 | sp+0x290/0x278 未写入（脏栈），必失败 | 低·无效 |
| E | 0x564a0 起 | trampoline 把 KEY/IV 换硬编码常量 | ≥60 | 需先实测 dump .bss 的 32B KEY+16B IV | 高 |
| F | 0x563a4 附近 | 让 0x55a78 返回**预置官方签名串**（放 .data 常驻区） | ≥24+数据 | 需复刻输出格式；但官方 v2 证书**可从原包离线提取**，是唯一能离线算对 KEY 的路线 | 中高 |
| G | 导出 SecShell_DeriveKey(0x5b4c0) | 通用 KDF（salt=.data 0x6e0ce，内调 `SecShell_Ticket@plt`），非 key 直出接口 | — | 不宜作 hook 点 | — |

**A+F 是唯一可能自洽的静态路线**；A+E 需先实测 dump .bss（IV 0x787a0 / KEY 0x788a0）。
链式后果：F 实为「把官方签名串钉死」，因任何重打包都会使 v2 块失效。

## ⑤ 「运行时替换够不够」结论

**不够（实测级判据）**：
1. 走 PackageManager 的只有 sig-check(0x557f4)，输出仅进 `check-signature` 报告项与掩码位（0x48fb8/0x48f8c），**不参与解密**。
2. key-unwrap(0x562e4) 的输入来自 0x55a78 对内存 APK 的 v2 块解析（memcmp "APK Sig Block 42" + 内存 buffer 读取 0x4b3a0），**完全不查 PackageManager**；`.data:0x6e0cd = 0x01` 实测锁死该分支。
3. 故 Java/Frida 伪造 getPackageInfo 签名最多让 `check-signature` 变 pass、消除 repack 报告，**asset/dex 仍解不开**，StubProvider 仍 missing。

**要真跑起来三选一**：(a) 让 0x55a78 读到官方 v2 块（与改包矛盾）；(b) 硬编码官方 KEY/IV（需实测 dump .bss）；(c) 钉死官方签名串（F，证书可从原包离线提取，格式待复刻）。任何 .text 改动都要先做 A，否则被 self-text-check 抓。
