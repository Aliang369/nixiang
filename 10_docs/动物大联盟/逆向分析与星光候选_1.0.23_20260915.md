## 启动兼容处理

APKSecure 在 `dev.mars.secure.ProxyApplication.attachBaseContext()` 中启动原生签名校验。重签后仅追加 dex 不足以启动，因此：

1. Manifest 的 Application 改为 `com.starry.magic.dwdlm.DwdlmApplication`；
2. 该类继承官方 `dev.mars.secure.ProxyApplication`；
3. 在调用 `super.attachBaseContext()` 前安装 `SignSpoof`，将官方 `CN=shan` 证书回灌到 `PackageManager` 证书路径；
4. 随后才进入 APKSecure 原初始化，避免 `key unwrap failed (sig/package mismatch)`。

该路径的静态结构已核对；真实 APKSecure 启动结果为 NOT PROVEN，需装机后以 `dev_mars_native` 日志确认。
## 2026-09-16 深夜补充：APKSecure 全局校验点已打通

本轮不再盲调 boot 偏移，改为重扫 `libsecret.so` 的全局校验与状态机，结论如下：

1. `SecShell_Require(name,result,detail)` 不能把所有结果统一改成 `pass`。
   - `server-verify` 在本包没有 endpoint，原结果应为 `skip`；强改 `pass` 会让后续 `token-gate` 进入“必须有 token”的分支，`onShellCreate` 提前返回。
   - 现在只把环境/自校验类 `fail` 提升为 `pass`；`server-verify` 固定 `skip`，`kill-on-fail` 保留原值。
2. 壳状态变量地址（ELF 重定位核对）：`0x70318`=dirty、`0x70328`=checked、`0x7032C`=failed、`0x70358`=attach-ready。
   - 之前误把 `0xFFF` 写进 dirty，导致 `onShellCreate` 跳过 `BingoApplication.onCreate`。
   - 现在在 `onShellCreate` 前同时归一化内存状态与 `.sec_shell_state` 文件：`ready=1/dirty=0/failed=0/checked=0xFFF`。
3. 真机冷启动已实证：`onShellCreate after app=com.bingo.cocos.bridge.BingoApplication`，`BingoApplication.onCreate` 执行，`PluginHelper` 初始化链正常。
4. `evalString` 入口定位已修正：`dlsym(RTLD_DEFAULT)` 看不到壳私有 namespace 里的 JNI 桥；改为内存解析 `libcocos2djs.so` ELF dynsym，拿到 JNI 桥后再沿 `BL` 解析到真实 `ScriptEngine::evalString`。
   - 冷启动日志：`evalString resolved from JNI bridge jni=0x... target=0x...`，hook 安装成功。

## 2026-09-18 停止结论（最终）

用户决定停止本作，不再继续资源更新/星光落地；本节覆盖前文所有未闭合推测。

### 干净对照结果

- 设备上的 `fs-arm64` Frida server 是最初的环境污染源。关闭后官方原包可正常：`BingoApplication.onCreate` -> `onSetVersionCallback` -> `检查更新完成/资源列表下载完成` -> `下载完成`，`files/res` 生成 33676 个文件。
- Frida 开启时官方包会跳过 `BingoApplication.onCreate`，`PluginHelper` 未初始化，随后退出，不能作为基线。
- `spoof-only`（仅签名伪装 + 自定义 Application，无星光 Hook）：Frida 关闭后仍不能完成 unshell 到 `BingoApplication`，没有更新回调。
- `state-only`（只做状态归一化）与 `data-only`（只轮询数据状态、不改 libsecret/Cocos 代码）能把 `BingoApplication.onCreate` 拉起来，但原生更新回调仍不触发，停在数据检查并随后 `exit(0)`。
- 在 Frida 观测中确认自然 `checked` 掩码是 `0x7ef`；将代码从原先强写的 `0xfff` 改成 `0x7ef` 后，`data-only` 仍未恢复更新，因此这不是单点修复项。

### 根因判断

- APKSecure 除签名外还校验受保护条目，并检测新增 dex/so。星光包必然新增 `classes2.dex`、`libstarry_magic.so`、`libc++_shared.so`，同时修改 `AndroidManifest.xml`，因此签名伪装只能过签名，不能过完整性。
- 完整性失败后，壳虽然可被强行归一化状态并 unshell，但没有恢复官方完整校验后建立的内部票据/生命周期状态；游戏原生更新器因此不进入 `onSetVersionCallback`，`files/res` 不下载。
- 结论：要保留原版下载路径，必须让受保护条目在壳看来完整，或补齐壳的完整票据/请求链，或在原生更新门禁处做定向绕过；仅靠签名伪装和状态变量归一化不足以解决。
