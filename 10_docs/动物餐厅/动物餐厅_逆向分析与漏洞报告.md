# 上篇：漏洞总览

## 1. 目标概况

- 引擎：Cocos Creator JS（`.jsc` = XXTEA(padding=False, key=`431FEWJOTe-gecTW`) + gzip）
- 服务器：国内 native 服 `https://ios-inland-restaurant.twomiles.cn:8060`、微信小程序服 `https://restaurant.twomiles.cn`、QQ 服、全球服、HK 服
- 身份体系：客户端 RSA(512, PKCS1 v1.5) 加密 openid 作为唯一身份，**无 Cookie/Authorization/会话绑定**，`sessionKey` 为 `"undefined"+时间戳`
- 经济体系：货币/道具为**客户端权威**（本地 `changeData` + 云存档上传），服务端多数“奖励”最终仍需客户端本地写入

## 2. 测试方法

- 静态分析：解密全部 `.jsc.js`，梳理 160+ HTTP 接口与 WebSocket 协议
- 动态验证：真机（root/PLK110）+ 补丁版诊断包 `[NET]` 日志；跨服务器接口直连测试
- 仅使用自有账号：微信小程序号（阿亮）、游客号、一次性游客号

## 3. 漏洞清单

### 3.1 高危

#### 3.1.1 全局缺失会话鉴权，身份仅凭 openid（根因）

所有接口只认请求中的 `openid`（RSA 加密），无会话/Cookie/二次校验。攻击者拿到任意账号的 openid 即可冒充该账号调用绝大多数接口。

**修复建议**：统一登录态（会话 Token/Cookie），服务端将 openid 与会话绑定；对所有状态修改接口做归属校验。

#### 3.1.2 openFudai 跨账号货币入账（已实测）

- 接口：`POST /openFudai`
- 请求：`openid`（访问者，随机 64 字节也接受）、`friendId`（目标**明文 openid**）、`money/star/magnifier/money_film`
- 影响：给任意账号挂“好友收获福袋”，数值无上限、无频控、可重复累加（实测 990000×3 + 测试笔直接入账）
- 领取：目标客户端 `getFudaiInfo` → `getFudaiReward` 本地入账
- 修复：服务端校验访问者身份与好友关系、限制金额与频率、对 friendId 做归属/绑定校验

#### 3.1.3 searchFriendById 返回目标明文 openid（已实测）

- 接口：`GET /searchFriendById`（friendId 可为“复制编号”即 RSA 密文）
- 影响：加密编号 → 明文 openid，是后续一切越权的钥匙
- 修复：仅返回必要展示字段，不返回 openid；或要求会话

#### 3.1.4 downloadRecord 任意 openid 读完整云存档（已实测）

- 接口：`GET /downloadRecord`（native 挑战应答，公钥在客户端）
- 影响：可下载任意账号完整本地存档（291/257 个键），数值可用 `globalKey=openid` 解码（实测 money/diamond/star 等）
- 修复：下载前校验请求者会话与 openid 归属；存档字段按需最小化

#### 3.1.5 changeSelfInfo 任意 openid 改昵称/头像（已实测）

- 接口：`POST /changeSelfInfo`
- 影响：给任意账号改名/改头像（越权写，可用于冒充/骚扰），实测一次性游客改名成功
- 修复：服务端绑定当前登录 openid，禁止客户端指定他人 openid

#### 3.1.6 getAllFriends 任意 openid 读好友列表（已实测）

- 接口：`GET /getAllFriends`
- 影响：读取任意账号好友列表，含好友**明文 openid**、昵称、头像、starSum（实测读到阿亮好友 `oe6z64oMu...`）
- 修复：校验会话与 openid 归属

#### 3.1.7 acceptActivityInvite 任意邀请刷记录（已实测）

- 接口：`POST /activity/acceptActivityInvite`（openid=任意接受者，inviterId=目标明文 openid）
- 影响：给任意账号刷邀请记录（实测 liby/christmas2025 入账），活动开启时可刷邀请奖励
- 修复：校验接受者真实登录态、邀请来源与关系，限制次数

#### 3.1.8 WebSocket / AI 客服通道弱认证（已实测）

- 地址：`wss://restaurant.twomiles.cn:8001`
- 认证：`{type:"auth", openid:<明文>, code, codeType}`；`codeType:"native"` + 随机 code 即可对**任意 openid** 认证成功（微信 code 才校验）
- 影响：冒充任意账号与 AI 客服（大模型流式对话）发消息/收回复；配合 `customer-service/getChatHistory` 可读对方聊天记录
- 修复：WS 认证必须绑定登录态，不允许 native 伪 code 冒充

#### 3.1.9 visitFriendHome / visitFriendCourtyard 越权读（已实测）

- 接口：`POST /visitFriendHome`、`GET /visitFriendCourtyard`（仅目标 openid + keyMap，无请求者身份）
- 影响：读取任意账号庭院布局、家具坐标/状态、养殖等私有数据
- 修复：校验好友关系与会话

### 3.2 中危

- `getSelfInfo` / `getSignupTime` / `getBlockedUserInfo`：任意 openid 读取资料、注册时间、反作弊状态
- `customer-service/getChatHistory`：任意 openid 读取对方 AI 客服聊天历史
- `sendEmail`（圣诞贺卡）：任意 `fromOpenId/toOpenId`，可伪造发件人给任意账号发卡（无道具载荷）
- `tapjoy/ironsource getCurrency`：任意 openid 查 offerwall 余额；`spendCurrency` 余额为空也返回成功（奖励仍为客户端本地发放）
- `receiveReward`：rewardId 不校验（返回 0），但客户端无 dataMap 条目不发奖，影响受限
- 客户端免广告/免支付（**12.37 真机已复测通过**）：
  - 免广告：钩 `AppActivity.showRewardAd` / `isRewardVideoADReady`（及/或 `userData.isAdReady`/`realShowAd`）
  - 免内购：`PayMentModel` 渠道 fakepay + **`PayMentSystem.changeOrderStatus` → true**；菜单侧用 `window.__starryNoIap` jsc 门控最稳
  - 详见下篇 §8 / §10.3 / §10.5

### 3.3 低危 / 残余风险

- `MiPayNetSign` 密钥 `twgame_MiJJc` 客户端硬编码：微信小程序支付“先建单不支付 + 伪造 wxMiPaySuccess”组合路径（需目标微信会话内 hook/改包）
- 分享/邀请链接明文泄漏 openid：`inviteId=`/`openid=` query；native 分享 `info` 为 AES-CBC，key/IV 客户端硬编码可解
- 本地存档弱加密：`globalKey=twgame_rj32io`（游客）或账号 openid，`t+5位MD5+3位随机数+数值`，客户端权威可改
- debug 残留接口 `debug_sync_item`/`debug_flush_data`：当前无效果

## 4. 已排除 / 无效路径

- 兑换码自制：`getOneCode` 服务端 DB 校验，真码已用返回 -1000，其余 -100，10 位随机空间不可枚举
- 邮件带奖励：`sendEmail` 字段固定，附加 reward/items 被服务端丢弃
- 云存档注入（uploadRecord）：只能更新已有存档，外部伪造被服务端异常检测并处罚账号（实测 App 微信账号被暂停存档）；微信/QQ 小程序走平台加密
- 云存档写入（app_wx 重放/改值）：真实客户端抓包原样重放仅短暂成功 1 次，随后被记录一致性校验拒绝；稳定窗口实验前第三个微信测试号再次被处罚，判定 app_wx 写档/改值不可行，仅一次性 guest 全仿真可写（详见下篇 §9.48–§9.49）
- 云存档注入（uploadRecord）：已修正——native 账号走“loginNativeGuest → checkLogin(完整参数+设备签名) → checkRecord → uploadRecord(伪造 MD5 签名)”完整时序可真正落库且未触发处罚（一次性游客实测）；App 微信账号曾触发处罚，可能与缺失登录时序/真实账号风控有关；微信/QQ 小程序仍走平台加密不可写
- uploadStar 排行榜伪造：服务端返回 -100
- 支付验单盲打伪造：`checkPayment`/`checkWxMiOrder`/`wxMiPaySuccess` 对不存在的订单全部拒绝
- 神秘盒/盲盒：活动休眠，接口空数据

## 5. 修复建议汇总

1. 建立统一会话鉴权，服务端强制校验 openid 归属
2. 敏感读写接口（好友、云存档、资料、庭院、福袋、邀请、客服）增加会话 + 关系 + 频控校验
3. 服务端对 `openFudai` 金额/频次做白名单与上限，禁止负数/异常大额
4. 客户端签名密钥（MiPayNetSign/AES/globalKey）迁移到服务端，不做硬编码
5. 移除或关闭 debug 残留接口与明文分享参数

## 4. 发现的漏洞/风险点

### 4.1 本地存档对货币“弱加密”且客户端权威

- 位置：`assets/main/index.jsc.js` userData（约 61351-61720 行）
- `globalKey = "twgame_rj32io"`
- 数值写入格式：`"t" + 5位MD5校验 + 3位随机数 + 数值`
- 关键本地键：
  - `money_diamond` 钻石
  - `money_skipAdCard` 免广告卡
  - `money` / `money_plate` / `money_bell` / `money_film` / `fastener`
  - `freeDiaMondCount` 免费钻石次数
  - `debugTime` 调试时间偏移
- 影响：知道格式和 `globalKey` 即可离线伪造/修改本地货币；实际设备上也可直接改 `/data/data/inland.twgame.restaurant/...` 中的 localStorage 文件
- 限制：`proxyObj` 对部分对象做 `MD5(obj+"proxyObj")` 签名，改坏会 `gameClose`，需要同时更新签名

### 4.2 广告奖励完全由客户端回调决定（免广告/刷奖励）

- 位置：`assets/main/index.jsc.js` `showAd` / `realShowAd`（约 62324-62450 行）
- Android 端通过 `org/cocos2dx/javascript/AppActivity.showRewardAd()` 拉起广告，结果写入全局 `RewardAdCallback`，JS 收到 `"0"` 即回调成功并发放奖励
- 免广告卡路径：`money_skipAdCard > 0` 时 `showAd` 直接弹“跳过广告”界面，不播放广告
- 多处业务判定：`isAdReady() || getDataSync("money_skipAdCard")`，本地改大该值即可全局免广告
- Frida 可验证：hook `RewardAdCallback` / `showAd` / `isAdReady`，把广告结果直接置为成功

### 4.3 免费钻石可无限领取

- 位置：`assets/Script/index.jsc.js` 约 393840-393880 行 `onFreeDiaClick`
- `freeDiaMondCount == 0` 时直接发放 `freeDiamond`，不播广告也不验服务端
- 把本地 `freeDiaMondCount` 清零即可反复领取

### 4.4 内置 GM/调试功能

- 模块：`GMHelper`、`GMToolDlg`、`GMTool2Dlg`、`debugInputDlg`
  - `assets/Script/index.jsc.js` 198315 / 199165 / 199255 / 393317
- `config.isDebug = false`，但 Frida 可改；`isDebug` 打开后界面会生成 DEBUG 按钮（`createGMButton`）
- `debugTime` 支持时间快进 1 分钟/5 分钟/1 小时/6 小时/1 天/30 天（约 201988-202050 行）
- `debugAllBad` / `debugAllGood` 可绕过“广告是否就绪”判定（如 83926、84115、295902 行）
- 注意：这属于测试功能残留，不是上线本应保留的功能

### 4.5 服务端调试接口残留

- `netManager` 暴露 `debug_sync_item`、`debug_flush_data`（`assets/main/index.jsc.js` 55890-55915 行附近）
- 正式服若未禁用，可能被用来同步/刷数据；需动态抓包确认

### 4.6 IAP 支付有服务端验证，纯本地“免支付”较难

- 渠道支付方法在 **`PayMentModel`**（`androidWxPay` 等）；`purchaseSuccess` / **`changeOrderStatus` 在 `PayMentSystem`**（12.37 已核对，勿混为一谈）
- `purchaseSuccess` → `changeOrderStatus` → 按渠道调用 `checkPayment` / `verifyOrder_Huawei` / `verifyWxAppPay` 等服务端接口，通过后才 `receiveOrderItems` 发奖并 toast
- 因此“免费购买付费礼包”不能只改本地；客户端免支付须同时假渠道成功 + 让 `changeOrderStatus` 过关（见 §8 / §10）
- 4.1-4.3 的钻石/货币/免广告路径仍足够影响游戏经济

### 4.7 反作弊为客户端计数，可被本地重置

- `cheatingAdNum`、`cheatingCount`、`cheatingTouch` 等均为本地计数，只弹警告/限制
- `uploadSyseyeCheatingTouch` 上报也可能被 hook 掉

## 8. 免支付最终方案（真机实测通过）

- 修改内容（v4 包内）：
  - **`PayMentModel`：** `androidWxPay` / `sdkboxPay` / `wxMiNiGamePay` / `qqMiNiPay` / `wxIOSPay` / `huaweiPMSPay` / `googlePay` / `globalIosPay` / `inlandIosPay` 全部直接返回 `{status:0, orderItem:{orderId:"fakepay", payType, pay_situation}}`
  - **`PayMentSystem`：** `changeOrderStatus` 固定返回 `Promise.resolve(true)`，跳过服务端验单（**与渠道方法不在同一类**）

  - 只 patch 渠道、不 patch `PayMentSystem.changeOrderStatus` → 会进支付页或返回无 `pay_success`（12.37 菜单首版踩坑，见 §10.2）

- 成品：`08_output/动物餐厅_12.35_patched_v4-aligned-debugSigned.apk`

## 9. 微信登录与“ID 刷奖励”机制

### 9.1 微信登录失败原因

- 微信服务器校验的是真实 APK 签名，我们 patch 的 `DeviceHelper`/`TapSignKit` 只影响游戏服务端和 TapTap，微信开放平台仍按 debug 签名校验，所以返回“签名不对”
- 免广告/免支付为客户端逻辑 patch，与登录方式无关；游客登录不受影响

### 9.2 ID 显示与存储

- 设置里“复制 ID”复制的是 `base64(RSA(openid))`（`copyToClipboard` 中 `f.encrypt(c.openid, "base64")`），不是明文 openid
- 明文 openid（如 `guest_xxx`）存在 `jsb.sqlite` 的 `openid` 字段，几乎所有服务端请求都带它

### 9.3 “只凭 ID 刷奖励”的疑似服务端接口

- `addActivityItem`：`addLibyActivityItem` 把请求里的 `openid` 设为客户端自己的 openid 后 POST，载荷形如 `{openid, num}`；若服务端不绑定会话，拿到目标 openid 即可给任意账号加 Liby 活动次数并兑换奖励
- `debug_sync_item` / `debug_flush_data`：调试用活动数据接口，正式服未关闭时可被直接调用
- `receiveReward`：带 `openid + rewardId + orderId`，若校验弱可被枚举/伪造
- `code/checkCodeUsed`：兑换码接口，若码可预测或可复用也可能被刷
- 以上均需抓包确认服务端是否真的缺少鉴权；建议只在自己测试账号上验证

  1. 本地存档/客户端注入：货币道具客户端权威，改本地数据或 hook RewardConfig.receive 后云同步（可发任意道具，但不是纯服务端“只凭ID”）
  2. 泄漏的运营/GM 后台：对任意 openid 直接发任意道具（内部权限，不在 APK 内）
  3. 旧版本或其他服务器集群残留接口：本版本/服务器不可用
  4. 官方手动补偿条目：服务端配置，普通玩家无法自行注入

### 9.21 云存档注入验证结果与账号类型边界（2026-08-05）

- 游戏内云存档 UI：`showRecordDlg` 对 `userType=="guest"` 走 `onGuestAuth`，游客正常没有云存档入口（UI 层限制）
- 但服务端 `uploadRecord` 不校验 userType：直接用游客号伪造存档（无害标记键）上传返回 `{"status":0}`，下载回读确认已落库，随后已恢复原档（291→292→291 键）
- 真实可利用对象：native 登录账号（app_wx / app_qq / app_apple / app_fb / app_line / app_huawei 等）使用同一 native `uploadRecord`（checkSign2=MD5("32roiFEI"+record+openid) 截取，secret 客户端硬编码），只凭明文 openid 可伪造任意存档
- 不可利用对象：微信/QQ 小程序账号走 `uploadEncryptRecord`（平台 crypto manager 加密），外部无法伪造；阿亮（微信服小程序账号）不受此漏洞影响
- 生效条件：目标客户端执行“下载云存档/换机/重装/数据转移”时才应用注入存档；目标本地已有数据时通常本地上传覆盖云端
- 数值加密复刻：getEncryptString 为 `t + MD5(value+100+rand + globalKey + key)[17,3,27,11,23] + rand + value`，globalKey 会被设置为账号 openid（游客号实测 = openid）

### 9.23 微信小程序云存档加密机制（2026-08-05）

- 加密方式（代码确认）：`wx.getUserCryptoManager().getLatestUserKey()` 获取 `encryptKey/iv/version/expireTime`，CryptoJS AES（默认 CBC/PKCS7）加密整份存档，请求只带 `{encryptedData, encryptKeyVersion}`
- 密钥来源：微信运行时按“当前小程序用户会话”下发，按用户+时效，**不存在客户端包内**，外部只凭 openid 拿不到
- 服务端用对应 version 的微信用户密钥解密；攻击者无该密钥无法伪造/篡改
- 唯一获取途径：hook 目标设备上正在运行的小程序（抓 getLatestUserKey / wxEncryptData 的明文与密钥），等于设备级控制，不是“只凭 ID”
- 结论：微信小程序账号云存档注入对只凭 ID 的外部攻击封死；云注入有效目标仅为 native 登录账号（app_wx/app_qq/app_apple 等，走 MD5 签名的 uploadRecord）

- “给其他号加钻石”可行路径：设备/链路侧云存档注入（money_diamond 等），需控制目标账号会话；或本地免支付 patch 后云同步，非服务器充值、无订单流水
- 残余未实测：拿到真实 orderId 后伪造 wxMiPaySuccess（MiPayNetSign 密钥硬编码 twgame_MiJJc），需真实订单/泄露订单，风险高
- openFudai 仍只支持 money/star/magnifier/money_film，不支持钻石/充值

### 9.63 跨账号应用条件（2026-08-05）

- 给其他号改档必须让目标号在可控环境登录：服务端只接受活动客户端会话写入，平台密钥按用户+会话+时效下发，外部直传不落库
- 流程：目标号登录 → 抓 getLatestUserKey → 触发上传 → mitmproxy 解密改值 → 重加密放行 → 强制下载生效
- 电脑 QQ 小程序理论可行但需 PC 端运行时 hook（非 Android J2V8），工具链未打通；当前已验证链路仅 Android 真机 QQ/微信小程序
- “只凭 ID”不可行；多号通用工具可将 Frida 抓钥结果写配置，mitmproxy 插件按目标号动态读取

### 9.66 checkBlackInfo 一致性导致 -2801 临时风控（2026-08-05）

- 现象：配置 `money_checkInCard +10000`、`money_bell +33` 后上传，游戏提示封号
- 抓包：`uploadEncryptRecord` 返回 `status:0` 落库成功，但随后 `checkBlackInfo` 返回 `{"status":-2801,"banLevel":1}`，客户端 `checkToShowBanNotice` 弹 BanNoticeView
- 根因：`checkBlackInfo` 会另外明文上报 money/cumulative_money/diamond/plate/film/bell/skipAdCard/playTime/starSum 的 t 值；代理只改了加密上传的 `money_bell=100000033`，`checkBlackInfo` 仍上报 `100000000`，服务端两侧对不上判定异常
- 修复：`modify_addon.py` 现在同时改写 `checkBlackInfo` 的 record（无前缀 t 字段），并同步改写 `checkRecord` 查询参数 money/dia/plate/bell/skipAd
- 复查：`getBlockedUserInfo` 仍 `isBlocked:false`，账号未永久删除；`banLevel:1` 更可能是临时风控提示，后续验证应换一次性新号，先小改再上传
