## 中断 / 第二失败恢复用例清单

1. happy path：双文件替换成功 → journal 清理 → project.manifest 字节不变（实测比对）
2. 幂等：双 patched → NOOP，不写 journal
3. 未知 hash → ABORT_UNKNOWN，一个字节都不写
4. 起始混态 → ABORT_MIXED，不盲写，提示先 recover
5. 第二文件 rename 失败 → 回滚第一文件，双原件保全，journal 记 `failed_rolled_back`，recover → CLEANED_ROLLED_BACK
6. 第二文件之前中断（模拟崩溃、不回滚）→ 落成混态，recover 判混合 → 用备份回滚到双原件（RECOVERED_ROLLBACK）
7. 双文件都换完、journal 未删时崩溃 → recover 判双 patched → CLEANED_DONE，文件不动
8. 残留 `.dwct.tmp` → 拒绝覆盖（防半写入），原件不动

替换顺序：main 先、Script 后。理由：main 的 bootstrap 定义 `window.__starryGate`，Script 的门写作 `window.__starryGate && …`；两种半套态都只会让门恒 false（不崩），但仍按"混合即回滚"处理。

## 未证 / 已知未知（不得写成已解决）

- **native `jsb.AssetsManager` 是否在非下载路径回调 verifyCallback 未证**（C++ 不可见）。JS 层只能看到：`setVerifyCallback` 在 `createAssetsManager` 注册一次；`verifyRemoteManifest` 唯一调用点在它内部，读的是 `restaurant-hot-update_temp/project.manifest.temp`（下载来的清单）并做 RSA 验签。`ALREADY_UP_TO_DATE` 只说明版本相等，**不能推出 native 没有别的完整性检查**。
- **signed manifest 一律不动**：sign 用内置公钥 RSA 验签、无私钥 ⇒ 伪造 sign 不可行（硬结论）；改 md5 是否有检查取决于是否走 update 校验路径，且即便不被检查也无收益（校验是拿下载清单的 md5 比对下载文件）。
- 服务端是否接受官方签名（即 -18 是否由签名驱动）**未证**，本原型不触碰服务端、不吞 -18。
- 真机是否生效、稳定性、掉帧/崩溃均未测。
- 官方热更 bump 版本后会下载新文件覆盖补丁：**补丁必须重新识别 hash 再重放**；未知 hash 一律 abort，不盲写。
