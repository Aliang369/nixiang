## 3. 「单看这两条路径能修吗」——分两层回答

### 3.1 这两条路径本身：查过了，没有可修的缺陷

**路径 A：签名回灌 `SignSpoof`（+ `SignSpoofAppComponentFactory`）**
- 装机时序对：Manifest 实测 `appComponentFactory=SignSpoofAppComponentFactory`，Application 保持官方 `AccessSDKApplicationWrapper`；factory 在 Instantiator 阶段执行，早于 `attachBaseContext`/Provider/TapSDK 取数。
- 取数面全覆盖：全 APK 唯一读 `GET_SIGNATURES` 的是 `TapSignKit.getSign`（`getPackageInfo(pkg,0x40)` → `signatures[0]` → MD5）；另外真读 `signatures[]` 的第三方=闪验一键登录(`shanyan_sdk/tool/h`，取 MD5)、移动一键登录(`cmic/gen/sdk/e/l`)、图灵盾、QQ/微信/支付宝与广告 SDK——**全部走被我们改写的那个数组**。
- `SigningInfo` 新 API 在本包只有 `androidx.browser`(TWA) 一处用，与登录无关，所以「数组被 clone 导致改写丢失」这个隐患对本包不构成问题。
- 烘焙证书复核无 明日方舟 那类 base64 事故：DER 845B，MD5 `c9950f9c…`、SHA-256 `b147f6a4…`、`CN=sagely`，与 09-19 记录逐位一致。

**路径 B：强制网页登录 `TapLoginForceWeb.sanitize()`**
- 本包 TapSDK=4.5.0（`tap-login_release`），dex 逐条核验：`com.taptap.sdk.login.ui.TapTapLoginActivity.impl` 为 final、构造器内 new（PreCreated 时必非空）；`LoginActivityImpl.loginHandlers=[Cloud, Client, Phone(单例)]`；`LoginHandler` 只有 `canHandle`/`getFragment` 两个方法（noop 代理返 false/null 安全）；`onCreate` 遍历无一命中 → `fallbackToWeb`，异常分支 `catch(Throwable)` 后同样 `fallbackToWeb`。
- `com.wanda.sf3.wd` 确在包内 classes8.dex 的白名单里。

⇒ **这两条路对本包是「装得早、覆盖得全、命得中」的。要在这两条路里找一个能解释外部登录挂的 bug，静态上找不到。**

### 3.2 但登录根本不是这两条路管的

- 游戏账号体系是 **hoolai access SDK**（`com.hoolai.access.account.*`：`AutoLoginActivity` / `LoginPhoneFragment`(手机号+验证码) / `QuickLoginFragment`+`shanyan/PhoneQuickLogin`(运营商一键取号) / `RealNameFragment`(实名防沉迷) / `TAPLogin`(TapTap 入口，`loginWithScopes`)，底层 `com.access.platform.library.*`）。
- 该 SDK 的 **Java 层没有任何签名校验点**；它的服务端侧（`productId 3015 / channelId 10247`）风控与 iZinNO/图灵盾/闪验这类**字符串加密的 native 采集**（`libturingad.so`/`libmsaoaidsec.so` 内确有 `/data/app/` 串），不走 `PackageManager`，签名回灌兜不住。
- 也就是说：若报错用户的登录方式是一键取号/实名/服务端风控拒绝，或用户包不是这一版，**改这两条路径不会有效果**。

## 7. 按「sdk + 非正规」两条提示重做的定位（2026-09-20 18:4x，补充 §3/§4）

操作者澄清：现象是**两条提示**——一条含「SDK」、一条含「非正规」；无报错用户日志。按此重新定位，`§3.2` 的"两条路无可修缺陷"结论**不变且更强化**。

### 7.1 两条提示的出处（实测）
- **`非正规` ⇒ `NOT_GENUINE_APP = 非正版应用，请下载正版应用`**，在 **hoolai access 渠道 SDK 的文案表** `assets/access_localization.ini`（简体第 46 行；繁体第 156 行 `非正版應用程式，請下載正版應用`）。
  - 设备上 `/sdcard/Android/data/com.wanda.sf3.wd/files/access_localization.ini` 与包内**逐字节一致** ⇒ 文案没被热更覆盖，这条就是 access SDK 自己的报错，不是 TapTap、不是星光侧文案。
  - 全包（8 个 dex + resources.arsc + assets 全条目流式扫描，脚本 `/tmp/sf3_login_audit/scan_apk.py`）**只有这一处**「非正/正规」类字串；游戏自身本地化表（`assets/bin/Data/e713034e…`）里的 `盗版/非正` 命中全是「健康游戏忠告」与剧情文本，非报错。
  - 该 ini 的 key 在 Java/dex 与 `libaccess.so`/`libdata.so` 明文中都**没有引用点** ⇒ 取文案走动态 key（native/服务端下发码 → 查表），符合 access SDK 的 `JNIShowHandle::PopAloneToast/PopViewToast(std::string)` 弹法。
- **`SDK` ⇒ 同一张表的初始化类文案**，候选（按 native 事件顺序）：`INIT_SYSTEM_ERROR 初始化系统异常`、`INIT_CFG_ERROR 初始化配置文件异常`、`PARSE_INIT_INFO_ERROR 解析初始化数据错误`、`CHANNEL_NOT_SUPPORT_LOGIN 渠道登陆不支持`；
  `libdata.so` 里的渠道初始化事件名 `start_channel_init` / `channel_init_success` / `channel_init_failed` / `channel_init_timeout` 说明**渠道初始化**是有独立失败/超时分支的，与「SDK 初始化」类提示对应。⇒ 需要操作者给准确文案才能定到具体 key，不猜。

### 7.2 正版校验实际在哪（静态实测）
- `libaccess.so`：`ConvertUtil::appSignatures(_JNIEnv*, _jobject*)`、`ConvertUtil::formatSignatures(std::string const&, std::string&)`、`HNDynamic::CongfigSignature(std::string const&)`，字符串面 `signatures` / `[Landroid/content/pm/Signature;` / `SHA1` / `signature is NULL!!!`
  ⇒ **这一路是走 JNI 取 `PackageInfo.signatures` 的**，在 `SignSpoof.applyFake` 的改写覆盖面内（回灌官方 `CN=sagely` DER 后，native 拿到的就是官方证书）。
- `libdata.so`：`HNSDKMgr::UpdateSignatureMd5(std::string)` / `HNSDKMgr::SignatureMd5()`；请求参数面有 `sign`、`signature`、**`binarySign`**，以及头模板 `oaid;idfa;deviceId;app-version;core-version;sdk-version;package-id;content-type`、路径 `/official/realName/verify`、`/official/authorization/token/verify`、`/channel/…/verifyActivity/`。
- 包内同时存在 **网易易盾 NIS**：`com/netease/nis/sdkwrapper`（混淆包装）+ **`libEncryptorP.so`**（全库字符串加密，除自身名字外无可读串）。`binarySign` 属于对 **APK 二进制/签名块** 的原生证明，**不经过 `PackageManager`** ⇒ 签名回灌兜不住这一路。

### 7.3 由此得到的判断
1. 「改 `SignSpoof` / `TapLoginForceWeb` 这两条路径」不能修「非正版应用」提示：它由 hoolai access 平台侧按 渠道初始化/正版校验 判定，且候选判据是 native `binarySign`（易盾），这两条路径都够不着。
2. 本机反证仍在：同一份星光包今天 17:05:37 拿到过服务端 JWT（`channel=hoolai`）⇒ 正版校验**至少不是一进门就必然拒**，需要区分「弹提示但仍可登录」与「弹提示后登录中断」两种现象。
3. 若确认是 `binarySign` 面：可动的方向只有「让渠道初始化不携带/不被判定」（观测易盾调用点与失败分支）——**属于新增改动面，需单独授权，且要评估服务端风控后果，本轮不做**。

## 8. 追加（2026-09-20 晚）：定位到 `HNAccessCore::checkCopyright()` 并落地补丁

§7.2 的 `binarySign` 是一条候选；本轮另在 `libcpp.so` 找到与提示 key **同名**的确定性证据链：

- **字符串面**：`libcpp.so` `0xCE15` = `"Config Signature Md5: NOT_GENUINE_APP"`、`0xDC0A` = `"Config Signature Md5: %s"`、`0xDED0` = `"/libs"`；`libcore.so` 的报错码名表里同样有 `NOT_GENUINE_APP`（与 §7.1 的文案表 key 对应）。
- **函数面**：`libcpp.so` 导出 `_ZNK12HNAccessCore14checkCopyrightEv`（file `0x17320`），由 `HNAccessCore::InitServerCfg`（`0x15E10`）在 `0x162EC` 调用。
- **逻辑**：`HNConfigMgr::SandboxPath()` 取父目录 + `/libs` → `ExistFile`；**不存在则该函数返回 `1`**（干净安装首次启动走这条，所以第一次能进）；存在则 `FileMD5Encrypt` 与 `HNConfigMgr::BinaryFingerprint()` 比对，不等即写 `NOT_GENUINE_APP` 并返回 `0` → SDK 初始化失败（对应「非正版应用」/「SDK init error」两条提示）。
- **返回值极性（反汇编实测，非猜）**：该函数是单出口 `mov w0, w19; ret`；调用方 `tbz w20, #0, 0x1632C`，`ret==1` 落 `0x15F54` 的配置 map 加载（正常路径），`ret==0` 才进异常分支。

**修法**：Dobby hook `checkCopyright` 恒定返回 `1`，等于让所有设备复现「干净安装」的行为；补丁是登录可用性修复、与菜单功能开关无关，常驻生效。挂载时机由 `onLoad`（`Sf3_OnLoad`）起独立轮询线程，不等 `waitLib=libil2cpp.so` + `initDelayMs=5s` 的 `tryInit`；`TryInit`/`Tick` 兜底。

**产物**：`08_output/暗影格斗3/暗影格斗3_1.45.3_surgical-releaseSigned.apk`，md5 `ae42b36dded2ab783522dfe8fe7798ce`，包内 so `62218946c5d81557d0996e0ba926288e`；已同签覆盖装机，设备 `base.apk` md5 一致。

**底包说明**：原版 TapTap 包已不在 `02_apks`，按用户确认「直接用拉回的包改」，走 `04_scripts/暗影格斗3/sf3_so_only.sh`（只换 `libstarry_magic.so` 重签；4962 条原始条目逐字节不变）。

**验证与缺口**：本机进程内存里 `checkCopyright` 开头已被改写为 `adrp x17 / add x17 / br x17` 跳板 ⇒ 补丁**已挂载**实证；但**本机不复现该 bug**（属 §7.3 第 2 条的反证样本），外部问题用户能否救回**只能靠实测反馈**。
