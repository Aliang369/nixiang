## 3. 三次事故与根因（均为本轮实测）

### 事故一：Dobby 直挂热更属性取值口 ⇒ 玩家不再攻击（已回退；该功能 2026-10-17 按用户指定**整项移除**）

- **做法**：Hook `HotFix.Common.AttributeData.GetAttackSpeed()`，命中英雄侧时 `orig × 倍率`。
- **现象**：`atkspd hero x5 0.000 -> 0.001 hits=1..5` —— **取值口恒返回 0**；
  英雄攻速=0 ⇒ **玩家完全不攻击（站着不动）**；连带 **秒杀/全屏一起变 0 命中**
  （玩家不攻击 ⇒ `EntityCharacter.UpdateHp` 根本不被调用）。
- **根因（推断，证据支持）**：热更小方法不适合 Dobby inline hook。仓库既有铁律
  「函数体不足 16 字节 ⇒ Dobby 16 字节补丁会改写紧随其后的邻居方法入口，跳过该槽位」
  （2026-10-17 `nhsy2` 同款告警）。属性取值口极可能正是这种小方法。
- **处置**：**该挂点作废**，代码内留事故注释，`so` 串门禁确认 `atkspd*` 已 0 命中。
- **重做方向（未实施）**：走「数据型」—— 定位英雄 `AttributeData` 实例 +
  `AttributeOneElement`（`AttrKey@0x10` / `Value@0x18`）里的攻速键，`SafeWrite` + Tick 轮询维持，
  **零代码 hook**。前置未知项＝英雄 `AttributeData` 实例指针的获取路径
  （`AttributeOut.attributeData@0x30` 需实例注册表；`EntityCharacter` 63 字段中无属性指针）。

### 事故二：启动期反复全 image 扫描 ⇒ SIGSEGV（已修）

- **现象**：`Fatal signal 11 (SEGV_MAPERR), fault addr 0x4088`，栈在 `libil2cpp.so`；
  崩溃前 200ms 日志为 `ClassFromNameScan: built map for image=… classes=406`。
- **根因**：热更未就绪时 Tick 每 200ms 反复装钩，`FindBattle` 走 `ClassFromNameScan`
  降级路径**逐个 image 建表**，该半初始化窗口内崩溃。与国服早年为 gjc2 定下的
  「**禁止启动期 init，改用户开功能后懒装**（继续局死锁案）」同源。
- **处置**：改懒装 —— **只有用户开了功能才尝试装钩**，启动 **20s（100 tick）静默期**内一律不装，
  之后 ≥1s 间隔、最多 60 次。实测：05:07:19 懒装成功、零崩溃。

### 事故三：调 `il2cpp_field_get_type` / `il2cpp_type_get_name` ⇒ SIGABRT（已撤）

- **现象**：`Fatal signal 6 (SIGABRT) in tid <mod 线程>`，紧随 `DUMP EntityManager` 之后。
- **根因**：install 期（半初始化窗口）调这两个 API 会让 **il2cpp 自己 abort**，
  与仓库已记录的「此时调 `class_from_name`/`class_name` 会 abort」同源。
- **处置**：**移除**，并在代码与 `硬约束.md` 里明令不得再引入；
  字段类型判定改用「读原始字节 + 多解释打印」的纯内存方式。

### 附带陷阱：ndk-build 增量复用 obj ⇒ 探针代码进正式包

`ndk-build` **不追踪编译标志变化**：探针构建与正式构建共用 `obj_gjc2intl` 时，
正式包会复用探针目标文件。本轮靠 so 串门禁（`TYPLIST` 应为 0）抓到。
**已修**：`gjc2intl_so_only.sh` 中 `GJC2INTL_PROBE=1` 走独立 `obj_gjc2intl_probe`/`libs_gjc2intl_probe`。

## 4. 秒杀「有伤害 + 怪物回血」——**已结案**（根因＝本作伤害以**负值**存放）

**实锤（2026-10-17 `RAW#` 探针，秒杀关闭时的原始样本，见 `rec_raw2/logcat.txt`）**：

```
RAW#0 hurtval=0xffffffffffffff9c lo32=-100 hi32=-1 f32=-nan i64=-100 | enemy=EntityMonster hp@0xa0 i32=200
RAW#2 hurtval=0xffffffffffffff6a lo32=-150 hi32=-1 f32=-nan i64=-150 | enemy=EntityMonster hp@0xa0 i32=200
RAW#3 hurtval=0xffffffffffffff9c lo32=-100 ... | hp@0xa0 i32=50
```

| 结论 | 判据 |
|------|------|
| `TakeDamageData.HurtValue@0x30` 类型＝**int64** | 8 字节槽、`hi32=-1` 符号扩展、`i64=-100/-150` 为合理伤害 |
| 伤害以**负值**存放，游戏按 `Hp += HurtValue` 结算 | 原始样本恒为负（-100/-150）；正值样本只出现在我们写入之后（`0x…05f5e0ff`=+99999999） |
| **它不是 float/double** | `f32=-nan`、`f64=-nan` |
| 敌人血量字段＝`EntityCharacter.CurrentHp@0xa0`，类型 **int32** | 按名解析命中 `0xa0`；样本 200→100→50 正常递减；`f32` 解释为 denormal ⇒ 非浮点 |

**根因**：旧代码写 **+99999999**，在该语义下等于**给怪物回血 99999999** ⇒ 用户现象
「打怪有伤害但怪物自动回血」完全吻合（伤害显示来自游戏自身管线，血量却因我们的写入被拉回）。

**修复**：`kOneshotDamage` 改为 **`-99999999`**（一行）。修复后包内 so md5 `b2a4ed8a…`。
**修复效果＝用户实测确认「怪物一击死」**（2026-10-17）。
⚠️ 机器侧缺口：该次验收的记录仪窗口（`rec_final`）被提前停止，日志内无 `oneshot` 行
⇒ 本条**仅有人工口述证据**（按仓规「人工＝终审」成立）；`oneshot dmg=-99999999` 只证明写入方向
正确，机器侧未留对应佐证。

**已排除项（仍成立）**：`HurtValue@0x30` 偏移正确、写 int64 不越过 `Attacker@0x38`；
`AttributeData` 60 个方法各有独立 methodPointer（非共用跳板）。

**方法论教训（写进 `硬约束.md` E9）**：探针**必须读在任何写入之前**，且 `damageData` 可能对象池
复用 ⇒ 取「游戏原始值」必须让对应功能**处于关闭态**。首次探针读在写入之后，白跑一轮。

### 4b. 历史记录（上一版推断，已被上表取代）

原假设为「若 HurtValue 是 float 则 int64 写入读出≈1e-36」，**该假设已被否证**（实测 -nan）。
另对照国服教训：国服 1.1.9 记录「`EntityCharacter.UpdateHp/ChangeHp/BeforeHurtTarget` 全 0 命中
（方法还在、无人调用）」，其全屏改挂 `CharacterComponentOnHit.OnHitByBullet`。
国际版 1.0.1 `UpdateHp` **确实被调用且确实是伤害通道**（本探针在 `UpdateHp` 内直接读到游戏原始
伤害值 -100/-150，非显示侧）⇒ 两版不可互相照搬。
