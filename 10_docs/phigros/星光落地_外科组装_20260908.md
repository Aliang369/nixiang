## 2. 外科方案要点

- 原包仅 1 个 `classes.dex` → 星光 smali → `classes2.dex`（ART 连续 dex 规则）；官方 `classes.dex` / `resources.arsc` / `libil2cpp.so` sha256 脚本内断言字节不动，另做全量 CRC/size/compress_type/名字字节/utf8-flag 对比（mismatch=0）。
- 官方 Manifest application 节点**无 android:name**（默认 `android.app.Application`）→ StarryApp.smali 保持 `.super Landroid/app/Application;`，无需 zhmr 式官方 App 继承补丁；注入=application 挂 StarryApp + SYSTEM_ALERT_WINDOW / FOREGROUND_SERVICE / FOREGROUND_SERVICE_SPECIAL_USE（原包仅 INTERNET/ACCESS_NETWORK_STATE 两条权限）+ MenuService（specialUse，stopWithTask=false）。
- 大包适配：Manifest 生成用「迷你 APK」（python 流式剔除 assets/lib/dex/META-INF 只留 res+arsc+manifest，166 entries）→ apktool 往返，避开 2.6G 全量 decode 落盘；zip 合并全程流式（`zin.open`→`copyfileobj`→`zout.open`，2.67G 不整体读内存）；zipalign 后立即删 unsigned 再签名（峰值两份全包 ≈5GiB，脚本有 ≥5G 磁盘预检）。
- 磁盘环境：/tmp 与 /Users 同一 APFS 卷，本次可用仅 ~6G，峰值流程实测通过。

## 3. >2G 包 zip64 归一化（本次新增，实测实锤）

python zipfile `ZIP64_LIMIT=2^31-1`（非 4G）：2.67G 包合并产物被写入 **zip64 EOCD + 晚期条目 CD zip64 extra**（hoff=0xFFFFFFFF、vneed=45）。实测后果（build-tools 36.0.0 zipalign，静态链接 libziparchive）：

1. zip64 EOCD 路径对 >2G 文件直接 `Unable to open as zip archive: Undefined error: 0`（zipalign -c 对原包 2.67G 经典 EOCD 通过，排除文件大小本身）；
2. 逐条目 970 处 CD `vneed=45` 与本地头 `ver=20` 不一致 → 新版 BadPack 防护 `WARNING: header mismatch`（数量=偏移 >2^31 的条目数，逐一对出）。

修复（脚本内 `normalize_zip`，合并后运行）：剥离逐条目 zip64 extra 还原真实 hoff（uint32 合法域 <4G）、vneed 回填本地头版本、尾部改写**纯经典 EOCD**（与原包 EOCD 形态一致，原包即无 zip64 记录）。修复后 `zipalign -f` 正常、`zipalign -c 4` 成品通过。
