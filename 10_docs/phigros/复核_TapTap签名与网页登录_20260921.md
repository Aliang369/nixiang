## 2. 静态实证（官方 3.20.0 base.apk，2026-09-21 拉自真机）

设备：`f9a116a2`（OPD2404），已装 `com.PigeonGames.Phigros` 3.20.0 / vc154；已装 `com.taptap`。

### 2.1 dex 面（classes.dex，5.87MB，单 dex）

- 渠道 SDK 为**老线** `com.taptap.sdk` + `com.tds`：`TapLoginHelper / TapLoginInnerConfig / IscTapLoginService`，
  日志 `register isc service TapLogin com.taptap.sdk.IscTapLoginService`。
- **不存在** `com.taptap.sdk.kit.internal.utils.TapSignKit`（新版「TapTap 去验签」要改的类），
  仅存在 `com.tapsdk.antiaddiction.utils.TapTapSignUtil` —— 那是**防沉迷服务端请求签名**（MAC 头），与 APK 证书校验无关。
- 全域搜 `checkSignatures` / `GET_SIGNATURES` / `Landroid/content/pm/Signature;`：
  命中的只有 google-gms / twitter / youtube / androidx 的公开校验代码，**无游戏侧或渠道侧的包签名校验**。
- 登录路由实锤（`smali` 反编译自官方 dex）：
  - `com/taptap/sdk/ui/LoginClient.sendLoginRequest`：try 内优先 `CloudGameHandler` → 否则 `ActivityHandler.authorize()`
    （= 拉起 TapTap 客户端 SSO）；`catch (Exception)` → `handlePhoneVerify`/`handlePhoneVerify2` → 最后 `WebViewHandler.authorize()`。
  - `LoginClient.onLoginFailed()` → 直接 `WebViewHandler.authorize()`。
  - → **客户端 SSO 失败（含签名不匹配、未安装、用户取消）会自动降级到内嵌 WebView 登录**，不是死路。

### 2.2 IL2CPP 面（global-metadata.dat，metadata v31）

- `libil2cpp.so` 内**不含** `getPackageInfo` / `android/content/pm/Signature` / `signatures` 任何字符串
  → 游戏层无运行时包签名查询。
- metadata 里确有 `CheckSignature` / `GetSignature` / `VerifySignature` 三个方法名，但字符串堆邻域实锤其归属：
  - `CheckSignature` ⊂ `Mono.Security.Authenticode.AuthenticodeDeformatter`
  - `VerifySignature` ⊂ `Mono.Math.BigInteger` / `DSAManaged`
  - `GetSignature` ⊂ `System.Runtime.Remoting`（`CADMessageBase`）与 `AndroidJNIHelper`
  → **全是 mono/BLC 标准库自带**，非游戏自研校验。故「Unity IL2CPP 无签名校验」这一脚本假设在本包成立。

## 3.4 ⚠️ 追加实测：游戏内「账号与统计」登录**确实失败**，原因是渠道签名（推翻 §3.3 的"不需要补丁"）

> 触发点：游戏内 → 账号与统计 → TapTap 登录（与首页那次防沉迷快速认证是**两条不同链路**）
> 证据：`evidence_20260921/logcat_游戏内账号登录_signature_not_match_20260921.txt`（+ `游戏内登录_关键行.txt`）

```

01:44:37.403 START com.taptap.sdk.TapLoginHelperActivity (LAUNCH_MULTIPLE)
```

### 关键判定

| 问题 | 结论 |
|------|------|
| 失败原因 | **`signature not match`**（TapTap 客户端校验调用方 APK 签名），游戏把 `code=-1` 统一显示成「登录失败，请检查网络」——**不是网络问题** |
| 与首页 SSO 的区别 | 首页那次（§3.2/§3.3）是防沉迷 `startupWithTapTap` 通道，未触发签名校验，所以看起来"通"；账号登录这条走 `startTapLogin` → 客户端校验 → **必失败** |
| 失败后是否自动降级网页 | **没有**。`LoginBlock.onActivityResult` 收到 `resultCode=-1` 直接 `finish()`，全包搜不到 `fallbackToWeb`；本 SDK 只有 `LoginClient.sendLoginRequest` 的 catch 分支才落 `WebViewHandler` |
| 因此 §3.3 的"不需要强制网页登录补丁" | **仅对首页链路成立，对游戏内账号登录不成立——此结论作废**。账号登录必须强制走内嵌网页 |

### 补丁其实已经写好了，只是没给 Phigros 开

`mod菜单/starry-mod-menu/app/src/main/java/com/starry/magic/sign/TapLoginForceWeb.java` 内已有 **14 个包的白名单**（终末地 / 无尽探险 / 凡尘西游修真记 / 正中靶心2 / 一念通天 / 偶像梦幻祭2 / 燃烧纪元 / 宝石战争 / 暗影格斗3 / 弹壳战机…），**`com.PigeonGames.Phigros` 不在其中**。

它对本包**恰好命中已实装的旧版路径**（`forceOldImplWebEarly`）：

1. 白名单包的 `com.taptap.sdk.ui.TapTapActivity` 在 **`onActivityPreCreated`**（`onCreate` 之前）被拦；
2. 把 intent extra `"request"` 换成 `YnttLoginRequest`（`yntt_smali/com/starry/magic/sign/`，`.super Lcom/taptap/sdk/LoginRequest;`，其 `getRequestCode()` 恒 `throw IllegalStateException`）；
3. `LoginClient.sendLoginRequest` 的 `try` 里调 `getRequestCode()` → 抛异常 → `catch` → `handlePhoneVerify`/`handlePhoneVerify2` 都不命中 → **`WebViewHandler.authorize()` 内嵌网页登录**；
4. `sendLoginRequest` 返回 false → `LoginBlock.startAuthorizeByClient=false`，不会再去拉客户端。

本包与该路径的匹配点（逐项核实）：

| 前置条件 | Phigros 3.20.0 实测/反编译 |
|----------|---------------------------|
| 存在 `com.taptap.sdk.ui.TapTapActivity` | ✅（运行日志 START + smali 在包内） |
| `TapTapActivity.onCreate` 从 intent extra `"request"` 取 Parcelable → 塞进 `LoginBlock` Bundle | ✅（onCreate 第 249–280 行） |
| `LoginClient.sendLoginRequest(LoginRequest)` 调 `getRequestCode()` 且在 `try` 内 | ✅（旧版路径 `forceOldImplWebEarly` 注释所述场景） |
| `sendLoginRequest` 返回 false 时 `LoginBlock` 走 `client.onLoginFailed()` → WebView | ✅（`onViewCreated`：`if-eqz` → `LoginClient.onLoginFailed()` → `WebViewHandler.authorize`） |
| 生命周期回调已注册（`onActivityPreCreated`） | ✅ `StarryApp.onCreate` / `StarryInitProvider.onCreate` 均注册 `registerActivityLifecycleCallbacks` |

→ **最小改动 = 白名单加一行 `"com.PigeonGames.Phigros"` + 注入 `YnttLoginRequest` 两个 smali**（官方 `classes.dex` 仍可字节保留，走外科 zip；不需碰官方 dex）。

## 4. 若最终确认需要补丁，落点在哪（本包版本）

`taptap-web-login.md` 的版本 1/2/3 类名在本包**都不存在**，不能照抄。本包对应点为：

| 目的 | 本包类/方法 |
|------|-------------|
| 禁止拉起 TapTap 客户端 SSO，直接走网页 | `Lcom/taptap/sdk/ui/LoginClient;->sendLoginRequest(Lcom/taptap/sdk/LoginRequest;)Z` 内让 `ActivityHandler.authorize` 抛 `Exception`（或直接调 `WebViewHandler.authorize`） |
| 更外科做法 | 改 `Lcom/taptap/sdk/ui/ActivityHandler;->authorize(Lcom/taptap/sdk/LoginRequest;)V` 恒抛 `ActivityNotFoundException("starry_force_web_login")`（与 skill 版本 3 同思路） |
| 强制网页登录的入口 | `Lcom/taptap/sdk/ui/WebViewHandler;->authorize(Lcom/taptap/sdk/LoginRequest;)V`（`WebBlock` 内嵌 WebView） |

前提：这些类在官方 `classes.dex`，而上一轮外科方案是**官方 classes.dex 字节保留**。
若要改必须放弃该 dex 的字节级保留，改走「定向 dex 重编 + 外科 zip」，属方案级变更，需先确认 TapTap 确实不通。

## 5. 剩余风险与建议

1. **不要复刻 TapSignKit 补丁**：本包无该类，硬套只会白改（除非先升级渠道 SDK）。
2. **不要强行压到网页登录**：实测 SSO 已通，强压会丢掉 TapTap 账号态（云存档/成就依赖账号）。
3. **渠道签名真正的校验面在服务端**：TapTap 侧按 `clientID` + 登记签名校验，本次实测未触发拒绝；
   若后续换包/换版本出现登录失败，先看 TapTap 客户端侧返回码，再考虑客户端补丁。
   参考 [TapTap 登录 FAQ（chain validation failed / 签名相关）](https://developer.taptap.io/docs/sdk/taptap-login/faq/)。
4. **鉴权阻塞已解除**（见 §3.3）：`auth_grant` 已下发、`满分` 在 bootstrap 里 `enabled=true`。
   若换设备/换后台环境再遇 `flag=false`，属鉴权缓存（`auth_cache_sec=600` / `auth_expire_at`）到期，重新拉取即可。
5. 上一轮 `surgical_phigros_3.20.0.sh` 注释里那句「无签名校验绕过需求」建议补限定：
   **仅指游戏自身；渠道 SDK 走的是客户端 SSO，实测改签后仍可用**。
