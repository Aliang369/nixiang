### 2.4 推荐挂点与伪 IL

**挂点**：`PlayerManager.RefreshMP(bool isLoadSave)` 入口（方法首指令前插入）。
参数断言：`AssertParams(m, new[]{"isLoadSave"}, new[]{"Boolean"})`。

```il
// ---- 插入块（在 RefreshMP 首条原指令之前）----
ldstr    "inf_mp"
call     bool Starry.StarryConfig::GetBool(string)
brfalse  SKIP
ldarg.0                                     // 目标对象（stfld 需要 对象, 值）
ldarg.0
ldfld    float32 PlayerManager::mp          // 上限
stfld    float32 PlayerManager::curMp       // curMp = mp
SKIP: nop
// ---- 以下原 IL 一个字不动 ----
```

**为什么这一处足够 / 为什么不破坏上限、UI、存档**：

1. **上限不被突破**：`curMp` 只在 `RefreshMP` 内被夹（`:1853 curMp >= mp → curMp = mp`），我们写的就是 `mp` 本身，恒等在边界上，`mpFator` 恒 1.0，不越界。
2. **UI 自洽**：同一函数随后照常执行 `mpText.text`、`mpImgObjList` 上色、`DOFillAmount(1)` —— 不需要额外补 UI 逻辑；`mpFadeImg` 因为 `fator>=1` 自然不显示。
3. **存档不脏**：`RefreshMP` 不写 `SaveDataManager`；只有玩家主动存档时 `:1153` 才把 `curMp` 抄进存档，此时存的是满蓝（读档仍满蓝，非破坏性、可逆）。
4. **游戏自带同语义先例**：`:1852-1855` 邪神 8（`EVIL_EIGHT`）本身就写 `curMp = mp`，说明这个赋值被原逻辑接受（不是 hack 出来的非法状态）。
5. **关闭即原样**：只是一条 `if` 前置分支，`inf_mp=0` 时 `brfalse` 直落原首指令，原 IL 无修改（与 6 个既有功能同风格）。
6. **性能**：`RefreshMP` 本来就只在扣/回蓝后调用，不是每帧；再叠加 `StarryConfig` 2 秒缓存读文件，无热路径开销。

**被否决的方案**（说明覆盖度取舍）：

| 方案 | 否决理由 |
|---|---|
| 逐点改 17 处 `curMp -=` | 17 个补丁点，后续热更一改就漏；且 `AoeSkillControl` 的扣量来自局部变量，改参数不成立 |
| 抬 `GetMpMax` / `mp` 上限 | 只把上限变大，蓝照样会被扣光（`curMp` 独立递减），语义错 |
| 改 `SkillUseManager.OnUseSkillEnd` | 那已经是【无限技能】的挂点，且只覆盖技能，不覆盖道具/障碍/持续光束（17 条里只有 1 条） |

### 2.5 与【无限技能】(inf_skill) 的语义区分（两开关互不影响）

| | 无限技能 `inf_skill`（已有） | 无限蓝 `inf_mp`（新增） |
|---|---|---|
| 挂点 | `SkillUseManager.OnUseSkillEnd(int,int)` 入口 `mpConsume = 0` | `PlayerManager.RefreshMP(bool)` 入口 `curMp = mp` |
| 覆盖面 | 技能释放收尾这 1 条路径（含**魔法宝石血转蓝**：`SkillUseManager.cs:7469-7477` 有宝石时改扣 `curHp`） | 全部 17 条 `curMp -=`（技能/道具/障碍/角色特性/持续光束…）；**不含**宝石的 `curHp` 扣血路径 |
| 观感 | 蓝条会真的下降再回（若同时开 inf_mp 则不降） | 蓝条常满，扣完立刻回满 |
| 关闭后 | `mpConsume` 保持原值，原扣蓝逻辑原样执行 | `curMp` 不再被抬，原扣蓝/回蓝逻辑原样执行 |

> 二者不是替代关系：宝石在场时 `OnUseSkillEnd` 扣的是 `curHp`，`inf_mp` **管不到**；反之道具/光束扣蓝 `inf_skill` 也管不到。同时开启互不干扰（`inf_skill` 先让 `mpConsume=0`，`inf_mp` 再把蓝抬满，都只是各自入口的 if）。

辅助方法（新建在已存在的 `Starry.HkldPatch` 类型里，与 `ForceUnlock` 同例）：

```csharp
// 语义：move_speed_x 是整数百分比，100 = 1.0x（与原版 moveSpeed=100 !=> 1.0x 口径一致）
public static int ScaleMoveSpeed(int v)
{
    int x = Starry.StarryConfig.GetInt("move_speed_x", 100);
    if (x <= 100) return v;                 // 缺省/关闭 = 原值，零副作用
    int r = v * x / 100;                    // 999*999=998001，int 不溢出
    if (r < 1) r = 1;
    if (r > 999) r = 999;                   // 与 :1234 的 Clamp(...,1,999) 同边界
    return r;
}
```

**语义选择：属性倍率，不是直接置值。** 理由：
- 原值来自「装备 `curMoveSpeed` + 星石 `stone_moveSpeed` + 角色 `baseMoveSpeed` + `tempSpeed` + `tempSuperSpeedBuffMoveSpeed`」的加总（`:1234`），置值会抹掉玩家养成/BUFF；
- 倍率天然幂等：`SetBaseAttribution` 每次都从头重算再乘，不会叠加放大（这点很关键，若挂在 `tempSpeed` 累加字段上就会指数膨胀）；
- 属性面板 %、跑动动画、翻滚数值自动一致，不需要第二处补丁（**A 方案特性；B 方案改为「面板不变、动画仍同步」，见 §3.5**）。

**关于 GetInt 只支持整数（重要）**：`move_speed_x` 用 **整数百分比**（100/150/200 = 1.0x/1.5x/2.0x），
**不需要新增 `GetFloat`**，native 侧沿用现有 `Slider_*`（整数）通道即可，`Starry.StarryConfig` 与 `HkldMod.cpp` 都不必新增浮点解析。
若产品坚持要 1.25x 这类小数，则必须：① `Patch.cs` 增 `GetFloat`（`float.TryParse` + `System.Globalization` 或简化 `(float)GetInt("move_speed_x100",100)/100`）② native `WriteConfigKey` 写千分比整数——**本文件给出但建议不采用**，用 `move_speed_x` 整数百分比即可满足菜单 1..500 的粒度。

**倍率天花板（必须告知用户）**：`moveSpeed` 在上游被 `Clamp(...,1,999)`，我们只在**下游**再乘 ⇒ 若基础 moveSpeed 已≥300%，`x=200` 会被 999 夹住，实际倍率 <2x。基础 100% 时理论上限 9.99x；建议 sliders 上限 300。

#### 3.5.3 插入点合法性（插入 ≠ 改 ret）

- 每条 `ret` 执行前栈顶**恰好是 1 个 `float`**（返回值）；插 `call float32 Starry.HkldPatch::MoveMul(float32)` 后：弹 1 个 float、回推 1 个 float ⇒ **净栈深变化 0**，`maxstack 2` 无需上调，`ret` 仍拿到 float。
- **无需新增/重定向 `ret`**：全方法仅 `IL_000b: bne.un.s IL_0020` 一个分支，目标是 `IL_0020`（非 `ret`）；无异常处理表（无 try/catch/finally）。实现时必须断言「**没有任何分支/switch/leave 指令的操作数是这两条 `ret`**」，否则插入会被绕过。
- 原指令一条不删，只是每条 `ret` 前多一条 `call`（与既有 6 功能的「入口前置 call」同性质，只是位置在出口）。
- 语义：原返回值被 helper 消费后回推同类型值 ⇒「原逻辑原样执行，开关关闭时逐位等价」。

#### 3.5.4 伪 IL 与 helper 语义

```il

call float32 Starry.HkldPatch::MoveMul(float32)
ret
```

```csharp
// 整数百分比倍率：100 = 1.0x（与原版 GetRealMoveSpeed 的 /100f 口径同源）
public static float MoveMul(float v)
{
    int x = Starry.StarryConfig.GetInt("move_speed_x", 100);
    if (x <= 100) return v;              // 缺省/关闭 = 原值逐位不变
    if (x > 1000) x = 1000;              // 保护：本地配置被手改时不至于爆表
    return v * x / 100f;
}
```

> 穿墙风险完全由滑条上限控制（建议 300，见 §7-8）；`x<=100` 一律直返，保证「关掉即原样」。

## 5. 通用写法要点（与现有 6 功能同风格）

1. **只插入、不删改**：所有补丁都是「入口/指定指令后 `InsertBefore`/`InsertAfter` 一个新块 + 一个 `Brfalse SKIP`」，原指令集合保持完整（现有反例断言就是查 `Mathf.Clamp` 是否还在）。
2. **参数名 + 类型双断言**：`AssertParams(m, names, typeNames)`（`Patch.cs` 已有 helper），错位是静默 bug，运行时才炸。
3. **成员解析宽容**：`TolerantRefs` 那套垫片仍适用；本文件新增解析的只有 `TotalAttributes.moveSpeed`（`int`）与 `PlayerManager.mp/curMp`（`float`），都是同程序集类型，不需要新垫片。
4. **`MaxStackSize`**：无限蓝块瞬时栈深 2（对象 + float），若原 `MaxStackSize < 2` 需上调；移动速度（B 方案）在 `ret` 前插 `call float32 MoveMul(float32)` 属**栈中性**（弹 1 回 1），`maxstack 2` 无需改动。
5. **幂等防重**：沿用 `HasLdstr(m, key)` 判重（`[skip] ... 已含 key`），避免重复打补丁导致叠加。
6. **不要碰`Main.cpp`/`MainModern.cpp`/`GameConfig.h`/公共 `Android.mk`**；新增的 IL helper 只加在 `Starry.HkldPatch` 类型内。

## 7. 风险与副作用（逐条，按严重度）

1. **【中】蓝尽自停逻辑失效**：有 2 条扣蓝点会在 `RefreshMP()` **之后**立刻读 `curMp` 判断"是否断开"——
   `CapybaraLemonAbilityControl.cs:255 if (curMp < GetMpConsume()) StopBeamAtk();`、
   `JingAbilityControl.cs:1700 if (curMp < 0f) curMp = 0f;`（后者无害）。
