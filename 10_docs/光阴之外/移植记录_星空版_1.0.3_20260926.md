## 3. 为什么本作必须走 evalString splice 而不是 so 内 hook

- 本作引擎是 **Cocos Creator 3.x（JSB）**，没有 `libil2cpp.so`、没有 `global-metadata.dat`、没有 HybridCLR 热更 DLL —— 先例爆裂防线/圣翼传说的整套 il2cpp 字段路线**完全不适用**。
- 游戏逻辑全在 `assets/**/*.jsc` 里，且**全部加密**（文件头 `02a16608` / `17883af7` / `bc9d6966` / `f36570cb`…）。xxtea key 是编译期注入的，so 里没有 UUID 形式的 key ⇒ **离线解密已放弃**（这是第一轮踩过的死路）。
- 斌哥的做法就是绕开加密：hook 脚本引擎入口，在**解密后的明文**上动手。星空侧采用同构路线但**不依赖 `Function.prototype.toString`**（斌哥壳靠它重编译 browserify 工厂函数，一旦游戏方改用 native 编译函数就会整套失效）—— 我们直接改**脚本文本本身**，交给原 `evalString` 执行，对引擎无感。
- 为什么 Dobby 在本作可用（与爆裂防线相反）：本作没有 il2cpp 解释器分发层，`evalString` 是普通 C++ 导出函数，在 `libcocos2djs.so` 的 **dynsym** 里就有：`_ZN2se12ScriptEngine10evalStringEPKclPNS_5ValueES2_` ⇒ `DobbySymbolResolver` 一次命中（实测日志 `[Gyzw] hooked se::evalString @0x78c9141da0`）。

## 4. 实现要点

源码：`mod菜单/starry-mod-menu/app/src/main/jni/Games/{GyzwEntry.cpp,GyzwMod.h,GyzwMod.cpp,GyzwPatchJs.h}` + `app/src/main/java/com/starry/magic/cocos/GyzwHooks.java`

### 4.1 hook 目标与早期抢挂

| 项 | 值 |
|---|---|
| 库 | `libcocos2djs.so` |
| 符号 | `_ZN2se12ScriptEngine10evalStringEPKclPNS_5ValueES2_` |
| 签名 | `se::ScriptEngine::evalString(const char* script, long length, se::Value* ret, const char* fileName)` |
| 挂载时机 | `Gyzw_OnLoad` → `Gyzw_StartEarlyHookThread`：独立线程 **3000 × 20 ms** 轮询 `isLibraryLoaded("libcocos2djs.so")`，库一加载立刻 `DobbySymbolResolver` + `DobbyHook` |

`initRetryMax=120` / `initRetryIntervalMs=2000000`（2 s）—— 早期线程负责抢在 boot JS 首次 eval 之前，主 tick 只做状态同步。

### 4.2 窗口过滤与 boot JS 落盘

```cpp
// GyzwMod.cpp:423-424
// 窗口过滤：boot JS 约 1.87MB；1MB..48MB 之外的脚本一律直通
if (n < 1024 * 1024 || n > 48 * 1024 * 1024) return orig(...);
```

- 只有落在这个长度窗口里的脚本才进入 splice 流程，其余（配置脚本、热更小脚本、native 回调）**一律原样直通**，避免误伤。
- `DumpBootJsOnce()`（`GyzwMod.cpp:382`）把第一份进入窗口的脚本文本写到 `getFilesDir()/gyzw_boot.js`（实测 **11,650,461 B**）—— 这是**唯一**能看到解密后游戏逻辑的途径，锚点核对与后续维护都靠它。
- 实测 `[Gyzw] splice #1 len=11769666->11771766 file=assets/script/index.jsc` ⇒ 前缀 + 4 处替换共 **+2,100 B**。

### 4.3 幂等标记与别名捕获（自愈核心）

- 幂等标记 `kGyzwPatchMarker = "starry_gyzw_v1"`：脚本文本里已含此串 ⇒ 直接直通，防热更重载二次注入叠加放大。
- 入场三串齐全才认定是目标 boot JS：
  - `var u = t.isDie();`
  - `this.setCurHp(this.curHp + e, t);`
  - `return r && r[o] || this._oneSpeed;`
- **`BtConst` 模块别名捕获**（`CaptureAlias`，`GyzwMod.cpp:241`）：功能 1/2 需要 `X.BtConst.EUnitType`，而 `X` 是打包器生成的单字母别名（斌哥那边靠运行时正则 `/(\w+)\.BtConst\.EUnitType\./` 现捕）。星空侧在 4 个锚点各自的 64 KB 邻域里找 `.BtConst.EUnitType.` 前面那个标识符，取最频繁者；**捕获失败 ⇒ 整个 splice 直接放弃**（`LOGW "[Gyzw] BtConst alias capture failed — abort splice"`），绝不带着半截补丁上桌。
- 实测本作捕获结果：`bv=r`（`[Gyzw] gyzw js patched bv=r`）。

### 4.4 4 处锚点替换（与斌哥同锚点、同语义，独立重写）

| # | 锚点（原文） | 星空替换体语义 |
|---|---|---|
| 1 | `var u = t.isDie();` | `if(on(1) && e<0 && (o.type===Hero\|\|o.type===Lord) && t.type===Monster) e = Math.floor(100*e);` —— 只放大「英雄/领主 → 怪物」，怪物打英雄不放大 |
| 2 | `this.setCurHp(this.curHp + e, t);` | `if(on(2) && e<0 && this.type===Hero){ if(typeof this.__mfl!=='number') this.__mfl=Math.floor(this.maxHp*(0.91+0.04*Math.random())); e = Math.max(e, Math.min(0, this.__mfl - this.curHp)); }` —— **不硬写 0**，每只英雄首次随机地板 |
| 3 | `return r && r[o] \|\| this._oneSpeed;` | `if(on(3) && m>1) return {trueSpeed: Math.max(_g3v.trueSpeed*m, m), displaySpeed:…, openId:…};` —— `m = val(3)`（滑块 1..10） |
| 4 | `for (var e = Math.min(3, Math.floor(this._logicAccumulator / this._logicFrameRate)), t = 0; t < e; t++) {` | `Math.min(3,…)` → `Math.min(on(3) ? Math.max(val(3),3) : 3, …)` —— 不装这条，3a 的倍率会被逻辑步 `min(3)` 卡在约 3× |

- **每处替换体自带 `try{…}catch(_gNe){}`**：任一锚点形态漂移（游戏热更改代码）只会静默跳过该功能，不会让 boot JS 抛异常导致开不了游戏。
- 4 处都用 `ReplaceRequired`（`GyzwMod.cpp:223`）：**锚点出现次数 > 1 ⇒ 判定为歧义，放弃 splice**（宁可不生效，不可错改）。
- 开关读取走 JS 侧 `window.__starryGyzwOn(n)` / `window.__starryGyzwVal(n)`，实现是先读内存镜像 `g.__starryGyzwState`，回落 `jsb.reflection.callStaticMethod("com.starry.magic.cocos.GyzwHooks", "getRet", "(I)Z", n)` / `"getVal", "(I)I"`。
- 状态同步链：`GyzwMod.cpp:171 SyncJavaRets()`（把 native 侧 `g_features[]`/`g_values[]` 推进 Java `GyzwHooks.RET/VAL`，`:190-192` 单独 `CallStaticVoidMethod(g_hooksSetNoAd, …)`）+ `:199 SyncJsState()`（推 JS 侧镜像）。

### 4.5 免广告：3 处 smali 门控（真入口定位花了三轮）

**真入口 = `com.sp.common.SPBaseController.getRewardVideo(Lcom/sp/sdk/core/callback/RewardVideoCallback;)V`，只在 `classes4.dex`**（`classes3.dex` 里根本没有这个类）。判据是 logcat 里那行 `SPSDK: SpBaseController 获取广告----` 正是该方法体首发出的。

| # | dex | 类.方法 | 门控点 |
|---|---|---|---|
| a | classes4 | `com.sp.common.SPBaseController.getRewardVideo` | **真入口**（`.registers` 3→5） |
| b | classes3 | `com.sp.mod.tapad.TapAdModImpl.getRewardVideo` | 同层兄弟入口（`.registers` 4→8） |
| c | classes3 | `com.sp.mod.tapad.manager.TapAdRewardManager.showRewardVideoAutoAd` | 自动广告路径（`.registers` 5→10） |

门控体（三处同形）：

```smali
invoke-static {}, Lcom/starry/magic/cocos/GyzwHooks;->shouldSkipAd()Z
move-result v0
# ★极性铁律：if-eqz = 「noAd 为 false 时跳回原逻辑」
if-eqz v0, :gyzw_*_orig
# 同形假回调：先 onResult(0,"视频观看完成") 再 onAdClose("广告页面已关闭")，然后 return-void
```

**★极性铁律（本轮最大的坑）**：三处最初全写成 `if-nez v0, :gyzw_*_orig` ⇒ 语义变成「`shouldSkipAd()` 为 true 时跳回原广告逻辑」= **开启免广告反而走真广告路径**。对照已验证先例 `mod菜单/starry-mod-menu/scripts/surgical_dwct_12.39.sh:193` 是 `if-eqz v0, :cond_starry_ad` 才改对。**今后任何门控落点，先对照 Dwct 先例核极性，不能凭 `if-nez` 直觉写。**

**★smali 硬坑（会崩整包）**：插门控必须把 `.registers` 抬到 `cur + need_words`。第一版没抬，`invoke-interface` 用 6 个寄存器超了上限 ⇒ ART 报 `outs_size (6d) > registers_size (5d)` ⇒ **整个 dex 被拒收** ⇒ `ClassNotFoundException: Didn't find class "com.sp.sdk.core.GameApplication"`（`AppComponentFactory.instantiateApplication` FATAL，开机即崩）。另：`invoke-interface/range {p2 .. v4}` 会被汇编器拒（`A register range must have the lower register listed first` / `Invalid register count: -4`）⇒ 改 `move-object v0, p2` + 递增 `{v0 .. v5}`。

## 5. 反作弊审计

**答：一行都没做。本作没有任何屏蔽上报/反检测处理。**

- 斌哥自己的 boot JS 头注释亲笔警告：「竞技场有 replay 战报上报、种子确定性 ⇒ PVP 大概率服务器可对账」，并建议「三功能先在 PVE 主线/推图测；PVP 别开尤其无敌（双方都 Hero 互相无敌卡死）」。
- 斌哥的**无敌刻意不写 0**，而是每只英雄留 91~95% 血量地板 —— 这是作者主动做的「降可疑度」设计，说明本作服务端有血量/属性侧校验的**可能性**。星空侧**保持同样保守策略**：功能 2 同样留随机地板，功能 1 只放大「英雄/领主 → 怪物」方向（怪物打英雄不放大，避免双向被对账）。
- 星空侧**未**拦截任何上报；**未**做防封号；**未**移植 `libtoolChecker.so`（RootBeer，仅存在于斌哥包，无证据承担反检测职责）。
- 本作广告是 TapAD 激励视频（`TAPAD_MEDIA_ID=1108734` / `TAPAD_SPACE_ID=1065279`），免广告走**客户端回调伪造**（直接发 `onResult(0,"视频观看完成")`）⇒ 若服务端对激励视频做**发放校验**，理论上可对账。建议先在 PVE 场景验证。
- `AD_CONFIG=0` **不能**当「广告总开关关闭」的证据：该文件注释字节在源文件里已退化为字面 `?`，encoding 不可恢复。

同一份源码两次 `surgical` 产出的 `classes3/4/5.dex` **字节不同**（`3a874b8b21a0`/`e58bb4a10a84`/`e0d5f9aa396f` vs `9d0a51d77611`/`bdff0f4ffb3e`/`3e8e931a872a`），但：

## 7. 遗留项

1. **`GyzwMod.cpp:199 SyncJsState()` 索引不一致（未修）**：把 `g_noAd` 写进 `ret[4]`，而 `GYZW_FEAT_NOAD = 5`（`[4]` 是 `Category_广告` 占位）。当前免广告只走 Java `GyzwHooks.shouldSkipAd()`（smali 门控），JS 侧 `__starryGyzwOn(4)` 从未被读，故**无功能影响**；若后续要在 JS 侧也读免广告开关，须先修此处。
2. **PVP 可对账风险未处理**：见 §5。功能 1 已限制方向、功能 2 已留地板，但未做任何服务端对账规避。
3. **免广告未做服务端校验规避**：客户端伪造回调，若服务端校验激励视频发放，理论上可对账。
4. **`libtoolChecker.so` 未移植**（RootBeer，仅斌哥包独有）。
5. **热更兼容性**：锚点是 boot JS 源码串，游戏一旦热更改这几行，对应功能会静默失效（`try/catch` 兜住，不会崩）；届时重跑 `dump` 阶段取新的 `gyzw_boot.js` 重新核对锚点即可。`classes3/4.dex` 的广告门控同理，需重跑 `surgical`。
6. **`BtConst` 别名捕获失败即整体放弃**：这是刻意的保守设计（宁可不生效不可错改），但意味着若打包器换别名策略，功能 1/2 会全灭而功能 3 正常。
