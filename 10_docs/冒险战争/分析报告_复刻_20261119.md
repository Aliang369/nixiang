## 结论先行

1. **APK 基线就是旧版同一个构建**：AOT（CodeRegistration `0x37323a0` / MetadataRegistration `0x389b1c8`、`GameMain` TypeDefIndex 1929、`LoadDll` RVA `0x2D35674`）、`data.unity3d`（6228 MonoScript，mygame 4108）、以及 APK 内热更程序集 mygame `e58aa7ef…`/18,009,088、HotFix `b32dc742…`/1,274,880，全部与旧文档**逐项/逐字节一致**。唯一确定变化是包名 `com.bhzf.zbml` → `com.mxzz.zbml` 与重签。[实测]
2. **运行时加载的不是 APK 基线，而是 1.1.085 新构建**：设备 `files/versionName.txt` = 1.1.085，`files/TZWD9JF…` 容器 18,826,273 B → **mygame.dll 18,826,240 B / sha256 `9802e7ed91c9ec86a4cfc4862c30da7a79df346834b88411a59d5e5c206411a8`**（旧设备版是 f44f75b8 / 18,655,744）。[实测]
3. **挂点仍在**：`Battle.Life::AddHP(JInt, Life, int) -> void` 在 1.1.085 中 IL **245**、maxstack 8、locals 6、EH 0，与 APK 基线**仅 6 条指令位置不同**（`==0` 判定的 codegen），语义等价 ⇒ 旧补丁语义（入口早退 / 改 `value`）**可直接复用**。[实测]
4. **路线仍适用**：程序集是 HybridCLR 热更 dll（解释执行）⇒ 继续「`Assembly.Load(byte[])` 边界按 sha256 换字节 + 离线 Cecil IL 补丁」，**不需要** native methodPointer hook。[推断，证据链见 §四]
5. **给 builder 的硬要求**：被替换体 sha256 白名单必须包含 **`9802e7ed…` / 18,826,240**（运行时版）；旧的 f44f75b8 在本次设备上不会命中。[实测]

- 基线：`Call JInt::op_Implicit(JInt)` + `Ldc_I4_0` + `Bgt`

**补丁语义是否需要调整：不需要。** 结构级证据：①签名/IL 规模/栈额度/locals/EH 全相同；②`_curHP` 仍是 `JInt` 且在方法体内被 `+= value` 写；③`GetPlayer()`/`GetCamp()` 仍在；④枚举值未变。**唯一必须改的是 sha256 白名单**（新增 `9802e7ed…`）与 ini 路径包名。

**旧 b5/b7/b8 教训（沿用，builder 必读）**：`实现记录_星光版.md` §七 —— ①禁 `typeof(...)` 引入 `System.Private.CoreLib`；②全关时 `AllOff()` 直接跳原方法首条、零 JInt 读写；③helper 单出口 + 局部存返回值，避免 `Incompatible stack heights`；④秒杀构造失败必须保留原 `value`（`TryAdjust` 返回 bool）。

## 四、路线判断

**结论：仍适用「Assembly.Load 边界换字节 + 离线 IL 补丁」，不改 native hook。**

依据链：
1. 玩法程序集是热更 dll，AOT 中无 `Battle` 命名空间（F2/F3）⇒ 玩法代码不在 `libil2cpp.so`，native methodPointer hook 没有对应 IL2CPP 方法体可钩。
2. 加载链仍在 AOT 的 `GameMain.LoadDll`（RVA `0x2D35674`，与旧一致）→ `AesHelper.LoadDll` → `Assembly.Load(byte[])` ⇒ 字节数组边界存在。[推断：RVA 与旧相同 + 旧轮反汇编结论]
3. 设备侧无明文 dll（F5）⇒ 不能走「替换文件」路线，只能在加载边界换字节。
4. 备选（仅当 1–3 被推翻时）：native 侧钩 `il2cpp_resolve_icall` / HybridCLR 解释器入口 —— **本轮不采用**，证据不支持且成本高。
