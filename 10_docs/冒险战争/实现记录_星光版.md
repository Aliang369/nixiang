## 一、路线

引擎 = Unity IL2CPP + HybridCLR 热更。玩法全在热更程序集（`mygame`）里、解释执行，
`libil2cpp.so` 没有对应机器码 ⇒ 不在玩法方法上 hook：

1. **离线 IL 补丁**：Cecil 改 `Battle.Life::AddHP` 入口（`04_scripts/冒险战争/ilpatch/`）。
2. **加载边界换字节**：native hook `System.Reflection.Assembly.Load(byte[])`，
   收到的字节按 **官方 sha256 白名单**匹配 → 用 `il2cpp_array_new` 按补丁体真实长度重新分配容器替换；
   不匹配一律 **PASSTHROUGH**（不崩、不闪退）（`jni/Games/MxzzMod.cpp`，机制同 `HkldMod.cpp`）。
3. **开关通道** = `/data/user/0/com.mxzz.zbml/files/starry_config.ini`（native 写 `god=1`/`kill=1`，
   补丁体 `Starry.StarryConfig` 读，2s 缓存；文件缺失/异常 ⇒ 全默认关）。

★ 与旧版霸海争锋 b8 的两处方法级差异：
- 版本辨识从「长度比对」改成 **sha256 白名单**（热更换版频繁，等长不同内容用长度比不出来）。
- 白名单**双条目**（热更 1.1.085 + APK 基线），各自换成**同版本**的补丁体；
  玩家热更未完成时加载基线版也能命中（卸载重装/热更丢失场景）。

## 二·补 · `kMxzzSelfShas` 幂等表的作用（b2 相对 b1 的唯一代码差异）

native 在 `Assembly.Load(byte[])` 边界只能看到「这一次传进来的字节」。若同一份**已替换过的补丁体**
被再次交给 `Assembly.Load`（同程序集二次加载 / 代码内重入 / 框架重试），它的 sha 既不是官方 sha（不在
`kMxzzPayloads`），也不是「未知版本」——不加区分就会走进 PASSTHROUGH 分支并弹一次
「游戏热更版本与补丁不符」的 toast，对用户是**错误信息**。

b2 起：`MxzzPayload.h` 同时生成 `kMxzzSelfShas`（每个补丁体自身的 sha256，由生成器从产物直接算），
`MxzzMod.cpp` 在查表前先 `IsPatchedBody(sha)` → 命中则记一行
`缓冲区已是补丁版（幂等放行）` 并直接原样放行：**不替换、不告警、不弹 toast**。
判据来自实际字节（生成期），不是猜，也不引入新的版本假设。

## 三、补丁语义与「为什么这样写」

**注入的 9 条前缀**（`Battle.Life::AddHP` 最前）：

```
call  Starry.MxzzPatch::AllOff()      // 两开关都关 ⇒ true
brtrue ORIG                           // 全关：直接跳原首条，零 JInt 读/写/转换
ldarg.0 / ldarg.1 / ldloca V6         // this, value, out adj
call  Starry.MxzzPatch::AdjustValue(Life, JInt, out JInt) -> bool
brfalse ORIG                          // 判定不成立/异常 ⇒ 原样执行
ldloc V6 / starg value                // 成立 ⇒ 写回**同一个**参数槽
```

**AdjustValue 语义**（互斥、fail-safe）：

| 条件 | 结果 |
|---|---|
| `god=1` 且 `value<0` 且 `CampOf(this)==FRIEND_CAMP(1)` | `adjusted = new JInt(0)`（本次伤害归零） |
| `kill=1` 且 `value<0` 且 `CampOf(this)==ENEMY_CAMP(0)` | `adjusted = new JInt(-(long)_curHP - 1)`（一次打空并致死） |
| 其它（治疗 `value>=0`、阵营空/未初始化） | 返回 false ⇒ **保留原 value**，走原逻辑 |
| 任何异常 | catch → false（等价「不改」） |

选择理由（对旧 b8 的两处修正，均为静态证据驱动）：

1. **不早退，改写 value 后落回原体**。证据：`AddHP` 尾部对 `_curHP` 有 4 处 `stfld`，
   并有 `OnLifeHPChange` / `AddLogicRecord` 等记录调用；旧 b8 的「god 命中即 `ret`」
   会跳过全部写入与记录（旧文档已把这条列为已知副作用），状态分叉风险大。
   改成 `value = 0` 后仍走单一写路径：血量不变、记录一致、Buff 触发路径不变。
2. **两个功能合并进一个 helper**（旧版是 BlockGod + TryAdjust 两个）：
   前缀从 16 条降到 9 条、只有一个写回点、只有一个 `out JInt` 局部，注入面更小。

保留的 b8 四个静态缺陷修法：
① mscorlib 一律取目标程序集自带引用（`Corlib()`），不用 `typeof` 引 `System.Private.CoreLib`；
② `AllOff()` 短路，自身零 JInt 操作；③ helper 结果存局部、单一 `ret` 出口；
④ 只有 `AdjustValue` 返回 true 才 `starg`，失败保留原 value（绝不写 0 覆盖）。

未做（按证据不做，非遗漏）：不写死任何 RVA/偏移/方法下标；`_curHP` 只读不写（无需定位 stfld 之一）；
Camp 语义从枚举成员名 + 常量值双读，不靠数字猜。

## 九、工具限度（归档必读）

1. `--cmp` 的「结构一致」≠「行为一致」：它比对 opcode/操作数/分支索引，不校验 MaxStack 峰值、不校验运行期语义。
2. 前缀长度（9）是`patched−original`的 pure-length 推定；前缀内容由 Gate 的 13 项意图断言单独覆盖（不是靠比对）。
3. `--info` 的 token 来自 Cecil `MetadataToken`，与 IL2CPP dump 侧 token 同源（dev 0x0601A468 与 re-analyst 报告一致），但**不是 RVA**。
4. 补丁体是**托管程序集**，与 `libil2cpp.so` 的 RVA/偏移无关；换 so/换 metadata 时本补丁不受影响，反之亦然。
5. `MxzzPayload.h` 是**生成物**（`gen_mxzz_payload_header.py`），禁手改；改 dll 必须重跑 `mxzz_build_so.sh`。
6. 构建机差异：ndk-build 在含中文的路径（`mod菜单`）下会 `unable to open output file`，必须走 ASCII junction `starry_link`（脚本已内置）；javac/R8/baksmali 的 argv 也不吃非 ASCII 路径（脚本把源与 stub 拷进 ASCII 临时目录）。

## 十一、b3 崩溃静态结论（待 Lead/verifier 交叉复核）

**症状**：b3 冷启约 2s，SIGSEGV/SEGV_MAPERR；#00/#01/#02 在 `libil2cpp.so`(BuildId 33287dfe…)，

**结论：il2cpp_domain_get 在运行时/元数据初始化完成前被调用 ⇒ libil2cpp 内空指针解引用。**

| 证据 | 内容 |
|---|---|
| A 我方 so 反汇编 | `0x14EA8: bl 0x1B5DC`；`0x1B5DC: ldr x0,[x0,#0x20]; cbz x0; br x0` = 间接调用 `Api::domain_get`；上下文 `0x14E9C..0x14EB4` 与 `MxzzMod.cpp` 的 `if (api.thread_attach) { dom = api.Domain(); if (dom) api.thread_attach(dom); }` 逐字对应 |
| B libil2cpp 反汇编 | `il2cpp_domain_get`(0x1A4266C) `b` 0x1A05A98；该函数 `ldr x0,[x20,#0xF18]`（domain 全局）`cbnz` 失败后分配、再 `ldr x8,[x8,#0x10]`（运行时/元数据全局 0x398A000+0xE50），把该值当参数 `bl 0x19B3554`；此刻该值为 **NULL** |

| 时间线 | 21.377 so loaded → 22.073 `[Il2Cpp] api loaded` → 22.075 houdini 转储（首帧）→ 22.126 CRASH；**距 so 加载约 0.75s**，期间无任何自有 error 日志 |

**定性**：与补丁体（dev `6bb9bd12…`/base `00299687…`）、dex、Manifest、so 依赖**均无关**；
问题在「首次触碰 il2cpp 的时刻」。MxzzEntry 抄了 Hkld 的 `initDelayMs=0 / 600×100ms`。

**仓内同类口径（既有教训，非类比）**：8 个 Entry 显式 2–5s「避开 il2cpp/HybridCLR 半初始化」
（Blfx 5s「等 il2cpp 类表/HybridCLR 热更程序集就绪」）；Il2CppApi.cpp r20 注释亦记「≤2 级诊断一次 il2cpp API 都不做」
用于规避「启动约 4s 干净退出」。

**候选修复（未实施）**：
- A（主）：`initDelayMs=5000000`(5s) + `initRetryMax=120` + `initRetryIntervalMs=2000000`(2s)，fast-retry 线程改 1s 起步退避。

  且同线程第 3 次故障会 SIGKILL，故不作主方案。

**Hkld 为何不崩**：已证差异＝验证环境（Hkld 2026-11-13 真机 OPPO OPD2404/Android 15；本作雷电 x86 + houdini）；

**待复核**：① 0x14EA8→domain_get 归属；② 0x398A000+0xE50 的「运行时全局」命名（只证了此处为 NULL 且被解引用）。
