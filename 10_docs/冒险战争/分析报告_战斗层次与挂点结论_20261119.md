> 版本：热更 1.1.085（mygame 18,826,240 B / sha256 9802e7ed…）｜APK 基线 1.1.036（versionCode 7）
> 环境：雷电模拟器 x86 + houdini，已 root，arm64-v8a
> 结论状态：**已收敛；本作当前版本放弃「客户端改血量」路线**

## 一、结论

**这一版战斗是「服务端结算 + 客户端按记录回放」，客户端不计算伤害。** 挂 `Battle.Life::AddHP` 或 `ClientLife::set_HP` 都只能改画面，改不了战果。

## 二、实测硬数据（b16，内存直读，通道已自证）

计数挂在逻辑层与表现层，由 native 用 `il2cpp_field_static_get_value` 直接读取（绕开一切日志通道）：

```
21:58:02  逻辑层 cBtl=0  cFrame=3944  cAdd=0   | 表现层 setHpHit=144 godHit=87 killHit=25 | camp=1 cur=21146 val=7080
21:58:07  逻辑层 cBtl=0  cFrame=4341  cAdd=0   | 表现层 setHpHit=144 godHit=87 killHit=25 | camp=1 cur=21146 val=0
```

| 计数 | 挂点 | 值 | 判读 |
|---|---|---|---|
| `cFrame` | `LogicBattle::Update / FixedUpdate` | 4341 | 战斗在推进，不是没进战斗 |
| `cBtl` | `LogicBattle::CreateBattle` | **0** | 本地不创建逻辑战斗 |
| `cAdd` | `Battle.Life::AddHP` | **0** | 4341 帧里客户端一次伤害都没算 |
| `setHpHit` | `ClientLife::set_HP` | 144 | 表现层血量由记录驱动写入 |
| `godHit / killHit` | 记录层改写命中 | 87 / 25 | 补丁逻辑本身正常，确实命中 |
| `camp` | `ClientLife.campType` | 1 | 阵营判定正确（FRIEND_CAMP=1） |

通道自证：同版本 `GTLauncher::Awake/Start` 计数各为 1，证明「读内存计数」这条路可靠，不是测不出来。

## 三、静态证据链

### 3.1 `Battle.Life` 在本包不可构造（原始挂点失效的根因）

对 `mygame_dev_1085.dll`（7274 类型）与 `mygame.dll`（1.1.036 基线，7024 类型）全量扫描：

| 检查项 | 结果 |
|---|---|
| `newobj Battle.Life` | 0 |
| `call Life::.ctor` | 0 |
| `ldtoken Battle.Life` | 0 |
| 继承 `Battle.Life` 的子类 | 0 |
| 唯一实体容器 `Cell.m_pLifeObject` 的赋值点 | 0 |

`Battle.Life : Battle.AIBase`（非 MonoBehaviour），因此没有「反射/预制体实例化」的解释。字段引用 26 处、`AddHP` 13 个调用点都在，但运行期从未被构造 ⇒ `AddHP` 永不执行。与实测 `cAdd=0` 互为印证。

⚠ 判据提醒：不要用 `newobj=0` 判「类已死」——`ClientLife` 同样 `newobj=0`，但它是 MonoBehaviour，由预制体实例化，是活的。要看基类。

### 3.2 两条 HP 通道

```
逻辑层：Battle.Life : Battle.AIBase，_curHP = JInt（JEngine.AntiCheat）
        BattleField._lifeList : Dictionary<JInt, Battle.Life>
        写点：AddHP / SetHP / Clear / SetAllAttr / FoceFillUpHP / CheckMaximumHealth

表现层：ClientLife : HeroAnimatorExtension（MonoBehaviour，实战单位表现体）
        _curHp = Int64，全类唯一写点 = set_HP 的 IL@0002 stfld
        set_HP 调用方：LogicRecord_HPValue::PerformDoRecord / BattleConfLoaderAction::LifeDead /
                      ImmediatelyLifeDead / BattleReportPlayer::OnCreateSuspendPerformerLifeCallback
```

### 3.3 战斗引擎结构（客户端有能力，但这一版没跑）

```
LogicBattle::CreateBattle          ← ImitateBattleRun::StartLoigcBattl / ClientRealtimeComputing / BattleEditor…
LogicBattle::CreateBackgroundBattle ← StageManager::BackgroundBattle
LogicBattle::ImmediatelyBattle     ← StageManager::RunOnlyLogicBattle
LogicBattle::Update                ← Game::Update
LogicBattle::FixedUpdate           ← Game::FixedUpdate
BattleField::Create / Recovery     ← ClientPoolManager.BattleFieldDataPool
```

客户端具备本地模拟能力（`ClientRealtimeComputing` 即「客户端实时计算」入口），但实测这一版战斗走记录回放，`CreateBattle` 未调用。

### 3.4 记录回放链

```
ClientLogicRecord::DoRecord → RealDoRecord → LogicRecord_HPValue::PerformDoRecord → ClientLife.set_HP
                                                             → set_MaxHP / set_HPPercent / UpdateUI
LogicRecord_Dead::PerformDoRecord → set_LogicDead(true) / set_Killer / EventManager.DispatchEvent
ClientLife::Update → PlayDeadperform → ToDissover（溶解消失）
ClientLife::DoDead ← BattleDirector::AllDead / ClientLife::Update
记录池：ClientPoolManager.LogicRecord_HPValuePool / _DeadPool / …
```

**HP 与死亡是两条独立通道**：血被保住 ≠ 不会死。死亡由 `LogicRecord_Dead` + `DoDead/ToDissover` 决定，这解释了「血满还死」的现象。

## 四、已做过的尝试与结论（省后来人的时间）

| 挂点 | 结果 |
|---|---|
| `Battle.Life::AddHP`（前缀改 value） | 永不执行（Life 不可构造） |
| `ClientLife::set_HP` | 命中 144 次，只影响画面 |
| `LogicRecord_HPValue::PerformDoRecord`（改写 hp） | 命中，血条不再掉，战果不变 |
| `ClientLife::DoDead / set_LogicDead / PlayDeadperform / ToDissover` | 命中，死亡画面被拦住，结算仍按记录/服务端 |
| `LogicRecord_Dead::PerformDoRecord` | 命中，跳过死亡记录，同样只是画面 |

共性根因：以上全部位于「表现/回放」层，战果由记录内容与上層服务端决定。

## 五、若要「真效果」的可行方向（未实施，需授权）

- **A 篡改下行记录**：在 `RealDoRecord` 处把敌方 hp 全改 0、丢弃我方死亡记录。
  效果＝画面与客户端统计判胜；服务端结果不变，奖励以服务端为准，且「上报结果不一致」有风控风险。
- **B 改上行请求**：改战前/战后请求里的阵容、属性、增益字段，让服务端自己算出胜利。
  效果＝真实战果改变；需先摸清请求结构与签名（`NetSecProtectHelper::GetDataSign / IsEmulator / IsRootDevice / GetFpToken` 存在），封号风险高。

两条都必须获得明确授权后再做，本文件不构成实施许可。

## 六、环境与工具注意事项（踩过的坑）

- `System.IO.File` 与 `UnityEngine.Debug.Log` 两条日志通道在本运行时曾长时间零输出，用它们判断「代码是否执行」会误判；**判据要用内存静态字段 + native 直读**。
- HybridCLR 解释执行类型的静态字段可被 `il2cpp_field_static_get_value` 正确读取（已用 `GTLauncher` 计数自证）。
- houdini 下 `libil2cpp` 全段无 x 权限，不能用 maps 权限位判可执行（历史结论仍成立）。
- 出包写盘必须复用 `TolerantRefs`（`TolerantAssemblyResolver / ShimFactory / ConstantAudit`），否则因 DOTween / Unity.ThirdParty 等缺引用程序集导致整包写盘失败。
- 新补丁器：`04_scripts/冒险战争/ilpatch2/`（挂点可换，写盘链已通）。
