### 1.1 token/时间黑洞 top-N（按代价排序）

1. **入口点未先查框架先例**（≈ 全会话 30%～40% 排查成本）
   现象：星空包装机后 so 从未 dlopen。根因：`<application android:name>` 在本包/本机不被采用，而这个坑框架里早有结论——`mod菜单/starry-mod-menu/app/src/main/java/com/starry/magic/StarryInitProvider.java` 类注释逐字写着「星光无 Application 替换注入：终末地（ACE/TSS）实测 Manifest 的 `android:name` Application 被替换为非预期类时…**因此不改 Manifest 的 Application，改由本 Provider 在应用进程启动时自动初始化**」。
   本可怎么做：开工第一步 `grep -rln "Application\|Provider\|ComponentFactory" mod菜单/starry-mod-menu/app/src/main/java/com/starry/magic/` 并读类注释（约 10 分钟），直接选 Provider 入口，省掉整个 8 种取证过程。

2. **判据顺序倒置**（≈ 20%～30% 排查成本）
   现象：段判定先从最重、最不可靠的手段开始（frida Java 桥、`dumpsys` 读 className、`package_cache`、`packages.xml`），这些都读不到 `ApplicationInfo.className`，属结构性死路。
   本可怎么做：先选"一条命令能证伪"的判据——`adb logcat -c` → 冷启 → `grep -aE "Starry|starry_magic|MenuService|Mod_Menu"`（30 秒出结论），再用 `/proc/<pid>/maps` 佐证，最后用 `am start-foreground-service -n <pkg>/<类>` 的报错文本判断"组件是否被平台登记"（实测有效：`Requires permission not exported from uid …`＝已登记 / `Not found`＝未登记）。

3. **工具环境常识现查现试**（≈ 6 调用 + 2 轮等待）
   macOS 无 `timeout`（rc=127）；frida CLI 输出重定向到文件会丢 `console.log`（须用 `-o`）；Frida 17 无内置 Java 桥（`Java is not defined`，需 `frida-java-bridge` + `Compiler()` 打包，仓库设施在 `01_tools/phantom-frida/src`）；`logcat -v time` 行是 `MM-DD HH:MM:SS.mmm L/Tag ( PID): msg`，`awk '$3==<pid>'` 全空，正解 `grep -a "( <pid>)"`；`logcat -b all -d` 是多缓冲拼接、非时间序且会轮转。
   本可怎么做：这几条一次性落 `TOOLBOOK.md` 二-b，开工 preflight 回读。

4. **推送链路盲等**（3 次各 60 s+ 超时）
   SSH（22 与 `ssh.github.com:443`）被网络阻断，连续 3 次 `git push` 等到超时才发现要切 HTTPS。
   本可怎么做：push 前先 `ssh -o ConnectTimeout=5 -T git@github.com`；失败且 `gh auth token` 可用就直接走 HTTPS，并在输出写明"已用 HTTPS 绕行，remote 未改"。

## 2. 已验证、可复用的关键事实

### 2.1 入口与判据
- 注入入口三级判据：① 自家 tag `logcat`（先 `logcat -c` 冷启，窗口必须覆盖进程启动）② `/proc/<pid>/maps` 有无自家 so ③ `am start-foreground-service -n <pkg>/<类>` 报错文本（已登记 vs `Not found`）。**`dumpsys` 在本机读不到 `ApplicationInfo.className`**（`dumpsys package -v`、`cmd package dump`、105722 行全量 dump 里 `className=` 零命中），`packages.xml`/`package_cache` 也不含本包组件 ⇒ 这三条是死路。
- 兄弟 Android，`<application android:name>` 在本包/本机不生效（属性记录合法、aapt2 复读正常，但类从未实例化；`--no-incremental` 流式安装亦同）⇒ 入口改走 `ContentProvider`：`<provider com.starry.magic.StarryInitProvider authorities="<pkg>.starryinit" exported=false enabled=true>`，**插在 `<application>` 首个子元素位置**。框架另有 `appComponentFactory` 入口（`StarryAppCompFactory0`、`YsxzAppComponentFactory`）可作备选。

### 2.2 AXML / Manifest
- `resource map` 语义＝**按字符串索引稠密排列**（`map[i]`＝池内第 i 条的 res id）；追加基址必须 `(chunk总长-8)//4`（写成 `(总长-16)//4` 会整体错位 2 位 ⇒ 新增属性的 res id 被平台读成 0，而 **aapt2 复读照样通过**）；补丁器必须自带"回读 res map 值 == 期望 res id"的断言。
- 官方 `AndroidManifest.xml`：池 241 串 / map 40 条；真实组件比"6 个 service"多得多——含多个 `<provider>`（TapTap `TapUpdateFileProvider`、`androidx.startup.InitializationProvider`、`TapTapKitInitProvider` 等），**provider 入口是既有机制、可直接借用**。

### 2.3 dex / IL2CPP
- 新包 dex 布局：`classes.dex` 65020 / `classes2.dex` 65230 / **`classes3.dex` 65533（仅剩 3 位）** / `classes4.dex` 37691 ⇒ **合并目标必须按"方法数余量"自动选**，禁止硬编码 `classesN`（本次合并后 `classes4.dex` 39785，余量 → 25751）。
- 版本接手必测三件：dex 数量与逐 dex 方法数余量、旧版 Manifest 依赖的等长槽是否还存在、`libil2cpp.so` 与 `global-metadata.dat` 的 md5。
- Il2CppDumper 打印 `WARNING: find JNI_OnLoad` / `ERROR: This file may be protected.` 属无害噪声，产物照常完整；dump.cs 的 RVA 注释行**带前导 tab**（`l.strip().startswith("// RVA: ")` 才匹配得到），记录口径＝该行 `RVA:`（RX 段与 `Offset:` 差 `0x4000`，`ELF_BIAS=0x4000` 本版未变）。

### 2.4 TapTap
- 强制网页登录＝覆盖 intent extra `com_taptap_sdk_login_request` 里的 `loginType="embedded_web"`，在 `LoginTypes$Companion.from(String)` 阶段即胜出；0912 那套改 `ClientLoginUtils.isClientLogin` 只影响"默认推断"（`LoginCoordinator.getLoginType(Activity)` 路径），对显式 `loginType` 无效。
- 框架反射入口带**前置白名单门禁**：`TapLoginForceWeb.java` 的 `PKG_WHITELIST` 漏配 ⇒ 5 个入口静默 `return`、零日志 ⇒ 表现为"功能没生效但一切正常"。
- 签名伪装只在**进程内**有效（系统侧仍是星光证书）⇒ TapTap 客户端 SSO 永远过不了，强制网页登录是必需项不是可选项。
