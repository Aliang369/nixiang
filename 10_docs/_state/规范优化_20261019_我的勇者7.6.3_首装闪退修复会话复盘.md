## E. 黑洞 Top-N 与替代路线

### E-1【最贵】没有先查仓内候选经验，重复推导已在库的同一根因（跨会话复发）
- **现象/证据**：`pending_experience.md` §B 候选经验 **#2**「必须区分『APK 内嵌构建』与『运行时热更构建』两份 libil2cpp / metadata」（`10_docs/_state/pending_experience.md:121-123`）、**#3**「这类游戏星光侧挂点必须按名解析 + 序言字节校验，禁止写死 RVA」（同文件 :126-127），均来自 2026-10-18 保卫向日葵会话。本轮从 0 重新推导同一结论，中途还被设备侧 md5 误导。
- **根因**：该经验是**候选状态**且落点写在 `skill/re-extract/binge-memdiff.md`（抓包/提取路径），而本轮的路径是 `skill/starry-mod`（出包路径）⇒ 规则存在但**不可发现**；开工路由（AGENTS §3）也没有「开工先扫 pending_experience」这一步。
- **实际代价**：约 8–10 次工具调用 + 一次错误结论 + 回退；上下文约 15–20 K。
- **本可怎么做**：定位到包后、装机前，第一条检索就是
  `grep -n "metadata\|热更 so\|内嵌" 10_docs/_state/pending_experience.md` →
  直接问「包内 so 与 metadata 是否同源？」，用一条 `unzip -p` 对比两条 sha256 即可定向。
- **下次触发**：任务涉及「已有包的运行时/热更/so 偏移」时，**开工第 3 步**必须先扫 `pending_experience.md` + `prior_art.sh`。
- **验收**：下一次同类任务在装机前就能报出「so/metadata 同源校验」结论，且不出现「先怀疑、再推翻」的往返。

### E-2 交付/验收口径缺「干净安装」，同一游戏两次踩
- **现象/证据**：2026-10-18 的交付是在旧机 `f9a116a2`（早已热更到 357、`files/update/current` 有配套副本）上做**同签名覆盖安装**验证通过（`10_docs/_state/games/我的勇者.md` 上一版摘要原话「同签名覆盖安装（不卸载、不丢数据）」）；本轮在干净机复现崩溃。
- **根因**：验收只覆盖「升级路径」，未覆盖「首次安装路径」，而发布场景恰好是后者；`stages.md` 的装机阶段与 `post_install_precheck` 都没有「必须覆盖干净安装」这一条。
- **实际代价**：一次无效交付 + 用户白测 1 轮 + 本轮整轮返工（约 100+ step）。
- **本可怎么做**：出包后**先卸载再全新安装**跑一次预检（本轮实际就是这么发现问题的，只是发生在返工阶段）。
- **下次触发**：任何「发给别人/换设备」的包，装机阶段必须包含一次 `pm uninstall` → 全新安装 → 预检；覆盖安装只能作为附加证据。
- **验收**：交付前日志里同时存在「干净安装」与（可选）「覆盖安装」两条预检记录。

### E-3 用设备侧 `md5sum` 与本地 `shasum` 混比，读了一个可能正在被写的文件 → 错误结论
- **现象/证据**：先 `adb shell md5sum` 得 `f46039db…`，与本地包内 `2959d55b…` 不同 ⇒ 我据此推断「运行时 metadata 被改写/版本不同」；随后 `adb pull` 落盘 + `cmp -l` 得 **0 差异**，结论推翻。
- **根因**：跨工具哈希口径混用（md5 vs sha256 混述）+ 未遵守「先落盘再比对」的同源纪律（该纪律仓内已有，写作 `先落盘再 grep`，未覆盖「比对哈希」）。
- **实际代价**：2–3 次调用 + 一次进入记录的错误结论（已在崩溃记录 §4 修正）。
- **本可怎么做**：直接 `adb pull` 到 `/tmp` → 本地统一 `shasum -a 256` + `cmp`。
- **下次触发**：任何「设备侧文件 vs 本地文件」比较，一律先 pull 再本地同算法比对。
- **验收**：同类比较不再出现「设备算 md5、本地算 sha256」混比。

### E-4 修复所需配套文件的最短路径没识别，多花一轮用户等待
- **现象/证据**：我给出三选一（TapTap 重下 / 旧机 `f9a116a2` / Windows 端 `02_apks`），用户实际做法是「在**同一台**小米上装回官方包」——一句话解决，`adb pull` 38 s 完成。
- **根因**：把"底包来源"当作外部资源问题，没先问「用户手上的设备能否直接产出该文件」；也漏了 `02_apks/` 已空（`ls 02_apks` 只有 README 与 3 个无关包）这一事实的即时利用。
- **实际代价**：1 轮往返（约 10 min 用户等待）。
- **本可怎么做**：第一句就问「装一个官方原版到这台/任一台手机，我 adb pull 即可，1 分钟」。
- **下次触发**：缺 apk / so / metadata 时，先枚举「已授权的设备能否产出」→ 再考虑下载/跨机。
- **验收**：同类缺口一轮内解决，不再出现"要用户去找文件"的往返。

### E-5 D1 并行纪律违规（calls/step 1.25、单发 71.4%）
- **现象/证据**：75 个 step 只有 1 个调用。
- **根因**：诊断链路是"读 → 判 → 再读"，同文件（surgical 脚本 13 次、崩溃 logcat 多次切片）串行；部分是真等待（装机 1.5 GB、预检 3 min、`adb pull`），但同源的独立读（如 `unzip -l` 与 `aapt2`、`git status` 与 `du`）本可合发。
- **实际代价**：step 数偏高，触碰 108 step；用户观感"一直在跑"。
- **本可怎么做**：把「同一阶段、互不依赖的只读命令」一次性合并（例如装机前把 `unzip -l` / `aapt2 badging` / 签名校验三条并入一次调用）。
- **下次触发**：连续两个 step 只发 1 个只读命令时，强制检查能否与下一步合并。
- **验收**：同类会话 `session_metrics --gate` 的 D1 不再 FAIL。

### E-6 同一文件读-改-写分散（触达 26 次含绝对/相对重复计数）
- **现象/证据**：`surgical_wdyz_7.6.3.sh` 触达 13 次（另 13 次为绝对路径重复），其中多次是「读一段 → 改一处 → 再读下一段」。
- **根因**：`edit` 需要先 `read` 的机制约束 + 我没有一次性把「要改的三处区域」读全。
- **实际代价**：约 6–8 次多余调用。
- **本可怎么做**：先 `read` 目标区间（`offset/limit` 两段）→ 连续 `edit` 三处（不同区域不冲突时）。
- **下次触发**：同一文件预计 ≥3 处改动时，先读全目标区域再连续编辑。
- **验收**：同文件触达次数 ≤ 改动处数 + 2。

### 必要成本（明确不判为浪费）
- 两次 1.5 GB 装机 + 两次 3 分钟预检：正是它们把一个模糊的用户传闻变成 `FAIL_A`/`PASS_TO_HUMAN` 二值证据，是本轮唯一可靠的验收来源。
- 8.5 KB 单条结果：内容即崩溃现场帧，属关键证据。
- 逐行核对 `current.md` 的他人改动：`stage_shared_file` 的 dry-run 反复三轮（先漏 `迷雾大陆`/`终末地`），代价 2 次调用，换来 5 处他人改动零污染。

## L. 可执行优化提案

### P0-1【出包静态门禁】直装包若替换 `libil2cpp.so`，必须校验 metadata 同源（或直接禁止替换）
- **问题与证据**：旧包 so=357（`aeb62966…`）而 metadata=底包（`2959d55b…`），在干净机 100% 崩（2/2 复现）；官方底包同机正常（A/B 已闭环）。
- **根因与影响面**：出包脚本可任意替换 so，而 metadata 由底包透传；流水线上没有任何一步校验二者同源。影响所有「内嵌热更 so 出直装包」的游戏（本仓多个 `surgical_*` 脚本具备该能力）。
- **具体方案**：
  1. `04_scripts/_common/pre_install_gate.sh` 增「查9：so/metadata 同源」——输入包与底包时，若 `lib/arm64-v8a/libil2cpp.so` 与底包不同，则要求同时声明并校验 metadata（提供 `--metadata <file>` 或 `--expect-metadata-sha256`）；缺失即 FAIL。
  2. `04_scripts/_common/stages.md` 装机阶段"四查"→"五查"，并把该查写进 install 阶段的必过清单。
  3. `skill/starry-mod/SKILL.md` 增一条硬规则：「**不得只换 so**；要么不换（走按名兜底），要么 so+metadata+资源成套」。
- **为什么优于旧方法**：把"事后靠运行期崩溃发现"提前到"出包即 FAIL"，省一次 1.5 GB 装机 + 一轮用户实测。
- **风险/边界**：metadata 有时被壳加密/改写，需允许 `--allow-metadata-rewrite` 显式例外；对"so 与底包相同"的包直接 PASS。
- **验收**：拿本轮旧包（md5 `fe12162d…`）跑门禁应 **FAIL**；拿修复包（`d98c7e72…`）应 **PASS**；两条命令写进验收清单。
- **状态**：`未做`（执行会话无权限改 `04_scripts/_common/**` 与 `skill/**`）。

### P0-2【验收口径】直装包必须做一次「干净安装」验收

- **根因与影响面**：发布场景是首装，验收却只覆盖升级路径。影响所有对外分发的包。
- **具体方案**：`04_scripts/_common/stages.md` 装机阶段的"装机前产物四查"之后增加一条**验收口径**；`mod菜单/starry-mod-menu/scripts/` 的出包脚本（或 `install_starry_apk.sh --clean`）在收尾时打印「是否做过干净安装预检」；`skill/starry-mod/SKILL.md` 的交付清单加一行。

### P1-1【脚本缺陷】`install_starry_apk.sh --clean` 在无 root 机上静默跳过卸载
- **问题与证据**：`adbsu "pm uninstall ${PKG}" || true`（`:147`，`adbsu` 定义 `:71-72`）在无 `su` 设备上必然失败且被 `|| true` 吞掉；随后 install 因签名冲突失败，脚本以通用错误退出，用户/代理需自行推断。本轮我实际是**手动** `adb uninstall` 才装上。
- **根因**：`--clean` 分支假设设备有 root；但 `install_starry_apk.sh` 头部又明确支持非 root 机（"实测小米 96f0d883 无 su"）。
- **具体方案**：`:147` 改为分支——有 root 走 `adbsu`，无 root 走 `adb uninstall "$PKG"`；并把"卸载成功/失败"落一行可判读日志（当前 `|| true` 完全静默）。
- **风险/边界**：非 root 卸载无法做外置数据归位（`chown` 需 root），应在日志里明示"外置数据将丢失"。
- **验收**：无 root 机上 `--clean` 能完成"卸载→安装"并在日志出现 `uninstall ok (no-root)`；root 机行为不变。
- **状态**：`未做`（执行会话不改善共享脚本）。
