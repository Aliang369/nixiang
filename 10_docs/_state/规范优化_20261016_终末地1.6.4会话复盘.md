### 本会话 token/时间黑洞（按代价排序）

1. **反查标签写成字符类 `grep -a -q '[Wggls]'` → 白跑一整轮构建**。现象：`[1/6]` 报「so 仍含上一款标签 [Wggls]」假 FAIL；根因：BRE 把 `[Wggls]` 当**字符类**（匹配任意单个 `W/g/l/s`），而 1.5.3 原脚本写的是转义 `'\[Wggls\]'`，我抄写时丢了反斜杠。连锁代价：修完必须**重跑 ndk-build+gradle+merge+sign 全链**（$WORK 已被 trap 清）。**本可怎么做**：反查他游标签一律 `grep -aFq`（本轮已就地改成 `-F` 并写注释）。
2. **`aapt2 … | grep -q` 在 `set -o pipefail` 下自造"失败" → 又白跑一整轮 merge+sign**。现象：`[5/6]` 后门禁报「StarryInitProvider 未写进 Manifest」，但包内**其实有**；根因：`grep -q` 命中即退出 → aapt2 吃 SIGPIPE(141) → pipefail 把整条管道判失败。**本可怎么做**：① 脚本内门禁一律「先落盘再 grep」（已改）；② **昂贵脚本一开始就该有 `KEEP_WORK` 开关**（我事后才补 `ENDFIELD_KEEP_WORK=1`，当时没有 → 只能重跑）。
3. **会话中段跑裸 `git fetch` 挂住 60 s+**。现象：SSH 22/443 通道探测超时，作业转后台占坑，我另发 `job_kill` 收尾。**本可怎么做**：判「远端是否同步」看 `git status -sb` 的 ahead/behind 已足够；确需 fetch 时套 `with_timeout.sh` 或走 `push_main` 的通道逻辑，不在主线上裸跑。

## 2. 已验证、可复用的关键事实

### 2.1 跨版本稳定性（实测，1.5.3 → 1.6.4）
- ACE so **字节级同尺寸**：`libtersafe2.so` 5,609,568 / `libtprt.so` 1,879,688（与 1.5.3 记载完全相同）。
- 官方签名证书 MD5 **跨版本同值** `1cf808541a17bf218d3dd5a30787e485` ⇒ SignSpoof 常量无需随版本改。
- `global-metadata.dat` 加密头仍 `94 43 72 12`；Unity 仍 2021.3.34f5；Application 仍 `com.u8.sdk.U8Application`；ACE 组件 GP6/GP7 齐；dex 布局同构（6 dex，`classes6.dex`=720 B 占位 ⇒ 空闲下标 7）。
- **方法**：这五条同构性可当作「同游戏大版本跳变是否可原样复刻」的快速判据（省掉重做保护面分析）。

### 2.2 挂点层（实测 logcat，`09_test/终末地/precheck_20261016_011743/`）
- `[Endfield] CalcSig argc=4 [ret=System.Double p0=…DamagePackData& p1=Boolean& p2=Boolean& p3=…BATTLE_REPORT_INFO&]`、`CalculateDamage hooked argc=4 static=1 double_ret`、`ApplyModifier hooked managed_argc=1`、`jump hooked MovePipelineAir.CanJumpAgain argc=0`、`cd hooked Skill.CheckCd argc=0`、`cost hooked Skill.CheckCost argc=0`、`faction native=1`、`hooks sync calc=1 apply=1 jump=1 skillCd=0`。
- 与 1.5.3 记载「static/argc=4/ret=double/参数全 byref」**逐项一致**；唯一 miss 是历史即预期的 `CheckSkillCd`。
- `[Il2Cpp] ImageOf … name=Gameplay.Beyond.dll` 解析成功 ⇒ 抓点文档定义的 Assembly 层在 1.6.4 仍成立；`strtab … PLAINTEXT`（`count=249`）；`StarryBridgeTest: nativeGetFeatureList = PASS`。

### 2.3 **方法论（本轮最有复用价值）**：`SyncHooks()` 跑在 `TryInit()` 与每 300 ms 的 `Tick()`，**不是等开关才装**

## 4. 优化方案（按价值排序）

### P0-1 大资源游戏「异签名卸载重装」的外置数据保护应通用化
- **问题**：`pm uninstall` 会连带清 `/sdcard/Android/data/<pkg>`；本游戏实测 29,990 MB（`files/VFS`），卸载即静默丢，重下代价极高。而现有 `_common` 无任何通用步骤（已核：`grep -rln "Android/data\|nxreserve" 04_scripts/_common skill` 无命中；仅 2 个游戏私有脚本各处理过属主问题）。
- **方案**：① 把「同卷 `mv` 落备胎 → 读新 uid → 归位 + `chown -R` + `restorecon`」写成 `skill/starry-mod/SKILL.md`「分发与装机红线」的通用步骤（含"备胎非空才允许卸载"的硬闸门）；② 视需要抽 `04_scripts/_common/rescue_extdata.sh`（`--pkg` / `--reserve` / `--restore`）。
- [落点] `skill/starry-mod/SKILL.md`「分发与装机红线」节（`清数据 = Mod + 热更资源双杀` 之后）；候选 helper：`04_scripts/_common/rescue_extdata.sh`（新建）。
- **成本/风险**：低（逻辑已验证，仅搬运）；风险＝不同机型 FUSE 是否允许同卷 rename（本轮 OnePlus/Android 16 可行，需在至少另一台机器复测）。
- **验收**：另一款大资源游戏卸载重装后 `du -sm` 前后一致 + 属主 `u0_aXXXX` == 新 uid + 游戏可正常读资源。
- **状态**：候选（跨游戏·通用）。框架侧登记见 FW-12。

### P1-3 「按名解析型游戏」的挂点证据在 L2 阶段即可取到（方法论下沉）
- **问题**：仓库现行 `skill/re-implement` 挂点五步门禁把「挂点是否生效」默认留到 L3 用户实测；但本轮证明对 `SyncHooks` 立即装钩的实现，**冷启 logcat 已有 `hooked … argc=N`**，可提前判定。
- **方案**：在挂点五步门禁补一条「**先判实现是否立即装钩**（grep `SyncHooks`/`tryInit` 调用点）⇒ 是则 L2 冷启必须核对 `hooks sync …` 与各 `hooked` 行，把它当作第 5 步（路线锁定）的机器判据」，减少用户轮消耗。
- [落点] `skill/re-implement/SKILL.md` 挂点五步门禁节（§22 附近）+ `skill/re-implement/hook-rules.md` 对应节；实例证据引 `10_docs/终末地/版本适配_1.6.4_20261016.md` §七。
- **成本/风险**：低；风险＝把"已装钩"误当"功能生效"（提案已明确只作**解析层**判据，不替代 L3）。
- **验收**：下一款按名解析游戏在 L2 阶段就能给出 `hooked` 证据，且复盘里区分「解析通过 / 效果未验」。
