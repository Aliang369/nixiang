# 外部方案台账（仓外检索结果，查一次双机复用）

> 用途：把「仓内没有、外面有（或外面已证明不通）」的结论沉下来，避免同一个问题反复烧 step 重新查。
> 建立依据：2026-10-15 用户本会话「按照你说的方案进行全量修改」（三轮评估：REA 评估 / GitHub 高星对照 / 外部检索消失机制）。
> 配套：`04_scripts/_common/prior_art.sh`（仓内 rc=1 ⇒ 触发外部检索）· `04_scripts/_common/session_start.sh` 查7 · `skill/diagnosis-index.md`「外部检索协议」。
> 铁律：**外部来源＝文档/自述级证据，一律先落「候选」；本仓实测通过才升「已合并」**。绝不因为外面说行就改框架。
> 越界红线：搜到私服 / 服务端模拟类方案 ⇒ 记进 §2「已评估·不接入」，不进候选。
> 维护：新增一行即追加；失效只改状态（候选 / 待验证 / 已合并 / 已否定 / 已过时），**不删行**。

## 4. 关键提醒（来自本仓既有结论的对照，避免误读外部结论）

- **「Cpp2IL 失败」有前提**：`skill/re-analyze/protection/nesec-inmemory-dex.md` §206 那次是 **Cpp2IL 吃内存 dump 出来的 so**（page 0 非 ELF 头、符号表被随机化）⇒ 失败属**输入坏**，不能据此判断 Cpp2IL 不支持新 metadata。下次遇到**磁盘版**新 metadata 先单独复测 Cpp2IL 再下结论。
- **星数与相关性在本领域反相关**：16k 的 AssetStudio / 19k 的 CheatEngine / 16k 的 VirtualXposed 对本仓痛点几乎无用；对口的是 **5 星**的 [NebulaIL2CPP](https://github.com/NebulaIL2CPP/NebulaIL2CPP)（Android ARM64 IL2CPP Native Mod Loader，与本仓同型）与 0.8k 的 ghidriff。**找方案时不要按星数过滤。**
- **中文源密度高于英文源**：加固 / 壳 / 手游 mod 这条线，看雪 + MT 论坛 + 吾爱的实操帖命中率明显高于 GitHub（例：易盾 so 加固 dump 的首条命中就是 MT 论坛帖）。
- **外部方案的最大价值常常是"别人已证明此路不通"**：省掉一整轮装机（≈20 min 重包 + 1 个用户 L3 实测轮），而不是拿到能直接用的代码。
