## 2. 六条重复出现的问题（按可回收成本排序）

### R1 `AGENTS.md` 因超预算被整份丢弃 —— 每个 step 都在裸奔（致命）
现象：两个会话每个 user 消息后都跟随
`Workspace instruction budget 65536 bytes: omitted AGENTS.md`。
实测 `AGENTS.md` = **67,191 B > 65,536 B 预算 ⇒ 整份不注入**。
代价：本工作区「读取/授权/协作/工具专属」的唯一入口文件**从未进入模型**，
规则靠 `read` 手动补读（55fc139c 仅 18 次、62fb2110 仅 3 次），
等于每轮都在无规则状态下开工——这是「反复违规但不知情」的总根因，也是本次两份复盘里
「明明有规则却没遵守」条目（如编辑前核对上下文）复发的机理。
回收：把入口拆成 ≤32 KB 的「必读核心」＋外链，或直接抬预算；预计一次改动回收此后**所有会话**的返工。

### R2 91–93% 的 step 只发 1 个工具调用（最大且最好回收）
实测 calls/step 分布：
- 55fc139c：`{1: 537, 2: 49, 5: 1}` ⇒ 单发占 **91.5%**
- 62fb2110：`{1: 487, 2: 33, 3: 1}` ⇒ 单发占 **93.5%**

且相邻调用大量互相独立（`ls` 三连、`grep` 两处、读两个文件、跑两个脚本）。
代价：若独立调用以 2 个合并，step 数比现在少 ~30%，等价省掉 30% 的 82 K 缓存重读。
回收：**并行批次纪律**（见 §3 A1），是本方案里纯收益、零风险的一条。

### R3 单个源文件吃掉全部编辑成本（`DkzjMod.cpp` 147 / 158 次触达）
| | bash 触达 | `read` | `edit` | 合计 |
|---|---|---|---|---|
| 55fc139c | 49 | 27 | 58 | **147** |
| 62fb2110 | 55 | 34 | 51 | **158** |

文件本体 63,443 B。`bash` 对它的 49/55 次触达里绝大多数是
`sed -n` / `grep -n` / `awk` 看片段——**原生 `read`（带 offset/limit）能一次拿到同样内容且更省**。
代价：两会话在同一个文件上花掉 = 一个文件的完整内容被重新载入约 10 遍。
回收：改文件前先 `read` 目标区间并**锁定行号**，编辑后不整份复读；
同一文件的连续 `edit` 合并成一批（见 §3 A2）。

### R4 用 bash 做文本检索／编辑（329 / 286 次）
两个会话里含 `grep`/`awk`/`sed -n`/`head` 的 bash 调用占全部 bash 的
**73.6%（329/447）** 与 **75.3%（286/380）**。
典型浪费形态：
- `cd /Users/aliang/Documents/nixiang && D=06_dumped/蛋壳战机/il2cpp_dump_1.1.8/dump.cs`
  出现在 **92 次**（62fb2110）/ **25+11 次**（55fc139c）。dump.cs 是 1,653,151 行，
  一次不设限的 grep 可返回 3 万字符（实测最大单条工具结果 **31,699 字符**）。
- 巨量结果直接进上下文 → 早触发 `compress` → 19/20 次手动压缩 →
  再被 `compaction/prune` 二次裁剪（18/11 次）。
回收：**检索走原生 `grep` 工具**（可限定 `path` + 单文件）＋
对大 dump「先落盘再切片读」，见 §3 A3。
计划里还有一条硬约束：同一 dump 文件的 grep **每轮 ≤10 次**，超了先改查询而不是加次数。

### R5 目标在压缩后丢失，用户被迫重复陈述（两次会话都发生）
用户原话（m00232 55fc139c）：「这是别人的mod改包，我让你找的是被人功能单」。
用户原话（m01299 55fc139c）：「你现在在干什么？你在找什么？我让你修偷盗技能不能升级的问题，你在干什么？」
用户原话（2652/2732/2746/2759/2828，62fb2110）：
「我让你去看别人的你看了吗？」「给我答复，不要在哪里自己瞎猜了」
「…你猜测完还是错误，浪费的是我时间知道吗？」「还在分析你麻痹啊，停止等我的软件啊」。
同时 `10_docs/蛋壳战机/硬约束.md`（2,284 B，正是为「压缩后不得凭记忆行事」而设）：
55fc139c 里只被引用 6 次、其中大部分是**收尾时才创建**；62fb2110 引用 18 次但首读在会话中段。
回收：每轮「用户新指令」到手先做**三行硬约束回填**（原话逐字＋交付形态＋判定方式），
落盘到 `硬约束.md`，再动手；压缩后开工第一动作是复读该文件。见 §3 A4。

### R6 深度探查的结论以「全量报告」入父上下文（62fb2110 尤重）
子代理回报最大的三条消息分别是 **35,557 / 25,448 / 1,937 字符**，
且第二条 25,448 字符与它前一条 35,557 字符内容高度重叠（同一份报告的回答＋settled 通知重复入上下文）。
再叠加 1,527 条 reasoning（55fc139c 812 KB、62fb2110 857 KB），
父上下文在 turn 3 就撞上 ~150 K 峰值。
回收：子代理**只回「结论 ≤20 行 + 文件路径 + md5」**，全文落盘；父只读落盘文件的相关段。见 §3 A5。

## 3. 可执行方案（A 立即做 / B 一周内做 / C 结构性）

### A1 并行批次纪律（对应 R2）
- 规则：**同一 step 内，凡「下一步动作不依赖其返回」的调用必须合并发出**。典型可合并组：
  1. 侦察组：`pwd` + `ls -la 目录A` + `glob *.apk` + `read 状态索引`
  2. 取证组：两个不同文件的 `read`／两处不相关 `grep`
  3. 构建组：`dump_*.sh` + 并行的 `md5/shasum` 校验
- 目标阈值：calls/step 从 1.09 → **≥1.6**（即单发占比 <60%）。
- 验证：会话结束跑一次 `acp_status`，或对 `session.v4.jsonl` 统计 calls/step 分布。

### A2 大源文件专用通道（对应 R3）
- 只对 `mod菜单/**/Games/DkzjMod.cpp` 一类「主战场文件」约定：
  1. 改动前：`read(offset, limit)` 锁定区间，记录行号；
  2. 插入类编辑 `old_string` 取「锚点行 ±1 行」（此条已在 1.1.8 复盘 P0-1 提出，此处补充**取行号**的机械动作）；
  3. 编译由 `dkzj_build_so.sh` 报错反向定位，**不整份复读文件**；
  4. 同一批逻辑改动连续 `edit` 一次发完。
- 验证：单会话对该文件的 `bash` 触达从 49/55 降到 ≤15。

### A3 大 dump 检索协议（对应 R4）
- 禁止：对 `06_dumped/**/dump.cs`（165 万行）做无 `head`/无 `-m` 的 grep。
- 模板（直接复用）：
  ```bash
  # 只取前 N 条并附行号，避免整段入上下文
  grep -n -m 20 -- '<符号名>' 06_dumped/蛋壳战机/il2cpp_dump_1.1.8/dump.cs
  # 需要上下文时按行号切片
  sed -n '1234560,1234620p' 06_dumped/蛋壳战机/il2cpp_dump_1.1.8/dump.cs
  ```
- 硬约束：同一 dump 每轮 grep ≤10 次；超限必须先换查询词或改走 `/tmp` 脚本聚合后再读小结果。
- 验证：单会话含 dump.cs 的 bash 从 103 次降到 ≤30，且无单条结果 >8 KB。

### A4 硬约束三行回填 + 压缩后复读（对应 R5）
- 用户每下达一次功能类指令，先落盘三行到 `10_docs/{游戏}/硬约束.md`：
  1. **原话逐字**（带消息号）；
  2. **交付形态**（真机换包／只出报告／改哪个文件）；
  3. **判定方式**（用什么证据算完成）。
- 每次 `compress` 之后、动手前，第一动作固定为 `read 10_docs/{游戏}/硬约束.md`。
- 连续 ≥15 次工具调用无结论 ⇒ 先输出「已知／未知／下一步／预计代价」（此条已在 1.1.8 复盘 P0-2 落地，
  此处升级为**每个新指令开头就做回填**，从源头预防）。
- 验证：用户「你在干什么」类质问次数 = 0；`硬约束.md` 首读与会话首条指令同轮完成。

### A5 子代理交付协议（对应 R6）
- 子代理回报**只允许**：`① 结论 ≤20 行 ② 落盘路径 ③ 行数/md5 ④ 未闭环项`。
- 全文一律落盘到 `10_docs/{游戏}/…`，父代理需要时按段 `read`。
- 同一报告禁止「回答 + settled 通知」两次全量入上下文（回一条即够）。
- 验证：单条子代理入父上下文消息 ≤3,000 字符（现状最大 35,557）。

### B1 入口文件减重（对应 R1，最高杠杆）
- 目标：`AGENTS.md` ≤ 32 KB，保证在任何预算下都注入成功。
- 拆法（不丢政策）：保留「读取路由＋授权边界＋协作纪律＋工具专属指针」为核心；
  把 `### 增量（日期…）` 各节（现 6 节，占大半）迁到 `10_docs/_state/规范变更日志.md`，
  `AGENTS.md` 只留一行指针。
- 校验：`wc -c AGENTS.md` ≤ 32768，并用任意一次新会话确认不再出现 `omitted AGENTS.md`。
- 备注：`TOOLBOOK.md` 已 140,715 B。它属按需读文件，但也要在入口写死「只读需要的章节」。

### B2 压缩预算前置（当前是反应式）
- 现状：19/20 次 `compress` 全部发生在上下文已接近峰值（~140–150 K）时，
  且 `compaction/prune` 还追加 18/11 次。
- 做法：把压缩触发点前移到 **~90 K**；并规定「一个压缩条目只装一个主题」，
  避免出现 `step 151: m00225–m00785 早期菜单/文档上下文（历史）` 这类 560 条消息的大块。
- 收益：减少 prune 次数与压缩时的长输出（compress 参数本身单条最大 10,850 字符）。

### B3 状态索引的读取代价
- 实测引用次数（工具调用参数内）：`_state/current.md` 23 / 2 次，`_state/games/蛋壳战机.md` 34 / 4 次。
  两个会话对同一个游戏状态文件的读取落差达 8 倍，说明没有稳定的「开工必读」节拍。
- 做法：开工节拍固定为 `current.md 摘要行 → games/{游戏}.md 当前摘要 → 硬约束.md` 三条一次并发读完，
  之后本轮不再重复读（除内容被本轮改动）。

### C 结构性：把「次数」变成可见指标
- 在 `04_scripts/_common/` 增一个只读统计脚本 `session_metrics.py`（读 `session.v4.jsonl`）：
  输出 calls/step 分布、bash 占比、单文件触达 top10、单条结果 >8 KB 的条目、compress 触发时的上下文水位。
- 用途：每轮收尾时一行输出，替代「凭感觉说这次效率低」。这是把 §2 六条从纪律变成闸门的唯一机械手段。
