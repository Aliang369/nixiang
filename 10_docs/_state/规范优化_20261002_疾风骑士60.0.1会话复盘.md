### 本会话 token/时间黑洞（按代价排序）

1. **54 个 hook 全装成功、5 个功能却无效 —— 没装探针就先下结论**（v4）。
   现象：logcat 里 54 条 `hooked` 全绿，用户实测 5 项无效。根因：挂点靠方法名猜语义，装钩成功 ≠ 打中真实调用路径。
   本可怎么做：**写功能代码时同步加 `JFQS_TRACE` 探针（每钩前 N 次打 `trace <fn> orig=<v>`），构建前就留好**，装机后一轮 logcat 即可判定「压根没被调用 / 被调用了但语义不是我以为的」。本会话是 v5 才补探针，等于白烧一轮构建+装机+用户实测。

2. **无限跳跃三轮反复（v2 → v4 → v5 → v6）—— 挂谓词而非挂数量上限**。
   现象：先挂 `CanMoreJump()`/`CheckCanJump()` 恒真 ⇒ 自动连跳；再挂 `PlayerJumpCooltime()` ⇒ 仍自动跳。
   根因：`CheckCanJump()` 是**状态门禁**（"现在允许起跳吗"），恒真 ⇒ 状态机每帧都认为可跳；`CanMoreJump()` 只是派生谓词 `MoreJumpCount > 0`。
   本可怎么做：**「无限 X」类需求一律先反汇编找到「数量上限」的来源函数**（此处 `GetMaxMoreJumpCount()` = `CheckEquipNormalArtifact(0x6d) ? level+1 : 1`，默认 1 ⇒ 地面 1 + 空中 1 = 共 2 跳，与用户描述完全吻合），只改上限，判定/门禁一律交回 orig。用户自己一句话就点破了正解。

## §2 已验证、可复用的关键事实

### 2.1 IL2CPP 按名 hook 的 ABI 表（实测，本轮全部 54 槽验证）

- 返回值：`bool`/`int` 走 `w0`，`float` 走 `s0`。
- 实例方法签名 = `(void* self, args..., MethodInfo*)`；静态方法 = `(args..., MethodInfo*)`。
- **结构体参数 > 16 字节走 AAPCS64 隐藏指针**：`PlayerData.TakeDamage(PlayerTakeDamageInfo info)`，该 struct ≈ 0x30 = 48 B ⇒ 实际签名是 `(void* self, int damage, void* info, void* method)`。
- **`ObscuredInt`（24 B）走 sret ⇒ 不可 hook `get_gold` 这类 getter**（本会话死路，`PlayerData` 金币还是局内货币不落库，`DataController` 无 `LoadGold/SaveGold`）。
- 本轮全部 54 槽一律 `rva=0, expectInsn=0, ns=""`（纯 by-name），RVA 只作注释——规避跨版本漂移，版本升级重打时不需要重算 RVA。

### 2.2 ★「无限 X」类功能：只改数量上限，不改判定谓词（本会话最贵的一条）

反汇编链条（`PlayerMovement`，RVA 均为 60.0.1 实测）：

| 函数 | RVA | 语义 | 能不能挂 |
|------|-----|------|----------|
| `GetMaxMoreJumpCount()` | `0x37C4728` | `CheckEquipNormalArtifact(0x6d) ? (artifactLevel + 1) : 1`，**默认 1** | ✅ **唯一正解**，改成 999 |
| `CanMoreJump()` | `0x37C47E4` | 纯派生谓词 `MoreJumpCount > 0` | ❌ 恒真 → 自动连跳 |
| `CheckCanJump()` | `0x37BB970` | 状态门禁（读 `[+0x470]`/`[+0x4d0]`/`[+0x4dc]` 三个 Obscured 状态位） | ❌ 恒真 → 每帧都认为可跳 |
| `PlayerJumpCooltime(float offset)` | `0x37C47A4` | `(Time.time - [this+0x838]) > (offset + const)` 起跳节流 | ❌ 恒真 → 每帧允许 |
| `PlayerMoreJumpCountReset(int moreCount)` | `0x37C46C0` | 落地时 `w0 = GetMaxMoreJumpCount() + moreCount` 存回 `[this+0x440]`（ObscuredInt 24 B） | 不必挂 |

**默认 1 ⇒ 地面 1 跳 + 空中 1 跳 = 总共 2 跳**，与用户「跳跃本身是限制只能跳两次」的描述完全吻合——用户的口头描述经常就是最好的定位线索。

### 2.3 ★「解锁」类功能：必须真写存档，不能让读谓词撒谎

v4 事故：`LoadPetUnlock` 恒真但不落库 ⇒ 装备后宠物 ID 进存档、拥有标记没进 ⇒ 重启关功能弹「尚未拥有该宠物」并**卡死 UI**。
v5 正解：`Load*Unlock` 同时调对应 `Save*Unlock`（用 `MemoFirst` 去重，避免每帧写盘）。
适用面：角色/皮肤/武器/宠物/神器/技能/协同全部解锁项。

### 2.4 ★技能冷却的真门禁不是名字里带 `CoolTime` 的那些函数

`CheckCanSubSkillByCoolTime()`（`0x3817E6C`）**名字骗人**，实际 = `CheckCanAttackSkill() && !CheckEquipNormalArtifact(0x23) && !CheckEquipNormalArtifact(0x15b)`；`SkillCoolTime` 只喂 UI 显示。
**真门禁 = `PlayerMovement + 0x588` 这一个计时字段**：
- `get_WeaponSkillCoolTime()` `0x37AA27C` = `ldr s0,[x0,#0x588]; ret`
- `SetWeaponSkillCoolTime(bool more)` `0x37B596C` = 把 `[this+0x588]` 填满
- `SetPlusWeaponSkillCoolTime(float)` `0x37D3D6C` = 加减

⇒ 拦这两个写入点 + `SafeWriteF32(self, 0x588, 0.0f)`，另加 7 个冷却 getter 返 0。

### 2.5 ★免广告的真收口 + 一个内置后门

- 真实广告走 MarSDK Java `com.mar.sdk.gg.topon.ToponAd`（`KSRewardLandScapeVideoActivity`，快手激励横屏），入口是 `MarSDKManager.ShowReward` argc=6（`0x3BD1B90`）/ argc=7（`0x3BDA06C`）⇒ 开免广告时跳过 orig，依次 `InvokeAction(onShow) → success → onClosed` 发奖。
- `ADXManager`（cid 138016）是**另一套未启用**的系统，挂它无效。
- **内置后门**：`0x3BD1CEC` 处 `bl #0x6B5D97C`（`UnityEngine.PlayerPrefs.HasKey(string)`），为 true 时直接 `br x2` 调 success 回调、完全不弹广告。key 名未挖出（metadata strings 无果，`[0x7254000+0x1e0]` interned 槽运行时填充）。
- `MarSDKManager` **不在 `Assembly-CSharp.dll`**（`FindClassInImage` 扫 8191 类未命中）⇒ 依赖跨 image `FindClass` 回退，**版本升级可能失效**（已记为 NOT PROVEN）。

### 2.6 RVA 零重定位的判定法（一次比对省掉整个 dump 重做）

比对照物与底包的 `libil2cpp.so` + `global-metadata.dat` 两个 md5；两者都逐字节相同 ⇒ 同一份 `dump.cs` / `methods.txt` 对两者通用，RVA 直接复用。本会话据此省掉了对整个 dump 的重跑。
换算口径：**`file_off = RVA − 0x4000`**。

### 2.7 并发装钩竞态会以 `SIGSEGV(SEGV_ACCERR)` 形式炸在 Dobby 内部

根因：`HookSlotInstall` 的幂等检查 `if (s.origPtr && *s.origPtr) return true;` 是**非原子 check-then-act**；UI 线程与游戏线程同时进 `SyncHooks()` ⇒ 同址两次 `DobbyHook` ⇒ `DobbyCodePatch` 越界 memcpy。
栈特征：`__memcpy_aarch64_simd ← DobbyCodePatch+96 ← DobbyHook+216 ← boot-framework.oat`。
修法：`std::mutex g_installMutex` + double-check。**注意 `DobbyHook(...) != 0` 只接返回码，接不住 Dobby 内部的进程级 SIGSEGV**，所以还需要 `sigsetjmp` 保护区 + `sigaltstack` + `g_slotDead[]` 槽位熔断（炸过的槽位本会话不重试，避免每 5 s 一次闪退）。诚实边界：Dobby 炸后内部状态可能不一致，只熔断不回滚。

### 2.8 菜单模板规范 vs 遗留先例（区分判据）

- 顶层**恰好 5 键**：`template_id` / `name` / `package` / `source` / `features`。禁止 `version`/`game_id`/`note`/`type`/`min`/`max`/`default`。
- 每个 feature **只有** `{feat_num, name}`，`name` 是纯功能名（无 `Slider_`/`Toggle_` 前缀与参数）。
- **`Category_*` 分组行不写进 features**，功能项保留真实下标（分组占 0 ⇒ 首项是 1；本游戏分组占 0 和 8 ⇒ `feat_num` 为 1–7、9–16）。
- `source` = 符号形式 `Games/{Xxx}Entry.cpp {数组名} + Games/{Xxx}Mod.h {枚举名} @ {版本}`。
- **遗留判据**：`10_docs/大话蜀山/dhss_menu_template.json`、`10_docs/地城狩猎/dcsl_menu_template.json` 含分组行 ⇒ 规范前遗留，**不可抄**。合规样例：`10_docs/消消英雄2/xxh2_menu_template.json`、`10_docs/潮汐守望者/cxswz_menu_template.json`、`10_docs/造梦西游/zmxy_menu_template.json`（均从 feat_num 1 起）。
- 后端 admin UI **无 JSON 批量导入**，只能逐字段粘贴 ⇒ `feat_num` 必须**带缺口**录入，否则全部开关串位。

## §3 优化方案（可执行，按价值排序）

### P0-1 `hook-rules.md` 新增 §28「谓词/门禁恒真陷阱：无限类只改数量上限」
- 问题：本轮无限跳跃烧了 3 轮往返（v2→v4→v5→v6），根因是把「状态门禁」和「数量上限」混为一谈。现有 `hook-rules.md` 27 节里没有这一条。
- 方案：新增一节，写清「判定谓词 / 状态门禁 / 数量上限」三分，规定：收到「无限 X」需求时，**先反汇编定位数量上限的来源函数**（典型形态：读 `ObscuredInt` 计数字段、或 `hasArtifact ? level+1 : 默认值`），只改上限；判定与门禁一律交回 orig。附本轮 `GetMaxMoreJumpCount` / `CanMoreJump` / `CheckCanJump` / `PlayerJumpCooltime` 四函数对照表（见本文 2.2）。
- [落点] `skill/re-implement/hook-rules.md:376`（文件末尾追加 `## 28. …`）。

### P0-2 `unlock-pattern.md` 新增「模式四：解锁必须真写存档」
- 问题：v4 用户存档被污染并卡死 UI。现有 `unlock-pattern.md` 的模式一~三都是「让门控判定撒谎」，且 `unlock-pattern.md:172` 一句「不要做一次性改存档」在「回退」语境下写的，**极易被读成本条的反面**。
- 方案：新增模式四，写明 `Load*Unlock` 必须同调对应 `Save*Unlock`（`MemoFirst` 去重防每帧写盘）；并在 `unlock-pattern.md:172` 那句后面补一句限定：「该句仅指『回退时不要靠一次性改存档』；**持久解锁本身必须真写存档**，见模式四」。
- [落点] `skill/re-implement/unlock-pattern.md:179`（追加 `## 模式四：…`）+ `unlock-pattern.md:172`（补限定语）。

### P0-3 `hook-rules.md` 新增 §29「功能无效先探针，别先改代码」
- 问题：v4 时 54 条 `hooked` 全绿但 5 项功能无效；根因是装钩成功 ≠ 打中真实调用路径。本轮是 v5 才补 `JFQS_TRACE`。
- 方案：新增一节，规定**写功能 hook 时同步加探针宏（编译期可关），首次装机后必须先跑一轮 logcat 读 `trace <fn> orig=<v>`**，再判定功能是否生效；只有确认「被调用了但语义不符」才动挂点。把「探针」从「出问题后的补救」提升为「首轮必装」。
- [落点] `skill/re-implement/hook-rules.md`（紧随 §28 之后追加 `## 29. …`）；可参照既有 `hook-rules.md:308` §26 的写法。

### P0-4 `finalize_game_delivery.sh` 模板断言升级
- 问题：现有断言只查顶层 5 键 + 每个 feature `set(x) == {'feat_num','name'}`，**抓不到 `Category_` 分组行混进 features**（本轮就是用户人工质问才发现的）。
- 方案：断言追加两条：① `features` 中不得存在 `name` 以 `Category_` 开头或语义为纯分组名的项；② 校验 `feat_num` 严格递增且无重复，并在检测到缺口时**打印**「检测到 feat_num 缺口 0/8 —— 确认这是分组下标，录入后台时必须带缺口」。
- [落点] `04_scripts/_common/finalize_game_delivery.sh`（菜单模板断言段）。

### P1-1 `_TemplateMod.cpp` 模板级补并发保护 + 信号兜底
- 问题：本轮两次闪退（并发装钩竞态、Dobby 内部崩溃）都源于**模板本身没有这些保护**，是新游戏生成器产出的骨架缺失，每个游戏都要重新踩。
- 方案：把 `std::mutex g_installMutex` + double-check 的 `HookSlotInstall`、`sigsetjmp` 保护区（`DobbyHookGuarded`/`ReadU32Guarded`/`RunGuarded`）、`sigaltstack` 备用栈、`g_slotDead[]` 槽位熔断全部下沉到模板；`thread_local` 标注清楚（hook 体在 UI/游戏/SDK 回调线程并发）。
- [落点] `mod菜单/starry-mod-menu/app/src/main/jni/Games/_TemplateMod.cpp`（11,986 B）+ `_TemplateMod.h`（1,564 B）；同步 `skill/re-implement/hook-rules.md` §0 的生成器说明。
