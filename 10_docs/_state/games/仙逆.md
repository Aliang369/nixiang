## 功能实现（全部 JS 层，`Games/XnbzMod.cpp` 的 `kPatchJs`）

| 功能 | 挂钩点 | 做法 |
|---|---|---|
| 无敌 | `BattleUnit.prototype.updateState` 本地血量账本 + `isAlive` / `health` getter | 回放中把我方生命顶住（`isAlive` 恒真） |
| 伤害倍率 | `BattleUnit.prototype.applySequentialDamage` + `BattleManager.applyActionEffect[SegmentOnly]` 的 `scale(t)` | 我方对敌伤害放大（1 = 关，2..100） |
| 强制胜利 | 引擎 `BattleManager.prototype.startBattle` | 读服务端真实 `winner` 后改 `winner=1`（**只影响显示/回放分支**） |
| 重试判胜 | `BattleModule.prototype.startBattle` + `Network.requestFightResult` | **结算回包到手后**判断：服务端判负 ⇒ 本场不伪造胜利、不弹失败礼包、1.5 s 后重开本场让服务端重算（`RETRY_MAX=3`，超限打 `retry cap hit`） |

诊断串：`replay try#N win=? actions=?` / `settle: rawWin=? rewardItems=? retry=?` / `server judged LOSS -> retry #N/3` / `server judged WIN after retry #N` / `retry cap hit (3)` / `force win #N`。

## ★服务端权威边界（判停依据）

1. 战斗在 `game.fightbegin` 由服务端算完整场；请求体只 `{type,id,extra}`，`extra` = 记录号/排名，**不含我方属性**。
2. 奖励 = `game.fightresult` 回包的 `changes.items`；`ResponseUtil.checkResponse` 只处理 `messages` 推送，**不写本地账目** ⇒ 客户端改 `isWin` 只改显示。
3. 战斗相关服务端接口只有 `fightbegin/fightresult/fightoverwhelming/pvesweep/templequickbattle/fourduelsweep/outertrialsweep/activitydrummingquicksettle`，**无任何「客户端上报胜负」通道**。
4. 重试判胜（唯一理论可行路径）实测：服务端判负后重算不翻盘 ⇒ 按确定性结算处理。**不做本地假奖励**（用户明确不要）。
5. 将来要真奖励只剩：真提升服务端战力 / 走服务端本来就发奖的入口（碾压、扫荡，门槛在服务端）/ 服务端侧改动。

## 三件环境改动的实现

1. **去签名**：`sign/SignSpoof.java` 新增 `XNBZ_PKG` / `XNBZ_CERT_B64`（原厂 `CN=qqian` 证书回灌）＋ `classes7.dex` 的 `TapSignKit.getSign(Landroid/content/Context;)Ljava/lang/String;` 固定返回 `82c51c4ac68ac5d3197ef4c2b19e1ef6`（标记 `# starry_sign_bypass`）。
2. **TapTap 强制网页登录**：`sign/TapLoginForceWeb.java` 的 `PKG_WHITELIST` 追加 `com.qqsy.xnbz` ＋ `classes7.dex` 的 `ClientLoginUtils.isClientLogin(Landroid/app/Activity;…)Z` 恒 false（标记 `# starry: force WebLogin`）。本作走**新版路径**（`TapTapLoginActivity` + `ClientLoginUtils` + `WebLoginFragment`），无旧版 `TapTapActivity` / `ClientLoginHandler`。
3. **菜单注入**：`classes11.dex`（星空 5 类）+ Manifest 分支 B（provider `authorities=com.qqsy.xnbz.starryinit`、`initOrder=2147483647`；service `MenuService` `foregroundServiceType=specialUse`）+ 权限 `SYSTEM_ALERT_WINDOW` / `FOREGROUND_SERVICE(_SPECIAL_USE)`；装机后 `appops set com.qqsy.xnbz SYSTEM_ALERT_WINDOW allow`（Android 16 上须走 `su -c`）。

## 途中踩过的坑（防复现）

1. smali 方法体替换必须用 `.locals` 而非 `.registers`（否则 dex2oat 校验 `outs_size > registers_size` 拒绝，启动即崩）。
2. Android 16 `appops set` 须走 su（shell uid 2000 无 `MANAGE_APP_OPS_MODES`）⇒ `xnbz_install.sh` 三级回退；**不授权则悬浮菜单不显示**。
3. v4 重试判胜的时机 bug：在回放开始 700 ms 就重开 ⇒ 战斗被打断、服务端无第二场；v5 改为**结算回包后** 1.5 s 重开。
4. `evalString` 注入必须先缓存 `XnbzHooks` 全局引用（`FindClass` 在 `JNI_OnLoad` 之外会因 classloader 失败）。
