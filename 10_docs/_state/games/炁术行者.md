- **★ 2026-10-07 两处真机复议（用户报「默认值拉满 + 功能没效果」）**：
  1. `SeekBar` 默认值原写成 max（`_20`/`_50`）⇒ 菜单一开就是拉满。已改成下限：`SeekBar_伤害倍率_1_20_1` / `SeekBar_减伤_0_50_0`（原版口径）。
  2. **投值通路错**：补丁原先只在「首次注入」装一个页面内 `setInterval` 轮询，而星光菜单是**独立 Activity 浮层**，盖住游戏时 WebView 变不可见 ⇒ 浏览器节流/冻结页面定时器 ⇒ 拖完滑块值投不进游戏。已改成**每次注入都重读状态并投值**（Java 守护跑在 Handler 上，不受页面节流影响），页面内 `setInterval` 只作前台兜底；并加了 `beat` 心跳日志便于对账。离线回归补了对应断言（19 项）。
  3. **★ 根因（框架级 bug，已修）**：`ModBridge` 构造函数里**无条件** `Preferences.clearFeaturePrefs()`（注释写的是「功能列表随 so 切换就丢旧偏好」）——而菜单浮层**每次重开都新建 ModBridge** ⇒ 玩家刚拖的滑块值立刻被抹掉。走 native hook 的游戏无感（值在 so 里），但 H5/JS 补丁靠 `StarryH5.getState()` 读这些偏好取值 ⇒ 现象就是「拖了滑块游戏没反应」。
     修法：新增 `Preferences.clearFeaturePrefsIfListChanged(sig)`，**只有功能列表指纹真的变化**才清；`ModBridge` 传 `nativeGetFeatureList()` 拼出的指纹。
     连带的第二个坑：某些 ROM 的偏好 XML 往返会**给字符串补尾随空白**（实测多 4 个空格），直接 `equals` 会永远判「变了」⇒ 每次启动照清。已加 `canonSig()`（去全部空白后再比/再落盘）。实测三次冷启「清偏好」日志 0 次。
     ⚠️ 影响面：该改动对**所有**走 `ModBridge` 的游戏生效 —— 从前「每次启动默认全关」的隐式行为，变回「按『保存功能偏好』保存玩家设置」（即框架原本的设计语义）。
