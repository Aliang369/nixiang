# 游戏状态摘要目录

## 写入规则

- 每个游戏一个 `{游戏}.md`，保存该游戏的详细状态、hash、证据入口、挂起项和下一步。
- 文件结构固定为三段，**`当前摘要` 必须在最前面**（后续会话只读这一段即可开工）：
  1. `## 当前摘要` —— 最近结论、粗状态、下一步；一行一条，不写过程。
  2. `## 本地产物与关键输入` —— 见下方专节。
  3. `## 历史记录` —— 旧轮次、迁移历史，只在摘要要求追溯时才读。
- `../current.md` 只保留一行索引，不复制长结论。
- 更新顺序：先改本目录的目标游戏摘要，再更新 `../current.md` 的最近日期和粗状态。
- 单一功能反复反馈时，在游戏摘要中链接 `功能验收卡.md`；长日志目录补
  `README.md`，只列决定性证据和最短复现命令。

## 本地产物与关键输入（每份摘要必备）

目的：让下一次会话**不用扫目录**就知道手上有什么、哪些是不可再生的。

```markdown
## 本地产物与关键输入

| 路径 | 内容 / 指纹 | 可再生性 | 说明 |
|---|---|---|---|
| 06_dumped/{游戏}/{轮次}/ | 解密文本（版本档案） | 可再生（重跑解密） | 指纹对照依据 |
| 09_test、07_patched 下的底包 APK | 身份/hash 登记在 [底包再获取台账](../底包再获取台账.md) | **已删（2026-09-30 起）** | APK 不留本地；删前先登记，再获取路径见台账 |
| 10_docs/{游戏}/evidence_日期/ | 决定性日志行 | — | 复现入口 |
```

- **`02_apks/` 与 `08_output/` 不在此表登记为"现状"**：两者由用户手动增删、AI 不可控。
  只写"用户声明：本次是否有原版/星光包"并标注日期；**不要**在摘要里断言其存在性。
- 可再生性只有三档：可再生（写出重跑命令）/ 不可再生（写出为什么）/ 未知（写出待确认）。
  标注不可再生的输入，清理时必须显式列出并保留。

## 读取规则

- 会话开始只读 `../current.md`，确认目标游戏后只读对应的 `{游戏}.md` 的
  **「当前摘要」与「本地产物与关键输入」**两段；不要为“同步状态”通读历史段。
- 不因“同步状态”通读本目录全部文件。
- `current.md` 中的旧长记录已完整保存在
  `../history/current_before_split_20260920.md`，需要追溯历史时再定点查阅。
