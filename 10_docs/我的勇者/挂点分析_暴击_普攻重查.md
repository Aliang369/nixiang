## 2. 暴击判定只有一处

`Battle.Step.Skill.DamageCriticalStep.BeginCalculateStep` RVA **0x4894218**（dump 612496，TypeDefIndex 16806），区间 0x4894218–0x4894428：

```
0x48942B8  A = fromObj.Get<X>(0x6A)            接口方法，x1=106
0x4894324  B = targetObj.Get<X>(0x6B)          接口方法，x1=107
0x4894328  p = A - B
0x4894330~40  p = clamp(p, 0, 1)               fmin + fcsel(pl)
0x489434C  roll = Random.Range(0f,1f)          bl 0x789A524
0x4894350  fcmp roll, p
0x4894354  b.pl 非暴击分支 (0x48943A0)          即 roll >= p → 不暴击
── 暴击分支 0x4894358 ──
0x48943D4  x0 = fromObj.Get<X>(0x6C)           x1=108，返回引用类型
0x48943E0  x0 == null → 抛 NRE
0x48943E8  mult = f(x0)                        bl 0x4896428（ObscuredFloat 取值类工具，333 个调用者）
0x48943F4  x8 = ctx.log (+0x48)
0x48943FC  [x8+0x258+0x8C] = mult              ← 暴击倍率落盘
0x4894400  ctx.curValue(+0x28) *= mult
0x4894410  ctx.isCrite(+0x3C) = 1
── 非暴击分支 0x48943A0 ──
0x48943B8  [log+0x258+0x8C] = 1.0f  (w10=0x3F800000)
0x4894410  ctx.isCrite(+0x3C) = 0
```

**`ctx.isCrite`(0x3C) 的唯一写入者就是这条 `strb w8,[x19,#0x3c]`(@0x4894410)。**
- 扫描整个 step 代码区 0x4892000–0x489A000，`strb w?,[x?,#0x3c]` 只有 0x4894410 一处；
- `GetDamageSettle`(0x47F9D0C–0x47FA6DC) 与 `Settle`(0x47F8768–0x47F94F8) 区间内**没有**任何写 `+0x2C`/`+0x3C` 的指令；
- `DamageSettle`（技能配置类，dump 606553）没有 isCrit 字段 → 暴击不可能来自技能配置或服务端字段。

⇒ **推断（证据链充分）**：`DamageCriticalStep` 必须出现在 `SkillDamagePipeline` 的 23 步里，否则玩家伤害永远不会暴击（游戏内白字/黄字都存在）。同一结构下 `SkillDamageFromMonsterPipeline` 的 12 步也必然含它（怪物会暴击）。

### 是否存在第二条暴击判定？——没有
- `BC_SettleCrit`（dump 613869）：buff 触发条件（`IBuffActiveCondition`），与伤害结算无关；
- `BattleAttrTools.GetCritRate`(0x48A0C28) / `GetCritDamage`(0x48A0934)：属性表换算工具，**全 so 无直接 BL 调用者**（只被虚调用/间接使用）；
- `OnCriChange`(0x48A117C) / `OnCriDamageChange`(0x48A10CC)：属性变更回调，改的是 MAttribute；
- 全 so 里 `Random.Range(0,1)` 的 129 个调用点中，落在 step 区的只有 0x48935D8、0x489384C、0x489434C（本暴击步）、0x4896AF8，其余是伤害浮动等，没有第二处"暴击 roll"。

## 3. 为什么你打 0x4894350 没生效

先排掉低级错误：文件偏移 0x4890350 原始字节 = `00 20 28 1e 65 02 00 54`
（`fcmp s0,s8` + `b.pl`），RVA 0x4894350 反汇编一致，**位置没错**。
若该步真的执行，无条件跳 0x4894358 必然置 `ctx.isCrite=1` → `DamageSettleData.isCrite=1` → `ShowDamageText` 走 `GetNumStr(isCritical=true)` → 必出黄字。

所以"没黄字"意味着至少一条前提不成立。按可能性排序：

1. **该 so 的 23 步里没有这个 step**（与 §2 的必要性推理冲突，但只有运行时能证伪；见 §4 探针）。
2. **你看到的数字不是这条链显示的**：`LHeroRunningHitProcess`（dump 587572）重写了 `ProcessDamage`(Slot 17, RVA 0x4782C68) 与 `ProcessAddHp`，其 `ProcessDamage` 内**没有** `ldrb [#0x2C]`、也没有调用 `ShowDamageText`(0x4781268)，只做纯虚调用（0x4782D18/0x4782D88/0x4782DF0 `blr`）。若测试场景走的是这个子类，强制暴击不会改变数字样式。
3. **补丁页被覆盖**：热更 so 在进入战斗/切场景时可能重新映射或被完整性校验还原。"内存已确认"需要在**进战斗之后、同一 pid** 再确认一次（`/proc/<pid>/maps` 里 so 的基址 + `maps` 对应页的 4 字节）。
4. **反作弊复算**：`BattleServerLog.CheckDamage` RVA 0x47ECBAC 会再次调用 `OnBeSkillHit`(0x47ED44C) 复算伤害并 `ShowBanLog`；暴击率异常可能触发纠正/丢弃，但不会把数字变白。

## 4. 一次测出分流：4 字节探针（先打这个）

**文件偏移 0x47F77E0（RVA 0x47FB7E0，在 SettleDamage 内）**

| 项 | 值 |
|---|---|
| 原始 | `28 F3 40 39` = `ldrb w8,[x25,#0x3c]`（读 ctx.isCrite） |
| 改成 | `28 00 80 52` = `mov w8,#1` |
| 下一指令 | 0x47FB7E8 `strb w8,[x21,#0x2c]`（写 DamageSettleData.isCrite）保持不变 |

作用：**绕开整条 stepList**，让每一条伤害结算的 `isCrite` 恒为 1。

- 结果 A：出黄字 ⇒ 显示链、管线选择、池对象都正常，问题只在"暴击步没跑到"⇒ 回 0x4894218 重新定位（先查是否在 23 步内）。
- 结果 B：仍无黄字 ⇒ 你看到的数字根本不走 `DamageSettleData→ShowDamageText`（对应 §3-2），要把挂点挪到显示层/对应模式的 HitProcess。

这条探针只改显示标志，不改伤害数值，副作用可逆、易归因。

## 5. 最终改法（"一定生效"的形态）

### 主挂点（真暴击，暴伤走角色属性）
`DamageCriticalStep` 0x4894350：`1e282000` → `02 00 00 14`（`fcmp s0,s8` → `b #+8`）
＝你现有的补丁。它是对的地方，但需先过 §4 探针确认该步在链路里。

### 兜底 / 叠加（视觉 100% 暴击 + 固定 2 倍伤害）
同一函数 `SettleDamage`，三处 4 字节，都在文件偏移 0x47F77xx：

| 文件偏移 | RVA | 原始 | 改成 | 作用 |
|---|---|---|---|---|
| 0x47F77E0 | 0x47FB7E0 | `28 F3 40 39` `ldrb w8,[x25,#0x3c]` | `28 00 80 52` `mov w8,#1` | isCrite 恒 1（黄字） |
| 0x47F77E4 | 0x47FB7E4 | `E1 03 27 1E` `fmov s1,wzr` | `01 10 20 1E` `fmov s1,#2.0` | 常量槽改为 2.0 |
| 0x47F77F0 | 0x47FB7F0 | `00 48 21 1E` `fmax s0,s0,s1` | `00 08 21 1E` `fmul s0,s0,s1` | value = max(cur,0)×2 |

注意：**若暴击步同时也在跑**，`ctx.curValue` 已被乘过一次暴伤，最终 = 暴伤 × 2（叠加）。只想要黄字不动伤害，就只打第一处。

### 不推荐
- 改 `fromObj.GetX(0x6A)` / 属性表（`GetCritRate`）——那是**共用的属性取值接口**，牵一发动全身；
- 改 `ProcessSettle` / `ShowDamageText` 的 isCritical 分支——只能改颜色，伤害不涨，且分支多易错。

## 6. 未闭环清单

1. **23 步的精确成员名单**：`SkillDamagePipeline..ctor` 用 `ldr x0,[GOT 0x8012xxx] → bl 0x31e41DC(Box) → bl AddStep` 的形态逐条加步（0x4798C24 起，共 23 个块），GOT 槽位序列已提取（0x7B8,0x7C0,0x7C8,0x800,0x818,0x6D8,0x6E0,0x6E8,0x6F0,0x6F8,0x700,0x710,0x718,0x758…），但 GOT 槽 → `Il2CppClass*` → TypeDefIndex 的映射在 metadata v31 里不在 `global-metadata.dat`（`metadataUsagePairs` 已移入 so，需运行时解析），静态无法一一命名。已用"必要性推理"补位：isCrite 唯一写入者只能来自该步。
2. **`fromObj.GetX(0x6A)` / `targetObj.GetX(0x6B)` 的确切语义**：已确证是同一接口类的两个方法（dispatch 各用 `interfaceOffset+4`），参数 106/107，返回 float；判定式 `p=clamp(A-B,0,1)` 说明是"暴击率 − 目标抗暴"。具体对应 `MAttribute` 的哪个属性 id 未逐一定名。
3. **`0x4896428` 的确切身份**（暴击倍率取值工具，333 个调用者）：按 `(x0=引用类型, x1=null) → float` 形态推断为 Obscured 数值解包，未验证。
4. **测试场景用的是哪个 HitProcess 子类**（`BaseLHitProcess` vs `LHeroRunningHitProcess` vs `LHeroRunningOtherHeroHitProcess`）——决定 §3-2 是否成立，需运行时确认。
5. 0x4894350 补丁"已刷 icache 但无效"的现场证据（进战斗后的 `/proc/<pid>/mem` 复核）未取得，属运行侧，不在本次静态范围。
