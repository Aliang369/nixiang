## 0. 结论速览（先看这 8 条）

1. **0x489433C 的 `fcsel s8,s1,s0,pl` 确实是「暴击率 clamp01」，s8 就是有效暴击率**：s8 在 0x48942CC 由 `GetAttr(106)` 结果写入，0x489433C 被 `clamp01(rate-resist)` 覆盖一次，此后到 0x4894350 之间**再无人写 s8**。前序文档判断正确。
2. **比较方向正确**：`b.pl`（cond=PL，编码 `65 02 00 54`，imm19=19→+0x4C）落在 **0x48943A0 = 非暴击分支**；即 `r >= rate → 非暴击`。成立。
3. **Q3a 的怀疑被否证：暴击分支确实把 w8 置 1** —— 0x4894404 `mov w8,#1`（`28 00 80 52`），随后 0x4894410 `strb w8,[x19,#0x3C]`。非暴击分支 0x48943B0 `mov w8,wzr` 置 0。两支都完整，**不存在「忘了置 isCrite」的 bug**。
4. **s8=1.0 后必然走暴击分支**：`Random.Range(0f,1f)` 返回 r∈[0,1)，`fcmp s0,s8` 得负 → N=1 → PL 不成立 → **不跳，直落 0x4894358**；暴击分支内 `curValue *= 暴伤(attr108)` 且 `isCrite=1`。**补丁语义完全正确**。
5. **无第二道门**：整函数 0x4894218–0x4894424 内只有空引用检查，**没有 canCrit / 技能禁暴击 / 目标类型判断**；0x4894334 之前、0x4894410 之后都没有任何其它判定。
6. **无下游覆盖**：Battle 段（0x47–0x4A）内写 `log[+0x258][+0x8C]` 倍率槽的只有 2 处 —— 0x47F13EC 与本函数 0x48943FC；写 `[ctx+0x3C]` 的在本函数邻域只有 0x4894410 一处。**isCrite 与倍率槽都不会被后续 step 抹掉**。
7. ⇒ **失效原因不在指令逻辑**。既然字节确已在内存里、语义又必然强制暴击，唯一自洽的解释是**被改写的这 4 字节没有进入实际执行路径**（详见 §6 的三级判据）。这不是「改错指令」，而是「改了但没跑」。
8. **最简正确改法**：把 **0x4894350** 的 `fcmp s0,s8`（`00 20 28 1e`）改成 **`b 0x4894358`（`02 00 00 14`）**。单条 4 字节，**不看标志、不看 s8、不看随机数**，无条件直落暴击分支（顺带省掉一次 Random.Range 调用）。

## 3. Q1 复核：0x489433C 是不是「暴击率 clamp01」→ 是

- 语义链：`s8 = GetAttr(106)` → `diff = s8 - GetAttr(107)` → `fcmp diff,0` → `fcsel pl ? min(diff,1) : +0.0`
  = `clamp01(暴击率 − 抗暴)`。
- **标志位不留缺口**：0x4894334 `fcmp` 之后到 0x489433C 之间只有 0x4894338 `fmov s0,wzr`（浮点移动，不改 NZCV）。
- **s8 不可被后续覆盖**：0x4894340/0x4894344/0x4894348/0x489434C 分别写 s0/s1/x0 并调用 Random.Range，**都不碰 s8**；AAPCS64 下 d8 是 callee-saved，`bl` 回来 s8 仍在。
- ⇒ **把 s8 钉成 1.0，是有效且唯一的暴击率入口**。

## 4. Q2 复核：强制 1.0 后是否真会走到暴击分支 → 会

- `b.pl` 的 cond 字段 = 0b0101 = **PL（N==0）**；`fcmp s0,s8` = `r − 1.0`，因 `r∈[0,1)` 必为负 → N=1 → PL 假 → **不跳，直落 0x4894358**。
- 暴击分支内：`mov w8,#1`（0x4894404）→ `fmul s0,s0,s1`（0x4894408，`curValue *= 暴伤`）→ `strb w8,[x19,#0x3C]`（0x4894410，`isCrite=1`）。
- ⇒ 前序文档 §2-C 的三条结论（真暴伤、就地乘、写 isCrite）**全部成立**。

## 6. 真正的失效原因判定

**指令逻辑已被证否为原因。** 剩下的机制只有一种类型：**被改的 4 字节没有进入实际执行流**。按可能性排序并给出**可判定的三级探针**：

### 因 1（最可能）：I-Cache 未同步
ARM64 上 dcache 与 icache 不保证一致。若补丁是「`mprotect` + 裸写 / `process_vm_writev` / `dd` 到 `/proc/pid/mem`」，**数据读回一定是新字节**（这正是「运行时内存已确认字节变成 08 10 2e 1e」能成立的原因），但 **CPU 取指仍可能命中旧 icache 行** → 行为零变化。这是「内存看着改了、游戏没反应」最典型的成因。
- 判据：补丁后必须对 `[addr, addr+4)` 做一次 `__clear_cache` / `cacheflush(ICACHE)`；Frida 场景用 `Memory.patchCode()`（内部自动 flush），**不要**用 `Memory.write()` 改代码。
- 交叉验证：把 0x4894354 的 `b.pl` 也改成 `nop`（`1f 20 03 d5`）。若两条 4 字节补丁**都**毫无变化，基本可锁定为「代码写入未生效」而非语义问题。

### 因 2：改的模块 ≠ 实际执行的模块（热更覆盖）
热更包场景下 `libil2cpp.so` 可能同时存在于 APK `lib/arm64-v8a/` 与 `/data/data/com.rsg.wdyz/files/…` 热更目录，游戏优先加载后者。此时打 APK 内 so 或打错路径的那份，**文件确实被改了、游戏确实没变**。
- 判据：从 `/proc/<pid>/maps` 取实际映射的 `libil2cpp.so` 路径与 inode，`sha256` 与 `/tmp/wdyz357/libil2cpp.so` 比对；并确认补丁写入的是**同一个映射**（基址 + 0x489433C 落在该 mapping 的 [start,end) 内）。

### 因 3：写入地址口径多算/少算 0x4000
`VA = Offset + 0x4000`。若补丁表里既写了 Offset 又让装载器再加一次 0x4000，实际落到 `0x489833C`；此时若「验证」也在同一个错地址读回，就会看到自己写的字节，形成自证循环。
- 判据：验证时不要按偏移读回，而是 **dump 出 `base+0x4894330` 起 0x20 字节并反汇编**，确认改后的序列是 `fmov s1,#1.0 / fmov s0,wzr / fmov s8,#1.0 / fmov s0,wzr / fmov s1,#1.0`。若在 `base+0x4894330` 看到的是 `fcsel`，就说明写偏了。

## 7. 「能真正确保 100% 暴击」的最简正确改法

### 7.1 首选：0x4894350 单条 4 字节 `b 0x4894358`

| 项 | 值 |
|---|---|
| 文件偏移 | **0x4890350**（RVA/VA 0x4894350） |
| 原字节 | `00 20 28 1e`（`fcmp s0, s8`） |
| 新字节 | **`02 00 00 14`**（`b #8` → 0x4894358） |
| 编码校验 | `llvm-mc -triple=aarch64 -disassemble` → `b #8` ✅ |
| 顺带效果 | 0x4894354 的 `b.pl` 被跳过；**Random.Range 调用（0x489434C）也不再执行** |

**为什么这次一定生效（相比 `fmov s8,#1.0`）**：
- 不依赖 `sFlag`、不依赖 `s8`、不依赖随机数、不依赖 `Random.Range` 的返回值域 —— **无条件转移**；
- 不受「0x4894350 之前 s8 被任何东西改写」影响（原方案把正确性押在 s8 上）；
- 仍从 0x4894358 进真正的暴击分支，**照拿真实暴伤、照写 log 倍率槽、照置 isCrite=1**，不是「假暴击」；
- 唯一代价：随机数不再消耗（对本函数无副作用，r 只在此处使用）。

### 7.2 备选（做 A/B 对照用，不建议做正式方案）
- 0x4890354 `b.pl` → `nop`：`65 02 00 54` → **`1f 20 03 d5`**。等价效果，且**不看标志位**，可与 7.1 互为验证。

### 7.3 是否需要对英雄门控 → **需要**
- 本函数**没有任何「攻击方是英雄」的判断**，`ClassTagOf` 之类的东西一次都没出现；它按 `context->fromObj` 的 106 − `targetObj` 的 107 通用结算。
- `SkillDamagePipeline` 与 `SkillDamageFromMonsterPipeline` 是两条独立管线（dump.cs:589345 / 589360），但**无法从静态上排除两者复用同一个 `DamageCriticalStep`**（前序文档 §5.1 的搜索为 0 命中，不代表排除）。
- 因此若不做门控，**怪物打玩家也会 100% 暴击**（玩家承受的暴击伤害显著上升，属于玩法副作用）。门控判据沿用已验证的 `ClassTagOf(*(void**)(ctx+0x10))==2`（HeroCore），且必须在 `x19` 仍有效的位置取。
- 若选 7.1 的纯 4 字节无条件跳转，则**没有门控余量**，副作用必然存在；要门控就得回到前序文档方案 A（`b <stub>` + 判类 + 分别回 0x48943A0 / 0x4894358）。

## 8. 未闭环项（明确「待验证 / 读不懂」）

1. **待验证**：本轮只能证明「指令语义必然强制暴击」，无法从静态上证明现场补丁为何没生效。§6 的三个因需按三级探针之一在设备侧确认（**需真机/运行期**，超出本轮只做静态的边界）。
2. **待验证**：0x47F13EC 那处写 `[+0x8C]` 的代码属于哪个类/是否在 `DamageCriticalStep` 之后运行；本轮只确认它不在本函数邻域，未定位其宿主函数。
3. **待验证**：怪物→英雄是否复用同一 `DamageCriticalStep`（决定门控必要性）。两条管线的 step 组装在 `Creat()/.ctor()` 里只出现 boxed struct 的类元数据指针，**本轮未找到可判定的字面量证据**，结论仍为空。
