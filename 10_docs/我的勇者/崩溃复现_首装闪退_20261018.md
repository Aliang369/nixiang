## 4bis. 游戏自带热更框架的行为（决定性的第二块证据）

崩溃前 `23:57:33.8~34.06` 这段全是游戏自己的补丁框架 `r2.labs.unitypatch.UnityPatch`（原生 `libunitypatch.so` 13 KB + `libapkpatch.so` 412 KB，dex 在 `classes.dex`）：

```

I UnityPatch: LibAbi :arm64-v8a

D UnityPatch: SourceSoDir: …/lib/arm64
I UnityPatch: ClearCache. / FilesCheck.
I UnityPatch: PatchNew
I UnityPatch: PatchCheck.
I UnityPatch: ZipTools.CheckCRCZip(…/files/update/patch/assets/base.zip,…)
I UnityPatch: PatchCheck.NewPatchSoDir == false        ← 没有可用补丁副本
I UnityPatch: ZipTools.CheckCRCZip(…/files/update/current/assets/base.zip,…)
```

⇒ 该游戏**运行时优先用 `files/update/current`（热更副本），没有才回退到 APK 内的 so**。这与旧机 `f9a116a2` 上 `/proc/<pid>/maps` 证实「加载的是 update/current 的 so」完全一致。

## 4ter. 根因推断（证据支持，机制待验证）

**包内 so 与包内 metadata 不是同一版本：`libil2cpp.so` = 热更 build 357（4.ter-1），`global-metadata.dat` 仍是底包 09-24 那份（外科脚本只替换 so，不碰 metadata；zip 内条目时间戳 09-24 佐证）。**

- 旧机 `f9a116a2`：早已热更到 357，`files/update/current` 里有配套的 357 so+metadata ⇒ 运行时根本不加载包内 so ⇒ 功能正常。
- 干净机器（本机/别人）：无 update 副本 ⇒ 回退加载包内 **357 so + 底包 metadata** ⇒ il2cpp 类型/方法表错位 ⇒ `Class::Init` 类互递归 ⇒ 栈溢出崩溃（与 §3 栈形态吻合）。

待验证点：357 与底包的 metadata 是否真的有语义差异（两份同为 30,489,828 B；`挂点分析_简报_hu357.md` 记录的运行时 metadata sha256 `fe5ed638…` 与本包内 `2959d55b…` 不同，但该文件已被后续操作覆盖，无法本地复现比对）。

## 5. 与 2026-10-18 白天「实测通过」的差异（重要）

白天那次是在旧机 `f9a116a2` 上**同签名覆盖安装**——那台机器早已热更到 build 357，`files/` 下已有 357 的运行时数据；本次是**全新安装**（`files/` 从零生成）。
⇒ 同一 apk 在「已热更过的机器」可用，在「干净机器」首启即崩，与用户反馈的「别人装了就闪退」一致。

## 6. 对照实验与根因确认（2026-10-19 补齐，本节已闭环 §6 旧结论）

- **A/B 对照**：用户在同一台小米上装回官方原版并 `adb pull` 底包（`02_apks/我的勇者/我的勇者_7.6.3_base.apk`，md5 `4274b183…`，签名 `CN=rn`，包内 so sha256 `8640f5fa…`）→ 冷启**空转 25 s 存活无崩溃**（pid 27320）。
- **关键交叉验证**：官方原版（底包 so）跑起来后，加载器写出的运行时 metadata sha256 = `fe5ed638…`，与 `挂点分析_简报_hu357.md` 记录的「运行时 metadata」完全一致；而包内静态 metadata 是 `2959d55b…`。
  ⇒ 该文件是**加载器改写后的副本**，不是版本标记；版本配套关系不变：**底包 so + 底包 metadata = 可跑；357 so + 底包 metadata = 崩**。
- **结论**：崩溃由包内 so 与 metadata 不配套导致（§4ter 推断成立），非设备、非易盾、非 mod 挂点补丁（崩溃早于任何 `hooked` 日志）。
