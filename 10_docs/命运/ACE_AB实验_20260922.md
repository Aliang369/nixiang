## 2. 方法
- 探针脚本：`04_scripts/命运/ace_ab_probe.sh`
  - `build <variant>` 生成单变量包；`run <variant> [--wipe]` 净装 + 启动 + 观察 75s
  - 判定：`exit-info`（reason/status）+ **主进程**启动次数（`am_proc_start.*,com.bilibili.fatego,` 带尾逗号，排除 `:pushservice`）+ `I Unity` 日志行数（>200 = 真进游戏）+ 75s/81s 双采样 `pidof`
  - ⚠️ 教训：**单次 `pidof` 会骗人**——崩溃循环中恰好采样到活着的进程会误报 ALIVE（AB-3 首轮即踩坑，故改为多重判据）
- zip 重写器：`04_scripts/命运/ab_zipmerge.py`
  - **逐字节搬运** local header + name + extra + 压缩数据，只定点 `--add` / `--replace`，并逐条比对原始压缩流 sha1 → 保证「除目标条目外，官方条目压缩流一字不改」
  - 无 add/replace 时输出与源 `cmp` 字节完全相同（已自校验）
  - 关键坑：中央目录 CDH 打包必须 `<IHHHHHHIIIHHHHHII`（**6 个 H**）；`--replace` 要同步 patch CDH 的 flags/method/time/date/crc/csize/usize
- 每轮 `pm uninstall --user 0` 净装（uid 递增，`exit-info` 按 uid 隔离，互不污染）

### AB-4 为什么无效
ab4 换上了声明 `com.starry.magic.StarryInitProvider` / `MenuService` 的 Manifest，但**没有把 `classes15.dex` 加进去** → 类不存在 → 启动即 `reason=4 (APP CRASH(EXCEPTION))`（OPPO `gaia:crashbox … error_type:java_crash`）。这是 Java 层 ClassNotFound，**不是 ACE 信号杀**，不能用来判定「manifest 改动是否被检测」。重做设计见 §5。

## 4. 结论（最终，已全部跑完）

1. **重签 / zipalign 重排 / 全包重压 都不是触发面。**
   推翻了此前「1839 条条目压缩流被我们重新压缩 → 触发 ACE」的假设（AB-2 全量重压仍 ALIVE）。
   同时证明设备环境（KSU root、`/data/local/tmp` 旧 dump 残留、独立安装的 `com.starry.magic` 包）不构成杀因。
2. **新增任何 dex 条目即杀，与内容无关**：AB-8 只加一个**内容中性的空类** `Lcom/bilibili/fatego/Helper;`（496 B）→ KILLED（6 启 5 杀，SIGBUS）。
3. **新增任何 `lib/arm64-v8a/*.so` 条目即杀，与内容无关**：AB-9 只加**仅 `JNI_OnLoad` 的最小 so**（4912 B、无任何关键词）→ KILLED（SIGBUS）。
4. **改已有官方 dex 的内容也杀**：AB-10 不加任何条目，只把同一个中性空类并进官方 `classes14.dex` 再 `--replace` → KILLED（5 启 4 杀，SIGSEGV+SIGBUS）。
5. **新增 `assets/` 条目不杀**：AB-7 → ALIVE（`I Unity` 11,532 行、活过 81s、SIGNALED=0）。
6. 击杀形态高度一致：`SIGNALED` + SIGBUS(7)/SIGSEGV(11)、~10–20s 延迟、rss≈119–123MB、**无 tombstone、无应用日志、从未进 Unity**。

**判定**：ACE 校验的是 **① 官方 dex 集合的逐字节内容** + **② `lib/` 的官方条目清单**，而**不校验 `assets/`**。
由于中性载荷同样被杀，这**不是内容级扫描** → **字符串清洗/去特征/strip 全部无用**。

⇒ **标准外科路线（新增 dex + 新增 so + 改 Manifest）在 FGO 2.129.0 上被实测彻底否决**；与公主连结/终末地/雷霆（同路线可用）不同，FGO 这一代 ACE 更严。改已有 dex、改已有 so 亦无出口。

## 6.5 决定性突破（2026-09-22 21:00~21:25，AB-38 ~ AB-42）

### 根因：libtprt.so 里明文存着 libtersafe2.so 的期望 MD5
`lib/arm64-v8a/libtprt.so` 内：
- 偏移 `0x16956c` = `7ede1789133339d4f5abde86056165b1` = MD5(`lib/arm64-v8a/libtersafe2.so`)
- 偏移 `0x1694ec` = `98bcf05ccfd698482e96e550252ab77a` = MD5(`lib/armeabi-v7a/libtersafe2.so`)

用 python 遍历官方 APK 全部 3531 条目算 MD5 反查：**只有这两个条目命中**，其余 3529 条 0 命中 ⇒ 这就是 ACE 的
「libtersafe2 完整性期望值」表。**libtprt.so 自己的 MD5 在 libtprt/libtersafe2 里都不存在** ⇒ libtprt 无自校验，
可以改它的字节而不被发现（这是整个直装路线的立足点）。

**替换攻击**：把 libtersafe2.so 换成我们的 so，同时把 libtprt 里那条期望 MD5 改成**载荷的 MD5**（同长度 ASCII 替换，
大小不变）→ 摘要校验通过。工具：`04_scripts/命运/patch_expected_md5.py`（`--also HEX32` 可追加替换目标）。

### 实验链
| 变体 | 载荷 | 结果 |
|---|---|---|
| AB-38 `ab38-probe` | 探针 so（挂钩 open/openat/fopen/dlopen/dlsym） | 自己递归爆栈（`Hook_open` 内 `__android_log_print` 再触发 open）；但**证明真崩溃会产生 tombstone**，与 ACE 击杀（无 tombstone）可区分 |
| AB-39 `ab39-hashpatch` | 纯桩 + hashpatch | pid 17617 存活 **40 s**（同载荷不补哈希只有 6~11 s） |
| AB-40 `ab40-hashprobe` | 探针 + hashpatch | 仍是探针自身递归崩（`reason=5 APP CRASH(NATIVE)`，F DEBUG 全是 `Hook_open+844`）；挂完钩后第一个 open 是 `…/lib/arm64/libtprt.so` |
| **AB-41 `ab41-hashmod`** | **真·菜单载荷**（星光 so + 内嵌 classes15.dex）+ hashpatch + 菜单清单 | **首次跑进 Application 引导与我们的注入路径**（`[fgo] 早期注入完成 ✔`、`菜单 dex 已注入应用 ClassLoader`），但进程 1~2 s 崩、被反复自动重启（风暴） |
| **AB-42 `ab42-hashmod-nosq`** | 同 AB-41，但 **`MYGWZD_NO_SQ=1`（编译掉 SignalQuarantine）** | ✅ **pid 10015 稳定存活 ≥60 s**，Java/网络栈完全起来（pthread: TcmReceiver / OkHttp / Conscrypt / Okio Watchdog / SurfaceSyncGroup…共 24 线程），无新 tombstone |

**AB-41 风暴的凶手是我们自己**：`SignalQuarantine`（全线程屏蔽致命信号 + seccomp 拒绝
tgkill/tkill/kill/rt_sigqueueinfo）与 AB-30「屏蔽反而把寿命从 10.8 s 缩到 3.3 s」完全一致。关掉它之后进程稳定。

### 结论：可用的无 root 直装配方（不新增任何 zip 条目）
1. 载荷 = 星光 mod so（`libs_mygwzd/arm64-v8a/libstarry_magic.so`）+ 内嵌菜单 dex（`EMBED_OFF=0x40000`，
   布局 `STARRYDEX` + u32 len + u32 crc32 + dex），补齐到官方 libtersafe2.so 长度并用 `crc32_keep.py` 配平 CRC32；
2. 用该载荷**替换** `lib/arm64-v8a/libtersafe2.so`；
3. 用 `patch_expected_md5.py` 改写 libtprt 里的期望 MD5 后**替换** `lib/arm64-v8a/libtprt.so`（大小不变）；
4. **替换** `AndroidManifest.xml`（只加 `com.starry.magic.menu.MenuService` + `com.starry.magic.StarryInitProvider`，
   保留官方 `com.bilibili.fatego.App` 与 `androidx.core.app.CoreComponentFactory`）；
5. 重新签名（v1+v2+v3，`01_tools/starry_release.jks`）。
仍不触碰：新增 dex/lib 条目（必死）、修改既有 dex/lib 内容（密码学摘要必死）。
