# 命运（FGO）2.129.0 免改包代码注入通道（Cobbler / bgcplugin）

> 背景：AB 实验矩阵（见 `10_docs/命运/ACE_AB实验_20260922.md`）已实测**否决一切 APK 改包路线**。
> 本文记录在此约束下，**官方包自带的两条「动态加载外部代码」通道**——它们让我们的代码在
> *官方签名、零改包、ACE 认为干净* 的进程内执行，是唯一的免改包出路。
> 全部结论来自官方 dex 静态阅读 + 设备实测观察，未修改官方包一个字节。

## 0. 前置事实（矩阵，已实测）

| 改动 | 结果 |
|---|---|
| 零改动仅重签（AB-1） | ✅ ALIVE |
| 全条目重压（AB-2） | ✅ ALIVE |
| **新增任意 `assets/` 文件（AB-7）** | ✅ ALIVE |
| 新增 `classes15.dex`（内容中性的空类，AB-8） | ❌ SIGBUS 杀 |
| 新增 `lib/arm64-v8a/*.so`（仅 `JNI_OnLoad` 的最小 so，AB-9） | ❌ SIGBUS 杀 |
| 改**已有** `classes14.dex` 内容（并入同一个中性空类，AB-10） | ❌ SIGSEGV+SIGBUS 杀 |
| 官方原包（未重签、零改动，AB-0） | ✅ ALIVE（实机复核：Unity 起、pid 稳定） |

⇒ ACE 校验 **官方 dex 集合的逐字节内容** + **`lib/` 官方条目清单**，且**不校验 `assets/`**；
由于中性载荷同样被杀，**不是内容关键词扫描** → 字符串清洗/去特征无用。

## 1. 通道 A：腾讯 Cobbler 热补丁（`com.gsc.cobbler`，位于 `classes8.dex`）

### 1.1 事实链

| 项 | 位置 | 值 |
|---|---|---|
| 策略接口 | `com/gsc/pub/deploy/CobblerConfig.smali:92` | `http://static.biligame.net/gamesdk/cobbler/config`（**明文 HTTP**；实测该 URL 返回 `301 → https://...`，即客户端**先发 HTTP**） |
| 初始化 | `com/gsc/pub/GSCPub.smali:7562`、`com/gsc/pub/task/a.smali:101` | `Cobbler.getInstance().init(ConfigProvider)` |
| 触发 | `com/gsc/cobbler/Cobbler.smali:93` | `init()` 内调 `patchConfig()` |
| 取配置 | `com/gsc/cobbler/api/DefaultPatchApiImp.smali:140` `getPatchConfig(sdkVer, gameId, appVer)` | 先 `requestConfig()`（网络）；响应非空 → `putCache` + `parseConfig` + **返回 List\<Patch\>**；为空/IO 异常 → `getConfigError()` 只 `parseConfig(getCache())` 并**丢弃返回值**（缓存路径实际无效 → **必须伪造网络响应**） |
| 请求 | 同文件 `:474` | `Cobbler.configUrl()` + `getPatchConfigParams()`（`gameId`/`appVer`/`sdkVer`）→ `com/http/lib/HttpClientUtils.doRequest` |
| 下载+应用 | `com/gsc/cobbler/patch/PatchManager.smali:210`(download) / `:402`(patch) | `new DexClassLoader(patchPath, optimizedDir, null, context.getClassLoader())` → `loadClass(patch.getPatchesInfoImplClassFullName())` → 转 `PatchesInfo` → `getPatchedClassesInfo()` → 反射把 `ChangeQuickRedirect` 回灌官方类 |
| 缓存目录 | `Cobbler.smali:163` `getDefaultCacheFile()` | `context.getCacheDir()/cobbler` |
| 常量 | `com/gsc/cobbler/constant/Constant` | `PATCH_DOWNLOAD_NAME="patch.jar"`、`PATCH_CACHE_DIR="cobbler_cache"`、`CONFIG_KEY="cobblerConfigKey"`、`TAG="Cobbler"` |
| prefs | `com/gsc/cobbler/data/ConfigCache` → `SharedPreferencesProvider` | 文件 `cobblerPreference`（key `cobblerConfigKey`） |
| 内置默认 patch | `Cobbler.smali:121` `defaultPatch(downloadUrl, patchSign)` | `setPatchesInfoImplClassFullName("com.base.cobbler.patch.PatchesInfoImpl")` ← **我们的 patch.jar 必须提供的类名** |

### 1.2 伪造策略 JSON（结构已从 `parseConfig` + `Strategy.parse` + `Patch.parse` 反推）

```json
{
  "cobblerSwitch": true,
  "<sdkVer>": {                        // optJSONObject(sdkVer)，sdkVer = 客户端传入
    "strategy": [
      { "patchId": "P1",               // getString，必填
        "gameIdList": ["..."], "appVerList": ["..."],
        "modelList": ["..."], "brandList": ["..."],
        "osStrategy": { } }
    ],
    "patches": [
      { "patchId": "P1",
        "patchName": "x", "patchSign": "<md5>", "downloadUrl": "http://<我们的服务器>/patch.jar",
        "patchesInfoImplClassFullName": "com.base.cobbler.patch.PatchesInfoImpl",
        "appSign": "...", "highPriority": false, "isSuccessPatch": false, "localDir": "..." }
    ]
  }
}
```
匹配逻辑：`Strategy.matchPatchIds(gameId, appVer, SDK_INT, BRAND, MODEL)` → 命中集合；
`patches[]` 中 `patchId ∈ 命中集合` 的项被下载并应用。

### 1.3 为什么这条路能成

`PatchManager` 用的是**官方自己的 `DexClassLoader` + 官方自己的 `ChangeQuickRedirect` 回灌机制**，
APK 一个字节都没改 → ACE 的第 0 层（包体/dex/lib）校验完全看不到我们。
已被 Cobbler 插桩（即**可被我们 patch**）的类包括：
`com/gsc/pub/deploy/PluginConfig`（proxy index `0x439f`）、`com/base/bgcplugin/BgcPluginManager`、
`com/biligamesdk/cloudgame/message/handler/*`、`classes.dex/2/3/4/5/7/9` 中的多个类。

## 2. 通道 B：B站 bgcplugin 插件框架（`com.base.bgcplugin`，位于 `classes2.dex`）

### 2.1 事实链

| 项 | 位置 | 值 |
|---|---|---|
| 初始化 | `com/gsc/pub/GSCPubCommon.smali:730`、`com/gsc/pub/deploy/a.smali:343` | `BgcPluginManager.init(Application, ConfigProvider)` |
| ConfigProvider 实现 | `com/gsc/pub/deploy/PluginConfig` | 构造里 `new File(getCacheDir(), "plugins")` → **debugDir = `cacheDir/plugins`**（并 `mkdirs`） |
| 总开关 | `PluginConfig.enable()`（`:618`） | `FeatureFlagWrapper.getBoolean("bgc_plugin_enable", false)` ← **可被本地特性开关翻转**（设备上存在 `files/featureFlagConfig.0`） |
| 调试通道 | `PluginConfig.debugEnable()`（`:602`） | **硬编码 `return false`** → 官方包内此门关闭（除非先 patch 它：该方法是 Cobbler 插桩点，含 `changeQuickRedirect`） |
| 调试插件扫描 | `PluginFramework.resolveDebugPlugins(File)` | `dir.isDirectory()` → `listFiles()` → **任何以 `.apk` 结尾的文件** → `new DebugPlugin(...)`（**无签名/无网络校验**） |
| 正常通道 | `PluginConfig.requestConfig()`（`:743`） | `HttpClientUtils.doGet(Lcom/gsc/pub/deploy/b;->a)` → 基址 **`https://api.biligame.net`**（`b.smali`：`.field public static a:Ljava/lang/String; = "https://api.biligame.net"`）+ path `/sdk-hot-deploy/pluginPackage/client/config`，UA `Mozilla/5.0 BSGameSDK`，请求带 `pluginsInfo` 参数 |
| 响应字段 | 同文件 `:847-883` | `pluginUrl` / `pluginCode` / `pluginVersion` / `pluginMd5` / `pluginType` |
| 内置插件目录 | `PluginConfig.pluginBuiltInDir()`（`:682`） | `"gsc_plugins"` |

### 2.2 两条子路

- **B1 调试通道**：`debugEnable()` 硬编码 false → 需先经通道 A patch 该方法返回 true，再把我们的 `xxx.apk`
  放进 `/data/data/com.bilibili.fatego/cache/plugins/` → 框架直接加载它。**组合拳**。
- **B2 正常通道**：伪造 `https://api.biligame.net/sdk-hot-deploy/pluginPackage/client/config` 的响应，
  给出 `pluginUrl`（我们的插件包）+ `pluginMd5` → 框架下载并安装插件。**需 HTTPS MITM**（该基址是 https）。

## 3. 设备实测（2026-09-22 17:31–17:34，官方原包 uid=10830）

- 官方原包 **ALIVE**：pid 15994 在 t=30s/t=90s 均存活，`am_proc_start` 3 次，exit-info 无任何 SIGNALED。
- 应用流程真的走到了 SDK 层：`AgreementWebActivity`（隐私协议）→ `UnityPlayerNativeActivity`（Unity 起）→ **`I GSCPubCommon: login`** + `com.gsc.phone_login.PhoneLoginActivity`（17:33:36）。
  ⇒ **`com.gsc.pub`（GSCPub/GSCPubCommon）在本机确实初始化** → 通道 A 的 `Cobbler.init` 与通道 B 的 `BgcPluginManager.init` 的调用点都被执行到。
- 旁证：`shared_prefs/bgc_plugin.xml` 被创建（bgcplugin 框架确实跑过）；`files/featureFlagConfig.0`(371 B)、`files/config_s.0`、`files/data/`、`files/shell_cache/`、`files/ace_shell_di.dat` 存在。
- 但**尚未看到 Cobbler 落地痕迹**：无 `shared_prefs/cobblerPreference.xml`、无 `cache/cobbler/`、无 `Cobbler` tag 日志。
  两种可能：① `patchConfig()` 的请求失败/响应为空（`putCache` 未执行）→ 与「必须伪造网络响应」一致；② init 尚未走到。
  **下一步就是用拦截服务器来区分**（若我们的伪响应被 `putCache` 写进 `cobblerPreference.xml`，即证明通道活着且可伪造）。

## 4. 落地方案（分阶段，可验证）

**阶段 1 — 通道活性证明（低风险，不改任何游戏逻辑）**
1. root 侧把 `static.biligame.net` 指向我们的 HTTP 服务器（hosts 覆盖或 `iptables -t nat` DNAT 到本机 80 端口）。
2. 服务器对 `GET /gamesdk/cobbler/config` 返回 `200` + 合法 JSON（`cobblerSwitch:true`，`patches:[]`）。
3. 启动游戏；判定：`/data/data/com.bilibili.fatego/shared_prefs/cobblerPreference.xml` 是否出现并含我们的 JSON。
   - 出现 ⇒ 伪造成功、通道可用，进入阶段 2。
   - 不出现 ⇒ Cobbler 未 init 或 HTTP 层被拦；转通道 B1/B2 或 Zygisk 路线。

**阶段 2 — 代码执行（PoC）**
4. 造 `patch.jar`：内含 `com.base.cobbler.patch.PatchesInfoImpl implements PatchesInfo` 返回
   `PatchedClassInfo` 列表（目标类选一个**启动早期必被执行**且已被 Cobbler 插桩的类，如 `com/gsc/pub/deploy/PluginConfig`），
   其 `ChangeQuickRedirect` 实现里做一件可观测的事（写文件 + 打日志）。
5. `downloadUrl` 指向我们的服务器；`patchSign` 用我们自算的 md5（`PatchManager` 的校验规则需按实现给对）。
6. 判定：目标方法被调用时出现我们的日志/文件 ⇒ **官方进程内任意 Java 代码执行成立**。

**阶段 3 — 接回星光菜单**
7. 在第 2 阶段的 Java 代码里 `System.load("/data/data/com.bilibili.fatego/files/libstarry_magic.so")`
   （so 由 root 预先放入；**不要放 `lib/`，避免 maps 里出现 apk-lib 路径**）。
8. 现有 `MygwzdMod.cpp` 的 il2cpp 按名解析 + 懒装 hook 逻辑**完全复用**，功能无需改动。

## 5. 风险与待验证

| 风险 | 说明 | 缓解 |
|---|---|---|
| ACE 监控 Cobbler/bgcplugin | 这两条是腾讯/本家机制，通常在白名单内，但未证实 | 阶段 1 只做无副作用空 patch；观察是否被 SIGBUS |
| HTTPS 通道（`api.biligame.net`） | 需系统级 CA（root 装入 `/system/etc/security/cacerts`）+ MITM | 优先走通道 A（`static.biligame.net` 是 HTTP，**无需 TLS**） |
| `patchSign` 校验规则 | `PatchManager` 的 md5/签名校验细节未读完 | 读 `PatchManager.smali:210-402` 补全 |
| `ChangeQuickRedirect` 回灌要求 | 目标类需已被插桩、方法签名一致 | 先选 `PluginConfig.debugEnable()`（无参、返回 boolean）做最小 PoC |
| so 映射可被 ACE 发现 | 雷霆案例：非 apk lib 路径映射 = 杀因 | 加载后立即 `unlink`/用 memfd、改中性文件名、必要时内存态 |
| 设备/账号风控 | 反复崩溃循环可能触发服务端处置 | 每轮实验后 `am force-stop`，不连续刷 |
