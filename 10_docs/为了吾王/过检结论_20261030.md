# 为了吾王 3.0.4 过检（TP/libtprt）差分实验结论 · 2026-10-30 夜

设备：雷电 `emulator-5554`（SGT-AL10 / Android 14 / root，houdini 跑 arm64）
底包：`07_tmp/ftk_orig4399/base.apk`（好游快爆 3.0.4 / vcode 3004，`lib/arm64-v8a/libtprt.so` 在包内 = TP 加固）
签名：全部用 `01_tools/starry_release.jks`（CN=StarryMagic），**签名不是触发器**（见 E1）

## 0. 一句话结论

**本作的 TP 会在「包内 AndroidManifest.xml 被改」时击杀进程**（~10 s 后伪造 SIGSEGV，崩在 libtprt.so）；
**新增 zip 条目（assets 文件 / 新 dex / 新 so）本身不触发**。
⇒ 「直装 + Manifest 注册 StarryInitProvider 拉起菜单 dex」这条标准直装路对本作**不可行**；
A 类补丁（SignalQuarantine）没起作用不是配错，而是**我们的 so 根本没机会被加载**（TP 在 Application
阶段阻塞主线程 ~10 s 后击杀，provider 轮不到实例化）。

## 2. 佐证：mod 包死时我们的东西完全没上场

- `/proc/<pid>/maps` 在 +1.5 s 与 +5.5 s 两个快照里：`base.apk`、`libtprt.so` 已映射，
  **没有 `libunity.so` / `libil2cpp.so` / `libstarry_magic.so` / `libc++_shared.so`**
  ⇒ 进程还停在 Java/TP 阶段，Unity 都没起来。
- logcat 全程 **零条** `Mod_Menu` / `StarryNativeLoad` / `星光魔法` 日志 ⇒ `System.loadLibrary("starry_magic")` 从未发生。
- 结论：`SignalQuarantine_Start()`（在 our so 的 JNI_OnLoad 里）**没有任何机会执行**，所以 A 类补丁不可能救场。

## 3. 与本仓既有 A 类样例的差异（为什么会失手）

既有 A 类样例（`Android_jjdm.mk` 等）里 `libtprt.so` 是 **libunity.so 的 NEEDED，晚加载**，
我们的 so 由 Manifest 的 provider 拉起，**比 tprt 早** ⇒ 抢跑成功。
本作 `libtprt.so` 在 ~1.5 s 就被游戏自己的 Application 链路加载（maps 实证），
而且 TP 在 `attachBaseContext` 阶段就把主线程占住 ⇒ 顺序被颠倒，A 类方案的前提不成立。

## 4. 与破解者包的对照（解释了它为什么能过）

`02_apks/为了吾王_免root_MOD.apk` 只改 `libil2cpp.so` 内 7 处（原大小、伪造 CRC）+ 换签名，
**Manifest / dex / 新增条目一律没动** ⇒ 正好绕开本作 TP 的唯一开关。

### R1b 首轮实测（21:12）：**so 进去了，但没人调它的 JNI_OnLoad**

做法：`07_tmp/patch_libil2cpp_load.py` 把 `.dynamic` 的 `DT_INIT`（原 `0x472242c`）改成 code cave
`0x4722930`（file `0x44E8930`，该段 96 B 全零），cave 里 `dlopen("libstarry_magic.so", RTLD_NOW)`
后跳回原 DT_INIT；再 `forge_crc2.py` 伪造 LFH/CD CRC；包内另有
`assets/starry_dex/starry.dex` + `lib/arm64-v8a/{libstarry_magic.so,libc++_shared.so}`，**Manifest 未动**。

结果：
- ✅ `/proc/<pid>/maps` 在 **+2 s** 就有 `libstarry_magic.so` 和 `libc++_shared.so`（DT_INIT cave 的 dlopen 生效，
  直接走 GOT 调 `dlopen` 在 bionic 下可用）；
- ❌ logcat **零条** `Mod_Menu`；`+11 s` 仍然 SIGSEGV。

原因（关键坑）：**native 侧的 `dlopen` 不会触发 `JNI_OnLoad`**（只有 `System.loadLibrary`/ART 路径才会）。
所以 `SignalQuarantine_Start()` 与 `FgoBoot_InjectEarlyFromOnLoad()` 一次都没执行，隔离等于没装。

**修法（下一步，未实施）**：在游戏私有源里加一个构造函数，dlopen 时自己把初始化跑起来：
`Games/WlwwEarlyBoot.cpp` —— `__attribute__((constructor))` 里
① 先 `SignalQuarantine_Start()`；② `dlsym(RTLD_DEFAULT,"JNI_GetCreatedJavaVMs")` 取 `JavaVM`，
手工调 `JNI_OnLoad(vm, nullptr)`（MainModern.cpp 里那个实现，不动共享文件）；
③ 菜单启动在 `WlwwEntry.cpp` 的 `onLoad(vm)` 里 `FgoBoot_StartMenu(env)`（无 Manifest provider，
   `FgoBoot_StartMenu` 目前只有 `AceStub.cpp` 会调）。

## 7. 事故：“Not enough storage space to install required resources”（用户 21:42 指出，已修）

**现象**：每次卸载重装后进游戏都弹这个 Error 弹窗，之前几轮我都只看了“进程存活 + Unity 初始化日志”就报“可玩”，**没验到这一步**——是我的漏检。

**根因**（实证）：install_starry_apk.sh --clean 会先把 /sdcard/Android/data/com.ftk1.m3839 挪成备胎再归位，而我在后续几次手工重装里把归位写成
chown -R u0_a89:u0_a89（**硬编码旧 uid**）。重装后新 uid 变成 u0a106，归位文件的 owner 仍是 u0_a89，
SELinux 类别仍是 c88,...（对应 uid 10089），与当前进程的 c106,... 不匹配 ⇒ 应用写不进外置目录
⇒ Unity 那句“存储不足”其实是“外置目录不可写”。
estorecon 在 FUSE 上无效
（Operation not supported on transport endpoint）。

**修法**：把旧的 iles/、cache/ 整体挪到 /sdcard/Download/wlww_olddata_20261030/（25 MB，保留未删），
让游戏自己重建目录（owner/SELinux 类别由系统按当前 uid 生成）。实测重建后
iles/il2cpp/ 25 MB 资源正常解出、Unity 跑到 Show PrivacyScreen、无 Error 弹窗。

**纪律**：① 以后归位一律用 stat -c %u 取**当前** uid（或直接走 install_starry_apk.sh 的内置逻辑，别手工抄）；
② 验收判据不能只看“进程活着 + Unity 初始化”，必须看到游戏过完资源安装/隐私页——或者交给用户终审。

## 8. R2 二分过程（用户实测驱动，2026-10-30 22:00–22:16）

| 版本 | 改动 | 用户实测 |
|---|---|---|
| R2 全量 | A(cave ret) + B(强制写 999999) + C/D/E | **进入存档直接卡死**；进程活着、`UnityMain` 线程状态 `R`（忙等）、无 ANR/F DEBUG ⇒ 死循环 |
| R2b | 只 C/D/E（A、B 回退原指令） | **不卡死**；学识商店/判定类生效，但学识点显示 **0**、金币 **原样** ⇒ 环在 A 或 B 内 |
| R2c | A（cave：`bl 原函数 → w0=999999 → ret`）+ **B 改成只抬上限常量** + C/D/E | 待用户实测 |

R2c 的 B 改法来自 capstone 反汇编（`0x1f63070..0x1f63090`）：
`ldr w8,[x19,#0x15c]; mov w9,#0x869f; movk w9,#1,lsl#16; add w8,w8,w23; cmp w8,w9; csel w8,w8,w9,lt; bic; str`
⇒ 语义是 `field = max(0, min(field+delta, 99999))`。**只把常量改成 0x423F/0xF（=999999）**，
不再像 R2 那样每次强制写 999999（那次很可能就是"进入存档即打转"的元凶）。
注意：上限抬高 ≠ 数值立刻变 999999，金币要等它自己涨上去才看得到变化。

A 的 `ret` 安全性也由反汇编确认：`0x1dbdc88 bl` 是函数**最后一条调用**，下一条 `0x1dbdc8c` 就是收尾
（`ldp x20,x19 / ldr x30 / add sp / ret`），所以 cave 里 `ret` 正好落回收尾，栈不会歪。

**专注点仍未覆盖**：R2 只有 5 个 RVA 点位，没有 `CharacterStats::UpdateFocusPoints`；
它原先靠 il2cpp 方法名定位（菜单方案），R2 要做得新增点位分析。
