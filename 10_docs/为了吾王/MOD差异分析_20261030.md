# 为了吾王（For The King）免root MOD 差异分析 · 2026-10-30

## 0. 结论一句话

`02_apks/为了吾王_免root_MOD.apk` = **好游快爆官方 3.0.4 原包（`com.ftk1.m3839`，vcode 3004）
原样重打包**：2253 个 zip 条目里**只有 `lib/arm64-v8a/libil2cpp.so` 被改了 7 处、共 67 字节**，
其余全部字节一致（含全部 dex、AndroidManifest.xml、resources.arsc、libunity.so、全部 Unity 资源、
global-metadata.dat）；对外只有 `META-INF/FTK.RSA`、`FTK.SF` 换成破解者自签证书。
改完还把 **zip 中央目录里的 CRC32 伪造成了原值**（未压缩大小、CRC 都与原包相同），
所以任何"对比 CRC/大小"的工具都会误报"没改过"。

## 3. libil2cpp.so 实际改动（arm64，7 处 / 67 字节）

`lib/armeabi-v7a/libil2cpp.so` **0 处改动** ⇒ 只影响 64 位设备（雷电/主流手机都是 arm64）。

文件偏移 → 语义（vaddr = 文件偏移 + 0x1000，该段；代码洞段 delta = 0x2DA000）：

| # | 文件偏移 | 原始指令 | 改成 | 效果（推断） |
|---|---|---|---|---|
| 1 | `0x1DBCC88` | `bl 0x2491180` | `bl 0x4720000`（进代码洞 stub1） | 某取值函数 → **直接返回 999999** |
| 2 | `0x1DBD5B4` | `cset w0, gt`（判断 `f()>0`） | `mov w0, #1` | 某 bool 判定 **恒真** |
| 3 | `0x1F62088` | `csel w8, w8, w9, lt`（把值夹到 ≤0x1869F=99999） | `b 0x4720020`（进代码洞 stub2） | 上限 99999 → **改成 999999** |
| 4 | `0x1F6903C` | `cset w0, ge`（`this.0x15C >= arg`） | `mov w0, #1` | 某"够不够"判定 **恒真** |
| 5 | `0x2059C14` | `cset w0, ls`（`fcmp s9,s8` 浮点比较） | `mov w0, #1` | 某浮点条件判定 **恒真** |
| 6 | `0x44E5610` | `00000000` | `51219C6A` | 填充区 4 字节，**CRC32 伪造修正用**，无功能 |
| 7 | `0x44E6000` | 全 0（可执行填充段） | 见下 2 个 stub | 代码洞 |

### 代码洞 stub1（vaddr 0x4720000，被 #1 调用）

```
stp x29, x30, [sp, #-0x10]!
bl  0x2528180            ; 调另一个函数（原调用目标是 0x2491180，已换）
ldp x29, x30, [sp], #0x10
mov w0, #0x423F
movk w0, #0xF, lsl #16   ; w0 = 0xF423F = 999999
ret
```

### 代码洞 stub2（vaddr 0x4720020，被 #3 跳入）

```
mov w8, #0x423F
movk w8, #0xF, lsl #16   ; w8 = 999999
b  0x200308C             ; 带着 w8=999999 继续执行
```

### 补丁性质

- 4 处是 `cset`（条件置 1）→ `mov w0,#1`：把"是否满足条件"的判断点成恒真，典型用于
  **已购买/DLC 已拥有/等级或资源达标/冷却完成** 这类布尔闸门。
- 1 处是"数值夹取上限"从 **99999 抬到 999999**，同时另一处 getter 直接返回 **999999**。
  两处都引用同一实例字段 `+0x15C`（int），指向同一个被加成/夹取的数值（货币或资源计数）。
- 注入方式 = 在 .so 尾部空白可执行段写 stub + 改 1 条指令跳过去，**没有新增 so、没有 dex 注入、
  没有悬浮窗权限、没有去壳/加壳**。manifest 权限反而比原包少（缺 REORDER_TASKS、READ_PRIVILEGED_PHONE_STATE）。

## 4. 未解决 / 待验证

- **具体方法名未知**：`global-metadata.dat`（25,330,628 B，与原包逐字节一致）头部被保护过
  （magic 不是 `AF1BB1FA`，前 0x120 字节不是合法 (offset,size) 表；但文件里 `get_`×8877、
  `UnityEngine`×4196 等名字仍可读 ⇒ 只有部分区域被加密，属 TP（libtprt.so）按包抽 1/4 加密）。
  要把 4 个补丁点对上 C# 方法名，需要 **运行时解密后的 metadata 内存 dump**，再跑
  `01_tools/il2cppdumper/Il2CppDumper.exe`。
- 反向验证：TapTap 包与好游快爆包的 `libil2cpp.so` 在 `.rodata/.text/il2cpp` 各有约 **25%~26%** 字节不同，
  而 `.dynsym`/`.rela.dyn`(14 MB)/`.data.rel.ro` **完全一致** ⇒ 两包是**同一份二进制被各自按包加固**
  （TP 加密函数子集），不是两次不同编译。所以**静态跨渠道比 .so 永远看不出改动**，必须先对齐渠道。

## 4.1 运行时取证记录（2026-10-30，A 路线）

设备：雷电 9（`emulator-5554`，root 可用：`su -c id` = uid=0）。

| 事实 | 证据 |
|---|---|
| 设备是 **x86_64 宿主 + houdini 转译**，游戏以 arm64 跑 | `getprop ro.product.cpu.abi` = x86_64，abilist 含 arm64-v8a；maps 里 `/lib/arm64/libil2cpp.so` |
| phantom-frida 17.16.4（arm64）能起但**挂不上该进程** | `ps -A` 看不到 fs-arm64；`enumerate_processes()` 105 条里没有 com.ftk1.m3839；`attach(7364)` → `ServerNotRunningError: closed` |
| 游戏把 metadata 落到外部存储 | `/storage/emulated/0/Android/data/com.ftk1.m3839/files/il2cpp/Metadata/global-metadata.dat`（25,330,628 B，md5 `95bf7acc55afe96865e140f657f3794e`） |
| 落盘副本 = APK 内 asset **逐字节相同**（仍是混淆版） | sha256 比对一致 |
| **运行时内存里也没有标准魔数 `0xFAB11BAF`** | root 直读 `/proc/7364/mem` 全量扫描：匿名段 276 个共 10,971 MB（不限权限）+ rw 段 195 个共 2,095 MB + 小堆 347 段，全部无命中 |
| libil2cpp 代码段是 **r--p 按需解密**（TP 懒解密），不是 r-xp | `maps`：`400023000000-40002498e000 r--p 00000000 .../libil2cpp.so` |
| metadata 加载锚点 | `.so` 内字符串 `global-metadata.dat` @ 文件偏移 `0xF01913`（.rodata） |

结论：**Il2CppDumper 路线对本作不可行**（它入口就要 `magic 0xFAB11BAF` + version + (offset,size) 表，
本作 metadata 是被整体改过的自定义/混淆格式，磁盘和内存里都没有标准魔数）。
要继续拿方法名，只剩两条：
① **静态反混淆**：从 `0xF01913` 反查 xref 找到 metadata 解析入口，看它如何解释被改的 header
（可能还原成标准 metadata 再喂 Il2CppDumper，也可能只能拿到方法表位置做自建 RVA→名字映射）；
② 换 **arm64 原生真机**（如 `96f0d883`）跑 frida —— 但这只解决"挂不上"，不解决"内存里没有标准 metadata"，
所以①是主线，②只在需要内存态 hook 时才用。

## 4.2 A2 静态反混淆结果（2026-10-30）

加载链已完全打通（全部在 `.rodata`/代码段可读区，TP 没加密这几页）：

| 环节 | 地址（arm64 vaddr） | 内容 |
|---|---|---|
| metadata 字符串 | `0xF01913` | `.rodata` 里唯一一处 `"global-metadata.dat"`；三个包（TapTap/好游快爆/MOD）xref 完全相同 |
| 引用点 | `0x1B85540` | `adrp x0,#0xF01000; add x0,x0,#0x913` |
| `MetadataCache::Initialize` | `0x1B85530` | 读完 header 后按**标准 il2cpp 布局**取字段并除结构体大小：`+0xAC /24`、`+0xB4 >>6`、`+0xA4`、`+0x30/+0x34/+0x40 /8` → 说明运行时 header 布局是标准的 |
| `MetadataLoader::LoadMetadataFile` | `0x1B468FC` | **第一条指令就是 `b 0x4722A8C`**（被重定向） |
| 重定向目标 | `0x4722A8C` | `ldr x8,[0x4725E0]; ldr x1,[0x4725C8]; ldr x2,[x8,#0x138]; br x2` = 运行时 vtable 分发（`0x4720000` 起的 R+X 附加段，正是 MOD 作者也用过的代码洞区）|

结论：**真正的 metadata 解包/解密代码不在 `libil2cpp.so` 里**，而是加载时由 `libtprt.so`（TP 运行时）填进那张 vtable 的 ——
所以静态逆 `libil2cpp.so` 拿不到解混淆算法。

内存侧证据（`/proc/7364/mem`，root 直读）：

- `PlayerInventory`、`CharacterStats` 等 metadata 字符串**确实在内存里**（命中 4 个段），说明 metadata 已加载；
- 但内存里 **既没有 `0xFAB11BAF`**（扫描 11 GB 匿名段 + 2 GB rw 段 + 347 个小堆段 + 全部权限），
  **也没有文件里任何 96~128 字节原文片段**；
- 内存中的字符串是**重新排布过的**：每个名字前带有 `01 00 00 00 <hash> 00 00 00` + 8 字节对齐填充
  （文件里只是 `\0` 分隔）⇒ 运行时用的是 TP **重新序列化**过的 metadata 格式；
- 因此"从内存 dump 出 24.2 MB 连续 buffer"也不成立（按文件内 `PlayerInventory` 的偏移反推的基址 `~0x7B859FC75634` 根本没被映射）。

**最终判定：Il2CppDumper（含"dump 内存再喂"变体）对本作不可行。**
要拿到方法名只剩"逆 `libtprt` 的 metadata 重序列化格式"，属独立大工程，投入产出比不成立。

## 4.3 metadata 明文获取（2026-10-30 突破 + 卡点）

**拿到了**：`libil2cpp.so` 里 `MetadataCache::Initialize` 的全局 `[base+0x4507068]` 就是 metadata 指针，
运行时读出 = `0x7b85c58ee000`（就是 maps 里那个 24.2 MB 的 `/dev/zero (deleted)`）。
dump 下来后确认它是**明文 metadata**：`+0x18 (string 表)` 处直接是
`Assembly-CSharp\0Assembly-CSharp.dll\0<Module>\0<>f__AnonymousType0\`2\0get_assembly\0...`，
按 header 解出 `Assembly-CSharp.dll` 有 6394 个类型、`<Module>` 等，全部可读。
全部方法名/类型名字符串都在明文里可读。

**卡点**：这份 metadata 被**针对性改过**（防 dumper），共 4 处：
1. `+0x00 sanity` 被清零（不是 `0xFAB11BAF`）→ 所有工具第一步就退出；
2. `+0x04 version` 被写成 **24**，实际结构体尺寸是 **v27.2**（methodDef 40 B、typeDef 88 B、assembly 64 B）；
3. header 里**整对被抽掉了 `properties`**（offset/count 各少 8 字节），后面所有 (offset,count) 顺序整体前移一对；
4. `stringLiteral` 表与其数据段两段**单独加密**（熵 8.00，其余段 2.0–6.0 全是明文）。

补齐 1–3（重建 header 到 0x118、偏移整体 +0x18、两段 usage 置空）后，Il2CppDumper 能读进 metadata，
但在建字典时撞上被加密的 stringLiteral 段（`duplicate key 134217728`）而失败；
自写解析器已能正确读出 image/type/method 名字（`Assembly-CSharp.dll`、`<Module>`、`assembly`、`Instance`…），
但 **RVA↔方法索引** 的映射（Il2CppCodeRegistration → CodeGenModule.methodPointers）与 typeDef 字段布局尚未对齐，
本轮未推进到"把 5 个补丁点对上方法名"。

**结论：功能名（C# 方法名）静态不可得**；要坐实"游戏内名字"，成本最低的是
装 MOD 后在游戏里看一眼那个变成 999999 的数值（1 次用户操作），或逆 `libtprt`（大工程）。

## 5. 可照搬的部分

1. **补丁配方本身**（7 处偏移+字节）可原样套到任何官方 3.0.4 的 arm64 `libil2cpp.so` 上，
   但套之前必须逐处核对原字节一致（TP 加密区域随机，跨包可能对不上）。
2. **代码洞位置**：`0x44E6000` 起那段在 R+X 段里、原本全 0，可安全写入 stub。
3. **CRC32 伪造技巧**（改完把 zip 中央目录 CRC 改回原值 + 在填充区补 4 字节）——反检测手段，可选用。
4. 功能层面（4 个闸门 + 数值上限）是我们自己出包时要 hook 的点位候选；
   在 `路线锁定.md` 里可按 RVA 记录，等拿到方法名再替换成符号级挂点。
