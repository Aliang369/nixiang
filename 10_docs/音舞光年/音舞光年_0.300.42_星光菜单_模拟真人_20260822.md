## 5. 版本更新：为什么旧 invoke 失效 & 怎么重定位（方法论）

> **原则：锚定「语义 + 运行时证据」，不锚定「上一版的 file_off」。**  
> 本节是维护手册，不要求改 mod 做自动扫描；下次小版本失效时按此流程人工/脚本定位即可。

### 5.1 0.300.42 到底发生了什么（不是「找不到」，是「搬走了」）

| 地址 | 0.300.41 | 0.300.42 磁盘 | 含义 |
|------|----------|---------------|------|
| file `0x2660BDC` | 116B HybridCLR **invoke 桩**（prologue `fe0f1df8…`） | **首条指令 = RET** | 旧槽位已废弃，不是入口 |
| file `0x2660BE0` | 桩内 +4 处仍在同一函数里 | **另一段无关代码** | 误把「+4」当新入口 → 钩错 / `hits=0` |
| file `0x2BAC188` | 不存在 | **与 41 桩 97% 字节相同** 的 116B 函数 | **真正的新 invoke 桩** |

根因：**Unity/HybridCLR 重编 libil2cpp.so 时，内部解释器 helper 会整体搬迁**；斌哥壳当年钉在 `0x2660BDC` 的 trampoline 也跟着失效。  
Il2CppDumper **看不到** `SendScore` / `BubbleConfig`（玩法在热更 DLL），所以**不能**指望 dump.cs 给出新 RVA。

### 5.2 历次误判（下次更新禁止重复）

| 误判 | 为何错 |
|------|--------|
| 沿用 `0x2664BDC` / `0x2660BE0` | 42 对局 Trace **`invoke=0`**；BE0 不是 BDC+4 新入口 |
| `il2cpp_runtime_invoke` 过滤 SendScore | HybridCLR 热更方法 **`score=0`**，不走导出 |
| types 表 **MethodPointer** 白名单 | 对局 **`patch=0`**；且 MP 常为 invoke 4-arg，native 三参钩 → SIGSEGV |
| API 解析的 `MethodInfo*` 匹配 | 运行时 invoke 里 **MI 指针 ≠ API 解析结果** |
| Dobby 钩 `il2cpp_method_get_name` 导出 | **SIGILL**；只能在 invoke 桩**内部**直调 get_name |
| 无过滤钩全局 invoke | 每秒数千次 → 必须 **a1=MethodInfo + 方法名过滤**，且 **SafePtr 后再改参** |

### 5.3 需要理解的「逻辑链」（比记一个 offset 重要）

```
菜单 ON → libil2cpp 内 HybridCLR invoke 桩（4 参）
         → a1 = MethodInfo*，桩内/钩内 il2cpp_method_get_name
         → 命中 SendScore / CalcNoteScore 等 + class *KeyJudgment* / BubbleNodeController
         → a2 参数块 +0x8（或 valuetype params[0]）= ScoreType
         → 原函数继续执行 → 自动跳舞 + 出分
```

维护时只要这条链还在，**换的是桩的 file_off，不是换 hook 思路**。  
自动跳舞能成，说明 **SendScore 过滤 + 改分** 仍有效；不必再绕 `isAutoPlay` 写字段（历次 log 有、局内无感）。

### 5.4 下次小版本失效时的标准流程（推荐顺序）

**阶段 A — 确认是「挂点搬迁」还是「路径变了」**

1. 进关开功能，抓 `adb logcat | grep Ywgn`  
   - `hooked invoke @ …` 有、`hits=0` → **高概率仅 offset 搬迁**（本次即此）  
   - 连 `hooked` 都没有 → maps 解析 / so 未加载 / 功能未开  
   - `hits>0` 但局内 MISS → 参数布局变（查 `+0x8` / `params[0]`），不是桩地址

2. 可选：`STARRY_TRACE=1` 编译，对局 30s，看 SendScore 是否仍经 invoke 4-arg（比盲猜 MP 快）

**阶段 B — 静态 diff 找新 file_off（首选，不必进游戏）**

1. 取 **上一有效版** 与 **新版** 的 `lib/arm64-v8a/libil2cpp.so`  
2. 从旧版已知桩（如 41 的 `0x2660BDC`）截取 **116 字节** 函数体  
3. 在新 so 中做 **子串 / 模糊匹配**（本次 41@BDC vs 42@2BAC188 = **113/116 字节一致**）  
4. 校验候选（避免误匹配）：
   - prologue `fe0f1df8…`  
   - 116B 内 **恰好 3 条 BL + 末尾 RET**（42 新址 **唯一** 命中）  
   - 对照 BL 目标是否也成对搬迁（41: `0x2664c50`→42: `0x2bb01fc` 等）

脚本参考：`04_scripts/_common/diff_il2cpp_mem.py`（改包 stub 对比）；可另写「两版 APK 抽 so → 导出 invoke 候选 file_off」的一次性脚本，**不必写进 mod 热路径**。

**阶段 C — 改 mod 前必须 runtime 验收**

1. 仅改 `FILE_INVOKE_xx` 常量（或 OTA `invoke_file`，见 Hzsj 范例）  
2. `ywgn_so_only.sh` + 进关实测  
3. log 必须出现：`MI score …SendScore` + `SendScore→… #N` 且 **N 随对局增长**  
4. 关 Trace，再出正式 so  

**阶段 D — 若 B 阶段找不到同型 116B 函数**

说明 HybridCLR **换调用路径**（不是简单搬迁），需回到：

- StarryTrace 对局抓 SendScore 真实 caller / 参数布局  
- 或斌哥新包 memdiff 找新 B-stub  
- **禁止** 直接上 runtime_invoke / MP 白名单 / 扫堆 AutoPlay

### 5.5 与「在 mod 里自动扫特征」的边界

| 做法 | 评价 |
|------|------|
| **发版前**用脚本 diff 两版 il2cpp，人工确认 file_off | ✅ 推荐；可复现、可写进文档 |
| OTA 下发 `invoke_file`（常量热更，仍须先定位） | ✅ 可选；Hzsj 已有先例 |
| mod 运行时全 so 扫 prologue | ⚠️ 仅在多次验证签名唯一后考虑；本次 3BL+RET+头 16B 在 42 **唯一**，但未跨版本证明 |
| 无 diff 无 Trace 硬编码「小版本不变」 | ❌ 本次 41→42 已翻车 |

**结论：** 下次更新优先 **「旧版桩 blob → 新版 so 匹配 + 进关 log 验收」**；理解 §5.3 调用链比记 `0x2BAC188` 更能复现功能。
