## 0. 一句话结论

斌哥包 = **官方 2026.10.8 游戏本体（libil2cpp / libunity 未 patch，与官方逐字节同源）**

## 3. 四个 IL2CPP 挂点（Dobby hook 目标，含特征码）

`libSDKloading.so` 里含 `::` 的游戏方法名**只有这 4 条**（其余全在 dex，且已被壳加密）。
描述符表位于 `.data.rel.ro` vaddr **0x150fe30**，stride **0x38 = 56 B**，4 条 + 终止；
每条 = `{+0x00 char* 方法名; +0x08 u64 期望地址; +0x10 40 字节 AArch64 特征码}`：

| 槽 | 方法名 | 期望地址(RVA) | 文件偏移 | 40 字节特征码（LE 指令字） |
|---|---|---|---|---|
| 0 | `NEON.Game.Killable::TakeDamage` | **0x3eceefc** | 0x3ecaefc | `6db733ed 6d012beb 6d0223e9 a9037bfd a9046ffc a90567fa a9065ff8 a90757f6 a9084ff4 d10703ff` |
| 1 | `NEON.Game.Hearts::TakeDamage` | **0x3f2ee90** | 0x3f2ae90 | `d102c3ff a9085ffe a90957f6 a90a4ff4 f001d6f6 f001adf7 aa0203f3 396deac8 f9429af7 aa0103f5` |
| 2 | `NEON.Framework.Attri::TryGetValue` | **0x3cb6580** | 0x3cb2580 | `d10103ff f9000bfe a90257f6 a9034ff4 d001eab6 aa0203f3 aa0103f4 394c26c8 aa0003f5 37000128` |
| 3 | `NEON.Game.Killable::Update` | **0x3eceac0** | 0x3ecaac0 | `39442008 34000288 fc1e0fe8 a9014ffe aa0003f3 bd410c08 aa1f03e0 94bc0d7c 1e202900 bd411261` |

**已实证核对（本轮最重要的验证）**：
把 4 条特征码拿去斌哥包内的 `libil2cpp.so`（130,351,104 B）按 `file off = RVA − 0x4000` 比对
（该 so 的 `LOAD#2`：off 0x2c0b590 / vaddr 0x2c0f590 ⇒ **vaddr = file off + 0x4000**），
**4/4 精确命中且各自在整库中只出现 1 次**（`bytes.count(needle)==1`）。
⇒ `期望地址` 就是该方法在官方 2026.10.8 `libil2cpp.so` 里的**链接期虚拟地址**，
且斌哥包**没有改动游戏 so**，改的只是运行时挂点。

- 槽0/槽1/槽2 的特征码起点＝方法**入口序言**（首指令即 `stp d13,d12,[sp,#-0x90]!` 之类的预索引保栈）。
- 槽3 `Killable::Update` 的命中点在**函数体内**（`ldrb w8,[x0,#0x108]; cbz w8,…` 之后），
  属 Dobby 支持的**函数中段 hook**——移植时不能用「按名挂入口」直接等价复刻。

## 4. 挂点安装链路（地址台账，便于移植时对照）

```
描述符表 0x150fe30 (stride 0x38, 4 条)
   │  解析器 0x2d1848：对每条用 memmem(可执行段, 特征码, 40) 扫地址 A
   │                    delta = A − 期望地址；要求 4 条 delta 完全一致（自检）
   ↓
目标地址数组 .bss 0x16b0ec0（4×8 B）
   │  安装器 0x2ce454：count = [0x16b1e00+0x1e0] 上限 6（超出只装前 6 个）
   │    target = [0x16b0ec0 + i*8]; replacement = [0x150fce0 + i*8]; orig → 0x16ddc8 + i*8
   │    slotmap[installed] = i → 0x16af070 + installed*4（失败写 −1）
   │    日志：0x428658 '安装特征索引:%d 地址:%lx 到HOOK槽:%d'
   ↓
替换函数表 0x150fce0（6 条薄跳板：0x2d9380/0x2d9394/0x2d93ac/0x2d93c4/0x2d93dc/0x2d93f4）
   │  每条 = `mov w0,#槽号(0..5); mov x1,x0; mov x2,x1; mov w3,w2; b 0x2d940c`
   ↓
共用分发器 0x2d940c：pthread_mutex_lock(0x16b0e90) → orig = [0x16ddc8 + 槽*8]
                     orig 非空则调用 orig（否则返回 0）→ 运行时自检/锁定特征索引
                     （日志 0x428708 '自动锁定特征索引:%d 地址:%lx'、
                       0x4286c5 '已拆除其余误判的 unityrun 候选 hook，仅保留索引:%d'）
```

Dobby 本体：`DobbyHook`(0x2e1d8c) / `DobbyDestroy` / `DobbySymbolResolver` / `DobbyBuildVersion`
＝ `Dobby-20210616-223aabc`；调用点 `DobbyHook`=0x2ce4fc / 0x2ce624 / 0x2d9284 / 0x2d92c8。

**框架级 hook（不是游戏挂点，但决定功能可用性）**：
- `DobbySymbolResolver("libdl.so","android_dlopen_ext")` @0x2ce5ec ⇒ 挂 `android_dlopen_ext` 做
  「**被动捕获**」libil2cpp 装载（日志 `[主动绑定] dlopen(libil2cpp.so) 失败 -> 仍只能靠被动捕获`）；
- `il2cpp_runtime_class_init` 当「**就绪触发器**」（`[就绪触发] 已挂 … 等游戏自己把我们叫醒`）；
- `Assembly::Load` / `Assembly::GetTypes` 自取程序集镜像供 `Get_FunDoMethods` 按名取函数；
- 反作弊：`[反作弊] BuildPassCheckInfo HIT model=%p extraIntDic=%p -> NULL`；
- 内嵌 metadata dumper（会写 `files/dump.cs`）；日志 tag＝`blackwind调试`。

## 5. 字段改值表（无限手雷 / 无限跳跃的**真身**）

静态初始化器 0x2c6854–0x2c69b8 在 `.bss` 建表：**基址 0x16b1420，尾指针 0x16b15d8，
stride 0x28 = 40 B**，10 条 + 终止条。每条：

```
+0x00 char*  显示名（日志用）
+0x08 char*  字段名  ← 运行时按此名「不区分大小写」匹配
+0x10 double 目标值
+0x18 int    分组号（本表全为 3）
+0x20 char*  类别标签（手雷 / 跳跃 / 全屏）
```

| 类别标签 | 组号 | 目标值 | 字段名 |
|---|---|---|---|
| `手雷` (0x428857) | 3 | **9999.0** (`0x40C3878000000000`) | `DefaultBomb`, `FireBomb`, `IceBomb`, `ThunderBomb`, `Liquor_Bomb`, `FinalBombCount`, `MaxBomb` |
| `跳跃` (0x42885e) | 3 | **99.0** (`0x4058C00000000000`) | `MultipleJumpCountLimit`, `ExtraMultipleJumpCountLimit`, `FinalMultipleJumpCountLimit`（匹配名另用 `multipleJumpCountLimit` 小写形） |
| `全屏` (0x428865) | — | — | **静态表无条目** → 由服务端远程配置注入 |

消费逻辑（0x2cf948 与 0x2dc4f8 两处）：
`门控 = (组号==4) ? [0x16b13d4] : [0x16b13d0]`，为 0 则跳过该条；
候选字段串与 `[+0x08]` 做逐字节 `tolower` 后比对；命中后
**仅当 `current < 目标值` 才写 `current = 目标值`（只提升不降低）**；
再按 `[+0x20]` ∈{手雷,跳跃,全屏} 归类并自增计数数组 `0x16b1698 + idx*4`（上限 7）。

> 这就是「无限手雷 / 无限跳跃」**不是 hook、而是改数值上限**的原因：
> 手雷上限提到 9999、跳跃上限提到 99 ⇒ 玩家体感无限。

## 6. 特性开关分发器 0x2d5fb8（featNum 0..14）

`cmp w3,#0xe; b.hi` + `adr x10,0x2d5fe8` + `ldrb w11,[0x4254ec + w3]` 跳转表，共 **15 路**；
实参 `w5`=int 数值、`w6`=bool 开关。已知映射：

| featNum | 名称（日志原文） | 写入开关字节 | 附带配置 |
|---|---|---|---|
| 0 | 百倍伤害 | `0x16b13c8` | `[0x16af064] = w5`（倍率） |
| 1 | 玩家无敌 | `0x16b13cc` | — |
| 2 | 战斗速度×5 | `0x16b13d0` | `[0x16af068] = w5` |
| 3 | 无限体力 | `0x16b13d4` | — |
| 4 | 无限货币 | `0x16b13d8` | — |
| 5 / 6 | （无日志） | `0x16b13dc` / `0x16b13e0` | 另有一路写 `[0x16af060]` |
| 7–14 | 未逐条展开 | — | 由壳服务端配置按 featNum 下发 |

消费门控：字段表用 `0x16b13d0`（feat2）/`0x16b13d4`（组号4）；挂点分发器读 `0x16b13c8`→伤害、`0x16b13cc`→无敌。

## 8. 对下一步「星空版移植」的对接建议

1. **可 1:1 复刻的部分（4 个挂点）**：我们已有本游戏自己的解密 metadata（`/tmp/neonabyss2_dev/meta_v31.dat`）
   与 `HookByName(rva=0)` 框架，可直接按名挂
   `NEON.Game.Killable::TakeDamage` / `NEON.Game.Hearts::TakeDamage` /
   `NEON.Framework.Attri::TryGetValue` / `NEON.Game.Killable::Update`。
   但注意槽3 的斌哥挂点**在函数体内**（中段），若要完全等价需 AOB 中段挂载。
2. **更稳的定位法**：直接复用斌哥的 40 字节特征码（已在官方 10.8 so 上各自唯一命中）
   ⇒ 版本无关挂载，比 `HookByName` 更抗更新（本仓在「我本布衣世家录 / 敢达争锋对决」已有 AOB 成功先例）。
3. **无限手雷 / 无限跳跃**不是 hook 能做的：需要实现「**字段名 → 目标值（只提升不降低）**」的改值器
   （读对象实例字段并写回），或改为挂对应的字段消费点/上限判定点。
4. **全屏攻击**缺少静态条目：需要**冷启动 runtime 抓取**（壳会从服务端拉配置）才能看到字段名与目标值；
   旁证是 dex 的密文表与 `libSDKloading.so` 的字段匹配器。
5. **运行时验证的前置障碍**：themis 反调试使 `frida attach` 现有进程必超时、
   `dd /proc/<pid>/mem` 报 I/O error ⇒ 运行时抓点必须**冷启动**
   （`frida -U -f com.veewo.neonabyss2`）或在用户重开游戏时进行（本轮未打扰用户游戏进程）。
