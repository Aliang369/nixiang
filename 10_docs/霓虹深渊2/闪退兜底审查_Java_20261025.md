## A. 启动 / 弹菜单路径上「没有 try/catch 兜底」的调用点

### A0. 先给出结构性事实：兜底边界在哪里

两条兜底线是明确的：

1. **`MenuSafeHandler`**（`menu/MenuSafeHandler.java:20-29`）只保护**经由 `mainHandler.post`** 的 Runnable：

```java
20:    public void dispatchMessage(Message msg) {
21:        try {
22:            super.dispatchMessage(msg);
23:        } catch (Throwable t) {
24:            Log.e(tag, "menu callback exception isolated", t);
```
而 `MenuService.java:208` 与 `NativeMenuController.java:105` 的 `mainHandler` 就是它 —— 所以**所有 `mainHandler.post(...)` 内部的异常被隔离**。

2. **以下三条路径不经 MenuSafeHandler**，异常直接落到 Looper/框架，最后走 `CrashHandler` → 系统默认处理 → **进程死亡**：
   - Service / Activity 生命周期回调本身（`onCreate`、`onActivityResumed` 等，AMS 直接调用）；
   - **View 监听器**（Switch / SeekBar / Button / EditText / PopupWindow 菜单项，由 `ViewRootImpl` 在主 looper 直接分发，**不经过我们的 handler**）；
   - `authExec` 线程池任务（`NativeMenuController.java:106` `Executors.newSingleThreadExecutor()`，无自定义 `UncaughtExceptionHandler`）。

这一条是理解 A/C 全部结论的前提。

- 【静态阅读】缺口成立。
- 【历史实测(文档)】同类事故已在代码注释中记录：`MenuService.java:609-610`「无悔华夏等重 Application 机型会 ForegroundServiceDidNotStartInTimeException」——说明这条 onCreate 路径确实在生产中炸过。

## B. `CrashHandler` 到底是「记录后仍死」还是「吞掉保活」？

### 结论：**记录 + Toast 提示 + 睡 1.5s + 交回系统默认处理 = 进程一定死。它不是保活器。**

要点（全部【静态阅读】）：

1. **第 92-97 行无分支可以"活下来"**：`defaultHandler` 非空 → 交回系统（`RuntimeInit$KillApplicationHandler` → 杀进程）；为空 → 显式 `killProcess + System.exit(10)`。**没有"吞掉异常继续跑"的分支。**
2. **不会把死进程变成活进程，反而多 1.5 秒白屏/卡顿**（第 88 行 `Thread.sleep(1500)` 在**抛出异常的线程**上执行；若该线程是主线程，就是 1.5s 无响应 + 之后杀进程 —— 用户观感上更像"卡住然后闪退"，也更容易被 ROM 记为 ANR）。【静态阅读】
3. 类注释自己写明了意图，`CrashHandler.java:21-22`「只覆盖 Java 层——native 段错误不经过这里」。**native 崩溃（SIGSEGV/SIGABRT，例如某个功能 hook 写坏内存）Java 层完全无法兜底。**【静态阅读】
4. 落盘位置 `getLogDirectory()`（`CrashHandler.java:168-183`）优先 `Android/media/<包名>/files/crash_logs`，取日志不必 root —— 这对**定案 A/C 中实际是哪一条**很有用（见 §E 末判据）。

**对用户现象的直接含义**：既然 CrashHandler 不保活，那么①和②两类闪退如果发生在 Java 层，**都能在 `Android/media/com.veewo.neonabyss2/files/crash_logs/crash_*.txt` 里找到完整堆栈 + 全线程转储**（`CrashHandler.java:120-166` `buildCrashReport` 含 `ALL THREADS`）。这是把本报告从"静态推断"推进到"实测定案"的唯一低成本路径。

`MenuSafeHandler` 与它不是一回事，别混：
- `MenuSafeHandler.dispatchMessage`（`menu/MenuSafeHandler.java:20-29`）**吞掉并保活**（只 `CrashHandler.logException(t)` 落盘，不转发给 defaultHandler）；
- `CrashHandler`（全局 `Thread.setDefaultUncaughtExceptionHandler`）**记录后仍死**。
- 也就是说：**只有走 `mainHandler.post` 的回调被保活，其他一律死。** 这个不对称是本报告 A/C 全部缺口的根因。

### C7. 为什么「开启某个功能就闪退」很可能是 native 而不是 Java

把 C1–C6 合起来看，Java 侧对 **Exception / Error** 的拦截相当到位（`safeCall` 覆盖 `Throwable`）。一台 root 的 Android 14 设备上「拨开关就闪退」并且 **`crash_logs` 里没有 Java 堆栈**，基本只能是 native 段错误：

- 判据：`logcat -b crash` 里出现 `F signal <pid> ... SIGSEGV/SIGABRT` 且**没有** `FATAL EXCEPTION` → native；
- 若出现 `FATAL EXCEPTION: main` + `MenuItem/onCheckedChanged`/`onProgressChanged` 帧 → Java，必是 C1–C4 某个监听器里漏出的异常（**但按现有代码，这需要 `bridge.*` 自己抛**，而它被 `safeCall` 包住了，所以概率低）。
- 【待验证】：必须以真机 crash log 定案，不接受"按经验推测"。

## E. 按「缺失兜底」严重程度排序的待补点（8 条）

> 排序依据：①是否落在**进程启动/每次 resume**（影响面最大）②异常类型是否**必然杀死进程**（无任何 catch）③是否有现成最小改动。每条都给「文件:行 + 最小改动 + 降级行为」。

### E1（最高）`catch (Exception)` → `catch (Throwable)`，并给失败态降级

- **位置**：`menu/MenuService.java:842`（`tryShowMenuWithRetry`）、`menu/MenuService.java:831`（`ensureNativeMenu`）
- 现状：`catch (Exception e)` 接不住 `ExceptionInInitializerError` / `NoClassDefFoundError` / `UnsatisfiedLinkError` / `OutOfMemoryError`，而这些正是「UI 树构建 / `MagicRes` 静态初始化 / so 未加载」时会抛的类型；漏出即冒泡到 `onCreate`（`MenuService.java:643`）→ 进程死。
- **最小改动**：两处 `catch (Exception e)` → `catch (Throwable e)`；`tryShowMenuWithRetry` 的重试计数保留。
- **降级**：Error 也变成"这次没挂上，1.5s 后再试 / 30s 后放弃并 `Log.e`"，不杀游戏。
- 等级：【静态阅读】。这条同时是「打开菜单就闪退」最可能的止血点。

### E2（最高）`showMenu()` 公开入口补兜底

- **位置**：`menu/MenuService.java:890-896`
- 现状：`public void showMenu()` 里 `showMenuNative(host)` **零保护**；`showMenuNative`（`MenuService.java:923-940`）本体也无 try。任何调用方（注入点 / JS / 未来代码）触发异常 = 崩。
- **最小改动**：`showMenu()` 整体包 `try { ... } catch (Throwable t) { Log.e(TAG,"showMenu failed",t); }`。
- **降级**：静默失败，不崩；心跳（`MenuService.java:300-315`）会再次尝试。
- 等级：【静态阅读】。

### E3（高）`onCreate` 内两处裸调用包兜底

- **位置**：`menu/MenuService.java:632`（`registerResumeWatcher()`）、`menu/MenuService.java:774`（`getApplication().registerActivityLifecycleCallbacks(...)`）
- **最小改动**：
  ```java
  try { registerResumeWatcher(); } catch (Throwable t) { Log.e(TAG, "registerResumeWatcher failed", t); }
  ```
  并在 `774` 前加 `Application app = getApplication(); if (app == null) return;`
- **降级**：没注册成生命周期回调 → 菜单仅靠心跳 + `findResumedActivityViaThread`（`MenuService.java:550-582`，已有 `catch (Throwable)`）工作，功能不丢。
- 等级：【静态阅读】。

### E4（高）`authExec` 三个 OTA/清理任务补 `try/catch(Throwable)`

- **位置**：`menu/NativeMenuController.java:1457`、`1493`、`1537`；配套 `ota/PlayOtaManager.java:124-128`
- 现状：worker 线程未捕获异常 = 杀进程（`Executors.newSingleThreadExecutor()` 无自定义 handler）。
- **最小改动**：三个 `authExec.execute(() -> { ... })` 的 lambda 体各包一层 `try{...}catch(Throwable t){ mainHandler.post(() -> showToast("操作失败：" + t)); }`，并在 `finally` 里 `btn.setEnabled(true)`（现在异常时按钮永久 disabled）。
- **降级**：本次 OTA 失败 + toast 告知，游戏不受影响。
- 等级：【静态阅读】。「设置页点一下就闪退」的直接止血点。

### E5（中高）开关监听器整体兜底 + 让 native 真失败能回滚

- **位置**：`menu/NativeMenuController.java:2205-2214`（`attachToggleListener`）；配套 `bridge/ModBridge.java:307`（`safeCall(() -> nativeSetFeature(...))` 吞异常后仍 `return true`，见 `:311`）
- **最小改动（两步）**：
  1. listener 体包 `try { ... } catch (Throwable t) { buttonView.setOnCheckedChangeListener(null); buttonView.setChecked(!on); attachToggleListener(sw,num,raw); showToast("操作失败"); }`
  2. `safeCall` 加返回值版本（`private static boolean safeCallBool(Runnable)`），native 抛异常时 `onToggleChanged` 返回 `false` → 复用现有回滚分支。
- **降级**：native 失败时开关**回弹到原状态 + toast**，不再出现"UI 开、native 关、偏好已写 ON"的脏三元组（当前 `ModBridge.java:303` 先写偏好、`:307` 后调 native，失败无回滚）。
- 等级：【静态阅读】。

### E6（中）滑块 / 下拉 / 输入框三个监听器统一兜底 + 失败回滚 UI

- **位置**：`menu/NativeMenuController.java:1839-1850`（SeekBar）、`2022-2037`（Spinner item）、`1946-1957`（EditText 失焦）
- 现状：三者**无 try/catch**；且 **只有 Spinner** 在失败时保持旧显示，SeekBar 的数值 TextView + 滑块位置**不回退**（`1842` 先 `fVal.setText`）。
- **最小改动**：三处 listener 体包 `catch (Throwable)`；SeekBar 失败分支补 `seekBar.setProgress(Preferences.loadPrefInt(num) - fMin);`（或记录 drag 前值并恢复）。
- **降级**：不崩 + UI 与 native 状态一致。
- 等级：【静态阅读】。

### E7（中）Game Activity 生命周期回调的同步段补兜底

- **位置**：`menu/MenuService.java:720`（`onActivityResumed` 内 `attachHostFocusWatcher(a)` → `787-799`）、`menu/MenuService.java:735`（`onActivityPaused` → `detachHostFocusWatcher` `801-812`）
- 现状：这两段**不经 MenuSafeHandler**，异常直接杀进程；且 `onActivityResumed` 每个 Activity 都会跑。
- **最小改动**：`attachHostFocusWatcher` 调用处包 `try{...}catch(Throwable t){Log.w(TAG,"focus watcher failed",t);}`；`onActivityDestroyed` 整段同理。
- **降级**：失去焦点监听（只影响 ColoOS 分屏/浮窗的藏窗时机），菜单与功能不受影响。
- 等级：【静态阅读】。「打开游戏就闪退」的第二个候选面。

### E8（中低）两处 native 直调 + 一处 Provider 一致性缺口

- **位置 A**：`bridge/ModBridge.java:373-384`（`getFeatureListJSON()` 直接 `String[] features = nativeGetFeatureList();` **无 try**）、`bridge/ModBridge.java:806-812`（`lockAllFeatures()` 直接 `String[] features = nativeGetFeatureList();` **无 try**）。这两处可在 so 未加载时抛 `UnsatisfiedLinkError`（`Error` 子类）→ 若由 JS/UI 主线程调用即崩。对照：同类 `getFeatureListRaw()`（`:385-391`）**有** try，说明是遗漏而非设计。
- **位置 B**：`StarryInitProvider.java:82-90` 两个 Activity 回调**无 try**，与 `StarryApp.java:126-136` 的同名回调不一致。
- **最小改动**：A 两处仿 `getFeatureListRaw` 包 `catch (UnsatisfiedLinkError)`（或直接改调 `getFeatureListRaw()`）；B 两处补 `try{...}catch(Throwable ignored){}`。
- **降级**：返回空列表 / 跳过强制网页登录改动，均不影响进程存活。
- 等级：【静态阅读】。

### E. 补充：不建议做（会掩盖证据）的改法

- **不要**把 `CrashHandler` 改成"吞掉 + 保活"：`crash/CrashHandler.java:80-99` 现在的语义（记录 → 交回系统）是**唯一能留下可复现堆栈**的设计；改成保活会让进程带着半初始化状态继续跑，症状从"闪退"变成"功能点了没反应/存档写坏"，更难查。若要减少用户流失，正确做法是**消灭异常源**（E1–E8），而不是吞异常。
- **不要**为了兜 native 段错误而在 Java 里加 try/catch —— 无效（`crash/CrashHandler.java:21-22` 已注明 native 崩溃不经过这里）；native 侧要靠 SafeProbe/桩纪律。
