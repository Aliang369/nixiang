# 霓虹深渊2 武器满级（Soul 等级 → 9）抓点与实现 — 2026-10-27（r29）

> 需求原话：「新增加一个功能武器等级满级（游戏里的武器可以升级，通过分解其他武器获得经验，
> 然后提升武器的等级，最高级好像是9级，等级提升对应的那些属性也需要提升，不是单纯等级的ui改变）」
>
> 结论先行：本作武器等级 = **Soul（灵魂）等级**，满级 9；属性提升由
> `FirearmsPowerUp.LevelUpWeaponCore(exp, level, rules)` 应用 `UpgradeRules` 完成。
> 因此功能实现**只调游戏自己的这个方法**（不写字段、不伪造 UI），属性按游戏规则真实生效。

## 1. 离线元数据是怎么拿到的（本轮关键能力恢复）

r23 起官方把 `assets/bin/Data/Managed/Metadata/global-metadata.dat` 整份磁盘加密，离线 Dumper 失效；
本轮发现**运行时副本可读**：

1. 启动官方游戏，root 下看 `/proc/<pid>/maps`：
   ```
   23945216 0x726e800000 rw-p /storage/emulated/0/Android/data/com.veewo.neonabyss2/files/il2cpp/Metadata/global-metadata.dat
   ```
   ⇒ 游戏把「解密后的元数据」映射/落盘到外部私有目录（该文件 23,941,692 B，与 APK 内同长）。
2. 但**磁盘那份与内存那份不同**（`cmp -l` 588 万字节不一致），内存那份才是真身：
   ```
   adb exec-out su -c "dd if=/proc/<pid>/mem bs=4096 skip=<addr/4096> count=5846" > meta_mem.dat
   ```
3. 头部 magic `0xFAB11BAF` 正常，**version 字段被改成 16**（合法值应为 31）⇒ LibCpp2IL/Il2CppDumper
   都会拒绝或按 v16 误解析。把 offset 4 的 4 字节改成 31 即恢复：
   ```
   struct.pack_into('<I', buf, 4, 31)
   ```
4. 之后 `01_tools/MetadataSearch`（LibCpp2IL）可正常枚举：
   `dotnet run -c Release -- /tmp/nhsy2/meta_v31.dat 6000.0.73f1 types|methods|fields|sig|str <arg>`
   实测 **26,584 个 typeDef**，类名/方法名/字段名/签名全部可读（RVA 仍不可得，本游戏本来就按名挂点）。

> 该 dump 只在内存态存在；`/tmp/nhsy2/meta_v31.dat` 属临时产物，不入库。

## 3. 实现（native，`Games/nhsy2Mod.cpp` §6.8）—— r29b 定稿版

新增菜单项 `Toggle_武器满级`（战斗分类末尾，下标 6 ⇒ 资源分类后移，「解锁标准版」回到槽 8）。

### 3.1 ★ r29a 事故与两条硬教训（第一版实现作废）

| 现象 | 真机日志 | 结论 |
|---|---|---|
| 分解武器那一刻整局卡死 | `wlv: LevelUpWeaponCore 拦截 level 0 → 9（exp=5 命中#1）` 之后无输出 | 我们改写了 `LevelUpWeaponCore` 的入参，把游戏踢进死循环 |
| 等级升到 10、19（超过 9） | `OnWeaponSoulDataChanged level=10 / level=19` | 第 2 参**不是目标等级**（按 +9 叠加）；本作满级**不是 9**，`SoulLevel / 9` 只是公式归一化 |
| `rules` 指针被判非法 | `wlv: GetSoulUpgradeRules 失败 rules=0x74923abfc0 exc=0x0` | `UpgradeRules` 是**值类型**，`runtime_invoke` 返回**装箱对象**，当指针传给 `LevelUpWeaponCore` ⇒ ABI 不符 ⇒ 规则表读垃圾 |

**教训**：① 值类型返回值不能直接当指针传给游戏方法（必须先判断/拆箱）；② 参数语义没实证前不许改写；
③ 「跨 ABI 调游戏方法」这条路线在 themis 保护的本作里代价极高，优先走「只改数据/只改返回值」。

### 3.2 r29b 定稿实现：只放大「分解经验」，升级交给游戏自己

| 槽 tag | 方法（按名） | 作用 |
|---|---|---|
| `Wlv_DecompExp` | `NEON.Game.LootSystem.SoulLevelConfig.GetDecomposeExp(Int32) -> Int32` | **唯一改写点**：返回值 `< 200000` 时抬到 200000（只抬不降） |
| `Wlv_MaxLevel` | `SoulLevelConfig.GetMaxLevel() -> Int32` | 只读探针：真机打出本作真实满级 |
| `Wlv_Core` | `FirearmsPowerUp.LevelUpWeaponCore(Int32,Int32,UpgradeRules)` | 只读探针（**不改参数**） |
| `Wlv_Changed` | `FirearmsPowerUp.OnWeaponSoulDataChanged(...)` | 只读探针：`newLevel` 即 L2 判据 |
| `Wlv_EnsureInit` | `FirearmsPowerUp.EnsureSoulDataInitialized()` | 只读探针（武器初始化时机） |

语义：开关打开 ⇒ 在分解房分解一把武器，游戏拿到 200000 经验 ⇒ **由游戏自己的升级循环**
（含它自己的满级判定、`UpgradeRules` 属性应用、HUD 刷新）把武器一路升到满级。
不调用任何游戏方法、不写任何字段 ⇒ 关闭开关立即恢复原值，状态不可能被改坏。

## 4. 判据

- 装钩：`install pass: ok=73 dead=0/77` + `install skip: 3`（新增 5 槽后总数 72→77）。
- 武器初始化/升级：`wlv: OnWeaponSoulDataChanged level=… needExp=… exp=…`。
- 分解：`wlv: 分解经验放大 <原值> -> 200000（分解#N）`。
- 满级：`wlv: SoulLevelConfig.GetMaxLevel() = <真实满级>`（本轮由探针实测记录）。
- L3：分解一把武器 ⇒ 等级连跳到满级、属性同步变高、**不卡死**。

## 5. 已知取舍 / 未决

- `GetDecomposeExp` 若也被 UI 用来「预览分解可得经验」，预览数字同样会显示 200000（纯显示差异）。
- 「拿起来就满级」目前**没有**做：需要调用游戏方法或写 `CurSoulData` 字段，r29a 已证明风险过高；
  当前路径是「分解一次即满级」，与用户描述的「分解其他武器获得经验升级」一致。
- 真实满级值以 `Wlv_MaxLevel` 探针日志为准；拿到后回填本文档，并评估是否需要"按需分级"。

## 6. r29d（2026-10-27，按用户指定方向改向）——压缩"升级所需经验"，不再动分解经验

用户原话：「分解后的经验会在游戏屏幕中显示导致整个游戏边卡，然后多了直接卡死，
看看可以不可以不改分解后的经验，改获得经验后的加成变多？」

| 轮次 | 做法 | 结果 |
|---|---|---|
| r29a | 强改 `LevelUpWeaponCore` 入参 + 值类型 `UpgradeRules` 当指针传 | 分解即卡死（挂点已永久删除） |
| r29b | `GetDecomposeExp` 放大到 200000 | 大数字上屏 + 连跳 ⇒ 主线程拖死 |
| r29c | 放大到 5000 + 满级需求护栏 + 删掉 LevelUpWeaponCore 挂点 | 数字仍然大；用户要求改成"经验更值钱" |
| **r29d** | **分解经验保持原样**；`GetLevelUpRequireExp(level)` 未满级恒返 **1**、满级返 int32 上限；`UpgradeRules.get_ExpRequireMultiplier()` 压到 ≤0.05 | 待 L3 |

- 真机实测：`SoulLevelConfig.GetMaxLevel() = 9`（满级就是 9）；`GetDecomposeExp` 原值如 20；`needExp` 1→2 级 = 60、2→3 级 = 100（真机 `OnWeaponSoulDataChanged` 探针）。
- 语义：同样 20 点经验，因为每级只要 1 点，会连跳 8 级到 9；升级规则仍由游戏自己应用（属性真实提升）。
- 挂点（5 槽，全部纯标量，冻结风险最低）：`Wlv_ReqExp`（唯一改写）、`Wlv_ReqMul`（float getter，tiny4 补丁）、`Wlv_MaxLevel` / `Wlv_Changed` / `Wlv_EnsureInit`（只读探针）。
- 装机判据：`install pass: ok=73 dead=0/77` + skip 3；`wlv: 升级需求 X -> 1（level=N）`、`wlv: 满级需求护栏 level=9 req … -> 134217727`、`wlv: OnWeaponSoulDataChanged level=9`。

## 7. r29f（2026-10-27）——真机反汇编定位到唯一正确的改写点

r29d 实测 `needExp` 恒 60 ⇒ 说明 `GetLevelUpRequireExp(Int32)`（argc=1）与
`UpgradeRules.get_ExpRequireMultiplier()` **都不在升级路径上**。

做法：新增只读探针 `debug.starry.nhsy2_wlv_probe=1`（只解析 MethodInfo 并打印地址，不挂钩），
再用 root 从 `/proc/<pid>/mem` 按 `MethodInfo->methodPointer` 取代码段，本地 capstone 反汇编。

关键结论（`ProcessExpGain` 真身）：

```
newExp  = *exp + (int)(baseExp * rules.ExpGainMultiplier)
if (IsMaxLevel(level, rules)) return false;
needExp = max(1, (int)(GetLevelUpRequireExp(level, rules) * pct));   // ← 0xc54 那个重载
if (newExp < needExp) return false;
… 进入升级流程
```

⇒ 决定"几级"的是 **`GetLevelUpRequireExp(Int32, UpgradeRules)`**（argc=2 的第二个重载，
序言 `D10103FF 6D0123E9`），ABI = `x0=this, w1=level, s0..s3=UpgradeRules(4×float)`。

因此 r29f 改为：按"名字 + 2 参数 + 序言特征"在类方法表里精确定位该方法，
用带 4 个 float 的钩子签名原样转发（绝不重演 r29a 的 `void*` 事故），
未满级返回 1（每级 1 点经验）、满级返回游戏原值（由游戏自己的 `IsMaxLevel` 收口）。

- 装机判据：`wlv: ReqExp2 精确装钩 ok target=libil2cpp.so+0xc54`
- 生效判据：`wlv: ReqExp2 需求 60 -> 1（level=1 第N次）` → `OnWeaponSoulDataChanged level=9`
- 探针开关：`adb shell setprop debug.starry.nhsy2_wlv_probe 1`（只读、可随时关）

**永久教训（写入 skill 时用）**：
1. 值类型（结构体）返回/入参绝不能当指针传（`UpgradeRules`）⇒ 挂点必须按真实 ABI 写（4×float 走 s0–s3）。
2. 「改个 getter 让它更便宜」之前，必须先证明**升级路径真的调用它**——用 `debug.starry.nhsy2_wlv_probe=1`
   打印 MethodInfo 地址 + capstone 反汇编 `ProcessExpGain` 看 `bl` 目标，比反复让用户试快得多。
3. 不要自造上限：游戏自己会在算需求前先判 `IsMaxLevel`，多写的"保护"反而制造 bug。
