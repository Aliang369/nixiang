## 2. ① dynsym / 名字层（证据）

```
$ llvm-readelf -SW libil2cpp.so
There are 5 section headers ... [1].note.gnu.build-id [2].dynstr(0x3709c8,0x1c0e3) [3].dynamic [4].shstrtab
$ llvm-readelf -dW libil2cpp.so
SYMTAB 0x4b8 / STRTAB 0x3709c8 / STRSZ 114915 / HASH 0xeac8 / RELACOUNT 822298 / JMPREL 0x14400 PLTRELSZ 144
INIT_ARRAY 0x0 INIT_ARRAYSZ 0 INIT 0x8413eac          ← 无 .init_array，初始化走 DT_INIT
NEEDED: liblog.so libm.so libdl.so libc.so            ← 不需要 libc++_shared.so
```

1. **符号表里 2454 项**（`Symbol table for image contains 2454 entries`）。编号 1–2 是真符号（`_Znwm` 0x33d8f50 size 112 / `_ZdlPv` 0x33d9038 size 8，WEAK），**编号 3 起全部是垃圾**：value 形如 `0x3fe48ddd600`（远大于文件大小 138,559,488）、size 形如 3,099,626,735、名字是乱码。
2. **名字层是凯撒 +1 位移**，例：
   `3: TztufnObujwf`MDigmbhtDboTfuIidefoGmbh` → 解码 `SystemNative_LCflagsCanSetHiddenFlag`；另一条 `ddh}fdjsidhfyhm` → `ccg|ecirhgexgl`（同类）。
3. **整文件 0 个明文 `il2cpp_`**：`LC_ALL=C grep -aoi 'il2cpp_[A-Za-z0-9_]*' libil2cpp.so` → 0 命中；真实 `.dynstr`（0x3709c8，114,915 B）单独抓出来也 **0** 命中。
4. **解码后仍拿不到关键 3 API**：对 2454 个名字整体 −1 解码，得到 `il2cpp_*` 仅 **10** 个（如 `il2cpp_class_get_properties`、`il2cpp_is_vm_thread`、`il2cpp_memory_pool_set_region_size`），**`il2cpp_class_from_name` / `il2cpp_assembly_get_image` / `il2cpp_class_get_method_from_name` 命中数均为 0** ⇒ 这 3 个是**从符号表中直接摘除**，不是单纯改名。
5. **导入面完好、导出面废掉**：6 条 JUMP_SLOT 的导入名是明文，可正常链接：
   `__cxa_finalize / __cxa_atexit / memset / sscanf / __stack_chk_fail / __android_log_print`。
   注意 **没有 mprotect/mmap/dlsym/dlopen 导入**；尾部加固 stub 里只用 3 条直接系统调用（openat/read/close，见 §4）。
6. **框架 so 侧早已为此写好降级**（`strings libstarry_magic.so`）：
   ```
   [Il2Cpp] NOTE: il2cpp_class_from_name poisoned/absent -> ClassFromNameScan fallback
   [Il2Cpp] NOTE: il2cpp_class_get_method_from_name poisoned/absent -> GetMethodScan fallback (methods=%d pcount=%d)
   [Il2Cpp] strtab plaintext il2cpp_ count=%d
   ```

**结论（①）**：按名解析（`dlopen`+`dlsym`）在本包**必然失败**，且失败原因比 r24 记录的「凯撒+1 诱饵」更硬——关键 3 API 已被摘名。复用 r33 框架 so 是安全的（它本就走 ClassFromNameScan/GetMethodScan/ImageOf 降级并已交付 ok=76），但**任何「按名解析」的新代码都不要再写**；`dynsym` 自解析（`debug.starry.nhsy2_dynsym`）继续保持默认关。
**待验证**：libil2cpp 的 DT_INIT（themis stub）是否在运行时把名字层还原回内存（若还原，dlsym 会变成可用）。本轮静态证据不足以定论：stub 内 48 处 `blr x8` 走函数指针表（RW 尾段 0x841e760），且**无 mprotect/mmap 导入**、只有 3 条 svc（openat/read/close），故「运行时解名」缺少直接证据；判据建议留到真机一条 `dlsym` 探针。

## 3. ② metadata（证据）

```
$ xxd -l 64 global-metadata.dat
00000000: af1b b1fa 1000 0000 7801 0000 6152 0500
          ^magic=FAB11BAF  ^version=0x10  ^0x178=376(=头部长度?)  ^0x55261
```
- 魔数 = **0xFAB11BAF**（标准 il2cpp metadata），version = **16**；但 `libunity.so` 内含 `6000.0.73f1`（Unity 6），Unity 6 的 metadata version 应为 31/33 ⇒ **头部 version 与引擎不匹配**，头部字段不可信。
- 名字层不可读：`mscorlib` / `UnityEngine` / `System.Runtime` / `SoulLevelConfig` / `UpgradeRules` / `GetLevelUpRequireExp` / `OnWeaponSoulDataChanged` / `ClientLoginUtils` 全部 **0 命中**；凯撒 +1 变体（`VojuzFohjof` 等）也 0 命中。
- 熵：head1M 6.375 / mid1M 5.389 / tail1M 6.204（非高熵加密，但也不是可读名字表）；抽样 ASCII 片段是半坏形态：`UN>TY_UDIT`、`NITf_ED)TORJ`、`nlo{ded`IScFneP`（疑似逐字节替换/位移的字符串堆）。
- 形态仍是 **单文件** `Managed/Metadata/global-metadata.dat`，未回退到 r33 之前的「decoy + System.ctor.dll-resources.dat」形态（`Managed/Resources/` 下只有正常的 `*-resources.dat`：mscorlib 337,563 B、Newtonsoft.Json 900 B 等）。

**结论（②）**：**只能运行时**。离线 dumper 会先卡在 version=16（结构按 v16 解析必错），且即便对上版本也没有可读的类型/方法名 ⇒ 拿不到 hook 所需的 method token/签名。需要类名/方法名时继续走「运行时 + ClassFromNameScan/GetMethodScan」路线（r29/r31 的按名定位口径仍然成立，因为它是运行时按名调 `GetMethodScan`，不依赖 metadata 静态可读性）。

## 5. 加固面（简版，未做项单列）

- libil2cpp 的 ELF **只有 5 个节**（.note.gnu.build-id/.dynstr/.dynamic/.shstrtab），段表 13 个 phdr、7 个 PT_LOAD；**INIT_ARRAYSZ=0，初始化走 `DT_INIT=0x8413eac`**（typical packer stub），尾段另有 0x8410000(RX,0x5ef0)/0x8415ef0/0x8416120 三个小段，其中 0x841e760 是 stub 用的全局函数指针表。
- stub 内明文串（实测）：`libthemis-v8.so`（0x84116a3）、`libthemiv8.s`（0x84116b8，诱饵名）、版本串 `7.0.6 (git@git.xindong.com:GameSecurity/themis-llvm.git a03763f395a5db516118de260e8b0e6e7b4a4858)` ⇒ 游戏侧加固＝**心动自研 themis-llvm 7.0.6**（控制流扁平化），与 r33 同源，**无新增第三家保护**。
- **名字撞车的更正**：`libthemis.so` / `libthemis-v8.so` **不是**心动 themis，而是 **TapTap SDK 的 ThemisLite + 崩溃捕获**：导出 `Java_com_taptap_sdk_themis_lite_ThemisLite_zXq3tVwP`/`vQe8bYsT`、`JNI_OnLoad`、`crash_signal_handler_org`、`bridge_crash_signal_handler`、`ReportExceptionEx`、`set_adid`；`libthemis-v8.so` 导入 **sigaction / sigprocmask / pthread_sigmask / prctl / mmap / mprotect / syscall / dl_iterate_phdr**，且 `FLAGS_1 = NOW NODELETE`。⇒ 「themis 会顶掉信号处理器」的静态依据首次落到具体库与具体 API（信号链被 TapTap ThemisLite/CrashSight 抢占，而非游戏加固），对 r27 的 `RearmFaultGuard` 结论是**加强**，不是推翻。
- `libpuerts.so`（新增 17 MB，V8/JS 绑定）：NEEDED 仅 liblog/libm/libdl/libc，INIT_ARRAY 6 项，未见信号相关导入 ⇒ 对 hook/信号链无新增风险面。

## 7. 出包前必须先解决（本轮新增/复核）

1. **补 `libc++_shared.so`（1,794,776 B / ed7aeec9…）到 `lib/arm64-v8a/`**，否则框架 so 不能加载——这是复用 e5811424… 的硬前提。
2. 解析链保持**只走降级**（ClassFromNameScan/GetMethodScan/ImageOf），`dynsym` 自解析默认关；不要新增任何 `dlsym("il2cpp_*")` 依赖。
3. 沿用 safemask=4（reprotect 关）；信号链需重新 `RearmFaultGuard`——因为 TapTap ThemisLite/CrashSight（`bridge_crash_signal_handler`）仍会抢链头。
4. metadata 不作为离线 hook 依据；类/方法定位一律运行时按名。
