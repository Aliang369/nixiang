# 造梦西游·黎尤浩劫篇 1.1.0 — 反检测 / 上报 / 存档 面评估

> 日期：2026-09-29 · 对象：官方 4399 包 `com.xm4399.zmxy6hj` 1.1.0/vc3（底包 md5 `d5ca1909…`）
> 方法：**纯静态**（APK 静态拆解 + 6 个 dex 全量 baksmali + native `strings`）。
> 所有结论标注证据来源；读不到的部分（加密 JS、服务端）明确标「待验证」。
> 相关：[造梦西游_星光复刻_20260929.md](造梦西游_星光复刻_20260929.md)

## 0. 先给结论

1. **客户端确实有设备风控，而且被主动初始化**：4399 运营 SDK 会 `SmAntiFraud`（数美风控）启动，采集
   adid/bssid/cell/network/oaid/ssid/wifiip，channel=`4399`；另有**腾讯图灵盾**（`libturingmfa.so` +
   `com.tencent.turingfd.sdk.mfa.*`，内含 TracerPid 检测）与 FN SDK 的**模拟器检测**（`MnqUtil` 一长串模拟器包名）。
   本机是 KernelSU root + 注入包，**正落在这些 SDK 的检测面里**。
2. **签名校验已被挡住（已验证）**：包里多个模块会读 `PackageInfo.signatures`，星光 `SignSpoof` 运行时命中
   `spoof hit pkg=com.xm4399.zmxy6hj md5=c07390da1d165f6d004588f7d3847d77` → Java 侧统一看到官方证书。
3. **崩溃上报是活的，且是最直接的自曝通道**：`AppActivity` 直接调 `CrashReport.initCrashReport(...)`，
   包内带 `libBugly_Native.so`、`libBugly-idasc.so`。我们注入的 `libstarry_magic.so` 一旦崩，栈里就带这个名字。
4. **4399 云存档没启用**：`CloudArchive`/`ApiCloudArchive` 在包里但**找不到任何调用方**（死代码）。
   本作是联网游戏，存档与结算在游戏服；所以「存档上传」的封号风险是**服务端数值校验**，不是 4399 平台侧。
5. **最大的封号风险不在客户端检测，而在服务端行为**：伤害倍率/无敌直接改变结算数据（伤害、耗时、掉落、排行）。
   客户端怎么藏都挡不住服务端判定 —— 功能开得越猛、场景越"公开"（排行/成就/组队），被判定概率越高。

排除的同名坑（避免误报）：

- `libcocos2djs.so` 的 `se::Object::isRooted()` 是 Cocos 引擎的 **GC 根判定**，与 root 检测无关。
- `PatternsCompat` 里的 `frida` 命中来自 IANA 顶级域名正则，不是检测。
- `CGManager` 遍历 APK 条目（跳过 `META-INF/`）**不算摘要**（无 MessageDigest），是 FN SDK 的资源/更新逻辑。

## 3. 可选方案（**需你点名才做**，属新增功能，默认不动）

| 方案 | 作用 | 成本/风险 |
|------|------|-----------|
| A. 静默上报（Bugly / 4399 埋点 / 数美） | 让上报不发出 | 成本低；**风险中高**：数美是支付/登录风控链的一环，缺上报或上报异常本身可能触发风控标记；心跳缺失也可能异常 |
| B. 反检测应答（数美/图灵盾 root·hook·调试判定返回"干净"） | 降低设备风控命中 | 成本中（类名方法名混淆，需按特征定位）；只覆盖已知路径，SDK 升级即失效 |
| C. 隐藏注入痕迹 | 抗 APK 条目/哈希类校验 | 成本高（需保证 dex/so 不被条目级比对发现，多数方案治标） |
| D. 功能使用纪律（**性价比最高**） | 不产生服务端异常数据 | 零成本：倍率默认压低（2–5），避开排行/成就/组队/PvP 场景开无敌与百倍，不连续刷结算异常的关卡 |
| E. 崩溃自曝治理 | 避免 mod 异常被上报 | 成本低：确认/加强 mod 侧异常兜底，不让 `libstarry_magic.so` 出栈 |

## 4. 待验证（静态确认不了）

1. **游戏服接口与结算逻辑**：在加密 JS（`assets/main/index.jsc`，XXTEA）里，静态读不到 → 是否有「战斗结算校验 / 客户端完整性上报」需要运行时验证。
2. **数美/图灵盾实际是否发请求、发到哪**：需运行时抓网络（`fp.fengkongcloud.com` 之类）才能证。
3. **native 层是否有反调试/完整性校验**：`libsecsdk.so` 等未做深反汇编，目前只是"无特征串"。

## 5. 建议的最小验证（低成本）

1. 运行时抓一次冷启动的网络请求（需你同意用抓包/`tcpdump`），列出发往 数美/Bugly/4399 analy 的请求，确认上报是否真的发生（而不是 SDK 只在包里）。
2. 若要屏蔽，**逐项点名**（例如"只屏蔽 Bugly 崩溃上报"），避免连带打坏登录/支付风控链。
