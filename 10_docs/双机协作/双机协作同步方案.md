## 1. 总体架构：本地双仓 + git 当脊梁 + 局域网只同步大头

```
┌─────────────────────────────┐         ┌─────────────────────────────┐
│  Mac  · 主机名 mac           │         │  Win  · 主机名 win           │
│  根: /Users/aliang/Documents │         │  根: E:\nixiang              │
│      /nixiang                │         │  Git Bash 中 = /e/nixiang    │
│                              │         │  MSYS 兼容垫片映射            │
│  ┌────────────────────────┐  │         │  /Users/aliang/Documents/    │
│  │ 本地完整仓（同一份）    │  │         │  nixiang → E:\nixiang        │
│  └────────────────────────┘  │         │  ┌────────────────────────┐  │
└──────────┬───────────────────┘         └──┴────────────────────────┘──┘
           │                                          │
           │  ① 小文本层：git（唯一通道）              │
           ├────────────► GitHub: Aliang369/nixiang ◄─┤
           │              （可选：Win 上建裸仓当主 origin，        │
           │               走内网 ssh:// 推送，GitHub 降级为备份）  │
           │                                          │
           │  ② 大头层：Syncthing / rsync（局域网，绝不进 git）    │
           ├──────────────────────────────────────────┤
           │     02_apks · 08_output · 06_dumped(二进制) · 07_patched
           │
           │  ③ 工具层：各装各的，永不共享
           └     01_tools · 05_ida · NDK · IDA/Ghidra 工程
```

**三层各有各的通道，永远不要交叉：**

| 层 | 走什么 | 绝对不能做什么 |
|---|---|---|
| 小文本层（`04_scripts` `10_docs` `mod菜单` 源码 `skill` `06_dumped` 文本） | **只走 git** | 不要把 `.git/` 放进任何同步器（Syncthing/iCloud/OneDrive）——会产生 `index.lock` 残留和索引损坏 |
| 大头层（4-6 GB 可再生/用户手工管理的产物） | Syncthing 或单向 rsync，或干脆各机重生成 | 不要 `git add -f` 进去（历史上 `.git` 曾膨胀到 279 MB） |
| 工具层（`01_tools`、`05_ida`、IDE 工程、设备状态） | 各机独立 | 不要共享（平台不兼容 + 体积大 + 有锁） |

## 2. 机器角色与文件归属（硬规则）

### 2.1 一机一游戏（最重要的一条）

> 同一轮里，**一个游戏的目录只允许一台机器写**。跨机同时改 `04_scripts/{游戏}/` 或 `10_docs/{游戏}/` 是唯一会造成真实合并冲突的场景。

这与 `AGENTS.md`「多代理协作先划定文件归属」是同一条规则，只是从"多代理"扩展到了"多机器"。

开工前明确写出：

```
本轮归属：
  mac  → 游戏 A、游戏 B
  win  → 游戏 C
  （10_docs/_state/current.md 与 games/*.md 由第一次 pull 的那台机器写，另一台只读）
```

### 2.2 状态索引的单一写者

`10_docs/_state/current.md` 和 `10_docs/_state/games/{游戏}.md` 每轮都要写，是**最高冲突概率的文件**。
规则：**谁本轮动了某个游戏，谁就写它的摘要；另一台机器对它只读**。真要跨机改，先 `git pull --rebase`，改完立刻推。索引行 ≤400 字符（`AGENTS.md` 已有硬上限）也顺带降低了冲突面。

### 2.3 设备归属

- 一台手机同时只由一台电脑做 adb / frida 操作，避免 `adb server` 抢占和 frida-server 版本错乱。
- 各机在 `~/.bashrc` 里固定自己的设备：`export ANDROID_SERIAL=<serial>`。
- `.device_serial`（17 个，已被跟踪）是**机器私有状态**，不该入库，处理见 §8。

## 3. 命令与终端的分流规则（🚨 最容易误导的部分）

### 3.1 终端选择：三选一，不能乱用

| 标记 | 环境 | 用在哪 |
|---|---|---|
| 【Mac · zsh】 | macOS 默认交互 shell | 交互命令；仓库 `.sh` 一律用 `bash <脚本>` 显式调用 |
| 【Win · Git Bash】 | `C:\Program Files\Git\bin\bash.exe` | ✅ **`04_scripts/**/*.sh` 的唯一合法执行环境** |
| 【Win · PowerShell 管理员】 | 仅在初始化/系统设置时 | 跑 `win_bootstrap.ps1`、改 PATH、建 junction |

**红线：**
- ❌ 不要用 PowerShell 跑 `.sh`。`.\xxx.sh` 会走文件关联或被拒绝执行，报错与真实原因无关。
- ❌ 不要用 `cmd.exe` 跑 `.sh`。
- ⚠️ WSL2 是另一个选择，但**不推荐作为默认**：仓库若放 `/mnt/c/` 走 9p 文件系统会慢数倍；放 WSL 内部又拿不到 Windows 侧的 adb（USB 需 usbipd-win）。**结论：Git Bash 优先，WSL 只在某个游戏必须 Linux 工具链时才用。**

### 3.3 三条会静默出错的坑（务必记牢）

1. **bash 版本方向是反的。**
   Mac 上跑的是 **bash 3.2.57**（Apple 自带），Win 的 Git Bash 是 **bash 5.x**。
   在 Win 上写脚本很容易顺手用 `mapfile` / `readarray` / `declare -A` / `local -n` / `${v^^}` / `;;&`，**在 Win 上跑得好好的，回到 Mac 整套脚本直接跑不起来**。
   仓库已有 `04_scripts/_common/preflight.sh` 的 **bash 3.2 门禁**专门抓这个（和"`$VAR` 紧跟中文导致变量名被并进去"的 unbound variable 陷阱）。
   → **规则：Win 上任何 `.sh` 改动，合回 main 之前必须在 Mac 上跑一次 `preflight.sh`。** 已知现状：有 7 个文件在用 `mapfile`（待专项核查）。

2. **`md5` ≠ `md5sum`。**
   仓库里 `md5` 出现 2166 次、`md5sum` 41 次、`shasum` 144 次 —— 三套并存。Win 的 Git Bash **没有 `md5`**，会 `command not found`。校验脚本时不要照抄 Mac 的命令行。

3. **`stat -f` 与 `stat -c` 参数完全不兼容。**
   87 个文件用 BSD 的 `-f`，35 个用 GNU 的 `-c`。**在错的那台机器上不会报错，会返回垃圾字符串**，然后被写进 hash 台账 —— 这类错误最难查。跨机改脚本时优先改成 `shasum -a 256`（两机都有）或本地封装。

## 4. 让仓库在 Win 上能跑：三个兼容垫片

### 4.1 `.gitattributes`（已落地）

已新增在仓库根。作用：锁定 `*.sh` 等文本为 **LF**、Windows 原生脚本为 CRLF、APK/dex/so/i64 等为 binary。
配套两台机器都必须执行（`win_bootstrap.ps1` 已自动做）：

```bash
git config --global core.autocrlf false
git config --global core.ignorecase false      # 关键：防止"只改大小写的重命名"静默不同步
git config --global core.longpaths true        # Windows 必须
git config --global core.quotepath false       # 中文路径正常显示
```

> ⚠️ 新增 `.gitattributes` **不改动任何已有 blob**（本轮实测：加完后 `git status` 没有任何新变化，原有 2 个已修改文件 mtime 早于本文件，是真实内容改动）。
> 若日后出现大批"已修改"，先查 `git ls-files --eol | grep -E 'i/(crlf|mixed)'` 逐个核对来源，**不要**盲目 `git add --renormalize .`（会造出巨型 diff 掩盖真实改动）。
>
> 已知需要**豁免换行转换**的目录（已写入 `.gitattributes` 末尾的例外段，`-text`）：`06_dumped/**/apk_assets/**`、`06_dumped/**/il2cpp_dump_*/**`、`10_docs/**/apk_assets/**`、`10_docs/**/lua_dump/**`。这些是 dump / 解包的第三方原始字节，被 normalise 会破坏与真机资源的可比性。**以后新增同类目录，同样要加豁免。**

### 4.2 MSYS 兼容垫片：让 8525 处 Mac 绝对路径在 Win 上原样生效（⚠️ 本方案的核心）

**问题**：8525 处字面量 `/Users/aliang/Documents/nixiang` 写死在 364 个脚本里。Win 上 Git Bash 的 `/` 指向 Git 安装前缀，因此这个路径会被解析成
`C:\Program Files\Git\Users\aliang\Documents\nixiang`（不存在）→ 脚本一开头就 `cd` 失败。

**为什么不用"批量替换成 `$NIXIANG_ROOT`"**：8525 处改动会产生巨型 diff，而且后续每条从 Mac 来的提交都要重新合并，风险远高于收益。留作第二阶段的独立专项（§8）。

**推荐做法：一次性的目录联接（junction），零 diff。**

在 Win 上以**管理员 PowerShell**执行：

```powershell
# 1) 真实仓库放短路径（不要有空格，不要放 OneDrive/iCloud 里）
# E: 必须是本机固定硬盘；目标目录由 git clone 自动创建，无需先 mkdir
git clone git@github.com:Aliang369/nixiang.git E:\nixiang

# 2) 在 Git 安装前缀下造出 Mac 的同名路径，联接到真实仓库
$gitRoot = Split-Path (Split-Path (Get-Command git).Source -Parent) -Parent
New-Item -ItemType Directory -Force -Path "$gitRoot\Users\aliang\Documents" | Out-Null
New-Item -ItemType Junction -Path "$gitRoot\Users\aliang\Documents\nixiang" -Target "E:\nixiang"
```

做完后，**所有写死 Mac 路径的旧脚本在 Win 上无需修改即可运行**：

```bash
# 【Win · Git Bash】——完全照抄 Mac 文档里的命令，不改一个字
cd /Users/aliang/Documents/nixiang && git status -sb
bash 04_scripts/_common/preflight.sh 04_scripts/_common/env.sh
```

`win_bootstrap.ps1` 的第 6 步会自动做这件事（`-SkipJunction` 可跳过）。

注意事项：
- **`E:\nixiang` 所在的 E: 盘必须是本机固定硬盘**（内置 SSD/HDD）。U 盘、移动硬盘、网络映射盘都不行：junction 会随盘符消失而失效，且 git / NDK / Gradle 在可移动或网络卷上会慢到不可用。`win_bootstrap.ps1` 第 0 步会用 `Win32_LogicalDisk.DriveType` 检查并警告。
- 写在 `C:\Program Files\Git\` 下需要管理员。若不想提权，把 Git 装成**用户级**（`winget install Git.Git --scope user`），路径变成 `%LOCALAPPDATA%\Programs\Git`，脚本第 5 步会自动识别。
- Git for Windows 大版本升级偶尔会重建安装目录 → **升级后重跑 `win_bootstrap.ps1` 即可恢复**。
- 两台机器上同一个脚本的"真实路径"不同，但**字面量相同**，所以文档、日志、`pipeline.json` 里的路径都能互相看懂 —— 这是选它而不是选 sed 替换的主要原因。

### 4.3 `env.sh` 双机分支（✅ 2026-10-01 已应用，见 `env.sh.win.patch`）

`04_scripts/_common/env.sh` 是全仓共享环境入口，但里面有三处 macOS 专有逻辑：

| 位置 | 现状 | Win 上的后果 |
|---|---|---|
| python 解析 | `/opt/homebrew/bin/python3.11` | 解析不到 → fallback 到系统 python |
| SDK 默认值 | `$HOME/Library/Android/sdk` | 目录不存在 → `NIXIANG_BUILD_TOOLS` 为空 |
| 存在性判定 | `[[ -x "$dir/zipalign" ]]` | Windows 是 `zipalign.exe` / `apksigner.bat`，`-x` 不做扩展名补全 → **恒为假** |
| java 17 | `/usr/libexec/java_home -v 17` | 命令不存在 |

好消息：`env.sh` 里的
`NIXIANG_ROOT="$(cd "$(dirname "${BASH_SOURCE[0]}")/../.." && pwd)"`
**已经是可移植写法** —— 这是全仓唯一正确的根路径来源。**新脚本一律这样取根，禁止再写字面量路径。**

补丁内容、实际合入的差异、Mac 侧实测结果和两机验证命令都写在同目录 `env.sh.win.patch`。

**Mac 侧回归验证（2026-10-01，改动后实测）**：

```bash
bash -c 'source 04_scripts/_common/env.sh; echo "$NIXIANG_HOST|$NIXIANG_PYTHON|$NIXIANG_BUILD_TOOLS|$NIXIANG_ZIPALIGN|$NIXIANG_APKSIGNER|$NIXIANG_JAVA17"'
# mac|/opt/homebrew/bin/python3.11|.../build-tools/36.0.0|.../zipalign|.../apksigner|（空）
bash 04_scripts/_common/preflight.sh 04_scripts/_common/env.sh   # PASS（退出码 0）
```

⚠️ `NIXIANG_JAVA17` 在 Mac 上**本来就是空的**，不是这次改动造成的回归：本机 `JAVA_HOME` 已指向
`~/Library/Java/JavaVirtualMachines/jdk-17.0.2.jdk/Contents/Home` 且 `java -version` 已是 17.0.2，
原版判断条件不成立；全仓也没有第二个文件用到 `NIXIANG_JAVA17`。**Win 上它必须非空**（那是新分支要干活的地方）。

### 4.4 Mac 命令垫片：不动机器上任何一行脚本

体检发现老脚本大量直接用 macOS 自带命令，Win 的 Git Bash 上没有对应物：

| Mac 命令 | 调用点 | Git Bash 上的情况 |
|---|---|---|
| `md5 -q <file>` | **512 处** | **没有 `md5`**（只有 `md5sum`）→ `command not found`，脚本拿到空值继续跑 → 静默出错 |
| `stat -f %z` | 16 处 | `stat` 是 GNU 的，`-f` 含义不同 → 报错或给出垃圾值 |
| `stat -f %Sm` | 1 处 | 同上 |
| `shasum -a 256` | 234 处 | Git Bash 通常自带 `shasum`；缺失时需兜底 |
| `stat -c %s`（GNU 写法） | 35 处 | ✅ 原生可用 |

**处理方式：不去改仓库里的 2166 处调用，而是在 Win 的 `~/.bashrc` 里把这三个命令垫成函数**
（`win_bootstrap.ps1` Step 5 写入，Step 8 自检）。理由：

1. 零 diff —— 仓库里一行不改，Mac 侧完全不受影响，也不会产生第二个机器永远要重新对齐的巨型提交；
2. 无 hash 漂移 —— `_state`、装机记录里已经存了计算好的 **md5** 值，把它们改成 sha256 会让历史值全部对不上；
3. `export -f` 让 `bash 04_scripts/xxx.sh` 这类**不读 `.bashrc` 的非交互子 shell** 也继承垫片。

**已在 Mac 的 bash 3.2.57 上做真实验证**（用桩 `md5sum` + 真实 `md5` 对照）：

| 检查 | 结果 |
|---|---|
| here-string 提取出来的 61 行 `bash -n` | ✅ 语法通过 |
| 垫片 `md5 -q <1 字节文件>` | `9dd4e461268c8034f5c8564e155c67a6` —— **与真 mac `md5 -q` 逐字节一致** |
| `md5 -r` / `stat -f %z` | `hash  file` / `1` |
| `bash -c "md5 -q $f"` 子 shell 继承 | ✅ 有输出，证明 `export -f` 在 bash 3.2 下有效 |
| `stat -f %Sm`（1 处调用） | ⚠️ NOT PROVEN：Mac 的 `stat` 是 BSD，测不了 GNU 分支；Win 上是 GNU stat，理论可用 |

> 注意：垫片只在 **Git Bash** 里生效。**不要在 PowerShell 里跑 `.sh`**，那里什么都没有。
> 若某个脚本被 `sh script.sh` 调用（而不是 `bash script.sh`），垫片函数不继承 —— 现状 shebang 全是
> `#!/usr/bin/env bash`，所以按 §3.1 用 `bash xxx.sh` 就没事。

## 6. 日常 SOP

### 6.1 开工（每台机器，每轮开始）

```bash
# 【Mac · zsh】 或 【Win · Git Bash】——同样是这个写法
cd "$NIXIANG_ROOT"
git status -sb                 # 必须干净；不干净先处理，不要 pull
git pull --rebase --autostash
git log --oneline -5           # 确认拿到了另一台机器的提交
```

### 6.2 收工（每台机器，每轮结束）

```bash
git -C "$NIXIANG_ROOT" status --porcelain          # 检查有没有漏掉的改动
git -C "$NIXIANG_ROOT" add <本机归属范围内的文件>   # 白名单提交，禁止 git add -A
git -C "$NIXIANG_ROOT" commit -m "<游戏>: <做了什么>"
git -C "$NIXIANG_ROOT" push
```

Mac 上收尾继续走现成口令（`archive_scoped_git.sh` 默认已推送）：
`收尾+正式包+清理+git`。

### 6.3 冲突处理

| 场景 | 处理 |
|---|---|
| `pull --rebase` 报 `10_docs/_state/*.md` 冲突 | 按 §2.2「谁本轮动这个游戏谁赢」，另一台的改动通常是"索引行"，手工合并两行即可，**别用 `-X theirs/ours` 一把梭** |
| 冲突涉及 `04_scripts/{游戏}/**` | 说明 §2.1 被违反了。**停下**，两台机器各自说明改了哪一段，人工合并后由一台机器重跑 `preflight.sh` |
| 冲突涉及 `install_result*.json` / `.device_serial` | 这是机器私有状态，**两台都不该改它**。取本机版本，并按 §8 把它们移出跟踪 |
| push 被拒（远端有新提交） | `git pull --rebase --autostash` 后再 push。**永不 `push --force`** |
| network / 网络失败 | 保留本地提交并报告，不重试覆盖 |

### 6.4 大头层同步（Syncthing，按需）

只在确实需要跨机看同一批 APK/产物时才开。**关键配置：文件夹类型用 Send Only / Receive Only，不要用 Send & Receive**——这样不会产生 `.sync-conflict-*` 文件。

```
文件夹 1: E:\nixiang\08_output      ↔  /Users/aliang/Documents/nixiang/08_output
文件夹 2: E:\nixiang\02_apks        ↔  /Users/aliang/Documents/nixiang/02_apks

Node A(mac): Send Only      Node B(win): Receive Only
忽略模式（两台都填）：
   .git/**, **/.git/**, **/.gradle/**, **/build/**, **/obj_*/**, **/libs_*/**,
   **/jniLibs/**, **/__pycache__/**, **/*.pyc, **/pipeline.lock, **/*.tmp
```

**绝不同步清单（放任何同步器里都会出事）**：`.git/`、`01_tools/`、`05_ida/`、`mod菜单/**/build/`、`**/.gradle*`。

按 `AGENTS.md` 的现行政策，其实**更省事的做法是不开 Syncthing**：APK 用完即删（只在 `10_docs/_state/底包再获取台账.md` 登记），dump 各机重生成，`08_output` 由用户手工管理。**建议先按不开同步跑两周，真的被"另一台没有这个包"卡住再开。**
