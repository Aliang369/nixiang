> 2026-09-23 凌晨。会话按用户要求暂停（"还是闪退，先暂停总结吧，明天再搞了"）。
> 本文只记录**可复现的硬证据 + 已入包的改动 + 明日按优先级要做的事**。

## 一、结论（CLAIM / VERDICT / EVIDENCE）

### CLAIM 1：直装包能装、能启动、菜单能挂，但启动 ~13s 进程被信号杀死（3/3 复现）
- VERDICT：**已确认**
- EVIDENCE：
  - `[quarantine] 信号隔离启动 pid=25892` → `StarryMagic … RegisterNatives 19/19 全部成功` → `MenuService: overlayVisible=true attached=true`（悬浮窗正常）
  - `E/Mod_Menu: [crash] sig=11(SIGSEGV) code=1(SEGV_MAPERR) fault=0x18a44 pid=25892 tid=26566`
  - `I/ActivityManager: Process com.blade.bd (pid 25892) has died: fg TOP` / `handleProcessKilled`
  - 三次复现：pid 20727(tid 21475) / pid 22619(tid 23727) / pid 25892(tid 26566)，崩溃时刻都在启动后 13.2~14.2s。

### CLAIM 2：崩溃与我们的 Lua 玩法层（Jjdm 模块）无关
- VERDICT：**已确认**
- EVIDENCE：全程 `[Jjdm]` 日志 **0 条**。框架主循环 `MainModern.cpp:250` `if (!session_live()) { forceClear; sleep(0.5); continue; }`，而 `session_live()==g_rt_ok`（授权 grant 通过才为真）。**未授权 ⇒ Tick 从不执行 ⇒ `Jjdm_TryInit` 从未被调用 ⇒ 没有装任何 Dobby hook、没有注入 Lua。**

### CLAIM 3：崩溃现场是「控制流跳到未映射地址 0x18a44」，不是空指针读
- VERDICT：**新证据（今日新增 ucontext 现场日志后才拿到）**
- EVIDENCE：`[crash] fault-pc=0x18a44 <unmapped> lr=0x18a44 sp=0x75a7a21ddc fp=0x75a7a22440 fault_addr=0x18a44`
  - `pc == lr == fault_addr == 0x18a44` → 典型 `ret` / `br x30` 跳到坏 LR（若是指令取指失败，PC 就是那个坏地址）。
  - `dladdr` 判定 0x18a44 **不属于任何已加载模块**（该进程所有模块都在 0x7xxx 高地址）。
  - 三次复现地址**逐字节一致**（0x18A44 = 100932），更像「故意跳野地址的 kill switch」，而不是随机指针损坏。
  - ⚠️ 旧日志里的 `sender_pid=100932 sender_uid=0` 是 siginfo 的 union 别名（= 0x18A44），**不是真发送者**；早期把 `si_pid` 当发送者是误读。

### CLAIM 4：信号链 = 内核 → libbytehook.so → libsigchain.so `art::SignalChain::Handler` → 我们
- VERDICT：**已确认（反汇编）**
- EVIDENCE：
  - `#01 libsigchain.so+0x60b8`：`libsigchain.so` 符号表 `_ZN3art11SignalChain7HandlerEiP7siginfoPv @0x5c38`，`0x60b4 blr x8` 调链上处理器，`0x60b8` 正是它的返回地址。
  - `#02 libbytehook.so+0x93a8`：该处 `0x93a4 blr x8` 的返回地址，前置逻辑为 `ldrb w8,[x25]; tbnz w8,#2 → SA_SIGINFO 分支` + `ldr x8,[x25,#8]; cmp x8,#2; b.lo`（<2 即 SIG_DFL/SIG_IGN 跳过）→ **就是在"调用先前保存的处理器"**；`libbytehook.so` 动态符号含 `sigsetjmp/siglongjmp/sigaction/sigprocmask/sigfillset`。
  - `libbytehook.so` 是**官方包自带**（`lib/arm64-v8a/libbytehook.so` 43536 B + `assets/g/wrappers/com.bytedance.android.gsdk.transplanted@bytehook@1.0.2-b0936434`），我方新增的只有 `libstarry_magic.so`。

### CLAIM 5：「记录后 return，让信号链继续」的修法**不足以**救活；故障被重放 6 次仍无人处理
- VERDICT：**已确认（真机实测，今晚最后一次运行）**
- EVIDENCE：`[crash] 让信号链继续（第 1/6 次）…（第 6/6 次）sig=11 tid=26566` ×6 → `[crash] 已达让行上限，交给默认处理（重发信号 11）` → `has died`。
- 推论：**不是 bytehook 的"可恢复探针"**——bytehook 与 sigchain 都不认这个故障，回到内核后故障指令被反复重放。⇒ 是真的野跳。

## 二、今日已入包的改动（都已编译进当前 APK）

1. `mod菜单/starry-mod-menu/app/src/main/jni/Games/CrashTrap.cpp`

2. `Games/JjdmMod.cpp`

## 五、教训（别重犯）

- **不要用 frida 的 `Process.attachModuleObserver` onAdded 里做 `Interceptor.*`**（loader 锁内调用 → 进程早期即死/挂）。本次 frida「中和 CrashTrap」实验因此无效，还叠加了「frida spawn 的进程 + 系统/AMS 另起一个进程」双进程互相干扰。要做同类实验请用 `am start` + attach，且只做读操作。
- 框架 `SignalQuarantine` 的 seccomp 过滤器拦了 `tgkill(131)/tkill(130)/kill(129)/rt_sigqueueinfo(138)/rt_tgsigqueueinfo(240)`（日志 `rc=0 errno=2`）⇒ 我们重发信号无效、**系统也不产生 tombstone**（`/data/tombstones/` 最新仍是旧的）。排查崩溃不要指望 tombstone。
- `.so` 被 `-w -s` + `-Wl,--gc-sections,--strip-all` 剥符号 ⇒ `llvm-addr2line` 无效，必须用 `-Wl,-Map=` 重链出 map 来定位地址归属。
- 本会话 `web_search` 不可用（`Command Code web search has no API key`）。
