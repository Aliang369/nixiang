# 经验卡：TapTap 验签弹窗与强制网页登录（改包法，2026-10-28 定案）

> 用户定案原话（2026-10-28）：「这套流程超级可以，**以后 taptap 签名校验和 tap 登陆的网页强制登陆都按照现在的方法去改包操作，不要再用我们之前的签名伪装的办法**」。
> ⇒ 跨游戏默认做法：**静态改游戏包体（dex 补丁）**，不再用 `SignSpoof.java`（白名单 + hook PackageManager + 隐藏 API 豁免）。
> 首个落地游戏：绿梦 1.0.5（TapSDK 4.8.2）。验证设备：小米 M2102K1AC / Android 14 user / 无 root。

## 为什么放弃运行时签名伪装

- `SignSpoof` 依赖 `VMRuntime.setHiddenApiExemptions`（隐藏 API 豁免）：userdebug（雷电）能过，**user 版真机必失败**——
  ```
  E StarrySignSpoof: exemptHiddenApis(meta) failed → InvocationTargetException
  ```
- 用户原话：「太吃设备环境」「很多游戏设备都漏过这个问题，只是之前我以为是游戏问题」。

## 两个位置（用户的分法，实测证实）

| 位置 | 现象 | 本质 |
|---|---|---|
| ① 签名校验 | 改签安装后弹「【tapsdk】…包名/签名…未正确配置」 | TapTap 服务端按 package + 证书 MD5 比对开发者中心配置；**失败会变成硬门闩**，不只是提示 |
| ② 登录方式 | ①过掉后点登录拉起 TapTap 客户端 | 由 SDK 的 handler 分支决定，改成 Web 即可，无额外校验 |

## 补丁一：掐掉验签弹窗 **并且**放行门闩（关键）

调用链（`classes2.dex`，TapSDK 4.8.2）：

```
TapStartUp → GatekeeperRepository（拉服务端配置）
  ├─ 失败 → gatekeeperError != null → showErrorToast(TapNetworkException) → 协程 $showErrorToast$1 → Toast + banner(tag=TapInitializer)
  └─ loadGatekeeperSuccess = false
InitializerServiceImpl（所有业务接口的统一入口）
  └─ isGatekeeperLoadedSuccessfully() == false → showGatekeeperError(); return false   ← 登录等全部静默失败
```

**只掐 toast 会变成"点了没反应"（静默失败）**——这是 2026-10-28 踩过的坑。必须两处都改：

1. `com/taptap/sdk/initializer/repository/GatekeeperRepository` → `isGatekeeperLoadedSuccessfully()Z` 恒返回 `true`
   ```smali
   .registers 2
   const/4 v0, 0x1
   return v0
   ```
2. （可选，防其它错误路径弹窗）`GatekeeperRepository.showErrorToast(TapNetworkException)` 方法体首插 `return-void`，
   **保留原 `.registers`**（改成小值会 smali 编译失败：`This method requires at least 3 registers`）。

## 补丁二：强制网页登录

```
com/taptap/sdk/login/internal/LoginActivityImpl：
  handler 数组 = [CloudLoginHandler, ClientLoginHandler]，逐个 canHandle() 选第一个，
  instance-of 决定 LoginEntrance（CLOUD / CLIENT / else⇒WEB）
```

把两处 handler 的**实例化**换成 `…/handlers/web/WebHandler`（4 行：`new-instance` + `invoke-direct <init>` 各两处），
`instance-of` 判断保持不动 ⇒ entrance 自动落 `WEB`。
`WebHandler.canHandle()` 恒 true、`getFragment()` → `WebLoginFragment`（WebView 登录）。
**不要**改 `instance-of`，否则 entrance 会被误判成 CLOUD/CLIENT。

## 附带：摘掉运行时签名伪装（dex 级，不动共享源码）

`com/starry/magic/StarryInitProvider.smali` 里 `invoke-static {}, Lcom/starry/magic/sign/SignSpoof;->install()V` 注释掉即可
（`SignSpoof.java` 本身不动）。验证：logcat 中 `StarrySignSpoof` 行数归零。

## 实测证据（绿梦，真机）

```
v30（摘 SignSpoof + showErrorToast no-op）：banner=0、SignSpoof=0、功能 state 正常、cage 正常
v31（+handler→WebHandler）：banner=0，但点登录无反应 ← 因为门闩仍未放行
v32（+isGatekeeperLoadedSuccessfully→true）：
  15:13:05 mCurrentFocus=com.taptap.sdk.login.ui.TapTapLoginActivity
  15:13:05 InputMethodManager: showSoftInput() view=android.webkit.WebView{… app:id/webview …}  ← 网页登录出来了
  15:13:11 TapTapLoginActivity paused → MainFragmentActivity resumed（这次是人为按返回）
```

## 排错方法论（重要，别再踩）

- **PowerShell 的 `Select-String -Path "...\**\*.smali"` 在 PS 5.1 不递归**，会给出"0 命中"的假阴性。
  查 smali 一律用 `grep` 工具（ripgrep）或 `Get-ChildItem -Recurse | Select-String`。
- smali 里中文可能是 `\uXXXX` 转义，也可能原文——两种都要搜；**服务端下发的文案**在 dex/arsc/so 里根本不存在（本例即是），
  所以"按文案搜代码"会白跑，应该按 **tag 常量**（如 `TapInitializer`）反查调用点。
- 找弹窗/错误出口的可靠手法：先 grep 日志 tag 常量 → 看 `showXxxError`/`showToast` 之类方法 → 顺 `InitializerServiceImpl` 这类统一入口找门闩。

## 适用范围与反例

- 适用：TapSDK 4.x（本例 4.8.2）Android 端，Kotlin + 混淆 `SourceFile` 的包结构。
- 反例/失效条件：TapSDK 升级大版本后类名与锚点会变（`GatekeeperRepository` / `LoginActivityImpl` 需重新核对）；
  若某游戏登录不走 `LoginActivityImpl`（例如直接用 C++ 层登录），本补丁二不适用。
- **雷电（LDPlayer14 / houdini）**：补丁都生效（banner=0、菜单与授权链正常），但游戏仍会在 12–33 s 被 FG 自杀带走
  （houdini 的 guest 退出不发 host syscall；seccomp 三层 arch——x86_64 231 / arm64 94 / i386 252——都拦不到，
  libc `_exit/exit/syscall` 钩子也拦不到）。**本方法解决的是"能进游戏"，不解决雷电上的反自杀**。

## 2026-10-29 增补：双轨方案（签名＝B 运行时替换；登录＝A 静态改包）· 暗影格斗3 实证

> 用户当轮指令原话（2026-10-29）：「**可以加按照你这个说的，等结束后记下来，后续就按照这个方案走，补全我们的新方法**」。
> ⇒ 本文件顶部「不再用运行时签名伪装」的口径按此**修正为分工制**：`SignSpoof` 类仍然删除、不得复活；
> 但**「换 `PackageInfo.CREATOR` 的签名杀手」（MT ApkSignatureKillerEx 形态）成为 TapTap/hoolai 类签名校验的现行首选**。

### 分工（一句话：结果类校验用 B，入口/流程类用 A）

| 要过的东西 | 用哪轨 | 依据 |
|---|---|---|
| 签名真伪（C# 常量比对、native `checkCopyright`、SDK 把证书 SHA-1 上报服务端） | **B 运行时替换** | 一次覆盖所有消费者，服务端看到的也是官方值；A 要逐点找，漏一处即弹窗 |
| TapTap 登录方式（唤起客户端 / 网页登录）、渠道 handler 选择 | **A 静态改包** | 属流程分支不是真假值；一个 action 常量即可（见下） |
| 加固壳 / ACE / SecShell 等 | **A**（或壳自带入口） | 改 Application 父类会打乱壳初始化顺序 |
| 直读 APK 文件自校验、v2/v3 签名块摘要 | **A**（B 无效） | 这类不经 PackageManager，只能改文件或改校验点 |

### B 的落地配方（暗影格斗3 1.45.3 实测通过）

1. **取官方证书 DER**：从官方 APK 的 `META-INF/*.RSA` 取 DER（本例 845B，`CN=sagely`），base64 备用（长度 ~1.1 KB）。
2. **放 killer dex**：MT `bin/mt/signature/KillerApplication193`（+ 内部 `$j`/`$l`）单独打成一个 `classesN.dex`；
   若其父类引用了原包里的壳类（本例 `com.wanda.sf3.wd.PkjNluikmwxGUJv`），把 `.super` 与构造里的
   `invoke-direct` 改成 `Landroid/app/Application;`。
3. **改父类挂载**：`androidx/multidex/MultiDexApplication.smali` 的 `.super Landroid/app/Application;`
   → `.super Lbin/mt/signature/KillerApplication193;`（游戏 Application 继承 MultiDexApplication ⇒ 构造期即装好，Manifest 不动）。
4. **门禁断言**（写进 `surgical_*`）：`classesN.dex` 回读含 `KillerApplication193` 且 `.super` 是 Application、含官方证书 base64；
   `classes5.dex` 回读含 `KillerApplication193` 引用；打包后 zip 内两份 dex sha256 == 工作副本。
5. **验收判据（关键）**：**连续 3 次冷启**都要 `InitSuccessCallBack`。只测一次会把「首启过、二启挂」当成成功。

### 为什么必须清缓存（这是自研简化版失败的唯一原因）

- 只替换 `PackageInfo.CREATOR` 不够：`Parcel` 按类名缓存 creator（`mCreators`/`sPairedCreators`），
  `PackageManager` 另有 `sPackageInfoCache`；不复位就仍拿到旧 creator。
- 实测对照（暗影格斗3）：自研「只换 CREATOR」版**首启成功、二启必弹「SDK init error」**；
  frida 抓 `ConvertUtil::appSignatures` 第二次启动仍返回改签证书 SHA-1 `82:1C:92:E4:…`。
  换成 MT killer（CREATOR + 三处清缓存）后 **3/3 冷启通过**。

### A 的落地配方（登录侧，本例最省事的一种）

- `classes.dex` 的 `com/taptap/sdk/login/internal/handlers/client/IntentHelper.smali`：
  `const-string p1, "com.taptap.sdk.action"` → `"com.tap12tap.sdk.action"`
  ⇒ 唤起 TapTap 客户端的 intent 永不匹配，登录自动落网页(H5)，也就绕开了客户端侧的调用方签名校验。
- 备选（上一版用过、更重）：把 `LoginActivityImpl` 的 handlers 换成 `WebHandler`；`TapSignKit.getSign` 恒返回官方证书 MD5。
  能只改 action 就别动 handler。

### 反面记录（别再走的路）

- 暗影格斗3 v6 四大静态补丁（`global-metadata.dat` 官方 SHA-1 常量、`TapSignKit.getSign`、`libcpp.so checkCopyright` 置 1、换 handler）：
  首启能过、**第二次启动 48 ms 即失败**（本地 C# 门闩过了，服务端仍看真实签名）。
- 结论：**同一链条不要双修**；签名侧只留 B，A 只改登录/入口那一段，否则失败无法归因。

### B 的挂载点：底包结构决定用哪种（2026-10-29 霓虹深渊2 实测通过）

killer 必须**在 Application 构造期**装好（ContentProvider 太晚、`Application.onCreate` 之后的校验已经取过签名），
所以「挂在哪」取决于底包的 `<application>` 与 dex 形态。三种形态按顺序判：

| 底包结构 | 挂载点 | 做法 |
|---|---|---|
| 有 `androidx/multidex/MultiDexApplication`（游戏 Application 继承它） | 改那个类的父类 | 暗影格斗3 配方：`MultiDexApplication.super → Lbin/mt/signature/KillerApplication193;`，Manifest 一点不动 |
| `<application>` **已有** `android:name`（指向游戏自己的 Application） | 让该 Application 继承 killer | 把游戏 Application 的 `.super` 改成 `KillerApplication193`（它自己原来继承 `Application` 时最省事） |
| `<application>` **没有** `android:name`（默认 `android.app.Application`），且无 MultiDexApplication | **自己造一个空壳挂上去** | ① killer dex 里加 `Lbin/mt/signature/SgKillerApp;`（`.super Lbin/mt/signature/KillerApplication193;`，只有一个空构造）② 解码 manifest，`<application ...>` 注入 `android:name="bin.mt.signature.SgKillerApp"`（保留原有 `appComponentFactory`）③ 重新编码二进制 AXML 再塞回包 |

霓虹深渊2 属**第三种**（底包 `<application>` 无 `android:name`、有 `appComponentFactory="androidx.core.app.CoreComponentFactory"`、
dex 里没有 `androidx/multidex`）。实测：3/3 冷启无崩溃、`[Login] TapTapSDK.Init done`、无验签弹窗。

配套注意：
- killer 的证书 base64 必须**从底包 `META-INF/*.RSA` 现取 DER** 再 base64（本游戏 674 B → 900 字符，按 76 字符 `\n` 折行），
  包名字串一并改；直接搬别的包里的 base64 等于给别人的证书做伪装，必挂。
- killer **运行期不打日志**（logcat 里 `grep -i signature` 恒 0 命中）⇒ 不能把「没日志」当「没生效」，
  判据只能用 TapSDK `Init done`、登录结果、有无验签弹窗。
- 出包基座可以是**上一个已交付的星光包**（保留 manifest 注入的 provider/service 与 `assets/certs/`），
  只替换 dex/so/manifest；但官方底包仍必须备一份用于：① 取证书 DER ② 门禁查12 的逐字节比对基准。
