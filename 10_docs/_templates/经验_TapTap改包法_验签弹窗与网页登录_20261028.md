# 经验卡：TapTap 验签弹窗与强制网页登录（改包法，2026-10-28 定案）

> 用户定案原话（2026-10-28）：「这套流程超级可以，**以后 taptap 签名校验和 tap 登陆的网页强制登陆都按照现在的方法去改包操作，不要再用我们之前的签名伪装的办法**」。
> ⇒ 跨游戏默认做法：**静态改游戏包体（dex 补丁）**，不再用 `SignSpoof.java`（白名单 + hook PackageManager + 隐藏 API 豁免）。
> 首个落地游戏：绿梦 1.0.5（TapSDK 4.8.2）。验证设备：小米 M2102K1AC / Android 14 user / 无 root。

## 为什么放弃运行时签名伪装

- `SignSpoof` 依赖 `VMRuntime.setHiddenApiExemptions`（隐藏 API 豁免）：userdebug（雷电）能过，**user 版真机必失败**——
  ```
  E StarrySignSpoof: exemptHiddenApis(meta) failed → InvocationTargetException
  ```
- 用户原话：「太吃设备环境」「很多游戏设备都漏过这个问题，只是之前我以为是游戏问题」。

## 两个位置（用户的分法，实测证实）

| 位置 | 现象 | 本质 |
|---|---|---|
| ① 签名校验 | 改签安装后弹「【tapsdk】…包名/签名…未正确配置」 | TapTap 服务端按 package + 证书 MD5 比对开发者中心配置；**失败会变成硬门闩**，不只是提示 |
| ② 登录方式 | ①过掉后点登录拉起 TapTap 客户端 | 由 SDK 的 handler 分支决定，改成 Web 即可，无额外校验 |

## 补丁一：掐掉验签弹窗 **并且**放行门闩（关键）

调用链（`classes2.dex`，TapSDK 4.8.2）：

```
TapStartUp → GatekeeperRepository（拉服务端配置）
  ├─ 失败 → gatekeeperError != null → showErrorToast(TapNetworkException) → 协程 $showErrorToast$1 → Toast + banner(tag=TapInitializer)
  └─ loadGatekeeperSuccess = false
InitializerServiceImpl（所有业务接口的统一入口）
  └─ isGatekeeperLoadedSuccessfully() == false → showGatekeeperError(); return false   ← 登录等全部静默失败
```

**只掐 toast 会变成"点了没反应"（静默失败）**——这是 2026-10-28 踩过的坑。必须两处都改：

1. `com/taptap/sdk/initializer/repository/GatekeeperRepository` → `isGatekeeperLoadedSuccessfully()Z` 恒返回 `true`
   ```smali
   .registers 2
   const/4 v0, 0x1
   return v0
   ```
2. （可选，防其它错误路径弹窗）`GatekeeperRepository.showErrorToast(TapNetworkException)` 方法体首插 `return-void`，
   **保留原 `.registers`**（改成小值会 smali 编译失败：`This method requires at least 3 registers`）。

## 补丁二：强制网页登录

```
com/taptap/sdk/login/internal/LoginActivityImpl：
  handler 数组 = [CloudLoginHandler, ClientLoginHandler]，逐个 canHandle() 选第一个，
  instance-of 决定 LoginEntrance（CLOUD / CLIENT / else⇒WEB）
```

把两处 handler 的**实例化**换成 `…/handlers/web/WebHandler`（4 行：`new-instance` + `invoke-direct <init>` 各两处），
`instance-of` 判断保持不动 ⇒ entrance 自动落 `WEB`。
`WebHandler.canHandle()` 恒 true、`getFragment()` → `WebLoginFragment`（WebView 登录）。
**不要**改 `instance-of`，否则 entrance 会被误判成 CLOUD/CLIENT。

## 附带：摘掉运行时签名伪装（dex 级，不动共享源码）

`com/starry/magic/StarryInitProvider.smali` 里 `invoke-static {}, Lcom/starry/magic/sign/SignSpoof;->install()V` 注释掉即可
（`SignSpoof.java` 本身不动）。验证：logcat 中 `StarrySignSpoof` 行数归零。

```
v30（摘 SignSpoof + showErrorToast no-op）：banner=0、SignSpoof=0、功能 state 正常、cage 正常
v31（+handler→WebHandler）：banner=0，但点登录无反应 ← 因为门闩仍未放行

```

## 排错方法论（重要，别再踩）

- **PowerShell 的 `Select-String -Path "...\**\*.smali"` 在 PS 5.1 不递归**，会给出"0 命中"的假阴性。
  查 smali 一律用 `grep` 工具（ripgrep）或 `Get-ChildItem -Recurse | Select-String`。
- smali 里中文可能是 `\uXXXX` 转义，也可能原文——两种都要搜；**服务端下发的文案**在 dex/arsc/so 里根本不存在（本例即是），
  所以"按文案搜代码"会白跑，应该按 **tag 常量**（如 `TapInitializer`）反查调用点。
- 找弹窗/错误出口的可靠手法：先 grep 日志 tag 常量 → 看 `showXxxError`/`showToast` 之类方法 → 顺 `InitializerServiceImpl` 这类统一入口找门闩。

## 适用范围与反例

- 适用：TapSDK 4.x（本例 4.8.2）Android 端，Kotlin + 混淆 `SourceFile` 的包结构。
- 反例/失效条件：TapSDK 升级大版本后类名与锚点会变（`GatekeeperRepository` / `LoginActivityImpl` 需重新核对）；
  若某游戏登录不走 `LoginActivityImpl`（例如直接用 C++ 层登录），本补丁二不适用。
- **雷电（LDPlayer14 / houdini）**：补丁都生效（banner=0、菜单与授权链正常），但游戏仍会在 12–33 s 被 FG 自杀带走
  （houdini 的 guest 退出不发 host syscall；seccomp 三层 arch——x86_64 231 / arm64 94 / i386 252——都拦不到，
  libc `_exit/exit/syscall` 钩子也拦不到）。**本方法解决的是"能进游戏"，不解决雷电上的反自杀**。
