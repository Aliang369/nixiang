## 2. 观察、解释与候选经验

- **观察事实**：
  1. APK 内 `ScriptingAssemblies.json` 列有 `Game.dll`、`Main.dll` 等业务程序集，但登录前的两次内存 dump 里**只有第三方库/BCL 的 BSJB（17 个）**，无任何业务类型名。
  2. 用户登录进游戏后，同一进程再 dump：出现 HybridCLR 解释器结构与业务类型名表（如 `AdventureCatchRate`、`AdventureEventCatchLumi*`）。
  3. **但业务程序集的原始 PE 字节仍不在堆里**：对同一区间做 BSJB + MZ 反查 carve，得到的仍是那 17 个第三方库，业务程序集 carve 不出来。
  4. 最终拿到业务程序集的路径是：解密远端下发并缓存的加密 bundle（自定义 `LGEB` 容器）→ 取出 `Game.dll`（21,086,720 B）。
- **候选解释 H1**：业务载体（热更程序集/脚本）在登录或热更完成后才从远端拉取并加载；加载形态由运行时转换（HybridCLR 解释器结构），**原始 PE 可能被释放**，因此"已加载"不等于"能 carve 出 PE"。
- **替代解释 H2**：只是 dump 时机或区间没覆盖（进程/区间选错）。对照组：同一进程登录前后抓相同区间，业务符号计数由 0 变正，H2 被排除。
- **拟提炼的经验**（带前提/动作/预期）：
  - 前提：业务逻辑不在主二进制里（HybridCLR 程序集、xLua、Cocos JSC、远端 Addressables bundle 等热更载体）。
  - 动作 1（门禁）：在开始 dump/抓点前，先做**载体符号探针**，在 dump 里搜目标载体的魔数或已知符号（BSJB、业务类型名、脚本名、jsc/UnityFS 头）。若只有引擎与第三方库符号，判定"载体未加载完成"，先去确认游戏内状态（是否登录、是否进到目标场景、热更是否完成），**不要在此状态深挖保护层**。
  - 动作 2（分流）：确认已加载后，若业务 PE 仍 carve 不到，直接转"加密载体离线解密"路线，不要继续扩大堆扫描范围。
  - 预期：省掉整轮无效 dump 与保护层逆向；把定位成本压到"确认状态"这一句话。
- **适用范围**：任何"业务逻辑在热更载体"的 Unity/IL2CPP/HybridCLR、xLua、Cocos 游戏，且具备 root 只读内存访问；与保护品牌无关。
- **不适用范围 / 已知例外**：业务逻辑全在 AOT 主二进制或 DEX 内的游戏（本条不构成前置）；纯服务端逻辑、客户端无对应载体的场景。

## 3. 反证、失效与最小区分实验

- **可推翻的观察**：在登录前（或未进目标场景）就能稳定 dump 到业务类型名/业务 PE 的游戏。
- **已收集反证**：无。本样本构成一次前后对照。
- **失效条件**：游戏改为把业务程序集常驻在内存且不释放 PE；或热更载体改为启动即加载（不依赖登录）。
- **失效后处置**：降为"待验证"并标注适用前提；不影响动作 2（加密载体解密分流）。
- **最小区分实验**：同一进程、同一地址区间，分别在"未登录"与"已进入目标场景"两个状态各抓一次；比较业务符号计数（0 → 正）。单一变量为游戏内状态。
- **停止条件**：两次状态对照仍无差异 → 停止该分流思路，转正常静态分析；超出只读授权即停止。
