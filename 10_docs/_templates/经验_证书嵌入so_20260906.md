## 2. 观察、解释与候选经验

- 观察事实（实测）：
  1. 证书仅一处消费点：`AuthClient.init()` 读 PEM → TrustManager 证书固定；`request()` 对 HTTPS 在 `pinnedSslContext == null` 时 fail-closed（拒发，不退回系统信任）。
  2. `xxd -i` 产出的数组经 `#include` 编进 so，`SetByteArrayRegion` 回传 Java 后 `CertificateFactory.generateCertificate` 可正常解析 PEM 字节流。
  3. 实机日志：`RegisterNatives 19/19 全部成功`、`nativeGetPinnedCert = PASS`（自检 PASS=15 FAIL=0）、`pinned cert loaded from native so: CN=47.100.216.101`、bootstrap/heartbeat 均 ← 200。
- 拟提炼的经验（带前提）：
  - **前提**：框架为 RegisterNatives 桥接架构；证书为公开公钥（非密钥）；AuthClient 已有 fail-closed 语义。
  - **动作**：`xxd -i ../assets/certs/starlight.crt > CertPinned.h` → Main.cpp include 并注册 `()[B` 桥接方法 → AuthClient 从 `ModBridge.nativeGetPinnedCert()` 取字节，删 assets 读取。
  - **预期结果**：游戏外科包无需带 `assets/certs`；证书特征从 APK assets 明文收进 so 数据段；旧 `surgical_*.sh` 不改也兼容（多拷的死文件无人读）。
- 适用范围：星光框架 2026-09-06 大改版（RegisterNatives 桥接）之后的包；自测壳、外科注入、雷霆战机 assets 落盘加载路线、OTA so 均随 so 自带证书。
- 不适用 / 已知例外：
  - **存量旧包不受影响也不升级**：已分发包仍读 assets（旧 AuthClient），服务端兼容已验证（大改版经验 §6 同理）。
  - 纯 Java 侧证书轮换不再可行：换 `starlight.crt` 必须重编 so（CertPinned.h 头部已注释命令），与「切游戏必重编 so」流程对齐。
  - so 体积 +1.2KB 级，可忽略；若未来证书变多需评估。

## 3. 反证、失效与最小区分实验

- 可推翻的观察：某 ROM/加固对 so 数据段做完整性校验或重定位后取数失败（本次未遇）。
- 失效条件：RegisterNatives 桥接架构变更；证书文件名/格式改 DER 时 `xxd -i` 流程需同步改；NDK 工具链大版本变化导致 `--gc-sections` 行为差异（本次已验证数据保留）。
- 失效处置：降为待验证，AuthClient 报错日志为 `so 内未烘焙固定证书` / `native 未加载`，fail-closed 不闪退。
- 最小区分实验（已做）：同包同 so，先 cert=1 判定（`grep -a "BEGIN CERTIFICATE"`）再装机，200 响应为 TLS 固定链通过信号。
- 停止条件：本卡仅覆盖框架自测样本；任一真实游戏外科包装机回归后可升级证据状态。
