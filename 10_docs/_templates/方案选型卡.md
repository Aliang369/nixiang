# 方案选型卡（动手前必须先填，等用户选）

> 触发条件（命中任意一条就必须出卡，**先出卡再动手**）：
> ① 涉及**出网**（访问/借用/部署任何外部服务器）；② 涉及**改动外部机器或用户资产**（服务器、路由器、用户装机、用户账号）；
> ③ 涉及**变更交付形态**（改包重签 ↔ 免 root 直装 ↔ 需要电脑/助手/root 等前提变化）；
> ④ 需要用户在真机上**花额外动作**（点按钮、开权限、每次开局操作一次）；
> ⑤ 同一问题已有 ≥2 条可行路线且代价不可比。
>
> 违例的代价（真实历史）：一次「顺手改服务器」直接引爆用户震怒并作废整段产出；
> 一次「形态擅自改成 root 版」让用户推倒重来 —— 都不是技术失败，是**没让用户选**。

## 填法

```markdown
# 方案选型卡：{问题}（{日期}）

- 问题一句话：
- 为什么必须让用户选（命中触发条件第几条）：
- 我的推荐：方案 X（理由一句话）

| 方案 | 做法（具体到命令/文件） | 用户要做什么 | 代价 / 风险 | 可逆性 | 我不选它的理由（其余行填） |
|---|---|---|---|---|---|
| A | … | … | … | 完全可逆 / 需还原步骤 | （推荐行填写「推荐：…」） |
| B | … | … | … | … | … |
| C（含「不做」） | … | … | … | … | … |

- 不做会怎样（默认选项必须列出来）：
- 需要用户回答的**一句话**（只问一个问题）：
```

## 两条纪律

1. **推荐可以不采纳**：用户选了非推荐项就照做，不得在执行时「悄悄带回推荐方案」；要改回必须再出一次卡。
2. **选完落盘**：用户选定后把该行结论追加到 `10_docs/{游戏}/硬约束.md`（或对应技术文档），注明消息号 —— 否则下个会话会重新提一遍同样的三选一。

## 反面教训（为什么需要这张卡）

| 实例 | 后果 |
|---|---|
| 为了绕开下载慢，直接动了外部服务器 | 用户：「我让你在改东西，你老动我服务器…我让你动了吗？」⇒ 产出全部作废、服务端全量还原 |
| 未经询问把交付形态做成 root 版 | 用户：「外科组装一直是无 root 的直装」⇒ 整条路线推倒重做 |
| 把「需要电脑推包」当成默认前提 | 用户：「那你做个毛的无 root 直装包啊…结果你告诉我还需要借助电脑」 |
