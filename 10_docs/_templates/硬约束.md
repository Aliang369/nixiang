# 硬约束（游戏级）— 结构与判据（唯一正文）

> 用途：保存**单个游戏**的用户要求与工程红线，并让 AI 一眼看出「这条现在还生效吗、对哪个版本生效、我该怎么执行」。
> 落点：`10_docs/{游戏}/硬约束.md`（一游戏一份）。**不新建第二份**，也不把游戏级要求写回 `AGENTS.md`。
> 分类、优先级、冲突处理的总原则在 `AGENTS.md` §1.1–§1.4；本文件只定义**这份文件自己的字段与判据**，不重复政策。
> 机器检查：`python3 -B 04_scripts/_common/audit_workspace_docs.py constraints`（缺列/缺状态/缺适用范围即报；旧格式只警告）。

---

## 1. 分区（决定 AI 开工时读不读）

| 区 | 内容 | 开工默认读取 |
|---|---|---|
| **A 当前生效约束** | 长期用户硬约束、工程红线、安全/授权边界 | ✅ 必读 |
| **B 一次性与任务级要求** | 只对当前轮/版本/渠道/设备/本次交付有效 | ✅ 必读（用完即标"范围已结束"） |
| **C 默认偏好** | 通常这样做，可因条件调整 | 按需 |
| **D 技术事实与已验证经验** | 本游戏实测机制、故障原因、限制 | 按需 |
| **E 待核验** | 来源/范围判断不清，**默认不生效** | ❌ 除追溯/排查冲突外不读 |
| **F 历史与失效** | 已失效、被替代、已完成、事故记录 | ❌ 除追溯外不读 |

原则：**保留原文 ≠ 继续强制**。F 区保留原话与失效依据，但不进当前执行上下文；E 区不得被当成依据约束本轮。

## 2. 字段定义（A/B 区表列，顺序固定）

| 列 | 必填 | 含义与允许值 |
|---|---|---|
| `#` | ✅ | 行号全局唯一、只增不改（被替代的行保留号，新行取新号） |
| `类别` | ✅ | **只放 `A` 或 `B`**（见 §3）。C（偏好）/D（技术事实）有独立分区，写进 A/B 表会被审计器判错 |
| `强度` | ✅ | `必须` / `禁止` / `照 XX 做` / `偏好` / `记录`（**只表示要求强度，不表示长期有效**） |
| `原话/来源（逐字，含出处）` | ✅ | 用户原话逐字 + 消息号/日期；非用户原话写清文件出处。**概括标 `（意译）`；AI 的总结不得写进本列** |
| `可执行含义` | ✅ | AI 具体做什么/不得做什么（可操作、可判定） |
| `适用范围与生效条件` | ✅ | 游戏/渠道/版本/设备 + 何时开始、何时结束 |
| `例外/解除` | ✅ | 允许偏离的条件与授权来源；无例外写 `无` |
| `状态` | ✅ | `生效` / `一次性` / `待核验` / `已失效` / `已被 #N 替代` / `已完成` |
| `证据/权威落点` | ✅ | 支撑证据（日志/文档/md5/实测行）与规则正文落点（本文件行号、`路线锁定.md`、`skill/**`） |

C/D 区用同一套简表（列：`# | 内容 | 适用条件 | 证据`，**行号同样必填且全文件唯一**，审计器对 C/D 做与 A/B 同等的表头/行号/字段检查）；E 区列：`# | 内容（原文） | 原可执行含义 | 不确定点 | 已做的保守处置`；F 区列：`# | 原话/来源 | 曾经的执行含义 | 状态与失效依据 | 日期`。

## 3. 分类判据（先判类，再判强度）

- **A 长期硬约束**：用户明确指向未来/默认/持续/跨任务，或经本项目反复验证的安全红线、工程红线。必须能回答"来源是谁、对哪个范围生效"。
- **B 当前任务要求**：出现范围限定（"这次""本轮""这个版本""先做这个""看看能不能""这个包""这台设备"），或只对本次交付有效的点名/授权/上限。
- **C 默认偏好**：方法上的倾向（优先复用现成脚本、先静态后动态、少往返），违反不算违规。
- **D 技术事实**：实测出来的机制/限制（"该战斗是服务端权威制""so 带 emutls 就静默降级"）。**不得写成"必须/禁止"命令**；确需强制时升 A 并写清范围。
- **E 待核验**：来源不明（无原话、无消息号、无日期、无文件出处）或范围判断不清。**默认不生效**。
- **F 历史**：状态已过期（`已失效`/`已被 #N 替代`/`已完成`）。

三条否定判据（最容易判错）：

1. 用户说过「必须/禁止」**不等于** A；没有范围指向、只在当轮语境成立 ⇒ B。
2. 单次实验、单版本、单设备有效 ⇒ B 或 D；推广到全部版本必须有证据或用户明说。
3. 从原话**推导**出来的约束（用户没说的部分）必须显式标「AI 推导」或「工程推导」，范围收窄到推导依据覆盖的部分，不得伪装成用户原话。

补充判据（2026-10-27 第二轮，来源：迁移后实测出的真实错分）：

4. **范围词只是提示，不是判据**：「这次/本轮/这个版本/看看能不能/这台设备」出现时先看它指向**什么对象**（一次交付？一个版本？一台设备？还是一类做法）；反过来，**没有范围词也不等于长期**——任务书式的第一句话（"真机已root已安装…要求替换成星空包"）通常是 B，除非它约束的是跨轮次仍成立的东西（底包身份、签名方案）。**一句原话同时含长期要求与当轮要求时，拆成两行**，各自写独立适用范围；拆不清就整句按 B 处理并注明。
5. **技术事实不自动升 A**：实测结论（机制、偏移、字段语义、验收结果）先落 D；要变成"必须/禁止"必须有用户指令或门禁授权，并写清"谁要求、对什么范围"。验收结论（"功能没问题/感觉不到"）属 D 或 F，不是 A。
6. **A 类工程红线四要素**：可定位来源（原话＋消息号/日期，或实测记录位置）＋适用范围＋**稳定性依据**（为什么跨轮次仍成立：实测复现、机制约束、编译期护栏；只写"反复验证"不算，要给可复查的证据位置）＋唯一权威落点。缺任一要素 ⇒ 降为 B/D，或标「AI 推导·待核验」进 E。
7. **已完成/已判停的任务要求必须落地为状态**：某轮任务的阶段顺序、验收判据、交付物要求在完成后**移入 F 区并标「已完成（依据）」**；游戏已被用户判停时，A 区只保留重启交付时仍适用的口径，并在元信息写明"该游戏已收尾，A 区仅重启时适用"。
8. **状态与分区必须一致**：A/B 区只能是 `生效`/`一次性`；`已完成`/`已失效`/`已被 #N 替代` 的行一律在 F 区（审计器会把这种不一致判为错误）。**A 类还必须是 `生效`**——标「一次性」说明它是当轮要求，应记 B 类。
9. **B 类会过期，必须有人负责收敛**：B 行的「适用范围」一旦结束（该轮交付完成 / 判停 / 被新版本替代），当轮就把它移入 F 区并写「已完成 ⇒ 依据」＋原状态/适用范围/证据。**审计器只能查格式（A/B 表不允许「已完成」、A 类不允许「一次性」），不能自行判断某轮任务是否真的结束**，所以每个 B 行都必须能在 `_state/games/{游戏}.md` 找到「进行中/已收官」的证据；找不到证据就保持 B 并在报告里标明「范围是否结束待确认」。

## 4. 写入规则

- 用户下达或修改约束的**当轮**就落一行（属于记录，不是提案）；漏记比写错更糟——先记下来，类别判错下轮可改。
- **永不删行**：失效只改 `状态` 并写失效依据（用户新指令 / 版本换代 / 被 #N 替代）与日期；需要"清空"时把行移入 F 区。
- 一次性要求与正常基准**分行记录**：基准行状态保持 `生效`，一次性行写 `一次性` + 结束条件，并在变更记录注明"不改正常口径"。
- 想让 AI 长期照做的要求进 A；只想本轮照做的进 B。**判不准时默认 B**（保守：不过度持久化）。
- 约束范围外（换游戏/换版本/与 A 区范围不符）时，AI 可判不适用，但必须在汇报里写出依据。

## 7. 迁移说明（2026-10-27 治理会话）

- 旧版本只有 `原话 | 类型 | 可执行化 | 违反实例 | 状态` 五列，没有"类别/适用范围/例外/权威落点"，无法区分长期要求与当轮要求，导致过时行被反复注入当前上下文。
- 迁移规则（已用于本仓 28 份游戏硬约束）：原 `类型` → `强度`；原 `可执行化` → `可执行含义`；原 `违反实例` → 证据；`类别` 按 §3 逐行判定，判不准落 E；`状态` 含「失效/作废/被替代」→ F 区；含「已完成/已履行」→ F 区（不默认继续生效）。
- **迁移不改原文**：原话、消息号、证据逐字保留；不补写不存在的消息号，不把推断写成用户原话。原文件的第二张表（工程红线/字段事实）按 §3 分别并入 A 与 D，并保留原表标题避免外链断。

## 8. 为什么要这份文件（不要走回头路）

- 反面教训一：冒险与征途 1.5.9 用户 8 次以上要求「照斌哥的改」，长会话 prune 后硬指令被稀释成"历史聊天记录"。
- 反面教训二：把一次性定制误标成"新标准"（2026-10-18 炁术行者），导致正常口径失效、5 处文档回改。
- 结论不是"记得更牢"或"写得更硬"，而是：**分区 + 字段 + 状态可审计**，让 AI 只在正确范围按正确强度执行。
