## 2. 观察、解释与候选经验

- **观察事实**：
  1. 捕捉请求 `cmd 3053` 的字段为 `EventId` / `CostItem` / `GestureResultList`（repeated int32），其中 `GestureResultList` 由客户端把每个音符的判定等级（`General=0/Good=1/Perfect=2/Miss=3`）逐条填入。
  2. 服务端回包给的是 `SuccWeight` 与 `Result`，即成功率与成败由服务端依据该列表计算后下发，客户端只负责表现。
  3. 客户端本地另有一套同源公式只用于 UI 显示（敲击分 + 喂食 + 道具 + 逃跑次数 + 风格加成）。
  4. 游戏自带"全 Perfect"通路：`_NeedAutoPerfectCatch() => IsCanAutoAdventure || AdvAccState != Normal` 会在每个音符的完美时点自动点击；月卡加速路径更是直接 `_FillPerfectOperations()` 跳过小游戏。
  5. 同类客户端自算字段还有 `Cmd_QTE_Music_Result_Req{ MusicSocre = score*10000, MusicNodeNum }`（本版未找到调用点，属"存在但未启用"）。
- **候选解释 H1**：这类"客户端上传结算输入"的字段同时具有两种身份——对风控是**检测面**（服务端可校验/重放），对功能可行性是**唯一真实杠杆**（服务端承认的输入）。因此分析时应优先枚举它们，而不是先去改显示层。
- **替代解释 H2**：服务端可能对列表长度、内容分布或账号权益做校验，使该杠杆不可用。本样本**未验证**（无发包实验），故不得声称"可用"。
- **拟提炼的经验**（带前提/动作/预期）：
  - 触发：评估"概率/评分/次数/时长/结果"类功能，或做上报表盘点时。
  - 动作：① 枚举客户端→服务端的结算输入字段（repeated 列表、score、result、duration、count）；② 同一份清单双向使用：标出服务端可能校验的点（风控面）与客户端可影响的点（可行性面）；③ 按风险从低到高选手段：**用游戏自带的托管/自动/扫荡/加速路径产生同一种载荷** ＞ 在配置范围内的参数调整 ＞ 伪造载荷；④ 声称可行前必须先验证服务端是否校验长度/范围/权益。
  - 预期结果：把"改显示数字"这类无效方案提前排除，避免误把 UI 公式当作可实现性证据。
- **适用范围**：任何"结算/奖励由服务端按客户端上传输入计算"的联网游戏，与引擎无关。
- **不适用范围 / 已知例外**：结算完全由服务端生成、客户端不参与输入的玩法（此时只剩自动化类手段）；已有反例：`skill/re-implement/anti-cheat-pattern.md` 记录过服务端重放战斗、客户端上报与重放不一致导致结算失败并报错（`STAGE_VERIFY_FAILED=78`），说明"能改"不等于"能过"。

## 3. 反证、失效与最小区分实验

- **可推翻的观察**：服务端对同一输入多次返回不同结果（随机在服务端），或客户端字段仅用于展示、结算另有接口。
- **已收集反证**：无（本样本未做发包实验）。
- **失效条件**：服务端改为自行生成输入（不再信任客户端列表），或引入时间戳/序列校验使列表不可复用。
- **失效后处置**：把该字段从"可行性面"移到"仅风控面"，并回到自动化类手段评估。
- **最小区分实验**（需另行授权，属对外发包）：
  - 对照组 A：正常手打产生的中等判定列表；对照组 B：游戏自带自动路径产生的全 Perfect 列表（两者都是游戏自身会发出的合法载荷）。比较服务端回包的 `SuccWeight` 是否按公式抬升。
  - 对照组 C（仅在确认 A/B 都正常后，且单独授权）：长度/内容异常的列表，观察是否被拒或触发风控。
  - 判定阈值：`SuccWeight` 与客户端本地公式一致 = 服务端按输入计算；被拒/无响应 = 有校验。
- **停止条件**：涉及下发/写服务端状态、或需要超过已授权范围时立即停止并申请；单次实验不得重放、不得放大数量。
