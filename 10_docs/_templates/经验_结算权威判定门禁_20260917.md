## 2. 观察、解释与候选经验

- **观察事实**（同一份反编译源码内可直接定位）：
  1. `BattleServerInvoker.BattleAttack/BattleSkill` 只发送"攻击"或"用哪个技能 ID"，**不携带任何伤害数值**。
  2. 客户端收到的是服务端下发的 `Notify_DamageHit`、`BattleActionEvent`、`BattleStateSnapshot`；另有独立战斗服登录与客户端帧号上报（`BattlePing(FrameReq)`）。
  3. 单位血量/血上限/死亡/技能 CD/充能/可用性全部由服务端结构 `LumiState` 填充（`BattleHeroProperty.StartProperty/UpdateProperty`）。
  4. 客户端 `OnNotifyDamageHit` 只做飘字与受击表现；`BattleHero._OnHPUpdated` 只刷新 UI。
- **候选解释 H1**：该类战斗为服务端权威（服务端算数值、客户端只发动作 + 播放表现），因此任何"客户端乘系数"的方案只改表现，不改结算。
- **替代解释 H2**：客户端本地也跑一份仿真，服务端仅做弱校验（部分游戏如此）。区分证据：客户端是否存在本地伤害计算入口、是否由服务端下发每个伤害事件。本样本中两者皆指向 H1。
- **拟提炼的经验**（通用门禁，不预设结论）：
  - 触发：任何"攻击倍率 / 无敌 / 无限技能 / 加速 / 数值类"功能需求，在写实现之前。
  - 动作：先填**权威判定五问**——① 客户端发包带的是数值还是动作？② 是否收到服务端伤害/状态事件？③ 属性是否全部由服务端结构填充？④ 是否有独立战斗服会话与帧号/心跳？⑤ UI 是否只订阅数据变化回调？
  - 判据与出口：客户端权威 → 可走数值改写；服务端权威 → 只能做表现层或"自动化"（自动攻击/自动放技能/自动拾取），不得按数值型功能宣传；混合 → 逐项判定，禁止整体结论。
  - 预期结果：把"做不了的功能"在动手前筛掉，避免出包后才发现只能改飘字。
- **适用范围**：所有带战斗/结算/资源产出校验的联网游戏，与引擎无关（Unity/Cocos/Lua 均适用）。
- **不适用范围 / 已知例外**：纯单机、离线模式、有明确客户端权威模式（如部分 PvE 本地战斗）的游戏；需按出口三分法逐项核实，而不是整包套用。

## 3. 反证、失效与最小区分实验

- **可推翻的观察**：发现客户端存在真实的伤害/血量计算入口，且服务端回包与本地计算不一致时不覆盖。
- **已收集反证**：无。
- **失效条件**：游戏改为客户端权威战斗（例如离线模式或客户端模拟 + 事后校验）；或该模式与服务端重放校验解耦。
- **失效后处置**：改判为"客户端权威"，功能可做但需重新评估风控面；同步更新对应游戏的可行性文档。
- **最小区分实验**：同一场战斗内，仅改本地伤害显示的系数（不动协议），观察服务端下发的 HP 数值是否随之变化；HP 不变即服务端权威（H1），HP 跟随即客户端权威（H2）。
- **停止条件**：五问中任一为"否"且无法补证时，先把结论降为 NOT PROVEN，不进入实现；超出授权（例如需要抓包或改包）时停下申请。
