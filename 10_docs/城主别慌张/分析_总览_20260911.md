## 0. 结论摘要（TL;DR）

1. **本作不是原生游戏**。它是 **Cocos Creator 3.8.8 的 `web-mobile`（H5）构建**，运行在 **腾讯 X5 WebView** 内，由盒子 `com.xiaoyougames.h5boxgame.MainActivity` + `com.chaunmi.fastwebview` 承载。
   → **APK 内没有游戏业务逻辑**（无 `libil2cpp.so`、无 `libcocos2djs.so`；包内 `assets/game/` 只有引擎与战斗仿真库的历史快照）；**14 MB 的游戏业务代码 100% 来自 CDN**。
2. **线上与包内是两个不同构建**：APK 内置离线包停留在 2026-06-24 构建（`bundle.45292.js`），线上当前构建是 `bundle.c0e2a.js` / 脚本包 `index.2946f.js`。包内离线资源对新构建**基本失效**，运行时几乎全部走网络（首次进游戏后大量落 X5 磁盘缓存 `cache/custom`）。
3. **因此「星空版」的正确形态是**：原生壳（星菜单 + 鉴权 + 注入守护）+ **注入进页面的 JS 补丁**（实现玩法功能）。
   **不需要** il2cpp/Cocos 原生 hook，**不需要**改 APK 内的游戏资源，`libstarry_magic.so` 在这里只承担「菜单 + 功能表 + 鉴权 + 状态存储」。
4. **免广告锚点已证实为单点**：全游戏 `xy.U.sdk.watchAd` **只有 1 个调用点**（`AdModel.doWatchAd`），而 `tryWatchAd` 有 **21 处**调用（覆盖所有激励视频入口）。包装这一处即可全局免广告，且仍会走完 `uploadAdAction(Click/Over)` 与协议 **11801** 的上报，保持协议一致。
5. **上报面**：战斗结算 **12102**（`result` / `begin_seed` / `last_seed` + `level`/`wave`/`hp`/`drop`/`damage`/`use_skill`…）、广告完成 **11801**、埋点 `https://tf-api.shryou.com/api/v1/log?`、SDK 侧 `https://exc.llewan.com/v1/LogHandle/Common`。战斗输入只有**结构校验**（`validateLogicInput` 只查字段存在性，无 checksum/签名）。
6. **意外发现**：游戏**自带 GM / 调试开关**，全部由 **URL 查询参数**驱动（`debugFight` 位掩码 89 处引用、`showGM`、`nofight`、`unBlock`、`testHard`…），入口 URL 由原生 `buildFinalGameUrl()` 拼接 → 原生侧可控。详见 `GM与调试开关_20260911.md`。

**可逆空间**：大。**主要风险**：不是反调试/完整性校验，而是**上报一致性**（战斗摘要与种子）与**服务端校验**（见 §7）。

7. **★ 最大阻断（2026-09-12 实测新增）：华为渠道包一旦重签名，平台登录就静默卡死**（盒子停在加载页、零报错、无登录弹窗）。已用单变量 A/B 定案：官方原包正常起华为 ID 登录界面，而「内容与原包逐字节相同、仅换签名」的对照件同样卡死 ⇒ 变量是**签名**，不是我方 mod 代码。校验发生在华为自己的进程/AGC 侧，`SignSpoof` 够不着。**结论：华为渠道 + 星空包不可交付**，需换非华为渠道包；详见 §5.3。

## 4. 注入方案（选定）

### 4.1 为什么不能在包内改游戏资源

子资源（JS/PNG/JSON）会被 `AssetResourceInterceptor` 用 `assets/game/<path>` 命中并**优先于网络**返回；但**主框架（HTML）请求是否走该链路，取决于 X5 调用哪个重载**，而 FastWebView 两分支行为不同：

- `InnerX5FastClient.shouldInterceptRequest(WebView, WebResourceRequest)` → `onIntercept()` → 先委托 listener，未命中再走 `loadFromWebViewCache()`（**经缓存链**，即离线包能生效）；
- `InnerX5FastClient.shouldInterceptRequest(WebView, String)` → **只委托 listener，直接返回 null，不查缓存链**（离线包不生效）。

→ 若主框架走前者，往 `assets/game/` 塞 `yh.html` 就能覆盖入口页；若走后者则不能。**（实机未验证，标「待验证」）**
→ 本方案**不依赖**这一判定：无论哪种，运行时注入都成立。之所以选运行时注入，是因为**离线包本身已与新构建脱节**（见 §1.2），改包内资源对当前版本基本无效。
（另：`WebSettings.setAllowFileAccess(false)` 但 `setAllowFileAccessFromFileURLs/UniversalAccessFromFileURLs(true)`；`loadDataWithBaseURL` 会改变 origin，影响游戏对 `tf-api.shryou.com` 的 XHR，不采用。）

### 4.2 选定方案：Manifest 声明 Provider + 页面内 JS 补丁（★ 不动游戏任何 dex）

```
[原生侧] AndroidManifest.xml 新增两个 provider（外科只换 Manifest 与新增 dex）
  ├─ com.starry.magic.StarryInitProvider（框架已有，声明即生效）
  │    → 加载 libstarry_magic.so、SignSpoof.install()、起 MenuService
  │    → 注册 ActivityLifecycleCallbacks
  └─ com.starry.magic.h5box.CzbhzH5Provider（本作新增，classes4.dex）
       → onActivityCreated / onActivityResumed → StarryH5.attachTo(activity)
            ├─ 遍历 View 树找游戏 WebView（优先 com.chaunmi...FastX5WebView；
            │   同类候选按面积取最大，排除宿主自带的 overlayWebView）
            ├─ webView.addJavascriptInterface(new StarryH5(ctx), "StarryH5")
            └─ 起注入守护：每 1s（未 ack）/ 5s（已 ack）
                 loadUrl("javascript:" + <补丁源>)
[补丁侧] assets/starry/czbhz_patch.js（外科新增）
  ├─ 幂等守卫 window.__czbhz_v1（页面重载后自动重装）
  ├─ 自延迟：500ms 轮询等 window.xy / xy.D.ad / xy.battleClient 就绪
  ├─ 读状态：window.StarryH5.getState()（JSON，带菜单开关与数值）
  └─ 装钩子：xy.D.ad.canSkipAdWatch 置真（免广告，P1）等
```

**为什么放弃最初的 smali 注入方案**（本作相对其它游戏最大的一处调整）

| 原方案（已废弃） | 现方案 | 理由 |
|---|---|---|
| patch `LWSdkApplication.smali`（`loadLibrary` + `SignSpoof`）与 `MainActivity.smali`（`MenuService` + `StarryH5.install`） | Manifest 声明 Provider，靠生命周期回调拿时机 | 宿主 `MainActivity` 位于 **classes.dex（7.7MB、多 dex 顶部文件）**；baksmali+smali 整包重建既慢，又有方法数/顺序漂移风险。Provider 方案让 **classes.dex / classes2.dex / classes3.dex 逐字节不变**（外科脚本内 sha256 断言把关） |

### 4.3 JS 补丁的加载时序与自我保护

- **时序**：补丁在页面开始加载后的任意时刻注入；`window.xy` 在 `Core.ts` 执行时才存在，业务模块按 `System.import` 顺序异步装入。补丁用轮询（如 200 ms）等待目标对象就绪再装钩子——**不假设任何时序**。
- **幂等**：`window.__czbhz_v1` 守卫；重载即重装。
- **降级**：任一钩子安装失败只记日志，不影响游戏（补丁自身 try/catch 包住每个钩子）。
- **可观测**：补丁通过 `window.StarryH5.log(...)` 把关键节点回传 logcat，供无侵入验证。

### 4.4 注入通道的两个实测坑（2026-09-12，均已在代码里修掉）

**坑一：`loadUrl("javascript:…")` 会被 URL 解析吞掉，且完全静默。**

`loadUrl("javascript:" + src)` 把整个脚本当 **URL** 处理：`%` 会被百分号解码，脚本里只要出现 `%23` 就解出 `#`，而 `#` 是 URL 的片段起点 —— **脚本被当场截断**。本作补丁注释里恰好有一处 `%233280`，于是脚本被切断在块注释中间 → 整段语法错误 → WebView **静默丢弃**（logcat 里连一条报错都没有）。

实测症状极具误导性：注入侧的日志一切正常（`找到游戏 WebView`、`addJavascriptInterface 已挂载`、`注入第 N 次`，无异常），但补丁侧**一行日志都没有**。用 CDP 在页面里求值才定位到：`typeof window.StarryH5 === "object"`（桥在）而 `window.__czbhz_v1 === undefined`（补丁从未执行）。

**修法**：改用 `evaluateJavascript`（不经 URL 解析，任意字符与长度都安全），按「名字 + 参数个数」反射扫描以同时兼容 `android.webkit` 与腾讯 X5 两套签名；只有它不可用时才退回 `loadUrl`，且退路会先做 `%`→`%25`、`#`→`%23` 转义。补丁本体里的那处 `%` 也已改写掉（双保险）。

**坑二：`about:blank` 阶段注入的补丁不会自动跟到真正的游戏页。**

补丁首次执行发生在 `about:blank`，`window.xy` 尚未存在，守卫与轮询都在等 `window.xy`。页面随后换成真正的游戏文档时是**全新的 JS 上下文**，需要再注入一次。守护因此保持周期注入（首轮 1 s、收到 ack 后 5 s），不依赖一次性注入。

> 现场取证手法（无调试器也能用）：本作三个位置硬编码了 `setWebContentsDebuggingEnabled(true)`，因此 `adb forward tcp:9222 localabstract:webview_devtools_remote_<pid>` 后可用 CDP 在页面内直接求值/看资源请求。这是本次能快速定位坑一的关键手段。

### 5.1 免广告为什么选 `canSkipAdWatch` 而不是别的口子

已核实的原始实现（`06_dumped/城主别慌张/mods/mod_SdkUtils.pretty.js:282`）：

```js
SdkUtils.watchAd = function (e) {
    o.D.ad.canSkipAdWatch() ? e.run()                       // ← 官方特权捷径
      : <支付宝PC端> : <xyMini.watchVideoAd 真拉起广告> ...
};
// AdModel 构造函数内（AdModel.ts.pretty.js:63）：
o.canSkipAdWatch = function () { return i.D.privilege.getPrivilegeValue(r.SkipAd) > 0 }
```

- 全库 `canSkipAdWatch` **只有这 1 个调用点**（已 grep 全量模块确认）⇒ 置真 = 扮演"拥有免广告特权的正常玩家"，**不绕开游戏自己的任何数据流**。
- 之后的 `onWatchAdDone` → `sendMsg(11801,{type,params})` 与真播路径完全一致（详见 §6）。

**已排除的替代口子**（每一处都是"看起来更省事、实际更容易暴露"）：

| 口子 | 为什么不选 |
|---|---|
| `AdModel.getAdInfo().leftTimes/canWatch` | 绕过 `watchAd → onWatchAdDone`，**11801 根本不发** → 服务端不记账、UI 不刷新，比官包更可疑 |
| 给 `SdkUtils.uploadAdAction` 补真上报 | 它本来就是**空函数**（`e.uploadAdAction = function (e, i) {}`），补上报等于凭空制造差异 |
| 改 `getWatchTimes` | 恒返回 0，是游戏自身的既有行为，不要动 |
| 直接 `AdModel.doWatchAd` → `onWatchAdDone` | 跨过 Click/Over 语义，偏离大于 P1（列 P3 备选） |

### 5.3 ★ 渠道签名约束：华为渠道重签名后**平台登录静默卡死**（本作最大结构性阻断）

**结论（2026-09-12 实测，单变量 A/B）**：本作是**华为渠道包**（`channel=huawei`、`lw_channel_type=huawei`、AGC/HMS 登录）。**只要重签名，华为侧就不再放行登录**；盒子一直停在加载页（"正在疯狂加载.."），全程零报错、零登录弹窗。

| 包 | 内容 | 签名证书 | 实测结果 |
|---|---|---|---|
| 官方原包 | 原版 | `CN=XingXuan, O=XingXuan`（广州星玄）<br>SHA-256 `f9732a3f…` | **正常拉起华为 ID 登录界面**并继续请求盒子配置 |

| 星空包 `surgical` | 原版 + mod | `CN=StarryMagic` | 同上 |

**证据**：`07_patched/城主别慌张/diag_resign/e2_resign_only_1.0.10.apk` 经脚本闭环断言证明「5099 条非 META-INF 条目与原包逐字节相同、且不含 `classes4.dex`/补丁/`libstarry_magic.so`」，即除签名块外与原包无差别。官方包那次运行在 HMS Core 进程留下 `LoginOrRegisterBySmsActivity` / `StartUpGuideLoginActivity`（`hasAccount: false`）日志并继续请求 `sd/config`；两个重签名包**均无**这些痕迹，`sd/config` 请求次数为 0。

**为什么 `SignSpoof` 兜不住**：签名校验发生在**华为自己的进程**（`com.huawei.hwid`）与服务端 AGC 侧（按注册的签名指纹认应用），而 `SignSpoof` 只改**本进程** `PackageInfo.CREATOR` 的反序列化结果。本包内读取签名的三处（`com/huawei/hms/utils/PackageManagerHelper`、`com/huawei/secure/android/common/sign/HiPkgSignManager`、`com/blankj/utilcode/util/AppUtils`）中，前两者的用途是 **HMS 校验 HMS Core 自身**，`HiPkgSignManager` 在本包内**零调用者**；没有任何一处是"校验本应用签名"。

**对本作交付形态的影响（必须先解决才能谈"可交付"）**：

| 路线 | 可行性 | 说明 |
|---|---|---|
| **换非华为渠道包**（官方/TapTap/4399/应用宝…） | **推荐** | 线上代码是 CDN 同一份（`yyplat=lwazbox`），§5 的 5 项功能钩子与渠道无关，**现有补丁/入口/功能表可整体复用**，只需重做渠道适配（渠道包名、`SignSpoof` 名单、`pipeline.json` 参数）。这是唯一能出"可交付星空版"的路 |

### 5.4 离线行为回归闸门（进不了游戏时，怎么证明功能逻辑是对的）

**为什么需要**：§5.3 的渠道签名阻断让 5 项功能**没法在真机上做行为验证**（装得上、注入链全绿，但进不去游戏）。于是补一个离线闸门：`04_scripts/城主别慌张/offline_regression.js`。

**做法**：Node + `vm` 造一个 `window` / `window.xy` 仿真环境，把**即将打进包里的那份补丁源码**（直接从 `assets/starry/czbhz_patch.js` 读）原样丢进去跑，并按虚拟时钟驱动它的 500 ms 主循环（`Date.now`/`setInterval` 全部可控）。仿真对象按实机逆向结论搭：`attr` 用真实数字键（`1001/1002/1005/1101/1103/1200/3001/3046`），`li.teams` 的形态按 dumped 代码分两种 —— **PVE 单队**（`startLocalPveFight` 只 push 我方一队）与 **PVP/GVE 双队**（`buildPvpLogicInput` = `[Challenge, Rival]`、`onResGve` 同）。

**25 项断言，分 6 组**：

| 组 | 覆盖 |
|---|---|
| A 装载与守卫 | 桥未就绪**不占守卫**且不抛；桥就绪后写守卫 + 装载日志 + ack；重复注入被守卫拦住（一个定时器、日志不重复） |
| B 授权门控 | `live=0` 免广告与四项战斗**全部哑火**；`live=1` 生效；开关关掉**立刻回落**到原函数；`live` 由 1 变 0 立即停止 |
| C 免广告 | P1 包装 `canSkipAdWatch` 并打标记（幂等不重复装）；被游戏重建冲掉后**自愈补装**；无 AdModel 时超时后 P2 包装 `sdk.watchAd` 且**真播路径零调用**；`live=0` 时 P2 必须回落真播 |
| D 战斗四项 | PVE 四项都落到我方；**★ PVP/GVE 对手 8 个属性一个字都不能动**；同一 `logicInput` 二次入口（模拟 12103 重入）**不复利**；中途改滑块按首见原值重算（×50 → ×10 得 10000 而非 500000）；`player_id` 数字/字符串混用仍认出我方；倍率 1 时数值不变 |
| E 鲁棒性 | 畸形 `logicInput`（含 `null`、`teams:[null,{units:null}]`）不抛且**不阻断开战**；单位缺 `attr` 跳过；战斗钩子被重建后自愈；`xy` 延迟就绪也能装上；战场结构诊断只打一次 |
| F 源码级地雷 | 补丁源码**禁止出现 `%` 与 `#`**（连注释也不行 —— 见 §4.4）；`featNum` 常量与 `CzbhzEntry.cpp` 菜单顺序对齐；补丁代码内不得出现 `loadUrl` 调用 |

**★ 它立刻抓出一个真 bug**：`移速` 那段原先写在 `if (isMine)` **外面**。PVE 只有我方一队所以看不出来，但 **PVP/GVE 里 `teams` 是两队同数组** ⇒ 对手也会被一起加速（实测用例：对手 `speed` 从 90 变 270）。已修（把 `spd` 移回 `isMine` 内），修后 25/25 全过。这就是"进不了游戏"时最该有的那道网。

**已接入管线**：阶段 `offline_regression`（位于 `impl_mod` 之后、`build_so` 之前），且 `build_so.requires = [offline_regression]` —— **补丁逻辑不过关就不许出包**。

**边界（别把它的结论说过头）**：它证明的是**补丁的判定、写入、幂等、自愈**都对；它**证明不了游戏内最终效果**（服务端是否重放 `begin_seed/last_seed`、伤害流水线里 `dam_bonus` 的实际倍率语义等仍是 §9 的待验证项）。

### 6.3 真正的对抗面在服务端

## 7. 风险与合规边界

- **上报一致性优先于功能强度**：`hp` 进度、`damage`、`drop`、`use_skill`、`fight_time`/`frame_index` 与 `result` 之间的自洽性必须照看（细项见战斗钩子文档 §上报一致性）。
- **补丁日志禁止走 `console.error`**：`MainActivity:1706` 的 `onConsoleMessage` 把 ERROR 级日志 `postCatchedException` 进 Bugly，而 Bugly 崩溃报告**登录后已 `setUserId(uid)` 绑定账号**。补丁一律用 `window.StarryH5.log()`（logcat tag `StarryCzbhzJs`），不碰网页控制台。
- **不使用**会直接产生服务端写操作或异常账本的路径（如凭空发奖协议）。
- **不做**客户端完整性/签名伪造之外的多余动作；`SignSpoof` 只在需要时启用。本作**不在** `SignSpoof` 的包名伪造表内（且 `getSignMd5` 零调用），因此**保持不伪造**，避免喂出与官包不符的签名。
- **测试边界**：装机/运行/抓包需用户明确授权；不卸载、不清数据（优先覆盖安装）。
- 所有功能默认**全部关闭**，随星菜单授权链路解锁；授权失效即 `lockAllFeatures()`。
