## ③ 反作弊结论

### 3.1 直接回答

> **有没有真正启用的客户端反作弊/检测？**
> **没有。本包对"游戏逻辑有影响"的客户端反作弊项 = 0 项。**

已实现但**未接线**（存在代码、无调用者，均已 smali 复核）：

1. `CheckSimulator`（含 MuMu / BlueStacks / 夜神 / 逍遥 / Genymotion / 海马玩 / vPhone / Windroy 等 53 个包名 + qemu 特征 + `ro.kernel.qemu` + CPU ABI + `Build.FINGERPRINT`）—— 零调用。
2. blankj `DeviceUtils.isDeviceRooted` / `isEmulator` —— 零调用。
3. `SdkProxyUtils.getSignMd5`（签名证书 MD5）—— 零调用。

真正**生效**的"检测"仅有一项，且**只上报不处置**：

4. Bugly `ab.q()`（18 条 su 路径 + `test-keys`）→ 结果作为 **`A13` 字段随崩溃报告上传**到 `android.bugly.qq.com/rqd/async` 等；游戏本体没有任何基于该标记的分支（无弹窗、无踢线、无功能禁用、不进入游戏服务端）。

另外两类**容易被误读成"客户端反作弊"**的东西：

5. **服务端权威的战斗校验**：12102 上传 `begin_seed/last_seed`（+ 无尽模式客户端 md5 令牌），服务端可回 `50005` 且 `req_id=23002`（战斗错误），客户端行为 = 踢出战斗 + 回收战斗 + `toast("fight.error")`（有 `tip_id` 时用服务端文案）。这是**服务端判定**，客户端无任何本地校验逻辑（本地自查代码被 `pkgType===DevLocal` 关闭）。
6. **服务端封禁 UI 闸门**：`_data.banIDs`（服务端下发）+ `isBeingBan()` → 拒绝打开被禁模块并弹 `common.ban_module`；`unBlock=1` 可关。这是运营侧封禁的**客户端呈现**，不是检测。另发现**服务端授权的 GM 后门**（登录响应 `allow_gm=1` → 主界面 GM 按钮 → `GmWin`/`GmDebugPveWin`，可本地构造战斗并 `noServer` 跳过上报）。

### 4.1 现有广告链（完整实测链路）

**11801 的真实性质（重要纠正）** `[实测]`：

- `ModuleProxy extends BaseProxy` 未覆写 `sendMsg` → `BaseProxy.sendMsg` → `xy.net.sendMsg` → `NetMgr.sendMsg`：
  `this._net.request({action:"msg", method:""+11801, data:{type,params}, isCompress:false, channelid:Game})`
  → **11801 是一次真正的服务端请求**，不是纯本地事件。
- 服务端以 **50011** 回执，`MainProxy` 注册 `onMsg(50011, onResUserActionSuc)`（`@6185441`）→ `gms.dispatchEvent(ResUserActionSuc + "_" + req_id)` → 客户端 `onResActionSuc(11801, ...)` 的监听者被唤醒（`ComSucWin.onAdUpdate` `@2237495`、`QuickRewardWin.onAdSuc` `@7632361`）。
- 也就是说：**广告奖励/列表刷新走的是服务端回执链路**，而 11801 请求体里**没有任何"广告确实播过"的证明**（只有 `type` + 调用方透传 `params`，多数调用点为 `undefined`）。

**关键佐证：服务端确实按 11801 记账** `[实测]`（`ExploreRewardModel.ts`，用 `script_index.tsv` 切片）：

```
getAdLeftTimes()    = adLimitTime - getAdTimes()
canWatchAd()        = getAdTimes() < adLimitTime
```

即"已看广告次数 `AfkReward.AdTimes`"是**服务端持有的计数**，客户端只做展示与前置判断；`QuickRewardWin.onClick("btnAd")` 正是 `exploreReward.canWatchAd() ? ad.tryWatchAd(AdType.GUAJI) : toast(900104)`。
→ **服务端唯一能知道"这次广告看完了"的入口就是 11801**（`{type:GUAJI}`）——这也解释了为什么 `onWatchAdDone` 必须发 11801，以及为什么"跳过播放但保留 `onWatchAdDone`"在服务端视角与官包完全等价。

### 4.2 推荐路径（按一致性从高到低）

| 方案 | 挂点 | 优点 | 需照看 |
|---|---|---|---|
| **P1（推荐）** | `AdModel.prototype.canSkipAdWatch` → 恒 `true`（或让 `xy.D.privilege.getPrivilegeValue(PrivilegeType.SkipAd) > 0`） | **改动最小**：`SdkUtils.watchAd` 内部本就存在该捷径（原本给"免广告特权"用），走完 `e.run()` → `onWatchAdDone` → **11801 与真实播放路径完全一致**（`{type, params}` 不变）；不触发 `xyMini.watchVideoAd`，不发任何广告请求 | ①`getAdInfo` 仍需 `canWatch===true`（即 `Video.Advertisement[type].times > 0`），否则 `checkWatchAd` 提前拦截；②特权值可能被服务端下发的特权数据覆盖 → hook getter 而非写数据 |
| P2 | `SdkUtils.watchAd(e)` 直接 `e.run()` | 语义最直白，完全跳过广告平台与原生 | 与方法 1 等价；注意保留 `e.run()` 的调用时机（不要改成同步返回 true 而不 run） |
| P3 | `AdModel.doWatchAd` → 直接 `onWatchAdDone(type, params, handler)` | 连 `uploadAdAction` 都不经过 | 若日后 `uploadAdAction` 变成非空实现，会与官方路径产生差异 → 需同步补上 |
| ✗ 不推荐 | 改 `AdModel.getAdInfo().leftTimes/canWatch` | 能绕过 `checkWatchAd` 的拦截 | **会绕过 `watchAd`→`onWatchAdDone`，导致 11801 根本不发** → 服务端不记账、UI 不刷新，反而与官包不一致 |
| ✗ 不推荐 | 在 `uploadAdAction` 里补一个真上报 | — | 官方是空函数；补上报 = **主动增加与官包的差异**，是暴露点 |

### 4.3 需要照看的字段清单

| 字段 | 来源 | 说明 |
|---|---|---|
| `type` | 调用方传入（`AdType`，例：`QuickRewardWin` 传 `c.GUAJI`） | 进入 11801 载荷，必须原样透传 |
| `params` | 调用方传入（`AdModel.tryWatchAd(t, e, n)` 的第 2 参） | 进入 11801 载荷；多数调用点为 `undefined` → 保持"不传/undefined"，不要补 `{}` 之外的东西 |
| `Video.Advertisement[type].times` | 配置表（`xy.cfg.get("Video.Advertisement")`） | 决定 `AdModel.getAdInfo.leftTimes/canWatch`，也参与 `ExploreRewardModel.adLimitTime`；**不要本地放大**，否则 `getAdInfo` 返回值与官包不同（`QuickRewardWin.updatePrivilege` 会读 `cfg("Video.Advertisement").get(c.GUAJI).times` 决定 tips 文案，`adBtnUpdate` 会按 `exploreReward.canWatchAd()` 置灰按钮） |
| `AfkReward.AdTimes`（`exploreReward.getAdTimes()`） | **服务端下发的模块数据** | 服务端广告计数；`canWatchAd()` 的判定依据。**不要本地改**：改了只影响客户端置灰/tips，服务端仍按真实计数；若真的跳过广告却不发 11801，服务端计数不增长，很快 `canWatchAd()` 变 false 且按钮置灰（会比官包更容易暴露"没看广告"） |
| `watchedTimes` | `AdModel.getWatchTimes`（恒 0） | 本版无本地计数，**不要新增计数**（否则反而成为差异） |
| `leftTimes` | `max(times + 0 - watchedTimes, 0)` | 展示型字段 |
| `lastWatchedTime` / `countDownTime` | 恒 `undefined` / `0` | 本版**无广告冷却**；若客户端脚本或改动注入了冷却值，会弹 `common.ad_cool_time` toast |
| `canSkipAdWatch()` 的语义 | `privilege.getPrivilegeValue(SkipAd) > 0` | P1 就是复用它；`PrivilegeUpdate` 事件会刷新特权 → hook 需覆盖 getter 而非一次性赋值 |
| `red_id` | 配置 | 红点，与本链路无关 |
| `PrivilegeModel` / `PrivilegeType.SkipAd` | `mods2/PrivilegeModel.ts` | 若要"做得像真特权"，需同时让特权 UI 与 `canSkipAdWatch` 自洽（否则玩家看到"未购买特权"却能跳过广告——但这属于客户端表现，服务端不可见） |

### 4.4 会破坏一致性的细节（避坑）

1. **别调 `xyMini.watchVideoAd`**：它会走 `doNativeWatchVideoAd` → 华为广告 SDK `loadAd/showAd`（`HwAds`）→ 原生 `handleLoadAdResult`/`handleShowAdResult`（含 `adRetryTimes<=5` 重试加载，`MainActivity.java:611-668`）→ 上报广告链路。P1/P2/P3 都不触发它。
2. **别改 `sendToWeb("onNativeShowAdCb", ...)` 内容**：`{code: canReward, msg:""}`，`code==2` 会被 JS 当失败处理（`mod_SdkUtils.pretty.js:459-466`）。
3. **保留 2.8 s/1 s 的延迟语义（可选）**：真实路径在 `checkWatchVideoAdCb` 前有延时；若服务端对 11801 有频率风控，瞬间返回可能在时间线上"太快"（`[待验证]`，当前无证据表明服务端看时间间隔）。
4. **`isOnReviewMode` 相关 UI 与广告无关但同屏**：`QuickRewardWin.setupUI` 在提审模式下隐藏特权入口（`mod_SdkUtils.pretty.js:487` 判定）——提审服上别开"免广告特权"外观，容易被窗口比对。
5. **免广告 ≠ 免上报**：任何方案都必须让 `onWatchAdDone` 正常执行，否则 11801 缺失本身就是差异。
