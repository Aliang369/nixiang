## 3. 注入实现（为什么是「Manifest 声明 Provider + 页面内 JS 补丁」）

游戏是 **Cocos Creator 3.8.8 `web-mobile`（H5）跑在 X5 WebView 里**，APK 内没有游戏业务逻辑（14 MB 业务脚本全在 CDN，且包内离线包停在 2026-06-24 旧构建），因此**不能在包内改游戏资源**。选定形态：

| 组件 | 作用 |
|---|---|
| `StarryInitProvider`（框架自带） | 加载 `libstarry_magic.so` → `SignSpoof.install()`（本作包名不在其名单内，等价 no-op）→ 启 `MenuService` |
| `CzbhzH5Provider`（本作新增，**只被 Manifest 引用**） | 注册 `ActivityLifecycleCallbacks`，在 Activity 创建/恢复时调 `StarryH5.attachTo()` |
| `StarryH5`（本作新增） | 遍历 View 树找到游戏 WebView → 反射 `addJavascriptInterface("StarryH5")` → 守护线程周期注入补丁 |
| `assets/starry/czbhz_patch.js` | 页面内补丁：实现 5 项功能，幂等 + 自延迟等 `window.xy` 就绪 |

**为什么加 Provider 而不改游戏 dex**：Provider 只需 Manifest 声明即可由系统实例化，于是**游戏三个 dex 与 `resources.arsc` 可以保持零改动**（本作 dex 侧唯一新增是只含 `com/starry/**` 的 `classes4.dex`），把"改包"的爆炸半径压到最小。

**本次修掉的两个真实缺陷（都在注入通道，不在功能逻辑）**

1. **`loadUrl("javascript:…")` 被 URL 解析吞掉，且完全静默**：`javascript:` URL 会做百分号解码，补丁注释里一处 `%233280` 解出 `#` 触发片段截断 → 脚本被切断在块注释中间 → 整段语法错误被 WebView 静默丢弃（logcat 零报错，注入侧日志全正常，只有补丁一行日志都没有）。改用 `evaluateJavascript`（按名 + 参数个数反射，兼容 `android.webkit` 与 X5 两套签名），退路 `loadUrl` 做 `%`→`%25`、`#`→`%23` 转义；补丁里那处 `%` 也改写掉。
2. **`about:blank` 阶段注入的补丁不会跟到真正的游戏页**：换文档即换 JS 上下文，必须再注入 → 守护保持周期注入而非一次性注入。

现场取证手法：本作三处硬编码 `setWebContentsDebuggingEnabled(true)`，故 `adb forward tcp:9222 localabstract:webview_devtools_remote_<pid>` 后可用 CDP 在页面内直接求值（`typeof window.StarryH5` / `window.__czbhz_v1` / 资源请求列表），这是定位缺陷 1 的关键。

### 4.5 离线行为回归（进不去游戏时，功能逻辑的证据从哪来）

§5 的渠道签名阻断使 5 项功能**无法在真机上验证行为**（装得上、注入链全绿、就是进不去）。补的闸门是 `04_scripts/城主别慌张/offline_regression.js`：

- **做法**：Node + `vm` 造 `window` / `window.xy` 仿真，把**即将打进包里的那份补丁源码**（直接从 `assets/starry/czbhz_patch.js` 读）原样跑起来，并用虚拟时钟驱动它自己的 500 ms 主循环（`Date.now`/`setInterval` 可控 ⇒ 能测"超时后切 P2""被冲掉后补装"这类时序行为）。
- **仿真保真度**：`attr` 用真实数字键（`1001/1002/1005/1101/1103/1200/3001/3046`）；`li.teams` 分两种形态，取自 dumped 代码 —— **PVE 只有我方一队**（`startLocalPveFight`）、**PVP/GVE 两队同数组**（`buildPvpLogicInput` / `onResGve`）。
- **25 项断言**分 6 组：装载与守卫 / 授权门控 / 免广告（含 P2 与自愈）/ 战斗四项 / 鲁棒性 / 源码级地雷。`node 04_scripts/城主别慌张/offline_regression.js` ⇒ **25/25 通过**。
- **它抓出一个真 bug**：`移速` 原先写在 `if (isMine)` 外面 ⇒ **PVP/GVE 里对手也被一起加速**（用例实测对手 `speed` 90 → 270）；PVE 因只有我方一队而看不出来。已修（`spd` 移回 `isMine` 内），修后全绿。
- **已接入管线**：阶段 `offline_regression` 位于 `impl_mod` 与 `build_so` 之间，且 `build_so.requires=[offline_regression]` ⇒ **补丁逻辑不过关不许出包**。
- **边界**：它证明补丁的**判定/写入/幂等/自愈**，证明不了游戏内最终效果（服务端种子重放、`dam_bonus` 的实际倍率语义仍是 §7 的待验证项）。

## 5. ★ 阻断：华为渠道重签名后平台登录静默卡死

### 5.1 现象

安装后启动，盒子停在**"正在疯狂加载.."**加载页；**没有华为登录弹窗**；logcat **零报错**。HMS 初始化事件走完、乐玩 SDK `activeLog` 成功（`response: {"code":1,"msg":"success"}`）后**再无任何动作**，盒子**从未请求** `https://tf-api.shryou.com/sd/config`（次数 = 0）。

### 5.2 单变量 A/B（决定性）

| 组 | 内容 | 签名 | 实测 |
|---|---|---|---|
| 控制组 | 官方原包 | `CN=XingXuan, O=XingXuan`（广州星玄）SHA-256 `f9732a3f…` | ✅ **正常拉起华为 ID 登录界面**（HMS Core 进程 4593 内 `LoginOrRegisterBySmsActivity` / `StartUpGuideLoginActivity`，`hasAccount: false`），并继续走到盒子配置请求 |
| 实验组 A | **同内容**、仅换签名 | `CN=StarryMagic` SHA-256 `83c5cc0b…` | ❌ 同样卡加载页，**从不触发**登录界面，`sd/config` 请求 0 次 |
| 实验组 B | 原包 + mod（星空包） | `CN=StarryMagic` | ❌ 同上 |

实验组 A 由 `diag_resign_only.sh` 产出，脚本闭环断言证明它「与原包 **5099 条非 META-INF 条目逐字节相同**，且不含 `classes4.dex` / 补丁 / `libstarry_magic.so`」—— 即**除签名块外与原包无差别**。

⇒ **变量是签名**，不是我们的 mod 代码；也不是设备/HMS 环境（同机同时刻官方原包能登录）。

### 5.3 为什么 `SignSpoof` 兜不住

`SignSpoof` 只替换**本进程** `PackageInfo.CREATOR` 的反序列化结果。而校验发生在**华为自己的进程 + AGC 服务端**（按注册的签名指纹认应用）。本包内读取签名的三处：

| 位置 | 用途 | 对本应用签名的意义 |
|---|---|---|
| `com/huawei/hms/utils/PackageManagerHelper` | HMS SDK 工具（`getPackageInfo(…,64/128)`） | 用于校验 **HMS Core 自身** |
| `com/huawei/secure/android/common/sign/HiPkgSignManager` | 华为安全公共库 | 本包内**零调用者** |
| `com/blankj/utilcode/util/AppUtils` | blankj 工具类 | 应用侧**零调用**（死代码） |

**没有任何一处是"校验本应用签名"** ⇒ 本进程内无可挂钩点。华为侧究竟卡在本地 hwid 校验还是 AGC 服务端指纹，未取到直接证据（列 §7 U8）。

### 5.4 对交付形态的影响

| 路线 | 可行性 |
|---|---|
| **换非华为渠道包**（官方/TapTap/4399/应用宝…） | **推荐**：线上代码是 CDN 同一份（`yyplat=lwazbox`），§6 的 5 项功能钩子与渠道无关，**补丁/入口/功能表可整体复用**，只需重做渠道适配（包名、`SignSpoof` 名单、`pipeline.json` 参数） |
| 改盒子渠道配置绕过华为登录 | 待评估：`lwsdk.xml` 内 `channel=lewan` / `lw_channel_type=huawei`；若能让包走不绑签名的渠道（乐玩自有/游客）可保住华为包体，但可能换账号体系，且渠道可能被服务端校验 |
| 保持官方签名（不动 APK） | 只能本机实测：root/LSPosed 注入本进程，或本地 MITM 改写 CDN 的 JS（本包 `network_security_config.xml` **信任用户 CA + 允许明文**，技术上可行）；**不是星空版形态** |
| 华为渠道 + 星空包 | **不可交付** |

## 10. 方法论教训（候选，待审批后才并入 `skill/`）

1. **`loadUrl("javascript:…")` 不可用于注入长脚本**：它经过 URL 解析（百分号解码 + `#` 截断 + 长度/转义问题），且失败**完全静默**。H5 注入一律用 `evaluateJavascript`（X5 与 `android.webkit` 签名不同，按名 + 参数个数反射兼容）。
2. **平台渠道可能把签名指纹绑定到登录**：华为渠道（AGC/HMS）重签名后登录静默卡死且零报错。**判定手法**＝"内容与原包逐字节相同、只换签名"的对照件 + 官方原包控制组，单变量 A/B。
3. **跨进程校验是 `SignSpoof` 的边界**：它只改本进程 `PackageInfo.CREATOR`；凡校验发生在别的进程或服务端，一律兜不住。（与"百分之一"的结论一致：登录不绑签名是例外，不是通例。）
4. **H5 游戏的现场取证**：`setWebContentsDebuggingEnabled(true)` + `adb forward` + CDP 求值，比对着 logcat 猜快得多（本次靠它把"补丁没执行"从猜测变成事实）。
5. **别把环境问题当环境问题**：本作三次改判（真机缺 HMS → 怀疑 MuMu 的 HMS Core 残缺 → 最终由 A/B 定案为**签名**）。教训：先做**同机同时刻的对照**，再谈归因。
6. **进不了游戏时，"行为证据"要用仿真补**：把补丁源码丢进 Node + `vm` 造的游戏对象仿真里跑，能测出判定/写入/幂等/时序自愈 —— 本作靠它抓出一个**只有 PVP 才暴露**的作用域 bug（PVE 的 `teams` 只有我方一队，所以单机测试永远看不见）。前提是仿真对象按 dumped 代码分形态搭（PVE 单队 / PVP 双队），否则就是自欺欺人的"自测通过"。
7. **APK 成品 md5 不能当身份**：同源码连跑两次 `surgical` 得到不同 md5（gradle/签名块时间戳不可复现）。要比就比**不变量**：游戏 dex/资源 sha256、条目数、包内补丁/so 的 md5、签名者。
