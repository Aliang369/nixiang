## ② `showGM` 与 GM 窗口清单

### 2.1 `showGM` 的真身：**不是 GM 面板开关，而是"免 SDK 直充"开关**

**【事实】** 全库 `showGM` 只出现 **1 次**，在 `SdkUtils.ts` **L109**，位于 `SdkUtils.pay()` 内：

```js
if (h.pkgType !== m.DevLocal && 1 != a.config.query.data.showGM || n.isNative) {
    // → 走平台支付 SDK：xyMini.pay(v)
} else {
    o.proxy.pay.reqCharge(e, g, i)   // → 走服务端充值协议 10402
}
```

真值表（`h=GlobalVar`, `m=GamePkgType`, `n=PlatformJudge`）：

| pkgType | showGM | isNative | 走的路径 |
|---|---|---|---|
| 非 1（非 DevLocal） | `1` | `false` | **`proxy.pay.reqCharge` → 协议 10402**（服务端测试充值） |
| 非 1 | `1` | `true` | 平台支付 SDK（原生壳覆盖，showGM 无效） |
| 非 1 | 未设/≠1 | 任意 | 平台支付 SDK |
| `1`（DevLocal） | 任意 | 任意 | `proxy.pay.reqCharge` → 10402 |

**结论**：`showGM=1` 只在 **H5（非原生）环境**下生效，作用是让"充值"不再唤起平台支付，而改发**服务端充值协议 10402**。它 **不控制任何 GM 面板的显示**，与 GM 入口无关。**【推断】** 名字取自"显示 GM/测试充值"。**【待验证】** 服务端对非白名单账号的 10402 是否放行。

### 2.2 GM 入口的真实门控：服务端 `allow_gm`

**【事实】** `MainProxy.ts` **L42**（收 30001 登录响应时）：
```js
c.allowGM = 1 === n.allow_gm || c.pkgType == a.DevLocal,
```
- `c` = `GlobalVar`，`c.allowGM` 默认 `false`（`GlobalVar.ts`：`allowGM:!1`）
- `n.allow_gm` 来自**登录响应包**（服务端字段）

**【事实】** 主界面按钮可见性 = `allowGM`：`MainTabBar.ts` **L67–69**
```js

t.get("btnGm", R.allowGM),      // R = GlobalVar；BaseViewComp.get(name, visible)
```

**【推断/关键】** 因此 **`?showGM=1` 不会让 GM 按钮出现**。要让 GM 入口出现，必须满足其一：
- (A) 服务端登录响应里 `allow_gm == 1`（白名单账号）；
- (B) 让客户端认为 `pkgType == 1 (DevLocal)`。

(B) 的两条客户端路径（**【事实】**）：

1. **URL 参数**：`LoginView.ts` **L60**

⚠️ 注意 `Main.ts` **L45** 在 `beforeInit()` 里会把 `pkgType` 强制回 `H5Release(2)`：

`beforeInit` 在启动早期执行、`LoginView.initShow` 在拉完 `config/version` 后执行，**后者更晚**，所以 `pkgType` 参数**大概率**最终生效——但这条时序链 **【推断】**，需真机验证（见 §7）。

```js
var o = "ws://" + a.game_ip + ":" + a.game_port;
```

### 4.3 关键结论（回答"启用内置 GM 会被服务端记录吗"）

1. **会被记录的部分（服务端一定可见）**：
   - `GmWin` 的**提交命令**（10405）、**发道具**（10401）；`GmSpecWin` 的每条命令（10405）；`GmWin` 的 `Fight <id>`（12101）；`showGM=1` 的充值（10402）。
   - **`GmFightWin.btnJump`** 在真实战斗里会发 **12102**，且带着"种头=种尾"的破绽。
2. **不会被服务端看到的部分**：所有纯调试位（`debugFight` 的 11 个位中除 `FightJump`/`AutoFight` 会影响结算时序外都是渲染级）、`GmDebugPveWin` 全流程、`GmSelectCard*`、`nofight`/`unBlock`/`debugCity`/`noModel`/`noFloatingText`/`noguide`/`drawCircle`/`barH`/`checkCfgWord`/`testGuide`/`guide`/`abTest`/`cfgTag`/`useZfb`…（全部纯客户端）。
3. **服务端拒绝时的降级方式**：**几乎没有**。客户端只有
   - `FightProxy.onResError` 特判 `req_id == 23002`（战斗数据异常）→ `excapeBattle` + `recycleFight` + toast；
   - 其余错误统一 toast；
   - 12102 超时弹「重新提交」；
   - **没有任何"GM 被拒后回滚本地状态"的逻辑**。也就是说：**如果服务端不认 GM 操作，客户端通常会卡在等待响应/超时的状态**，而不是自动降级。

### 5.2 逐条"能否只靠 URL 参数触发"

> ⚠️ `Battle.onBattleEnd` 的第一个条件 `l < b.Explore` 是**字符串比较**（`l = getFightType(fight_id)` = `fight_id` 的前 3 个字符，`b.Explore = "101"`）。字符串序下 **只有 `"100"`（`GmSelfPvP`）满足 `"100" < "101"`**；`"102"`–`"106"`、`"200"`+、`"600"`、`"900"`+ 全部为 false，必须靠 `param.isQuick` / `param.noServer` 才能跳过 12102。**【事实】** 这是判断"某条快速结算路径会不会上报"的关键前提。

### 5.3 `SureVictory` / `DamageType.Immune` / `DamageType.Invincible` —— 实证结论

**【事实】** `BattleConst.ts`（来自主 bundle `bundle.c0e2a.js`）L40–69：


  只有 **105 王国 BOSS** 和 **106 无尽** 两个玩法的胜利条件用 `SureVictory`——这是**玩法配置层面的"打赢就结算"**，不是调试开关，也无法从 URL 打开。

- **`DamageType.Immune = 302`**：**【事实】** 全库 27 处引用，**全部是"消费方"**（飘字显示 `M`、字号、`fight_other` 资源、`MoveByCfgListBehavior` 的特判、`OnHurtEvent` 的 `L==o.Immune && (Q=e.after_hp)`、`WallImmuneComponent` 的城墙免疫计数）。**没有任何一处可由客户端开关产生 `Immune`** ——它由战斗逻辑库（`xy.battleClient.battleLogic`）在跑伤害结算时给出。

- `?debugFight=128`（屏蔽受击闪白）+ `?debugFight=64`（屏蔽 Buff 特效）→ 只是"画面不闪、特效不出"，**血量照掉、照样会死**；

- `?debugFight=512`（屏蔽移动）→ 敌人/单位**瞬移代替移动**，不是免伤。

| **`10401` 刷道具** | 上行、且服务端在独立算战力（30402 + `compareServerPower`），道具/战力对账容易发现。**禁用**。 |
| **`showGM=1`（10402 测试充值）** | 充值流水无平台订单号。**禁用**。 |
| **`?pkgType=1` / `mockUrlParams.customPkgType=1` 常态化** | 会把 `pkgType` 从 6/4 伪装成 1，进而：① 战斗连接从 `wss://domain:450/...` 退回 `ws://<game_ip>:<game_port>`（明文；`LoginView.ts` L68 主连接 / `Battle.ts` L535 GVE 房间）；② 埋点条件 `pkgType > DevLocal` 失效，`sendBurialPointNow` 的门控变化；③ `isTest()` 为真，部分开发分支（`FightUtil.getAllSkill` 系列、`Battle` 结果比对 `pkgType===DevLocal`）会被打开。**只建议在临时调试期开启，出包版本保持真实 pkgType。** |
| **`battleEditor=1`（postMessage 战斗编辑器桥）** | 允许父窗口下发 `applyRuntimePatch / startWithUnitData / resetBattle`，等价于把战斗运行时完全暴露。**禁用**。 |
| `testHard` / `testHard2` | 只在 `GmSelfPvP(100)` 战斗生效，且会刷 250/400 只怪 + `showStats()`。既非生产可用，触发条件又依赖 GM 面板。**不提供**。 |
| `debugLog` 全开 / `log=1` | 非 DevLocal 时 `Logger.setTags(null)` 会关掉全部日志（`LoginView.ts`），强行打开会让 `NetMgr.sendMsg` 的 `sendMsg====>` 明文日志暴增。**仅在排障时临时开**。 |

### 6.4 落地建议（星空版形态）

1. **注入层**：在 `xyMini` 上补一个 `mockUrlParams`（客户端覆盖 6 个键），**不修改原生已拼好的 URL**——这是最小侵入、最可回滚的接入点。
2. **功能层**：把「战斗加速」做成 `xy.fight.debugSpeedUp` 的滑杆（0/1/5/20/100），把「跳过技能选择」做成 `config.query.data.debugFight |= 32` 的开关；两者都**不发协议**。
3. **预演层**：把「本地试打」做成 `xy.fight.debugPveFight({fightId, roleList, msg:{seed,drop_seed}, isQuick:1, quickCount:0, noServer:1})`，并**在 UI 上明确标注"本地战斗，不上报"**。
4. **不要**暴露 `GmWin` / `GmFightWin` / `GmSpecWin` 原面板——它们混了 10401/10402/10405 三条上行路径，隔离成本高于重写。
5. 每次星空版发版前，用 `NetMgr.sendMsg` 的 `Logger.logBusiness("sendMsg====>", id, data)` 做一次**上行协议白名单核对**，确认没有 10401/10402/10405 漏出。
