## 1. 背景与要解决的问题

- 现状痛点：同一游戏版本内，战斗逻辑闪退、功能失效、新增功能等改动都需要重打 APK、重传、用户重下整包（工作区内实际包体从数百 MB 到 2.5 GB 级）。
- 期望形态：游戏相关 native 逻辑全部放后台；客户端首次自动获取，之后只在有更新时重新下发；壳只做接收器 + 框架 UI。
- 关键判断：该方向可行，且现有 OTA 已具备约 70% 的地基；缺的是插件化契约、游戏指纹绑定、原子落盘与自动回滚、动态菜单 schema、自动拉取状态机。

## 2. 目标与非目标

目标：

- 壳 APK 一次发布后尽量冻结，常规修复/调数值/加功能不动 APK。
- 首次自动获取；本地已有相同产物时零重复下载（sha 相同跳过）。
- 更新原子生效；坏包可自动回滚；错指纹绝不跨发。
- 全程可运营：撤销/下架、客户端自动回退、发布审计；不灰度、不做客户端遥测（D8/D9）；采用率与崩溃收集暂缓（2026-10-05 用户决定先不做）。

非目标：

- 不追求进程内热替换 so（Android 下不可靠，风险远大于收益）。
- 不把 dex/smali/注入点/签名回灌远程化，这些仍属壳级改动。
- 不为省流量做 so 差分更新（当前 so 规模下不值得；后续变大再评估）。
- 不在本方案内决定反检测强度升级；只把「远程加载带来的可见面变化」列为风险。
- 不在下载层做访问控制：无登录、无签名 URL、无业务限流；只保护服务器自身不被入侵攻击。
- 不在本期做客户端遥测/日志上传（D9）；全量日志与崩溃收集暂缓（2026-10-05 用户决定先不做，需要时再议）。

## 3. 当前实现盘点（事实依据，2026-10-05）

已具备：

- 后台每游戏只维护一份 latest，JSON 与 so 可合并发布，版本号必须递增：`auth-server/app/services/ota_store.py` `publish()`。
- 客户端按 `ver > local` 判断更新；逐文件 sha256 相同则跳过下载：`app/src/main/java/com/starry/magic/ota/PlayOtaManager.java` `downloadAndApplyLocked()`。
- 下载后 sha 校验 + HMAC 验签；签名载荷 `game_id|ver|json_sha|so_sha|note`：`PlayOtaManager.java`、`app/src/main/jni/Main.cpp` `mb_nativeVerifyOtaSig`、`ota_store.py` `sign_payload()`。
- 有 OTA so 就只加载 OTA，不退回包内旧逻辑；乐变双 classloader 有独占副本逻辑；加载失败兜底包内 so：`app/src/main/java/com/starry/magic/ota/StarryNativeLoad.java`。
- 覆盖安装新 APK 后用 `STARRYSTAMP` 比较包内 so 与 OTA so 新旧，避免旧 OTA 顶掉新包：`PlayOtaManager.invalidateOtaIfApkUpdated()`、`OtaSoStamp.java`。
- 服务端有按 IP 的 OTA 限流、so 下载需卡密会话、manifest 可匿名查询：`auth-server/app/security_guard.py`、`auth-server/app/routers/ota.py`、`auth-server/app/config.py`。

缺口：

- 自动拉取未接启动链：只有设置页手动「检查更新」按钮触发（`NativeMenuController.java` `startPlayOtaCheck()`）；启动路径只应用本地已有 patch.json，不下载（`MenuService.java` `bootstrapNativeIfNeeded()`）。
- manifest 只有 `game_id + ver`，没有游戏版本/metadata 指纹/ABI/shell API 绑定。
- 客户端落地是「删旧文件 → 逐个 rename」，非原子；服务端 publish 也是 unlink + move，均无断电/中断保护。
- 后台只有 latest，没有历史版本、last-known-good 与撤销；客户端清除补丁是整目录删除，无「回退上一版」语义。
- 验签为 HMAC-SHA256，密钥同时存在服务端与客户端 so（`grant_pepper()`），属防篡改混淆级，不是强安全边界。
- patch.json 目前只有 hzsj 有真正应用入口，其余游戏下载后忽略（`Main.cpp` `mb_nativeApplyPlayPatch` 注释）；其他游戏的 OTA 实际就是整份 so 重发。
  - D10 定案：直接移除该通道，客户端不再应用 patch.json 差分，统一按整份 so 下发/覆盖。
- 菜单功能项编译在壳内，新增功能仍需重发 APK。

## 4. 目标架构（五块）

1. 壳 APK：通用接入点（Application/Provider 注入、签名处理、卡密登录、心跳）+ 框架菜单 UI + 下载器/加载器 + 基线 so。每游戏一个冻结壳，同一份源码构建。
2. core so：稳定 ABI 的宿主层，负责菜单渲染、配置、插件加载、A/B 落盘、自检、回滚；不含任何单个游戏的业务逻辑。
3. 游戏插件 so：一个游戏 × 一个游戏指纹 × 一个 ABI 一份，包含全部 hook/RVA/数值/功能逻辑；按 feature id 向宿主注册实现。
4. 后台：按变体存 so 与元数据，负责签名、发布、撤销/下架、发布审计与服务器自身安全防护；灰度与采用率看板不在本期范围（D8/D9）。
5. 构建流水线：按游戏指纹构建 so、自动生成元数据、过门禁后发布，不再手工敲 ver/note。

数据流：

```text
壳启动 -> 识别(game_id/fingerprint/abi/shell_api)
       -> 查 manifest(匿名, 节流 1 分钟)
       -> 有匹配更新 -> 后台下载 so（无需登录）
       -> 校验(sha256/签名/指纹/ABI/shell_api)
       -> 写非活动槽 -> 原子切换
       -> 下次冷启加载 -> 自检 -> 成功标记 / 失败回滚
```

## 5. 核心契约

### 5.1 标识与版本模型

变体键（六元组，缺一不可）：

```text
game_id + channel + game_fingerprint + abi + shell_api + payload_ver
```

- `game_id`：游戏标识（与现有 auth game_id 对齐）。
- `channel`：TapTap/4399/小七/Google 等渠道差异（可空表示通用）。
- `game_fingerprint`：至少覆盖游戏版本号、关键 so（如 libil2cpp）sha256、global-metadata.dat、官方热更资源版本/内容哈希；口径沿用 `skill/re-extract/hotupdate-fingerprint-recheck.md` 的三查。
- `abi`：arm64-v8a / armeabi-v7a，必须与进程一致。
- `shell_api`：core ABI 版本区间（min/max），壳太旧不收新 so。
- `payload_ver`：单调递增整数；同时保留 `payload_id`（内容哈希短 id）便于人工核对。

### 5.2 manifest 字段（新增字段只增不改）

- 变体键字段、`ver`、`note`、`payload_id`
- `so_sha256`、`size`、`abi`、`game_fingerprint`、`game_ver`
- `min_shell_api` / `max_shell_api`
- `sig_hmac`（旧客户端兼容）、`sig2`（Ed25519，新客户端）
- `mandatory`、`restart_policy`
- `status`（draft/active/revoked）、`revoked_vers`
- 下载地址（相对路径或短期签名 URL）

### 5.3 插件 ABI

- 宿主初始化时传入函数指针表：UI 注册、配置读写、日志、内存读写、hook 注册、RVA 解析、feature 注册、自检上报。
- 版本号 `STARRY_ABI`，只走 C 接口；禁止 C++ 符号、STL 容器、异常跨边界。
- 入口：`starry_plugin_init(const starry_host_api_v1*)`，返回描述体（支持的游戏指纹、ABI 区间、feature 列表、自检函数）。
- 宿主按描述体决定是否加载；指纹或 ABI 不匹配直接拒绝，不尝试兼容。
- 插件不做 UI 渲染；如需自定义 UI，只能通过宿主提供的受限接口。

### 5.4 动态菜单 schema

- feature 由后台随 manifest/配置下发：`id`、类型（toggle/slider/input/button）、范围、默认值、分组、可见条件、排序。
- 壳只负责渲染与交互，插件按 `id` 绑定处理器。
- 关键不变量：菜单串自检（feature 数与 id 集合）必须与 manifest 一致；多一项即视为越界。

### 5.5 签名与完整性

- 目标态：Ed25519，私钥只在后台，公钥按 key id 编进壳；sha256 管完整性，签名管来源，撤销列表管旧版本。
- 过渡态：保留现有 HMAC 字段供旧客户端使用；新客户端优先验 Ed25519，双签并行一段时间。
- 反降级：客户端记录已应用过的最高 ver；服务端可下发 revoked_vers，命中即回退。
- 威胁模型澄清（2026-10-05 讨论）：签名不用于阻止用户本地改 so 自用（无法阻止，也不值得防）；它防的是攻击者控制客户端下载来源（DNS/中间人/CDN 投毒/后台被攻破）时把伪造补丁推给全体用户。若判定该风险可接受，保留 HMAC 即可；若不可接受，选 Ed25519 过渡双签。注意 Ed25519 公钥必须在壳内，以后升级需要全量换壳，所以现在做成本最低。
- 用户已确认（2026-10-05）：D6 选方案二（过渡双签）。老客户端继续验 HMAC，新壳客户端优先验 Ed25519；授权 grant 密钥、老客户端 OTA HMAC 密钥、新客户端 Ed25519 密钥对三者分离；APK keystore 保持不变。

### 5.6 多版本识别与路由（2026-10-05 用户确认方向）

目标：同一游戏多个版本同时存在时，为每个版本下发各自的 so，互不覆盖；识别不到时用壳内烧录的版本信息兜底。

识别三层，逐层收窄：

1. 构建期烧录（权威兜底）：打包壳时把 package、原始 versionCode/versionName、channel、目标 game_fingerprint、shell_api 固化进壳（asset 或生成的配置类），不依赖运行时读取。
2. 运行时读取：PackageManager 的 versionCode/versionName；乐变 overlay 等场景下该值可能不可靠（已有 STARRYSTAMP 误判教训），读取失败或与烧录值冲突时以烧录值为准。
3. 运行时指纹：关键 so（如 libil2cpp）/global-metadata.dat/官方热更资源的哈希，作为最终判据；版本号相同但内容不同也能区分。

manifest 请求至少携带：game_id、baked_build_id、version_code、version_name、channel、abi、game_fingerprint、shell_api。

服务端匹配优先级：精确指纹 >（game_ver+channel+abi）> baked_build_id；全部未命中返回「无补丁」，禁止兜底到其他变体的 so。
（以上优先级为 D14 定案，2026-10-05 用户确认：全不命中不发，且禁止跨变体兜底。）

服务端按变体表存储：同一 game_id 下允许多个游戏版本并存，发布时强制指定目标版本；旧版本用户继续使用自己的旧 so，不因别的版本发布而变化。

构建流水线：每打一个游戏版本的壳，生成版本清单（版本号+指纹+渠道+ABI）随壳烧录并登记后台；新增游戏版本时后台新增变体即可。

### 5.7 壳粒度与基线 so 的定义（2026-10-05 讨论澄清）

D1「每游戏冻结壳」的准确含义：

- 一套共享壳源码，每游戏、每游戏版本一份构建配置与冻结产物；不为每个游戏 fork 一套代码。
- 壳内包含：目标游戏接入点、签名/登录处理（如涉及）、菜单框架、下载器/加载器、烧录的版本与指纹信息。
- 冻结范围是「该游戏该版本的壳」：壳发布后，mod 逻辑更新只发远程 so，不再重打壳。
- 官方游戏出新版本仍需为新版本重打壳（因为 mod 壳是叠加在官方包体上的）；新游戏=新增一份壳配置，不是新代码分支。
- 不能用一个通用壳装多游戏：包名/签名/接入点/渠道/ABI 都与具体游戏绑定，mod 必须活在目标游戏进程内。

D2「基线 so」的准确含义：编进壳 APK 的 payload so（即包内 libstarry_magic.so），作为首次启动、无网、回滚时的兜底。

方案 A：内嵌完整当前逻辑。

- 优点：首装时远程 so 未下完或下载失败也能先用完整基线；远程 so 坏包回滚后仍有可用功能；用户无感（本方案游戏需卡密联网，无网场景差异已弱化）。
- 代价：APK 增加一个 so 的体积（当前百 KB 到几 MB，相对游戏包可忽略）；基线会随壳变旧，新功能不在里面；构建流水线需每次壳构建时产出并校验基线。

方案 B：仅最小框架。

- 优点：逻辑单一来源，只有 OTA so 一份；APK 略小；不存在基线与远程版本差异。
- 代价：无网=无功能；远程 so 坏了或服务器不可用，回滚后也无功能；首次体验依赖下载；用户容易误判为“菜单没用了”。

定案（D2）：选 A，保留现有「包内 so 兜底 + OTA 优先」行为；基线作为 slot 0，只保留一个活动 OTA 槽，回滚顺序为当前 OTA → 基线；基线只在壳重建时更新。
用户已确认（2026-10-05）：游戏本身走卡密登录、必须联网，B 的「无网无功能」差异弱化；但 A 在坏包回滚时仍有可用功能，体积代价又可忽略，故仍选 A。D5 同步确认为：客户端只保留一个活动 OTA 槽 + 基线，后台每变体只保留 latest（可下架）；不保留上一 OTA 版本，紧急回退目标为基线。

### 5.8 授权层与下发签名层的关系（2026-10-05 讨论澄清）

- 授权层（卡密登录/一机一码）：账号、卡密、设备绑定、session、心跳，回答「谁能用」。
- 分发层（OTA 签名）：manifest+so 的来源与完整性，回答「这份补丁是不是官方发的、有没有被改」，与用户身份无关。
- Ed25519 公钥对所有客户端相同，同一版本签名对所有用户相同；签名不绑定设备/账号/会话，不参与一机一码。
- 当前实现中两者共用了 grant_hmac_secret（授权 grant 与 OTA 验签同源）；升级时应解耦：授权继续用其 HMAC/session，OTA 单独使用 Ed25519 密钥对。
- 匿名下载与卡密登录可并存：启动时无需登录即可拉补丁；进游戏/开菜单仍按原逻辑卡密+设备校验；签名验证不依赖登录态。
- 防白嫖仍在授权层：so 是公开的（D15 已接受），防止免费使用靠壳/宿主在启用功能前做授权检查，而不是把 so 藏起来；Ed25519 只保证 so 没被别人伪造替换。
- 服务器风险也分开：授权库被拖是授权层问题；OTA 私钥离线保存时，服务器被攻破也不能伪造有效补丁。

### 5.9 三种「签名」的区分（2026-10-05 讨论澄清）

- APK 签名证书（keystore）：Android 安装身份；覆盖安装必须同证书；Android 8+ 的 SSAID 按「真实签名证书+系统用户」分配，因此它决定一机一码里的 v5 设备号。改它才会导致设备号漂移/登录不上。
- 游戏签名伪装（SignSpoof）：把 PackageInfo/SigningInfo 里游戏包的原厂证书回灌给游戏自身/TapSDK/渠道校验；只影响应用内看到的签名，不改变系统分配 SSAID 的真实证书。
- OTA 签名（HMAC/Ed25519）：只校验 manifest/so 是否官方发布、是否被改；不接触 PackageManager，不影响安装身份、SSAID、SignSpoof。
- 设备号链路（现状）：Preferences 缓存 device_id 优先 → v5 SSAID 哈希 → v4 Build 字段哈希 → 本地兜底；登录请求带 device_id + legacy_device_ids。
- 结论：D6 把 OTA 签名升级到 Ed25519 不会影响卡密登录/一机一码；唯一红线是 APK 签名证书（keystore）保持不变，否则 SSAID 变化导致设备号漂移。
- 边界定案（与 D6 一致）：SignSpoof、DeviceFingerprint、auth 相关逻辑留在冻结壳内，不随 OTA 下发，避免补丁影响安装身份与设备号。

### 5.10 回退触发与检查节奏（2026-10-05 讨论澄清）

三条互不依赖的回退通道：

1. 本地回退：OTA so 加载失败、自检失败或崩溃计数超阈值 → 直接回基线；不依赖网络和服务端。
2. 服务端撤销：客户端成功请求 manifest，得到明确的「无补丁/已撤销」状态 → 标记 pending_rollback，下次冷启动忽略并清理 OTA 槽，加载基线。
3. 新版本替换：下载到更高 ver 并校验通过 → 原子替换 OTA 槽；下一次冷启生效。

服务端删除不等于推送：

- 服务端下架/删除后，客户端只有下一次成功请求才得知；未启动的用户仍在使用本地已下载补丁。
- 网络错误、超时、5xx 不得当成「已下架」，必须保留本地补丁按退避重试，避免服务器故障直接导致全部用户掉回基线。
- manifest 必须有权威状态字段（如 `status=active|none|revoked`），不能靠 404 或请求失败判断；404 可能只是路由/缓存异常。

检查节奏（已定，D16）：

- 每次冷启动查一次 manifest（体积小），本地节流 1 分钟（1 分钟内的重复冷启不重复查）。
- 上轮启动失败/触发过回退时，本次强制检查。
- 长会话可选 30–60 分钟轮询 manifest（仅提前预取，生效仍需冷启）；不追求秒级召回，不引入推送通道。
- manifest 走 CDN/缓存 + ETag，降低请求量；下载不做拦截（D15）。

生效时机：运行中只标记 pending_rollback，不强行杀进程；下次冷启忽略/清理 OTA 槽并加载基线。若坏 so 直接导致加载崩溃，由本地 boot 计数在下次启动立即回退，不等待服务端。

### 5.11 D8/D9 定案与影响（2026-10-05 已确认）

D8 灰度：定案「不灰度，只全量」。

- 定义回顾：灰度＝新 so 先给一部分设备（白名单或按比例分桶），验证后再逐步扩大；被否的原因是没必要为它引入白名单/分桶/多版本并存的复杂度。
- 发布节奏：L1/L2/L3 门禁通过 → 直接全量推 latest；出问题靠「服务端撤销/下架 + 客户端下次冷启自动回退基线 + 更高 ver 快速修复版」兜底。
- 与 D5 的关系：不灰度后，后台「每变体只留 1 个 latest」不再需要临时保留两版的窗口，D5 保持纯净单版本模型。
- 代价（接受项）：坏版本一次触达全量；发现依赖用户反馈，止损依赖撤销生效速度（客户端下一次成功检查，冷启 + 1 分钟节流内，见 5.10）。

D9 遥测：定案「本期不做任何客户端回传」。

- 定义回顾：遥测＝客户端把检查/下载/应用/自检/回退结果上报服务端做聚合；三种选项（不上报/仅技术数据/含账号维度）本期都不做。
- 本期行为：壳只在本地维护 OTA 槽状态与 boot_state.json（尝试版本、失败原因、回退计数）；不上传、不新增权限、不采集设备信息。
- 后续独立项目（已暂缓）：全量日志/崩溃收集平台——谁的设备闪退、哪个功能有问题，落日志上传服务端；2026-10-05 用户决定先不做，不属于本补丁平台范围。
- 本地预留（只约束、不实现）：本地错误码与状态文件格式保持稳定（后续若重启该项目可直接复用）；不做上传实现；服务端侧只剩自身访问日志（下载量粗看）。
- 影响：没有采用率/失败率/回退次数看板；坏版本发现靠用户反馈；撤销后客户端在下一次成功检查时回退基线（见 5.10）。

## 6. 客户端运行时

### 6.1 启动状态机

1. 早期启动：读槽位状态与 boot 计数 → 加载当前 OTA so → 失败切基线。
2. 识别：拿到 game_id、fingerprint、abi、shell_api；指纹不匹配直接放弃远程 so。
3. 检查：启动后空闲时查 manifest，本地节流 1 分钟（指纹变化立即查）；manifest 可匿名查。
4. 决策：有匹配更新则自动后台下载，不需要登录/卡密；下载失败按退避重试，不阻塞启动。
5. 校验：sha256 + 签名 + 指纹 + ABI + shell_api 五重通过才落盘；支持断点续传、失败重试、仅 Wi-Fi 等策略。
6. 落盘：写入 staged → fsync → 复核 → 原子替换 ota 槽；基线始终保留为回退位，禁止「删旧再写」。
7. 生效：不热替换；打开游戏即后台预取，下次冷启自动生效，菜单显示「已就绪/重启生效」；首次安装本次启动仍用基线 so。
8. 自检：加载后跑插件自检（关键 hook 是否装上、feature 是否注册）；失败或崩溃计数超阈值自动回退。
9. 防砖：加载前先写「本次尝试版本」标记，下次启动先加计数；连续失败切基线并把坏版本拉黑。
10. 离线/首装：壳内嵌基线 so，保证无网、未登录也能进菜单；OTA 只做覆盖升级。

### 6.2 落盘布局（设计）

```text
files/starry_ota/{game_id}/
  current                 # 指针：ota / baseline
  boot_state.json         # 尝试计数、最后失败原因、已应用最高 ver
  ota/{manifest.json, libstarry_magic.so}   # 整份 so，无 patch 差分数据（D10）
  staged/                 # 下载与校验中的临时目录（校验后原子替换 ota）
```

### 6.3 生效与提示策略

- 默认：打开游戏即静默检查并下载；本次启动仍用已有的 so，下次冷启自动切换；菜单给状态与「立即重启」入口（是否弹窗见决策表）。
- 首次安装：壳内基线 so 保证游戏正常进入；OTA 在后台完成下载，不阻塞启动、不在启动过程强制重启。
- 手动功能移除：设置页不再提供「检查更新」与「清除补丁」，也不保留隐藏调试入口（D13）；应急只走服务端撤销 + 客户端自动回滚。
- 紧急修复：可标记 `mandatory`，弹一次不可取消提示，仍不热替换。
- 用户从不重启：预取完成即生效于下次自然冷启；不强制杀进程。

### 6.4 兼容旧机制

- 保留乐变多 classloader 的副本加载逻辑与包内兜底路径。
- 保留 STARRYSTAMP 守卫，但语义升级为「壳内基线 so 与 OTA so 的构建代际比较」。
- 旧客户端继续走 latest + HMAC；新客户端走变体查询 + Ed25519。

## 7. 服务端与后台

- 存储：内容寻址（sha256 命名的 blob）+ 变体索引 + 发布记录；每变体只保留一个 latest（D5），不保留历史版本。
- 接口：
  - 变体 manifest 查询（客户端上报 game_id/fingerprint/abi/shell_api/channel/current_ver）
  - 制品下载（公开直链，无需登录/签名/设备标识；支持 Range/断点续传）
  - 下载策略：不做业务层拦截与限流（D7/D15）；服务端只保留自身防护——管理端鉴权、game_id/路径校验、上传校验、TLS、基础设施层抗攻击。
  - 接受项：so 可被任何人下载与分析；以签名+哈希+撤销保证不被伪造、不被错发，不以访问控制防提取。
  - 本期无客户端回执/遥测（D9）；不实现上报端点，后续日志项目另立
  - 撤销列表下发
- 发布流程：草稿 → 全量（active）；随时可撤销/下架（D8）。
- 回滚：下架/撤销 latest，客户端自动回退基线；修复版以更高 ver 重新发布（D5）。
- 版本号规则：只增不减；坏版本下架后修复必须用更高 ver 重发，禁止复用旧 ver（客户端记住已应用最高 ver，会拒绝降级或同号）。
- 回退能力边界：自动回退只覆盖加载失败/自检失败/崩溃循环；能跑但功能有缺陷的版本无法自动识别，靠 L3 人工终审 + 用户反馈 + 更高 ver 快速修复处理（无遥测，D9）。
- 分发：先直连 FastAPI，量大后接对象存储/CDN；auth 服务不承载大文件流量。
- 兜底：无匹配指纹返回「无补丁」，绝不返回最近的其他变体。
- 审计：谁在何时发布了哪个版本、何时撤销/下架，全部落记录。

### 7.1 服务端专项（v0.18 新增，已收口）

前置定案（D17，2026-10-05 用户）：不兼容旧客户端与旧协议，按全新一套设计，游戏逐个迁移到新壳。由此直接取消：legacy 指针与旧客户端路由、旧接口双栈兼容期、patch.json 兼容保留。

以下为工程直接落地项（不再逐条询问用户）：

- 变体模型：变体键 = game_id + game_ver + channel + abi（+ shell_api 区间）；每变体独立 latest 与独立 ver 递增；渠道专属查不到时回落通用变体；旧游戏版本变体手动 retire，blob 保留 7 天后清理。
- 撤销语义：下架 = status=revoked 并保留 manifest 记录；404 一律不算撤销；客户端成功检查后才回退基线。
- 存储与原子性：内容寻址 blob（sha256 命名）+ 变体索引；发布 tmp → fsync → 原子切换 + 并发锁；索引只留 latest，blob 保留足够长的在途下载窗口。
- manifest v2：变体键字段、ver、payload_id、sha256、size、abi、game_ver、shell_api 区间、status（draft/active/revoked）、key_id、签名；不再有 patch.json。
- 缓存分层：manifest 短缓存 30–60 秒 + ETag；blob 永久/长缓存（immutable）；下载支持 Range 与断点续传。
- 发布流水线：自动递增 ver、读构建元数据（指纹/ABI/channel/shell_api）、自动签名、变体注册、审计记录；管理端鉴权 + 上传校验 + TLS。
- 观测与容灾：服务端访问日志最小集（下载计数、404/429/5xx、撤销记录）；索引/密钥/审计备份恢复；仍不做客户端遥测（D9）。

已定（v0.19）：

- D18 密钥与撤销签名（用户确认）：Ed25519-only，不做 HMAC 过渡；双钥——payload 私钥离线签，撤销用服务端在线控制钥单独签；客户端内置对应公钥，用 key_id 区分与轮换。
- D19 部署形态与撤销时限（用户提供规模口径）：直连 FastAPI 起步，接口按 CDN-ready 设计；DAU 百级 → 千级阶段请求量可忽略，真正的压力是 so 下载带宽；到 DAU ≥ 1000 或单次全量发布流量 ≥ 50 GB 时接对象存储 + CDN。撤销 SLA 按 1–2 分钟（manifest 30–60 秒 TTL + ETag）。下载 URL 由 manifest 下发，后续切 CDN 不需要换壳。

规模测算（2026-10-05，用户口径：DAU 百级 → 千级 → 上限万级）：

- manifest 查询：按每人每天 2–4 次冷启（1 分钟节流封顶）估算，万级 DAU ≈ 平均 0.3–0.5 QPS、晚高峰个位数 QPS；manifest 是小 JSON + ETag/304，单机直连完全够。
- so 下载：真正的带宽瓶颈。万级 DAU × 5–20 MB ≈ 50–200 GB/次全量发布；单机 100 Mbps 满打满算约 45 GB/小时，会打满出口并拖慢玩家；到千级就应该把 blob 放对象存储 + CDN。
- 访问策略：so 下载去掉卡密会话门禁（D7）；manifest 收紧的 per-IP 限流要放宽或去掉（CDN/NAT 场景容易误伤），服务器自保交给基础设施层（D15）。

后台管理入口（D20 已定）——复用现有 Tab 改造，不新做前端：

- 现状（已核对代码）：管理后台已有「游戏补丁」Tab（`static/admin/index.html` `#page-ota` + `static/admin/js/toasts_ota.js` 的 OTA 段）与「操作日志」Tab（`audit.js`）；后端已有 `/v1/admin/ota` 系列接口与 `publish_play_ota.sh`。

- 发布包格式（D20 细化，2026-10-05 用户）：单个 zip，内含 `manifest.json`（变体键 + ver + sha256 + size + abi + note + key_id）、`libstarry_magic.so`、`manifest.sig`（Ed25519 离线签名）；网页只负责上传，服务端验签 + 校验 sha256/元数据一致后入库；payload 私钥不出现于网页与服务端。
