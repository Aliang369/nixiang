## 一、本轮加的到底是什么防御（与勇士之心同一套）

| 件 | 落点（共享件，非本作私有） | 本作怎么接的 |
|---|---|---|
| 授权链单点（非对称票 v2/v3 + 三判据 + per-feature 掩码） | `jni/Includes/SgAuth.h` | 本来就在 `MainModern.cpp` 里（本作就是这个入口）⇒ 零改动 |
| **自完整性校验** | `jni/Includes/SgIntegrity.h` + `SgZip.h` + `sg_integ_mxyzt.h` | **本轮新接**：mk 开 `-DSG_HAVE_ZLIB=1 -DSG_REQUIRE_INTEGRITY=1`、`-DSG_INTEG_HEADER_FILE='"sg_integ_mxyzt.h"'`、`-lz` |
| 清单生成器（按游戏） | `04_scripts/_common/sg_pki/gen_integ_header.py --game mxyzt` | 本轮新增 `--game` 能力 + 本作条目表 |
| 出包门禁 C1–C9 | `04_scripts/_common/harden_apk.py`（本轮改成**游戏感知**） | 新增 `GAMES["冒险与征途"]` 表项 |
| 门禁共享入口 | `04_scripts/_common/harden_gate.sh`（本轮新增） | `surgical_mxyzt_1.5.9.sh` 第 `[6/7]` 步一行接入 |
| 装机凭证 | `09_test/冒险与征途/harden/<apk_md5>.stamp` | 门禁 PASS 自动写，`pre_install_gate.sh` 查11 认它 |

**本作是 native 型游戏（没有 boot js / 没有功能载荷）** ⇒ 不开 `-DSG_PAYLOAD_ENC`，
门禁的载荷四项（C6 密文新鲜 / C7 载荷层已编译 / C8 无明文泄漏 / C9 服务端已登记）自动记
**N/A**（不是 PASS 也不是 FAIL，见 `harden_apk.py` 的 `Report.skip`）。

完整性清单覆盖 **2 条**：`classes4.dex`（我们的菜单 dex）+ `assets/certs/starlight.crt`（证书钉扎）。
这两条正好对应破解的两条主路「删/换我的卡密 dex」「换证书绕授权」；so 自身由 P2-1 服务端签名
清单覆盖（`SgBuildManifest.h`，本轮未接，见 §五）。

**语义变化（必须知道）**：`SG_REQUIRE_INTEGRITY=1` 让授权链第三判据变成**硬门禁** ——
清单对不上 / 读不到 APK ⇒ `sgauth::live()` 恒 false ⇒ **所有功能静默失效**（菜单照开、开关照点、
没有任何效果，也不闪退）。这是 fail-closed 的设计意图，但对本作意味着**装机后必须先确认
`[V2] g=1`**，否则会表现为「功能全没了」。

## 五、真机回归发现的**框架级 bug**（已修，待登录复验）

### 5.1 现象
小米真机（`96f0d883`）上「卡密登录提示成功，但功能一个都没授权」：

```
AuthClient: POST /v1/auth/login → 200 (2021 bytes)
StarryMagic: [V2] r=0        ← nativeApplyGrant 返回 false（票被拒）
```

### 5.2 根因（代码级定案，非猜测）
服务端 `mint_grant_v3()` 在**该游戏没登记载荷 sha** 时返回 `None`
（`payload_build_key(game_id) is None`），于是登录响应是 `"grant3": null`。
客户端 `Preferences.pickGrant()` 用 `JSONObject.optString("grant3","")` 取票 ——
Android 的 `optString` 对 JSON null **不会**返回空串，而是
`JSON.toString(JSONObject.NULL)` → **字符串 `"null"`**（4 个字符，非空！），
于是 `pickGrant` 把 `"null"` 当票返回；native `sgauth::apply("null")` 找不到 `.` 分隔的签名
⇒ 直接 return 0 ⇒ `[V2] r=0` ⇒ 菜单 UI 显示登录成功、`live()` 却恒 false。

**影响面＝所有「没登记载荷 sha」的游戏**（即除勇士之心外所有新接入游戏）——不是本作个案。
雷电之所以"看起来正常"：它的 prefs 里存着**旧 v1 票**（`1|dev_…|mxyzt|…|edac62e3`），
冷启直接 apply 成功（`[V2] s=1 m=ffffffff`），根本没走 pickGrant 的新票路径。

### 5.3 修复（`Preferences.java`，全端唯一入口）
- 新增 `isValidGrant(s)`：非空、且不是 `"null"`（大小写不敏感）。
- `pickGrant()` 按 grant3 → grant2 → grant 顺序取**第一张 isValidGrant** 的票。
- `getAuthGrant()` 读侧同样过滤 ⇒ 旧包已经落进 prefs 的脏值 `"null"` 一并被净化，不必清数据。
- `isFeaturesAllowed()` 同步改用 `isValidGrant`。

   R 桩自动枚举），功能集未变（四开关串自检通过），但菜单交互需 L3 顺带确认。

   （`SgAuth.h` 过渡分支），所以即便服务端未升级，卡密登录照旧可用，只是享受不到非对称票收益。

   （a）把它改名为契约包名，或（b）显式用该环境变量出同名包，二者都要登记到裁剪清单。
