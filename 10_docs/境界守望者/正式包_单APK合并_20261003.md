# 境界守望者 · 正式包合并为「单 APK 无 root 直装包」

> 日期：2026-10-03 ｜ 关联：[功能阶段文档](./境界守望者_星光改造_功能阶段_20261003.md) §10 ｜ 脚本：`04_scripts/境界守望者/wor_merge_single.sh`

## 1. 为什么要合并

Google Play 的 App Bundle 分发形态是 **Split APK**：官方底包本身就是两个文件

| 文件 | 大小 | 内容 |
|---|---|---|
| `境界守望者_1.6.38.829.1_global_original.apk` | 171,550,562 B | base：`classes*.dex` / 资源 / `assets/Resources.dat`（**`lib/` 条目数 = 0**） |
| `境界守望者_1.6.38.829.1_global_split_config.arm64_v8a.apk` | 33,397,726 B | split：**35 个 `lib/arm64-v8a/*.so`** + manifest + `stamp-cert-sha256` + `META-INF/BNDLTOOL.*`（**无 dex、无 resources.arsc**） |

因为 base 里**一个 `.so` 都没有**，只装 base 会被 `pm` 拒（`INSTALL_FAILED_MISSING_SPLIT`），
所以开发阶段一直走 `pm install-multiple base split`。但交付给用户/后台上传需要**一个自包含、可无 root 直装的 APK**。

拦路属性在 `<manifest>`（不是 `<application>`）上：

```
android:requiredSplitTypes(0x0101064e)="base__abi"
android:splitTypes(0x0101064f)=""
```

外加两个 Play Core `splitcompat` 标记：
`<meta-data android:name="com.android.vending.splits.required">`、`<meta-data android:name="com.android.vending.splits">`
——单包形态下留着会让 `SplitCompat` 去找不存在的 split APK。

## 2. 合并脚本（6 步）

`bash 04_scripts/境界守望者/wor_merge_single.sh`（可用环境变量覆盖 `WOR_ORIG_APK` / `WOR_SPLIT_APK` /
`WOR_SIGNED_BASE` / `WOR_SIGNED_SPLIT` / `WOR_SINGLE_UNSIGNED` / `WOR_SINGLE_SIGNED` / `WOR_NEW_DEX`）

1. `apktool d -f -s --no-assets` 解官方 base，取**文本** `AndroidManifest.xml`
2. 文本 manifest 补丁：
   - 注入 3 个权限：`SYSTEM_ALERT_WINDOW` / `FOREGROUND_SERVICE` / `FOREGROUND_SERVICE_SPECIAL_USE`
   - 注入 `com.starry.magic.StarryInitProvider`（`android:authorities="com.ap.watcherofrealms.starryinit"`、`initOrder=100`）
   - 注入 `com.starry.magic.menu.MenuService`（`foregroundServiceType="specialUse"` + property `android.app.PROPERTY_SPECIAL_USE_FGS_SUBTYPE="MOD menu overlay"`）
   - **保留原 Application 类不替换**（`com.moba.unityplugin.MobaGameApplication`）
   - **摘除**：`android:requiredSplitTypes`、`android:splitTypes`、2 个 `com.android.vending.splits[.required]` meta-data
     （脚本日志：`摘除 [('requiredSplitTypes', True), ('splitTypes', True), ('vending.splits meta-data', 2)]`）
3. `apktool b` 后**只抽回 binary `AndroidManifest.xml`**（51,904 B），其余 apktool 产物丢弃
4. `aapt2` 回读校验：StarryInitProvider / MenuService / authority / `FOREGROUND_SERVICE_SPECIAL_USE` /
   `com.moba.unityplugin.MobaGameApplication` 均在；`requiredSplitTypes` 与 `com.android.vending.splits` 均已消失
5. zip 外科：源 = **已签** starry base（跳过 `stamp-cert-sha256`、`META-INF/MANIFEST.MF`、`META-INF/*.SF/.RSA/.DSA/.EC`）
   → 换入新 manifest → 追加 split 的 **35 个** `lib/arm64-v8a/*.so`（沿用 split 原件 `compress_type`）→ **997 条**（base 966 + 35 lib）
6. 自证 + 签名：35 个官方 `.so` sha256 与 split 逐个一致；`classes6.dex` 在；无 `stamp-cert-sha256`；无签名残留；
   星光 so 内 `[Wor]` ≥1 且 `[Cxswz]` = 0；`zipalign -f -p 4`；用 `01_tools/starry_release.jks`（alias `starry`）签名

### 4.1 已知限制：服务端战斗校验（`FightVerify` 子系统）⇒ 受校验玩法内不可用

游戏内会弹 **「战斗校验结果异常」**。用户实测确认两点：① **关掉功能开关（倍率 ×1、无敌关）不弹，开着才弹**；
② **弹出后该局不算数**（需重打、不给奖励）。本项与「单 APK 合并」无关——合并不触碰任何 dex/so 逻辑，
与 base+split 形态下运行的二进制完全一致。

**机制（静态定位所得，非推测）**：在 `global-metadata.dat` 中挖到完整的战斗校验框架：

```
CreateBattleVerifyFrames                     客户端生成「校验帧」
FightVerifyDataInput / FightVerifyResultDataOutput
FightVerifyType_Normal / _EmbattlePos / _RTA / _OnlyServerRun
DoNotVerify                                  存在「不校验」状态
Error_FightVerify / Error_FightVerify_Overload / Error_FightVerify_Speed_Cheat
Error_EmbattlePosCheat
StartAntiCheat / m_ServerAntiCheat / bConfirmCheating / bMaybeCheat
NetworkReplayController(89 处) / ReplayEngine(74 处) / IsStrictOfflineReplay / AllowLegacyOnlineReplay
```

即：客户端在战斗过程中录制校验帧（`CreateBattleVerifyFrames`）并上报，服务端以 `ReplayEngine` **独立重放**。
我们改写 `stHpChangeData.fValue`（伤害倍率）或清零我方承伤（无敌）只改变**本地**模拟，
服务端用同一批帧重放得到**未修改**的结果，两端不一致 ⇒ `Error_FightVerify` ⇒ 回弹提示。

**为什么客户端修不掉**：既然是确定性重放，**容差为 0**，缩小倍率同样无效。这与本仓
`10_docs/_state/games/咻咻勇者.md` 的判例同类（服务端按自己的战斗记录重放判定 `ret=260001`，
客户端侧清空结算上报亦无效）。

**已评估但未采用的路线**：

- 探测每个玩法的 `FightVerifyType`，圈出 `DoNotVerify` / `_OnlyServerRun` 的玩法——纯读取、零风险，
  但需新增一轮构建 + 装机 + 多玩法实测；**用户决定不再投入**。
- Hook `CreateBattleVerifyFrames` 使其不再产出校验帧——**明确不建议**：`m_ServerAntiCheat` /
  `bConfirmCheating` 的存在说明缺帧极可能被判为作弊，而本包要传到后台分发，代价是批量账号被标记，
  与「弹个提示且该局不算」不是一个量级。

**处置**：功能保留在菜单中，但**受服务端校验的玩法内实际不可用**（弹框且该局不结算）。
首次观测于单 APK 验证轮（`DMG` 处于 ×5/×10），截图
`06_dumped/境界守望者/screenshots/wor_single_apk_20261003_235539.png`。

**结论**：用户确认「不做，就到这」——本项作为已知限制归档，不再投入开发。

## 5. 与 base+split 形态的关系

- 两种形态的**星光逻辑完全相同**（同一个 `classes6.dex` + 同一个 `libstarry_magic.so`），单 APK 只是把 35 个 `.so` 搬进 base 并摘掉 split 属性。
- `08_output/境界守望者/` 目前同时保留：`…_starry-single.apk`（**正式交付包**）、`…_starry-releaseSigned.apk` + `…_starry-splitSigned.apk`（base+split 形态，开发期 `pm install-multiple` 用）。
- 拆分形态可用 `04_scripts/境界守望者/{wor_build_so.sh → surgical_wor_1.6.38.829.1.sh → wor_sign.sh}` 从 `02_apks` 底包完整重生成。

## 6. 坑

- **`adb` 是 Windows 程序**：本地文件参数必须是 Windows 形式路径（`C:/…` 正斜杠可用）。
  第一次因传 MSYS 路径 `/c/Users/…` 而失败：`adb: failed to stat /c/…/wor_single_ascii.apk: No such file or directory`（rc=1）；
  且脚本里若 `export MSYS_NO_PATHCONV=1`，Git Bash 的自动转换会被**禁掉**，此时必须显式给 Windows 路径。
- `dumpsys package` 的 `legacyNativeLibraryDir` 打印为相对值 `/lib`，**不可直接用**；改用 `codePath` 拼 `$CP/lib/arm64` 探测。
- 同目录的 `finalize_game_delivery.sh` 会把正式包路径交给 `apksigner.bat`（java）与原生 Windows python，
  两者都**必须收到 Windows 形式路径**（已在该脚本内加 `win_path()` 统一转换，见 `04_scripts/_common/finalize_game_delivery.sh`）。
