## 结论速览（先读这段）

**两项功能的静态结论（均为分析，未实测、未实现、未装机）**

- **无敌**：主战斗真实扣血链已定位到 `Battle.Life.AddHP`（写 `_curHP`，JInt 包装），受害者阵营用 `Life.GetPlayer().GetCamp()==FRIEND` 判定。**候选**：在该入口按阵营拦负值，或拦 `ReceiveDamage(3024)/ReceiveDamageByBuff(2618)`。**注意**：`FRIEND` 是"本机阵容"（含友军/召唤），不等于用户单体；早退会跳过 HPValue 记录写入。
- **秒杀**：**候选**为沿正常伤害路径对 `ENEMY` 放大伤害；**护盾/Deification/Prohibit/Desperation/死亡守卫存在，不保证一击必死**；`ForceSetLifeDead` 不等同完整死亡流程。
- **共同未知**：①玩家 camp 的最终赋值未实测 ②记录是输出、改本地值是否被覆盖未证 ③服务端校验强度未证（协议字段可承载 victory/seed/frame/damage/opdata，但**发送链路未定位**）④运行期实际加载的 mygame 版本未证（设备版与 APK 基线是不同构建）。

> 版本范围：下结论基于 **1.1.036**（`com.bhzf.zbml`）；APK 基线与设备热更两版 mygame 均解出并比对过结构。

### F6 native 解密库已定位但未证处理热更包
- `GameMain.DecryptFile`(VA 0x2D35A88) 反汇编仅约 100 B，是 icall 包装：构造 `"sqlite_unity_plugin"`(len19) + `"DecryptFile"`(len11) 调 `il2cpp_resolve_icall` ⇒ 算法在 `lib/arm64-v8a/libsqlite_unity_plugin.so`。
- `DecryptFile@0xd18f8`(332 B) **流程 [实测]**：fopen(src,rb)→fopen(dst,wb)→fread 全量→`ExpandKey(key@.data VA 0x1124a0)`→`BinaryDecrypt(buf+4, size-4, sched)`→fwrite(buf+4)；`ExpandKey@0xd0f1c` 按字节复制 16 B；`BinaryDecrypt@0xd145c` 首块与 `sched+0xa0` 异或后进入逆列混合；Sbox@0x111aa0 为标准 AES Sbox（`637c777bf26b6fc5…`）。
- **算法模式 [推断]**：由流程 + 标准 Sbox 推为「AES-128/ECB、跳过前 4 字节」；**轮数/模式/key 归属均未经调用证实**，X1 全矩阵试解失败即反证，不得当结论。
- .data 内 16 字节（file off 0x1024a0）：`00010204000002020000000000000000` —— **仅静态字节，未证用于 TRH/热更包**（见 X1）。

### F7 热更 dll 加载调用链（[实测] 反汇编调用图）

用自建 RVA→方法名表（`13_scratch/霸海争锋/rva_map.tsv`，58,091 条，源自 dump.cs 的 `// RVA` 行）解析 BL 目标：

- `GameMain.<LoadDll>d__22.MoveNext()`（RVA 0x2D367F4）依次调用：
  `GetSavePath()`(0x2D35458) → `String.Concat(str0,str1,str2)`(0x309E8C8) → `AesHelper.LoadDll(string dllPath)`(0x2EC3D4C) → `Assembly.Load(byte[] rawAssembly)`(0x30BD2E4) → `HybridCLR.RuntimeApi.LoadMetadataForAOTAssembly(byte[], HomologousImageMode)`(0x2D17454) → `GoToHotFixScene()`(0x2D35978)。
- `AesHelper.LoadDll`（[实测]，**已更正**）：`File.Open(path, FileMode.Open=3, FileAccess.Read=1, FileShare.Read=1)` → `new BinaryReader(stream)` → 按 vtable 调 `Length`/`ReadBytes` 读满 **byte[]**；随后**以尾调用（`b` 指令，不是 `bl`）跳到 `AesHelper.XORBytes(0x2EC3E3C)`** 做逐字节异或解密。此前只扫 `bl` 目标的结论（“无解密调用”）**是漏检，作废**——`XORBytes` 内实测 `data[i] ^= key[i % key.Length]`。
- 同类另有 AES 实现 [实测]：`AesDecryptBytes`(0x2EC3314) 调 `Encoding.UTF8.GetBytes` → `new AesManaged()` → `new Rfc2898DeriveBytes(string password, byte[] salt)` → `MemoryStream` → `CryptoStream`；**但它是否被 LoadDll/下载路径调用 [未证]**——存在实现 ≠ 该路径经过它，未证调用边前不追 passwd/salt。
- `GetFistDllPath(...)`（0x2D357A8）：`GetWebRequestPathWithPersistent(...)` → `String.op_Inequality` → `File.Exists(path)` ⇒ 该路径是**候选 dll 落点（推断）**；`File.Exists` 只证代码检查过该路径，**真假两分支各做什么未解**，也不证文件已落盘或运行时加载成功。
- `GetSavePath`（0x2D35458）**[实测]**：函数体调完类初始化后 `mov x0, xzr` 尾调用 `0x35B1574` = `UnityEngine.Application::get_persistentDataPath()` ⇒ **GetSavePath 返回 Application.persistentDataPath**（Android 即 `/storage/emulated/0/Android/data/com.bhzf.zbml/files`）。`GetSourcePath`(0x2D354A8) 同类结构、尾调用目标待解析。
- 设备侧 `find`（限 `/sdcard/Android/data/com.bhzf.zbml` + `/data/user/0/com.bhzf.zbml`）**没有任何 `*.dll`/`*.dll.bytes`**；同目录只有热更容器与 `il2cpp/Resources/*.dll-resources.dat`。

⇒ 目前 **未证** dll 落点：可能①以非 `.dll` 命名的容器文件存在；②首次进热更场景才落盘；③下载流经 AES 后直进内存（此为**其它分支的可行假设**，需独立证据，不替代已证的 `File.Open` 链）。三者都卡在同一处：容器/AES 调用边未证。

### F10 另一套 SkillAction 伤害链（主战斗关联未证；[实测] 代码级）

证据文件：`13_scratch/霸海争锋/decompiled/Unit_dev.cs`（设备版 `SkillAction.Unit`）、`dll/mygame.dll`（基线）。

- **扣血入口** `SkillAction.Unit.BeHurt(Unit attacker, Action action, long damage, ECombatResult result, EDamageType type)`（Unit_dev.cs:895）：
  `if (IsGod) return true;` → `result==ECR_Dodge ? AddHP(0,attacker,ECR_Dodge) : AddHP(-damage, attacker, result)`，恒返回 true。
- **真正写入** `SkillAction.Unit.AddHP(long hp, Unit attacker, ECombatResult result = ECR_Normal)`（:912）：
  `result==ECR_Dead → CurHp=0`；否则 `CurHp += hp; CurHp = Clamp(CurHp, 0, GetAttribute(EAT_MaxHp))`；随后 `IsDead = CurHp <= 0`、`if (IsDead) RemoveChild()`、`BattleField.MessageMgr.SendMessage(MessageId.HP_CHANGED, "Unit", this)`。
  `CurHp`（:231）→ `mAttributeHolder.CurHP`。
- **伤害触发者** `SkillAction.HitDamage.OnHitFeedback(Unit attacker, Unit attackee, params object[] param)`：
  `if (attackee.ActionStatus.CanHurt && !attackee.IsGod) attackee.BeHurt(attacker, action, num, result, type)`，num 可乘 `mDamageFactor/100`。
- **阵营/类型**：`Unit.CampType`（:251，`ECampType{EFT_Neutrality=1, EFT_Friend, EFT_Enemy}`）、`Unit.UnitType`（`EUnitType{EUT_None, EUT_Player, EUT_Monster, EUT_Summon}`）；`UnitMgr.CreateUnit(EUnitType type, string resID, Vector3 pos, float yaw, ECampType campType, bool activeAI)`、`GetUnitsByCamp(camp)`、`ForeachUnit(del, userData, camp)`。
- **原生无敌开关**：`Unit.IsGod`（:130，字段 isGod）——`BeHurt` 与 `HitDamage` 两处都短路。

> **边界**：以上只证「mygame 里存在这套单位/伤害系统」。**尚未证**它是用户所指主战斗（也可能是副玩法/小游戏），也**未证** `CampType==EFT_Friend` 就等于"用户操控的单体"（可能含友军/召唤/编队），`EUT_Player` 也可能用于敌方玩家。M1 的准确表述是「**mygame 含战斗实现**」，不是「AOT 无战斗实现」。

### F11 两套系统已分清：主战斗（ClientLife） vs 执行层（SkillAction.Unit）

> **重要更正**：F10 里那套 `SkillAction.Unit.BeHurt/AddHP` 只能证「mygame 里存在一套单位数值系统」，**不能**当作对用户主战斗的通用挂点。以下为实测的分层结果。

- **主战斗层（根命名空间）**：`BattleDirector`（`CreateHero`/`IEStartBattle`/`LoadActorsByIEnumeratorByCamp`/`ImmediatelyCreateHero(performerInfo, campType)`/`PlayVideoBattleRecording`/`SetPlayServerBattleRecordingByRecordInfo`/`ReentryPerform*`）+ `ClientLife : HeroAnimatorExtension`（**不是** Unit 子类）+ `BattleDefine.E_CAMP{FRIEND_CAMP, ENEMY_CAMP, CAMP_MAX}`。
  血量：`ClientLife.HP`（get/set，:238/:242）只做 `_curHp = value` → 同步 `PerformerData.CurHP` → `PerformerData.UnitData.SetCurHP(int)`（`PerformerInfo.UnitData`）。**该类全文没有 BeHurt/AddHP/SetHp 方法** ⇒ 主战斗的扣血是**外部赋值**，写入者尚未定位。
- **执行层（SkillAction）**：`Unit : BaseUnit`、`UnitMgr.CreateUnit(EUnitType, resID, pos, yaw, ECampType, activeAI)`、`BeHurt`(IsGod 短路)→`AddHP`(写 CurHp)、`ECampType{EFT_Neutrality/EFT_Friend/EFT_Enemy}`。
  引用关系实测：`ClientLife`/`BattleDirector` 仅有 `using SkillAction;`（ClientLife:8 / BattleDirector:12），**没有** `Unit`/`BaseUnit` 类型引用；`SkillAction` 被 `MiniGame.DodgeFist`（`AioliaStateBeHurt` 等）使用 ⇒ **更像小游戏/动作玩法的执行层**，是否参与主战斗**未证**。
- **战报/统计层**：`Battle.LogicRecord_Damage : ClientLogicRecord` 只做统计同步（`SynchronizeAllHeroCastDamage(FRIEND_CAMP/ENEMY_CAMP,…)`、`AllReceiveCure/AllShieldAbsorption`），**没有**任何 HP 写入或 Execute/OnUpdate；`LogicRecord_HPValue` 记录 `hp/maxhp/camp/castDamage`（含 `JEngine.AntiCheat.JInt` 反作弊包装）。⇒ 该层是**记录/校验**，不是扣血路径。

**对两项功能的含义（条件性）**：无敌/秒杀的候选挂点必须落到"真正写 HP 的地方"；目前在主战斗层只找到 `ClientLife.HP` 这个**赋值入口**（写入者未定位），在 SkillAction 层找到 `Unit.AddHP`（但适用范围未证）。`JInt` 反作弊包装与 `GM_VerifyPveBattleRequest` 的存在说明**部分玩法有校验**，本地改值风险未评估。

### F12 主战斗的真实数值链（三层）与受害者阵营

> 更正：本节旧版"主战斗 HP 由记录驱动、ClientLife.HP 是唯一落点"的说法**作废**。记录是**输出**，不是驱动源。

**真实扣血链（[实测] proj_dev/Battle/Life.cs，行号为设备版反编译产物）**：

```
Life.ReceiveDamage:3024  ── 3123-3125 Deification / ProhibitReceiveDamageAndCure 守卫 → AddHP(-jInt2)
Life.ReceiveDamageByBuff:2618 ── 同守卫 → AddHP(...)（:2700）
        ↓
Life.AddHP:2358  ── 前置 buff 触发（BEFOR_DEAD_CHANGE_HP 等）
        ↓
_curHP += value  (:2386，字段 _curHP 声明 :126，类型 JInt 反作弊包装)
        ↓
:2394-2405 clamp / Desperation 保命为 1 HP / SetLifeDead(pLauncher)
        ↓
:2416 生成 LogicRecord_HPValue（记录 = 本次变化的输出）
        ↓
LogicRecord_HPValue.PerformDoRecord → ClientLife.HP（表现/回放）
```

- **受害者阵营**：`Life.GetPlayer().GetCamp()`（`Life.cs`）；阵营枚举 `BattleDefine.E_CAMP{ENEMY=0, FRIEND=1, MAX=2}`（`BattleDefine.cs:298`）。
- **建场来源**：`StageManager.cs:1867 enemyDatas=Enemy / :1895 friendDatas=Friend / :1899 friendPerformerList`；`BattleField.cs:628/629 AddPlayer` 传入。⇒ `FRIEND` 指**本机阵容**（含友军/召唤），**不是单个玩家单位**。
- **不能用记录里的 camp 筛受害者**：`Life.cs:2411` 的 camp 来自**攻击者** `pLauncher.GetPlayer()`（或 victim 的敌方玩家），语义是"谁打的"，不是"谁挨打"。
- **旁路 `_curHP` 写入**（证明它不是唯一写入路径）：reset / `SetAllAttr` / 复活 / `FoceFillUpHP` / `CheckMaximumHealth` / `SetHP`。`HealthHp` 已见初始化读与其它写，**未见**除初始化外驱动 `_curHP`。
- **保命守卫（秒杀不能保证一击必死）**：护盾、`Deification`（神化）、`ProhibitReceiveDamageAndCure`、`DESPERATION_STATE`（濒死保 1 HP）、`SetLifeDead:1664` 的再守卫；死亡记录与击杀者连带在 `OnDead:1069`。`ForceSetLifeDead`（:1663）只置状态，**不等同完整死亡流程**，不作首选。

**另一套 SkillAction 伤害链（主战斗关联未证）**：`SkillAction.Unit.BeHurt(:895)→AddHP(:912)` 存在，但 `UnitMgr.CreateUnit` 在已扫程序集的**直接 IL 引用仅 `Demo::CreateUnit`（token 0x0600B4ED）**，另有 `EventSummonUnit` 私有 CreateUnit（召唤）。⇒ 只能写"已查链未关联主 Battle"，**不断言永不参与**。

**对两项的含义（条件性，未实现）**：
- **无敌**（候选）：在 `Life.AddHP` 入口对"受害者 `GetPlayer().GetCamp()==FRIEND`"拦截负值；或在 `ReceiveDamage:3024`/`ReceiveDamageByBuff:2618` 两个入口拦。副作用取决于落点：**在 AddHP 早退会跳过 :2416 的记录写入**（专家已撤回"早退仍写负记录"），且调用方 `else` 分支（:3131）不会因该 return 执行；在 ReceiveDamage 层拦则会保留 buff/统计的其它副作用。
- **秒杀**（候选）：沿正常伤害路径对"受害者 `GetCamp()==ENEMY`"放大伤害（走 `ReceiveDamage` 而非直接写 `_curHP`）。**护盾/Deification/Prohibit/Desperation/死亡守卫存在，不保证一击必死**；`ForceSetLifeDead` 不作首选。
- **未证**：改本地 `_curHP` 是否被后续记录/同步覆盖；服务端是否重算；PVP/世界BOSS 的实际校验。

**token 级 xref 工具**：`04_scripts/霸海争锋/xref/`（Cecil，net10.0，离线引用 `01_tools/Il2CppDumper/Mono.Cecil.dll`；build exit 0）。

### F13 HPValue 记录的生成与结算输入（[实测] 主战斗模拟器侧）

- **记录由客户端模拟器自己产生**：`Battle.Life.AddHP(JInt value, Life pLauncher, int RecursionCount)` 在每次血量变化后调用
  `m_pBattle.AddLogicRecord(UniqueID, LogicTypeEnum.HPValue, _curHP, GetAttr(HERO_ATTR_MAX_HP), 0L, (long)camp, value)`（Life.cs:2416），
  其中 `camp` 仅在 `value < 0` 时取 `pLauncher.GetPlayer().GetCamp()`，否则取己方敌方玩家阵营（Life.cs:2411-2415）。
- **落库路径**：`BattleField.AddLogicRecord(int uid, LogicTypeEnum, params long[])`（BattleField.cs:2210/2221）→ `LogicRecord.Create(...)`（LogicRecord.cs:115 的 `case HPValue`）→ `SetRecordData(...)`；`Battle/RecordData.cs` 的 `CompressLogicRecord/Add` 做同帧压缩。
- **应用路径（回放）**：`LogicRecord_HPValue.PerformDoRecord` → `Hero.HP/MaxHP/HPPercent/UpdateUI`；`StartRecord` 读 `_saveRecordDatas[0..3]`（hp/maxhp/?/camp），`pLauncherCamp` 读入但**不参与应用**。
- **结算/校验协议（结论按证据收紧）**：`PBMessage.GM_VerifyPveBattleRequest` 的序列化字段表为
  `_serverid/_stagetype/_stageid/_sceneid/_victory/_myroleid/_targetid/_randseed/_frame/_damage/_opdata(byte[]) / myrole(ReportRoleData) / trrole(ReportRoleData)`（PBMessage/GM_VerifyPveBattleRequest.cs:10-77）。
  **能证**：该协议**可承载**这些字段（胜负、种子、帧号、总伤害、一段不透明 `opdata`、双方角色数据）。
  **不能证**：实际是否上传这些内容、`opdata` 里是什么（可能是逐条事件/校验数据，也可能为空）、以及这是不是上传主通道。
  **xref 结果与其边界**：在 mygame_dev/HotFix/AdditionalLogic/HybridMain 四程序集内，对 `.ctor` 与 Send/Write/Serialize 形态 **0 命中**——这只说明**已扫程序集里的直接调用指令**没有命中；**反射、通用序列化/反序列化、或其它程序集**仍可能构造并发送，因此**不能推出"本地无发送点"**。
  ⇒ 唯一可写的结论：**实际发送链路未定位；服务端验证强度未知**（未做联网观测）。

**边界**：以上只证"记录由本地模拟生成并用于回放/上报"，**不证**服务端是否重算血量；也不构成"PVP 必为回放、PVE 必为本地"的结论。
