# 绿梦：时空之声 1.0.5 — 「替代 Frida」的动态手段全景调研

- 日期：2026-10-20（调研会话，纯检索 + 推理）
- 目标：`com.zhuziplay.lvmengnew.op` 1.0.5 / vc12035，壳 = `libFairGuard.so`
- 性质：**本会话未做任何真机操作**。凡未实测的结论一律标【文档】（有来源）／【推断】（有证据链）／【待验证】。
- 上游事实（直接采信、不重复推导）：壳载荷 = 标准 zlib DEFLATE，离线解包 + 改包链已跑通；35 s 闪退已用 NOP exit_group 绕过并进主界面；剩余 101–157 s 周期/延迟检测 = 异步 `tgkill` 阶梯 SIGILL→SIGTRAP→SIGKILL 杀 UnityMain；Frida 一注入即 SIGKILL；**ptrace ATTACH 不被反制**；`04_scripts/绿梦/fg_mprotect.c` 远程 svc 桩未正确执行、返回值垃圾。
- 边界：本文只做本地授权测试用方法选型，不含任何出网/服务端动作（硬约束 #5）。

## 0. 结论（先看这 6 条）

1. **不存在「装上就隐身」的 Frida 替代品。** FairGuard 的拦截是三层叠加：①模块/映射枚举（`dl_iterate_phdr`、`/proc/self/maps`、可疑线程名）②官方明写「禁止使用 Xposed、Frida 等各种外挂模块注入器……一旦发现立即闪退」③信号阶梯杀线程。任何「把代码送进目标进程」的方案都得先过 ①②。
2. **唯一同时满足「零注入、零落盘、直接给出 tgkill 调用者 PC」的是纯 ptrace syscall-stop 观测**：对目标全部线程 `PTRACE_SEIZE` + 循环 `PTRACE_SYSCALL`，在 **syscall-enter-stop 读 x8**，命中 129/130/131/138/424 就记 PC、LR(x30)、FP(x29) 并归一到 `libFairGuard.so` 的 RWX 段偏移。约 100–150 行 C，直接复用现有 ptrace 注入器的 attach 骨架；**不写目标内存、不加载 .so、不留文件、不新增线程名**。
3. **第二条独立路线是「吞信号 + 数据侧反推」**：ptrace 在 signal-delivery-stop 用 `PTRACE_CONT(sig=0)` 把 SIGILL/SIGTRAP 丢弃（手册明确 tracer 可「忽略被投递的信号」），阶梯变噪音；再对可写段做两次快照 diff 找被翻转的 tampered 字节，最后用 `NT_ARM_HW_WATCH` 硬件写观察点抓写入者 PC。**零注入**，且能独立回答「tampered 标志在哪」。
4. **seccomp `SECCOMP_RET_TRACE` 只能当「降开销版观察」**：能把 stop 从「每次系统调用」降到「只信号族」，但 ①装过滤器要一次代码执行（可用 syscall 重写代替注入）②会把 `/proc/pid/status` 的 `Seccomp` 从 0 变 2，**凭空造出一个新检测面**。排在 ptrace 全量观测之后。
5. **注入框架类（Zygisk / LSPosed / Riru / Magisk 模块 / libmem / Frida gadget）全部不推荐**：Java 层对 native cert 比较无用；Zygisk 系痕迹（`libzygisk`/`libriru` 映射名、匿名可执行段、模块清单差异）正是这类壳的常规扫描项；FairGuard 官方博客已把「注入器」列为立即闪退条件。
6. **DBI 类里 QBDI 明确不适用**（不自带注入方式，且文档写明「不处理信号、不处理多线程」——正好撞上本项目的信号阶梯 + Unity 多线程）；DynamoRIO 需前置 `drrun` 启动、Android AArch64 仍是 open 需求；unicorn/unidbg 只适合把单个函数抠出来离线跑。

## 1. 判定口径

四维打分，全部围绕本项目的真问题（**抓 tgkill 的调用者 PC → 反推 cert 比较 → tampered 标志**）：

| 维度 | 含义 |
|---|---|
| 注入面 | 是否需要进目标进程 / 写目标内存 / 落新文件 / 新线程 |
| 可见痕迹 | FairGuard 侧能看到的信号（maps 行、模块清单、线程名、`Seccomp`/`TracerPid` 字段、inotify 文件事件） |
| 成本 | 人日量级（含调试） |
| 抓 PC | 能否**直接**输出 tgkill 发起者的 PC/LR，而不是间接推断 |

## 2. 注入框架替代（Zygisk / LSPosed / Riru / Magisk / libmem）

### 2.1 Zygisk / Zygisk Next
- 机制：把模块 .so 注入 zygote，所有从 zygote fork 出的 app 进程天然带上该模块。Zygisk Next 是 KernelSU/APatch 上的独立实现，只保证 Zygisk API 行为一致，**不隐藏自己**。
- 对本项目：能把 native 代码放进 `libFairGuard.so` 所在进程，**但代价是全局可见痕迹**——映射名、模块清单增项、以及在 zygote 阶段就改动了进程状态。
- 可检测性【文档】：同类壳（腾讯 ACE/libtersafe）用 `dl_iterate_phdr` 枚举全部 SO 并比对预期清单、再用 `fopen` 读 `/proc/self/maps` 做备份扫描，且会检查可疑线程名（`gum-js-loop` 这类）；FairGuard 侧则宣称「主动识别恶意模块」+「禁止各种注入器，发现即闪退」。公开的检测器实现里，`libzygisk`、`libriru`、`frida-agent`、`LSPosed` 都是**固定字符串清单**命中项。
- 结论：**不推荐**。即使 `DenyList`/`SUSFS` 能藏 mount 与文件路径，也藏不住进程内映射与模块清单——公开资料的原话是「没有任何一种能保证同时抵御 maps、linker、mount 和原始系统调用检查」。

### 2.2 LSPosed / Xposed
- 只做 Java 层 hook。本项目的 cert 比较在 native（FairGuard 自己的 .so，无导入函数），Java 层 hook 连不到。
- 副作用与 2.1 同级（同一套注入链路 + 同名痕迹），收益为 0。
- 结论：**不推荐**（除非后续证明比较发生在 Java 层，而这与「常量运行期解码 + 信号阶梯」的形态不符）。

### 2.3 Riru
- Zygisk 的前身，已被 Zygisk 取代；痕迹同样是 `libriru*` 映射 + 模块目录。
- 结论：**不推荐**（无新能力，只有旧风险）。

### 2.4 Magisk 模块 / DenyList / Shamiko / SUSFS
- 这些解决的是「root 与 mount 可见性」，**不解决「进程内注入可见性」**。
- 对本项目唯一有价值的用法：SUSFS 这类内核补丁可以在 `/proc/<pid>/maps`、`/proc/mounts` 层做路径/挂载隐藏，**为 ptrace 路线争取更干净的旁路环境**（例如隐藏 `/data/local/tmp` 里的调试载荷文件）。
- 结论：**只当辅助**，不当主路线。

### 2.5 libmem
- README 平台表：Windows / Linux / FreeBSD；ARM 与 AArch64 标 `Untested`（**没有列 Android**，第三方 fork 才声称支持）。external 模式本质仍是 ptrace 读写。
- 结论：**不推荐**。它不提供任何现有 ptrace 骨架之外的能力，却引入一个未在 AArch64 Android 验证过的依赖。

### 2.6 「Frida 内核注入」与静态 gadget
- Frida 官方只有两条注入路径：`frida-server`（ptrace 注入 agent）与 gadget（作为 .so 预加载/改包加载）。**不存在官方内核态变体**；社区所谓「内核注入」实为内核模块读内存（见 §4.6），与 Frida 运行时无关。
- gadget 静态加载 = 改包（本项目已证明改包可行），但 gadget 映射一旦出现就是 `frida-gadget` 字符串命中，且其线程名/通信端口是经典特征。
- 结论：**不推荐**（与「Frida 必死」同源，只是把死法提前到启动阶段）。

### 2.7 memfd + dlopen（让注入物「无路径」）
- 思路：`memfd_create` 造匿名文件 → 写入 .so → `dlopen("/proc/self/fd/N")`，磁盘上不留文件、`maps` 里显示为 `/memfd:name (deleted)`，可躲开基于**路径**的清单比对。
- 局限：仍要一次代码执行来调 `dlopen`（即仍需 ptrace 注入 shellcode，与 `fg_mprotect.c` 同一难题）；且 `maps` 里仍是一条**匿名可执行映射**，壳若统计「非白名单的 exec 映射」照样命中。
- 结论：**仅作为 §7 P5 的注入载体**，不是独立路线。

## 3. 调试器 / 追踪替代

### 3.1 gdbserver / gdb
- 与 ptrace 同源（gdbserver 就是 ptrace 前端），因此「ptrace 不被反制」这条前提对它同样成立。
- 但：①NDK 近版本是否还带 `gdbserver`/`gdb` 需以本机 NDK 目录实测为准【待验证】；②`gdbserver` 要落一个可执行文件到设备（inotify/文件扫描面）；③**不能按系统调用号过滤**，`catch syscall tgkill` 在 remote 协议下支持度差，实际会退化成「全 syscall 停」，还不如自己写循环可控。
- 结论：**只作便利工具**（拿到 PC 后看寄存器/单步），不作抓 PC 的主方案。

### 3.2 lldb-server
- 同为 ptrace 前端，Android 平台调试的现行主力（AOSP 的调试文档已以 lldb 为主）。attach 到已运行进程可行，能读全部寄存器、设断点、在 signal-stop 处停住。
- 价值点：**它能停在 SIGILL 的 signal-delivery-stop**，让你看清「被杀线程当时在干什么」；但它给不了「发信号的线程的 PC」——那需要 syscall-enter 停点。
- 结论：**辅助**（定位被杀线程上下文 / 单步验证 patch），不作主方案。

### 3.3 radare2 ptrace 模式 / Cutter
- `r2 -d` 的 debugger 后端在 Linux/Android 上走 ptrace，能力等价于一个脚本化 gdb；优势是可脚本化（r2pipe）批量读内存、批量反汇编。
- 缺 syscall 过滤与稳定的多线程 attach 编排，长期跑 100 s+ 的观测容易掉线程。
- 结论：**可作离线/事后分析器**（拿到 PC 后反汇编 RWX 段），不作观测器。

### 3.4 QBDI（QuarkslaB DBI）
- 平台矩阵确实包含 Android + ARM/AArch64，API 也强。但文档两句话直接判死：**「QBDI 不包含首选的注入方式，设计上与外部注入工具配合」**（自带只有 LD_PRELOAD 版 `QBDIPreload`，Android app 上没有 LD_PRELOAD 入口）；**「当前限制：不处理信号、不处理多线程（不管新线程创建）」**。
- 对一个「异步信号阶梯 + Unity 多线程」的目标，QBDI 既进不去，也接不住信号。
- 结论：**不适用**。

### 3.5 DynamoRIO
- 官网自述支持 Windows/Linux/Android 与 IA-32/AMD64/ARM/AArch64；但仓库里 `Support for Android ARM64`（#7855）仍是 open 需求，AArch64+Android 的组合成熟度存疑【待验证】。
- 更硬的限制：DynamoRIO 是「由 drrun 启动目标」的模型，**不能 attach 一个已经在跑的进程**；本项目要观测的是用户已经点进主界面的对局，改启动方式等于重跑一遍 101 s 窗口，且 drrun 自身就是明显的注入痕迹。
- 结论：**不适用**（不是能力不够，是形态不对）。

### 3.6 unicorn / unidbg（离线模拟）
- 零检测风险（不碰真机进程），能在指令级日志里直接看到 `svc` 调用与返回。
- 但 FairGuard 载荷是**运行期原地解码 + 依赖真实 linker/JNI/Unity 环境**（本项目已实测：磁盘段与内存段逐块不同、0x1F0000 以上磁盘全零而内存有内容），整库模拟的环境补齐成本极高；unidbg 的常见用法是「抠单个函数 + 补 JNI」，适合**已知函数**而非「找函数」。
- 结论：**仅作拿到 killer 地址后的单函数复现**，不作发现工具。

## 4. 内存 dump / 读写替代

| 手段 | 权限模型 | 适用 | 备注 |
|---|---|---|---|
| `/proc/<pid>/mem` + `pread` | 打开时按 `PTRACE_MODE_ATTACH_FSCREDS` 检查 | 随机地址大批量读、整段 dump | 需先 `lseek` 到目标地址；root（su 域）可直接读，**不必 attach** |
| `process_vm_readv` | 按 `PTRACE_MODE_ATTACH_REALCREDS` 检查 | 连续大块、批量 iovec 读，速度最好 | 跨页会部分传输，长读要按页切；不保证原子 |
| `PTRACE_PEEKDATA/POKEDATA` | tracer 身份 | 少量字级读写（改寄存器/打补丁） | 每次 8 字节，大量读很慢 |
| `memfd_create` + `dlopen` | 同进程 | 免文件落地的代码加载 | `maps` 仍留匿名 exec 行 |
| `NT_ARM_HW_BREAK` / `NT_ARM_HW_WATCH` | tracer 身份（`PTRACE_SETREGSET`） | 硬件断点 / 数据写观察点，最多 4–8 个 | 抓「谁写了 tampered 标志」的最强单点工具 |
| 内核 ftrace / kprobe | root + tracefs | 进程内零痕迹地观测 syscall | 见 §5-C |

**本条要点**：本项目已有的 4 MB 运行期 dump 是用 Frida 做的；换成「root 进程直接 `process_vm_readv` / `pread(/proc/pid/mem)`」即可**完全脱离 Frida**，且不受 attach 反制影响（读权限只做 `PTRACE_MODE_ATTACH` 检查，root 直接过）。这也是后续「快照 diff」路线的基础设施。

**专门针对加固壳的开源方案盘点**：公开可查的只有 ①静态强度对比（FairGuard vs 腾讯 ACE：`.text` 仅 16 字节且全零、88.8% 文件区无节区描述、1002 个空名符号、可恢复 FDE = 0）②「某 Guard」的流程分析（`init_array` 里做模拟器检查、遍历 `/proc/self/maps` 取 lib 基址、GOT 替换、字符串内联解密；绕反调试靠 hook `strstr` 改 `TracerPid:`）。**没有**针对 FairGuard 的「注入绕过模块」开源项目；`SUSFS`/`Shamiko`/`NoHello` 一类只处理 root/mount 可见性。这条空白正好说明：能走的路只剩「不进进程」。

## 5. 抓 killer PC 的三条打法

### A（首选）纯 ptrace syscall-stop 观测

```
1) 枚举 /proc/<pid>/task/*，对每个 tid: ptrace(PTRACE_SEIZE, tid, 0, 0) -> PTRACE_INTERRUPT -> waitpid
2) PTRACE_SETOPTIONS: PTRACE_O_TRACECLONE | PTRACE_O_TRACEEXIT   (新线程自动纳入)
3) 循环: ptrace(PTRACE_SYSCALL, tid, 0, 0); waitpid(-1, &st, __WALL)
   - 判 syscall-stop: (st>>8) == (SIGTRAP|0x80)
   - 判进入/退出: PTRACE_GETREGSET(NT_ARM_SYSTEM_CALL, 0x404) 返回 -1 => 进入停点
   - 进入停点读 regs[8] (x8):
       129 kill / 130 tkill / 131 tgkill / 138 rt_sigqueueinfo / 424 pidfd_send_signal
       => 记录 tid, x8, x0..x2, PC, LR(x30), FP(x29)
       => PC-4 就是 svc 指令地址；LR 是 FairGuard 代码里的调用者返回地址
       => 用 /proc/pid/maps 把 PC/LR 归一到 libFairGuard.so 的 rwxp 段偏移
   - 继续时用 PTRACE_CONT(sig) 放行；想验证「信号是否真被执行」就 sig=0 丢弃
```

- 输出量：101–157 s 窗口里命中应该只有个位数行——这是**最小的观测面**。
- 成本：0.5–1 人日（attach 骨架已有）。
- 风险：全 syscall 停会让游戏明显变慢（futex/ioctl 密集），但「慢」不影响定位；若慢到窗口推不动，转 C。
- 附带收益：LR 指进 `libFairGuard.so` 的 RWX 段后，用 §4 的读法把该段 dump 出来离线反汇编，往回找「谁把 tampered 置 1」。

### B（并行）吞信号 + 快照 diff + 硬件写观察点

```
1) ptrace attach 后，所有 signal-delivery-stop 一律 PTRACE_CONT(sig=0) 丢弃
   （SIGILL/SIGTRAP 被吞；SIGKILL 吞不掉，所以阶梯最后一发要抢在它之前）
2) t≈90 s 与 t≈160 s 各做一次「可写段快照」：读 /proc/pid/maps 取 rw-p 段，process_vm_readv 批量读
3) 两次快照按 4 KiB 页 hash 比对 -> 差异页 -> 页内找单字节 0<->1 翻转（tampered 候选）
4) 对候选地址设 NT_ARM_HW_WATCH 写观察点 -> 命中即读 PC/LR，得到「写 tampered 的指令」
5) 反向再验：读该指令所在函数的调用者，通常就是 cert 比较点
```

- 成本：1–2 人日；风险极低（全程只读 + 信号丢弃）；**不依赖知道 tgkill 在哪**。
- 关键前提：SIGKILL 无法被 tracer 丢弃，所以要么在 SIGTRAP 阶段就把进程停住（PTRACE_SYSCALL 停点本身就是停住），要么在最后一发之前完成快照。

### C（降开销版）seccomp RET_TRACE 只筛信号族

- 原理：给目标装一个 BPF 过滤器，「全部 allow，仅 kill 族返回 `SECCOMP_RET_TRACE`」；tracer 用 `PTRACE_O_TRACESECCOMP` 收到 `PTRACE_EVENT_SECCOMP` 停点，此时寄存器里就是发起者上下文。
- 装过滤器的两种方式：①注入 shellcode 调 `seccomp()`（与 `fg_mprotect.c` 同一难题，已失败一次）②**syscall 重写**——在任意一次 syscall-enter-stop 把 x8 改成 317（`seccomp`），x0=`SECCOMP_SET_MODE_FILTER`、x2 指向事先用 `process_vm_writev` 写进目标可写页的 `sock_fprog`+BPF。系统调用手册明确 tracer「可以改变被请求的系统调用号」甚至「把号改成 -1 跳过」。**这条路完全不需要在目标里执行自写代码**，正好绕开 icache/栈可执行性这一整类失败。
- 代价：`/proc/<pid>/status` 的 `Seccomp` 字段从 0 变 2、`Seccomp_filters` 从 0 变 1，**这是新增的可见信号**；且过滤器一旦装错会 ENOSYS 一批系统调用把进程搞崩。
- 结论：A 跑得动就用 A；A 太慢（游戏被拖死）再上 C。

### D（交叉验证）内核 ftrace / kprobe
- 若 tracefs 可挂载且内核开了 syscall tracepoints，可以对 `sys_enter_tgkill` 事件开 `userstacktrace` 触发器，进程内**零痕迹**地拿到用户态调用栈（顶部帧≈svc 附近，配合 maps 解析）。
- 只给栈、不给精确调用者 PC；且依赖内核配置与 SELinux，成本 2–3 人日【待验证】。
- 用途：与 A 的结果对账（同一个 PC 出现两次才落定）。

## 6. 方案对比表

| 方案 | 注入面 | 主要可见痕迹 | 成本 | 直接抓调用者 PC | 判定 |
|---|---|---|---|---|---|
| **A. ptrace 全线程 syscall-stop** | 无（只 attach） | `TracerPid`（实测不反制） | 低（0.5–1 d） | **能**（PC/LR/FP 全给） | **P0 首选** |
| **B. 吞信号 + 快照 diff + HW 观察点** | 无 | 无（只读） | 中（1–2 d） | 能（抓写入者 PC，非 tgkill 发送者） | **P0 并行** |

## 7. 推荐与理由

**P0：A（ptrace syscall-stop）**——理由：①唯一零注入且能直接吐 PC/LR 的方案；②复用已验证「attach 不被反制」的前提，风险面已知；③命中判据是内核给的 syscall 号，不依赖壳的任何内部符号（本项目静态四路走死的根因就是符号/常量都被抹掉，这条路线**绕过了静态分析的整个前提**）；④0.5–1 人日。

**P0 并行：B（吞信号 + diff + HW watch）**——理由：即使 A 拿到 PC 落进一段高度混淆的 RWX 代码，B 还能**从数据侧**独立给出 tampered 字节与其写入者；两条路互为验证，任一成功都能闭环。风险最低（只读）。

**P2：C（seccomp）**——仅当 A 的 syscall 停点把游戏拖死。**注意新增 `Seccomp` 字段暴露**，且过滤器写错会 ENOSYS 连锁崩。

**P3：D（ftrace）**——对账用，不作为唯一证据。

**最后：P5（memfd + dlopen + ShadowHook/Dobby）**——只有在前几条都拿到「要 patch 的具体地址」之后才有意义；此时注入的是**极短命、匿名映射**的补丁模块，且要接受「一旦被模块识别就回到 SIGKILL」。

**明确不做**：Zygisk / LSPosed / Riru / Magisk 模块 / libmem / Frida 任何变体（含 gadget）/ QBDI / DynamoRIO 作主攻。

**每条路线的停止条件**：A 若在 101–157 s 窗口内**完全不出现** kill 族 syscall（说明信号不是本进程发的，例如由 shell 自己的看门狗线程之外的进程发），则转 B + D；B 若两次快照零差异页（说明 tampered 是寄存器/栈上临时值而非全局字节），则转「HW 观察点扫可疑页」；C 若装上过滤器后进程在装过滤器那一瞬就死，说明壳监控 `Seccomp` 字段，直接弃。

## 8. 与现有 fg_mprotect.c 的衔接（为什么不建议继续修 svc 桩）

`fg_mprotect.c` 的做法是「往目标栈写 svc 桩 → 改 PC 跳过去 → 读 x0」。这条路在本目标上有四个**结构性**难点（【推断】，按可能性排序）：

1. **I-cache 一致性**：`PTRACE_POKEDATA` 只改数据，不保证目标核的 I-cache 看到新指令；arm64 上必须由被调试进程执行 cache 维护才稳。表现就是「返回值垃圾 / 行为随机」，与本项目观察一致。
2. **栈页属性**：壳把某些线程栈/guard 页设成不可执行，桩一执行就 SIGSEGV，而 tracer 只看到「没回来」。
3. **上下文未对齐**：x0–x30 未保存、SP 未 16 字节对齐、x8 未设对、或没等到 syscall-exit-stop 就读 x0。
4. **壳的寄存器/栈自检**：栈上多出一段代码、PC 落在非映射段，本身就是异常信号。

**建议改为「syscall 重写」**：不做远程代码执行，而是在一次正常的 syscall-enter-stop 里把 x8/x0..x2 换成目标系统调用。调用手册明确允许改系统调用号，因此 `mprotect(PROT_NONE)` 或 `seccomp()` 都能这样发起，**零新代码、零 icache 问题、零栈页问题**。这也是 §5-C 的装过滤器手法。

## 10. 未闭环

1. **本会话零实测**：A/B/C 三条路都只有文档依据与推理，没有任何一条在 `f9a116a2` 上跑过。
2. **信号源未确认**：tgkill 是否由 FairGuard 自有线程发出、是否全部走裸 `svc`（而不是 bionic `pthread_kill`）未验证 —— 若走 libc，断点法也可用，A 的过滤集要加上进入 libc 的路径。

8. **35 s 段与 101–157 s 段是否同一 tampered 标志**未验证 —— 若不是，B 的 diff 会出现两类差异页，需要分时间窗取快照。
9. **A 路线开销**：全 syscall 停对 Unity（futex/ioctl 密集）的实际减速倍率未测，可能把 101 s 窗口拖到不可接受。
