# 绿梦：时空之声 — 换攻击面：启用源定位（Stage 9，离线为主 + fvv 只读取证）

- 问题：校验是 10-19 热更后才出现的，而 dll 里没有触发器（Stage 8）⇒「启用源」只可能在【热更资源/配置】或【云端】。
  本阶段把启用源查清，决定有没有干净的直装包绕法。
- 纪律：离线为主；fvv 只读 dump（未写入任何字节）；未装机、未碰屏幕、未逆壳。

## 1. 结论：**③ 云端 / 加密运行时配置 —— 本地没有可编辑的开关，无干净直装包绕法**

三条证据链（bundle / APK 内置 / fvv 运行目录）都没有"可读可编辑的策略文件"：

### 证据 A：bundle 全量 diff —— 只有 Assembly-ACT 是**语义**变化，其余全是重新编译的时间戳/MVID
- 两份 bundle 解压流**长度完全一致**（29,280,096 B），PE 条目**都 46 个、名字与顺序完全相同**（无新增程序集）。
- 逐个程序集取 md5 对比（10-16 提取出的 44 个 dll vs 10-19 bundle）：

| 项 | 结果 |
|---|---|
| Assembly-ACT | 14,529,536 → 14,534,656（+5,120 B，Stage 8 已证为玩法逻辑） |
| 其余 28 个"变化"的程序集 | **大小全部不变**，差异只在 3 类字段：PE COFF 时间戳（+0x88）、MVID GUID（#GUID）、签名 blob |
| 非 PE 区域 | 10-19 与 payload2 的 md5 完全一致 |
| 新增文件/配置 | **0 个**（无新程序集、无新 manifest、无策略文件） |

单个小程序集（Bamboo.HeartBeat.Runtime，5,632 B）的差异实证：70 字节差异，聚成 5 簇 ——
  0x88 时间戳(4B)、0xb78/0xd14/0xd71 三处 16B 级 GUID+签名。
⇒ **10-19 是一次全量重编译**（所有程序集都被重盖章），语义改动只有 ACT 那 5 KB 玩法逻辑。

### 证据 B：APK 内置没有 FairGuard 策略文件
- `assets/` 下与安全相关的只有 `Crashsight_Enabled`（腾讯 CrashSight）、`app_config.enc`、`global-metadata.dat` 等；
- 按 `fvv|ppd1|dmfbd|opdn|optn|policy|anti|protect` 过滤：**没有** FairGuard 的 .ppd1/.dmfbd/.opdn/.optn/policy 类文件。

### 证据 C：fvv 运行目录只有加密 blob，没有可读开关
- `/data/data/<pkg>/files/fvv/`：`.ppd1`（**272 B 高熵密文**，无任何可读字符串）+ `comm/` 子目录；
  目录创建时间 = **安装时（10-19 13:25）**，`.ppd1` 的 mtime 每次运行都被刷新（今天 01:36 又写了一次）。
- ⇒ 它是 FairGuard **自己生成并每轮重写**的加密状态，不是我们可以编辑的配置；改它既无字段可改，也会被重写。

## 2. 三类归属

| 类别 | 判定 | 依据 |
|---|---|---|
| ① bundle 内本地文件（可编辑 → 干净绕） | **否** | 46 个条目全是程序集，0 新增文件；唯一语义改动是玩法逻辑（Stage 8：无签名/包/证书引用） |
| ② fvv 运行配置 | **沾边但不可用** | `.ppd1` 是 272 B 密文、无字段、每轮重写；改它等于逆 FairGuard 的加密 |
| ③ 云端 | **最可能** | 本地三处都没有策略文件；而"10-16 满足 / 10-19 不满足"的变化只发生在服务端下发的热更决策上 |

**⇒ 启用源不在可编辑的本地文件里 ⇒ 没有干净的直装包绕法。**

一个反向自证：我们**自己 IL-patch 过的 dll**（内容被改）在 10-16 跑了 32 分钟没事（Stage 8 反证）——
说明 FairGuard 不按 dll 内容判定；它判定的是**别的、且在 10-19 变了的东西**，而那个东西**不在我们能读写的明文文件里**。

## 3. 未闭环

1. `.ppd1` 内容未解密（272 B 密文，需要 FairGuard 的 key ⇒ 属逆壳范畴，本阶段不做）；
   因此"fvv 里到底有没有签名校验开关"**无法直接证明**，只能证明"它不是可编辑的明文开关"。
2. 云端下发无法离线验证（需要抓包/服务端接口，本阶段未做）。
3. 10-19 bundle 的 `_manifest.bytes` 与 10-16 的 4,249 B 版本不同（10-16 的字节在 10-19 非 PE 区找不到），
   但**程序集清单完全相同** ⇒ 不构成"新增组件"的证据；若要精确比对 manifest 字段，需再解析一次。
4. 结论对"10-16 为什么满足"仍是推断：没有 10-16 时期同一设备的成功日志做对照（当时未做取证）。
