## 2. U1：loader 代码地图（静态确证的部分）

三个构造器（`.init_array` 由 78 条 R_AARCH64_RELATIVE 在加载期填值）：

| 桩 | 地址 | 已知调用点 |
|---|---|---|

## 4. 卡点与下一步（给下一轮）

卡点：**解密例程尚未定位**。已知的三个事实把搜索空间压得很小：
1. 解密是**原地**的（0x400..0x1F0000 偏移/长度不变），所以解密循环的写指针 = 读指针 + 0，跨 1.99 MB；
2. 它不读外部文件（deps 只有 liblog/libdl/libz/libstdc++/libm/libc，且 Stage 2 观测到 FairGuard 只在 ~29.6 s 做一次 open，与启动期解密无关）；
3. 密文熵 7.97、明文熵 6.40，**不是压缩**（压缩会先解压再解密，明文熵应更低且长度会变）。

因此解密循环必然在 0x413AB0..0x431350 这 121 KB 内，且以 "ldrb/ldr + 表变换 + strb/str" 形式出现。
下一步建议（按性价比排序）：
1. 用 capstone 扫壳区所有"双指针循环"（同一基址 +0/+1 的读写、计数器递减到 0），列出候选（预计 <20 个）；
2. 对每个候选回溯其参数来源：是否来自 0x42A488 那条 openat 之后的 read 缓冲，或直接来自被 mmap 的自身文件；
3. 0x42A488 处先把栈上字符串常量解出来（就是路径），确认它打开的是**自己的 .so** 还是 APK；
4. 若确认解密循环带 32/64 位分组与轮函数 ⇒ 按块密码处理（找轮常量/置换表）；若是逐字节表驱动 ⇒ 直接导出置换表。

## 6. 密码学分流（2026-10-20 补测，按决策官指定优先项）

输入：同址对齐的 (C, P) 对，C=disk[0x400..0x1F0000]，P=image[同址]，n=2,030,592 B。

| 检验 | 结果 | 判读 |
|---|---|---|
| 熵 | C=7.97，P=6.40，**KS=C⊕P 熵=8.00** | 密钥流接近均匀随机 |
| ECB 特征（16B） | P 里重复块 **5,879 组**，其中 C 也重复的 **0 组** | **非 ECB** |
| ECB 特征（32B） | P 重复 1,127 组，C 重复 0 组 | 同上 |
| CBC 特征 | 「前一块 C 相同且 P 相同」的对数 = **0**（无样本） | 既不能证实也不能否证 CBC |
| KS 周期 | 位移 16/32/64/256/4096/65536 的字节相同率 **0.35%–0.49%** | **无周期**，不是弱流/短周期 |
| 页级「未加密」 | 495 个 4K 页，完全未变页 **0**，最高相同率 2.27%，均值 0.35% | 无整页跳过 |
| **唯一结构泄漏** | payload 内 0x38..0x41C（**1,428 B**）**P 与 C 同时为全零** | 加密器**跳过全零块** |

**判定：强流密码（CTR/ChaCha 类）或带随机 IV 的块密码；既非 ECB 也非周期 XOR。**

对「改盘」的意义（取决于 IV 是否每次固定）：
- 若密钥/IV 对同一份文件**固定**：已有完整 (C,P) ⇒ 可直接导出 **KS = C⊕P**，改盘用 **C' = P' ⊕ KS** 重新加密（**不必逆出 key**）。
- 若 IV **每次随机**：同一磁盘不同次运行会得到不同镜像，KS 不可复用，改盘仍需逆 key。
- 判别方法：**再取一次冷启镜像**与 8297e6b9… 比对；逐字节相同 ⇒ IV 固定 ⇒ 走 C'=P'⊕KS。

## 9. 第二轮：定位解密例程的进展（2026-10-20，本会话）

### 9.1 已排除：0x42A3xx/0x42A4xx 一带是 mini-libc 封装，不是解密器
- `0x42A408`：变参函数（保存 x0..x7/q0..q7），末尾 `w0=-0x64(AT_FDCWD)` + `bl 0x42EB00` ⇒ **open() 封装**。
- `0x42A3A0`：`lsr x5,x5,#12` 后 `bl 0x42F600`（mmap），再按 `w3&0x22` 调 `0x42F800`(madvise) ⇒ **mmap() 封装**。
- `0x42A498` 起：栈上逐字节构造路径串（已抽出 39 字节，未解成形，见 §7）⇒ 带混淆路径的 open 调用者。

### 9.2 新增硬证据：全文件没有任何标准密码学常量
对全文做常量扫描，以下全部 0 命中：AES S-box(637c777b…)与逆 S-box、ChaCha 的 expand-32-byte-k、
SHA-256 K0(428a2f98，大小端都试)、MD5 T0(d76aa478)、SHA-1 K(5a827999)、CRC32(edb88320)、
XTEA delta(9e3779b9)、Base64 字母表 ⇒ **算法是自定义的**，没有现成原语可套。

### 9.3 0x431350 的 988 B 表更像索引/置换表，不是密钥材料
按 u32 看 0x431390..0x4313B0 有明显人工序列：

    0x10 0x11 0x12 0 0x08 7 9 6 0x0A 5 0x0B 4 0x0C 3 0x0D 2 0x0E 1 0x0F 0

0x431418 起又是 3 4 5 6 7 8 9 10 11 13 15 17 … 的单调序列，且表内含 0x1F0000（=载荷长度）。
⇒ 它是描述符/置换表（偏移、长度、索引重排），是「重排规则」的线索，但**不含 key**。

|---|---|

## 10. 第三轮：自加载器已识别 + 两条抓手被否证（2026-10-20）

### 10.1 `0x4234E0` = ELF 自加载器（不是解密器本身）
判读：`ldrh w5,[x1,#0x38]` = e_phnum、`ldr x0,[x1,#0x20]` = e_phoff、`mov w2,#0x38` + `umaddl` = 以 0x38（Elf64_Phdr）步长遍历 phdr；
命中 **PT_LOAD(1)** 与 **PT_DYNAMIC(2)**；随后 `sub x3,x1,x3` 算 **load bias**，再以 16B 步长遍历动态标签
`4`(HASH)/`5`(STRTAB)/`6`(SYMTAB)/`7`(RELA)/`0x14`(PLTREL)/`0x17`(JMPREL)/`0x6ffffef5`(GNU_HASH)。
⇒ 经典自重定位 + 符号解析，与 `.rela.dyn` 98 条（78 RELATIVE + 20 GLOB_DAT）完全吻合。

### 10.2 否证抓手①：壳代码从不引用 0x431350 的 988 B 表
- 壳区 30,036 条指令里 **adrp 只有 61 条**，目标页仅 0x413000/0x414000/0x442000/0x443000/0x444000，**没有 0x431000**。
- `movz/movk` 落在地址范围的只有 4 条，且是 `0x431BDE83`/`0x41C6xxxx` 这类除法魔数，不是地址。
- 98 条重定位的 addend 无一落在 0x431350..0x43172C。
⇒ 该表不是壳的索引来源（很可能是载荷自己的数据）。抓手①作废，省一轮。

### 10.3 否证抓手②的入口假设：`.text` 只有 121 KB，0x404200 一带是索引表不是代码
- section 表：`.text` = 0x413AB0..0x431350（0x1D8A0），壳的全部代码只在这一小段。
- 0x404200 处是 `14 00 00 00 15 00 00 00 16 00 00 00 18 00 00 00 00 00 00 00 19…`
  —— 递增 u32 序列（重定位/符号索引表），不是指令。
- 因此上一轮报的「代码里有 0x1F0000 常量」是**误报**：那是 u32 值 0x1F 的字节错位命中（0x40422A）。

### 10.4 关键发现：零区是运行期生成的指针，不是纯解密产物
`PT_LOAD#6`（文件偏移 0x3FAA08，filesz 0x55F8）：

| | 内容 |
|---|---|
| 磁盘 | **全零**（熵 0.00，zeroratio 1.000） |
| 运行镜像 | `ec 82 43 4e 73 00 00 00 / 58 83 43 4e 73 00 00 00 / bc 83 43 4e 73 …` ⇒ 每 8 字节一个运行期指针 |

⇒ 镜像这一段不是磁盘数据的函数，而是加载器用 load_bias + 相对偏移现算现写（指针数组/vtable/GOT 类结构）。
方案级结论：镜像 = f(磁盘) 只对**加密载荷区**成立；零区/指针区必须**模拟加载器的重定位与布局**才能复现。
下一步分工：①先逆加密载荷区 0x400..0x1F0000 的解密（纯函数）；②再处理零区生成规则（重定位表 + 布局）；两步齐了才谈 md5。
## 11. 第四轮：导入表证据 + 同址循环候选（2026-10-20）

### 11.2 同址 load/store 循环：135 个候选，判别力不足
扫描「同一 (base,index,disp) 上先 ldr 后 str」的循环，得 **135 个**候选（多为 memcpy/向量搬运形态），
最典型的是 0x414B80/0x414E40（len=52/57，8 对）与 0x415A60/0x415BD0（len=13，2 对）。
没有循环在体内出现 2 MB 级的边界常量（前面已证壳里没有 0x1F0000 字面量）⇒
**解密上界来自运行期寄存器**，静态线性扫无法把这 135 个再收敛。

### 11.3 由此产生的新假设（值得下一轮优先验证）
壳的自解密很可能是**两段式**：壳只解出「入口页/引导块」（够跑到 entry 0x10B00），
其余 2 MB 由**已解密的载荷代码自己解密**（自解密壳的常见结构）。这能解释为什么：
① 壳区只有 121 KB 且找不到 2 MB 上界的循环；② 镜像里 0x400 之后立刻是完整代码。
验证方法（低成本）：在镜像里找是否存在「第二个解密循环」——即载荷代码自身含对 base+0xXXXX 的同址写，
可用 `fg_unpack.py` 扩展成「在镜像载荷区里做同样的同址循环扫描」，与壳区结果对比。
## 12. 第五轮：镜像载荷区扫描 + 常量启发式失效（2026-10-20）

### 12.1 镜像载荷区全量反汇编（0x400..0x1F0000）

| 指标 | 值 |
|---|---|
| 解码指令 | **500,280** 条 |
| 反向分支（循环） | **20,438** 个 |
| 其中「小循环体内含同址 ldr→str」 | **1,257 个** |

典型候选：0x01BCE4（len=15，8 对）、0x01E230（len=30，12 对）、0x020278/0x02106C/0x0210AC（len 6–9）。
**1,257 个 = 载荷本身是完整程序，静态无判别力**，必须靠动态执行或数据流才能定到唯一那个。

### 12.2 常量启发式**失效**（关键负结论）
在镜像载荷区搜索步长/上界常量（u32 与 u64 都试）：

| 常量 | 命中 |
|---|---|
| 0x1F0000 | **0** |
| 0x200000 | **0** |
| 0x1E0000 | **0** |
| 0x1EC00 | 1 处（0x1A3EB，**非 4 字节对齐**，疑似误报） |
| movz/movk 立即数 ≈ 上述值 | **0** |

⇒ 解密上界**不是常量，而是从数据结构（phdr 的 p_filesz/p_memsz 之类）读出来的**，
这与 §10.1「0x4234E0 遍历 phdr 算 load bias」互相印证。「扫大上界常量」这条捷径判定无效。

### 12.3 引导块边界：静态无法确定
壳区同址循环里出现的最大偏移常量也未接近 2 MB（§11.2 已述）。引导块边界只能由动态执行得到。

1. **映射不能跨 4GB 边界**：`mem_map(BASE-0x1000, ...)` 会成功但读不到（静默建了个无效区），
   必须整段映射 `[BASE, BASE+0x500000)`；`BASE = 0x100000000`。
2. **必须先应用重定位**：不应用 `R_AARCH64_RELATIVE`(78) / `GLOB_DAT`(20) 时，壳会读 `[0x442DC8]=0` 然后
   在 `0x42460C ldr q5,[x1],#0x10` 处 UC_ERR_READ_UNMAPPED。补上 98 条重定位 + 一张全 `ret` 的桩页后即可正常跑。
3. svc 桩按 `x8` 号分发：`0x38`=openat（给假 fd）、`0x3f`=read（**按游标从磁盘 so 喂数据**）、
   `0x3e`=lseek、`0xde`=mmap（bump 分配）、`0xe2/0xd7`=mprotect/munmap、`0x5e`=exit_group(停)。

### 13.3 当前结果（40M 指令预算）

| 指标 | 值 |
|---|---|
| 写入载荷区 0x400..0x1F0000 的次数 | **0** |
| syscall 次数 | **1,099**（几乎全是 `read(fd=0xa, buf=0x7F17F2C0, 0x400)`） |
| 与运行镜像相同的 4K 页 | 4 / 1024（=解包未发生） |

⇒ 模拟器**跑得动**（加载、重定位、IO 桩都正常），但程序停在「反复 read 同一缓冲」的循环里，
40M 指令内没有进入解密。两种可能：①它在按 0x400 分段顺序读整个 so（需 ~4,365 次 read）；
②它在读文件头做重试（我们的假数据不满足某个校验）。

### 13.4 下一轮要做的三件事（已定位，成本可控）
1. 把 `--insn` 提到 **3 亿**（约 10 分钟）看 read 是否推进到文件尾并出现 mmap/write；
2. 在 read 桩里打印 `(cursor, 返回长度)`，判断是顺序读还是重试；
3. 若确认顺序读全文件：改为一次把整个文件读进缓冲，直接跳到解密后的阶段。
## 14. 第七轮：模拟跑通 init（并得到一个反直觉结果）

### 14.1 fd=0xa 是 `/proc/self/maps`（不是 so、不是 split APK）
`[openat] fd=10 path='/proc/self/maps'` —— 壳启动时先读自己的映射表（与 Stage 2 观测的 readlink/fd 行为一致），
read 游标 0x0→0x400→0x800… **单调递增 = 顺序读**。

### 14.2 关键修正：maps 里只能出现「模拟器真的映射过」的地址
壳会拿 maps 每段起始地址**解引用并比对 ELF 魔数**（0x4232B0 处 `ldr w3,[x1]` 比 `0x464C457F`，
再查 `ldrh [x1,#0x12]`==0xB7 即 e_machine=AArch64）。最初喂了含 `0x12c000000`/`0x7f0000000` 的假 maps，
壳一 deref 就 `UC_ERR_READ_UNMAPPED`（pc=0x1004232B4）。改成只列 BASE 段/STACK/HEAP 后通过。

### 14.3 反直觉结果：init 跑完**没有解压/解密载荷区**

| 指标 | 值 |
|---|---|
| 60M 指令后的 final pc | `0x100600000` = 桩页 STUB ⇒ **init 正常返回** |
| syscall 次数 | **4**（1×openat maps + 3×read） |
| 写入 0x400..0x1F0000 | **0** |
| 与运行镜像相同页 | 4 / 1024 |

两种解释，必须下一轮区分：
**(A) 我们的假环境让 init 早退**：某个 syscall/结构体返回值不合预期，走了「检测失败就不解」的分支；
**(B) 解密根本不在 init_array 里**：而在 `_start`(0x10B00) 之前的其它路径（例如壳自己实现的重定位+解密在 entry 前被调用）。

### 14.4 下一轮两个动作（成本都很低）
1. hook **全部** store（不限载荷区）并统计 init 到底写了哪些地址 → 看它是真的干了活还是立刻 return；
2. 打印每个 syscall 的**返回值**与随后 3 条指令，判断是否有 `cmp x0,#-1; b.eq 早退` 这类分支被我们触发。
## 15. 第八轮：三个构造器全跑 + 崩因定位

### 15.1 带全部 store 统计（按区域）与三构造器依次执行

| 区域 | 写入次数 |
|---|---|
| stack | 6,747 |
| image_data（0x44xxxx） | 20（如 0x444DD0=__bss_start、0x442FE0） |
| **载荷区 0x400..0x1F0000** | **0** |
| image_zero / heap | 0 |

ctor0(0x413B0C)、ctor1(0x413B10) 正常跑完：只做了「读 /proc/self/maps + 20 次数据写 + 栈操作」，**完全没触碰载荷区**。
ctor2(0x413B5C) 在 **0x4181C4** 崩（UC_ERR_READ_UNMAPPED），因此还不能断言早退。

### 15.2 maps 自检不是拦截点（假设 A 被否证）
把 ELF 头拷到 BASE+0x413000（让 maps 第二段也能过魔数比对），重跑结果**与不拷完全一致**
（0 次载荷写、final pc=桩页、syscall 仍 4 次）⇒ 自检不是拦住解密的原因。

### 15.3 ctor2 的崩因（已精确定位，是**我们环境**的缺陷）

    418190: adrp x1,0x442000 ; ldr x1,[x1,#0xdc0]   // GOT 槽（GLOB_DAT）
    4181b4: ldr x2,[x1]                            // 把 GOT 值当**对象指针**
    4181c4: ldr x2,[x2,#0xc0]                      // ← 崩在这里

我们给 20 个 GLOB_DAT 槽填的是**指向全 ret 桩页的地址**（当函数指针用），
但壳把它们当**对象指针**（[x2+0xc0] 取虚函数）。x2 于是等于 0xc0035fd6（ret 机器码），加 0xc0 即未映射。
⇒ 修法：GLOB_DAT 要给结构化的假对象（≥0x200 字节、各字段填 ret 桩地址的假 vtable），不能用裸 ret 页。

### 15.4 对主线的意义
目前三个 init_array 构造器里没有一个写载荷区（ctor2 还没跑通，但其前 20 条指令在建对象、取 vtable，不像解密入口）。
若修好 GLOB_DAT 后 ctor2 仍无载荷写，就基本坐实假设 B：解密发生在 entry(0x10B00) 之外的路径，
需要转向问题「谁在 entry 前把 rwxp 段解密」（壳自己的 _start、或 FairGuard 后续 remap 的线程）。
## 16. 第九轮：GLOB_DAT 修好后 ctor2 仍崩 —— 崩因变成「.bss 全局结构未初始化」

### 16.1 已按建议修 GLOB_DAT
20 个 GLOB_DAT 槽不再指向裸 ret 页，而是各自独立的 **0x200 字节假对象**（每 8 字节都填 ret 桩地址）。
结果：ctor2 **仍崩在同一地址 0x4181C4**，但崩因已经变了。

### 16.2 新崩因（精确到指令与数据来源）

    418190: adrp x1,0x442000 ; add x1,x1,#0xa60     // x1 = 0x442A60（.data.rel.ro）
    4181b0: ldr  x1,[x1,#0xdc0]                    // x1 = *(0x442DC0)
                                                   //   重定位里 [0x442DC0] <- 0x444D30（.bss 全局地址）
    4181b4: ldr  x2,[x1]                           // x2 = *(0x444D30) = 0（.bss 未初始化）
    4181c4: ldr  x2,[x2,#0xc0]                     // ← 崩

⇒ 壳期望 **0x444D30 这个全局结构在 ctor2 之前就已被填好**（真实进程里由 ctor0/ctor1 或更早路径写入），
模拟器里它还是 0。这不是 GLOB_DAT 的问题，而是**模拟器缺少真实进程已初始化的 .bss/.data 状态**。

### 16.3 最优修法（下一轮，成本很低）
用真实运行镜像的 .data/.bss 段**预置模拟器**：
现在只 dump 了 0x0..0x400000（4 MB），而模块的 rw 段在 0x442000..0x445218。
再取一次 **0x442000..0x446000**（16 KB）运行期内容，mem_write 到对应地址，
ctor2 就能跳过这类「全局结构未初始化」崩溃 —— 比重头逆向结构定义便宜得多。
## 17. 第十轮：rw 段预置（含懒映射）与交接点

### 17.1 已 dump 到真实 rw 段
设备实测映射：`7343dbb000-7343dbe000 rw-p 00442000 ... libFairGuard.so`（**3 页 = 12,288 B**，对应 va 0x442000..0x445000），
`dd bs=4096 skip=<addr/4096> count=3` 取回（`/tmp/fg_rw.bin`，仅工具侧临时文件）。

### 17.2 结果：ctor2 越过了 0x4181C4，但仍 0 载荷写

| 配置 | ctor0 | ctor1 | ctor2 | 载荷写 |
|---|---|---|---|---|
| 无预置（gcc 假对象 + 假 ELF） | 返回 | 返回 | **崩 0x4181C4** | 0 |

### 17.3 结论与**交接点**（本会话到此收尾，按决策官指令交给 A2）

  因此「解密发生在 init_array 内」这一可能性**已显著下降**（但不能 100% 排除，因为懒映射会掩盖真实错误路径）。
- 交接给 A2 的第一件事（二选一，都比现在精确）：

  **(b)** 直接转向「谁在 entry 前解密」：检查 `e_entry=0x10B00` 之前是否有 `mprotect(rwxp)`+解密，
      或在真实进程里对 `0x400..0x1F0000` 下**写守护**（硬件/软件断点），直接抓执行者。
- 已确认事实、未决问题、脚本入口、证据落点：§1–§17 全在本文档，`04_scripts/绿梦/fg_emu.py` 可直接复跑：

## 18. 第十一轮（A2）：解密引擎定位到 **0x41EF60**，且在 init_array 内（前一轮的「0 载荷写」是模拟器误判）

### 18.1 静态事实：ELF 里没有 DT_INIT，e_entry 落在加密区

| 项 | 值 | 含义 |
|---|---|---|
| `e_entry` | **0x10B00**（非 0） | 落在 A 区密文内 ⇒ 壳必须先让 0x10B00 变成代码才能交棒 |
| `dt_init` | **不存在**（DT_DYNAMIC 里只有 DT_INIT_ARRAY/DT_INIT_ARRAYSZ=32） | 没有独立于 .init_array 的入口 |
| `.init_array` | 0x442A20，4 槽；只有 3 条 RELATIVE（→0x413B0C / 0x413B10 / 0x413B5C），第 4 槽恒 0 | 构造器确实只有 3 个，前几轮的判断正确 |
| `PT_LOAD#0` | off 0x0 va 0x0 **filesz=memsz=0x43BAE8 flags=R+X** | **0x400..0x400000 全部是文件映射的只读可执行页** ⇒ 任何原地解密都必须先 `mprotect(PROT_WRITE|EXEC)`（PROT=7）或另建可写映射 |
| `PT_LOAD#1` | va 0x442A20 filesz 0x2300 memsz 0x27F8 flags=R+W | 唯一的可写段（12 KB 级），也就是 §17 预置的 /tmp/fg_rw.bin |

### 18.2 ctor2 只有 11 条指令，第 2 个调用就是解密引擎

```
413b5c  sub sp,sp,#0x30 ; stp x19,x30,[sp]
413b64  add x19,sp,#0x10 ; mov x0,x19
413b6c  bl  0x418190        // 在栈上造 0x20B 的「模块描述符」{vtable=0x442A60, +8=handle, +0x10=obj, +0x18=ctx}
413b70  mov x0,x19
413b74  bl  0x41EF60        // ★ 解密/自修复引擎（本轮的定位结果）
413b78  mov x0,x19
413b7c  bl  0x41821C        // 收尾
413b88  ret
```
⇒ **解密/重写引擎在 init_array 之内（init_array[2]），且是无条件直接调用**，不依赖任何检测通过分支。
（ctor0 = 0x413B0C 就是一条 `b 0x4234E0`（§10.1 的自加载器）；ctor1 = 0x413B10 走 malloc/0x4141B4/0x429640。）

### 18.3 0x41EF60 内部：全壳**唯一**两处 mprotect(PROT=7)

全壳 44,440+ 条指令里只有 1 个 mprotect 的 svc 桩（0x42EF00，x8=0xE2），其余 13 个内联 svc
在 0x42EB00..0x42F800（openat/read/write/exit_group/lseek/mmap/munmap…）。调用它的**只有两处**，
都在 0x41EF60 这个函数体（0x41EF60..0x4205EC，单出口 0x4205EC）里：

| EA | 形态 | 判读 |
|---|---|---|
| **0x41F0A4** | `mov w2,#7 ; blr x3`（x3 = vtable 槽 +0xE8 = mprotect 桩） | `mprotect(module_base, struct.field_0x424, RWX)`：先把整个镜像改成可写可执行 |
| **0x420074** | `x0=x22(页对齐) ; x1=[x21+0x70]+(x20-x22) ; w2=7 ; blr x3` | 同上，按 [页首, 尾) 再刷一次 |

改完属性后进入「记录表 → 定点重写」循环（0x41FF..0x4202A8）：

- 表指针 `x25=[x21+0x60]`、条目数 `w24=[x21+0x68]`，**步长 0x18** 的记录：
  `{u32 off @+0, u8 type @+5, u16 len @+6, u64 slot @+8}`
- `type==0x10` / `type==0x30` 走同一段：先算 32 位密钥
  `keystream = H(off ^ 0x258D950D, len ^ 0xAD31D0BE)`
  （djb2-变体：`w=0xAB23A1B4`，每字节 `w=w*33+b`，带 `0xD45D9F0D/0x8AD86495/0x5CDF66BA/0xE66AF3D9` 的混淆分支）
- 然后 `dup v1.4s,w1` + `eor v0.16b,v0,v1` + `str q0,[x16],#0x10`
  —— **源 = base+off+1，目的 = base+off**，末尾 `strb wzr,[dst+len]`。即「整体左移 1 字节 + 4 字节周期 XOR + 补 NUL」。
- 之后 `str x0,[x4]`（0x420300）把 `(rel + slot ^ [x21+0x78])` 写回记录：这是**指针槽的修补**。

⇒ 0x41EF60 = **自修复/自重定位引擎**（改段属性 + 解混淆字符串/符号名 + 补 GOT 槽），
它确实会往 0x400..0x1F0000 里写（该区正是它自己的 .dynsym/.dynstr/.rela 所在：0x405200/0x40B3C8/0x412FC8）。

### 18.4 否证：这套「32 位周期 XOR」**不是** 2MB 主体解密（关键负结论）

拿磁盘密文与运行期镜像（`fg_runtime/libFairGuard_rwxp.bin`）做差：

| 检验 | 结果 |
|---|---|
| 0x400..0x1F0000 中 byte-identical 的 4K 页 | **0 / 495**（整段都被改写过） |
| 令 X = disk ^ img，X[i]==X[i+4] 的比例 | **0.0039 ≈ 1/256**（= 随机，不是 4 字节周期密钥） |
| 长度 ≥64B 的「4 字节周期」连续段 | **0 段**（src 位移 0 / +1 / −1 三种都试过） |
| X 的零字节比 / 字节值分布 | 0.0035 / 256 种全出现 ⇒ 真正的流式密钥，不是常数密钥 |

⇒ 「每记录一个 32 位密钥」的解释**不能**覆盖 2MB：要么 2MB 主体用的是**真正的流/块密码**（另一处代码），
要么运行期该段根本不是「磁盘密文解密」，而是被**另一份数据整段替换**（压缩流/第二 blob）。
18.3 的引擎据此判定为「自修复」，不是主体解密器；**主体解密器仍未定位**。

### 18.5 前一轮「init 不写载荷」是**模拟器误判**（已精确定位到指令与寄存器）

用 `--trace` 抓 ctor2 的实际死亡点（`--entry 0x413b5c`，其余参数同 §17）：

```
[TRACE] hit 0x4181c4  x1=0x7343dbdd38  x2=0xB400007370A98C00   // = *(0x444D30)，带 0xB400 顶字节的堆指针
[TRACE] hit 0x4181d0  x1=0xB400007370BEC500  x2=0x0             // [x2+0xC0] 落在未映射页 → 惰性零页返回 0
final pc=0x0                                                     // blr x0 → 跳到 0
```

- 0x4181C4 `ldr x2,[x2,#0xC0]` 取的是**带标签的设备堆对象**（0xB4_TRUNC_007370A98C00），模拟器没有这块内存；
  惰性映射补 0 ⇒ 0x4181D0 `blr x2` 跳到 0 ⇒ `emu_start(until=0)` 把它当成「命中 until 正常结束」。
- 三构造器同跑一遍：**ctor1 与 ctor2 都以 PC=0 结束**，惰性补页 34 页，syscall 仅 4 次，`0x41EF60` **一次都没命中**。
  （§17.2 表里「+ rw 预置 + 懒映射 → 返回/返回/越过 0x4181C4」应改读为：ctor1/ctor2 **都是跳到 0 的假返回**。）
⇒ 「解密不在 init_array」这个结论**不成立**：引擎地址 0x41EF60 就在 ctor2 里，只是模拟器根本没跑到那一步（差 1 条 bl）。
  `fg_emu.py` 已加两条门禁：ctor 结束若 PC==0 打印 WARN、结尾打印 lazy-mapped pages（本轮 34 ⇒ 结果不可信）。

   **记录表的真实内容就能直接给出「哪些 off 被改写」**，这才是主体解密器的入口线索。
3. 设备侧写守护（B③ 原案）：把 PT_LOAD#0 的 p_flags 从 5 改成 4/6（去 X 或去 R 都会立刻崩），
   或反过来**只保留 R**，冷启抓 SIGSEGV 的 PC —— 由 18.1 已知写载荷必须过 mprotect，
   所以更值得守的是 **mprotect 的返回点 0x41F0A8 / 0x420078**：谁在 mprotect 之后立刻写载荷，PC 就在那附近。
   改 ELF 头不触发完整性闸门已由 B 区实验证明。
4. 若 2MB 主体其实是「整段替换」：核对 0x1F0000..0x1F452D 那 17,709 B 高熵块（结尾 `77 00 00 00` 后全零）
   是否是某个压缩/加密流的一部分（可先试 lz4/zlib/aPLib 头与熵分布）。

## 21. 第十四轮（A2）：blob 头 `+0x10` = **变体/构建标签选择器**（不是校验和）⇒ 改包无需动它

### 21.1 谁读它、读来干嘛（静态确证，EA 齐全）
唯一读者在 **0x415398**，同一函数里 x20 = `base+0x400`（blob 头）——这一点由 0x4153C8 反证：

```

415394  ldr  w1,[x20,#0x24]      // blob +0x24
415398  ldr  w19,[x20,#0x10]     // ★ w19 = blob +0x10 = 0x97976BDE
4153b0  blr  x3                  // (先干一件与 x22 字符串缓冲有关的事)
4153b4  mov  w2,#0x6bde ; movk w2,#0x9797,lsl#16   // w2 = 0x97976BDE
4153b8  mov  w1,#0xa588 ; movk w1,#0xc25c,lsl#16   // w1 = 0xC25CA588
4153c4  cmp  w19,w2
4153c8  str  w1,[x20,#0x34]      // 无条件写 "已处理" 标记 0xC25CA588
4153cc  b.eq 0x416b24            // ← 本 build 走这里
4153d0  cmp  w19,0xB4009B11 ; b.eq 0x415730
4153e0  cmp  w19,0xA6A70A93 ; b.eq 0x415708
4153f0  cmp  w19,0x992B4166 ; b.eq 0x415EF8
```

本 build 的分支 0x416B24 立刻读 `+0x20`(csize) 与 `+0x1C`(usize) 去干活，其余分支同型

⇒ **`+0x10` 是「变体/构建标签」白名单**（6 个已知值各对应一条实现路径），**没有任何地方对它做校验和比对**：

## 22. 第十五轮（A2）：`csetm w0,ne; exit_group` 三点同型 —— 是**指针自洽校验**，不是证书比较；且 NOP 后 w0 是死值

### 22.1 三个同型点（决策官只知道两个；**第三个 0x28F2E0 是新发现**）

| # | cmp | csetm（原字节） | bl exit_group | 之后 |
|---|---|---|---|---|
| 1 | `0x2F084 cmp x1,x0` | **0x2F088** `e0 03 9f 5a` | 0x2F08C `5d b3 0c 94` | `b 0x2E7C4` |
| 2 | `0x47E14 cmp x5,x0` | **0x47E18** `e0 03 9f 5a` | 0x47E1C `f9 4f 0c 94` | `b 0x3984C` |
| 3 | `0x28F2DC cmp x1,x0` | **0x28F2E0** `e0 03 9f 5a` | 0x28F2E4 `c7 32 03 94` | `b 0x27D9CC` |

全载荷 16 处 `csetm w?,ne` 里，只有这 3 处后面紧跟 `bl 0x35BE00`（= `mov x8,#0x5E; svc #0` exit_group）。

### 22.2 比较的两个操作数：**都来自同一个指针自己**，没有证书参与

```
  ldrb   w?, [p]              // 取 p[0] 的 bit0
  ubfiz  x?, x?, #3, #1       // → 0 或 8
  add    x?, p, x?
  ldr    x0, [x?, #8]         // 第 1 级解引用（封装指针解封：tag 位选 +0/+8）
  ldrb   w?, [x0]
  ubfiz  x?, x?, #3, #1
  add    x0, x0, x?
  ldr    x0, [x0, #8]         // 第 2 级
  ldr    x0, [x0, #0x18]      // 第 3 级
  ldr    x0, [x0, #0x18]      // 第 4 级
  cmp    p, x0                // ★ 解封/链式解引用出来的指针必须指回 p 自己
  csetm  w0, ne               // w0 = (p != x0) ? -1 : 0
  bl     0x35BE00             // exit_group(w0)  —— 匹配退 0，不匹配退 -1
```
⇒ 这三点是 **FairGuard 的封装指针/对象自洽校验**（"解码出来的指针必须等于原指针"）：
「期望值」就由 p 自身的 tag 位算出，**不需要任何外部期望数据**；
这三处附近没有任何与 `map+0x6000`（APK v2 签名块）相关的位移读，**静态看不到证书参与**。
所以「一个是读 APK 证书的结果、一个是期望证书」这个模型在这三个 EA 上不成立。

### 22.3 关键负面结论：NOP 掉 exit 之后，w0 是**死值**

三个落点（`b 0x2E7C4` / `b 0x3984C` / `b 0x27D9CC`）的第一条指令就把 x0/w0 重写：
`mov x0,#0x5EE8` / `mov x0,#0x1A10` / `mov x0,#0x76E0`。
⇒ **"把比较结果改成 match" 无法改变 102s 的行为**（在 exit 已被 NOP 的前提下，w0 根本没人读）。
match/mismatch 唯一能起作用的地方是 **exit 的退出码（0 vs -1）**，也就是说必须**保留 exit 调用**才有意义。
这同时给出一条判据：35s 那次到底是退出码 0 还是 -1，决定了这三处到底是"校验通过后正常退出"还是"校验失败的退出"。

### 22.4 已产出两个补丁产物（均 roundtrip 通过，文件长度 4,477,792 不变）

| 文件 | patch | 明文差异 | md5 |
|---|---|---|---|
| `libFairGuard_match.so` | 3 处 `csetm` → `mov w0,#0`（**保留 exit**） | 3 段 × 4 B = **12 B** | `da1ff827d1c89a2abae104f31cba7b08` |
| `libFairGuard_match_noexit.so` | 上述 3 处 + 3 处 `bl exit_group` → `nop` | 4 段 = **23 B** | `5367d37b309c6151afb01cb7a4ea8da9` |

patch 字节：`csetm w0,ne` `e0 03 9f 5a` → **`00 00 80 52`**（`mov w0,#0` = "match" 值）。
两个文件除流区与头 `+0x20`（2 B）外零改动，`+0x10` 保持 `0x97976BDE`。

### 22.5 未闭环

2. 若 35s 本来就是 0（= 校验通过后正常退出），则「签名 mismatch 状态」必然由**别的比较点**产生，

## 23. 第十六轮（A2）：v2 签名块读者 / tampered 标志 —— **静态四条路全部走死**，改用动态读监视（脚本已给）

### 23.1 先给一个能省时间的范围事实
解包镜像 4.2 MB 里**真正的代码只有 0x35D434..0x3B3D28（346 KB，88,197 条指令，40 个函数序言）**，
其余 3.8 MB 是数据/表（0x3B3D28 之后逐条反汇编会出现成片的 `udf` = 数据）。
⇒ 任何"在载荷里搜指令"的工作**只应在这 346 KB 里做**，全镜像线性反汇编必然全是噪声。

### 23.2 四条静态路线全部否证（本轮实测）

| 路线 | 结果 |
|---|---|
| 明文常量 **"APK Sig Block 42" / "base.apk" / "/proc/self/maps" / "PK\\x05\\x06" / "signature" / "sha256"** | 磁盘 so 与解包镜像**各 0 命中**（全部运行期解码） |
| **0x6000 / 0x17000 / 0xAB3* / 0xAB36000** 立即数或 load 位移 | shell 与载荷 text 里**全部无有效命中**（只有 `movk #0x6000,lsl#16` 与成片 `udf` 噪声） |
| **硬件时间源**（`mrs cntvct_el0` 等，用来找周期检测的驱动源） | 载荷 text 只有 3 条 `mrs`（ctr_el0/fpcr），shell 1 条 `ctr_el0` ⇒ **没有 cntvct**，周期检测的计时走 libc 或外部线程 |
| 证书指纹（含 256 单字节 XOR、二进制/十六进制两种形态） | 前几轮已 0 命中，本轮复核仍 0 |

⇒ 「谁读 v2 块」**无法用常量/字符串定位**，因为 FairGuard 把解析常量全部运行期解码（与本 so 其它部分同构）。

### 23.3 反证：三个 35s 点**不读任何标志**
0x2F08C / 0x47E1C / 0x28F2E0 三条路径里（各自前 ~20 条指令内）**没有任何 `ldrb/ldr` 读全局布尔**，
只有对 p 自身的链式解引用 + `cmp p,x0`。⇒ 若 D 认为"tampered 标志同时喂 35s 与 102s"，
那么 **35s 的触发者不是这三点**（这三点只是"指针自洽检查 + exit"）。

### 23.4 交付：读监视脚本 `04_scripts/绿梦/fg_v2watch.js`（node --check 通过）
思路：v2 块所在段是 `r--s` 文件映射（maps 里 offset 0xAB36000、含 base.apk），
用 **frida-gum 的 `MemoryAccessMonitor`** 把该段置为不可访问并接管缺页，
**任何读/写都会回调，`details.from` 就是发起访问的指令地址**（= 读取者 PC）。
```
adb shell am force-stop com.zhuziplay.lvmengnew.op
frida -U -f com.zhuziplay.lvmengnew.op -l 04_scripts/绿梦/fg_v2watch.js --no-pause
```
输出形如 `[HIT] op=read from=0x7343d9xxxx (libFairGuard.so+0x2f0a4) access=0x...`，
同一个 from 只打印一次（去重），64 次后自动关闭，避免刷屏与过量开销。
脚本只读，不改任何字节；**风险**：FairGuard 装了 sigaction 信号处理器，缺页接管可能被它察觉（会重映射/自检），
若出现异常早退就改用 frida `Stalker` 只跟那几个线程，或改用 GDB 硬件读断点。

### 23.5 拿到 reader PC 之后的最短路径
1. 在解包镜像里反汇编 `reader_va ± 0x400`（偏移 = PC - 模块基址，模块基址 = maps 里 libFairGuard.so 段首）；
2. 前 3 层调用者里找 **`ldrb/ldr` 读"期望值"缓冲** + 之后的 `cmp/b.ne` 或 `cset`；
3. 该 `cmp` 的结果寄存器若被 `strb/str` 写进一个 adrp 全局 → 那就是 **tampered 标志**，
   把它改成恒"未 tamper"（`strb wzr,[..]` 或把 `cmp` 换 `cmp x,x`）即可同时压掉 35s 与 102s 的响应。

### 23.6 未闭环
1. v2 块读者 PC（需 23.4 的动态一次运行）；2. tampered 标志地址（依赖 1）；3. 102s 周期检测的驱动源（无 cntvct，疑外部线程/libc 计时）。
