# 绿梦 2026-10-30 热更导致五项功能失效 —— 诊断与修复

> 触发：用户报「游戏热更导致游戏功能失效」。设备＝小米 M2102K1AC（`96f0d883`，Android 14 / arm64，**无 root**）。
> 本文是单游戏事实（技术记录），通用流程见 `skill/re-extract/hotupdate-fingerprint-recheck.md`。

## 1. 结论（实测，非推断）

热更换了 **Dll 热更程序集 bundle**，我们打补丁的那份被游戏清掉了 ⇒ `Assembly-ACT.dll` 回到官方未补丁状态
⇒ 五项功能全部失效（菜单/授权/native 壳都正常，只是战斗侧 IL 补丁不在了）。

| 项 | 热更前（v32 交付时） | 热更后（2026-10-29 22:24） |
|---|---|---|
| Dll 清单 | `Dll_prod_1.0.0_prod.a_52.bytes` | `Dll_prod_1.0.0_prod.a_56.bytes`（构建时间 `2026/10/29 19:05:22`，`prod_1.0.0_prod.a_13037`） |
| bundle 哈希（目录名） | `f8124a60540376c3583f7e7d15eaf9e0`（`BundleFiles/f8/…`） | `17d93118365e63ab20bf267703295779`（`BundleFiles/17/…`） |
| `__data` | 13,212,366 B（我们的补丁 bundle，crc `33feacc8`） | 13,183,369 B（官方新包，crc `8bb6550b`） |
| `Assembly-ACT.dll` | 14,583,296 B | **14,587,904 B**（+4,608） |
| 补丁目录 `f8/…` | 有我们的 `__data`/`__info` | **空**（2026-10-30 01:35 被游戏清掉） |

证据：设备 `/sdcard/Android/data/com.zhuziplay.lvmengnew.op/files/yoo/Dll/`
（`ManifestFiles/` 内 a_52/a_56 并存、`CacheRecords.snapshot` 两条记录、`BundleFiles/f8` 目录 mtime 01:35 且为空）。

**机理**：`LvmengPayloadProvider`（classes4.dex）把 `assets/lvmeng/{__data,__info}` 每次启动写进
**写死的** `yoo/Dll/BundleFiles/f8/f8124a60…/`。热更后清单指向新哈希，游戏只读 `17/17d9…`，
f8 里的补丁不被加载；同时游戏按新版本清掉旧缓存目录 ⇒ 补丁彻底失效。

## 2. 修复（不换 so、不改 Manifest、不动菜单框架）

1. **取新 dll**：`bundle_repack.py extract-stream/inspect/locate-pe` 从新 bundle 解出解压流（29,334,364 B），
   `Assembly-ACT.dll` 落在流内 `off=6711832 size=14587904`。
2. **重注入 IL**（`ilpatch build --phase 2 --padsize 14587904 --keep-size 1`）：6 个挂点全部命中，等长回填，**常量丢失 0**
   - `Hello::Run` prefix → `StarryBootstrap`
   - `ACT.Battle.SystemTime::FixedUpdate` postfix → `s_starryTick`（全局变速/每帧驱动）
   - `ACT.Battle.CompAbility::ServerSetHP` prefix → `OnSetHP`（自定义血量，条件 `starg`）
   - `ACT.Battle.SystemAbility::ServerResolveDamage` prefix → `OnResolveDamage`（伤害倍率）
   - `ACT.Battle.Configs.ActionSetJumpCount::Do` postfix → `OnSetJumpCount`（无限跳跃）
   - `ACT.Battle.CompMotion::RecoverMotionCount` postfix → `OnRecoverMotion`（无限技能/跳跃兜底）
3. **重打 bundle**：`bundle_repack.py replace --offset 6711832 --size 14587904` → `__data` **13,221,333 B**（224 块、索引 0 不透明块原样保留）；
   `write-info` → `__info`（18 B，crc `d6d3451d`，size 13221333）。回读解压流逐字节比对：补丁 dll 与 bundle 内切片 `MATCH`。
4. **dex 改包（classes4.dex，baksmali→smali）**：
   - `BUNDLE_GUID` / `GUID_DIR` / 实际建目录用的路径串（`yoo/Dll/BundleFiles/…`）→ `17d93118…`、`17/17d93118…`（4 处）；
   - `writeSnapshotIfAbsent` 的「snapshot 已存在就 return」改成无条件跳转（`if-eqz` → `goto`）：
     **必须**每次重写 snapshot，否则游戏用自己下载的官方记录（crc `8bb6550b` / size 13,183,369）判定我们
     13,221,333 B 的补丁大小不符 → 删档重下 ⇒ 补丁又被冲掉。
5. **出包**：`04_scripts/绿梦/repack_apk_payload.py`（新增，跨平台）以设备现装 v32（`base.apk` md5 `775f8017…`）为底包，
   只换 `classes4.dex` / `assets/lvmeng/__data` / `assets/lvmeng/__info`，其余 1334 条逐条 sha256 不变，zipalign `-p 4` + apksigner 重签。

## 7. 第二轮：r4 补 su 修复（10-30 下午）

### 7.1 r4（并入 r3 的 su 修复）
- 症状（他人反馈 + 本机复现）：**点悬浮球就闪退**；小米 96f0d883（无 `su`）不闪退，无法本地复现。
- 根因：昨天发布的 `hotfix20261030` 的 `classes4.dex` 基线取的是设备现装 v32，**没并入 r3 的 su 卡死修复**，
  有 `su` 二进制但未授权的机型上 `showMenuNative → Preferences.with()` 被钉死 ⇒ ANR/闪退。
- 做法（`04_scripts/绿梦/lvmeng_build_dex.sh` + `merge_menu_classes.py`）：从 r3 源码（`f647ee92`）编出
  `DeviceFingerprint` / `Preferences` / `LvmengPayloadProvider` 三个类，**外科替换**进已部署 dex，其余类逐字节保持。
  只换这三个类而不是整包重编，是为了保住部署 dex 的 desugaring 形态（`$$ExternalSyntheticApiModelOutline*`）；
  替换后机器校验「其余类零差异、外部引用 83 个签名 0 缺失」。
- 结果：`绿梦_1.0.5_starry-r4-releaseSigned.apk`（md5 `c6df1a77…`），装机后**点悬浮球不再闪退**、菜单正常展开。

### 7.2 r5（r4 暴露的真 bug：登录点了没反应）
- 症状：菜单账号页输入卡密 → 点「登录」只弹「登录中…」，**一个请求都不发**（`NativeMenu` / `AuthClient` 日志一行没有）。
- 根因（代码级，**框架级缺陷，影响所有走 su 兜底的游戏**）：`DeviceFingerprint.runSu()` 里 `p.waitFor()`
  **没有超时**，只靠旁路线程到点 `destroyForcibly()` —— 对 D 态 / 被 seccomp 停住的子进程无效 ⇒ `waitFor()`
  永久阻塞**调用线程**。该调用线程正是 `authExec`（`newSingleThreadExecutor`）的首个任务 `fetchBootstrapOnce`：
  首次装机无缓存 → `getOrCreateDeviceId → writeSeed → runSu → waitFor()` 卡死 ⇒ 线程永不返回 ⇒ 后续所有授权任务
  （含点「登录」）在队列里排到死。日志特征：只有 toast，`NativeMenu`/`AuthClient` 零行。
- 修复：`waitFor` 挪进旁路线程 `starry-su-wait`，主调方 `join(timeoutMs)` 到点即返回 `-1` 并置 `suBroken` 熔断，
  **调用方永不被拖死**；同时在 `writeSeed` / `resolveDeviceIdSlow` 加打点（下次卡住日志直接指行）。
- 证据（r5 装机重启后，`96f0d883`）：
  ```
  13:42:18.682 NativeMenu: bootstrap fetch game_id=lmskzs
  13:42:18.683 AuthClient: GET /v1/bootstrap?…&device_id=dev_1f09f3e6…
  13:42:19.039 AuthClient: ← 200 (675 bytes)          ← 旧包上这两行从未出现
  13:42:55.361 NativeMenu: login with game_id=lmskzs
  13:42:55.362 AuthClient: POST /v1/auth/login
  13:42:55.836 AuthClient: ← 200 (1881 bytes)         ← 登录成功，票已下发
  13:42:55.849 StarryMagic: [V2] s=1 m=ffffffff       ← grant 应用、功能放行
  ```
- 结论：r5 = `绿梦_1.0.5_starry-r5-releaseSigned.apk`（md5 `3e8c2d41…`），登录链路实测打通。
- 未验证：**冷装首启**的 su 卡点只剩静态保证（本次装机时设备号已缓存，没再走慢路径）。

### 7.3 r6（r5 仍有洞：清数据后冷启又卡死，卡点在 `Runtime.exec` 本身）

- 症状（用户清数据后复测）：又只剩「登录中…」。**确认设备装的就是 r5**——日志里出现了 r5 独有打点
  `设备号采集开始（无有效缓存，走慢路径）` 与 `su 尝试(1500ms 上限): …`。
- 实测卡点（打点直接指出来）：
  ```
  13:53:43.193 StarryPrefs: step2 身份已落盘 → 开始写 seed
  13:53:43.198 DeviceFingerprint: su 尝试(1500ms 上限): mkdir -p '/storage/emulated/0/Android/starry_mag…
  （之后既无「熔断」也无「seed 写入」行，直到进程被杀）
  ```
  ⇒ r5 只给 `p.waitFor()` 加了超时，**`Runtime.exec()` 自己就会不返回**（forkAndExec 在子进程被 seccomp 笼子
  /不可中断状态停住时，父进程读 errno 管道永远等不到结果）⇒ 超时机制根本没机会触发。
  触发路径：清数据 → 设备号无缓存 → `resolveDeviceIdSlow` → `writeSeed` 直接写不了 → 又调一次 su → 卡死。
- 修复（两处，缺一不可）：
  1. `writeSeedFile` **彻底删掉 su 兜底**——种子文件只是「prefs 被清后找回同一身份」的可选加速，写不进就放弃；
     实测清数据后 SSAID 不变、设备号仍重建为同一个 `dev_1f09f3e6…`，不影响授权。
  2. `runSu` **把 exec + 读 stdout + waitFor 全塞进工作线程 `starry-su-worker`**，调用方只 `join(1.5s)`，
     到点无条件返回 `-1` 并熔断 ⇒ 任何调用线程（含 `authExec` 单线程池）都不可能被拖住。
- 证据（r6 装机冷启 + 用户点登录）：
  ```
  13:58:06.680 NativeMenu: bootstrap fetch game_id=lmskzs
  13:58:06.683 AuthClient: GET /v1/bootstrap?…device_id=dev_1f09f3e6…
  13:58:07.081 AuthClient: ← 200
  14:03:26.561 AuthClient: POST /v1/auth/login  → ← 404 (42 bytes)   ← 首点一次 404（网关/瞬时）
  14:03:37.813 AuthClient: POST /v1/auth/login  → ← 200 (1881 bytes)
  14:03:38.300 StarryMagic: [V2] s=1 m=ffffffff                      ← 授权成功、功能放行
  ```
- 正式包：`绿梦_1.0.5_starry-r6-releaseSigned.apk`（md5 `450a0de5ddeb3a905514eae788695596`，
  sha256 `f081094dff2700d2…`，`classes4.dex` 570,356 B / sha256 `2f0cf12e…`）。
- 残余观察：首点拿到过一次 `404`（42 字节，网关/瞬时），重试即 200；若他人复现「点一次没反应、再点一次成功」，
  按这条处理，不是客户端 bug。
