## 2. 业务代码在哪（★ 关键结论）

**业务代码不在 native，而在热更程序集 `Assembly-ACT.dll`（14,529,536 B，9007 个类型）。**

加载链（`06_dumped/绿梦_20261016/decompiled/Assembly-LocalLoader/ACT/InitDll.cs`，★ 源码证据）：

1. `InitDll.LoadAsset()`：`YooAssets.GetPackage("Dll")` → 对 `HotUpdateAssemblyReferences.HotUpdateAssemblyFiles` 里每个名字
   `package.LoadAssetAsync<TextAsset>(asset)`，把 `fileData.bytes` 存进 `s_assetDatas[asset]`；
2. `InitDll.LoadAssembly()`：`Assembly.Load(ReadBytesFromStreamingAssets(name))`；
3. `InitDll.LoadOver()`：`_hotUpdateAss.GetType("Hello").GetMethod("Run").Invoke(null, null)` —— 热更入口是 **`Hello.Run()`**。

`CreateDecryptionServices()`（`ACT/YooAssetPackageInitUtility.cs:163`）**只对 `AssetType.RawFile` 返回解密服务**，
`Dll` 包返回 `null` ⇒ **Dll bundle 不做额外解密**。

⇒ 推论（△）：要改游戏逻辑，只能改 `Assembly-ACT.dll` 的 IL。
`libil2cpp.so` 里没有热更方法的独立 AOT 入口，native hook 打不到业务逻辑（与 `skill/re-implement/hotfix-dll-replace-pattern.md` 一致）。

穷举 1,144–1,191 起点 × 多个长度 × 多档目标尺寸全部失败）。索引 1..223 全部正常解压。
游戏自身能正常跑 ⇒ 该块被某种方式变换过（未查明，★未确认）。
**因此工具把索引 0 当成不透明数据原样保留（内容/位置/compressedSize 全不动）**；
替换目标 `Assembly-ACT.dll` 位于解压流偏移 **649120**、长度 **14,529,536**，完全落在索引 ≥1 的块内，不受影响。

**44 个 PE 已从解压流中拷出并识别**（`06_dumped/绿梦_20261016/hotfix_dll/`）：`Assembly-ACT`(14.5 MB)、

## 4. 投递链（★ 已端到端验证的「空操作」实验）

## 5. IL 补丁可行性（★ 已实测）

- 工具：`04_scripts/绿梦/ilpatch/`（由 `04_scripts/邂逅在迷宫/ilpatch/` 模板改造，Mono.Cecil 0.11.4 / net10）。
- **尺寸 linchpin 通过**：`dotnet run -c Release -- roundtrip` ⇒
  `src=14529536 → dst=14419968`，**delta = −109,568 B（−0.754%）**，`常量丢失 = 0`。
- ⇒ 补丁后有 **~109 KB 余量**，可**零填充回 14,529,536 B**，从而 SerializedFile 对象表（`byteStart`/`byteSize`）**不用改**，
  也就不需要解开不可解的索引 0 块。**补丁后必须恰好等长**（工具 `replace --size` 会强制校验）。
- ⚠ **别把「Cecil 重写产物」的一个假警报当故障**（2026-10-16 实测）：用 `ilspycmd` 反编译重写后的 dll，
  某些方法（如 `ACT.Battle.SystemTime::.ctor`）会出现 `Unknown result type / Expected Obj, but got Unknown` 注释。
  实测隔离：**纯 roundtrip（零注入）同样 10 条，原 dll 0 条**，且三者 AssemblyRef 数都是 84
  ⇒ 这是**重写本身的渲染/解析差异**（我们缺 4 个参照程序集），**不是注入引入的 IL 问题**。
  判据要用「原 dll vs 纯 roundtrip vs 补丁 dll」三方对照，不要单看补丁 dll 就判死。
- 写盘期 `AssemblyResolutionException`（`MetadataBuilder.GetConstantType ← CheckedResolve ← AddParameter`）由
  `TolerantRefs.cs` 的「垫片 + 宽容解析器 + 常量台账」三层处置（照 `hotfix-dll-replace-pattern.md` §6）。

## 8. ⚠ 取证通道：本游戏**吞掉 `Debug.Log` / `Debug.LogWarning`**

**这是本游戏最容易误判的一条，所有"看 logcat 判功能是否生效"的写法都要先过这一关。**

源码证据：`decompiled/Assembly-LocalLoader/ACT.Initialize.Flow/InitDebugTool.cs` 的 `ResetLogHandler()` 把 Unity
的 `Debug.unityLogger.logHandler` 换成 `LuminApplication.APM.LuminLogHandler`，而它的实现是**只转发 Error/Exception**：

```csharp
public void LogFormat(LogType logType, UnityEngine.Object context, string format, params object[] args) {
    if (logType == LogType.Exception || logType == LogType.Error)
        _defaultLogHandler?.LogFormat(logType, context, format, args);
}
public void LogException(Exception exception, UnityEngine.Object context) { _defaultLogHandler?.LogException(...); }
```

⇒ **托管侧 `Debug.Log` 与 `Debug.LogWarning` 一律进不了 logcat。**

2026-10-16 实测对照（阶段 1 冷启，全新进程 pid 16034，`05:03:15 Force stopping` → `05:03:29 Start proc` → `05:03:33 Displayed MainFragmentActivity`）：

| 判据 | 结果 |
|---|---|
| 我们注入的 `Debug.Log("[StarryLvmeng] stage1 init")` | **0 命中** |
| 游戏自己的 `Debug.Log("Hello, World20")`（`Hello.cs:10`） | **0 命中** |
| Unity 原生引擎消息（`W Unity : The referenced script … is missing!`） | **181 行**（正常出现） |

**结论与写法**：
1. **别把「没有日志」当成「注入没生效」** —— 必须先区分是「没跑」还是「被吞」。
2. 托管侧的证据日志一律走 **`Debug.LogError`**（或 `Debug.LogException`），该 handler 明确转发；
   为免刷屏，只在关键判据处打 2–3 行。
3. Unity 原生引擎消息（`Unity` tag 下的 `W`/`E`）是**绕过托管 logger** 的，照样可见 ——
   不能拿它当"托管日志通道正常"的证据。
4. `04_scripts/绿梦/l2_check.sh` 的判据 grep 的是 `\[StarryLvmeng\]`、不区分级别，所以改成 `LogError` 后即可命中。

## 9. ⚠ 注入 IL 只能用「游戏自己用过」的反射/BCL API（AOT 裁剪）

**2026-10-16 实测（阶段 1 第一次冷启就炸在这上面）**：注入的引导代码抛
```
System.MissingMethodException: MethodNotFind System.Reflection.MethodInfo::Invoke
  at Hello.StarryBootstrap () → Hello.Run () → ACT.InitDll.LoadOver ()
```
即 **`MethodInfo::Invoke` 在 AOT 侧解析不到**（`Invoke` 实际声明在 `MethodBase` 上；
IL2CPP 对解释执行的调用点按声明类型解析，写 `MethodInfo::Invoke` 找不到）。

**判据做法（照抄）**：拿游戏自己的 IL 当"可用 API 白名单"——
`ikdasm <游戏 dll> | grep -oE "类型::方法\("` 统计真实使用过的重载。实测结论：

| API | 游戏里的使用情况 | 结论 |
|---|---|---|
| `System.Reflection.MethodBase::Invoke(object, object[])` | `InitDll::LoadOver` 用过（`IL_0093 callvirt …MethodBase::Invoke`） | ✅ 可用，**必须写 MethodBase 而不是 MethodInfo** |
| `System.Type::GetMethod(string)`（1 参） | `LoadOver` 用过 | ✅ 可用 |
| `System.Type::GetMethod(string, BindingFlags)`（2 参） | **0 处** | ❌ 有裁剪风险，不用 |
| `System.Delegate::CreateDelegate(Type, MethodInfo)` | **0 处**（LocalLoader 与 Assembly-ACT 都是 0） | ❌ 不可用 ⇒ 每帧 tick 改成把 `MethodInfo` 存静态字段、用 `MethodBase::Invoke(null,null)` 反射调用 |
| `File.Exists` / `File.ReadAllBytes` / `File.ReadAllText(string)` / `File.WriteAllText(string,string,Encoding)` + `Encoding.UTF8` | 游戏多处使用 | ✅ 可用（证据文件就靠它们） |

**教训**：给热更程序集注入 IL 时，**不要按"标准 .NET 一定有"来选 API**，要按"这个游戏的 AOT 里确实链接过"来选；
判据就是 `ikdasm` 数重载。同类坑见 `10_docs/_templates/经验_HybridCLR热更DllImport不可用_20260916.md`（DllImport 那条）。

- 证书：官方 `CN=lvmeng` SHA-256 `cb41e01e…` → 我们 `CN=StarryMagic` `83c5cc0b…`。
- 结果：卸载官方包 → 装重签包（34.8 s）→ 冷启 pid 6758 → **32 min 后仍在战斗画面**，
  `/proc/6758/maps` 里 `libFairGuard.so`/`libil2cpp.so`/`libunity.so` 三者齐全，
  logcat 无 `C03-*`、无 FairGuard 关键字、无干净自退。
- 判据落点：`09_test/绿梦/fgtest_20261019_025706/`（`launch.txt`/`life.txt`/`logcat.txt`）。
- ⚠ 结论边界：只证明**签名变更**可过；**内容变更（dex / Manifest / assets）** 尚未测，是直装包下一道闸门。
