- 目标：`com.zhuziplay.lvmengnew.op` 1.0.5 / vc12035，壳 = `libFairGuard.so`
- 性质：全部结论标【文档】（有来源）／【推断】（有证据链但未实测）／【待验证】。

## 0. 结论（先看这 6 条）

1. **GG 不是「不注入的 Frida」，而是「附着一堆可枚举痕迹的 ptrace 工具」。** 它靠 `PTRACE_ATTACH` 接管目标才能改内存；作者（Enyby）原话：没有 ptrace 就只能读、不能改，读要靠 `/dev/mem` 或 `/proc/pid/mem` 且需在设置里开「扩展/实验性内存访问」。GG 报错 `{105} PTRACE_ATTACH: Operation not permitted` 就是「目标已被别的 tracer 占着」。[来源](https://gameguardian.net/forum/topic/17373-kernel-support-for-anti-ptrace/) [来源](https://gameguardian.net/forum/topic/19199-105-ptrace_attach-error-operation-not-permitted/)
2. **在「ptrace attach 不被反制」这个前提下，GG 的 attach 环节大概率也不被反制——但那不是 GG 的主要命中面。** 它的主要命中面是**可枚举痕迹**：安装包名（FG 博客明写「一些修改器变种会盗用其他应用的包名来躲避检测」，反证 FG 扫包名）、root/su、Magisk、虚拟机/虚拟框架、GG 自身进程与文件、以及批量扫描的**行为**（FG 明写「行为检测，无需特征」）。GG 论坛的老帖也印证：游戏会「发现你装了 GG」，玩家得靠 XPrivacy 屏蔽包名/应用列表才能过。[来源](https://www.fair-guard.com/news/222.html) [来源](https://www.fair-guard.com/news/34.html) [来源](https://gameguardian.net/forum/topic/23402-how-to-hide-gg-from-games-in-10-easy-steps/)
3. **真正可复用的是「GG 式读法」，不是 GG 这个成品**：root 侧 `process_vm_readv`（首选）或 `pread(/proc/pid/mem)`（回退）——**只做一次 ptrace access-mode 检查，不建立 tracer 关系**，因此 `/proc/<pid>/status` 的 `TracerPid` 始终为 0，也不在目标里留任何映射/线程/文件。这是本项目「零注入」约束下最干净的内存读取通道。[man 7](https://man7.org/linux/man-pages/man2/process_vm_readv.2.html)
4. **只读不够，抓 killer PC 还得靠 ptrace 的「停点」**：`PTRACE_SYSCALL` 的 syscall-enter-stop（读 x8 = 129/130/131/138/424）、或 `NT_ARM_HW_BREAK`/`NT_ARM_HW_WATCH` 硬件断点/观察点。后者**不需要往目标里执行任何自写代码**——正好绕开 `fg_mprotect.c` 卡住的「远程 svc 桩不执行」难题。现成库可用 KittyMemoryEx（`PTRACE_SEIZE` + 硬件断点 + perf_event 观察点 + 双内存后端）。[来源](https://github.com/MJx0/KittyMemoryEx)
5. **推荐顺序：P0 自写 root 只读读取器（process_vm_readv）+ 已通的 ptrace 停点抓 PC > P1 现成库 KittyMemoryEx > P2 GG（只当交互式搜索 UI）> P3 内核 KPM/KO 驱动。** 理由统一成一句：**越靠近「只读 + 不建 tracer 关系 + 不落文件」越不可检测；越靠近「成品工具 + root/VM/Magisk + 批量扫描」越容易被 FG 的专项策略命中。**
6. **别把 GG 当「能改就有用」**：本项目的死点是 cert 比较→tampered 标志，属**判定逻辑**而非数值；GG 擅长「反复搜索→定位→改数值」，对「找一条比较指令的 PC」几乎无增益（它的搜索是模式匹配，不是调用栈追踪）。

## 1. GG 读/写内存的底层机制（分层 + 版本/root 差异）

### 1.1 四层读写通道

| 层 | 通道 | 权限模型 | 是否留 tracer 关系 | 事实等级 |
|---|---|---|---|---|
| L1 | `PTRACE_ATTACH/SEIZE` + `PTRACE_PEEKDATA/POKEDATA` | tracer 身份（同 uid + dumpable，或 CAP_SYS_PTRACE） | **是**：`TracerPid` = tracer pid | 【文档】GG 作者自述 + GG 报错码 |
| L1' | attach 后 `/proc/<pid>/mem` 的 `pread/pwrite`（GG 批量搜索的实际读法） | 打开时按 `PTRACE_MODE_ATTACH_FSCREDS` 检查 | 是（因为先 attach 了） | 【推断】由 GG「搜索速度」与 Enyby 描述推得 |
| L2 | 直接 `open("/proc/<pid>/mem")` + `pread`（不 attach） | 同上，root/CAP_SYS_PTRACE 直接过 | **否** | 【文档】`dd if=/proc/pid/mem` 类工具即此路 |
| L3 | `process_vm_readv/writev` | 按 `PTRACE_MODE_ATTACH_REALCREDS` 检查；root 过 | **否**（只做 access 检查，不建 tracer 关系） | 【文档】man + 内核 `mm_access()` 语义 |
| L4 | 内核模块（KPM/KO 驱动，ioctl/netlink/dev 节点） | 内核态，绕过用户态 syscall | 否（但 root 侧痕迹更重） | 【文档】GG 生态对接项目 |

- **GG 官方口径（最关键的一段原文）**：Enyby 2017 年答「Kernel Support for anti-ptrace」——「GG use it（`/dev/mem`）but only partially. For it need enable Extended or Experimental access to memory in GG settings.」以及「**without ptrace you can not modify memory of process. Even if you have /dev/mem. Most of implementation /dev/mem and /proc/pid/mem allow only read data from it. Then if game ptrace defended you can only read process memory but not able to change it.**」→ 这就是「ptrace 被防 ⇒ 只能读不能写」的权威来源。[来源](https://gameguardian.net/forum/topic/17373-kernel-support-for-anti-ptrace/)
- **GG 依赖 attach 的直接证据**：`{105} PTRACE_ATTACH error: Operation not permitted` 是 GG 的固定错误码，论坛解释为「内存编辑器必须先 attach 到游戏进程才能工作；若已被别的进程 attach 就做不到」。[来源](https://gameguardian.net/forum/topic/19199-105-ptrace_attach-error-operation-not-permitted/)
- **GG 的 root 形态**：FG 两篇文章都指出 GG 需要 root，常跑在虚拟机/虚拟框架里拿「假 root」，拿到 root 后用 Magisk 对游戏隐藏进程。[来源](https://www.fair-guard.com/news/222.html) [来源](https://www.fair-guard.com/news/34.html)
- **内核驱动层（GG 生态的现实形态）**：公开项目 `Gg_Docking_Kernel` 描述「使任意可执行文件对接内核驱动」，核心是 **hook syscall 270（`process_vm_readv`）** 把读请求转给 KPM/KO 驱动，从而「绕过用户态检测」，并列出 10 种主流 KPM/KO 驱动。中文教程亦复述同一路线（「一键部署内核驱动实现内存读写通道下沉至内核态」）。[来源](https://github.com/ZYPyDoki/Gg_Docking_Kernel) [来源](https://blog.csdn.net/2301_79226998/article/details/167175241)
  - 反向读法很重要：**这些工具把 `process_vm_readv` 当成默认读通道**，说明 L3 就是「用户态读取器」的标准做法；它们之所以要下沉到内核，是因为**用户态 syscall 可被观测/拦截**——这恰好是我们需要评估的检测面。

### 1.2 Android 版本 / root 情况的差异

| 情形 | 可用通道 | 说明 |
|---|---|---|
| 未 root，普通 app | 全部不可用（除自己进程） | 跨进程访问被 **SELinux（untrusted_app）+ Yama ptrace_scope** 拒；stock Android 上 ptrace_scope 通常为 1（只允许父子/CAP_SYS_PTRACE）[来源](https://www.yinkoshield.com/knowledge-center/mobile-runtime-attacks/runtime-memory-manipulation/) [来源](https://www.kernel.org/doc/html/latest/admin-guide/LSM/Yama.html) |
| root（su 域，本项目设备 `f9a116a2` = KernelSU `u:r:ksu:s0`） | L1/L2/L3 全可用 | CAP_SYS_PTRACE 过 access 检查；L3 不需要 attach |
| KernelSU / APatch + 可加载模块 | L4 可用 | 需内核版本匹配、KPM/KO 签名/密钥；崩机风险 |
| Android 12+ | 同上，SELinux 更严 | 常见失败是 `EACCES/EPERM` 而非 API 缺失【推断】 |

- 细节：L3 的返回值可能是**部分传输**（跨页/未驻留页），长读要按页切 iovec —— 与姊妹文档 §4 的「按页切」一致。[man 7](https://man7.org/linux/man-pages/man2/process_vm_readv.2.html)
- 批量读性能：`process_vm_readv` 就是为替代「逐字 `PTRACE_PEEKDATA`」而引入的（strace 早在 2012 年就提交过同类补丁）。[来源](https://lists.strace.io/pipermail/strace-devel/2012-January/002064.html)

## 2. 可检测性：GG vs Frida vs 自写读取器

### 2.1 检测点清单（按「谁会被命中」归类）

| 检测点 | 具体判据 | Frida | GG（成品） | 自写 L2/L3 读取器 |
|---|---|---|---|---|
| `TracerPid` | `/proc/self/status` 第 6 行非 0 | 命中（ptrace 注入） | **命中**（attach） | **不命中**（无 tracer 关系）【推断】 |
| 映射枚举 | `/proc/self/maps`/`dl_iterate_phdr` 里的 `frida-agent`、匿名 exec 段 | 强命中 | 弱（GG 在别的进程） | 不命中（目标内无新映射） |
| 线程名 | `gum-js-loop`/`gmain` 等 | 命中 | 不命中 | 不命中 |
| 端口/套接字 | 27042 等 | 命中 | 不命中 | 不命中（若走 adb shell 管道/文件） |
| 安装包/应用列表 | `PackageManager` 查 `com.gameguardian` 等 | 不命中 | **强命中**（FG 专项；变种靠盗包名绕过，反证在扫包名） | 不命中（纯二进制，可不出现在应用列表） |
| root / su / Magisk | `su` 路径、`magisk` 痕迹、mount 差异 | 常伴生 | **强命中**（FG 有「Magisk 专项检测」，宣称隐藏选项全开也能识别） | **命中**（同一条 root 前提，无法回避） |
| 虚拟空间/框架/云手机 | 容器特征、`/proc` 异常 | — | **强命中**（FG 安全环境检测「个性化闪退」） | 不命中（本项目不用虚拟空间） |
| 代码完整性 | 内存 `.text` 与磁盘 hash 漂移、异常 rwx | 命中（inline hook） | 命中（改代码时） | **不命中（只读）** |
| 行为侧 | 跨进程读的**访问模式**：整段扫描、踩「陷阱页」、页驻留突变 | 弱（不扫内存） | **强命中**（FG 宣称「行为检测，无需特征」） | **可能命中**（取决于读取范围/频率） |
| Seccomp 字段 | `Seccomp: 2` | 不命中 | 不命中 | 不命中（不装过滤器） |

- FG 的两句关键宣称：①「针对修改器，不同于目前市面游戏保护使用的特征检测，潜心研发了**行为检测**方法，无需特征即可检测，修改器无论如何免杀都躲不过」；②「针对 GG 及其变种定制了专门应对策略」+「行为检测 + 安全环境检测 + Magisk 专项检测」。[来源](https://www.fair-guard.com/news/34.html) [来源](https://www.fair-guard.com/news/222.html)
- 「行为检测」的一个**公开可复现的实现样本**：在目标里 `mmap` 一页 `PROT_READ` 的陷阱区，把关键指针指向它；攻击者一读就触发缺页、页被物理后备，目标侧用页驻留状态判定「有人外部读了我」。这说明**只读也会被抓**，抓的是「访问模式」而非「注入」。→ 所以自写读取器要**只读已知小范围、低频、避开无意义全段扫描**。[来源](https://github.com/alaakaq/Detecting-process_vm_readv)
- GG 自身的「反检测」选项（隐藏 GG、随机包名、Lua 脚本）本质是**特征对抗**，对「行为检测 + 环境检测」无效；FG 2025 文章正是把「变种盗包名」列为「增加检测难度」而非「无法检测」。[来源](https://www.fair-guard.com/news/222.html)

### 2.2 直接回答「GG 式读内存是否可行/更稳」

- **attach 环节**：你的 `fg_mprotect.c` 已证明「ptrace ATTACH 不被反制」，GG 的 attach 走同一 syscall ⇒ 机制上可行。【推断，依据实测前提】
- **但「更稳」不成立**：GG 把 attach 之外的**五类可枚举痕迹**一起带进来（安装包、su/Magisk、可选虚拟空间、GG 自身守护进程、批量扫描行为），而 FG 对这五类都有公开的专门策略。
- **真正「更稳」的抽取物是 L3**：`process_vm_readv` 只做 access 检查、不建 tracer 关系、目标内零痕迹；把「GG 的搜索算法」重写成 60–150 行 C 就够了（`/proc/pid/maps` 取段 + `process_vm_readv` 批量读 + 本地匹配）。这也是 KittyMemoryEx 的默认后端之一。[来源](https://github.com/MJx0/KittyMemoryEx)

## 3. 同类 / 替代工具：原理与适用性对比

| 工具 | 原理 | 权限 | 对本项目的适用性 | 判定 |
|---|---|---|---|---|
| **GameGuardian（GG）** | attach + 读写 + Lua 脚本；可选 `/dev/mem`；生态可对接 KPM/KO 内核驱动 | root 或虚拟空间 | 擅长数值搜索/锁定；**对「找 cert 比较 PC」无直接能力**；痕迹多 | **只当 UI，不当方案** |
| **葫芦侠 / 八门神器 / 烧饼 / GG 各种改版** | 均是 GG 同类/变种（FG 2020 文章列出同一张表，并称「很多修改器都是 GG 的变种」） | root/VM | 同上，且维护性/可信度更差 | **否** |
| **KittyMemoryEx** | 外部进程库：`process_vm_readv/writev` 或 `/proc/pid/mem` 双后端；`PTRACE_SEIZE`；`NT_ARM_HW_BREAK` 硬断；`perf_event_open` 观察点；ELF/maps/linker 扫描；`dumpMemRange/dumpMemELF`；`ProcStatus` 读 `TracerPid` | root/匹配权限 | **本项目的「现成轮子」**：外部进程、无进程内注入、要的四个能力（读、dump、硬断、观察点）全有 | **P1 推荐** |
| **Il2CppMemoryDumper** | **纯 shell**，root 下 `dd if=/proc/$pid/mem` 按 `/proc/pid/maps` 段 dump `libil2cpp.so` + `global-metadata.dat`，再交 SoFixer/Il2CppDumper 离线还原 | root | 证明「`dd /proc/pid/mem` 即够用」；本项目已解包成功，价值在**运行期解密后段**的旁证 | 参考实现 |
| **mem-dump / PADumper 类** | 同上，按 maps 段 dump 指定 .so（如 libUE4.so） | root | 同类思路，无新增能力 | 参考 |
| **lldb-server / gdbserver** | ptrace 前端 | root | 能停在 SIGILL/SIGTRAP 的 signal-delivery-stop、看被杀线程现场；**给不了「发信号者的 PC」**（需 syscall-stop） | 辅助 |
| **Frida（对照）** | ptrace 注入 agent / gadget | root | **已废**（一注入即 SIGKILL，命中 maps/线程名类检测） | 否 |
| **Il2CppDumper / Cpp2IL** | 静态：解析 ELF + metadata 还原符号 | 离线 | 本项目壳把 metadata 运行期解密，需先有「运行期 dump」才有输入 | 下游工具 |
| **LIEF** | 静态 ELF/PE 解析与改写库（**不做运行期内存读写**） | 离线 | 只用于「拿到 dump 出来的 .so 后修段/改节/重打包」，与动态抓取无关 | 下游工具 |
| **内核 KPM/KO 驱动**（GG 生态对接的那些） | ioctl/netlink 内核读写，绕用户态 syscall | 内核模块 | 隐蔽性最高、成本/风险最高（签名/密钥、内核版本、崩机） | **P3 最后手段** |

- KittyMemoryEx 的能力原文：两个后端（`EK_MEM_OP_SYSCALL`=`process_vm_readv/writev`；`EK_MEM_OP_IO`=`/proc/<pid>/mem` + `pread/pwrite`）、`KittyTraceMgr`（`PTRACE_ATTACH`/`PTRACE_SEIZE`、硬/软断点、远程调用、`setHardBreakpointAndWait` 用调试寄存器、**no code patching**）、`KittyPerfWatch/KittyPerfTrap`（`perf_event_open` 硬件观察点）、`ProcStatus` **「used to check TracerPid before attaching」**。要求 root 或匹配的 ptrace 权限。[来源](https://github.com/MJx0/KittyMemoryEx)
- Il2CppMemoryDumper 原文：「Pure shell implementation」「Android Shell (root): `Il2CppMemoryDumper.sh <package>`」，脚本内实际是 `grep <target> /proc/$pid/maps` + `dd if="/proc/$pid/mem" bs=1 skip=<offset>`。[来源](https://github.com/MlgmXyysd/Il2CppMemoryDumper)
- LIEF 定位：解析/改写 ELF 的静态库，用于「dump 出来后修 ELF」（与本项目的 `SoFixer` 同层）。[来源](https://lief.re/)

## 4. 结论：推荐顺序与理由

**核心判据**：本项目的问题是「找到 cert 比较 → tampered 标志的 killer PC」，需要的不是「改数值」，而是**只读观测 + 一次精确停点**。按这个判据排序：

| 序 | 方案 | 为什么 | 主要风险 | 成本 |
|---|---|---|---|---|
| **P0** | **自写 root 只读采样器**：`/proc/pid/maps` + `process_vm_readv`（回退 `pread(/proc/pid/mem)`），静态链接小二进制，`su -c` 跑，输出落设备端文件由 adb 取回 | ①不建 tracer 关系 ⇒ `TracerPid`=0；②目标内零映射/零线程/零文件；③不受「Frida 注入即死」影响；④复用已确认的 root 前提 | 行为侧（整段扫描/陷阱页）仍可能被抓 ⇒ **只读已知小范围、低频** | 0.5 d |
| **P0'** | **已通 ptrace 停点**（与姊妹文档 A/B 同）：`PTRACE_SYSCALL` 抓 x8=131 的 enter-stop 取 PC/LR；或 `NT_ARM_HW_BREAK/WATCH` 硬断在 `tgkill`/tampered 标志上 | 唯一能**直接给 PC** 的路；硬断**不需要**远程执行自写代码，绕开 `fg_mprotect.c` 的死结 | 全 syscall 停拖慢游戏；硬断槽位仅 4–8 个 | 0.5–1 d |
| **P1** | **KittyMemoryEx** 当脚手架 | 上面两条它都封装好了（双后端 + 硬断 + 观察点 + dump），省掉自己写 maps 解析/断点编排 | 引入较大依赖；ABI/NDK 适配成本 | 0.5 d |
| **P2** | **GG（成品）** | 唯一优势是「交互式搜索 UI + Lua」，适合快速确认「某个数值在哪」 | 安装包/su/Magisk/VM/行为五类痕迹全暴露；FG 有 GG 专项策略；对找比较点无直接帮助 | 0.2 d |
| **P3** | **内核 KPM/KO 驱动** | 用户态完全不可见 | 需 KernelSU/APatch 可加载模块 + 内核匹配；崩机风险；FG 有 Magisk 专项检测 | 2–3 d |

**一句话答案**：
> 在 FairGuard 场景下，**「自写轻量 ptrace/process_vm_readv 读取器」明显优于「直接用 GG」**——前者只带走「root」这一条无法避免的痕迹，后者额外带走「安装包 + Magisk + 虚拟空间 + 扫描行为」四条可枚举痕迹，而 FG 对这四条都有公开的专门策略。GG 唯一值得借的是它的**读通道选择（`process_vm_readv`）**，不是它的**壳**。

**给 `fg_mprotect.c` 的具体改法（推断，待实测）**：
1. 放弃「往目标栈写 svc 桩 → 远程 mprotect」这条链（远程执行自写代码最难，且失败模式不可观测）。
2. 改走 `NT_ARM_HW_BREAK`：`PTRACE_SEIZE` 后对 `libc` 的 `tgkill`/`kill` 入口下硬件执行断点（或对 tampered 候选地址下 `NT_ARM_HW_WATCH` 写观察点），命中即读 `PC/LR/FP` 并归一到 `libFairGuard.so` 段偏移。**内核负责断点，不需要目标执行任何我们写的指令。**
3. 需要批量读内存时用 `process_vm_readv`（`PTRACE_PEEKDATA` 逐字读太慢，见 strace 补丁动机）。
