# 绿梦：时空之声 — FairGuard 逆壳：完整性闸门定位（+0x2D8708）

- 上一轮结论（`FairGuard逆壳_流块判定.md`）：载荷区 0x400..0x1F0000 内任意 1 字节改动 → 约 0.5 s 崩溃，崩在同一 PC。
- 本轮目标：静态定位 `libFairGuard.so+0x2D8708` 及其调用者，回答「闸门校验对象是什么」、以及「静态 patch 还有没有路」。
- 日期 / 设备：2026-10-20，`f9a116a2`（KernelSU）。证据源：运行期镜像 `libFairGuard_rwxp.bin`（8297e6b9…）、磁盘 .so（7bee7f8b…）、设备 tombstone、logcat。

## 1. 结论速览

1. **+0x2D8708 定位到了**，但**它不是"比较 → 跳转"型的校验代码**：它是 **B 区（0x1F0000..0x400000，运行期写入区）里的一段 VM/混淆代码**，崩在**函数序言读 GOT 槽时解引用空指针**。
2. **未找到可指认的"校验对象"**（整文件 hash / 载荷密文 hash / 明文 hash 都没有直接证据）。现有证据只能说到：改动载荷 → 某处初始化没做完 → 该函数第一次用那个全局时崩。
3. **静态 patch 路线被结构性堵死**：闸门代码所在 B 区**在磁盘上全是 0**（运行期才被写入），**磁盘上没有可以改的字节**；而在内存里改，仓库早已实测被 0.3 s 反制（`FairGuard自patch方案.md` §50）。

## 2. 代码性质判定（回应「B 区能不能直接反汇编」）

| 区域 | 位置 | 可解码率 | ret | udf | 判读 |
|---|---|---|---|---|---|
| A 区壳代码 | 磁盘 0x413AB0..0x431350（明文） | **99.3%** | 1,249 | 50 | 正常 AArch64 代码 |
| B 区整体 | 运行期镜像 0x200000..0x400000 | **92.9%** | 1,263 | **24,147** | **是代码，但混入大量 udf ⇒ VM/反汇编陷阱** |
| B 区局部 | 0x2D0000..0x2E0000 | 99.4% | 1 | 0 | 密集代码（switch 派发风格） |
| B 区头部 | 0x1F0000..0x210000 | 100% | 1 | 0 | 同上 |

⇒ **能直接反汇编**（不是加密/字节码不可读），但可读性被 `udf` 与 `cmp…b.eq` 派发链严重削弱；逐函数读代价高。
**关键前提：B 区在磁盘 .so 里是 0**（`FairGuard逆壳_阶段1_解包器.md` §1 已量化：0x1F0000..0x400000 磁盘熵 0.13 / 全零），所以本轮所有 B 区反汇编都是**对运行期镜像**做的，不是在磁盘文件上做的。

## 3. +0x2D8708 的指令级定位

崩溃函数序言（运行期镜像 0x2D86C0 起，帧 0x900+0xA0）：

```
0x2d86c0  sub  sp, sp, #0x900
0x2d86c8  sub  sp, sp, #0xa0
0x2d86d8  adrp x26, #0x3ff000
0x2d86f0  ldr  x0, [x26, #0xcc8]     ; x0 = *(void**)0x3FFCC8   ← GOT 槽
0x2d8700  add  x27, sp, #0x1f8
0x2d8704  str  w4, [x27]
0x2d8708  ldr  x0, [x0]              ; ←← 崩溃点：解引用空指针
0x2d870c  str  x0, [sp, #0x998]      ; 存到栈尾（典型 stack-canary 保存位）
0x2d8710  cbz  x21, #0x2dc128
```

- **0x3FFCC8 是 GOT 槽**：基线镜像里它的值 = `0x755ed92130`（另一模块里的地址，形态即 `__stack_chk_guard` 那类"取全局指针再取值"）。
- 该槽属于我们上一轮已量化的**指针簇 0x3FAA09..0x3FFFF3（2,053 个 8 字节指针，随 ASLR 整体平移）** ⇒ 它就是**运行期重定位后的 GOT 表**。
- tombstone 证据（设备 `/sdcard/Android/data/com.zhuziplay.lvmengnew.op/files/tombstone_0{0,1,2}`）：
  - `tombstone_02`（pid 25770，C[0x1B080] 翻转）：**SIGSEGV / "null pointer dereference"**，`pc=+0x2D8708`，**x0=0** ⇒ GOT 槽是 0，`ldr x0,[x0]` 崩。
  - `tombstone_00`（pid 26319，C[0x80000] 翻转）：SIGSEGV/MAPERR，`pc=+0x2D8700`（同函数、序言内），x0=0x3fb540。
  - 两者 x8=x9（同一值，两次运行不同：`0x979b0e670b5745b7` / `0x016239f7d01e1347`），x10=0x200、x11=0xb4 相同；lr 均落在 **libil2cpp.so**。
- 函数体内是典型混淆 VM 派发（`eor` 混洗 → `and w5,w5,#3` → `cmp w5,#1/#2` → 三路 `b.eq`，各分支用 `strb` 打散写回）⇒ 不是可读的业务逻辑，更像**壳自己的 VM 解释器/分发器**。

## 4. 「校验对象」判定：没有找到比较型闸门

| 假设 | 支持证据 | 反对证据 | 现状 |
|---|---|---|---|
| 整文件 hash | 载荷区/头部任一改动都能引起异常；EI_PAD 那次也留下过 tombstone | 复现 EI_PAD 改动**没有** tombstone；改动后崩溃点与"比较失败"语义不符（是 GOT 空指针，不是 abort/exit） | **未成立** |
| 载荷密文 hash | 载荷区改动 3/3 立崩（~0.5 s），同 PC | 崩溃前镜像里**该处明文并未改变**（0x1B080/0x80000 两处实测），说明"判定"不在明文侧；但也解释不了"为什么变了就崩" | **未成立但最接近** |
| 解密后明文 hash | — | 明文没变却照样崩 ⇒ 与"检出明文不同"矛盾 | **排除** |
| 定点结构（GOT/指针表） | 崩在 GOT 槽解引用；指针簇本就每跑不同 | 指针簇差异是 ASLR 正常现象，不能解释"改一个字节就崩" | **待验证** |

**当前能说的事实级结论**：改动载荷 → 进程在 ~0.5 s 内于 `+0x2D8708` 解引用空的 GOT 槽而崩；
`0x3FFCC8` 这个槽在同一次运行里没有被填上。至于是"壳主动跳过初始化"还是"初始化被破坏"，**现有证据不足以判定**，标**待验证**。

对照（同机同包，2026-10-20 复测）：
- **未改文件**：5/15/25 s 存活，35 s 已退出，**无新 tombstone** ⇒ 30 s 左右是**正常退出**，不是崩溃。
- **只改 e_ident[EI_PAD]（外区）**：首测留下 `tombstone_01`（SIGILL @ `+0x2C9A10`，~30 s），**复测无 tombstone** ⇒ 该现象不稳定，不作为判据。

## 5. 静态 patch 还有没有路

**结论：沿着"改磁盘 .so"这条路，没有静态落点。** 三条硬约束：

1. **闸门代码在 B 区，而 B 区磁盘上全是 0** —— 没有字节可改。要改只能改成**运行期内存**，即已被 `FairGuard自patch方案.md` §50 实测反制（0.3 s 内 `EXIT_SELF status=0`）的那条路。
2. **B 区内容的来源仍未确定**（阶段 1 未闭环 #2）。只要不知道它从哪来，就无法在磁盘侧控制它，也无法预先算出它。
3. **载荷区本身被校验**：这一轮与上一轮合计 4 次改动（0xD140、0x1B080、0x80000、EI_PAD）里，载荷区 3/3 立即崩，头部 1 次延迟异常 ⇒ KS 重加密产物写回磁盘后，**同样会先撞这道门**。

⇒ 对 KS 改盘路线的判定：**不是"再逆一步就能救"，而是"落点在运行期生成的内存里"**。要继续，只能走"运行期改内存 + 同时绕过反制"（成本高、仓库已有反制实测），或先回答「B 区来源」这个未闭环。

## 7. B 区载体定位（2026-10-20 追加，回答「B 区内容在哪个磁盘载体里」）

### 7.1 设备上没有 split APK（前提不成立）

- `pm path com.zhuziplay.lvmengnew.op` → **只有一条**：`base.apk`。
- 安装目录 `/data/app/~~5IyGZR0EJ3VFwA3pEd_GNw==/com.zhuziplay.lvmengnew.op-RRk20HDizHH-vp40JA-yzA==/` 下只有 `base.apk`(371,384,030 B)、`lib/`、`oat/`，**无任何 `split_config.*.apk`**。
- ⇒ 「B 区来自 split APK」这一前提在本机不成立（该包是单体安装 + 已有实验重打包，不是 split 安装）。

### 7.2 B 区内容既不在 APK、也不在磁盘 .so

| 检查 | 结果 |
|---|---|
| `base.apk` 的 **1,341 个条目全部解压后**搜 4 段 B 区特征（0x1F0000 / 0x250000 / 0x2D86C0 / 0x35B000 各 64 B） | **0 命中** |
| 原始 APK 字节流直接搜同 4 段特征（覆盖 `comp=0` 存储条目） | **0 命中** |
| 磁盘 `.so` 的 0x1F0000..0x400000 | **除 0x1F0000 起几 KB 外 100% 全零**（每 128 KB 块磁盘零率 100.00%，运行期零率仅 10–29%） |
| ELF section 表 | `.eh_frame_hdr`@0x3BD1F8、`.eh_frame`@0x3C0C20、`.gcc_except_table`@0x3D6720 都声明在这些偏移，但**磁盘上全是 0**；且 **0x1F0000..0x3BD1F8 没有任何 section（空洞）** |
| `assets/lvmeng/__data`（13,189,417 B） | `UnityFS` magic ⇒ 星光菜单资源 bundle，**不是** FairGuard 载荷 |
| `assets/lvmeng/fg_orig.apk`（179,649,718 B，存储不压缩） | 上一次重打包塞进去的**原包副本**；其 `lib/arm64-v8a/libFairGuard.so` md5 = `7bee7f8b…`，与设备上那份完全相同 |

**结论：B 区（0x1F0000..0x400000，2,162,688 B）在任何磁盘载体里都找不到原样明文**，它是**运行期由壳自己生成/填充**的。
⇒ 「改 split APK 就是静态 patch 面」不成立（既无 split，APK 里也没有这块内容）。

### 7.3 由此得到的唯一磁盘载体与矛盾

全文件里唯一高熵（7.97）且体量匹配的是 **0x400..0x1F0000（2,030,592 B）**，即阶段 1 记的「加密载荷」；B 区比它大 132,096 B（+6.5%），形态像「解密后再展开/翻译」。

但上一轮翻转实验显示：改这段字节**不改变**运行期明文、也不改变 B 区（差异只有 0x400..0xFFFF 的加载器暂存区 12 k B），
这与「B 由这段直接解密展开」**互相矛盾**，指向两种可能（均**待验证**）：

1. 壳读的是**包内压缩条目**（`base.apk` 里 `lib/arm64-v8a/libFairGuard.so` 是 `comp=8`），而不是 /data 里抽出的那份 → 改抽取文件不改变解密输入，只破坏一致性；
2. 壳另有一份不可见输入（自校验后从内存/别处重建）。

**决定性实验（下一步，一次装置往返）**：重打 `base.apk` 的 `lib/arm64-v8a/libFairGuard.so` 条目（重签、覆盖装、不清数据），再翻同一字节看 B 区是否随之变化。这一步同时判定「包内条目是不是真载体」。

## 8. 本节新增的未闭环

1. **B 区的生成输入**仍未定位（本节已排除：split APK、APK 任意条目明文、磁盘 .so 对应区）。
2. 「壳是否读包内压缩条目」——需 7.3 的重打实验判定。
3. 若壳确实读包内条目 ⇒ 静态 patch 面 = `base.apk` 的该条目（可做）；否则 B 区只剩运行期内存一条路（已被 0.3 s 反制）。

## 6. 未闭环

1. **B 区内容来源**（0x1F0000..0x400000 磁盘全零 → 运行期填满）——最高优先级，决定后面所有路。
2. `0x3FFCC8` 这个 GOT 槽由谁写、何时写；为何改动载荷后它没被填。
3. `0x2D86C0` 函数语义（VM 分发器？），以及它的调用者（本轮未能穿过 VM 派发链回溯）。
4. `tombstone_01`（EI_PAD 首测 SIGILL @0x2C9A10）未能复现，暂列偶发，不作判据。
5. 设备侧无残留：`libFairGuard.so` 已复原 `7bee7f8b44d9106165707f26c33ffca6`；本轮只做冷启/取证，零点击、不清数据、不装包。

## 9. GOT 槽 0x3FFCC8 与 2,053 指针表（2026-10-20 第三轮，纯静态 + 已有快照复算）

### 9.1 谁写 0x3FFCC8：**不是动态链接器**，是壳自己运行期填的表

| 检查 | 结果 |
|---|---|
| `.rela.dyn`（98 条：RELATIVE 78 + GLOB_DAT 20）、`.rela.plt`（10 条 JUMP_SLOT） | **r_offset 落在 0x1F0000..0x400000 的：0 条** |
| `.dynsym` 1,043 条符号 | 只有 41 个有名字；**没有 `__stack_chk_guard`**（导入是运行期 dlsym 解析，不走 PLT） |
| 表规模 | 0x3FA000..0x3FFFFF 共 **3,072** 个 8 字节槽 |
| 正常启动（baseline / ctrl / iv2 三份镜像一致） | **已填 2,344** 槽，其中 2,192 个值落在 0x7xxx（别的库/堆），728 个为 0 |
| A 区壳代码（磁盘 0x413000..0x442000，44,697 条可解码） | **没有任何 adrp 指向 0x3FA000..0x3FF000**，也没有一条 store 落进该区间 |
| B 区运行期代码（0x1F0000..0x400000，503,594 条可解码） | 730 条 adrp 指向 0x3FF000 页；24,444 条 store 的静态可算目标落进 0x3FA000..0x400000（含寄存器跟踪误差，量级仅供参考） |

⇒ 这张表（含 0x3FFCC8）**完全由壳在运行期填**，填充逻辑在 **B 区（运行期生成、磁盘上无字节）**，A 区壳代码不碰它。

### 9.2 填充前有没有"校验分支"：没抓到 cmp+跳过，但抓到**填充被截断**的硬证据

同一台机、同一取样时机（段出现后 ~0.2 s 的镜像快照）：

| 快照 | 表已填槽数 | `[0x3FFCC8]` |
|---|---|---|
| 对照（未改文件） | **2,344 / 3,072** | `0x755ed92130` |
| 翻转组（C[0x1B080] ^= 1） | **373 / 3,072** | **`0x0`** |

- 翻转组的 373 个已填槽**分散在 6 个 4 KB 页上**（0x3fa000:5、0x3fb000:44、0x3fc000:12、0x3fd000:60、0x3fe000:30、0x3ff000:222），**不是"顺序填到一半"的前缀** ⇒ 中断发生在**多个填表步骤**里，而不是单个循环跑到一半。
- 对照三份镜像（baseline / iv2 / ctrl）该槽值**完全相同**且非零 ⇒ 正常路径下它在启动早期必然被填。

⇒ 结论：**不是"校验通过才写某个槽"的局部开关，而是整个初始化/填表流程被中途中止**；崩溃只是"残表使用者"先撞到空槽（0x2D8708 恰好是该函数第一口读的就是 0x3FFCC8）。

### 9.3 改载荷 → 空指针崩溃的链路（本轮定版）

```
改载荷区任意 1 字节
   └─ 初始化流程中途中止（填表停在 373/3072，值仍为 0）
        └─ 0x3FFCC8 未填
             └─ 0x2D8708  ldr x0,[x0]  空指针 → SIGSEGV（~0.5 s）
```

**没有找到"读解密产物里的完整性标志/长度字段"这个中间环节**（上一轮假设 H1 未证实）：中断发生在磁盘不可见的 B 区代码里，静态追不到那个字段。

### 9.4 对 patch 路线的意义

- 填表逻辑在 **B 区（磁盘全零）**，A 区壳代码**不引用**该表 ⇒ **没有任何可静态修改的"填充开关"**。
- 与 §7、§9.2 合起来的判定不变：**"改磁盘 .so"这条静态 patch 面，对 B 区与填表逻辑都不存在**。
