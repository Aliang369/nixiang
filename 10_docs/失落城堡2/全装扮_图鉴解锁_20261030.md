# 失落城堡2 · 全装扮（装扮仓库/图鉴）解锁 —— 链路重建与挂点方案

> 版本：1.0.3 / vc10（官方原版 = 斌哥包字节相同）｜ 建档：2026-10-30
> 结论一句话：**灰显不是 `IsAppearanceItemUnlocked` 决定的**，而是各 UI 自己的
> `InitInventoryData` 把「账号已获得记录」和「配置表条目」逐项合并后写进
> `AppearanceItemData.mObtained`；卡片取锁 = `mShowLockCover && !mObtained`。
> 所以正确挂点是**合并处的两条判定**，不是那个谓词。

## 0. 为什么上一版没生效（一句话）

上一版把 `LC2.AppearanceMgr.IsAppearanceItemUnlocked`（`0x11944af8`）改成恒 `true`。
本次静态核实：它的调用点只有三处 ——
`CommonItemDetailMobileUnitUI.SetUnlockState`（详情面板的锁图标）、
`AppearanceMgr.<IsAppearanceItemSuitItemsAllObtained>b__35_0`、
`AppearanceUI.IsSuitPartUnlocked`（套装部件判定）。

**图鉴式列表和装扮页的格子灰显都不经过它** ⇒ 改它当然不变灰显。该槽位保留（详情面板仍需要它）。

### 名字→RVA 三步法（本作 Il2CppDumper 自动模式失效后的可靠替代）

1. **methodPointers 数组定位**：在运行时 bss 里搜「指向某个已知方法地址的 8 字节指针」。
   已知锚 = `AppearanceMgr.IsAppearanceItemUnlocked`=`0x11944af8` → 命中 `bss2.bin` 偏移 `0x4d2ef8`。
   该数组按 **token rid−1** 索引（同模块内相邻的 5 个方法全对齐验证通过）。
2. **模块结构定位**：方法数组首地址 `0x729b860b10` 的引用在 `bss1.bin` 偏移 `0x79a960`；
   结构体 `{u32 methodPointerCount; u32 pad; u64 methodPointers; u32 adjustorThunkCount; ...}`
   前置计数 = `0xd42c` = **54,316**，与 metadata 里 `LC2.Core.dll` 的方法总数完全相等 ⇒ 认对了。
3. **按图片方法数对齐**：metadata `images[165]` 每张图的方法数（`LC2.Core.dll`=54316 起）
   与候选数组的 count 对齐，得各模块 methodPointers 基址；`RVA = ptr[rid−1] − 0x72876b8000`。

> 已知局限：165 张图只稳定对齐 162 张（小模块计数重复导致贪心歧义），
> **`LC2.Core.dll` 是 100% 可靠的**（本次所有装扮代码都在它里面）。
> 另有两个大模块（覆盖 `0x6f00000–0x9b00000`，含卡片控制器外壳）未命名 ⇒
> 该区代码可读但无方法名（见 §3.3 的 `0x9afd8f4` 现场）。

## 3. 判定链（反汇编实证）

### 3.1 装扮仓库 · 合并（`0x11940d10`–`0x11940dd8`）

```

for i in list.Count:
    item = list[i]; item.[0x24] = 2
    if (obtainedList != null && obtainedList.Count >= 1):        ; 0x11940d58/0x11940d60
        j = 0
        rec = obtainedList[j]                                     ; 0xe3d7af8 = List.get_Item

### 3.3 卡片取锁（未命名程序集，现场可读）

`0x9afd894`：

## 4. 落地补丁（4 条 K_RESULT，全部挂在 feature 7 全装扮）

| 槽位 | RVA | 原字 → 新字 | 效果 |
|---|---|---|---|
| `SkinInvHit` | `0x11940d94` | `0x370000C0` → `0x14000006` | 仓库合并：无条件进「命中」分支 |
| `SkinInvOb` | `0x11940dac` | `0x394042E8` → `0x52800028` | 记录 obtained 位 → 恒 1（`mov w8,#1`） |
| `SkinUiHit` | `0x1194afd8` | `0x36000060` → `0xD503201F` | 装扮页：不跳过，落到下一条 |
| `SkinUiOb` | `0x1194afdc` | `0x39404308` → `0x52800028` | 同上恒 1 ⇒ `cbnz` 必跳进「命中」 |

保留原 `Appearance` 槽（`0x11944af8` 恒 true）→ 详情面板锁图标、套装判定一起过。

**为什么不直接置 `mShowLockCover=0`**：`0x11940618` 等 7 处（每个部位分支一处）都要改，
且装扮页的过滤是结构性的（不 Add），改 `mObtained` 一处解决两个页面。
**为什么不写 `mObtainedTime=null`**：始终走「命中真实记录」分支，时间/来源照样从记录拷，无空引用风险。

### 已知边界（写清，不装成功也说得明白）

1. 账号已获得记录为空（`obtainedList.Count == 0`）时，两条 `b.lt` 分支不经过补丁 ⇒ 仍是全灰。
   现实账号至少有一条（本机账号 2 条）——服务端 `GetAppearanceWarehouse` 必回记录。
2. 全装扮打开后，装扮仓库的「收集进度」按数据算会显示满；未发现「收集奖励领取」入口
   （`AppearanceInventoryUI` 无 claim 方法），故不会触发服务端校验。
3. 关闭开关：4 条补丁按 `g_slotSaved` 原字还原，已建好的列表要重开界面才回灰。

## 8. 【2026-10-30 13:10】第三改：命中「服务端列表为空 ⇒ 整函数 return」这条真正被走的分支

### 这一轮把「哪个页面」这件事查实了（不再靠猜）
`LC2.UIRoot.ShowAppearanceInventoryUI`（`0x10acb54c`，全工程唯一打开仓库的入口）的调用方只有两处：
- `LC2.AppearanceUI.<RegisterEvent>b__40_1`（装扮页上的按钮）
- `LC2.PassportUI.OpenAppearanceEntry`（名片 → 装扮入口）

⇒ 用户点开的「装扮仓库」**就是 `AppearanceInventoryUI`**（昨天挂错了系统的那一版只是搭错分支，UI 判断没错）。

### 昨天两条补丁为什么必然无效（关键证据）
`AppearanceInventoryUI.InitInventoryData` 的合并循环：

```
0x11940d10  ldr  x0,[x20,#0x120]     ; mAllAppearanceData
0x11940d14  cbz  x0, 0x11940de8      ; 列表空 → 直接返回
0x11940d30 ... 循环头  ldr w8,[x0,#0x18] ; cmp w21,w8 ; b.ge 结束
0x11940d4c  mov  x22, x0             ; x22 = AppearanceItemData*
0x11940d50  str  w27,[x0,#0x24]
0x11940d54  cbz  x19, 0x11940de8     ; ★ 账号已获得列表为 null → 整个函数 return（全部保持未获得）
0x11940d58 ... 遍历记录，String.Equals(记录.code(+0x30), item.mItemCode(+0x58))
0x11940dac  ldrb w8,[x23,#0x10]      ; 记录里的 obtained 位
0x11940db4  strb w8,[x22,#0x38]      ; item.mObtained
0x11940dc8  str  x1,[x22,#0x48]!     ; mSource（+写屏障）

昨天改的是 `0x11940d94`/`0x11940dac`，**都在 `0x11940d54` 之后**。只要 `x19`（服务端下发的已获得列表）为 null，
函数根本走不到那两行 ⇒ 补丁"装了但永远不执行"，与用户"毫无变化"的观察完全一致。

### 本改法（一个入口补丁覆盖两种情形）
`0x11940d54` → `b cave`；cave：`mov w8,#1` / `strb w8,[x22,#0x38]` / `b 0x11940ddc`
⇒ 每个配置项取出来后直接标"已获得"，再回循环尾取下一项；无论列表为 null 还是非 null 都成立。
代价：`mObtainedTime(+0x40)` / `mSource(+0x48)` 保持 null；已核 `AppearanceCardUnitUI.ShowDetail`（`0x1193b614`）
读的是卡片自身 `+0x48`（Text 组件），不读 item 的这两个字段，详情面板走 `AppearanceMgr.GetName/GetDescription`。

装机证据：`slot[7] SkinInvLock 已获得 stub 已装：入口 0x14648C87 → cave …（mObtained=1; b 0x11940DDC）`，
`hook 状态 want=6 have=6/12`，预检 `PASS_TO_HUMAN`。

`GetOrCreatePersistentSalt`、`GetDeviceKey`、`GetHashedUserId`、`GenerateHmacSHA256`、`BuildData/ExtractData`（带 IV/盐/HMAC 信封）。
密钥＝玩家身份 + 设备 + 持久盐派生 ⇒ 离线伪造需完整复刻派生链与设备侧盐文件，成本高，**暂缓**；
