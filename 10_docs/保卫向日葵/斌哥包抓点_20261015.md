## 2. ★关键结构：这台机器上 libil2cpp 有「两份」

这是本轮最容易踩坑的地方，**先用错一份会得到一整套错的 RVA**。

| 来源 | 路径 | 体积 | md5 | 说明 |
|---|---|---|---|---|
| A：APK 内嵌 | APK `lib/arm64-v8a/libil2cpp.so` | 62,032,888 | `f06868ccce285aae828ab7deb825805f` | 原版构建（bin哥不动游戏 so） |
| **B：热更落地** | `/data/data/com.bwxrk.yqmy.ty4/files/libil2cpp.so` | 62,235,240 | `895b34890507bcbcf76e9c312693fb10` | **运行时真正 dlopen 的那份** |

- 热更载体 = `libdod_hot_il2cpp.so`（235,784 B，dodjoy SDK），首启把 IL2CPP 落到
  `files/libil2cpp.so` + `/sdcard/Android/data/com.bwxrk.yqmy.ty4/files/StreamingAssets/ab/{arm64-v8a_libil2cpp.so, global-metadata.dat, patch-global-metadata.dat}`。
- `files/libil2cpp.so` 与 APK 内嵌那份**不是同一个构建**：全 EP_LOAD 段 filesz 都变大，
  section header 表被整体后移 202,352 B（`e_shoff` 0x03B284B8 → 0x03B59B28）。
- 运行时 maps 实测（pid 4348）：
  ```
  7486a37000-7487f72000 r--p 00000000  fe:48 431174  /data/data/com.bwxrk.yqmy.ty4/files/libil2cpp.so
  7487f72000-7488f3a000 r-xp 0153b000  fe:48 431174  /data/data/com.bwxrk.yqmy.ty4/files/libil2cpp.so
  ...
  ```
  ⇒ **基址 = `0x7486a37000`，且 RVA == 文件偏移（PH2 va==off==0x153b000）**。

- metadata 也两份：
  - APK `assets/bin/Data/Managed/Metadata/global-metadata.dat` = 14,253,536 B（＝`/sdcard/.../files/il2cpp/Metadata/` 那份）
  - 热更 `StreamingAssets/ab/global-metadata.dat` = `patch-global-metadata.dat` = **14,295,428 B，md5 `e2645ec3ad447e070e84cd140bf85595`**

> **Il2CppDumper 必须用 (B 的 so) + (热更 metadata)**。
> 用 A 那对也能 dump 出来，但是**另一套 RVA**（见 §4 双腿对照表）。

## 3. 抓点方法（路径 B 变体）

1. 设备侧 dump 运行内存：`bash 04_scripts/_common/dump_binge_shell_mem.sh com.bwxrk.yqmy.ty4 <outdir>`
   （KSU `dd /proc/<pid>/mem`，不用 Frida；壳反调试会杀进程）
2. **磁盘 `files/libil2cpp.so` vs 运行内存 RX 段逐字节 diff**（本次 34,508,800 B 里**只差 24 字节**）：
   ```
   rx_1 是否一致 差异=0
   rx_2 差异=12   首个不同 @0x7c
   rx_3 差异=0
   rx_4 差异=12   首个不同 @0xcf0
   rx_5 差异=0
   ```
   ⇒ **只有 2 处 patch**（＝只有 2 个钩子真正装上，与 §0 表一致）
3. 每处差异＝标准 12 字节跳桩 `ADRP X17,#page ; ADD X17,X17,#imm ; BR X17`：

| # | 内存 VA | 热更 so 文件偏移(=RVA) | 原指令（磁盘） | 补丁后（内存） | 跳桩目标 |
|---|---|---|---|---|---|
| A | `0x7488f3a07c` | `0x250307C` | `sub sp,sp,#0x40 / str x22,[sp,#0x10] / stp x21,x20,[sp,#0x20]` | `adrp x17,#0x755696e000; add x17,x17,#0xc5c; br x17` | `libSDKloading.so +0x2CEC5C` |
| B | `0x7488f3fcf0` | `0x2508CF0` | `stp x21,x20,[sp,#-0x20]! / stp x19,x30,[sp,#0x10] / ldr x8,[x0,#0x20]` | `adrp x17,#0x755696e000; add x17,x17,#0xa4; br x17` | `libSDKloading.so +0x2CE0A4` |

4. **RVA → 方法名**：Il2CppDumper(`files/libil2cpp.so` + 热更 metadata) → `dump.cs`（25.6 MB，761,152 行）。
   两个 RVA 都是**方法起始地址的精确命中**：

| RVA | dump.cs 行 | 签名 | 所属类（行号） | 程序集 |
|---|---|---|---|---|
| `0x250307C` | 11166（`Slot: 15`） | `public override void OnUpdate()` | `internal class BattleCoreSys : BaseLogicSys<BattleCoreSys>`（11060） | `GameLogic.dll` / `C6Game` |
| `0x2508CF0` | 11214 | `public void SelectRandomSkill(uint gid, uint skillIdx)` | 同上 | 同上 |
| `0x2785F48` | 14201 | `private float GetFinalTimeScale(int speed)` | `internal class BattleSys : BaseLogicSys<BattleSys>`（14038） | 同上 |

5. **壳自己就把答案写在内存里**：`libSDKloading.so` 的 rw 段（BSS）带一个**自述式中文字符串池**，
   直接给出功能名、钩点名、原理、风控结论。这是本轮最省力的证据源，见 §5。

## 4. 三个钩点：双腿 RVA 对照（★移植直接用）

| 方法 | APK 内嵌构建（A）RVA | 热更构建（B）RVA | 位移 |
|---|---|---|---|
| `C6Game.BattleCoreSys::OnUpdate()` | `0x24DDEE8` | `0x250307C` | `+0x25194` |
| `C6Game.BattleCoreSys::SelectRandomSkill(uint,uint)` | `0x24E3B5C` | `0x2508CF0` | `+0x25194` |
| `C6Game.BattleSys::GetFinalTimeScale(int)` | `0x2760BA0` | `0x2785F48` | `+0x253A8` |

派生不变量（**跨构建稳定，可作序言/布局校验**）：

GetFinalTimeScale - SelectRandomSkill           = 0x27D044 (A) / 0x27D258 (B)

`GetFinalTimeScale` 的反汇编序言（热更构建，`0x2785F48`）——可作为移植时的序言校验字节：

### 5.2 战斗加速（第 2 格）—— 机制完整，但**本次未生效**

```
[BW] ★战斗加速 就绪=%d。原理: 钩 BattleSys.GetFinalTimeScale(int) 的【返回值】——
     那是倍率的唯一出口(m_paramBattleDoubleSpeed@0x60 / TripleSpeed@0x64 的读点只有它),
     游戏自己拿返回值去设 timeScale
[BW] ☆解表实读: 游戏自带的'2倍速'其实只有 1.4 倍, '3倍速'只有 1.8 倍(参数89/90,
     自检 545=4.0/557=-0.99/572=1300 全吻合) —— UI 上的 2x/3x 是话术。所以想要 ×5 必须改这个返回值
[BW] ✅复算安全性: 档位存 ActorSaveData:BaseClientData(本地存档), 上传 proto 里零 speed 字段;
     timeScale 只让逻辑帧跑得快, 帧序列不变 -> 服务器按 InputData 重放结果一致。
     且这是游戏自带的月卡特权, 设计上必须支持
[BW] ⚠未知风险: 若服务器另有【墙钟时长】校验(客户端查不到), 加速会被看出来。
     ★判据照旧: 看奖励到不到账 / 下一关解不解锁
```

- 倍率**固定 ×5**，菜单调不了（壳原话：`开关块 case1 没有 value 处理, 菜单调不了。要改倍数告诉我`）。
- 字段：`BattleSys.m_paramBattleDoubleSpeed @0x60` / `m_paramBattleTripleSpeed @0x64`（dump.cs 已确认，行 14058/14059）。
- `GetFinalTimeScale` 就是把这些参数翻成最终 timeScale 的**唯一出口**（返回 float）。

**为什么没生效（已定量解释）**：壳的建档表是 **A（APK 内嵌构建）** 的，运行时 resolved 到 **B（热更构建）** ⇒ 守卫拒绝：

```
[BW☠] GetFinalTimeScale 偏移不符(实际2609984 期望2609452) -> 可能游戏已更新, 不装这个钩子
```

- `实际 = 2609984 = 0x27D340`、`期望 = 2609452 = 0x27D12C`，两者相差 `0x214`。
- 壳的读数口径已**完全还原**（精确到字节）：

  | 读数 | 壳打印值 | = 该构建真实 `GetFinalTimeScale − SelectRandomSkill` | 常数 |
  |---|---|---|---|
  | 期望（建档＝A 构建） | `0x27D12C` | `0x27D044` | `+0xE8` |
  | 实际（现场＝B 构建） | `0x27D340` | `0x27D258` | `+0xE8` |

  ⇒ 壳度量的是「相对 `SelectRandomSkill` 的位移 + 固定锚点常量 `0xE8`」；两构建该位移差 `0x27D258 − 0x27D044 = 0x214`，
  与壳打印的差 `0x27D340 − 0x27D12C = 0x214` **逐字节吻合**。
  结论：壳拿「A（APK 内嵌）构建的档案」比对「B（热更）构建的现场」，差 `0x214` 就主动罢工 —— **机制完全解释，无遗留疑问**。
- 同一次启动里钩 1/2 装上了 —— 因为它们是**按名解析**装的，不受建档偏移守卫约束。
