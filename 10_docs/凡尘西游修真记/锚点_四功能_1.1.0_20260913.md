## 0. 坐标口径（重要）

- **RVA = 运行时地址 − libil2cpp 映射基址**，等价于 ELF **vaddr**。
- ELF 实测：第一个 LOAD `off=0/vaddr=0`；**RX 段 `p_offset=0x16ab534` 但 `p_vaddr=0x16af534`（差 0x4000）**
  ⇒ 若按「file_off → VA」查 `/proc/self/maps` 必须传 **file_off = vaddr − 0x4000**；本模块的 RVA 仍直接等于 ELF vaddr。
- **★ 基址踩坑（2026-09-13 真机实测修复）**：本机 `/proc/self/maps` 同时存在两个 `libil2cpp.so` 的
  `off=0` 映射：一个是 OPPO 预加载残留的不可执行只读副本（`r--p`），另一个才是真正的 load bias。
  首轮实现按 maps 顺序取第一个 `off=0` 映射，恰好拿到只读副本，导致 `RandomRange`/`RemoveAt` 的
  RVA 序言校验读到错误字节，钩子从未装上。
  修复：主路径改用 `dl_iterate_phdr` 的 `dlpi_addr`；maps 兜底用同 inode 的可执行段与 `off=0` 映射配对；
  `VaInLib()` 只认可执行映射。运行时日志已验证 `libil2cpp base=0x… (dl_iterate_phdr)`。
- 上一轮会话曾用 base `0x733485B000`、本轮运行时 base `0x7332caf000`，**RVA 不变**（已交叉复核）。

### 3.5 掉落必掉（百分百爆率）

掉落概率全部在 `FightTimeMgr::GetSuccessWuPing` 内用 `UnityEngine.Random::Range(int,int)` 现算；
该函数是 `br x2` 存根（首次调用惰性解析真实实现并缓存），RVA `0x35ED058`，序言 `0xA9BE57FE`。
全库 **258 个调用点**，其中 11 个在本函数内：**6 个是概率闸门，5 个是随机选物品 ID**。

| # | 调用点（RVA） | 参数 | 判定语义 |
|---|---|---|---|
| 1 | `0x1AA07B4`（返回 `0x1AA07B8`） | `Range(0,100000)` | 权重命中：`cfg > rand` 才命中（cfg@item+0x20） |
| 2 | `0x1AA1434`（返回 `0x1AA1438`） | `Range(0,10000)` | `cfg*1000 <= rand` → 跳过 |
| 3 | `0x1AA1D78`（返回 `0x1AA1D7C`） | `Range(0,10000)` | `rand > 99` → 跳过（固定 1%） |
| 4 | `0x1AA253C`（返回 `0x1AA2540`） | `Range(0,1000)` | `rand >= 难度*10` → 跳过（难度 1~3 → 1~3%） |
| 5 | `0x1AA2750`（返回 `0x1AA2754`） | `Range(0,10000)` | `cfg*2000 <= rand` → 跳过 |
| 6 | `0x1AA297C`（返回 `0x1AA2980`） | `Range(0,10000)` | `cfg*2000 <= rand` → 跳过（另一分支） |

纯选择（**不改**，保持随机）：`0x1AA14A8 Range(2001,2037)`、`0x1AA170C Range(10001,10010)`、
`0x1AA18F4 Range(1001,1037)`、`0x1AA1A80 Range(2001,2037)`、`0x1AA20EC Range(3001,3069)`。

**实现**：钩 `0x35ED058`，按 `__builtin_return_address(0)` 命中上表 6 个返回地址 → 返回下界（均为 0）。
效果：配置里**非零概率**的掉落全部必掉；配置为 0 的项仍不掉（不伪造内容，只取消运气成分）。
运行时已验证 `0x35ED058` 就是 `Random.Range`：`Range(0,100) x12 = [61,51,46,35,87,61,35,63,81,59,71,11]`，
`Range(2001,2037) x8 = [2019,2012,2024,2015,2029,2018,2003,2003]`。

**⚠ 第一版结论修正（2026-09-13 晚）**：上表第 1 项 `0x1AA07B8` 不是「每一项各自过一次概率」，
而是主掉落池的**按权重「只选一个」**：

```text
0x1AA0790  loop:  i = 0 .. list.count-1
0x1AA07B4    rand = Random.Range(0, 100000)      // 返回地址 0x1AA07B8
0x1AA07D4    item = list.get_Item(i)
0x1AA07DC    weight = *(int32*)(item + 0x20)
0x1AA07E8    if (weight > rand) break          // 命中即跳出，进类型分发
```

即：一次结算只发一件。把 rand 压成 0 只能保证命中**第一个正权重候选**，
表里其余候选永远不会发 —— 这就是真机实测「提示两个物品只掉一个」的根因
（探针还原：该副本主池 `count=2` = `虎妖 weight=500` / `凡品开山斧 weight=1000`）。

**主池全候选实现（第二版）**：新增 `FightTimeMgr::GetSuccessWuPing` 本体钩子
（RVA `0x1AA0374`、序言 `0xD101C3FF`；全库唯一调用者 `fightProPlus@0x1A9BEC0` 为单次 `bl`，非循环）：

1. 先正常调一次原函数（保留上面 6 个闸门的既有行为）；
2. 读 `cfg = self+0x130` → `dropList = cfg+0x78`（List 布局：`+0x10` 数组 / `+0x18` 长度，
   元素指针在 `array+0x20+i*8`），快照各条目 `weight = item+0x20`；
3. 对其余每个 `weight > 0` 的候选逐个 replay：临时把别的条目 `weight` 写 0
   （与 `0x1AA07DC` 同口径，只写低 32 位），调完立即还原 → 该候选在 `b.gt` 处被命中；
4. replay 期间 `Random.Range` 钩子让 5 个附加闸门返回 `0x7FFFFFFF`（走“跳过”分支）
   → 附加奖励不重复发（5 个纯选择随机调用点都在闸门命中路径内，一并跳过）；
5. replay 期间尾部 `addLinShi`/`addXiuwei` 由 addData 钩子置 0 → 灵石/修为不重复结算。

**为什么必须挡尾部**：整函数只有一个 `ret`（`0x1AA31C0`），`0x1AA30E8` 的
`cfg[0x58]*500`（夹 1e5）与 `0x1AA3150` 的 `cfg[0x60]*cfg[0x58]*50`（夹 1e7）→
`addLinShi/addXiuwei` 是**每次调用都跑**的尾部；不挡就按 replay 次数白送资源。
（这两个是 `b` 尾调用 addData，故 addData 里 `__builtin_return_address(0)` 仍是
`0x1AA310C` / `0x1AA3174` —— 掉落翻倍锚点即由此成立。）

### 3.6 灵玉不减（2026-09-14 新增，真机实测通过）

**存储形态和所有其它货币都不一样 —— 灵玉是加密串，不是整型字段：**

| 位置 | 内容 | 实测 |
|---|---|---|

调用约定，收益低风险高（已否决）。
