## 0. 结论先行（TL;DR）

1. 排位/挑战走的是 **RhythmMaster 玩法**（`RhythmMasterVM`+`RhythmMasterMode`+UI 117），不是 KeyPress/KeyItem 那套。证据：`__110:71-90`、`__066:250-256`、`__050:1085-1091`。【实测】
2. 该玩法的"自动跳舞"是 **专用自动分支**：`117 OnUpdate` 里 `IsAutoMode()` → `AutoHold()`+`AutoNote()`（`__117:2351-2358`），**不是**模拟按键，也**不经过** `047 RhythmKeyItem:CheckJudge/CheckJudgeCheat`。【实测】
3. 自动分支最终**确实**调到了 `OnJudgeResult`→`typeMode:AdjustJudge`→`OnAdjustJudge`→`calcReduceHp`→`AdjustBlood`（`__117:4232-4261` → `__117:2886-2890` → `__015:741-752` → `__015:754-830`）。**链路没断**。【实测】
4. 真正的差异只有一个入参：**自动命中把判定档写死成 `SuperPerfectPlusPlusAdd=7`（`__117:4237-4240`），手动按键是 `GetJudgeResultByOffset()` 按时差算出的 1..7（`__117:5464-5468`、`__052:637-696`）**。而 016/020 的 `calcReduceHp` 把 judgeType 当作 `Judge_Basehp` 的**行键**，行缺失时回退 `Judge_Basehp[Miss]`（`__020:321-338`、`__016:156-173`）→ 顶档 7 若没有配行，加血量取到 Miss 行的 `Oursidevalue`（大概率 0）→ 表现为"不加血"。【推断｜关键缺口待验证】
5. 另有一条**与自动跳舞无关、但同样导致"不加血"的确定性缺陷**：现有 mod 的 `typeMode.AdjustJudge` 包装在 `judge_on` 打开时**直接 return，不调原函数**（`mod菜单/starry-mod-menu/app/src/main/jni/Games/ywtMod.cpp:423-446`），于是 `OnAdjustJudge`/`AddMyEnergy` 整段被跳过 → 判定概率开着的局**一定**不加血、不加能量。【实测（源码可见）】
6. 最小改动点（不碰 015/016/020、不碰 KeyItem）：见 §5 的 **C1（首选）** 与 **C0（必须先修）**。

## 2. 自动跳舞到底做了什么（117 全链路）

### 2.1 开关：`DanceVM.cheat_mode`
- `__023:120-122`：`CheatMode = {None=1, Prefect=2, Random=3}`。【实测】
- `__023:948-953`：`proto#22 GetCheatMode` = `return cheat_mode`；`proto#23 SetCheatMode(v)` = `cheat_mode = v`（模块级 upvalue）。【实测】
- mod 侧：`ywtMod.cpp:493-503` 调 `DanceVM.SetCheatMode(auto_on and (auto_mode==2 and 3 or 2) or 1)`。【实测】
- `__117:2070-2079` `proto#40 IsAutoMode` = `GetCheatMode() ~= CheatMode.None`。【实测】

### 2.2 每帧驱动（自动 vs 手动在同一函数的两个分支）
`__117:2351-2368`（`proto#46 OnUpdate`）：
```
[11] SELF R3 R0 "IsAutoMode"   [13] TEST R3 ... [14] JMP -> 20
[15] SELF R3 R0 "AutoHold"     [17] SELF R3 R0 "AutoNote"   [19] JMP -> 29
[20..24] CheckMissNotes        [25..28] CheckHoldTimeout / CheckFlickTimeout
[29] HoldCombo
```
- 自动：`AutoHold`+`AutoNote`，并**跳过** `CheckMissNotes`/`CheckHoldTimeout`/`CheckFlickTimeout`。【实测】
- 手动：走 `OnInputHandler`→`ProcessTouchInput`→`JudgeNoteAtTrack`（`__117:2341-2349`、`__117:5353-5456`）。【实测】

### 2.3 自动命中 = 直接写判定档，不是模拟按键
`__117:4160-4228`（`proto#71 AutoNote`）：`music_time - note.time >= 0` 时按 note 类型分派 `AutoHitTap/AutoHitFlick/AutoHitHold`（`[39] LE`、`[44]/[52]/[63] SELF`）。【实测】

`__117:4232-4261`（`proto#72 AutoHitTap`）：
```
[0] SELF R3 R2 "SetJudged"  [1] LOADBOOL R5 1        ; 直接把 note 标成已判定
[3..5] JudgeResultType.SuperPerfectPlusPlusAdd      ; ★ 硬编码顶档 7
[22] SELF R4 R0 "OnJudgeResult"
[23..28] 传参 x, 7, note.type, nil, note.nid
```
→ **没有任何"按下/触摸"事件，也不进 KeyItem**。【实测】

### 2.4 手动路径（参照物）
`__117:5353-5456`（`proto#81 JudgeNoteAtTrack`）判定时差在窗口内 → `[69] JudgeTap`。
`__117:5461-5478`（`proto#82 JudgeTap`）：
```
[0] SetJudged(true)
[3..8] RhythmMasterVM:GetJudgeResultByOffset(offset, judge_scale, get_judge)
[9..15] OnJudgeResult(x, judge_type(算出来的), note.type, nil, note.nid)
```
**两条路径的 OnJudgeResult 签名/位置完全相同，唯一差别是第 2 个实参 judgeType**：自动恒为 7，手动为 1..7。【实测】

## 3. 加血链路（谁在哪儿加）

| 步 | 位置 | 关键 opcode | 结论 |
|---|---|---|---|
| 1 | `__117:2886-2890` `proto#50 OnJudgeResult` | `GETTABLE typeMode` / `SELF AdjustJudge` / `CALL` / `MOVE R2 R6` | **无条件**先调 `typeMode:AdjustJudge(judgeType)`，返回值覆盖后续使用的判定档 |
| 2 | `__015:741-752` `DanceTMBattleBase:AdjustJudge` | `LE R0 256 1`(k[0]=7)、`LOADK R1 6`、`SELF OnAdjustJudge`、`SELF AddMyEnergy` | **judgeType<7 一律归一成 6**，7 保持 7；再调 OnAdjustJudge + 加能量 |

### 3.1 为什么"手动加、自动不加"（【推断】，缺口见 §6）
- 自动：`AdjustJudge(7)` → 015 不归一（7 不 < 7）→ `calcReduceHp(..., 7, true)` → `Judge_Basehp[7]`。
- 手动：绝大多数命中是 4/5/6 → 015 归一到 **6** → `Judge_Basehp[6]`（配置必有行，否则正常玩家的血量逻辑本身就崩）。
- 若 `Judge_Basehp` 只配了 1..6 行（合理：015 的归一化就是在告诉上层"战斗只关心 ≤6 档"），则 `[47] TEST R7` 为假 → 走 `[49..58]` 取 **Miss** 行 → `Oursidevalue` 通常为 0/负 → `delta≈0` → hp 不变 → **"不加血"**。
- 佐证（间接）：`__020:347-363` 的加成系数只对 4/5/6 生效，7 无加成，说明 7 这一档在这套血量公式里**没有被当成"有效档位"设计**。

## 4. 其它玩法为什么"自动也加血"（反证 117 才是异常点）

| 玩法 | 自动实现 | 是否走 AdjustJudge |
|---|---|---|
| KeyPress（035/036） | `__035:679-836`：`GetCheatMode` 判定后**调 `self:OnBtnHit()`**（Prefect 立即打 `AutoBeat`，Random 用 `cheat_interval` 延后打） | `OnBtnHit`(`__035:414-455`)→`GetJudgeResult`→`DoHit`(`__035:458-521`)，`DoHit` **首 4 条指令**即 `typeMode:AdjustJudge`（`__035:459-462`）→ 加血 ✓ |
| FloatDown（053） | `__053:694-771` `CheckJudgeCheat`：直接置 `judge_type = SuperPerfectPlus`(6) 或 `random(Good,SuperPerfectPlus)`，然后 `on_judge` | 走 `on_judge`→UI `OnJudgeResult`→`AdjustJudge`；**顶档给的是 6 不是 7** → 命中 `Judge_Basehp[6]` ✓ |
| Rhythm（047） | `__047:1066-1163` `CheckJudgeCheat`：Prefect→`SuperPerfectPlus`(6)、Random→`random(Good,SuperPerfectPlus)` | 同上 ✓ |
| **RhythmMaster（117，排位/挑战）** | `AutoHitTap` **硬编码 7** | 走 AdjustJudge 但给的是 7 ✗ |

> 这一列对比是本报告最强的旁证：**三个"自动也加血"的玩法，作弊档都封顶在 6；只有 117 用了 7。**（053/047 见 `__053:706-708` `SuperPerfectPlus`、`__047:1088-1091` `SuperPerfectPlus`）【实测】

### 4.1 047 CheckJudgeCheat vs CheckJudge：参数与 judge_index 时序（回答 lead 问题 2）
- 参数：两者都调 `on_judge(cb_self, key_info.key, key_info.type, judge_type[judge_index], judge_index)` —— **6 参、完全同构**：
  - `CheckJudge` 命中分支 `__047:957-968`；Miss 分支 `__047:899-910`；长键收尾分支 `__047:1009-1020`。
  - `CheckJudgeCheat` `__047:1134-1145`。
- 时序：两者都是 **先 `judge_index = judge_index + 1`，再写 `judge_type[judge_index]`，再回调**：
  - `CheckJudge`：`__047:1005-1016`（`[93] GETTABLE judge_index`→`[94] ADD 1`→`[95] SETTABLE`→`[98] SETTABLE judge_type`→回调）。
  - `CheckJudgeCheat`：`__047:1144-1147` 前置由 `UpdatePos` 完成（`__047:1010-1014`：`judge_index+1` 后才 `SELF CheckJudgeCheat`）。
- **不等价之处**（都不影响加血）：`CheckJudgeCheat` 不做 `can_judge/check_offset/cur_press_key` 校验、不做 `is_press=False`/`SetGray`/`Audio.Stop`（`__047:935-952` 对比 `__047:1120-1130`）；且档位来源是 `CheatMode` 而不是 `DanceRhythmVM:GetJudgeResult`（`__047:1068-1084`）。→ 结论：**047 的两条路径对下游 `on_judge` 是等价的，排位/挑战压根不走 047**。

## 5. 候选注入点（Lua 函数级，只出方案）

> 前提：现有 mod 已包 `typeMode.AdjustJudge`（实例级，`ywtMod.cpp:414-446`）。下表"共存"= 能否与该包装同时生效。

### C0（先修，独立缺陷）`ywtMod.cpp` 的 AdjustJudge 包装：先调原函数再返回伪档
- 现状：`if v ~= nil then ... return v end`（`ywtMod.cpp:430-441`）——**不调原函数**。
- 改法：`local r = aj(tm2, judgeType, ...)  -- 让 015 跑 OnAdjustJudge/AddMyEnergy` 然后再 `return v`。
- 入参：无需新增。副作用：加血/加能量按**原始档位**结算（不是伪档），自洽性最好。共存：就是改它本身。
- 证据：`__117:2889-2890` 只用返回值当"后续档位"，不要求它是 `AdjustJudge` 内部算出来的 → 先算后改安全。

### C1（首选，最小面）挂 `117 UI_DanceRhythmMasterMode_Ctrl.AutoHitTap`（chunk 117 / `proto#72`）
- 挂法：`local orig = ctrl.AutoHitTap`；包装时把 `JudgeResultType.SuperPerfectPlusPlusAdd` 换成 `SuperPerfectPlus`（6），或直接调 `orig(self, note, item)` 后再把 `note.judge_type`/`judge_type` 参数改为 6。
  更稳的做法是包 `ctrl.OnJudgeResult`：入口处 `if judgeType == 7 then judgeType = 6 end` 再调原函数（`__117:2886`）。
- 入参：`(self, note, item)` / `(self, x, judgeType, noteType, a4, nid)`，均为公开表字段，可从 `show_key_items` 拿到。
- 副作用：顶档从 SPlusAdd 降到 SP+ → 分数/ACC/评级略降（`__117:2919-2921` JudgeModule/Combo/Acc 用它）；判定特效档位变化。**不动血量公式、不动服务端交互**，自洽性最高。
- 共存：与 AdjustJudge 包装**同链且不冲突**（一个改入参、一个改出参）；但若 `judge_on` 开着，仍受 C0 影响 → 必须一起修。

### C2（备选，改动面大）挂 `015 DanceTMBattleBase.AdjustJudge`（chunk 015 / `proto#15`）
- 挂法：`if judgeType >= 7 then judgeType = 6 end` 后调原函数。
- 入参：`(self, judgeType)`。副作用：**全局**作用于 016/020/019/018/021 所有战斗 typeMode，等于把"顶档"从游戏里抹掉（分数/吸血/暴击都会跟着变）。
- 共存：**冲突**——现有 mod 包的是实例级 `self.typeMode.AdjustJudge`，会遮蔽类方法；两者叠加时执行顺序取决于谁先包。不推荐。

### C3（不推荐，仅调试）绕过判定档直接补血
- 挂 `015 OnAdjustJudge`（`proto#16`）或 `016/020 calcReduceHp`（`proto#5/#6`），在 `delta<=0` 时用固定行（11/12，或 `keyCount` 均值）兜底。
- 副作用：本地血量与服务端不一致，`__015:570-634 OnAttrSyncNoti` 会以回包覆盖 `hp`，排位可能出现血条跳变/结算异常；**与"只做静态分析"的阶段纪律也不冲突，但风险最高**。

## 7. 对 lead 四问的直接回答

1. **035 的 "AutoBeat" 分支调的是 `self:OnBtnHit()`**（`__035:744-760` Prefect 分支、`__035:821-836` Random 分支），`OnBtnHit` **不等价于**"玩家按下"但**等价于**"游戏内的合法击打"：它走 `play_ui:GetKeyResult()`→`DanceKeyPressVM:GetJudgeResult()`→`self:DoHit()`，而 `DoHit` 第一条有效指令就是 `typeMode:AdjustJudge`（`__035:459-462`）→ **KeyPress 玩法的自动跳舞是加血的**。
2. **047 的两条路径对 `on_judge` 等价**（6 参同构、judge_index 均先 +1 后写 judge_type），差异仅在"校验与 UI 收尾"（§4.1）。**排位/挑战不走 047**。
3. **自动跳舞时 DanceTM 的 `OnAdjustJudge/calcReduceHp` 会被调到**（`__117:2886-2890` 无条件调 `AdjustJudge`；`__015:741-752` 无条件调 `OnAdjustJudge`）——**没有被短路**。唯一"短路"在 mod 自己的 `AdjustJudge` 包装（`ywtMod.cpp:430-441`，`judge_on` 时提前 return）。生产代码里**没有**短路指令，问题在**入参档位 = 7**。
4. **最小改动点**：`UI_DanceRhythmMasterMode_Ctrl.AutoHitTap`（chunk **117**，`proto#72`，源 `UI_DanceRhythmMasterMode_Ctrl.lua:2202-2227`）——把 `SuperPerfectPlusPlusAdd(7)` 改为 `SuperPerfectPlus(6)`；或等价地包 `UI_DanceRhythmMasterMode_Ctrl.OnJudgeResult`（chunk **117**，`proto#50`，`:1376-1440`）入口归一 `7→6`。同时**必须**先修 C0（`ywtMod.cpp` 包装先调原函数），否则判定概率开启时依旧不加血。
