## 8. 结论

### 8.1 TapSDK 是否仍可直接改 → **可以，走改包法（A 轨）**

支撑事实：
1. `Lcom/taptap/sdk/**` 全部明文可改：classes11 定义 1788 个、classes2 定义 1142 个，class_defs 可解析、无壳。
2. 7 处补丁的目标类**全部存在**：GatekeeperRepository（classes2+classes11）、DefaultTapLoginFragmentProvider（classes11）、TapSignKit（classes2+classes11）、QGSdkUtils（classes7）、quicksdk/utility/k（classes.dex）、apkverify/Check（classes.dex）。
3. dex 内**没有**硬编码证书指纹，说明 Java 层的签名比对是从 native/常量取值（对应 `Check.getSignInfo` 走 libqkcheck.so），改 Java 侧返回值即可，不需要复活 SignSpoof。
4. 阻力点只有一个且已定位：**libqkcheck.so 的 native 校验**（含未知用途的 32 位常量 `526b7295…`）。P6「把 Check.getSignInfo 改成 Java 常量」正是绕开它；本次核对确认 libqkcheck.so 确实存在，P6 不是多余补丁。

⇒ 不需要运行时 SPI（`GameHookImpl`）。SPI 只作为改包被 QGSDK 服务端拒绝时的备选。

### 8.2 必须提前处理的结构风险

**GatekeeperRepository 与 TapSignKit 在 classes2 和 classes11 各有一份定义，形状完全相同。**
- Android 多 dex 的类查找按 classes.dex → classes2.dex → … 顺序，**先命中先用**，即运行期实际用的是 **classes2 的那份**。
- P1/P2/P4 只改 `smali_classes11` ⇒ 若不断言，**改了不生效**（这正是「补丁打了却没效果」类故障的典型成因）。
- 处置：P1/P2/P4 必须 **classes2 与 classes11 同改**，或在装机前用 `dexdump`/运行时确认实际加载来源。**本条待验证运行时归属**（静态只能证明两份都在、顺序上 classes2 在前）。
