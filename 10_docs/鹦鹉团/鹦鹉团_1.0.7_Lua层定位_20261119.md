## 0. 结论摘要（先看这段）

1. **判定不在 Lua。** 全区 111 个 Lua 5.3 chunk（luac 字节码，无源码）中**没有任何**判定计算逻辑：无 perfect/great/good/miss 分级阈值、无时间差 abs 比较、无命中率/概率变量、无 combo 计数、无 note 与输入的时间对齐。【实测】
2. Lua 里与「判定」有关的**只有表现与音效**：`lua_csys_challenge` 在预加载 `gameplay1_game_sy_perfect / _great / _miss / _combo_*` 等音效名（见 §4.2 证据 A），即 **Lua 是判定结果的消费方，不是产生方**。【实测】
3. **判定与玩法运行时在 C# 侧**，且是通过两种方式暴露给 Lua 的：
   - ① C# 注入的 Lua 全局：`DanceMgr` / `DanceVM` / `RhythmMasterConstants` —— 在 111 个 chunk 里**0 处定义**（无 SETTABUP），只有 4/7/22 处 GETTABUP 使用 ⇒ 只能由 C# 侧 `LuaEnv.Global.Set()` 注入。【实测】
   - ② `require "CSys.Dance.*"` 引用的 C# 命名空间：`CSys.Dance.DanceActor / DanceCamera / RhythmMasterConstants`（§6）。【实测】
4. 交给 dance 的 C# 目标清单见 **§6**（含每条的 Lua 侧引用位置 file:line）。
5. 玩法内核名称对齐：**「节奏模式 / RhythmMaster」** —— 音效与常量都以此命名（`gameplay1_…`、`DanceRhythmMasterMode`、`CSys.Dance.RhythmMasterConstants`），且 UI 文案里有「在音符到达判定区，点击即可」「连击数」「全完美(AP)」「超完美+」⇒ 下落式节奏玩法，判定在音符到达判定区时发生。（文案【实测】，判定位置【推断/C#，待 dance 用 IL2CPP 证实】）
6. 自动跳舞在本层**无法实现**：Lua 无输入模拟、无判定干预点；已确认 Lua 侧唯一的输入相关入口是 C# 的 `CS4Lua.InputMgr`（§6.3）。【实测】

## 4. 「判定在 Lua 还是 C#」——判据与证据

### 4.1 关键词全域扫描结果【实测】

对 111 份 dis 全文扫 18 个关键词（perfect/great/good/miss/combo/judge/score/probability/auto/robot/simulate/touch/tap/beat/rhythm/note/press/hit/rate）：

| 关键词 | 命中文件数 | 命中性质（逐条核过） |
|---|---:|---|
| judge / probability / robot / simulate | **0** | 零命中 |
| perfect / great / combo / beat / press | 1–5 | 全部是**音效/图标资源名**，非逻辑 |
| miss | 3 | 1 处音效名 + 2 处无关词（`SourceChannelRelationLoverValueMissRedBean`）|
| score / hit / rate / auto / tap / note | 5–9 | 均为 UI 文本、按钮名、`AddTap/EnableTap` 等交互方法名，无一处做判定计算 |

### 4.2 证据 A：Lua 只预加载判定音效（消费方）

`13_scratch/鹦鹉团/lua_dis/lua_csys_challenge.dis.txt` 第 1180–1232 行（函数 `PreloadImage`，函数头见 lua_csys_challenge.dis.txt:1109 的 `-- 子函数 31 (None @439)`）：

    [101] LOADK     R5        "gameplay1_game_sy_miss"
    [104] LOADK     R5        "gameplay1_game_sy_cool"
    [107] LOADK     R5        "gameplay1_game_sy_great"
    [110] LOADK     R5        "gameplay1_game_sy_perfect"
    [113] LOADK     R5        "gameplay1_game_sy_sperfect"
    [116] LOADK     R5        "gameplay1_game_sy_sperfect1"
    [119] LOADK     R5        "gameplay1_game_sy_combo_grey"
    [122] LOADK     R5        "gameplay1_game_sy_combo_green"
    …（combo_blue/purple/orange/red）

这些是 `SELF R3 R1 "Preload"` 的参数，即**资源预加载**。同一个函数里紧邻的是 `RhythmMasterConstants` 的音符贴图常量（`N4note1/2/3/4`、`Nnotefbody`、`Ntail`、`Ntailsl/r`、`Nnote_body_1` 等，行 1160–1230），同样只是 `Preload`。

⇒ 「判定等级」这件事 Lua 只认识**名字**（用来放音效），不认识**算法**。

### 4.3 证据 B：判定管理器是 C# 注入的全局，不是 Lua 模块

对 `DanceMgr` / `DanceVM` / `RhythmMasterConstants` 三个名字做「定义 vs 使用」统计（定义 = `SETTABUP`，使用 = `GETTABUP`）【实测】：

| 名字 | Lua 内定义 | 使用处 |
|---|---:|---|
| DanceMgr | **0** | lua_core_page.dis.txt:608、lua_csys_challenge.dis.txt:1056、lua_csys_opera.dis.txt:795、lua_csys_rhythmeditor.dis.txt:92（共 4）|
| DanceVM | **0** | lua_csys_bag:3554/3618、lua_csys_challenge:1064、lua_csys_opera:803、lua_csys_ugc:158/328、lua_core_page:576（共 7）|
| RhythmMasterConstants | **0** | lua_csys_challenge 共 22 处（如 1124/1128/1132…）|

`GETTABUP U0 "DanceMgr"` 是对 **_ENV 全局表**取值，而全库没有任何一处 `SETTABUP … "DanceMgr"` 写入 ⇒ 该全局只能由 C# 侧注入（xLua `luaEnv.Global.Set("DanceMgr", …)`）。【推断，证据链：全局表无定义 + xLua 常规注入方式；可用运行时 LuaEnv.Global 枚举证伪，属【待验证】】

真实调用点（可直接给 dance）：

`lua_core_page.dis.txt:600-613`（GotoCtrl 里单人进舞房）：

    [ 43] GETTABUP  R11  U0 "DanceMgr"
    [ 44] SELF      R11  R11 "StartDance"
    [ 45..49] arg: R13 R14 R15 R16 R17 …
    [ 54] CALL      R11  12 1

即 Lua 只负责**发起** `DanceMgr.StartDance(roomId, PlayModeId, …)`，进局后的判定由 C# 的 DanceMgr 负责。

### 4.4 证据 C：Lua 侧的「舞蹈/播放」模块全是表现层

以 `lua_csys_dance`（`DanceActor.lua`，594 行，32 函数）为例，函数名逐条列出【实测，见 lua_csys_dance.dis.txt】：

### 6.4 给 dance 的定位建议（不含结论，只给线索）

1. C# 侧优先找 `DanceMgr`（有 `StartDance`、被 4 个 Lua 模块调用）与 `RhythmMasterConstants` —— 后者是判定链路里最可能的常量表（音符类型/连击色阶/判定档）。
2. 判定档名字 Lua 侧已给全：`miss / cool / great / perfect / sperfect / sperfect1`（6 档，见 §4.2），C# 侧应能按这 6 个字符串或对应枚举命中。
3. 连击 UI 与音效播放由 Lua 消费，说明 C# 一定有「判定结果 → 事件/回调」出口；从 `DanceMgr` 的事件注册侧反查最小。
4. 「自动跳舞」若要落地，最可能的干预点是 C# 的输入/判定入口（`CS4Lua.InputMgr` 与 `DanceMgr` 之间），Lua 层没有可挂的点。

## 7. `lua_config_music` 是什么（重要，容易误判）【实测】

结构：`[["id","time","type","param"], …]`，370 行，`time` 最大 157,142.9（毫秒级时间轴）。

    [0, 0.0, 5, [""]]
    [1, 0.0, 3, ["cam_k_001", 1]]          ← 相机关键帧
    [2, 0.0, 4, [0.35]]
    [3, 0.0, 8, [1]]
    [4, 0.0, 9, [20200, 0, 2.232143, 0, 0.896]]   ← 5 参数事件
    [369, 157142.9, 9, [20229, 0, 3.660714, 0, 0.9834163]]

它**不是节奏谱面（note 表）**，而是 **TML（Timeline）事件轨**，与 `IdolMVDanceMgr` 的 `BeDanceTML / LoadDanceTML / PreLoadDanceTML / ReleaseDanceTML`（lua_csys_idolmvdance.dis.txt:87-99 的 SETTABLE 注册）对应，用于 MV/演出的相机与动作编排。

⇒ 谱面 note 数据**不在**客户端这份 Lua 配置里（UGC 作品的谱面走服务端下发或 C# 侧资源）。【推断，待验证】

### 13.2 自动跳舞路径裁决：选 **A（OnKeyDown）**

一句话结论：**走 A —— 包 RhythmMasterMode/Ctrl 的 OnUpdate，在判定窗口内调 ctrl:OnKeyDown({SlotN})，不要走 B 的 note:CheckJudge 直调。**

三条理由：

1. **B 会绕过上报与连击/长条逻辑**。HandlePressOrMove 里除了判定还做：holdstate/holdvalue 写入（__117:5034-5048）、滑键段位姿（PlaySlotAnim，__117:5055-5070）、以及后续 AddCombo/AddScore/AddSendKey（__052）。直接调 note:CheckJudge 只产生一次档位，容易造成"判定对了但连击/分数/上报不同步"。
2. **A 的参数面最小且已确认**：ctrl:OnKeyDown(keys) 只吃一个 keys 数组，keys[0] 取 Slot1..4，键值已确认为 KeyCode.D / F / J / K（__117:75-86：SETTABLE "Slot1"=KeyCode.D、"Slot2"=F、"Slot3"=J、"Slot4"=K；DiscRhythm 模式同样 D/F/J/K，__070:10-21）。而 B 需要自己算 slot（self.inr[lane+1][slot]），规则尚未完全逆清。
3. **反作弊风险为零**（§13.1）：CheckJudgeCheat 只读 CheatMode 全局，不看输入来源/频率，所以 A 与 B 都不会踩"检测"；既然没有检测压力，就选链路更完整的 A。

补充：**若嫌 A 的节奏控制麻烦，可以先开 CheatMode.** Prefect/Random 让判定自动吃满，再配合低频 A 触发（组合方案）。
