## 0. 结论速览（先看这 6 条）

1. **血量有两套容器**：DanceTMBase.player_hp_datas[roleID]={maxHp,hp}（单机/普通，014/018/021）与 DanceTMBattleBase.PlayerBloods[roleID]={roleID,maxHp,hp,shieldHp,team,DamPlus,...}（对战：挑战 016 / 排位 020 / 组队 019）。【实测】014:69、014:193-196、015:249-251
2. **"加血函数"只有一个（对战系）**：DanceTMBattleBase:OnAdjustJudge（015 proto#16，源行 327-377），每次判定做 hp = math.min(hp+calcReduceHp(...), maxHp) 再 math.max(hp,0)，然后刷 shieldHp 并抛 OnAttrSyncMyBlood 给 UI。【实测】015:777-830
3. **另一条加血路是技能**：AddBloodSkill:Use → EventManager.OnGlobalEvent("skillAddBlood", param.value) → DanceTMBattleBase:OnSkillAddBlood（015 proto#28）→ hp=min(hp+value,maxHp)。【实测】044:1163、015:1063、015:1010-1027
4. **注意 ExtraBlood 不是加 hp**：它汇总后写的是 shieldHp（护盾/格挡值），只在 Start / GetMyShieldHp 里出现。【实测】015:713-729（GetMyShieldHp）、015:502（Start 写 shieldHp）
5. **排位 vs 挑战不是同一套驱动**：排位（020）除本地判定外还吃服务端 18756 NfyCommitOperation 回执结算，并被 18801 NfyAttrSyncNoti 权威覆盖；挑战（016）只注册 OnEndStageResp，**没有** AttrSync / CommitOperation 订阅，血量纯本地。【实测】020:108/118、016 方法表
6. **hp 是服务端同步字段**：GASCommitOperationNoti{nRoleID,stKeyResult,stMatchStatusInfo,arrKeyCommit}、GASAttrSyncNoti{nRoleID,arrAttr}、BattleAttrType 1=MaxHP/2=HP/3=ShieldHp；上报走 015#7 Commit → QualifyVM.ReqAttrSyncReq（2417），下发 18801。【实测】dump.cs:221665、224383、204415-204417、224974/224976、015:565

## 3. 加血函数（写 += 的三处，别搞混）

| # | 函数 | 位置 | 表达式 | 触发者 | 触发条件 |

### 3.1 伤害公式（排位 020 / 挑战 016 几乎同构）

反汇编重建（020 proto#6 源 227-347；016 proto#5 源 48-105）：

    combo  = (judge > Miss) and combo+1  or 0          -- 020:284-287
    pCombo = (judge >= Perfect) and pCombo+1 or 0      -- 020:290-293
    bonus  = 1.0
    for cfg in ConfigMgr.GetConfigs(CfgEnum.Combo_Bonus) do
      if combo > cfg.ComboCount then bonus = 1.0 + cfg.ComboBonus/100 end   -- 020:300-306
    end
    cfg  = ConfigMgr.GetConfigById(CfgEnum.Judge_Basehp, judge)
           or GetConfigById(Judge_Basehp, JudgeResultType.Miss)             -- 020:311-326
    base = isSelf and cfg.Oursidevalue or cfg.Enemyvalue                    -- 020:328-336
    if judge == Perfect then bonus = bonus + 0.01
    elseif judge == Sperfect    then bonus = bonus + 0.02
    elseif judge == SperfectPlus then bonus = bonus + 0.02 end              -- 020:337-352
    crit = 0   -- pCombo >= Crit_Bonus.PerfectCount 时取 CritBonus/100，技能可再加 -- 020:357-389
    if isSelf and judge ~= Miss then dmg = base * (bonus + crit)            -- 020:441-446
    else                            dmg = (base / keyCount) * (bonus + crit) end
    dmg = math.floor(dmg)                                                   -- 020:454-457

- 排位额外：HalfHitWithTeam（2v2 队友伤害减半，020:472）、AdjustBlood（技能血修正，020:476）、组队 DamPlus（019:350-353）。
- **Miss 也返回非零**（走 base/keyCount），所以"掉血"只能来自配置里 Miss 档的负值。**缺证据**：CfgEnum.Judge_Basehp / Combo_Bonus / Crit_Bonus 的配置数值没 dump 出来（06_dumped/鹦鹉团/base 只有 global-metadata.dat、libil2cpp.so、libxlua.so），无法证明 Oursidevalue/Enemyvalue 的正负号。这是本文最大未闭合点（见 §9-1）。

## 7. "自动跳舞不加血"排查（与用户诉求直接相关）

### 7.1 官方 Auto 链路**确实**会经过 AdjustJudge

- 自动分支：035:751 [62] GetCheatMode → 035:803 [114] SELF R5 R0 "OnBtnHit"（Prefect 分支）/ 035:835 [146]（Random 分支）
- OnBtnHit → DoHit（035:443）→ AdjustJudge（035:460）
- 【实测】自动与手动在 Lua 层**走同一个 DoHit**，理论上同样会 hp +=。

### 7.2 实测不加血的三个候选（按可能性排序）

| # | 假设 | 证据 | 分级 |
|---|---|---|---|
| H1 | **mod 的 AdjustJudge 包装在判定开关打开时直接 return v，不调用原函数** → OnAdjustJudge 整个被跳过 → 血量一次都不变 | ywtMod.cpp:423 tm.AdjustJudge = function(...)；ywtMod.cpp:439 return v（未回原函数）；仅当 v==nil 才 ywtMod.cpp:443 return aj(tm2, judgeType, ...) | 【实测·代码级】 |
| H2 | "手动会加血"是在**判定开关关闭**时观察到的（走 443 原函数，H1 不成立）；自动时开关是开的 | 需日志 [Ywt] AJ pick=... 与 AJ skip 计数比对 | 【待验证】 |
| H3 | 自动命中被 play_ui:GetKeyResult() 判成 Miss 走 035:449 DoHit(Miss,1,false)，Miss 档数值极小/为负，视觉上"没加血" | 035:433-449（nil→Miss 分支） | 【待验证】 |

**修复方向（仅静态建议，本阶段未改代码）**：让判定包装在返回伪造判定的同时补一次血量结算——
1. 首选：包装里 local v = pickJudge(...) 后调 tm:OnAdjustJudge(v)（已存在、自带 min/max、刷 shield、抛 UI 事件），再 return v；
2. 或在 DoHit 之后补 tm:OnAdjustJudge(judge)；
3. 或在更外层包 DanceKeyPressMode.DoHit（035:86 声明点），判定与血量一处改完，避免两处漂移。
风险：OnAdjustJudge 内部还会 AddMyEnergy 之外的副作用需一并确认（015:748 在 AdjustJudge 里，不在 OnAdjustJudge 里，故补调 OnAdjustJudge 不会重复加能量）。
