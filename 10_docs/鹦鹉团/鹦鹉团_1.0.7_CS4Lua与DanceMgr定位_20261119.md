## 0. 三条结论先看

1. **CS4Lua.InputMgr 不是输入注入器，是键鼠回调注册器**（【实测】）。它返回的 InputManager 全类 13 个成员里**没有任何** Simulate / Fake / Virtual / Press / Touch / Click / Trigger / Dispatch —— 自动跳舞无法从这条 API 注入输入。
2. **DanceMgr / DanceVM / RhythmMasterConstants 在 C# 里都不存在**（dump.cs 各 0 命中）。CSys.* 是 **Lua 模块路径**（dance 已核实，本轮回读后采纳）。"从 DanceMgr 反查判定"这条路不成立。
3. **⚠️ Lua 层既有结论需撤回重做**：dance 的 .raw 是"每个 bundle 只抽了 1 个 chunk"，判定真正可能的落点（RhythmMasterMode.lua / RhythmMasterVM.lua / RhythmKeyItem.lua）从未被抽取。详见 §6，**补齐前不要按"判定在 C#"定挂点**。

### 6.2 补抽为何失败（技术边界）

bundle 内 payload 不是明文：

- 源路径串 LuaConfigTemp\lua_csys_dance\DanceActor.lua 在 bundle 里 find = **-1**（明文只出现在 bundle 索引区）；
- .raw 与 bundle 同偏移切片逐字节比对：前 18 字节相同，之后 8,653/9,376 字节不同；
- 每个 chunk 前有 10–13 字节自定义头，形如 4d 18 40 40 c0 [len] 00 00 f6 04，按长度推算的边界与下一个 magic 位置不能稳定对齐；
- 直接按 \x1bLuaS 暴力切片再喂 lua53_dis.py：lua_csys_dance 的 127 个 magic 命中**无一解析成功**（bad constant tag / IndexError）⇒ 命中绝大多数是密文巧合。

⇒ 需要 dance 的解密器/抽取脚本，或他全量重抽。按 AGENTS §3.2"禁止重造"，本轮不写第二套解码器。

## 7. 对 C1 / C2 的答复

### 7.1 C1：远端热更 Lua / 模块数

- **bundle 层能对上**：assets/Android/FileList.json 的 Files = 122 条（121 个 lua_*.unity3d + AssetMap.json）；APK assets/Android 下 lua_*.unity3d = 120 个（2 条差异待核）。Bundles 数组 918 条为其它资源。【实测】
- **chunk 层完全对不上**：真实 .lua 文件数 = 各 bundle 内文件名之和（strings 可枚举），远大于 111。
- 所以"进关后加载 APK 外 chunk"**无证据**；LuaManager._LuaLoader 只证明**通道存在**，不证明实际下发。
- 证伪方法（给 dance）：运行时枚举 LuaEnv 已加载 chunk 名，或 hook require / CustomLoader 记录每次请求的模块名与命中来源（APK / 远端），与 strings 枚举集合做差集；差集非空才说明有远端下发。

### 7.2 C2：服务端判定能否静态区分

**不能**，需运行时。判据按成本排序：

1. 补齐 Lua 后先看 RhythmMasterMode.lua / RhythmMasterVM.lua 有无本地判定（时间差比较、档位赋值、combo 自增）—— 有则判定=本地，服务端只收结果；
2. 抓包看 18756（KeyCommit 系）/ GASCommitOperationReq 的发送时序与条数：逐 key 上报 ⇒ 服务端逐条校验；局末一次上报 ⇒ 本地算、服务端只收（呼应 Lua 侧 ReqEndStage 带 danceGrade）；
3. 断网打一局：仍出 perfect/great/miss 且只结算失败 ⇒ 判定本地。
