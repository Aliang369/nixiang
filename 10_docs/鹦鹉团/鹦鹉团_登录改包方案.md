## 0. 三个必答问题（lead 问）

### ① 走哪条轨：**A 轨 · 静态改 dex（改包法）**，不走运行时 SPI

依据（实测，非推断）：

| 判据 | 实测结果 | 证据 |
|---|---|---|
| TapSDK 是否可达 | **可达**，且两个 dex 都有 | `smali_classes11` 1788 个 `com/taptap/sdk/*` smali、`smali_classes2` 1142 个（同一 SDK 被 multidex 切开） |
| 四个锚点类是否都在 | **全部命中** | `smali_classes11/com/taptap/sdk/{kit/internal/utils/TapSignKit, initializer/repository/GatekeeperRepository, initializer/service/InitializerServiceImpl, login/impl/ui/fragment/DefaultTapLoginFragmentProvider}.smali` |
| 是否有壳挡住静态改 | **无壳** | recon 实测：jiagu/nesec/DexHelper/mobisec/tprt/mocika/toolChecker/shellinfo 全 0 命中；13 dex 明文可反编译 |
| 换个说法：SPI 能不能替代 | **不能** | SPI（`core.TapTapWebLogin`）只改「选哪个 fragment/handler」，**改不了 `TapSignKit.getSign` 的返回值**，而签名回灌是服务端校验的唯一解（见 §2 第 4 步）。本包服务端校验成立 ⇒ 必须动 dex |

**结论**：A 轨四步（+ 本包特有的第 5 步）。SPI 只在「SDK 关进加密 payload」时才是正路，本包不属于该情况。
SPI 仍保留一处兜底用途：若 UX 上要「连网页登录都不让回落到客户端」，可另加 `games/ywt/GameHookImpl` 调 `core.TapTapWebLogin`（二者可共存，SPI 是冗余保险，不是必需）。

### ② 渠道参数密文（`assets/quicksdk.xml` 58,149 B）：**不解密，也不短路 QGSDK**

理由（代码反推）：

1. TapTap 初始化根本不读 manifest 里的 `TAP_PAGE_ID` 占位符。真正入口是 QGSDK 自己：
   `com/quickgamesdk/manager/ThirdManager.smali:911` `initTaptap(Landroid/content/Context;)V`
   → `QGConfig.getmTapID()` / `QGConfig.getmTapToken()`（:925/:930）→ `new TapTapSdkOptions(...)`（:952）
   → `com/taptap/sdk/core/TapTapSdk;->init(Context, TapTapSdkOptions, TapTapSdkBaseOptions[])`（:990）。
   ⇒ clientId/clientToken 是 QGSDK 运行时解密后再喂给 TapTapSDK 的，**改包法完全不触碰这层**，改完照常初始化。
2. **不能短路 QGSDK 直接调 `TapTapLogin`**：业务侧 uid/token 不是 TapTap 的账号对象，而是 QGSDK 中台换出来的
   `com.quicksdk.entity.UserInfo`（见 ③）。绕过 QGSDK 就绕过了换票，游戏侧拿不到 `userToken`，等于登录失败。
3. 需要动的只有 `assets/quicksdk.xml` 之外的**纯 SDK 内部判定**，与渠道配置无关。

### ③ 登录态从哪来、交给谁（类名 + 方法，全链已核到 smali 行号）


| 1001 错误码 | 本包 smali 内**无** `0x3e9` 常量（只有 WebSocket 的 CLOSE 码） | 1001 由 native `libtapsdkcore.so` 侧产生，不在 dex |

### 门闩为什么必须改（链路证据）
`TapTapLogin.smali:103 loginWithScopes` 第 5–9 行 → `TapSdkChecker.checkInitialize$default(checker, false, 1, null)`
（mask=1 ⇒ 布尔参数取默认值 **true**）→ `TapSdkChecker.checkInitialize(Z)Z`（:123）→ `InitializerServiceImpl.checkInitialize(Z)Z`（:78）
→ 内部依次判 `TapTapKit.isInitialized()`、`TapTapSdkInitializer.Companion.isAttached()`、`isGatekeeperLoadedSuccessfully()`；
任一项 false → 返回 false → **`loginWithScopes` 直接 `return-void`**，连登录界面都不出现。

而 `GatekeeperRepository$initialize$1$networkData$result$1.smali:223` 把 `TapSignKit.getSign(context)` 塞进
`GateKeeperRequest("android", packageName, signature)`（:230）上报 TapTap 服务端；服务端按登记的证书指纹比对，
改签包必然 `INVALID_CLIENT` → `GatekeeperRepository$initialize$1.smali:309-332` 把
`loadGatekeeperSuccess=false` + `gatekeeperError=…` + `showErrorToast(...)`。
⇒ **这就是「改完点登录没反应」的根因**，也是「只掐弹窗没用」的根因。

## 2. 七点改动清单（给 builder，逐条可直接落脚本）

> 全部锚点：`03_decompiled/鹦鹉团/apktool_1.0.7/smali_classes11/com/taptap/sdk/`
> 共用前提：只改方法体，**保留原 `.registers/.locals`**（改小值 smali 汇编会报 `requires at least N registers`）。

### P1 · 门闩恒放行（必需）
- 文件：`initializer/repository/GatekeeperRepository.smali`
- 方法：`.method public final isGatekeeperLoadedSuccessfully()Z`（第 431–438 行）
- 原体：`iget-boolean v0, p0, …->loadGatekeeperSuccess:Z` / `return v0`
- 改法：
```smali
.method public final isGatekeeperLoadedSuccessfully()Z
    .locals 1
    const/4 v0, 0x1
    return v0
.end method
```
- **不推荐**直接改 `InitializerServiceImpl.checkInitialize` 恒 true：那会连带绕过「SDK 未初始化」保护，
  在 `TapTapSdk.init` 尚未完成时可能让后续接口在空指针上崩。改 `isGatekeeperLoadedSuccessfully` 才是精准点
  （`checkInitialize` 里另外两项 `isInitialized/isAttached` 是真实健康判据，应保留）。

### P2 · 验签失败弹窗掐掉（必需，防「弹窗骚扰」与其它错误路径）
- 文件：同 P1
- 方法：`.method private final showErrorToast(Lcom/taptap/sdk/common/network/throwable/TapNetworkException;)V`（第 319–357 行）
- 改法：方法体首插 `return-void`，**保留 `.locals 3`**（原体确实用 v0/v1/v2 三个寄存器）
- 另一处可选：`showGatekeeperError()V`（第 440 行起）会弹「当前应用还未初始化」——**不建议动**，
  它只在 gatekeeperError==null 时走，属真异常路径，动了会掩盖后续排错信息。

### P3 · 登录入口恒 Web（必需）
- 文件：`login/impl/ui/fragment/DefaultTapLoginFragmentProvider.smali`
- 方法：`.method public provide(...)Landroid/app/Fragment;`（第 94–246 行）
- 锚点：第 184 行 `aget v2, v3, v2`（取 `$EnumSwitchMapping$0[loginType.ordinal()]`）
- 改法：**在第 184 行之后、第 186 行 `const/4 v3, 0x1` 之前**插入一行：
```smali
const/4 v2, 0x3
```
- 效果：后续 `if-eq v2,v3(1) :cond_2`、`if-eq v2,v3(2) :cond_1` 均不命中，`if-ne v2,v3(3) :cond_0` 也不成立
  ⇒ 顺序落到第 198–209 行的 `WebLoginFragment.Companion.newInstance(request, callback)`。
- 判据：全包只有这一处 `newInstance(ClientLoginFragment)`；改后该分支不可达即彻底断开客户端 SSO。

### P4 · 签名回灌（**必需，缺它必 1001**）
- 文件：`kit/internal/utils/TapSignKit.smali`
- 方法：`.method public final getSign(Landroid/content/Context;)Ljava/lang/String;`（第 59–128 行，原体 70 行）
  原体链路：`getPackageManager()` → `getPackageInfo(pkg, 0x40)` → `signatures[0]` → `Signature.toByteArray()` → `CommonUtils.getMD5([B)`，含 try/catch。
- 改法：整段替换为
```smali
.method public final getSign(Landroid/content/Context;)Ljava/lang/String;
    .locals 1
    const-string v0, "27c2d8ca4e5703d9ad2a1ee39d2a859d"
    return-object v0
.end method
```
- **回灌值出处（已双重交叉核对，2026-11-19 本机实测）**：
  - `META-INF/AIAUTION.RSA` → DER **720 B** → `openssl x509 -outform DER` → `md5 -q` = `27c2d8ca4e5703d9ad2a1ee39d2a859d`
  - `apksigner verify --print-certs`（build-tools 36.0.0）→ `Signer #1 certificate MD5 digest: 27c2d8ca4e5703d9ad2a1ee39d2a859d` ✅ 两处相等
  - 证书主体：`CN=Meta48, L=SH, C=CN`，SHA-1 `35a8e7b1b9ffe25f3413be2955c9a06b022992c9`，有效期 2026-05-13 → 2051-05-07
- 判据：装机后 `logcat` 不出现 `TapSDK 初始化失败（1001）` / `包名、签名错误`。

### P5 · QGSDK 侧签名值回灌（**本包特有，两处，建议首版一并做**）
> 依据：`鹦鹉团_反篡改校验排查_20261119.md` §2.2/§4（已实测出「每请求必带 signMd5」，且 QGSDK 本地**无**任何比较）
- **为什么是两处**：QGSDK 有两条并行上报路径，取值来源不同：
  - **路径 A（覆盖最广）**：`smali_classes7/com/quickgamesdk/net/QGParameter.smali:102-106` 在参数基类里 put `"signMd5"`，
    值来自 `QGSdkUtils.getApkSign(Context)`（`QGSdkUtils.smali:1179-1232`）→ `com.game.apkverify.Check.getSignInfo(ctx)[2]`（native）。
    ⇒ 所有 QGSDK 接口（登录/初始化/支付）都带这个值。
  - **路径 B**：`smali/com/quicksdk/net/a.smali:3319`（HashMap `"sign_md5"`）与 `smali/com/quicksdk/utility/b.smali:268`（JSON `"sign_md5"`），
    取值 `com/quicksdk/utility/k.smali` 的 `.method public static a(Landroid/content/Context;)Ljava/lang/String;`
    （**smali 第 62 行起**，取签名在 :81；别改到同文件无参的 `a()Ljava/lang/String;`（:21），那是另一个用途）。
- **改法（两个 Java 一行常量，均与 P4 同形）**：
  1. `smali_classes7/com/quickgamesdk/utils/QGSdkUtils.smali` `getApkSign(Landroid/content/Context;)Ljava/lang/String;`
     → 方法体换成 `const-string v0, "27c2d8ca4e5703d9ad2a1ee39d2a859d"` / `return-object v0`（保留原 `.locals`）
  2. `smali/com/quicksdk/utility/k.smali` `a(Landroid/content/Context;)Ljava/lang/String;` → 同上
- **为什么改 Java 而不是 native**：真正的值来自 `libqkcheck.so` 的 `getSignInfo[2]`；patch Java 两个取值点即可覆盖全部消费者，
  不必动 so（删/改 so 都不划算，且 `QuickSdkApplication` 有 exists 兜底，改 so 收益为零）。
- **风险分级待验证**：QGSDK 中台是否据此拒绝登录**未知**（本地代码只证明「值被上报」，无任何本地比对）。
  建议首版就做（同值、零副作用）；若首版只做 P1–P4 也能区分：失败会是 QGSDK 登录回调 `onFailed`／`thridLogin` 报错，
  而不是 TapTap 的 1001。

### P6 · 单点兜底：`com.game.apkverify.Check.getSignInfo` 由 native 改 Java 常量实现（lead 2026-11-19 裁决批准）

**为什么只改 P5a/P5b 不够（链路证据）**：
- `P5a` 改的是 `QGSdkUtils.getApkSign`，而 `QGSdkUtils.getApkSign` **只是** `[2]` 这一个元素的消费口子；
- `smali/com/quicksdk/net/a.smali:6107` **直接**调 `Check.getSignInfo(...)[String]`，并在 :6139-6165 依次取
  `[0]`→`signSubject`、`[1]`→`signIssuer`、`[2]`→`signMd5`、**`[3]`→`sign_sha1`**，**完全不经过** `getApkSign`；
- ⇒ 若 QGSDK 中台校验 `sign_sha1`（官方 cert SHA1 `35A8E7B1…`），P5a+P5b 都漏；
- ⇒ 改 `Check.getSignInfo` 是**唯一能一次覆盖 4 个字段**的点，且只动 1 个类。

**改动前的事实核查（全部实测）**：
| 项 | 结论 |
|---|---|
| 引用点 | 全包仅 3 处：`net/a.smali:6056`（getAPKCharacteristic）、`net/a.smali:6107`（getSignInfo）、`QGSdkUtils.smali:1190`（getSignInfo）；jadx 侧 0 处；无反射调用 |
| JNI 注册方式 | `libqkcheck.so` 内**无** `JNI_OnLoad`/`RegisterNatives` 串，纯 `Java_com_game_apkverify_Check_*` 静态命名 ⇒ 去掉 `native` 不会留下注册悬空 |
| 返回值格式 | `getCertificateInfo` 先 `get_digest("MD5")` 再 `get_digest("SHA1")`；`get_digest` 在 0xfb4 引用 `.rodata 0x1f80` 的 `"0123456789ABCDEF"` 表手工转十六进制 ⇒ **大写** |
| 数组顺序 | `[0]=getSubjectDN().toString()`、`[1]=getIssuerDN().toString()`、`[2]=MD5`、`[3]=SHA1`（与 `net/a` 的 4 个 key 一一对应） |

**改法**（同签名同返回类型，只去掉 `native` 并给方法体；原声明 2 行 → 32 行）：
```smali
.method public static getSignInfo(Ljava/lang/Object;)[Ljava/lang/String;
    .locals 3

    const/4 v0, 0x4

    new-array v0, v0, [Ljava/lang/String;

    const/4 v1, 0x0

    const-string v2, "C=CN,L=SH,CN=Meta48"          # subject（RFC2253）

    aput-object v2, v0, v1

    const/4 v1, 0x1

    const-string v2, "C=CN,L=SH,CN=Meta48"          # issuer（同值）

    aput-object v2, v0, v1

    const/4 v1, 0x2

    const-string v2, "27C2D8CA4E5703D9AD2A1EE39D2A859D"   # MD5（大写，照 native 格式）

    aput-object v2, v0, v1

    const/4 v1, 0x3

    const-string v2, "35A8E7B1B9FFE25F3413BE2955C9A06B022992C9"  # SHA1（大写）

    aput-object v2, v0, v1

    return-object v0
.end method
```
- `getAPKCharacteristic` **保持 native 不动**（它算 `MD5(certSHA1 + 入参 + 盐 526b7295…)`，硬要在 Java 里复刻容易失真，且它只填 `certificates` 一个字段）。
- 因该类仍有 native 方法，`QuickSdkApplication` 照旧 `System.loadLibrary("qkcheck")`，so 不能删。

**大小写口径（重要，两套 SDK 不同）**：
| 侧 | 取值来源 | 格式 | 常量 |
|---|---|---|---|
| TapTap（P4） | `CommonUtils.getHashString` → `Integer.toHexString` | **小写** | `27c2d8ca…859d` |
| QGSDK（P5a/P5b/P6） | native `get_digest` → `"0123456789ABCDEF"` 表 | **大写** | `27C2D8CA…859D` / `35A8E7B1…92C9` |
> ⚠️ 本轮据此把 P5a/P5b 的常量从早期草案的小写改成**大写**（否则 P5a 与 P6 的 `[2]` 会不一致）。

**证据级别**：引用点/无 RegisterNatives/大写表均为**实测**（grep + objdump）；「中台真的校验「仍在 §6 待验证。
