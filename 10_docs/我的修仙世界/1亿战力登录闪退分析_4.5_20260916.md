# 我的修仙世界 4.5 一亿战力登录闪退分析（2026-09-16）

> 样本：TapTap 4.5 / vc45 星光正式包，MD5 `0b24f8647e4d697204db95bf2060e90c`。  
> 游戏载荷与原版一致，分析对象为包内 `lib/arm64-v8a/libil2cpp.so`。  
> 结论等级：静态代码证据为“高置信”；具体用户是否命中该分支仍需一条运行时日志或原版 A/B 验证。

## 1. 结论

这不像“修改器 Hook 越界/空指针导致的随机闪退”。原版客户端在 `OtherButtonPanel.UpdatePower` 中存在明确的战力上限检查：

- 读取 `PlayerAttrMgr.power`，字段偏移 `+0x198`，类型 `long`。
- 在对应条件分支中，`power >= 100000001` 时直接调用 `UnityEngine.Application.Quit()`。
- 后续还有 `200000001`、`300000001`、`500000001`、`1000000001` 等分级阈值。
- 星光包的 `Application.Quit` Hook 只记录日志并继续调用原函数，因此不会阻止这次主动退出。

代码上最直接的归因是：**直接退出来自游戏原版的战力上限/反作弊检查；修改器没有直接写入 `PlayerAttrMgr.power`，但无限资源等功能会让账号更容易达到这个检查阈值。**

## 2. 静态证据

### 2.1 战力字段

`06_dumped/我的修仙世界/il2cpp_dump_4.5/dump.cs`：

```text
public class PlayerAttrMgr : BaseManager<PlayerAttrMgr>
    public long power; // 0x198

public class OtherButtonPanel : BasePanel
    private void UpdatePower() // RVA 0x1320DEC
```

### 2.2 原生分支

`OtherButtonPanel.UpdatePower` 内反汇编的关键路径：

```asm
; 100,000,001 = 0x5F5E101
0x1321144  ldr x8, [x0, #0x198]       ; PlayerAttrMgr.power
0x1321150  cmp x8, x9
0x1321154  b.lt 0x1321178             ; power < 100000001，跳过退出
0x1321174  bl 0x26E0120               ; Application.Quit()
```

同函数后续阈值：

```text
200000001
300000001
500000001
1000000001
```

### 2.4 前置分级条件

`UpdatePower` 在同一方法内多次比较一个前置整数值，再决定检查哪一档战力上限：

```asm
0x13210C8  cmp w8, #4
0x13210CC  b.gt 0x1321178    ; 大于4，跳过100M检查
0x1321194  cmp w8, #7
0x1321198  b.gt 0x1321244    ; 大于7，跳过200M检查
0x1321260  cmp w8, #9
0x1321264  b.gt 0x1321310    ; 大于9，继续跳过后面的检查
```

按当前反汇编的结构，可以得出这些分支特征：

- 前置值不大于 4：先检查 `>=100000001`。
- 前置值在 5 到 7：跳过 1 亿检查，下一档是 `>=200000001`。
- 前置值在 8 到 9：跳过前两档，下一档是 `>=300000001`。
- 前置值大于 9：当前代码会跳过这组五档战力退出分支，到达方法末尾。

因此“超过 1 亿必定退出”并不严格成立。准确说法是：命中第一档条件的账号，在战力达到 `100000001` 时会被这组检查退出；更高档账号的 1 亿战力不会触发第一档，但仍会受 2 亿、3 亿、5 亿或 10 亿档限制。

同一区块还会先调用 `GetCountInfo(...)`，所以它不是一条全局无条件的“战力大于某个数就杀进程”。目前仅凭静态代码无法把这个前置整数值安全命名为具体游戏字段；不能在文档里强行写成 VIP、境界或充值等级。

BinGe 壳自身的探针字符串也把这一范围标为：

```text
0x1320F78~0x13214A4 = UpdatePower
0x13F8xxx/0x13F9xxx = 属性战力检测
```

### 2.3 星光的退出处理

`mod菜单/starry-mod-menu/app/src/main/jni/Games/WdxsjMod.cpp:448`：

```cpp
static void Hooked_ApplicationQuit() {
    if (!g_logQuit.exchange(true)) {
        LOGW(WDXSJ_LOG " Application.Quit observed; forwarding to game");
    }
    if (g_origApplicationQuit) g_origApplicationQuit();
}
```

这不是崩溃兜底，而是明确放行原始退出。命中战力检查后，游戏会正常结束进程，外观上表现为“点登录游戏就闪退”。

## 3. 与三项修改器的关系

逐项核对当前实现：

- `HundredDamage`：只修改传给 `BattleMgr.HurtShow` 的 `hurt` 参数，没有写 `PlayerAttrMgr.power`。
- `Invincible`：只吞掉玩家 `NowHp` 的扣减，没有写战力。
- `Infinite Currency/Items`：修改 `GetItemNum` 的异常负值、`CheckConsume(List)` 的返回值，没有直接写 `PlayerAttrMgr.power` 或 `+0x198`。
- `Application.Quit`：没有吞掉退出，也没有制造新的退出。
- 源码中没有 `PlayerAttrMgr`、`0x198` 或战力字段的直接写入路径。

因此要区分两件事：

1. **直接原因**：原版客户端的 `UpdatePower` 阈值分支主动调用退出。
2. **间接形成条件**：无限货币道具等功能降低了资源消耗限制，可能让账号成长到正常玩法难以达到的 1 亿战力；达到阈值后，这个原版检查才被触发。

“修改器导致了一个 Hook 级闪退”这个说法不符合当前静态证据；“修改器促成了触发原版上限检查的账号状态”这个说法是成立的，但目前仍需同一账号的日志或原版包对照来把因果确认到 100%。

## 4. 一个很实用的判定方法

复现前抓取日志，重点只看以下几类：

```text
Application.Quit observed; forwarding to game
FATAL EXCEPTION
Fatal signal
SIGSEGV
SIGABRT
```

判定规则：

- 出现 `[wdxsj] Application.Quit observed; forwarding to game`，且没有 `FATAL EXCEPTION` / `SIGSEGV`：
  基本可确认是原版主动退出分支，优先检查 `PlayerAttrMgr.power` 是否已达到阈值。
- 只有 Java/native 崩溃栈，没有 `Application.Quit` 记录：
  说明是另一条问题链，不能把它归到这里的战力阈值。
- 同一账号换回 TapTap 原版，如果仍然在进入主界面时退出：
  证明触发条件来自账号/存档数据，而不是星光 Hook 内存错误。
- 关闭三个功能开关后仍然退出：
  也不能推翻上面的结论，因为战力已经保存在账号数据里，检查会在进入主界面时再次执行。

## 5. 结论边界

当前能确定的：

- 100M 附近确实存在原版主动退出分支。
- 阈值是 `100000001`，不是严格等于 `100000000`；显示达到 1 亿后，下一次战力刷新或增加 1 点即可命中。
- 退出不是当前 `Application.Quit` Hook 新增的副作用。

当前不能仅靠静态代码确定的：

- 这个具体用户一定命中了哪一个分支。
- 用户看到的“闪退”前是否留下了完整崩溃日志。
- 账号当前 `PlayerAttrMgr.power` 的精确存档值。

在拿到上述日志前，不应对战力字段做盲写、清存档或全局吞掉 `Application.Quit`。那会把“明确的主动退出”变成更难定位的状态异常。

## 6. 1 亿战力下不触发这条退出的条件

按当前静态代码，可能不触发 1 亿档退出的情况只有三类：

1. `PlayerAttrMgr.power <= 100000000`。这是最直接、最安全的边界，界面显示 1 亿时如果真实值仍是 100000000，下一点战力才跨线。
2. 账号前置分级值大于 4。此时会跳过 1 亿分支，但会进入 2 亿档，所以只是把上限抬高，不是取消限制。
3. 前置分级值大于 9。当前这段代码会连续跳过 100M、200M、300M、500M、1B 分支；但这是静态分支结果，不能证明该状态在线上正常可达，也不能排除同方法里更早的其他退出检查。

从修改器实现角度，可行但有风险的技术路线是：只在 `Application.Quit` 的调用来源属于 `UpdatePower` 这组战力阈值时跳过原函数。

对应的 `BL 0x26E0120` 调用点包括：

```text
0x1321174   100M 档
0x13210A0   前置计数档
0x1321240   200M 档
0x132130C   300M 档
0x13213D8   500M 档
0x13214A4   1B 档
```

更稳的做法不是全局吞掉 `Application.Quit`，而是在 Hook 里读取返回地址，只对这些来源做白名单拦截，其他退出照旧放行。此方案尚未实现、未构建、未测试；它绕过的是游戏原始退出策略，封号风险高于仅关闭功能开关。
