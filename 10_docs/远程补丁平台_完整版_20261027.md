## 0. 一句话目标与用户口径

- 现状痛点：同一游戏版本内，战斗闪退／功能失效／新增功能都要**重打 APK、重传、玩家重下整包**（工作区实际包体数百 MB 到 2.5 GB）。
- 目标形态：**壳 APK 冻结**；游戏 native 逻辑（`libstarry_magic.so`）**远程按变体下发**，玩家**打开游戏即自动取到并加载**，不再点「检查更新」、不再整包重下。
- 用户 2026-10-27 原话口径：「**就是把现在的热更改了，改成启动就加载热更的**」⇒ 见 §2 的 D11 修订提案。

## 1. 与现行机制的关系（别混淆的三个「热更」）

| 名词 | 谁的热更 | 我们的动作 | 现行状态 |
|---|---|---|---|
| 官方热更（游戏资源/DLL） | 游戏厂商 | 只检测换代（指纹三查），据此切 so 变体 | 已有：`skill/re-extract/hotupdate-fingerprint-recheck.md`；无限升级已实战（`Exec call len/fnv` 判据） |
| 我们的 OTA（`/v1/ota/*`） | 星空层 | 下发整份 `libstarry_magic.so` | 已有 70% 地基：`ota_store.publish()`、`PlayOtaManager`、`StarryNativeLoad`、`STARRYSTAMP` 守卫；**缺自动拉取、缺变体、缺原子槽、缺启动即加载** |
| 我们的载荷加密（P2-2） | 星空层 | 功能 JS/DLL 只以密文进包，票派生钥解封 | 已接入 3 个游戏（勇士之心 js / 无限升级 bins ×2） |

> 本平台 = 把第二行做成「启动即就绪」，并与第三行的载荷链路合流（§11）。

## 2. 「启动就加载」的确切语义 + D11 修订提案（需要拍板）

### 2.1 三种时序，只能选一种口径

| 方案 | 行为 | 首启/换版体验 | 代价 |
|---|---|---|---|
| **S1 下次冷启生效**（现 D11） | 本次启动用包内/旧 so，后台下完，**下次**冷启切新版 | 要重启一次才用上新功能 | 零风险，但用户体感就是「改了没生效」 |
| **S2 注入前等待（建议）** | 启动早期**并发**拉 manifest+so（+票），在**注入点前最多等 T 秒**；等到即本次生效；等不到用基线兜底继续在后台下 | 多数情况**本次启动就是新版**；弱网/断网落基线 | 首启最多多等 T 秒（建议 5–8 s，可配置；无限升级已实证「等票 3 s」有效） |
| S3 首启强制阻塞 | 无超时等下载完成 | 首启可能长时间黑屏 | 不可接受 |

**提案（D11′）**：采用 **S2** ——「启动即拉取、注入前等待、超时兜底基线、后台续下」。
这同时**顺带修掉当前最烦的现象**：DLL/JS 已注入但票或载荷晚到 ⇒ 整局无效、必须重启（§9.2 有实测根因）。

### 2.2 等待点只有两个（都必须早于注入）

- Cocos/JS 类：`se::evalString` 注入点（`HookedEvalString`）之前。
- DLL/Unity 类：补丁 DLL 装载点（`Exec call` 钩子）之前。
- 传票路径与载荷拉取**并行**，不要串行叠加等待时间。

## 3. 现状盘点（代码锚点，2026-10-05 盘点 + 2026-10-27 复核）

已具备：

- 后台每游戏一份 latest；`ver > local` 才更新；逐文件 sha256 相同跳过下载：`auth-server/app/services/ota_store.py` `publish()`、`PlayOtaManager.downloadAndApplyLocked()`。
- 下载后 sha 校验 + HMAC 验签：`PlayOtaManager.java`、`Main.cpp mb_nativeVerifyOtaSig`、`ota_store.py sign_payload()`。
- 有 OTA so 就只加载 OTA（不回落包内）：`StarryNativeLoad.java`；乐变双 classloader 有独占副本逻辑。
- 覆盖安装后按 `STARRYSTAMP` 比较包内 so 与 OTA so：`PlayOtaManager.invalidateOtaIfApkUpdated()`、`OtaSoStamp.java`（FW-13/FW-14 已修构建戳被 `--gc-sections` 回收的问题）。
- 服务端按 IP 限流、so 下载需卡密会话、manifest 可匿名查：`security_guard.py`、`routers/ota.py`、`config.py`。
- 加固侧（2026-10-27 复核，可直接复用）：`harden_apk.py check`（C1–C9）+ `harden_gate.sh` 一行接入、装机凭证 `09_test/<游戏>/harden/<md5>.stamp`、载荷 sha 按 `game_id` 落库（`GET/PUT /v1/admin/games/{id}/payload`）、`/v1/build/payload-status`。

缺口（= 本方案的施工面）：

- **自动拉取未接启动链**：只有设置页手动「检查更新」（`NativeMenuController.startPlayOtaCheck()`）；启动只应用本地已有 patch.json（`MenuService.bootstrapNativeIfNeeded()`）。
- manifest 只有 `game_id + ver`：无游戏版本/metadata 指纹/ABI/shell API 绑定 ⇒ 官方换代/多渠道会错配。
- 落盘非原子（删旧 → 逐个 rename），服务端 publish 也是 unlink+move，无断电保护。
- 后台只有 latest，无历史/LKG/撤销语义；客户端「清除补丁」是整目录删。
- 验签 HMAC，密钥在服务端与 so 里各一份（混淆级，不是安全边界）。
- `patch.json` 只有 hzsj 有真正应用入口，其他游戏下载后被忽略（D10 定案：整份 so，移除该通道）。
- 菜单功能项编译在壳内 ⇒ 新增功能仍要重发 APK（P1 动态菜单解决）。

## 4. 核心契约（定案摘要，细则见讨论稿 §5）

### 4.1 变体键（六元组，缺一不可）

```text
game_id + channel + game_fingerprint + abi + shell_api + payload_ver
```

`game_fingerprint` 至少覆盖：游戏版本号 + 关键 so（如 `libil2cpp.so`）sha256 + `global-metadata.dat` + 官方热更资源版本/内容哈希（口径＝热更指纹三查）。

### 4.2 manifest v2 字段（只增不改）

变体键字段、`ver`、`payload_id`、`so_sha256`、`size`、`abi`、`game_fingerprint`、`game_ver`、`min_shell_api`/`max_shell_api`、`sig_hmac`（旧客户端）、`sig2`（Ed25519）、`mandatory`、`restart_policy`、`status`(draft/active/revoked)、`revoked_vers`、下载地址。

### 4.3 其他已定契约（不在此重复正文）

| 项 | 定案 |
|---|---|
| 壳粒度（D1） | 一套共享壳源码；每游戏/每游戏版本一份构建配置与冻结产物；不为游戏 fork 代码 |
| 基线 so（D2） | 内嵌完整当前逻辑，slot 0 兜底；OTA 单活动槽优先 |
| 插件 ABI | `starry_plugin_init(const starry_host_api_v1*)`，只走 C 接口；指纹/ABI 不匹配直接拒绝，不兼容 |
| 动态菜单 | feature schema 随 manifest 下发，插件按 `id` 注册处理器；菜单串自检与 manifest 一致 |
| 签名（D6→D18） | 终态 Ed25519-only；payload 私钥**离线**签、撤销用服务端**在线控制钥**单独签；`key_id` 轮换；授权 grant 密钥与 OTA 密钥分离；**APK keystore 不变**（否则 SSAID→设备号漂移） |
| 多版本路由（D14） | 匹配优先级：精确指纹 >（game_ver+channel+abi）> baked_build_id；全不命中返回「无补丁」，**禁止跨变体兜底** |
| 回退（三通道） | 本地（加载/自检/崩溃计数）→ 基线；服务端撤销（明确 none/revoked 才回退，网络错误不算）；更高 ver 替换 |
| 检查节奏（D16） | 冷启动查一次 manifest，本地节流 1 分钟；manifest 30–60 s TTL + ETag；长会话可选 30–60 min 轮询（仅预取） |
| 灰度/遥测（D8/D9） | 不灰度只全量；本期零客户端回传 |

## 5. 客户端运行时（含「启动即加载」改造点）

### 5.1 启动状态机（S2 口径）

1. **T+0 早期（Application/Provider）**：读槽位状态 + boot 计数；**并发**发起 ①票续期 ②manifest 检查（节流 1 min）。
2. **识别**：`game_id / channel / abi / game_fingerprint / shell_api`；指纹不匹配直接放弃远程 so（用基线）。
3. **预取**：manifest 有匹配更新 ⇒ 后台下载（无登录门槛，D7/D15）；失败退避重试，不阻塞。
4. **注入前闸门**（唯一新增阻塞点）：`evalString` / DLL 装载前 `wait_ready(T)`；就绪条件＝（票可用 ∧ 载荷/so 可用）或 T 超时。
5. **校验**：sha256 + 签名 + 指纹 + ABI + shell_api 五重通过才落盘。
6. **落盘**：写 `staged/` → fsync → 复核 → **原子替换** OTA 槽；基线永不作废。
7. **生效**：本次启动就用（S2）；若不是本进程内下载完成，则下次冷启生效，菜单显示「已就绪/重启生效」。
8. **自检 + 防砖**：加载后跑插件自检（关键钩子是否装上、feature 是否注册）；加载前写「本次尝试版本」，连续失败切基线并拉黑。
9. **离线/首装**：基线 so 保证无网、未登录也能进菜单；OTA 只做覆盖升级。

### 5.2 落盘布局（不变）

```text
files/starry_ota/{game_id}/
  current                 # 指针：ota / baseline
  boot_state.json         # 尝试计数、最后失败原因、已应用最高 ver
  ota/{manifest.json, libstarry_magic.so}
  staged/                 # 下载与校验中的临时目录（校验后原子替换 ota）
```

### 5.3 提示策略

- 静默检查与下载；本次生效时不打扰；需重启时菜单一行「已就绪（重启生效）」。
- **移除**设置页「检查更新/清除补丁」，**不留隐藏入口**（D13）；应急只走服务端撤销 + 自动回滚。
- `mandatory` 可弹一次不可取消提示，仍不热替换。

### 5.4 兼容

- 保留乐变多 classloader 副本加载与包内兜底路径。
- `STARRYSTAMP` 语义升级为「壳内基线与 OTA so 的代际比较」。
- 不兼容旧客户端协议（D17）：游戏逐个迁移到新壳。

## 6. 服务端与后台

- 存储：内容寻址 blob（sha256 命名）+ 变体索引 + 发布记录；**每变体只留一个 latest**（D5）。
- 接口：变体 manifest 查询（匿名）、制品下载（公开直链 + Range/断点续传）、撤销列表下发。
- 下载层不做业务拦截/限流（D7/D15）；服务器只保留管理端鉴权、路径/上传校验、TLS、基础设施防护。
- 撤销语义：下架 = `status=revoked` 且保留记录；**404 一律不算撤销**；客户端成功检查后才回退基线。
- 原子性：发布 tmp → fsync → 原子切换 + 并发锁；blob 保留足够长的在途下载窗口（旧版变体 retire 后 blob 留 7 天）。
- 缓存分层：manifest 30–60 s + ETag；blob 长缓存（immutable）。
- 密钥：payload 私钥离线 + 撤销控制钥在线；两把公钥按 `key_id` 编进壳。
- 部署：直连 FastAPI 起步，CDN-ready；DAU ≥ 1000 或单次全量 ≥ 50 GB 时接对象存储 + CDN（D19）。
- 后台入口（D20）：复用现有「游戏补丁」Tab 改造 —— 列表变体化、发布只支持上传**本地已签名发布包**（zip：`manifest.json` + `libstarry_magic.so` + `manifest.sig`）、撤销/恢复、审计复用「操作日志」；页面不签名、不填 ver/note，私钥不出现于网页与服务端。
- 观测：只到服务端访问日志一级（下载量、404/429/5xx、撤销记录）；不做客户端遥测（D9）。

## 8. 验收（可执行清单）

- 同一壳连续发布 3 个 so 版本，L2 全过（P0 出口）。
- 人为投放坏包（加载即崩）⇒ 启动计数触发**自动回退基线**，用户可进游戏。
- 服务端撤销 latest ⇒ 客户端下一次成功检查后冷启回退基线（1 分钟内可发现，SLA 1–2 分钟）。
- 官方热更换代（`Exec call len/fnv` 变化 / bundle 版本变化）⇒ 指纹命中新变体；未命中返回「无补丁」，**不得**下发别的变体。
- 弱网/断网：注入前等待超时 ⇒ 基线可用、无崩溃、无 ANR。
- 覆盖安装新壳：`STARRYSTAMP` 正确清掉旧 OTA 槽；运行 so 与包内 so 一致（装机第二查）。

## 9. 风险与对策

| 风险 | 对策 |
|---|---|
| 坏 so 一发全量中招（D8 不灰度） | L1/L2/L3 + 启动计数 + 自动回退基线 + 撤销 + 更高 ver 快速修复，缺一不可 |
| 无遥测，坏版本发现慢（D9） | 接受项；靠用户反馈 + 服务端下载日志 + 快速撤销（日志/崩溃收集项目另立、已暂缓） |
| 游戏热更后错配 | 指纹硬闸 + 客户端本地校验 + 无匹配不下发 |
| 首启多等 T 秒引发卡顿抱怨 | T 可配置（默认 5–8 s）+ 只在「有匹配更新且未就绪」时等；基线兜底保证不黑屏 |
| 远程加载增加反检测面 | 沿用已验证加载路径；只在自有测试设备验证后全量 |
| 下载中断/断电 | `staged` 校验后原子替换；失败回退基线 |
| 带宽压力 | 公开直链走 CDN/对象存储；大文件不落 auth 服务 |
| so 被公开提取分析 | 接受项；签名+哈希+撤销保证不被伪造/错发，不做下载层拦截 |

### 9.2 顺带修掉的现网问题：「登录后功能不生效、必须重启」（实测根因，2026-10-27）

无限升级 vc1637 实证（`10_docs/无限升级/防御加固_vc1637_20261027.md` §13）：

```
00:09:33 hook installed
00:09:36 antiban baseline unsealed (防封 on / 功能 off, no v3 ticket)
00:09:47 [V2] s=1 m=ffffffff        ← 票 11 秒后才到位，已经晚了
```

⇒ 补丁 DLL **一进程只装载一次**，装载时没票 ⇒ 整局只有防封基线 ⇒ 用户必须重启。
本轮缓解＝装载前**等票最多 3 s** + 一次性 toast；根治＝本方案 §2 的 **S2「注入前等待」**（同一套「就绪闸门」同时覆盖票、载荷、so 三者）。

## 10. 分期落地（每阶段含文件级改动与出口标准）

### P0 启动即就绪闭环（本方案的核心里程碑）

改动面：

1. `PlayOtaManager`：新增 `checkAndPrefetchOnStartup()`（匿名 + 节流 1 min + 退避），从 `MenuService/StarryApp` 启动路径调用；移除手动入口相关 UI。
2. `StarryNativeLoad` / 注入点：新增 `starry_ota_wait_ready(T_ms)` 就绪闸门（票 ∧ so，或超时），C 接口给 native 侧。
3. 落盘原子化：`staged/` + fsync + 原子 rename + `current` 指针；`boot_state.json` 计数与回滚。
4. manifest v2 + 变体路由（服务端）；D10 移除 `patch.json` 通道；按 primary ABI 发布（D12）。
5. 服务端撤销/下架 + 「每变体一版 latest」；客户端识别 `status=none|revoked` 才回退。

出口标准：连续 3 个 so 版本 L2 全过；坏包自动回退；撤销演练通过；**首启/换版「本次启动即新版」在 2 台设备上实测达成**（弱网落基线不崩）。

### P1 动态菜单

feature schema 下发 + 插件按 id 注册；出口：新增功能不重发 APK，菜单串自检通过。

### P2 core/plugin 拆分

core so 稳定 ABI + 游戏插件 so；出口：新增一个游戏只发 so + 配置（除新包名外不产新壳）。

### P3 运营能力

CDN 接入、撤销/下架演练、发布审计。

## 11. 与另外三项能力（水印/上报/OTA 载荷下发）的关系

- 水印（P2-4，`10_docs/勇士之心/防御加固_P2后续三项_20261027.md`）：服务端按 `card_id` 算 `wm` 塞进票，客户端只显示 ⇒ 与本平台无耦合，可先做。
- 诱饵/异常上报（P2-3）：上报点写在共享 `SgPayload.h`/`SgIntegrity.h`；**D9 本期「零客户端回传」需要修订**才做（否则与遥测红线打架）⇒ 见 §12 待拍板项。
- OTA 载荷下发（P2-5）：与本平台是**同一件事的两个面** —— 本平台下发的是 so，P2-5 下发的是 so 内的功能载荷；建议**合流**：一次启动拉取同时取「so 变体 + 载荷密文 + 票」，共用 §2 就绪闸门。
