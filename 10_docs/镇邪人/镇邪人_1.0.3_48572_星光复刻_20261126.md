#### 3.3.1 兜底机制（结构派生 + 变体表 + hot 探针）

**为什么不用字面锚点**：混淆器每版重排变量名/模块别名，写死的字面锚点会整表失效，且 miss 时若只打 WARN 就放行原脚本，战斗四项会静默失效。故现行实现是「结构派生为主 + 变体表兜底 + 显式告警」：

> 1. **结构派生（根治）**：新增 `Games/ZxrDerive.h`，不再写死任何标识符，只认「语义形状」：
>    - 定点函数名 `FightChangeEntityHp` / `DamageCommonCalcFinal` / `CalcFinalAtkSpeedValue`（已知全部版本均存在，混淆器不改函数名）；
>    - 形参位置 + 语句模板；**混淆名与模块别名一律从 bundle 现取**；
>    - 命中前先校验「锚点全文在脚本里恰好 1 次」，不赌多命中。
> 2. **变体表（二级兜底）**：`gen_zxr_patch_header.py` 改为吃**多份 spec**，生成 `kZxrVariants_<hook>[]`（每钩子 1 条 insert + N 条锚点形状；insert 多份 spec 必须一致才放行）。现装 4 条全屏秒杀锚点形状（见 §3.3 表），伤害与攻速各 1 条。
> 3. **显式告警（C）**：`BuildHotPatch` 三个钩子任一失败即
>    - `W/Mod_Menu: [Zxr] hot-patch MISS: hooks failed: …`（写明哪个钩子、为什么）；
>    - 同时经 `ZxrHooks.logStatus` 打一条中文告警：「战斗补丁未命中热更脚本，四项战斗功能将静默失效（请重新出包）」；
>    - 从此每条功能日志带 `hot=` 探针：`hot=1` = 兜底已挂上、`hot=2` = 锚点全 miss（功能静默失效）、`hot=0` = 从未介入。

**执行顺序（唯一口径，代码即 `ZxrMod.cpp` 的 `BuildHotPatch`）**：① 结构派生 `derive=n/3` 优先 → ② 派生不全才查变体表 `variantTbl=<N>` → ③ 全 miss 记 `hot=2` + 双通道告警（英文 `hot-patch MISS` + `ZxrHooks.logStatus` 中文「请重新出包」），并记录 `derive=` 与 `variantTbl=` 两个数字。

**判据**：`[Zxr] hotfallback plan ok: derive=3/3 variantTbl=<N>` 表示三钩子全由结构派生命中；每条功能行 `splice=<n> hot=<0|1|2>` 中 `hot=0` 且 `splice=0` 表示包内 pin 命中、兜底让路。

**失效含义（读日志的唯一定义）**：
- `hot=1` 且 `splice=0` = 包内 pin 命中（正常首选路径）；`hot=1` 且 `splice≥1` = 兜底补的（也正常）；
- `hot=2` = **锚点全 miss**，战斗四项必然静默失效 ⇒ 直接看 `hot-patch MISS` 那行里的钩子名；菜单**不会**自动置灰（已知边界，尚未实现）。

**miss 后的处置**：先 `python3 04_scripts/镇邪人/gen_zxr_patch_header.py --out … <新spec> …` 补变体表；若派生也失败，说明**函数名或语句形状变了**（不是改名），需要按新明文改 `ZxrDerive.h` 的模板。改 `ZxrDerive.h` 属公共文件，须另开授权。

**已知边界**：
1. **菜单 UI 不会自动置灰**：`hot=2` 只有日志 + `logStatus` 告警；要让菜单把 #1~#4 标红/置灰需新增 Java 方法（`ZxrHooks.notifyHotUnpatched`）并重编 `classes8.dex`——刻意未做。
2. 派生依赖三个函数名不变（多版本实测稳定；服务端若改函数名 ⇒ 只能靠告警暴露）。
3. 变体表只覆盖见过的锚点形状；未见过的形状靠派生兜住，派生也兜不住就靠 `hot=2` 暴露。
4. **构建产物非逐字节幂等**：`apksigner` 与 `smali` 序列化都会让重复构建产出不同 sha256（大小稳定）。

**派生直证**：48572 明文上 `derive ok=3/3`，派生锚点与人工锚点逐字一致（§3.1 末条）。

## 5. 关键修复与判据

### 5.1 ZxrHooks 缺 R8 keep ⇒ 功能静默失效（必须修）

- 调用方两处都按**全名**：classes7 注入的 smali（`get_ret`/`set_ret`）与 JS 侧 `jsb.reflection.callStaticMethod("com.starry.magic.cocos.ZxrHooks", …)`。
- R8 实测把它改名 `com.starry.magic.cocos.ZxrHooks -> com.starry.magic.o.V0` ⇒ 运行时找不到类，**不报错、只是所有开关读不到**（典型静默失效）。
- 修法：`proguard-rules.pro` 与 `inject-dex-rules.pro` 各加 `-keep class com.starry.magic.cocos.ZxrHooks { *; }`。
- 判据：交付 `classes8.dex` 字节里 `ZxrHooks` 命中 1 次（实测），且 `com/starry/magic/o/` 命中 239 次（证明混淆确实开了、keep 确实生效）。

### 5.2 Preferences.clearFeaturePrefsIfListChanged 的 keep：只作探针

- 无任何外部按名调用（注入 smali 只按名引用 `MenuService`/`ZxrHooks`）；保留名字的唯一理由是**静态验收按字节找该串**。
- 因此只用 `-keepclassmembers class com.starry.magic.menu.Preferences { public static void clearFeaturePrefsIfListChanged(java.lang.String); }`，不整类 keep（不给探针额外背代码）。
- 判据：classes8 里 `clearFeaturePrefsIfListChanged` 1 次、`feature_list_sig` 1 次。

### 5.3 dex 验收判据必须按 R8 之后的形状取

- R8 混淆后 smali 里无 `NativeMenuController`（实测 0 次）⇒ 任何按 smali 类名或按固定字节串的验收判据都不能用。
- 现行判据：「按名 keep 的类（`ZxrHooks`）+ `com/starry/magic/o/` 包前缀（证明混淆确实开了）+ 偏好探针（`clearFeaturePrefsIfListChanged`/`feature_list_sig`）」。
- 颜色字节判据（`8b5cf6`/`9b7ed8`）在 classes8.dex 上都是 0 ⇒ **不能**用它证明「星空面板在位」；面板外观只能目视（§9 第 6 条）。
