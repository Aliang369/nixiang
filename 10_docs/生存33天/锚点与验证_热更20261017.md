## 2. 顺手查出的两处静默问题

| # | 问题 | 性质 | 本轮处置 |
|---|---|---|---|
| A | `BuildBaseDmgHook` 把施法者变量**写死成 `n`**；热更后 `DamageCommonCalcFinal(t,e,i,n,o,a,…)` 的 casterEntity 是**第 5 形参 `o`**（`valueData` 才是 `n`） | 「英雄→怪」判据恒假 ⇒ 百倍伤害的 baseDmg 路静默失效 | **修**：caster 与锚点一起参数化（结构派生读第 5/6 形参） |
| B | `TryInsertViewAtkHook` 的提前返回是**假阳性**：`s.find("sc33_atk_mul", p)` 里 `p` 取的是全文**首次** `GetViewFightTimeRate`（@1415230，早于 atk 钩子插入点），于是永远命中刚被 atk 钩子写进去的 `sc33_atk_mul` ⇒ 日志 `viewAtk=1` 是假的，该钩子**从未真正拼过**（1.0.23/1.0.24 同样如此） | 日志撒谎；实际行为 = 攻速只走主路 | **不改行为**（与用户已验收版本一致），仅记录 |

> A、B 都属于「写死会被改名的短标识符」类漂移，对应 `hook-rules.md` §24。

## 3. 取热更后明文（frida 在本机不可用 → 冻结法）

- frida（phantom 17.16.4，`-l 127.0.0.1:27042`）在本机 **所有 app 上都注入失败**
  （`agent connection closed unexpectedly`；spawn 走 AMS 10s start-timeout 被 kill），
  故未走 frida；**不是游戏反调试**（换任意 app 同样失败）。
- 改用「冻结 + 区域捞取」：
  1. 启动游戏，`adb logcat | grep -m1 "big eval len=.*combat=1"` 命中瞬间 `kill -STOP <pid>`
     （此刻 mod 的 `hooked_seEval` 尚未返回，原始 31MB 明文缓冲**一定在内存**）；
  2. `cat /proc/<pid>/maps` 取 `rw-p` 匿名区（≥16MB），逐区 `dd if=/proc/<pid>/mem` 本地 grep；
  3. 命中区 `0x745ec00000`（108MB）里同一段明文出现 **3 份、按 32MB 对齐**
     （游戏原缓冲 / mod 的 `src` 拷贝 / `patched` 拷贝），从区偏移 0 取 `len=31206123` 即整份原文；
  4. `kill -CONT <pid>`。
- 产物：`/tmp/sc33_hotfix/sc33_eval_main.js`（31,206,123 B，`window.__require = function t(e, i, n) {` 开头）。

## 4. 修复方案（`Games/Sc33Mod.cpp`）

**结构派生优先 + 变体表兜底**（不再依赖写死的短标识符）：

```
Sc33DeriveFightVars : prototype.FightChangeEntityHp = function(...) 形参表 → opts=第4、extra=第5
                      体内 `var p = X && X.force, d = X && X.trueDmg, <neg> = i < 0, _ = i > 0, m = 0;`
                      → opts 校验 + neg；体内 `<em>.EntityManager.Inst()` → em
Sc33DeriveBaseDmgVars: DamageCommonCalcFinal = function(...) 形参表 → caster=第5、tgt=第6
BuildFightHook(em, neg, opts, extra)  : AOE 递归改传 (aoeEnt,e,i,opts,extra)
BuildBaseDmgHook(tgt, caster)         : 施法者判据参数化
```

派生失败才回落变体表（新增热更变体 `var p = n && n.force, …, "h","f","n","o"`）。
