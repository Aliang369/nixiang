# 宝石战争 TapTap 6.0.012 可行性分析

> 日期：2026-09-16
> 范围：只做静态与只读验证，不修改 APK、不注入、不安装、不清数据。
> 设备：`f9a116a2`，当前前台包 `com.acing.gow.adv`
> 结论状态：加固与本地校验已完成静态判定；三项功能为“高可行”，但实现前仍需按 HybridCLR 加载方式设计 Hook，服务端风控为 NOT PROVEN。

## 1. 样本与版本

- 应用名：宝石战争
- 包名：`com.acing.gow.adv`
- 版本：`6.0.012` / `versionCode=6000012`
- 来源：TapTap 原版，`originatingPackageName=com.taptap`
- APK：单 base APK，529,494,836 bytes
- SDK：min 22 / target 30 / compile 33（Manifest 内旧字段不一致，不构成保护）
- APK MD5：`f207fc9d5b62b1a956a72c35c6a56def`
- APK SHA-256：`8ba59a1c27e15eb6d998840913a53c55c38eeaf102d78702624a1f0cece53969`
- 签名：v1 + v2，无 v3/v4；单 signer
- 签名证书 SHA-256：`8943b31609712c8c7fdf583ce26b204ad8b01dad8eb09f4c7d1f276458985bb4`
- 引擎：Unity 2022.3.62f1，ARM64，IL2CPP + HybridCLR 8.13.0
- 运行时 `global-metadata.dat` 与 APK 内文件 MD5 一致：`1da4a40bfb63f1dde4cee041ba294d2f`
- 设备 HotUpdate 目录为空，本次分析对应 APK 内置热更程序集，不是 CDN 覆盖版本

## 2. 加固结论

综合判定：**没有传统整包加固/壳，属于弱保护生产包。**

### 2.1 传统加固面

- `classes.dex`、`classes2.dex` 均为可直接解析的标准 DEX。
- 未发现常见壳 SO：`libjiagu`、DexHelper、网易易盾、APKSecure、KwProtect、SecShell 等。
- Application 为正常 `com.u8.sdk.U8Application`，不是壳代理 Application。
- `libil2cpp.so` 为正常 ELF64；导出 `JNI_OnLoad`、`il2cpp_init`、`il2cpp_runtime_invoke`。
- `global-metadata.dat` 头为 `AF 1B B1 FA`，metadata v31，未加密。
- Il2CppDumper 可直接完成 dump，代码注册与元数据注册均解析成功。
- 包内主 IL2CPP DummyDll 存在，但 `Assembly-CSharp` 中没有战斗业务类，说明业务代码走 HybridCLR 热更程序集。

### 2.2 热更程序集保护

热更入口为 `HotUpdateLoadDll`，加载：

- `assets/Android/Dlls/AOTMetadata.json`
- `assets/Android/Dlls/System.Platform.dll.bytes`
- `assets/Android/Dlls/System.Network.dll.bytes`
- `Main.unity3d`

保护形式很弱：

- `System.Platform.dll.bytes` 与 `System.Network.dll.bytes` 只有前 `0x100` 字节被循环 XOR。
- 静态初始化中的 `DllEncryptionKey` 长度为 6。
- 由标准 PE 头和静态初始化逻辑可还原 key：`04 10 05 1B 0A 01`。
- XOR 后两文件均为标准 PE32/.NET 程序集，可直接交给 ILSpy。
- `System.Network.dll` 是主要业务程序集，包含战斗、UI、数据模型、结果上报与调试作弊代码。

### 2.3 第三方安全组件

存在多个第三方检测/安全组件，但不是游戏专用反作弊：

- `libthemis.so`：TapTap GID/Themis，当前进程已加载。
- `libluster.so`：字节广告归因相关，当前进程已加载。
- `libmsaoaidsec.so`：OAID/设备标识安全，包含 `ptrace` 字符串，当前进程已加载。
- `libturingad.so`：腾讯广告风险 SDK，含 debugger 相关字符串，当前未见加载。
- `libA3AEECD8.so`：SONAME 为 `libjdog.so`，含 Xposed/Hook 检测字符串，当前未见加载。
- `libtkdna.so`：第三方归因库，未见游戏逻辑级复用。

这些组件可能对调试器、Xposed、Hook 环境做旁路检测，但没有发现它们参与战斗结算或三项功能的硬门禁。当前设备已 Root 且原版可正常启动，说明 Root 本身不是阻断条件。

## 3. 本地与远端校验点

### 3.1 TapTap 包签名

最关键的重签包校验点：

- `com.taptap.sdk.kit.internal.utils.TapSignKit.getSign()`
- 通过 `PackageManager.getPackageInfo(..., GET_SIGNATURES)` 读取当前 APK signer
- 取第一个 `Signature.toByteArray()` 后计算 MD5
- 该值由 TapTap Gatekeeper 初始化请求上传到 TapTap 服务端

性质：

- 不是本地“签名不一致就闪退”的硬校验。
- 但会影响 TapTap SDK 的 Gatekeeper、登录或渠道能力。
- 若后续真机做重签包，需处理签名回灌/签名伪装，否则 TapTap 侧可能出现登录或 Gatekeeper 异常。
- 独立加载器/MOD 菜单若在原生进程内运行，不重新签 APK，则不会触发该点。

### 3.2 热更文件完整性

`HotUpdateManifestValidator` 会校验：

- 文件路径
- 文件大小
- MD5/hash
- 启动必需文件闭包
- installed manifest 与 packaged manifest 的覆盖关系

影响：

- 直接改 APK 内 `System.Network.dll.bytes` 后，必须同步更新 `assets/Android/manifest.json` 的 hash/size。
- 设备后续 CDN 热更会校验/覆盖热更文件，直接改包容易被版本更新冲掉。
- 运行时 Hook 不改热更文件，不受该 MD5 门禁影响。

### 3.3 战斗结果上报

战斗结束走 `GWSubmitResultLoader`，函数名为 `submit_result`，上报内容包括：

- `BattleToken`
- `Result`
- `TroopHealth` / `OpponentTroopHealth` / `OpponentTroopArmor`
- `TroopIdsKilled`、`TroopsSummoned`、`TroopsTransformed`
- `Stats` 与 `StatsCRC`
- `BattleActions`
- 各玩法自己的 BattleIndex / Event / Arena / Peak Arena 字段

`StatsData.GetStatsCRC()` 只是：

- 对用户名/宝石/金币做加权 ASCII 求和；
- 对战斗 Stats 字符串做同样的 ASCII 求和；
- 两者 XOR。

这不是强防篡改，但服务端是否基于伤害、回合、棋局行为二次校验，当前客户端内看不到。PvE、PvP、竞技场、公会战、排行榜的风险等级不同，归为 NOT PROVEN。

### 3.4 自带作弊入口

正式包确实编译进了：

- `CheatButtonsPuzzle`：ChangeGem、ChargeMana、ChargeAndCast、KillTroop、StatusEffect、Attack+/Armor+/Magic+ 等。
- `CheatPanelBoard`：作弊面板。
- `PuzzleUI.CheatWinGame()`、`CheatLoseGame()`。
- `PuzzleTroop.DebugFillMana()`、`DebugHulkHealth()`、`DebugHulkAttack()` 等。

但生产环境下：

- `GoWApplication.CHEATS` getter 直接 `return false`。
- `CheatPanelBoard.Start()` 默认 `SetActive(false)`。
- `PuzzleUI.CheatUpdate()` 还显式拒绝 `GoWApplication.EnvironmentID == Production`。

所以不能通过普通配置直接开启游戏内置作弊面板。只能：

- 用独立 MOD 菜单/外挂逻辑实现功能；或
- Hook `GoWApplication.CHEATS` 并自行拉起 UI（仍不推荐，改动面更大）。

## 4. 三项功能可行性

结论：三项都属于**高可行**。关键不是“是否能找到逻辑”，而是业务代码在 HybridCLR 中，不能用普通 AOT `libil2cpp.so + 静态 RVA` 思路直接补机器码。

### 4.1 攻击倍率（可调）

可用两条路线：

1. 仅普通攻击倍率
   - 目标：`PuzzleTroop.GetAttack()`
   - 对玩家侧 `PuzzlePlayer.PlayerIndex == 0` 返回 `Attack * multiplier`
   - 影响普通 skull 伤害和 UI 攻击数值

2. 全局伤害倍率
   - 目标：`PuzzlePlayer.AdjustHealth(...)`
   - 当目标是 AI `PlayerIndex == 1` 且 `nAdjust < 0` 时，将 `nAdjust *= multiplier`
   - 同时覆盖普通攻击、法术和其他统一伤害入口
   - 副作用是敌方自伤/反射等也会被按倍率放大；若需精确只放大玩家造成的伤害，应额外过滤 `pAdjustmentCause`

建议菜单形态：

- 滑块 `1..100`，默认 `1`
- 1 = 原逻辑
- N = 最终伤害乘 N

### 4.2 上帝模式（无敌）

推荐主线：

- Hook `PuzzlePlayer.AdjustHealth(...)`
- 当目标为玩家侧 `PlayerIndex == 0` 且 `nAdjust < 0` 时，直接把伤害修正为 `0` 或拦截这次调用
- 返回原有的 `List<int>` 结构，保持调用方状态稳定

覆盖范围：

- 普通攻击
- 法术伤害
- true damage 参数路径
- 吞食、法术直接压血等最终仍走 `PuzzlePlayer.AdjustHealth` 的路径

需要额外补的边界：

- `PuzzleTroop.RunAway()` 直接写 `Health = 0`
- 少数效果直接调用 `PuzzleTroop.SetHealth(...)`
- 因此完整无敌版建议再加一层玩家侧 `PuzzleTroop.AdjustHealth/SetHealth` 守卫，或低频血量回填兜底

不建议：

- 只改 `Health` 字段。游戏伤害管线会经过护甲、真伤、状态、反射等多个入口，纯字段写入会被后续逻辑覆盖。

### 4.3 无限技能

指令链：

- `PuzzlePlayer.CastTroopSpell()`
- 施法前记录 manaPercent
- `pTroop.SetMana(0)` 扣光法力
- `PuzzleUI.DoSpell()` 执行技能
- `PuzzleTroop.CanCastSpell()` 要求 `Mana >= ManaRequired && !Silence && !SpellDisabled && !IsDead && Health > 0`

可行方案：

1. 施法后回填
   - Hook `PuzzlePlayer.CastTroopSpell`
   - 在返回后调用 `FillMana()` 或 `SetMana(ManaRequired)`

2. 拦截扣蓝
   - Hook `PuzzleTroop.SetMana(0)`，对玩家侧 troop 忽略这次清零

3. 强制可施放
   - Hook `PuzzleTroop.CanCastSpell()` 对玩家侧返回 true
   - 但 UI 的按钮显隐仍受 `UpdateManaDisplay()` 的 `Mana >= ManaRequired` 控制，单独改这个函数不够

推荐组合：

- 优先方案 1
- 若遇到 UI 按钮不刷新，再配合方案 3
- 不建议无条件绕过 `Silence/SpellDisabled`，保留原版状态效果更稳

## 5. HybridCLR 实现约束

这是本包唯一会显著增加实现成本的点，但不是加固：

- 游戏业务类在 `System.Network.dll`，运行前不在 `libil2cpp.so` 的 AOT 代码里。
- 静态 `dump.cs` 中 `Assembly-CSharp` 基本没有战斗类，Il2CppDumper 只覆盖 AOT 框架层。
- 正确路线是 HybridCLR-aware 方式：
  - 在 `System.Network` 加载完成后通过 IL2CPP 反射/Metadata 获取目标 `MethodInfo`
  - 读取其运行时 `methodPointer` / 解释器入口
  - 再做运行时 Hook；不同版本要考虑 HybridCLR 解释执行、JIT 或 AOT 转译状态
- 另一条路线是直接改 `System.Network.dll.bytes` 的 IL，再修复 manifest hash；但会被 CDN 热更和 manifest 校验影响，不作为首选。

## 6. 最终判断

| 项目 | 判定 | 说明 |
|---|---|---|
| 传统加固 | 无 | 标准 Unity IL2CPP，metadata 明文 |
| 热更保护 | 弱 | 仅前 256 字节 XOR，程序集正文为明文 .NET |
| 本地完整性 | 中低 | 热更 manifest 有 MD5/size 校验 |
| TapTap 校验 | 需关注 | Gatekeeper 使用包签名 MD5，重签包必须处理 |
| 游戏专用反作弊 | 未发现 | 主要安全逻辑来自第三方 SDK |
| 攻击倍率 | 可做 | `GetAttack` 或统一伤害入口均可 |
| 上帝模式 | 可做 | 拦截玩家侧 `AdjustHealth`，补直写血量边界 |
| 无限技能 | 可做 | 施法后回蓝或拦截 `SetMana(0)` |
| PvE 真机效果 | 待验证 | 静态可行，未做运行验证 |
| PvP/排行榜安全性 | NOT PROVEN | `submit_result` 服务端风控未知，不建议在联机玩法默认开启 |

综合结论：**可以逆向实现，难度主要在 HybridCLR 热更方法的运行时 Hook，不在加固或三项功能本身。** 若只面向单机/PvE 测试，可以进入下一阶段做最小 Hook 验证；若用于联机、竞技场、公会战或排行榜，需要先按服务端上报风险单独评估。
