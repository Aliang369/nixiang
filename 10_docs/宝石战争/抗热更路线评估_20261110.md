# 宝石战争 抗热更路线评估（A 方案实验记录，2026-11-10）

> 背景：本作热更频繁（1.0.0.04 → .06 → .11 → .14 → .15 五轮），每轮官方都会把未补丁的
> \`System.Network.dll.bytes\` 落到设备外部 \`files/HotUpdate/\`，覆盖包内补丁 DLL，三项功能失效。
> 用户问「能否在热更情况下保持功能可用」，本轮分 A（native 运行时挂接）/ C（一键重注）两条路评估。

## 1. 结论

- **A 失败（methodPointer 路线）**：hook 安装成功但命中恒为 0，隔离实验证实功能完全消失。
- **C 已落地**：\`04_scripts/宝石战争/bszz_hotfix_auto.sh\`，下次热更一条命令完成重注。
- A 仍有一条未验证的残余路线（hook 共享解释器入口），风险与成本显著更高，**本轮不推进**。

## 2. A 方案实验（三次迭代，全部有实测证据）

### 2.1 静态可行性（成立）

| 检查项 | 结果 |
|---|---|
| 热更类运行时可见 | \`il2cpp\` 21 个 API 全导出；\`PuzzlePlayer\`/\`PuzzleTroop\` 按短名解析成功 |
| 框架能力 | \`Unity/Il2CppApi.h\` 已封装 \`ClassFromName\`/\`GetMethod\`/\`SafeProbe\`（SIGSEGV 保护）；Dobby 可用 |

\`\`\`

### 2.4 隔离实验（决定性）

为排除「效果其实来自旧 IL 注入」的歧义，做隔离包：包内 \`System.Network.dll\` 换回**官方未补丁版**
（\`7f56d360…\`，已确认不含 \`StarryMagic\`），只留 hook。

- 装后零崩溃，\`DobbyHook rc=0\`，\`battle_begin\` 16:36:31 / 16:36:36 正常触发；
- \`AH hits=0\`（至 16:38:22），旧桥接日志 0 条；
- **用户实测口径「打完了，恢复正常了」⇒ 功能完全消失**。

⇒ 之前所有「功能有效」均来自 IL 注入；methodPointer 上的 hook 在本作**从未被调用**。

### 2.5 为什么失败（机制）

热更程序集内部方法互调时，HybridCLR 解释器直接用 \`InterpMethodInfo\` 调 \`Interpret(imi, …)\`，
**不经过 \`MethodInfo->methodPointer\`**。该指针只服务「AOT → 热更」的入口跳转，
而战斗逻辑全部发生在热更程序集内部 ⇒ 命中恒 0。这与
\`经验_HybridCLR直写三铁律_20260829\` 铁律一完全一致（战魂铭人同型）。

## 3. 残余路线（未验证，不推荐先做）

hook **共享解释器入口**（\`AdjustHealth\` 的 \`bl\` 目标 = \`mp + 0x1b9cc\`，随 ASLR 每次启动不同，可运行时算）：

- 需在入口按 \`imi\` 反查方法身份，再按 IL 参数索引读写 \`args\`；
- 风险：该入口承载**全部**热更方法调用，处理不当整游戏崩；\`AdjustHealth\` 12 参、返回 \`List<int>\`，
  args 布局与返回表示都需逐个确认；调用频率极高，性能开销需评估。
- 若将来要碰，先做「只计数不改行为」的透传 + 命中验证，再谈参数改写。

## 4. C 方案：一键重注（已落地）

\`04_scripts/宝石战争/bszz_hotfix_auto.sh\`——四件事一条命令：

1. 比对设备外部热更版本 vs 包内 manifest 版本，相同直接退出（幂等）；
2. 只读拉回真机已装包 + 外部增量（**不重下官方 APK、不重编 dex/so**）；
3. 解密 → 4 锚点注入 → 外科组装（142 资产逐条校验）→ 签名；
4. 覆盖安装（不清数据）→ 清空外部 HotUpdate → 装机预检。

用法：

\`\`\`bash
bash 04_scripts/宝石战争/bszz_hotfix_auto.sh                    # 自动按设备实际版本
BSZZ_SKIP_INSTALL=1 bash 04_scripts/宝石战争/bszz_hotfix_auto.sh # 只到签名
BSZZ_FORCE=1 bash 04_scripts/宝石战争/bszz_hotfix_auto.sh        # 版本相同也强制重做
\`\`\`

实测（2026-11-10 16:45）冒烟：外部已清空时正确判定「无需处理」并 exit 0。

**效率依据**：本轮 1.0.0.15 共 142 项资产中 **140 项与底包逐字节相同**，只有 Network 与 receipt 变化，
所以重注的真实工作量 = 1 个 DLL 的解密+注入 + zip 外科重组，无需搬运 440MB 资产。

## 5. 规律（供后续判断）

| 规律 | 证据 |
|---|---|
| 失效点恒为「外部官方 DLL 覆盖包内补丁」 | 1.0.0.06 / .14 / .15 四次同型 |
| native 侧从不随热更漂移 | \`libil2cpp.so\` \`ce2aac34…\`、\`global-metadata.dat\` \`a34f5825…\` 在 .14→.15 逐字节相同 |
| IL 锚点方法名跨 5 版零漂移 | \`AdjustDamage\`/\`ShouldKeepMana\`/\`AdjustHealthValue\`/\`ShouldBlockRunAway\` 5/5 命中 |
| 外部 HotUpdate 目录动不得 | 只换 DLL → 45s 内被回写；改 manifest+receipt → 目录被清空重建（1.0.0.06 实测） |
| 包内 manifest 版本 == CDN ⇒ 不回拉 | .06 / .14 / .15 三次验证，启动后外部保持 0 文件 |
