## 一、「检测到战斗作弊」是什么

两级弹窗，文案都来自热更 Lua 本地化表（APK/dex/il2cpp 内无中文串）：

| 链路 | 触发 | 出口 | 文案 key |
|---|---|---|---|
| A 服端警告 | 服端 WebSocket 事件 `anticheat.warning` → `AntiCheatManager.OnCheatWarning` | `TipCheatWarning` → `UIManager.OpenWindow("CheatWarningWindow")` | `cheat_warning_tip` |
| B 本地重放校验 | 大厅内 `AEventSceneEntered(Scene.Main)` → `CheckPlay` | 重放校验失败 → `UIManager.OpenWindow("ForcedWindow", GameText.GetText("cheat_play_tip"))` | **`cheat_play_tip`＝「检测到战斗作弊」** |

### 链路 B 的精确判定（`Application.Utility.AntiCheatManager`，源码行 82-117）

真实签名是 `CheckPlay(self, levelData, cb)`——**异步回调型**（反汇编 proto#8 @82-117），等价于：

```lua
function AntiCheatManager:CheckPlay(levelData, cb)
  if not self:ShouldCheckPlay() then cb(false) return end   -- ShouldCheckPlay = _customData.CheatCheckCount > 0
  if DeviceInfo.IsMinigame() then cb(false) return end
  if not levelData:IsWin() then cb(false) return end        -- 只在「赢了」的局校验
  if not Utility.IsModuleReady(EnvTaskManager) then cb(false) return end
  if not SideQuestInfoUtility.IsLevelDataTypeReplayable(levelData:GetType()) then cb(false) return end
  local dataStr = ReplayRecord.GetRecordDataStr(true)        -- force=true，绕过 recordValid
  EnvTaskManager:GetInstance():RunTask("EnvTaskReplay", dataStr, function(code, resultStr)
    -- 判通过：print("[AntiCheat] 作弊用户, 本次战斗未作弊") + SetCheatCheckCount(CheatCheckCount-1) + cb(false)
    -- 判失败：UIManager.OpenWindow("ForcedWindow", GameText.GetText("cheat_play_tip"), nil, …)
  end)
end
```

> ⚠️ **回调语义（踩过坑）**：`cb` 的第一个参数 `false` 表示「无作弊/放行」，游戏自己的「不检查」分支就是
> 提前 `cb(false)` 后 return（反汇编 `[15-18]`）。**包装 CheckPlay 时若不调用 `cb`，上层结算链会永远等不到回调
> ⇒ 打完一局不结算、界面卡住**（本轮真机实测事故，见 §四.7）。

### `CheatCheckCount`（观察期）语义 —— 实测 + 反汇编一致

- 服端下发 `anticheat.warning` → `OnCheatWarning` 把计数置 `DefaultCheatCheckCount = 30`；
- 此后每场**胜利**的局都跑一次本地重放校验，干净一场减 1；任一场失败就弹「检测到战斗作弊」；
- 计数为 0 时 `ShouldCheckPlay()` 为假，**校验完全不跑**（这就是「有时候才提示」的成因）。

### 服端凭什么给你发 `anticheat.warning`（本次新查明的关键一环）

`Application.Utility.SideQuestApi._BIEndQuest`（源码行 746-982，反汇编 `/tmp/x2dis/m_cef133c0.txt:2395-2476`）
在结算时构造一行 BI 数据 `R9`：

```lua
local predicted = AntiCheatManager:Judge(self)             -- 按战力估「每回合伤害」基准 → PredictedDamagePerRound
local real = 0
for _, c in ipairs(fightState[CSide.Side1].Characters) do
    real = real + c.Data:GetNum("DamagePerRound")           -- → RealDamagePerRound
end
R9.RealDamagePerRound      = real                           -- [567]
R9.PredictedDamagePerRound = predicted                      -- [568]
R9.Cheated                 = (predicted * 5 < real)          -- [569-576] MUL R23 5 R21 ⇒ 容忍带＝5×
BIRequest.EndQuest(…, NetworkManager.Json:encode(R9), …)    -- [641-646] 编码成字符串后当参数发出去
```

- `Cheated` / `RealDamagePerRound` / `PredictedDamagePerRound` **全仓只被 `SideQuestApi` 引用**
  （`grep` 全 1083 个模块确认）⇒ **它只走 BI，不进 `ApiRequest` 的玩法接口**。
- **容忍带＝5 倍**：`Real > 5 × Predicted` 才 `Cheated=true`；换言之 **≤5 倍伤害本来就不会被判作弊**，
  十倍伤害则必然踩线，服端据此发警告、开观察期。
- 结论：「拦/改 BI 里的伤害与 `Cheated`」同时就是「过检测」的核心动作 —— 两条需求在同一处收口。

## 二、处理方式

### ① 过检测（Lua 基线段 `[[1]]` `[[2]]`）

1. `AntiCheatManager.ShouldCheckPlay = function() return false end`
   —— 本地重放校验永不触发（不会再去跑 `EnvTaskReplay`，也不再多耗性能）。
2. `AntiCheatManager.CheckPlay = function(self, p1, p2)` —— 双保险，任何别处直接调用也空转，
   **但必须回调**：`if type(p2) == "function" then pcall(p2, false) end`
   （`false`＝放行，与游戏自身「不检查」分支的 `cb(false)` 完全一致）。
3. `AntiCheatManager.TipCheatWarning` / `OnCheatWarning` 直接吞，并把
   `LocalStorage` 的 `CheatWarningTimeLeftKey` 写 0（服端警告窗不再弹，重启后也不会补弹）。
4. **弹窗兜底**：包装 `UIManager.OpenWindow`，只拦作弊相关窗口：
   - 窗口名 `CheatWarningWindow` / `TestQuestCheatWindow` → 丢；
   - 窗口名 `ForcedWindow` 且文案命中 `cheat` 或「作弊」→ 丢
     （`ForcedWindow` 实为通用多选窗 `windows/multi_choice_window`，**不能无条件拦**，否则会误伤正常多选弹窗）。
   - 兼容点号/冒号两种调用形式（`AntiCheatManager` 用的是点号形式 `UIManager.OpenWindow(name, text)`）。

### ② 上报拦截

**分层**，因为不同出口的网络路径不同：

| 层 | 目标 | 手段 | 落点 |

  （`ChannelManager` 按 `GameConfig.GetChannelId()` 分派）⇒ 必然启用。该主机与登录/本体/进度无关，可切。
- 放行（拦了会影响正常游戏）：`*.alina-game.cn`（游戏本体/CDN/WebSocket `wss://blina-official.cliapi.alina-game.cn/ws`）、
  `*.taptap.cn` `*.taptap.com`（登录/实名）、`*.xdrnd.cn` `*.xdrnd.com`（SDK 网关/门槛）、`*.alipay.com`、`open.e.189.cn`。

  实测 `23:59:45.673` 加载 so，而 `cn.fly.FlyApplication.onCreate → FlySDK.init` 在其后
  ⇒ **构造器里装 hook 一定早于 Mob 初始化**；`Match2_TryInit()` 里再兜底重试一次。

#### L2 BI 漏斗（补偿式，为什么不用 no-op）

- `BINetworkManager.CustomSend` 是**唯一真正发送器**：`Send` 只是转发、`CachedSend` 只写本地缓存；
  上游 `BIRequest` 8 个出口（`GeneralSend`/`CommonAction`/`ReportDeviceInfo`/`EndQuest`/`Tutorial`/`SkipTimeline`/`NetLibRecords`/`Question`）。
- **不在 no-op 上收手，改成 `WrapForward`**：记录 → 清洗载荷 → **原样转发**（参数个数、顺序、返回值、回调时序全不变）。
  - 表参数递归改写（深度 ≤4）：`Cheated`/`IsCheat`/`IsHacked`/`IsHook`/`IsRoot`/`IsEmulator`/`IsDebug`/`IsFrida`/`IsModify` 等 → `false`；
    `RealDamagePerRound`（或 `RealDamage`）> `PredictedDamagePerRound × 1.8` → 压到 `floor(pred×1.8)`（远在 5× 容忍带内）。
  - 字符串参数：`{` 开头且含 `"Cheated"`/`"RealDamagePerRound"` 才 `NetworkManager.Json:decode` → 改 → `:encode` 写回
    （`_BIEndQuest` 正是把整行 JSON 化后当参数传的）；`pcall` 全包，失败**原样转发**。
  - 依据：勇士之心方法论「不禁止、只改值 / 缺失一条上报本身就是特征」。
  - 逃生口：`_G.__starry_bi_hard = true` 恢复硬空实现（老行为，`biBlock` 计数）。
- C#/native 侧入口：`BIRequest` 模块加载时会把 `CS.LuaManager.Instance.LuaBISend = BIRequest.CommonAction`，
  所以换完表字段后**必须重指一次**（`kAcScript [[5]]`，每次同步都重指，热重载后自动恢复）。
- BI 走的是**游戏自家域名**（`NetworkUtility.GetBiUrl` = `%s/bi/%s/%s`，host 来自 `NetworkUtility.BIHttpUrl`）
  ⇒ DNS 层拦 BI 会连坐登录/进度，只能在 Lua 层改。
- 附带：`ChannelTapReport._ReportEvent`（TapDB 真发送器）、`GameConfig.UpdateBuglyReportSceneData` 等三个 Bugly 场景埋点、
  `BIActionManager.OnEvent`（BI 已在漏斗层改值，入队只会白涨内存）—— 这三个是第三方埋点，保持空实现（其域名已被 L1 切断）。

**表 C · 一致性规则（互相能推出的量不能矛盾）**

1. **伤害账平**：`Σ逐角色/逐元素明细 ≈ RealDamagePerRound`。只压聚合不压明细＝自相矛盾，
   所以 `rr = (Predicted×1.8)/Real` **一路向下传递**（`biFixDetail` 计数），保持「干净但自洽」。
2. **观察期递减**：`CheckPlay` 只压掉重放/上报这一段，**照游戏自己的通过分支**把
   `CheatCheckCount` 减 1（`acDec` 计数）。避免「有观察期却永不递减」这种只有机器能造出的序列。
3. **不动调用方状态**：BI 载荷表一律走 `CopyTable`（深拷贝）后清洗，**只在真的改了值时才用副本替换形参**
   ⇒ 游戏内的伤害/面板/后续逻辑一个字节都不受影响（这是「不影响正常游戏」的硬保证）。
4. **不改调用时序**：`WrapForward` 原样转发参数个数/顺序/返回值/回调。
5. **不制造缺口**：所有原调用照发（只改值），不比官方少一条上报 —— 「缺失一条上报本身就是特征」。
6. **可观测**：每次真改了值打一行 `[StarryACG] BI清洗 BIRequest.EndQuest 聚合=N 明细=N 布尔=N`。

## 四、不做什么 + 为什么（诚实边界）

1. **不拦 `ApiRequest` / `ApiClient`（含回放字段、主关卡结算）**：这是玩法主链路，拦了会掉线/卡进度，
   与「不影响正常游戏」冲突。
2. **不改 `AntiCheatManager.SetCheatCheckCount`**：观察期计数照原语义递减并回传
   （`SaveCustomData` → 服端）。若把它强行清零/静默，反而会造出「有观察期却不递减」的异常序列
   —— 这正是「缺失一条上报本身就是特征」的坑。
3. **BI 只改值、不禁止**：载荷照发、结构不变（`WrapForward` 转发原函数），服端看到的是一份「干净但完整」的 BI。
   带功能的战斗里聚合与明细**同比例**下调（表 C.1），保持自洽；硬拦模式（`__starry_bi_hard`）留下的
   「BI 整段静默」是更强的特征，默认不用。
4. **不碰回放数据本身**（`ReplayRecord` / `ReplayInput`）：断线恢复、PvP 回放依赖它；改坏会导致战斗异常。
   （注意：观察期内 `CheckPlay` 会 `GetRecordDataStr(true)` 把回放数据交给 `EnvTaskReplay` 服端任务——
   我们的做法是让 `ShouldCheckPlay=false` 使这条任务根本不发起，而不是伪造回放。）
5. **未做服务端验证**：本方案只覆盖客户端可见出口，服端是否有其它旁路（如结果侧二次校验）无法从静态分析证实。
   这是**推断**，实测口径：装机后真机打几场带功能的战斗，观察 `acWin` 是否始终为 0、`biSeen`/`biFixDamage` 是否按预期递增、
   结算是否始终正常。
6. `Utility.IsSpecialCheatUser` 全仓只有它自己引用，且实现是 `return false, nil` 的空壳（已停用），**不作为依赖**。
7. **残余风险（已缩小，未归零）**：明细补偿用的是 `DAMAGE_KEYS` 精确键名
   （`DamagePerRound`/`Damage`/`TotalDamage`/`DamageAdd`/`HitDamage`/`DamageValue`）。
   若 `_BIGetElementDataList`/`_BIGetCharacterDataList` 里还有**其它名字**的伤害类字段
   （键名由名字表驱动、`GetNum(属性名)` 逐项取），那部分不会被缩放 —— 判据：结算后看
   `[StarryACG] BI清洗 …` 的`明细`计数是否随战力/倍率变化；彻底覆盖需再抓一次真实键名（下一轮 recon）。
8. **教训（本轮事故）**：`AntiCheatManager.CheckPlay(self, levelData, cb)` 是**异步回调型**，
   最早的裸 no-op 版本吞掉了 `cb` ⇒ 真机打完一局**不结算、卡死**。修法＝照游戏自身「不检查」分支回调 `cb(false)`。
   配套纪律：**包装任何被包装者调用过的函数前，先确认它是否持有回调/继续令牌**；一次性破坏性改动必须单独一轮、单独装机。
