## 一、「检测到战斗作弊」是什么

两级弹窗，文案都来自热更 Lua 本地化表（APK/dex/il2cpp 内无中文串）：

| 链路 | 触发 | 出口 | 文案 key |
|---|---|---|---|
| A 服端警告 | 服端 WebSocket 事件 `anticheat.warning` → `AntiCheatManager.OnCheatWarning` | `TipCheatWarning` → `UIManager.OpenWindow("CheatWarningWindow")` | `cheat_warning_tip` |
| B 本地重放校验 | 大厅内 `AEventSceneEntered(Scene.Main)` → `CheckPlay` | 重放校验失败 → `UIManager.OpenWindow("ForcedWindow", GameText.GetText("cheat_play_tip"))` | **`cheat_play_tip`＝「检测到战斗作弊」** |

### 链路 B 的精确判定（`Application.Utility.AntiCheatManager`，源码行 82-117）

```lua
function AntiCheatManager:CheckPlay(levelData)
  if not self:ShouldCheckPlay() then return end            -- ShouldCheckPlay = _customData.CheatCheckCount > 0
  if DeviceInfo.IsMinigame() then return end
  if not levelData:IsWin() then return end                  -- 只在「赢了」的局校验
  if not Utility.IsModuleReady(EnvTaskManager) then return end
  if not SideQuestInfoUtility.IsLevelDataTypeReplayable(levelData:GetType()) then return end
  local dataStr = ReplayRecord.GetRecordDataStr(true)        -- force=true，绕过 recordValid
  EnvTaskManager:GetInstance():RunTask("EnvTaskReplay", dataStr, cb)
end
```
回调里失败即 `OpenWindow("ForcedWindow", cheat_play_tip)`；通过则
`print("[AntiCheat] 作弊用户, 本次战斗未作弊")` + `SetCheatCheckCount(CheatCheckCount - 1)`。

### `CheatCheckCount`（观察期）语义 —— 实测 + 反汇编一致

- 服端下发 `anticheat.warning` → `OnCheatWarning` 把计数置 `DefaultCheatCheckCount = 30`；
- 此后每场**胜利**的局都跑一次本地重放校验，干净一场减 1；任一场失败就弹「检测到战斗作弊」；
- 计数为 0 时 `ShouldCheckPlay()` 为假，**校验完全不跑**（这就是「有时候才提示」的成因）。

### 服端凭什么给你发 `anticheat.warning`（本次新查明的关键一环）

`Application.Utility.SideQuestApi._BIEndQuest`（源码行 746-982）在结算时：

```lua
local predicted = AntiCheatManager:Judge(self)             -- 按战力估「每回合伤害」基准
local real = 0
for _, c in ipairs(fightState[CSide.Side1].Characters) do
    real = real + c.Data:GetNum("DamagePerRound")
end
levelData.RealDamagePerRound = real
levelData.PredictedDamagePerRound = predicted
levelData.Cheated = (predicted * N < real)                  -- 超阈值即判「作弊」（N 为配置倍数）
BIRequest.EndQuest(...)                                     -- ← 紧接着由 BI（BIPlay）发出去
```

- `Cheated` / `RealDamagePerRound` / `PredictedDamagePerRound` **全仓只被 `SideQuestApi` 引用**
  （`grep` 全 1083 个模块确认）⇒ **它只走 BI，不进 `ApiRequest` 的玩法接口**。
- 结论：**十倍伤害必然让 `Cheated=true`，而这条「伤害不合理」信号就是服端发警告、开观察期的输入**。
- 所以「拦 BI」同时就是「过检测」的核心动作 —— 两条需求在同一处收口。

## 二、处理方式

### ① 过检测（Lua 基线段 `[[1]]` `[[2]]`）

1. `AntiCheatManager.ShouldCheckPlay = function() return false end`
   —— 本地重放校验永不触发（不会再去跑 `EnvTaskReplay`，也不再多耗性能）。
2. `AntiCheatManager.CheckPlay = function(self) return end`
   —— 双保险，任何别处直接调用也空转。
3. `AntiCheatManager.TipCheatWarning` / `OnCheatWarning` 直接吞，并把
   `LocalStorage` 的 `CheatWarningTimeLeftKey` 写 0（服端警告窗不再弹，重启后也不会补弹）。
4. **弹窗兜底**：包装 `UIManager.OpenWindow`，只拦作弊相关窗口：
   - 窗口名 `CheatWarningWindow` / `TestQuestCheatWindow` → 丢；
   - 窗口名 `ForcedWindow` 且文案命中 `cheat` 或「作弊」→ 丢
     （`ForcedWindow` 实为通用多选窗 `windows/multi_choice_window`，**不能无条件拦**，否则会误伤正常多选弹窗）。
   - 兼容点号/冒号两种调用形式（`AntiCheatManager` 用的是点号形式 `UIManager.OpenWindow(name, text)`）。

### ② 上报拦截

**分层**，因为不同出口的网络路径不同：

| 层 | 目标 | 手段 | 落点 |
|---|---|---|---|
| L1 第三方 SDK | Mob/cn.fly（`.zztfly.com` 22 个端点，含 root/调试/模拟器/frida 环境指纹上报）、Bugly、TapDB、TapSDK 明文日志、运营商一键登录上报 | **native DNS 黑名单**（`getaddrinfo` / `android_getaddrinfofornet` / `gethostbyname[2]`） | `Match2Mod.cpp` DNS 段，构造器即装 |
| L2 游戏本体埋点 | BI 全通道（`BIAction` / `BIPlay` / 教程 / 问卷 / 下载 / 缓存补发）、TapDB 渠道上报、Bugly 场景埋点 | **Lua 漏斗层挂钩**（改值/空实现） | `kAcScript` `[[3]]`-`[[8]]` |
| L3 玩法接口 | `ApiRequest` / `ApiClient`（登录、进度、主关卡结算、回放字段） | **不动** | —— |

#### L1 DNS 黑名单（后缀）

```
.zztfly.com  .bugly.qq.com  .bugly.qcloud.com  .cros.wr.pvp.net  .trace.qq.com
.tapdb.net   openlog.tapapis.cn  openlog.tapapis.com  openlog.xdrnd.cn
.cmpassport.com  crbt.i139.cn  opencloud.wostore.cn  api-e189.21cn.com
```

- **必须含 `.zztfly.com`**：Mob 的 TCP 长连接目标 `host:port` 由
  `tgc.zztfly.com/tcp/config/init` 下发，只堵数据面会被纯 IP 绕过，堵住这个域名才能同时断掉下发。
- 放行（拦了会影响正常游戏）：`*.alina-game.cn`（游戏本体/CDN/WebSocket `wss://blina-official.cliapi.alina-game.cn/ws`）、
  `*.taptap.cn` `*.taptap.com`（登录/实名）、`*.xdrnd.cn` `*.xdrnd.com`（SDK 网关/门槛）、`*.alipay.com`、`open.e.189.cn`。
- 时机：我们的 so 由 `StarryInitProvider`（ContentProvider，早于 `Application.onCreate`）加载，
  实测 `23:59:45.673` 加载 so，而 `cn.fly.FlyApplication.onCreate → FlySDK.init` 在其后
  ⇒ **构造器里装 hook 一定早于 Mob 初始化**；`Match2_TryInit()` 里再兜底重试一次。

#### L2 BI 漏斗（为什么拦得住）

- `BINetworkManager.CustomSend` 是**唯一真正发送器**：`Send` 只是转发、`CachedSend` 只写本地缓存；
  上游 `BIRequest` 8 个出口（`GeneralSend`/`CommonAction`/`ReportDeviceInfo`/`EndQuest`/`Tutorial`/`SkipTimeline`/`NetLibRecords`/`Question`）。
- C#/native 侧还有入口：`BIRequest` 模块加载时会把 `CS.LuaManager.Instance.LuaBISend = BIRequest.CommonAction`，
  所以换完表字段后**必须重指一次**（`kAcScript [[5]]`，每次同步都重指，热重载后自动恢复）。
- BI 走的是**游戏自家域名**（`NetworkUtility.GetBiUrl` = `%s/bi/%s/%s`，host 来自 `NetworkUtility.BIHttpUrl`）
  ⇒ DNS 层拦 BI 会连坐登录/进度，只能在 Lua 层拦。
- 附带：`ChannelTapReport._ReportEvent`（TapDB 真发送器）、`GameConfig.UpdateBuglyReportSceneData` 等三个 Bugly 场景埋点、
  `BIActionManager.OnEvent`（BI 已死，入队只会白涨内存）。

## 三、诊断与验证

- **诊断状态**：Lua 全局 `_G.__starry_ac_state`（计数）：`acSkip`（被跳过的重放校验次数）、
  `acWin`（被拦掉的作弊弹窗次数）、`biBlock`（被拦的 BI 发送次数）、`tapBlock`、`buglyBlock`；
  首次武装会打一行 `[StarryACG] 过检测=… 弹窗兜底=… BI出口=… BI收口=… 渠道=… Bugly=… BIAction=…`。
- **logcat 锚点**：
  - `[Match2] 上报拦截武装完毕：DNS 黑名单 N 个入口（后缀数=13）`
  - `[Match2] 反作弊压制/上报拦截武装完成 (__starry_ac=1)`
  - `[Match2] DNS BLOCK <host>` / `[Match2] DNS allow <host>`（首见各打一次，用于确认黑名单命中与误伤）

## 四、不做什么 + 为什么（诚实边界）

1. **不拦 `ApiRequest` / `ApiClient`（含回放字段、主关卡结算）**：这是玩法主链路，拦了会掉线/卡进度，
   与「不影响正常游戏」冲突。
2. **不改 `AntiCheatManager.SetCheatCheckCount`**：观察期计数照原语义递减并回传
   （`SaveCustomData` → 服端）。若把它强行清零/静默，反而会造出「有观察期却不递减」的异常序列
   —— 这正是「缺失一条上报本身就是特征」的坑。
3. **不禁止、只压判定**：本地重放校验是「判定」而非「上报」，压掉它不会在服端留下缺报痕迹；
   真正的上报（BI）以空实现拦下，属阻断式，代价是服端 BI 分析看不到本机会话 ——
   已有「BI 完全静默」这一特征风险，换到的是伤害异常/时长异常等**强判据不出设备**。二者取其一，本轮选后者。
4. **不碰回放数据本身**（`ReplayRecord` / `ReplayInput`）：断线恢复、PvP 回放依赖它；改坏会导致战斗异常。
5. **未做服务端验证**：本方案只覆盖客户端可见出口，服端是否有其它旁路（如结果侧二次校验）无法从静态分析证实。
   这是**推断**，实测口径：本轮装机后需真机打几场带功能的战斗，观察 `acWin` 是否始终为 0、`biBlock` 是否随 BI 调用递增。
6. `Utility.IsSpecialCheatUser` 全仓只有它自己引用，且实现是 `return false, nil` 的空壳（已停用），**不作为依赖**。
