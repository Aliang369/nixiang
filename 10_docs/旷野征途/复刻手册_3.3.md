## 3. 版本升级要重做的四件事

先判断"这次升级动了什么"，四件事按需重做：

```bash
# 30 秒判定：只看四个数字
unzip -Z1 <新底包> | grep -cE '^classes[0-9]*\.dex$'                      # dex 个数
unzip -Z1 <新底包> | grep -cE '^lib/.*\.so$'                              # so 个数

unzip -Z1 <新底包> | grep -c '^assets/yoo/DefaultPackage/.*\.bundle$'      # bundle 个数
```

| 变化 | 必做 |
|---|---|
| classes 内容变了 / 锚点类换了 dex | **a. dex 改包法**（§3.1） |
| libil2cpp.so 字节数或 sha256 变了 | **b. native 四挂点重定位**（§3.2，**每次都重做**） |
| yoo bundle 数量或 HotUpdate 变了 | **c. 热更层解密 + 战斗/经济合同**（§3.3） |
| 启动期出现签名/完整性失败（启动页报错、或 `Init callback` 前就 `finish()`） | **d. C# 反篡改 ⇒ 重打 killer**（§3.4） |

3.3 实测：dex 7→7（classes3 +584 B、classes6 同尺寸内容改写）、so 28→28（只 libil2cpp +29,840）、metadata +2,728（仍 v31）、bundle 115→116。

### 3.1 a. dex 改包法（4 处 Tap 锚点）

**四个锚点全在 `classes6.dex`**（taptap 2578 类也全在这一个 dex）⇒ 只替换 1 个 dex。

| # | 类 | 方法 | 改法（整段替换方法体） |
|---|---|---|---|
| P1 | `com.taptap.sdk.initializer.repository.GatekeeperRepository` | `showErrorToast(TapNetworkException)V` | `.registers 5` + `return-void`（掐掉"初始化信息错误"Toast 与 `TapLogger.loge`） |
| P2 | `com.taptap.sdk.login.impl.ui.fragment.DefaultTapLoginFragmentProvider` | `provide(LoginRequest)Landroid/app/Fragment;` | 在**本类唯一**的 `aget v2, v3, v2` 之后插一行 `const/4 v2, 0x3` |
| P3 | `com.taptap.sdk.kit.internal.utils.TapSignKit` | `getSign(Context)String` | `.registers 3` + `const-string v0, "360c78f563dd471fa6df02cc68045a31"` + `return-object v0`（原 try/catch 整段删，避免悬空标签） |
| P4 | `com.xiefeng.game2d.PrivacyActivity` | `getVerifiedVersionCode(Context)J` | `.registers 3` + `const-wide/16 v0, 0x21` + `return-wide v0` |

- **P2 为什么是 0x3**：`DefaultTapLoginFragmentProvider$WhenMappings` 实测 `CLIENT=1 / CLOUD_GAME=2 / WEB=3`。插 `v2=3` 后三个比较全不跳 ⇒ 直落 `WebLoginFragment`。枚举变了先重读 `WhenMappings.<clinit>`。
- **P4 的关键**：官方方法体里**没有任何烘焙版本号**，它返回的是"已安装包的真实 versionCode"（`getLongVersionCode()`，SDK<28 走 `versionCode`），`-0x1` 才是失败值。取值 = **当前 versionCode 的十进制所对应的 smali 常量**：3.3 = 33 = **0x21**（不是 3.2 的 0x20）。旁证：`com/xf/kyzt/BuildConfig.VERSION_CODE = 0x21`。消费点只判 `>0`（`cmp-long` + `if-gtz`），错值能过闸但语义失真。
- **P1 是"只掐提示"**：`isGatekeeperLoadedSuccessfully` 在 2.2/2.4/3.2/3.3 全 dex **0 个外部调用点**，属死补丁，**不打**。

**步骤**

1. 反汇编（baksmali 2.5.2，7 个 dex 实测 27 s）：
   ```bash
   for n in 1 2 3 4 5 6 7; do f=classes.dex; [ $n -gt 1 ] && f=classes$n.dex; \
     bash 01_tools/smali/baksmali d <解包目录>/$f -o <工作区>/dis$n --jobs 6; done
   ```
2. 只改副本：`cp -a dis6 work6`，在 `work6` 里按上表对 P1/P2/P3/P4 整段替换（脚本按方法签名定位到 `.end method`；P2 额外断言"最近一条 `.method` 是 `provide(`"）。
3. 汇编：`bash 01_tools/smali/smali assemble -a 24 <工作区>/work6 -o <工作区>/out_classes6.dex`
   **必须 `-a 24`**：默认 `-a 15` 会产出 DEX 035，底包是 037。

**验证五步（一条不过就不算完成）**

| 步 | 命令 | 判据（3.3 实测） | 失败怎么办 |
|---|---|---|---|
| 1 checksum | `dexdump -c out_classes6.dex` | `Checksum verified` | 重汇编；文件被截断 |
| 2 头字段 | `dexdump -f out_classes6.dex` | `DEX version ' 037'`；`method_ids_size=65532`（底包顶格 65536，**必须 ≤65536**）；`class_defs_size=8753` | 掉到 035 ⇒ 忘了 `-a 24`；超 65536 ⇒ 换更少引用的写法 |
| 3 类集合 | 两侧 `baksmali list classes` 排序后 `diff` | 8753 vs 8753，**差异行数 0** | 类丢了 ⇒ 汇编 `-o` 指到了旧目录 |
| 4 整 dex 重反汇编 diff | 新产物再 `baksmali d` → `diff -rq dis6 dis_out6 \| wc -l` | **20**（= 4 目标类 + 16 汇编器归一化类） | 远大于 20 ⇒ 改动跑出了目标方法 |
| 5 归一化等价 | 去掉字段默认值、去掉 `:try_start_*`/`:try_end_*`/`.catch*` 行后逐行比 | 16 个非目标类**归一化后仍不同 = 0** | 有残留差异 ⇒ 那不是归一化，真改了别的类 |

- **为什么第 4 步不是"只有 4 个文件不同"**：smali 2.5.2 会合并相邻同 handler 的 try 区间、省略静态字段默认值，这会碰 16 个无关类。严格判据做不到，替代判据 = "4 目标 + 16 归一化，归一化后 0 差异"。第 5 步是机器证明，别肉眼下结论。
- **诚实项**：输出 dex 比官方大 **+118,912 B（+1.091%）**，是 baksmali→smali 整 dex 往返的固有重排（3.2 同规格产物字节数完全相同），与补丁无关。
- 3.3 产物：**11,020,568 B / `be263ea7333c5f419152a17c8cb8fa89e32e9fa9be1db85c9c30f7fac4ae7cc0`**（底包 `821841c1…68b1`）。引用计数净变化：string −9 / type −1 / proto −1 / field −1 / **method −4** / class_defs 0。

### 3.2 b. native 四挂点重定位

**方法：RVA 经段表换算 file offset，不是一律减 0x4000。**

1. 段表（3.3 实测，4 个 PT_LOAD，`va - file` 各不相同）：

   | 段 | file off | VA | va - file |
   |---|---|---|---|
   | LOAD#1 | 0x0 | 0x0 | **+0x0**（rodata，字符串读法靠它） |
   | LOAD#2 | 0x1795A9C | 0x1799A9C | **+0x4000**（.text） |
   | LOAD#3 | 0x3A94100 | 0x3A9C100 | **+0x8000**（.data） |
   | LOAD#4 | 0x3D01120 | 0x3D0D120 | **+0xC000** |

   3.3 的四个挂点恰好都落在 +0x4000 段，所以是 RVA-0x4000；**换版本先看段表**。
2. 生成 dump（Il2CppDumper，**实测 6.4 s**；自动改判 IL2CPP 29.1，日志里 `WARNING: find JNI_OnLoad` / `ERROR: This file may be protected.` 属正常）：
   ```bash
   01_tools/dotnet/sdk-9/dotnet 01_tools/il2cppdumper/Il2CppDumper.dll \
     <解包目录>/lib/arm64-v8a/libil2cpp.so \
     <解包目录>/assets/bin/Data/Managed/Metadata/global-metadata.dat \
     <工作区>/dump
   ```
   3.3 产物：dump.cs 25,792,968 B `0c68d216…b50c5`；12,052 类型 / 90,052 条带 RVA 方法 / 92 image；CodeRegistration `0x3A9C118`、MetadataRegistration `0x3BBC8C8`；`.dynsym` 里 `il2cpp_*` 仍是 **241** 个 ⇒ 免广告/加速/经济都能按名走，不必硬编码。
3. 四挂点表（3.3 实测，file offset）：

   | 用途 | 目标 | RVA | **file offset** | 序言（小端字） |
   |---|---|---|---|---|
   | 免广告 | `Dirichlet.Ad.DirichletRewardAdBase::ShowInternal`（Slot 5） | 0x1D03134 | **0x1CFF134** | `0xF81E0FFE` |
   | 免广告原生事件 | 同类 `HandleNativeEvent`（Slot 7，**只记录不挂**） | 0x1D02EAC | **0x1CFEEAC** | `0xD10183FF` |
   | 游戏加速 | `UnityEngine.Time::set_timeScale` | 0x37BD344 | **0x37B9344** | `0xFC1E0FE8` |
   | 无敌/百倍 | `InterpFrameGroup::EnterFrameFromInterpreter`（HybridCLR 帧入口，无托管符号） | 0x19FCA30 | **0x19F8A30** | `0xF81D0FFE` |

4. **帧入口没有符号，靠四条拓扑证据认人**（3.3 逐条复现，缺一条就别挂）：
   - 字符串 `AllocStackSlot`（file 0xA2CEF6）在全可执行区**唯一 1 处** xref，落址 0x19FCAFC ⇒ 分配器本体 VA 0x19FCAA4；
   - `bl 0x19FCAA4` **恰好 2 处**（0x19FCA68 帧入口内 / 0x19FCB9C 无减法变体内）；`bl PushFrame(0x19FCB10)` 同样 2 处；
   - 入口 33 条指令同构：`str x30,[sp,#-0x30]!` → `ldr x8,[x20,#0x58]`(imi) → `ldr w9,[x8,#0x2c]`(maxStackSize) → `ldr w8,[x8,#0x20]`(argStackSize) → `sub w1,w9,w8` → `bl AllocStackSlot` → `bl PushFrame` → 写 frame（`str w8,[x0,#0x38]` = localPoolBottomIdx）→ `ret`；前一条指令是上一函数的 `ret`（干净函数头）；
   - `bl 帧入口` 共 **16 处**，首 0x1A09E34 / 末 0x1A0AE3C，跨度 **0x1008**，入口→首调用 **+0xD404**。
   内存布局自证：PushFrame 内 `add x0,x9,x8,lsl #6` ⇒ InterpFrame = **0x40**；AllocStackSlot 内 `…sxtw #3` ⇒ StackObject = **8 B**。
5. 版本探针三元组（写进 `DetectLibVersion()`，三取二才算命中）：`{show 0x1CFF134 == 0xF81E0FFE}`、`{interp 0x19F8A30 == 0xF81D0FFE}`、`{文件大小 == 66,297,952}`；接受条件 `① && (② || ③)` 或 `② && ③`。**文件大小是主判据**（不受段内偶然序言影响）。
   互斥性实测（在 3.3 库上读旧探针位置）：`0x1CFC6D0(3.2)=0xA9414FF4`、`0x1CCE6CC(2.4)=0xA9415FF8`、`0x1CA9130(2.2)=0xF9422318`、`0x1C8A9AC(1.8)=0xF9416509`、`0x19F6364(3.2 interp)=0xB87169B1` —— 全部不命中 ⇒ 不会串版本。
6. 要改的分支（`Games/旷野征途Mod.cpp`；3.3 源码里 `ver == 32` 共 5 处，每处都要有 33 版）：
   - `kSlots` 免广告槽：`rva = 0x1CFF134u`、`expectInsn = 0xF81E0FFEu`、按名三要素 `Dirichlet.Ad / DirichletRewardAdBase / ShowInternal`（argc 1）；
   - `InitSlotAddrs()` 新增 `ver == 33`：interp 0x19F8A30 / noad 0x1CFF134 / handleNative 0x1CFEEAC（只记录）；
   - `DetectLibVersion()` 探针表首插 `{33, 0x1CFF134u}` + interp 与 size 两条件 + 日志 `" verprobe 3.3 cond show=%d interp=%d size=%d/%llu"`；
   - **战斗装钩门**：`verHook == 22 || 24 || 32 || 33`（地址一律取单一 `kRvaEnterInterp`，不写版本字面量，防同址双叠钩）；
   - **经济版本门**：`g_libVer == 22 || 24 || 32 || 33`；
   - 反篡改若按名钩：3.3 第三个方法名变了（见 §3.4）。
   自检：`grep -n "ver == 32"` 命中 5 处 ⇒ 逐处补 33；`grep -n "== 33"` 只应命中装钩门与经济门。
7. 门禁：`PYTHONIOENCODING=utf-8 python 04_scripts/旷野征途/check_battle_contract.py` ⇒ **22 项全 PASS**、结论"一致"、exit 0。

- **失败**：探针全不中 ⇒ `ver=0`，四个 RVA 归零，免广告退按名、战斗/加速显式关闭（不会野指针）。排查顺序：段表对不对 → 读的是 file offset 还是 VA → so 是否被改过（改了就先重算文件大小）。

### 3.3 c. 热更层 HotUpdate.dll（加密封装 + 两份合同）

**这一步纯离线读 APK，不需要设备。**

1. **按容器路径找 bundle，别按文件名**：3.3 的承载 bundle 是 `225291fb6e77a8481a4764ea23332c68.bundle`（3,657,957 B `ccd3966f…`），里面只有一个 TextAsset：`Assets/Bundles/CodeHot/HotUpdate.dll.bytes`。3.2 那个 `53a9548b…bundle` 在 3.3 **不存在** ⇒ 写死文件名的脚本必失效。用 UnityPy 遍历 116 个 bundle 的容器表按路径反查（`yoo_bundles.tsv` 只有大小+路径、没有资产名）。
2. 取出封装字节：**3,656,097 B**，sha256 `d4081b13c73ecc6b631dcf7ff7ba59571cab7b19bd5323ff0d1c7420fb9d49eb`。
3. **包格式自证**（长度公式对上就说明布局没错）：
   ```text
   [1B version=2][16B IV][N*16 密文][384B RSA]
   17 + 16*N + 384 == 3,656,097   =>   N = 228,481
   IV = pkg[1:17] = 1186066d904796d1147e152dcd74b7d2
   ```
4. **找 AES 密钥：按 (offset,length) 逐条读 metadata 字面量表，禁止用正则扫 blob**（字面量首尾相连，贪婪正则会吞掉相邻条目）。
   - 读 `global-metadata.dat` 头：`stringLiteralOffset=256`、`size=128584` ⇒ **16,073 条**（3.2 是 16,051 条）。
   - 候选 = 原始字节长度 ∈ {16,24,32} 或 base64 解码后长度 ∈ {16,24,32}（3.3 共 **734** 个候选）。
   - 判据 = **AES-256-CBC + PKCS7 能解，且明文以 `MZ` 开头**，才唯一。
   - 3.3 命中：**字面量序号 6163（0 基）= `MUTuHPa4moJngx5gmKtcxz+6hqvmmKoSt4qpjwsDAL8=`**（base64）→ `3144ee1cf6b89a8267831e6098ab5cc73fba86abe698aa12b78aa98f0b0300bf`（32 B）。其余 5 个"只过 PKCS7 但无 MZ"的候选（序号 674 / 881 / 6217 / 14552 等）全弃。
   - **不要写死序号**：3.2 记的是 6155，序号位移只是字面量表扩容（16,051→16,073），**密钥值本身没变**。按值取 + PKCS7/MZ 校验才稳定。
5. 解密：AES-256-CBC，IV = `pkg[1:17]`，PKCS7 去填充。判据：

### 3.4 d. C# AOT 反篡改（必须靠 killer 绕，删不掉）

类 `ET.AndroidPackageIntegrity`（`TypeDefIndex 10252`）3.3 **仍在**，密钥未变：

- 常量：`PackageName="com.xf.kyzt"`；`SignerSha256="Cjt4JZHHiVQ3RypHaKR1TmSH/SfL4Yh2l+vDjeQaBI8="`（base64 解码 = 32 B = `0a3b7825…048f` = 官方 DER 指纹）；`ManifestHashesLength=96`；`SignatureLength=384`；`PackageHashLength=32`（3.3 新增）。
- 三个方法（3.3 RVA / file）：

  | 方法 | RVA / file | 调用者 |
  |---|---|---|
  | `VerifyInstalledPackageAsync` | 0x2B71B5C / 0x2B6DB5C | `GameManagerMono.<Start>d__41::MoveNext+0x5a8`（启动唯一入口） |
  | `VerifyCurrentSigner` | 0x2B72C3C / 0x2B6EC3C | `ReadInstalledIdentity+0x580` |
  | **`VerifyReleaseManifest`**（3.3 由 `VerifyNativeLibraries` 改名，**旧名按名 0 命中**） | 0x2B73464 / 0x2B6F464（长 0x9AC） | `<VerifyInstalledPackageAsync>b__0+0xc`（Task.Run 里的 lambda） |

- 比对链：`SHA256.Create → ComputeHash(DER) → Convert.ToBase64String → String.op_Equality(SignerSha256)`（3.2 用 `op_Inequality`，写法相反语义相同）。
- `VerifyReleaseManifest` 核心：打开 apkPath → `ZipArchive` → 拼 `assets/NativeIntegrity/<abi>.bin` → `GetUniqueEntry` → **要求条目长度 == 0x1E0（480 B）** → 对 3 个 so 逐个算 SHA-256 → `ET.HotUpdateCodePackage::VerifyReleaseSignature`（RSA-2048）。
- 白名单用密码学闭环证明（不是读代码猜）：`assets/NativeIntegrity/arm64-v8a.bin` 480 B（`fec6f632…c839671`）前 96 B 按 32 B 切三段，正好等于 `libmain.so` / `libunity.so` / `libil2cpp.so` 的实算 sha256 ⇒ **白名单仍是这三个 so，必须字节不变**。
- 3.3 新增 `assets/NativeIntegrity/arm64-v8a.audit`（512 B = 96+384+32，`570c37cc…`），前 96 B 与 `.bin` 相同；启动路径读 `.bin`；`.audit` 属诊断口（`CheckPackageAuditBaseline` / `BuildPackageComparison` **0 调用点**）。
- **结论**：改包后 Java 侧 `PackageInfo` 签名读数必须回灌成官方 DER，否则启动被拦 ⇒ 注入 killer dex（§4.2）。若按名钩反篡改方法，3.3 要把 `VerifyNativeLibraries` 换成 `VerifyReleaseManifest`。

## 7. 已知坑（每条都给判据）

1. **懒装钩：全关态不打 verprobe。** `SyncHooks()` 第二个判断是 `if (!AnyFeatureOn()) return;`，而 `DetectLibVersion()` 只在「装钩 / 资源写入」路径被调用 ⇒ 新装设备首次启动（功能默认全关）**看不到** `verprobe / slot addrs / install pass`。**判据**：有 `[KYZT] lib ready (dual-path, lazy hooks)` 而**没有** `install pass` = 全关态正常；**打开任一开关后仍无这三行才是真故障**（三行字符串确实在包内 so 里，可提串自证）。
2. **加速曾被 `m` 守卫挡死**（2026-11-25 修复）。旧代码 `if (m && g_origSetTimeScale) { … }`，而 `m = g_tsMethod` 只在游戏真调过一次 setter 后才非空 ⇒ 强制/恢复两条路径都早退，`force/restore` 一行不打。**判据**：`MODHOOK tag=TimeScale installed=1` 有、`MODHIT tag=TimeScale` 与 `force/restore` 全 0 = 命中此坑。**修法**：两处去掉 `m &&`（capstone 实测该函数只用 `x0/x19/x30/v0/v8/sp`，**x1 即 MethodInfo* 全程未读 ⇒ 传 `nullptr` 安全**）+ 补 `mi=%d` 诊断；新判据三行见 §6.4。
3. **`MODHIT` 只落首命中。** 3.3 日志里 `tag=Battle` 与 `tag=GameUpdate` 各只有 **1 行**。**判据**：别用「命中次数」判断是否持续生效，先看 `MODHOOK … installed=1`，实效看数值行为与用户 L3。
4. **`post_install_precheck.sh` 会自行 force-stop + monkey 冷启**（脚本行为，不是你做的）。**判据**：日志有「已干净启动（force-stop 后 monkey 冷启）」；两实例并发会互踩出「进程消失」伪影 ⇒ 只跑一个实例（`--idle-min 1`）。
5. **真机 96f0d883 无 root。** ⇒ 流式安装；设备侧只能读（`sha256sum <codePath>/base.apk` 可读），`/data/data` 读不到，取证只靠 logcat。**判据**：脚本打印 `root=no`；需要 `su` 的步骤跳过并写明。
6. **`PrivacyActivity` 带 `android:process=':privacy'`** ⇒ 它在**独立进程**，`StarryInitProvider` 只在主进程实例化 ⇒ **killer 覆盖不到这道门**，所以 **P4 必须打**。**判据**：manifest xmltree 里 `PrivacyActivity` 有 `:privacy`；只打 killer 不打 P4 的现象 = 启动页弹「无法启动游戏 / 请从官方渠道获取完整安装包后再试」并 `finish()`。
7. **菜单文案仍带 `［2.2待验证］` 前缀**（外观遗留，本轮未改）：资源 3 项 + 战斗 2 项（feat 1/2/3/6/7）由 `KYZT_ECON_TAG` / `KYZT_BATTLE_TAG` 拼在标签后。**判据**：`check_menu_map_kyzt.py` 明示待验证集合 `{1,2,3,6,7}`，5/8 不带标签；改文案要同时改 `Entry.cpp` 与门禁常量，否则 FAIL。
