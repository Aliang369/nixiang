## 6. TapTap 登录打通（2026-11-09 21:20，关键）

**症状**：`[TapTap] Init callback failed: code=1001, message=TapSDK: 包名、签名错误` → 初始化失败，游戏卡「初始化TapTap服务」30s。

**根因**：TapSDK 4.10.9 在 init 阶段把包名+签名上报服务端比对后台登记，返回 1001。本地门闩（`isGatekeeperLoadedSuccessfully`／`showErrorToast`／登录路由改 Web）只能治本地判定，**治不了服务端验签**。

**解法（来自斌哥 1.4 改包）**：包里带 MT 签名杀手 dex —— `bin.mt.signature.KillerApplication193`（13,680 B，含 12 个内部类），硬编码官方 `O=xiefeng` 证书 base64，运行时替换 `PackageInfo.CREATOR` + 清 `PackageManager.sPackageInfoCache`／`Parcel.mCreators`。

**落地**：
1. 从 `旷野征途_1.4_binge_from_device_base.apk` 的 `classes2.dex` 取出，baksmali 后把 `.super Lcom/xf/kyzt/nxtOVAnjgXtvKSmcPLPj;` 与其 `<init>` 调用改成 `Landroid/app/Application;`（1.8 官方 manifest 无 `android:name`，走默认 Application；1.4 的混淆类 1.8 已不存在）。
2. smali 重组为 `killer.dex`（13,692 B）→ 作为 `classes3.dex` 注入（`07_patched/旷野征途/surgical/killer.dex`）。
3. 框架侧无需改：`StarryAppComponentFactory.mountSignatureKiller()` 用 `Class.forName(...,initialize=true)` 触发其 `<clinit>`。

**验证**：`SignatureKiller mounted: PackageInfo.CREATOR replaced`；`certificateSHA256=0a3b782591c78954...`（官方）而非 `83c5cc0b...`（我们的）；`[TapTap] Init callback success: accepted=True`；进入 `TapTapLoginActivity` 并登录成功进游戏；菜单 overlay 在登录页与游戏内均 `attached=true`。

**通用性**：MT 签名杀手 + `super` 改 `android.app.Application` 这套对「TapTap 渠道 + 官方包无自定义 Application」的游戏可复用；底包有自定义 Application 时则需把 super 改成该类的真实类名。

## 9. 战斗功能挂点定位（2026-11-09 23:30，IDA 静态 + frida 运行时取证）

### 9.1 结论先行：ApplyHp 没有 native RVA

用户原计划「IDA 定位 `BattleRoleActor.ApplyHp/4` 的 RVA」**在证据上不成立**，原因链：

| 证据 | 内容 |
|---|---|
| 主 metadata | `global-metadata.dat` 全文 `strings` 检索 `BattleRoleActor` / `ApplyHp` / `AccountMgr` **0 命中**；`dump.cs` 中 `Assembly-CSharp.dll` 区间仅 7 行（空壳） |
| 运行时 assembly | 89 个 image，末位为 **`HotUpdate.dll`（1859 个类）**，`Battle.BattleRoleActor` 在其中 |
| methodPointer | `ApplyHp` / `AddHp` / `DealBladeSector` / `PlayPoisonBurstVisual` / `InitRole` 等**全部共享同一个 mp**（本次会话 `0x772a715d14`= base+0x198bd14）⇒ HybridCLR 解释器桩，方法体是 IL，不是机器码 |

⇒ 战斗逻辑全部在 HybridCLR 解释层，libil2cpp.so 里不存在 `ApplyHp` 的函数体，IDA 无 RVA 可指。

### 9.2 真正可挂的 native 点：`InterpFrameGroup::EnterFrameFromInterpreter`

解释器每进入一个热更方法必经此函数（native），hook 它即可按 MethodInfo 过滤到 `ApplyHp` 并改参数。

| 项 | 值 |
|---|---|
| VA | **0x198b6a8** |
| file offset | **0x19876a8**（`va − file = 0x4000`，与先例同规则） |
| 序言指令 | `str x30, [sp, #-0x30]!` = **0xF81D0FFE**（运行时读回一致） |
| 签名 | `(void* self /*frameGroup*/, void* methodInfo, void* argsPkt)` |

**判定依据（四条独立证据）**：

1. 全 `.text`（36.7 MB）按先例签名（`mov x20,x1` + `ldr x8,[x20,#0x58]` + `ldr w9,[x8,#0x2c]` + `stp x20,x19,[x0]`）扫描 **仅 1 处命中** = 0x198b6c0（函数入口 0x198b6a8）。
2. 逐指令与先例语义一致：`ldr w8,[x8,#0x20]`(argStackObjectSize) → `sub w1,w9,w8` → 两次 `bl`(AllocStackSlot) → `stp x20,x19,[x0]`(帧压入 {MethodInfo, argBase}) → `str w22,[x0,#0x10]`。
3. BL 引用统计：**16 处，全部落在 0x1998aac–0x1999ab4**（约 0x1000 区间）⇒ 即 `Interpreter::Execute` 函数体内，符合「被 Execute 稀疏引用」语义。
4. 相邻函数边界干净：前一函数以 `ret` 结束于 0x198b6a4。

本 so 与「长生天机降世 1.0.3」同 HybridCLR 版本（`ldr x20,#0x58` / `ldr w9,[x8,#0x2c]` 偏移完全一致），故先例的 hook 语义可直接复用。

## 10. 战斗功能首轮落地的两个致命 bug（2026-11-09 23:55）

首包装机后用户实测「无敌 / 百倍伤害都没效果」。排查所得（结论均有落盘证据）：

### 10.1 BUG-1：Tick 里无节流跑全 image 类扫描 ⇒ 装钩从未执行

- `ResolveCombatMi()` 最初写成「每 Tick（200 ms）无条件调 `FindClassByShortName("BattleRoleActor")`」。
- 该 API 对热更类会退化到 `ClassFromNameScan`（89 个 image × 1859 类线性扫名），单次代价极高。
- 后果：Tick 线程被拖死 ⇒ `SyncHooks()` 长龙排在后面永不执行 ⇒ 内存验证 `libil2cpp+0x198b6a8` 仍是原始序言 `0xF81D0FFE`，**钩子根本没装**。
- 修复：解析节流为 5 s 一次（25 × 200 ms），且累计 40 次后放弃；`SyncHooks` 加 8 次重试上限，禁止每 Tick 反复 DobbyHook 同址（骨架既有禁忌）。

### 10.2 BUG-2：用全局 `g_reenter` 做去重 ⇒ 内层 ApplyHp 被整条挡掉

- 骨架的 `g_reenter` 本意防递归，但**解释器入口是可重入的**：ApplyHp 绝大多数是被别的热更方法（技能/AI/伤害流程）内部调用的，那时外层方法已进过一次 hook、全局标志为 true ⇒ 内层的 ApplyHp 直接走快路径放行，伤害处理永远不触发。
- 修复：改为 `static thread_local bool t_inApplyHp`，只挡 ApplyHp 自身递归。

### 11.2 事件模型（DirichletNativeEvent）

```
struct DirichletNativeEvent {

class DirichletNativeEventData {
    bool  RewardVerify;  // 0x10

    string RewardName;   // 0x18
```

`DirichletRewardAdBase::HandleNativeEvent(nativeEvent)` 是所有广告事件的唯一入口
