## 6. TapTap 登录打通（2026-11-09 21:20，关键）

**症状**：`[TapTap] Init callback failed: code=1001, message=TapSDK: 包名、签名错误` → 初始化失败，游戏卡「初始化TapTap服务」30s。

**根因**：TapSDK 4.10.9 在 init 阶段把包名+签名上报服务端比对后台登记，返回 1001。本地门闩（`isGatekeeperLoadedSuccessfully`／`showErrorToast`／登录路由改 Web）只能治本地判定，**治不了服务端验签**。

**解法（来自斌哥 1.4 改包）**：包里带 MT 签名杀手 dex —— `bin.mt.signature.KillerApplication193`（13,680 B，含 12 个内部类），硬编码官方 `O=xiefeng` 证书 base64，运行时替换 `PackageInfo.CREATOR` + 清 `PackageManager.sPackageInfoCache`／`Parcel.mCreators`。

**落地**：
1. 从 `旷野征途_1.4_binge_from_device_base.apk` 的 `classes2.dex` 取出，baksmali 后把 `.super Lcom/xf/kyzt/nxtOVAnjgXtvKSmcPLPj;` 与其 `<init>` 调用改成 `Landroid/app/Application;`（1.8 官方 manifest 无 `android:name`，走默认 Application；1.4 的混淆类 1.8 已不存在）。
2. smali 重组为 `killer.dex`（13,692 B）→ 作为 `classes3.dex` 注入（`07_patched/旷野征途/surgical/killer.dex`）。
3. 框架侧无需改：`StarryAppComponentFactory.mountSignatureKiller()` 用 `Class.forName(...,initialize=true)` 触发其 `<clinit>`。

**验证**：`SignatureKiller mounted: PackageInfo.CREATOR replaced`；`certificateSHA256=0a3b782591c78954...`（官方）而非 `83c5cc0b...`（我们的）；`[TapTap] Init callback success: accepted=True`；进入 `TapTapLoginActivity` 并登录成功进游戏；菜单 overlay 在登录页与游戏内均 `attached=true`。

**通用性**：MT 签名杀手 + `super` 改 `android.app.Application` 这套对「TapTap 渠道 + 官方包无自定义 Application」的游戏可复用；底包有自定义 Application 时则需把 super 改成该类的真实类名。

### 7.1 已确认的 1.8 数据结构（可复用，勿再重复诊断）

- `AccountMgr.instance`(静态, off=0) → `AccountInfo` 字段 **off=40**；`needSave` off=120
- `AccountInfo`：`players`(96, List<PlayerInfo>)、`points`(152, **Int64**)、`sharedGold`(168, **Nullable<Int64>**：has@+0/value@+8)、`warehouse`(184, AccountWarehouse)
- `AccountWarehouse`：`items`(24, List<ItemSaveData>)、`runtimeItems`(40, List<ItemRuntimeData>)、`capacity`(16)
- `ItemSaveData`：`count`(16)、`itemSaveid`(40)、`baseAttributes`(48)、`qualityAttributes`(56)、`enchantAttribute`(64) 等 20+ 字段
- `ItemManager`：**无 AddItem**；有 `GetNewItem/1 (Int32)→ItemRuntimeData`、`GetAll/0→Void`、`OnGetItem/1 (MapItem)→Boolean`、`SpawnItem/4`、`ChangeGold/1`、`get_gold/0`
- `ItemManager.instance` 与 `BattleRoleActor.instance` **均为 null**（非静态单例持有）

### 7.2 添加道具的失败路径（7 次，均被保护区拦截，游戏未崩）

1. `AddItem(id,count)` → 1.8 无此方法
2. `OnGetItem(int)` → 参数实为 `MapItem`（地图掉落物），SIG@0x27a6
3. `GetNewItem(id)` 传堆扫描实例 → SIG@0x0
4. `GetNewItem(id)` 传 nullptr → SIG@0x0（非静态方法，或 MethodInfo 不可直接 invoke）
5. 追加到 `warehouse.runtimeItems` → 未触发（上一步就失败）
6. `ItemManager.ChangeGold(int)` → SIG@0xb8（参数应为 Int64）

**结论**：1.8 的物品系统与 1.4 差异大（1.4 的 `AddItem` 已删），要通需要"构造 ItemSaveData 新对象并插入 items 列表"或"用 SpawnItem 走地图掉落"，两者都需再深挖一轮。

### 7.4 添加道具最终结论（2026-11-09 22:50）

**可用**：背包里**已有**的同名道具，按下拉选择 + 数量输入可以精确加量。
- 数据源：PlayerInfo.saveBags（List<ItemSaveData>）＋ PlayerInfo.bags（List<ItemRuntimeData>），两份都要改
- 物品 id 字段：ItemSaveData.baseItemid(off=164)、ItemRuntimeData.Itemid；数量字段都是 count
- 数量输入必须接 onInputChanged（Entry 里默认 nullptr），且 UI 是**失焦时**才回调

**不可用**：背包里没有的物品无法凭空创建。已排除的 7 条路径见 §7.2，另加：
- 克隆现有 ItemSaveData 改 baseItemid → 能进列表（saveBags、bags 都追加成功），但 UI 显示**乱码**：名称/类型/品质/属性字典全是模板的。
- 补 itemSaveid 唯一化（max+1）后仍乱码 —— 证明不是行号冲突，而是缺配置表数据。
- 拿配置表的入口 GetNewItem/1、GetItemByItemid/1、SpawnItem/4 在 1.8 上一律 SIG(11) @0x0（传实例、传 nullptr、堆扫描实例都试过）。
- 结论：造新物品必须在 il2cpp 侧正常调用配置表接口，该接口在当前注入环境下不可调用。**已移除克隆路径，避免继续产生脏物品。**

**乱码物品处置**：游戏内出售/丢弃该物品，或读档恢复（未触发存档时重启即回滚）。


### 7.5 新物品创建：HybridCLR 两条反射路径均封死（2026-11-09 23:05）

| 调用方式 | 结果 | 结论 |
|---|---|---|
| il2cpp_runtime_invoke | SIG(11) @0x0 | invoker 为空（HybridCLR 解释方法不填常规 invoker） |
| MethodInfo+0 methodPointer 裸调 | SIG(11) @0x9b13210dad578d | mp 非空(0x772c9de058)但签名不符：解释器入口是 (method,obj,args,ret) 布局，不是 (int,methodinfo) |

**配置池探查**：ItemManager 堆扫描到 53 个候选实例，inst[0].equipmentPoolItems(off=56)=0x76f38db100 非空（ConfigSet<ItemRuntimeData>）。
但对该泛型对象取 object_class/ClassName 会**在保护区外崩溃**（日志停在「ItemManager 实例 53 个」，进程退出），已移除该诊断。

**结论**：1.8 造新物品需要 (a) 按 HybridCLR 解释器约定调用，或 (b) 解析 ConfigSet 泛型容器结构；两者都超出当前注入框架的安全能力，且都容易崩游戏。
**不再尝试内存造物**。若要新物品，唯一剩余路径＝改存档文件（离线改、重启生效），需先解 AccountMgr.savePath + DecodeSaveText 的编码格式。

**当前稳定能力**（已装机验证）：金币+9999、积分+9999、游戏加速、背包已有道具按数量加量。
