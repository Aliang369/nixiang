# 静态闭环：伤害与属性（T12）

> 依据：`06_dumped/阿比斯少年冒险团/il2cpp_out/dump.cs` + `libil2cpp.so` 反汇编（capstone；RVA = dump 的 `// RVA:` = ELF vaddr = 文件偏移 + 0x4000）。
> 本轮**不接触设备**，全部静态证据。
> **越界污染声明**：方法内扫描按「方法起始 RVA + 固定条数」线性反汇编，未按真实函数边界裁剪，**短方法会读进邻居指令**。本文关键结论一律改用**单点窗口**（以目标指令为锚，向前回溯 0x40–0x80），标注【实测】的片段均为锚点窗口内的连续指令。
> 调用点统计用**全段线性扫描**（il2cpp 段一次扫完，43 s），按「最近方法起点 + 距离 < 0x2000」归属方法，存在少量误归属，量级可信。

## 1. 伤害落地路径

### 1.1 关键发现：`JJDKEBAMLNG` 是死代码

| 函数 | 全包调用点 | 结论 |
|---|---|---|
| `Unit::JJDKEBAMLNG(Unit, long)` RVA **0x354E28C**（L166928） | **0** | 无任何调用者（IFix 补丁点之外是死代码） |
| `Unit::JMIKMDBLCHB(Unit, long)` RVA **0x354B944**（L166967） | **1** | 唯一调用者 = `Unit::BLKEJBDMGAB` |

⇒ 上一轮把 `JJDKEBAMLNG` 当伤害入口是错的（它与 `JMIKMDBLCHB` 逻辑等价，但没人调）。**真正入口是 `Unit::BLKEJBDMGAB`。**

### 1.2 伤害入口：`Unit::BLKEJBDMGAB(EAGEDGNBJHM)`

| 项 | 值 |
|---|---|
| 签名 | `public void BLKEJBDMGAB(EAGEDGNBJHM GMLJOOEJCIE)` |
| 所属 | `Unit`（namespace 空） |
| RVA | **0x354B388** |
| dump 行 | **L166828** |
| 参数 | `EAGEDGNBJHM` = 伤害载荷结构（+0x10 int、+0x14 int、+0x18 阵营、+0x1C 伤害类型、+0x20 元素、+0x28 long、+0x38 long、+0x40 float、+0x44/0x48/0x4C …） |

~~~asm
; Unit::BLKEJBDMGAB  0x354B388（实测入口头部）
0x354B3A8  mov  x20, x1          ; x20 = 载荷指针（EAGEDGNBJHM*）
0x354B3AC  mov  x19, x0          ; x19 = this（Unit）
0x354B428  mov  w0, #0x90D8      ; IFix 方法 id
0x354B434  bl   WrappersManagerImpl::IsPatched
0x354B458  bl   ILFixDynamicMethodWrapper::__Gen_Wrap_215
0x354B45C  mov  x24, x0          ; 保存返回值
~~~

**伤害数值来源**：来自载荷 `EAGEDGNBJHM` 自带的数值字段（`+0x28 long`、`+0x40 float`），**不是**在函数内按属性 id 现算（属性计算发生在更上游的伤害构造处）。

### 1.3 唯一真实写入点 `JMIKMDBLCHB`（实测锚点窗口）

~~~asm
; Unit::JMIKMDBLCHB(Unit src, long delta) 逻辑段 0x354B9BC
0x354B9BC  ldr  x8, [x20, #0x1B0]   ; this.JAODIJCPHFL（Action<Unit,Unit,long>）
0x354B9C0  cbz  x8, 0x354B9E0
0x354B9C4  ldr  x9, [x8, #0x18]     ; delegate invoke
0x354B9DC  blr  x9                   ; raise 血量事件(src, this, delta)
0x354B9E0  ldr  w8, [x20, #0x150]   ; 阵营
0x354B9E4  cmp  w8, #1               ; == PLAYER
0x354B9E8  b.ne 0x354BA24            ; ★ 非 PLAYER 直接跳过，不写血量
0x354BA10  bl   0x7B0D8BC
0x354BA14  tbz  w0, #0, 0x354BA24
0x354BA18  ldr  x8, [x20, #0x190]   ; curHp
0x354BA1C  add  x8, x8, x19         ; += delta
0x354BA20  str  x8, [x20, #0x190]
~~~

**⇒ 落地公式（实测）**：`Unit+0x190 += delta`，delta 由 `BLKEJBDMGAB` 从载荷算出后以 x1 传入；**被 PLAYER 门控**，敌方单位走这条路不会写血量。

### 1.4 敌方血量路径：缺口（如实标注）

- `Unit` 内写 `+0x190` 的只有 `JMIKMDBLCHB`（1 个调用者）与两个无参方法 `HNNPDHDBACG`(0x35512F0)、`JBMGPALFFGB`(0x3552698)。
- 敌方受伤必有另一条路径，本轮**未定位**；最可能位置是 `KCPGOACDHOB`（Unit+0x38 驱动器）——它在 4 个方法里对**自己的** `+0x190/+0x198/+0x1A0` 三连写。
- 【待验证】敌方 HP 可能在驱动器对象而非 Unit 上。

## 2. 属性取值链：`CGIBCFFNFGL` 的真身

### 2.1 它是两层转发，不含合并逻辑

~~~asm
; PHBGLMHPMMC::CGIBCFFNFGL(KMLFBAENBMH) 0x36A2B30（L182407）
0x36A2B78  mov  x0, x20
0x36A2B7C  bl   PHBGLMHPMMC::OBKEGLFOOFC     ; 取属性容器 FPIALCOELGG
0x36A2B80  cbz  x0, 0x36A2B94
0x36A2B84  mov  w1, w19                       ; id
0x36A2B90  b    OKNDCLIKECF::FJMHJMEPFMC     ; 尾调用，容器侧分发
; ---- FJMHJMEPFMC ----
0x36A2C0C  ldr  x20, [x20, #0x50]             ; ★ 取 CGHEBBBLGLH : KEMEJCCDJKJ
0x36A2C20  ldrh w9, [x8, #0x12E]              ; 接口方法数
0x36A2C34  ldur x11, [x10, #-8] / cmp x11,x1  ; 线性查接口槽
0x36A2C80  br   x3                            ; ★ 虚分发到实现类
~~~

**⇒ 合并算法在 `KEMEJCCDJKJ` 实现类，容器只转发。** 三个实现类（实测 dump 行）：

| 类 | 行 | 实测行为 |
|---|---|---|
| `EHKMOKMNKKI : KEMEJCCDJKJ` | L183899 | **`KHPIJPHCFGP(KMLFBAENBMH)` 恒返回 0**（0x36B210C `mov w0,wzr ; ret`）⇒ 空对象 |
| `GGLILJGGPIK : KEMEJCCDJKJ, IDisposable` | L184041 | 可释放 ⇒ **疑为真正的可写实现** |
| `AGNKCIDBODI : KEMEJCCDJKJ` | L184225 | 未分析 |

**结论（实测转发链 + 推断合并位置）**：要改 id 的返回值，切入点是 **`CGHEBBBLGLH`（OKNDCLIKECF+0x50，类型 KEMEJCCDJKJ）指向的对象**，不是容器的 long 缓存。

### 2.2 数值属性根本不走 CGIBCFFNFGL（重要修正）

87 个 `CGIBCFFNFGL` 调用点里**没有任何 id 是 3/9/15/28/36/37**（实测统计）。实际出现的 id：39、43、58、60、65、101、108、119、120、121、124、126。

⇒ 数值属性走**另一条读接口** `KEMEJCCDJKJ::KHPIJPHCFGP(KMLFBAENBMH)`（接口 L183891），或直接读 6 个槽对象；`CGIBCFFNFGL` 只见用于**标志位** id（39 禁移动、43 光谱溢出、58 弹射次数等）。

> **对 `DAMAGE_IMMUNE(37)` 的影响**：静态未找到任何读 id=37 的调用点。⇒「把 37 弄成 >0 就免伤」目前**无静态支撑**，标【待验证】。

## 6. 给 v1.8 的单点建议

**改伤害就盯 `Unit::BLKEJBDMGAB(EAGEDGNBJHM)`（RVA 0x354B388，L166828）—— 它是唯一被调用的伤害落地函数，载荷自带数值字段（+0x28 long / +0x40 float），在这里做倍率/免疫判断不需要属性系统。**

1. **增伤/伤害倍率**：在 `BLKEJBDMGAB` 入口按倍率改写载荷 `+0x28`(long) 或 `+0x40`(float) 后再走原函数。【推断，需一次实测确认字段语义】
2. **敌方扣血**：别指望 `JMIKMDBLCHB`（PLAYER 门控）。可在 `BLKEJBDMGAB` 里直接写敌方 `+0x190`，或先定位驱动器侧 `KCPGOACDHOB+0x190` 语义。
3. **免疫**：暂不采用 id=37 方案（无静态支撑）；最小可行是在 `BLKEJBDMGAB` 入口对“目标是我方”的调用直接 return。
4. **CDR/攻速**：静态未闭环；下一轮反汇编 `GGLILJGGPIK::KHPIJPHCFGP(KMLFBAENBMH)`（L184041 起）即可拿到确切公式。

# 静态闭环 T13：G0–G3（血量确认 / 敌方扣血 / 属性合成 / id 读取点）

> 时间盒 40 min，纯静态，未接触设备。RVA = dump 的 `// RVA:` = ELF vaddr（= 文件偏移 + 0x4000）。
> **方法学限制（必须先看）**：本轮用「全段线性扫描 + 最近方法起点归属」找调用点。**接口方法调用不走 `bl`**（走 `FJMHJMEPFMC` 式接口分发辅助 + `br x3`），因此**对接口实现的直接调用点扫描结果恒为 0，不能据此断定"没人调用"**——这是本轮 G3 的核心教训。

## G0. `Unit+0x190` / `+0x1A0` 到底是不是 HP

### 结论：**不是"被 UI 读的血量"，但也不是无用字段**

| 检查项 | 结果 | 证据 |
|---|---|---|
| 全段扫 `ldr/str [x?,#0x190]` | 3079 处（ldr 2935 / str 144） | 全段线性扫描（74 s） |
| 其中属于 `Unit` 的 | **仅 4 处**：`JMIKMDBLCHB`(读+写)、`JJDKEBAMLNG`(读+写)、`FKIBMJHJACH`(读) | 实测 |
| 属于血量 UI / 伤害飘字类的 | **0 处**。命中 `BossAIController200601`、`BossArenaManager`、`BossArenaBattleEndDialog`、`PlayerInfoDialog` 等的都是**这些类自己的 +0x190 字段**（float/对象），与 Unit 无关 | 实测（按 `pre` 上下文核对基址寄存器） |
| `UnitHpBar` 是否读 Unit+0x190 | **否**（`UnitHpBar` 在 0x190/0x1A0 访问列表里完全没有出现） | 实测 |
| 血条 UI 的数字从哪来 | `Unit::KKGNKHFDCBG()`（0x354A5D4）→ `ldr x0,[x19,#0x120]` → `bl PHBGLMHPMMC::IFEHBJOMMMB` → `b OKNDCLIKECF::HKLDOFIAKDD` ⇒ **走属性容器，不走 Unit+0x190** | 实测（锚点窗口） |

### 判读

- `+0x1A0` 由 `FAGNIOBDNJA(long)` 写入且**钳位 ≥1**（0x354A7FC/0x354A808）——"钳位到 1"是**上限**语义（上限不能为 0），不是当前血量（当前血量该钳到 0）。
- `+0x190` 由 `JMIKMDBLCHB` 做 `+= delta` 且被 `+0x150 == 1 (PLAYER)` 门控。**只在 PLAYER 分支写，只被一个 getter 读** ⇒ 更像"玩家侧的战斗内累加值（承伤/护盾/临时值）"，而不是通用 HP。
- **可信结论**：`+0x190/+0x1A0` 是 Unit 上的**局部数值**，不是全局权威血量；权威值在属性容器（6 个 long 槽 + `KEMEJCCDJKJ`）。

**⇒ 对 v1.8 的影响：继续写 `+0x190` 大概率无效（与此前 4 次实测一致）。不要再投时间在这两个字段。**

## G1. 敌方扣血路径：**上轮结论是误读，已纠正**

`KCPGOACDHOB::OCKDCBJFDMB(int index)`（RVA 0x34AD634）反汇编（实测，锚点窗口 0x34AD6F8–0x34AD9B8）：

**敌方扣血路径：仍然静态未定位。** 已知事实收窄为：

- **下一步唯一正确的静态动作**：扫 `CGIBCFFNFGL`/`FJMHJMEPFMC` 之外，找**写属性容器**的路径 —— 即 `AGGAGLELDIM`（属性构建器）与 `FADNOHFBPCM` 的 6 个调用点，展开它如何写 6 个槽。

## 8. G2′：属性合成公式 —— **根本不存在"合成"，就是一个 int 数组**

> 这是本轮最重要的发现，直接推翻了我上一轮的 `(base+Σadd)×(1+Σrate)` 推断。

### 8.1 调用链（实测）

`GGLILJGGPIK::KHPIJPHCFGP(KMLFBAENBMH)` **0x36B4D38**（L184167）→ `0x36B4D90 b GGLILJGGPIK::ENBOJIGBIGL`（**enum 直接当 index 用，无映射表**）

`GGLILJGGPIK::ENBOJIGBIGL(int index)` **0x36B266C**（L184177）全文（实测，锚点窗口）：

~~~asm
0x36B26B4  ldr  x8, [x20, #0x10]     ; this.values（int[]）
0x36B26BC  ldr  w9, [x8, #0x18]      ; array.max_length（il2cpp 数组布局：+0x18 长度，+0x20 起数据）
0x36B26C0  cmp  w9, w19 ; b.le → 0    ; index >= len ⇒ 返回 0
0x36B26CC  add  x8, x8, w19, sxtw #2
0x36B26D0  ldr  w0, [x8, #0x20]      ; ★ return values[index]
0x36B26D4  ret
~~~

对应 setter（紧随其后的 `0x36B26F0`，实测）：`str w20,[x8,#0x20+index*4]`，且当写入 0 时把 `this+0x18` 的非零计数减 1。

### 8.2 结论

| 问题 | 答案 | 证据强度 |
|---|---|---|
| 6 个槽（+0x18…+0x40 的 MJJMGGGHDGE）如何合成最终值 | **不参与合成**。它们只是独立的 modifier 展示对象；`KHPIJPHCFGP` 完全不读它们 | 实测（函数体只有 4 条有效指令） |
| 是 `(base+Σadd)×(1+Σrate)` 吗 | **不是**。属性就是**扁平 int 数组的 `values[id]`**，没有 base/add/rate 概念 | 实测 |
| `KMLFBAENBMH id` 如何参与 | **直接当数组下标**（enum → index 无转换表） | 实测（`b 0x36B266C` 且函数签名就是 int） |
| 哪个 id 是 HP/攻击/移速/CDR | **就是枚举值本身**：3=HP_ADD、4=PHY_ATK_ADD、9=MOVE_SPEED_ADD、36=COOLDOWN_REDUCTION、37=DAMAGE_IMMUNE、28=FINAL_DAMAGE_RATE（见 §14.2 全表） | 实测（id=下标） |

**⇒ 属性写入的单点：`GGLILJGGPIK` 实例的 `values` 数组元素 `values[id]`（数组对象在 `this+0x10`，数据起于 `+0x20`）。**

**⇒ 一个重要推论**：属性表是**每个单位一份的 int 数组**，不像我上轮猜的"共享配置"。改 `values[37]=1` 只影响该实例。

### 8.3 与 6 个槽的关系（修正 §12.3）

- 6 个槽（`MJJMGGGHDGE`：`ACKAKNLFLDI`，4 long + 1 bool）是**给 UI/描述用的属性构成展示**（base/add/rate 三元正好对应 `(long,long,long)` 写入方法）。
- **战斗读数不走槽，走 int 数组**。所以 §12.3 里"改槽对象能改属性"的推断 **不成立，撤回**。

### 12.3 在 `BLKEJBDMGAB` 里的真实角色（实测）

~~~asm
0x354B4A0  ldr  w22,[x20,#0x14]   ; payload->+0x14 = ★被击中的单位 id（int）
0x354B4B0  mov  w0,w22
0x354B4B4  add  x21,x24,x21       ; delta = payload->+0x28 + payload->+0x38
0x354B4B8  bl   Unit::BMNEKPDMFCK ; ★ id → victim Unit
0x354B4F0  cbz  x22,#0x354B940    ; 查不到 → 整段跳过（不扣血）
0x354B4F4  mov  x0,x22            ; this = victim
0x354B4F8  mov  x1,x19            ; src  = 攻击者（BLKEJBDMGAB 的 this）
0x354B4FC  mov  x2,x21            ; delta

~~~

**⇒ 三点确认（实测）**：
1. `BLKEJBDMGAB` 是**挂在攻击者身上**的方法，参数是"打击载荷"；
2. `payload+0x14` = **受害者单位 id**（不是伤害值、不是系数）；
3. **伤害数值 = `payload+0x28` + `payload+0x38`**，中间**没有**属性乘法/加成。

### 12.4 对 v1.8 `values[28]` 方案意味着什么

| 判断 | 结论 | 强度 |
|---|---|---|

| `BLKEJBDMGAB` 内是否有属性乘算 | **这一段没有**。`0x354B4B8` 之后到 `0x354B510` 之间只做查表、判空、调扣血 | 实测 |

### 12.5 如果上游确实读 28：单位是百分比还是千分比

静态无法定论（乘法形式在未定位的上游代码里）。**但可用一次 so 日志判别（无需改包）**：

~~~text
[判别法] 把 values[28] 依次置 0 / 100 / 1000 三档，同一技能打同一只怪，记录 delta（在 BLKEJBDMGAB 的 0x354B4C0 打 x21）：
- 若 100 时 delta ≈ 2× 基线 ⇒ 单位是「百分比，公式 (100+v)/100」
- 若 1000 时 delta ≈ 2× 基线 ⇒ 单位是「千分比，公式 v/1000」
- 若三档 delta 完全不变 ⇒ 28 不参与，v1.9 必须改载荷（走 12.6）
~~~

### 12.6 v1.9 兜底（静态已确认可行）

`delta = payload+0x28 + payload+0x38`，且**乘算放在哪都不影响正确性**：在 `BLKEJBDMGAB` 入口把 `payload+0x28`（或 `+0x38`）乘倍率，等价于直接放大最终伤害。

⚠ 一个必须注意的点：**这个载荷是 struct（按值传递的指针）**，若同一帧内被多处复用，原地改会污染其他结算；安全做法是**先 memcpy 到栈上，改副本，再调用原逻辑**。

~~~asm
0x3646834  mov  w1, #0x3E                ; ★ id = 0x3E = 62 = KMLFBAENBMH::DAMAGE_GUARD
0x3646838  mov  x0, x29                  ; 属性容器（前面 IFEHBJOMMMB 拿到）
0x3646840  bl   OKNDCLIKECF::FJMHJMEPFMC ; ★ values[62]
0x3646844  mov  w8, w0
0x364684C  cmp  w8, #0
0x3646850  cset w20, gt                  ; w20 = (values[62] > 0)
0x3646854  csel w22, wzr, w22, gt        ; ★ guard>0 ⇒ 伤害分量 A = 0
0x364685C  csel w24, wzr, w19, gt        ; ★ guard>0 ⇒ 伤害分量 B = 0
~~~

之后：`w22 → payload+0x24`、`w24 → payload+0x38`（见 13.2），而 `delta = +0x28 + +0x38`（§12）⇒ **`values[62] > 0` 时 delta 至少归零一个分量**；若另一分量（+0x28，来自 x9）也为 0 或同样被 guard 覆盖，则**整体伤害为 0**。

**证据强度**：`id=0x3E` 与 `csel ... wzr` 均为实测指令；"整体归零"取决于 `+0x28` 的来源（x9，未逐条跟到），强度：**强推断**。

### 13.5 判定结论（按你的要求，不用"可能/大概"）

| 问题 | 结论 |

| 无敌单点 | **`values[62] = 1`**（DAMAGE_GUARD），在 `0x3646840` 被读，`>0` 即把伤害分量清零 |

## 15. 修正：`oknd+0x50` 之后不是「+0x10 就是 int[]」—— 必须先判实现类

> 现场症状：`oknd` 有效、`why=ok`，但「oknd+0x50 → +0x10 是 int[]」判为 `arr unusable`。

~~~c

void* args[1] = { &id };        // int32 id
Il2CppObject* boxed = il2cpp_runtime_invoke(mGet, attrset, args, NULL);
int value = *(int32_t*)il2cpp_object_unbox(boxed);   // 返回 int（值类型需 unbox）

// 方案 B（GGLILJGGPIK 专用，直接读数组，快但必须已判别类）
~~~

## 16. Q1–Q3：`+0x50` 到底是谁、AGNKCIDBODI 怎么写

### 16.1 Q3 先答（已定死）：+0x58..+0x80 的 6 个槽 = `EJDPGJLEICD`，与 id 分发**无关**

`FPIALCOELGG::ctor`（RVA **0x36B0D10**，L183766）实测：连续 6 次 `bl EJDPGJLEICD::ctor`（0x36A97F8），分别 `str [x0,#0x58]! / #0x60 / #0x68 / #0x70 / #0x78 / #0x80`。
⇒ 6 个 override 属性（`FJOCMFNNDOG/JDHMOEPPKPP/AJFOCIGEJJB/EPHGMPGHCFP/KFEOOMMDFAL/HHIABJACILO`）操作的是 **`EJDPGJLEICD` 对象**，它们是"属性构成展示槽"，**`KHPIJPHCFGP` 的分发完全不经过它们**（分发走 `+0x50`，见 §15.2）。

### 16.2 Q1：`+0x50` 的赋值 —— 静态未定死，但排除了两个候选

实测（全段扫描 new 调用点 + ctor 反汇编）：

| 事实 | 证据 |
|---|---|
| `AGNKCIDBODI` 全包只有 6 处被 `new`，其中 **3 处在 `PHBGLMHPMMC::ctor`**（0x36A5448/0x36A5470/0x36A5498），分别存入容器 **+0xC0 / +0xC8 / +0xD0** | 实测（ctl 窗口 0x36A53D0–0x36A54D4） |
| ⇒ **`+0x50` 不是这 3 个 AGNKCIDBODI**（偏移不同） | 实测 |
| `OKNDCLIKECF::ctor`（0x36AD8F0，L183664）只写 `+0x18`/`+0x20`… 等 6 个槽（对象由 `bl 0x71E54D4` 工厂产出） | 实测 |

**⇒ 结论（证据强度：强推断）**：`+0x50` 极可能指向 **`GGLILJGGPIK`**，由外部"属性构建器"（`AGGAGLELDIM` / `FFIGCMIJNEF`）通过 `IAPIHBKPLCF::HEDDFPGMEFH(FPIALCOELGG)`（PHBGLMHPMMC 实现 0x36A0E00）或直接赋值塞进去。
