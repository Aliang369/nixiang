## 10 崩溃归因结论（§9 收尾 · 2026-11-15 02:50）

### 10.1 一句话结论
**崩溃与 Dobby 无关；是解析层对 il2cpp API 的调用触发了 il2cpp 内部的 fatal（array-type 类 abort）。**
功能版 v1（无 Dobby，so 381,200 B）与探针版（398,688 B）崩溃特征逐条相同 ⇒ 排除 inline hook；归因交 builder 改解析器（绕开 assemblies 数组，改用 il2cpp_domain_assembly_open）。

### 10.2 五条支撑事实
| # | 事实 | 证据 |

| 1 | **三份 tombstone 同构** | 同一 pc 0x2f91348、同一 BuildId c7fa53dd…、同一信号 SIGABRT(SI_QUEUE)、同一线程名 UnityMain |

### 11.4 为什么 step=1 就被拒 —— 决定性证据（/proc/<pid>/maps）
```
进程 22918 的 so 段权限：
r--p 400020a40000-400020a8a000 libstarry_magic.so
r--p 400020a8a000-400020a8f000 libstarry_magic.so     ← 只有 r--/rw-，无 r-x

r--p 400022c00000-4000257c5000 libil2cpp.so           ← 同样无 r-x
r--p 4000257c8000-40002a947000 libil2cpp.so
r--p 40002a94a000-40002ae74000 libil2cpp.so
rw-p …（三个 so 的 data 段）
r-xp 73f431ecf000-… /system/vendor/lib64/libhoudini.so  ← 只有转译器有 X 权限
```
全进程映射统计：r-xp 315 段，但 **libil2cpp / libunity / libstarry_magic 三个 ARM so 一段 r-xp 都没有**。
⇒ 在 x86_64 + houdini 环境下，ARM so 的代码段是 r--p，执行由 libhoudini 的 JIT 承担。
⇒ v1.1 的 `sym_reject … 不在可执行段` 判断**在这个环境里恒为真**，于是 step=1 就安静放弃；
⇒ 而 v1 是绕过该检查直接 blr 到 r-- 页 ⇒ 上一轮那 149 次 Forwarding signal 11 的 SEGV 风暴。

### 11.5 结论（推断，标清楚）
1. **v1.1 的行为符合设计**：拒绝不可执行目标 → 安静降级 → 进程活着、菜单在、全部功能灰。比 v1 的崩溃好，但等于「模拟器上不可用」。
2. **这不是解析器逻辑 bug**：把 assemblies 数组换成 domain_assembly_open 解决不了根本问题——第 1 步 il2cpp_domain_get 的地址本身就过不了执行段校验。
3. **根因是 ARM 转译环境（houdini）**：真机上 libil2cpp 的 .text 是 r-xp，同一份代码应当能直接通过校验并调用；模拟器上无解（除非让 houdini 帮忙转译间接调用，但没有公开接口）。
4. 因此建议：要么在有 **arm64 真机**（或 arm64 宿主、非 houdini）上再验一次 —— 这是唯一能区分「代码问题」与「环境问题」的干净实验；要么明确接受「本模拟器只能验到菜单层（Java 侧）」这个边界。
