# 问题 3：无限技能无法用菜单按钮控制 —— 静态闭环复核

> 复核人：skill-checker（静态分析）｜日期：2026-11-16｜对象：AbssnmxtMod v2.1
> 证据分级：【实测】= dump.cs 行号 / RVA / 指令原文 / cpp 行号；【推断】= 有证据链的推理；【待验证】= 需动态/IFix 侧确认
> 材料：`06_dumped/阿比斯少年冒险团/libil2cpp.so`(141MB)、`il2cpp_out/dump.cs`；capstone 5.0.7 自跑，RVA==vaddr，va→offset 用 ELF 可执行段表

## 1. 结论

1. **lead 的 RVA 三条反推全部成立**，且 0x35547E4 的语义可以进一步确证为「以 HClock 当前时间为第一参数、对 Unit 技能容器的一次写冷却/技能状态虚调用」，**不是完整施放流程**。
2. **Java→native 链路是单源闭环，不存在「点了再反弹」**：开关值只写在 `g_features[3]`（MainModern.cpp:297-298），Tick 只是每 200ms 回读同一个数组（MainModern.cpp:254 → AbssnmxtMod.cpp:2545）。UI 回弹只有两条路：`feat_ok(3)==false` 或 native 调用失败（ModBridge.java:343/352）。
3. **v2.1 的修法方向正确且基本完备**：所有 7 个 hook 入口与 4 个数据面 Pass 均已受 `g_skill` 控制；关闭态等价于「未安装」（唯一残差是属性组的还原精度）。
4. 需要补的只有**健壮性**，不是功能：`orig==null` 静默、`skidC/D/E/F` 疑似无效 hook、AttrApplyPass 还原残差。

### 2.3 0x35547E4 到底写什么（补证 lead 的第 3 条）

```
0x3554830  bl  #0x45426a4  -> WrappersManagerImpl::IsPatched(0x971c)
0x3554874  bl  #0x354a530  -> Unit::DFNAOICKOJP()   ; = ldr [Unit+0x128] 技能容器 BKMDLBHDGNC
0x3554890  ldrb w11,[x9,#0x130] / ldrb w10,[x8,#0x130] / cmp / b.lo / b.eq   ; 类型(cast)检查
0x35548DC  mov  x0,xzr
0x35548E0  bl   #0x32a47cc  -> HClock::NMHDPNKKNBP()          ; 取 now
0x35548E8  mov  w1,w0                                          ; arg1 = now
0x35548F0  mov  w2,w20                                         ; arg2 = skill 枚举
0x35548F4  ldr  x5,[x8,#0x328]   ; 方法指针
0x35548F8  ldr  x4,[x8,#0x330]   ; MethodInfo*
0x35548FC  mov  w3,w19                                         ; arg3 = int 参数
0x355490C  br   x5                                             ; 虚调用
```

**槽位归属（【推断-强】）**：x0=容器、x1=now(int)、x2=PKFLGAEJICG、x3=int(默认 0)。在 dump.cs:176440-176441 找到 **Slot 31 `public virtual void FEJHANBJNCK(int OIIEBMPDOAJ, PKFLGAEJICG LCNAFOPBDBO, int POFMPDCMABK)` @0x360E330**，其参数名 `LCNAFOPBDBO / POFMPDCMABK` 与扩展方法 0x35547E4 的两个参数名**逐字相同**（dump.cs:167308），且扩展方法只是把 `Unit` 换成 `int now` 注入首位。对照 0x35546B0 走 **Slot 26 OIKKANJOLNC @0x3608534**（[x8+0x2d8]），同样参数名对位。两者槽位差 0x50（10 槽），不同方法，符合「bool 版查可用 / void 版写状态」的成对设计。

**语义判定：写冷却起点（或以其为基准的技能状态刷新），不是施放流程。** 依据：
- 函数体只有「IFix 检查 → 取容器 → cast 检查 → 取 now → 一次虚调用 → ret」，**没有任何资源扣减、目标选择、弹道生成的多步链**；施放流程不可能压成一次同签名虚调用。
- 同构的 bool 版 0x35546B0 返回「是否可用」，与「void 版写起点」天然成对。
- `HClock::NMHDPNKKNBP()` 是 `static int`（0x32A47CC，体内读全局 `[静态+0x20]→ldrb [x0+0x135]` 的时钟对象）【推断】= 当前时间基准/帧时间戳。
- **额外实测**：0x35546B0 在容器为 null 或 cast 失败时 `0x3554780-0x3554790: mov w0,#1; ret` —— **直接返回 true（可用）**。说明原生实现把「容器缺失」当作放行，skidA 的 kind2 恒返回 1 与原行为在空容器路径上等价，收益有限。

### 2.4 v2.0 缺 `g_skill` 判定（确认）

【实测】AbssnmxtMod.cpp:2089-2097 `ForceRun` 有判定（:2091）；v2.0 的 `VoidRun`/`SetByteRun` 没有 → 装上即恒生效，与「菜单按了没反应」现象一致。现源码 :2107 / :2119 已补。

## 3. Java→native 链路复核（「点了再反弹」不可能）

| 步 | 位置【实测】 | 行为 |
|---|---|---|
| 1 | FeatureListParser.java:45 | `Toggle_` → 开关型 |
| 2 | NativeMenuController.java:1758（canUse 分支）→ :2231-2241 | `attachToggleListener` → `bridge.onToggleChanged(num,raw,on)` |
| 3 | NativeMenuController.java:2234-2238 | **回弹唯一现场**：仅当返回 false 且 on==true 才 setChecked(false)+toast |
| 4 | ModBridge.java:333-359 | 337 bool 规格检查（`Toggle_无限技能` 通过）→ 343 `requireAuthForFeature` → 349 写偏好 → 352 `nativeSetFeature` → 失败才 354-356 回退；正常 359 return true |
| 5 | MainModern.cpp:285-303 | 292 `feat_ok` 门禁 → 297-298 `g_features[3]=enabled` → 300 `onFeatureChanged` |
| 6 | AbssnmxtMod.cpp:2522-2529 | `case ABSSNMXT_FEAT_SKILL(=3)` → `g_skill.store(enabled)` |
| 7 | MainModern.cpp:241/254 | 200ms 循环 `mod->tick(g_features,g_values)` |
| 8 | AbssnmxtMod.cpp:2545 | `g_skill.store(features[3])` —— 回读同一数组 |

**判定**：3 号位真源只有一个 `g_features[3]`；步骤 5 写它、步骤 8 读它，值相同 ⇒ **不存在「点了再反弹」**。回弹只可能来自 ①`sgauth::feat_ok(3)==false`（未授权）②`nativeSetFeature` JNI 抛错（tryCall 失败）③`isBoolFeatureSpec` 判错规格。当前清单 `Toggle_无限技能` 位于 AbssnmxtEntry.cpp:21，`ABSSNMXT_FEAT_SKILL=3`（AbssnmxtMod.h:24），索引一致，无错位。
其它可能（列出）：`featureInteractable(3)` 为 false 时菜单走 :1753-1756 灰色不可点分支（`attachBlockedToggle`），此时表现为「开关点不动」而非「没效果」，需与现象区分。

## 5. 改法复核与仍需补充

| 项 | 结论 | 说明 |
|---|---|---|
| `VoidRun` 用 `fn_v4_t(4×void*)` 调 orig | ✅ 正确 | 原函数实参 3 个（x0=容器, w1=now, w2=skill, w3=int）。AArch64 下按 64 位槽传 32 位值只读到低 32 位，函数体用 `w1/w2/w3` 取值，多传的第 4 个参数走 x3，不污染 callee（0x35547E4 用满 x1..x3，第 4 个需 x4 而签名只有 3 参 → 无越界）。 |
| `SetByteRun` 关闭时返回 orig 返回值 | ✅ 语义上正确（无妨） | 0x3006D98 是 **void**，w0 返回值调用方不看；关键是「关闭时不再写 +0xE8」这一点成立。 |
| `orig == null` 边界 | ⚠️ 需补 | 2092/2120 都是三元表达式静默兜底：ForceRun 返 0、SetByteRun 返 **1**（恒过，方向与「关闭」相反）。应改为 `LOGW` + 明确兜底，避免「以为透传其实没透传」。 |
| 空缺 | ⚠️ 建议补 | ①`g_skill` 切换时打一条状态日志（便于现场判断 200ms 窗口）；②修正 cfg:75/:80 注释里的类名/方法名互换。 |

**残余风险**
- **R1（低）**：Tick 200ms 才同步 → 关闭后最长 200ms 内仍生效；且若关闭瞬间已把 CD 起点清掉，需一次真实施放才能恢复计时，属表现层。
- **R2（中，待验证）**：`skidC` 0x3608534 是接口/基类的 virtual **声明体**（Slot 26），实际虚分派经 vtable 指向 override 实现，**hook 该地址很可能永不触发**（同族 skidD/E/F 需同样复核）。不构成关闭失效，但会污染日志与结论。
- **R3（低）**：AttrApplyPass 还原用 `g_grpBefore` 快照；若中途进程重启/重进战斗导致快照丢失，属性可能残留偏差。
- **R4（待验证）**：这些函数首部都有 `IsPatched(id)` IFix 分支（0x29 / 0x1981 / 0x971C / 0x970d）。当前无 IFix（否则功能不生效）；若将来出现 IFix，hook 仍命中入口，但原生体不执行，关闭态行为会退化为「IFix 语义」。
