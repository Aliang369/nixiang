## 2. 三条独立证据

### 证据 A（最强，静态）：metadata 参数签名逐一对号
- `meta_76f2c00000.bin` @ **0x2a0e5c + 36×11705 = 0x6b3e10** 起的 36B 记录：`name=8453("Load")`、`declType=1436`、`paramStart=15807`、`token=0x0602DBA`、`(paramCount<<16)|0xFFFF = 0x0001FFFF ⇒ pc=1`。原始首 4 字节 `6d 21 00 00`(=8453)。
- 参数表 `0x76cb60 + 12×15807 = 0x79ac84`：`{nameIndex, token=0x0800…, typeIndex=30177}`，参数名 **"rawAssembly"**。
- **typeIdx 30177 = `System.Byte[]`** 的三处旁证：11706 `rawSymbolStore`=30177、11707/11708 同；11696 `LoadFrom` 的 `hashValue`/`hashAlgorithm` 也是 30177（.NET API 里这两个就是 byte[]）。⇒ 30177 只能解释为 byte[] 数组类型。
- 8 条重载的组合（string/AssemblyName/byte[] 三族 × Evidence/SecurityContextSource 变体、pc=1/2/1/2/1/2/3/3）与 Mono mscorlib 的 `Assembly.Load` 声明集**逐条一一对应，无剩余、无缺项**。

### 证据 B：gi == method 定义索引（把上表钉到 VA 上）
- `bss1.bin`（槽区 VA 0x771a89d000）× methodPointers 表 VA `0x771a9bbde8`：`[11704]=0x7718f6bc48`、`[11705]=0x7718f6ba14`（与 mod 观测值一致）；旁证 `[16150]=0x77190a3f14` = mod 记录的 ExecuteRuntimeAssembly methodPointer，而 metadata 第 16150 号方法名正是 **"ExecuteRuntimeAssembly"**（declType 1943）。⇒ 索引空间一致，表中 VA 即真实 methodPointer。
- 11701…11708 在 metadata 中是**连续 8 条同名 "Load"**，与 mod 扫出的 gi 连续区间吻合（11706/7/8 是 mod 没列到的另外 3 条）。

### 证据 C：反汇编形态（capstone，`mscorlib_8k.bin` 已确认为解密后真代码）
- 入口 `0x7718f6ba14`：`str x30,[sp,#-0x30]!` / 存 x20-x22 / `ldrb w8,[x22,#0xcc1]` lazy-init 旗标 / `ldr x21,[x21,#0x1c0]` / `mov x20,x1`（保存 MethodInfo = **静态方法**约定）/ 后续 `mov x0,x19; mov x1,xzr; bl 0x7719cc2600` 与两次按 klass 取元数据后 `bl 0x7719c3a2b8`，尾部 `str x20,[x19,#0x10]!` + `b 0x7717725e64` 尾调用。**有独立 lazy-init 分支 + 完整序言**，与 11701/11703 的「5 条纯转发桩」形态明显不同。
- 11706/11707/11708 三条 byte[] 多参重载是 `mov w0,wzr; ret` / `ret` 的 **AOT 空桩**（`mscorlib_8k.bin` off 0xe4c/0xe5c/0xe60 原始字节 `e0031f2a c0035fd6 e0031f2a c0035fd6`、`c0035fd6`）⇒ 想注入 DLL 字节只能走 11705。
- 8K 块起始 VA 判定：`mscorlib_8k.bin` 在 `0x7718f6b000` 起点下，11701/11703 呈「同构孪生（仅立即数 0x60/0x20 不同）」、11705/11704 各为完整函数、0xbe4c 起为连续空桩，全部落在函数边界上 ⇒ base=0x7718f6b000 自洽。

## 4. 风险与未决

1. **11705 body 第一件事是 `bl 0x7719cc2600`（x1=0）**，而 ExecuteRuntimeAssembly 的 thunk 也正是 `mov x1,xzr; b 0x7719cc2600`，该目标已被实测为「3 个连续 ret」的 AOT 空桩疑似区。若 11705 只是「转发到空桩 + 返回 null」，hook 它**仍能拿到入参 x0**（我们要的就是这个），但**不能指望它自然完成加载**，覆写仍要在 hook 内做。
2. body 中 `str x20,[x19,#0x10]!` / `str x20,[x0,#0x50]!` 是对 x0 指向对象的写；若 x0 真是 byte[]，这两处写不合常理（数组 +0x10 是 bounds，+0x50 越界）。**推断**：函数内有「按 `Load(byte[],byte[],Evidence)` 语义取缓存槽再写回某静态对象」的路径，也可能 8K 块 base 存在页级偏差。**待验证**，但不影响 hook 目标（入口 16B 已给且与 11704 可区分）。
3. `typeIdx 30177` 未能在 metadata 内解析成字面 `System.Byte[]`：**该版本 Il2CppType 表不在 global-metadata 中**（元数据内无 types 表，8/12/16/20 四种步长假设全部证伪），需 `.so` 的 `Il2CppMetadataRegistration.types`（位于 r--p 只读段，本次 dump 未覆盖；磁盘 .so 该页为密文）。故 30177=byte[] 依赖 §2-A 的三处语义旁证，非字面解析。

## 5. 下一步候选（若 mod 探针证明 11705 不干活）

1. 先查 gi 11706/11707/11708 的 MethodInfo 是否被 HybridCLR 注册为 interpreted method（三参重载是 AOT 空桩，真实实现若存在只可能在解释器侧）。
2. `HybridCLR.RuntimeApi.LoadMetadataForAOTAssembly` 的 C++ wrapper；`RuntimeAssemblyLoader.ExecuteRuntimeAssembly`（gi 16150，metadata 声明 pc=2 而 thunk 只揉 x1=0，需另开一轮）。
3. 若目标只是「DLL 字节进入 runtime」，**11705 入口 + 自行覆写 x0** 仍是最短路径：x0 是托管 byte[]，改 `(byte*)x0+0x20`（数据）与 `+0x18`（长度）即可，无须找到 HybridCLR 内部入口。
