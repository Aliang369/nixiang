# 13.101（2,746,368）「点击秘境闪退」只读分析（2026-11-19）

> 范围：**只读**。未改载荷、未重打包、未动 so。结论按「证据 → 判断」顺序给，推断处标「推断/待验证」。
> 崩溃现场（lead 提供）：tombstone_24 / 14:15:50 / pid 32636 / UnityMain / SIGSEGV code=2 `SEGV_ACCERR` / fault=**0x76d8000000** / pc=libil2cpp+0x29d6030 / **1 frame**。

## 1. 崩溃现场的内存布局（判读）

```
00000076'd0000000-00000076'd7ffffff rw- 0 8000000     ← 128 MB 匿名可写区（官方 hot-update DLL 就落在这里：+0x36e62e0）
00000076'd8000000-00000076'dfffffff --- 0 8000000     ← 紧随其后 128 MB PROT_NONE
```

- fault 地址 = **rw- 区结束后的第一页**，页对齐，`SEGV_ACCERR`（权限错，不是未映射的 MAPERR）⇒ **越界一页**，不是空指针、不是野指针随机值。
- 该 rw- 区里放着本次热更的程序集（11-18 的 dump 就取自 `76d0000000+0x36e62e0`）⇒ 是**大块匿名 arena**（装载/解密缓冲）。
- 不是 GC 小对象堆（GC 堆不会整页 `PROT_NONE` 紧贴）；不是元数据堆（metadata 在 `0x76f2c00000`，另一块）。
- `1 frame` + pc 在解释器 ⇒ 托管 IL 正跑在解释执行路径上时踩的。

## 4. 问题③：128 MB 区域越界，最可能是哪类结构

| 候选 | 判断 | 依据 |
|---|---|---|
| 热更程序集装载/解密 arena | **最可能** | 崩溃的 rw- 128MB 区正是官方 hot-update DLL 所在区（+0x36e62e0）；紧随其后整页 `PROT_NONE` 是 arena 的守护页 |
| Unity 资源解压缓冲 / 大 AssetBundle 缓冲 | 可能 | 同为大块匿名 rw-；`1 frame` 在解释器说明是托管代码在跑，未必是资源线程 |
| il2cpp GC 小对象堆 | 不太可能 | Boehm/BDW 堆布局不会以 128MB rw- 紧跟整页 PROT_NONE 的形式出现；且 fault 页对齐 |
| metadata 堆 | 排除 | metadata 在 `0x76f2c00000`，另一块映射 |
| 我们的 `mode=selfarray` 新数组 | 排除（就地址而言） | 本轮 buf 形如 `0xb4000077…`，属托管/原生堆另一区段；且 selfarray 只被读、不被写 |

> 以上 1、2 为「推断」，未取寄存器/回栈，**标待验证**。

## 5. 结论（三选一）

**排除 A（今天新增导致）**：依据 §3 —— 相关方法的官方 IL 两版逐指令相同，hf4/hf5 注入结果也相同；今天唯一新增的是载荷换了官方基线 + 新三元组，**没有新增任何注入点**。

**倾向 B（既有注入 + 新内容触发）**：依据
- 注入在 11-18 的 hf4 上完全一样（§3 表），而 11-18 的 L3 用的是**旧官方 2,738,688**；
- 本次热更**确实改了关卡/敌人生成侧**：类型 diff 显示 `EnemyGenerate` 方法 86→87、字段 77→79，新增 5 个协程状态机（`<OnGenerate>d__121` / `<GenerateGroup>d__108` / `<MinCount>d__141` / `<TimeCount>d__114` / `<BeginCountDown>d__73`），`Enemy` 新增 `<Attack>d__104`；
- 点击路径实锤：`MiJingDetial::OnClick`（`IL_002F callvirt CanChanllage`，`ldloca.s V_2` 传 `bool&`）→ 我们的 feat9 把 `result` 强制 true → 进入战斗/生成流程（`EnemyGenerate`）。
⇒ 机制解释：**门禁被放开 ⇒ 走进原本进不去的秘境/生成路径 ⇒ 新内容侧（生成/缓冲）越界**。注入本身不写数组，是「放行」把执行带到了会越界的地方。

**不能排除 C（官方 bug/资源问题）**：同一条路径在**未打补丁的官方 DLL** 上是否也崩，目前无对照数据（无法在设备上跑纯官方）。

## 8. §5.1 那个 `br` 偏差的精核（栈语义，2026-11-19 复算）

### 8.1 指令与目标（实测）

```
官方: IL_01E7 ldarg.0 ; IL_01E8 ldarg.0 ; get_Hp ; IL_01EE ldloc.1 ; op_Subtraction ; IL_01F4 set_Hp
      IL_01F9 ldloc.0                       ← 压入**玩家** Character
      IL_01FA ldflda Character::_preCalculateData
补丁: IL_01E7 ldarg.0（官方原件，被后文 set_Hp 当 receiver）
      IL_01E8 ldstr oneshot ; GetBool ; brfalse → IL_0213
      IL_01F7 ldarg.0 ; ldarg.0 ; get_Hp ; ldarg.0 ; get_Hp ; op_Subtraction ; set_Hp
      IL_020E br → **IL_0225**（= ldflda，跳过 IL_0224 ldloc.0）
```

### 8.2 栈深复算（逐条，before→after）

| 官方 | 补丁 oneshot 分支 |
|---|---|
| `IL_01E7 ldarg.0` 0→1 | `IL_01E7 ldarg.0` 0→1 |
| `IL_01E8 ldarg.0` 1→2 | `ldstr/GetBool` 1→2→2 |
| `get_Hp` 2→2 | `brfalse` 2→**1** |
| `ldloc.1` 2→3 | `IL_01F7 ldarg.0` 1→2 |
| `op_Subtraction` 3→2 | `ldarg.0;get_Hp` 2→3 |
| `set_Hp` 2→**0** | `ldarg.0;get_Hp` 3→4 |
| `IL_01F9 ldloc.0` 0→1 | `op_Subtraction` 4→3 |
| `ldflda` **before=1**（对象＝玩家） | `set_Hp` 3→**1**（残留 `this`） |
| — | `br IL_0225`；`ldflda` **before=1**（对象＝**敌人自己**） |

### 8.3 结论

- **栈合法，无下溢**：`ldarg.0`(IL_01E7) 压的 `this` 被 set_Hp 消费后仍剩 1 个（因为 set_Hp 之后又压了 3 个、pop 2 个）——精确算是 3→1，残留的正是 IL_01E7 那个 `this`。
- **语义偏差仅限「读谁」**：官方读玩家 `_preCalculateData.leechHealAmount`；补丁读**敌人**同名字段（`Enemy : Character`，`ldflda` 打的是基类字段，地址合法，默认值 0）⇒ 表现＝秒杀时玩家吸血不结算（§5.1 已裁决不动），**不会产生非法指针/非法状态**。
- 因此 **P13/P14 不是「越界一页」的直接成因**；它最多是**放大器**（一帧内把敌人瞬间打死 ⇒ 死亡/掉落/结算链路集中触发；`EnemyGenerate` 正是本次热更改动最大的类）。
- 若 DIAG 不崩，仍按 lead 顺序二分，但**优先验 oneshot 的间接影响**（关掉后是否还崩），而不是指望它直接越界。
