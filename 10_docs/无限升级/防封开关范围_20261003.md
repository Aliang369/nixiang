# 无限升级 11.266018 / vc1637 — 「防封」菜单开关范围（2026-10-03）

> 用户口径（m02113）：「防封相关的代码做到菜单里，做成防封按钮控制，开启后就生效，不开启就不生效。
> 然后你看看那些是不适合做进去的，比如拦截更新的就不适合做进去」。
> 本文回答两件事：**开关到底控制哪些东西**、**哪些刻意不纳入控制（恒常开）以及为什么**。

## 一、开关本体

| 项 | 值 |
|---|---|
| 菜单项 | feat 16 `Toggle_防封`（`Games/WxsjVc1637Entry.cpp`） |
| 配置键 | **`block_report`**（沿用基线 DLL 里既有的键名，零改名成本） |
| 判定 | `StarryConfig::GetBool("block_report")`；缺键 / 值为 null ⇒ **false**（实测实现：`Get(key)==null → false; "1"→true; "true"→true`） |
| 默认 | **关**。`WxsjVc1637Mod.cpp::TryHookOnce()` 每次 hook 安装时显式写 `block_report=0`；只有用户点开菜单才写 1 |
| 生效时机 | 立即（DLL 侧每次调用都读键，无需重启游戏） |
| 持久性 | 与其它开关一致：**冷启动不保留**（菜单 `ModBridge.clearFeaturePrefs()` 既有设计；本轮额外确保冷启动初始值恒为 0） |

> 旧版本（≤ 2026-10-03 第2轮）这里是「`block_report` 缺键就补 1」= **无条件常开、玩家不可关**。
> 本条即为本次改版的直接来源；该旧写法已删除。

## 二、纳入开关的三组（关掉后完全回落到官方行为）

### A 组：基线自带的 37 处 `block_report` 门（`--dump-keys` 实测，逐点列全）
形态 `if (StarryConfig.GetBool("block_report")) return;`（`UploadMainSaveAsync` 那处是 `throw new Exception("starry offline")`）。
**这些门天生跟键走，一条 IL 都不用改**：

| 类别 | 调用点（`GetBool @ 类型::方法`） |
|---|---|
| 异常 / 作弊上报 | `DamageCheatRecordData::Record`、`InfinityCore.ItemUseAnomalyMonitor::CheckAmount`、`InfinityCore.ItemAddSourceAnomalyMonitor::CheckAddSource`（**仅 hf2/hf3 有**，12.x 二次热更新增的物品来源异常检查） |
| 云存档 + COS 直传 | `CloudRealtimeSaveMgr::{UpdateProgress,RequestUpload,HasValidUploadSession}`、`GameDatas.MainSaveCosUploadTool::{UploadMainSaveAsync,UploadBanSaveAsync}` |
| 腾讯 CLS 日志 | `GameDatas.TencentClsLogService::{Enqueue,TryBeginFlush,ConsumeFlushRequest}` |
| 风控 / 封号执法 | `NetWorkPlayerMgr::{Report,CheckBan,CheckBanReport,CheckBan2,BanGameAciton,DeleteData,ShowContentAndCloseGame,CheckOnLine,ServerMsg,ServerMsgBig,Warning}`、`InfinityCoreNormal.NetConver::{CheckGamePlayerAction,ForceBanGameAciton,UpDateBanStatu}` |
| 排行 / 数据同步 | `NetWorkPlayerMgr::{SendRank,SendRankNew02,FinishJuYuan}`、`InfinityCore.NetDataCalculater::{GetAllPlayerPFR,GetInventory,GetMiFaInventory,GetBaoShiWeight,GetUsdDaoJu,GetDataInfo,PlayerOnLine}` |
| 版本 | `NetWorkPlayerMgr::BlockVersion`（门仍在，但入口已被版本钉死成 no-op ⇒ 实际恒不执行，见第三节） |
| 存档救命链（**门已删，不受开关影响**） | `NetWorkPlayerMgr::{CheckCodeLocked,OnSaveGuardFailed}`（`PatchSaveGuardChain` 删门，见第三节） |

### B 组：δ 层 6 处「入口 `ret` + 原体保留」的无条件 no-op（本轮删除入口 ret）
`--scan-noop` 穷举基线，恰好 6 处，全是封号执法族；其中 5 处的**原体内自带 `block_report` 门**（只是被入口 `ret` 挡成死代码）：

| 方法 | 处理 |
|---|---|
| `NetWorkPlayerMgr::BanGameAciton` | 删入口 ret ⇒ 回落到体内门 |
| `InfinityCoreNormal.NetConver::CheckGamePlayerAction` | 同上 |
| `InfinityCoreNormal.NetConver::ForceBanGameAciton` | 同上 |
| `InfinityCoreNormal.NetConver::UpDateBanStatu` | 同上 |
| `InfinityCore.NetDataCalculater::PlayerOnLine` | 同上 |
| `NetWorkPlayerMgr::BanGame`（0 参） | 旧形态是「无条件清 `GameData.ban=false`」；本轮改为**门控清 ban**，并拆除旧插入的 4 条 |

⇒ 防封**开**：客户端不被封号流程锁死（清 `GameData.ban`、不执行执法动作）。
防封**关**：`BanGame()` → `BanGameAciton("BanGame")` 走原体 ⇒ **恢复官方封号表现**（banMask /「涉嫌修改游戏数据已进行封号处理」/ `Time.timeScale=0` 冻结 / 上传 ban 存档）。

### C 组：`StarryConfig::StrictBlockedRpc`（13 项「纯上报」名单，19 个出站通道共用）
原体是 13 个 `op_Equality` 白名单（`AddPlayerReport / CheckBanReport / CheckBan / OnRecordNewCheckCode / AddActiveRecord / SendDeviceInfoBack / PlayerToBackGround / PlayerToFrontGround / SendLocalLogToServer / SendRewardRecordToServer / UploadLog / ShowLogs / RequestRealtimeSaveUploadSession`），被 `NetBehaviour::SendRT/Send`、`AccountMgr.LoginScene.AccountMgrClient::Send` 等 19 处调用；每处形态是 `call StrictBlockedRpc / brfalse 原行为 / call NoteBlockedRpc / ret`。
本轮在方法**头部**插 `if (!block_report) return false;` ⇒ 一个插桩点整族随开关（关掉后出站过滤整体失效，恢复官方上报）。

## 三、刻意不纳入开关（恒常开）—— 以及为什么

| 不纳入的东西 | 理由（关掉会怎样） |
|---|---|
| **版本拦截族**（`PatchVersionPin`：`NetWorkPlayerMgr::Vch`/`BlockVersion`、`InfinityCore.NetDataCalculater::CurrentVersion`、`MainUIFuntions::ShowNewVersion`/`OnNewVersionClick`、`LowVersionMgr::NeedUpdate`/`OpenUrl`、`LowVersionMgr_InitScene::ShowOnShow`/`OnDownLoadClick` 共 9 个 no-op + `ResVersionApi::GetVersion`→`Int64.Max` + 3 处 `ReplaceApplicationVersion`） | **用户点名「拦截更新的不适合做进去」**，技术上也确实不能：关掉后游戏会接受官方热更 DLL，运行时长度变了 ⇒ 内嵌补丁 DLL 与官方 `byte[]` 长度不匹配（`pLen <= len` 不成立）⇒ 加载 hook **静默 skip**，玩家看到的是「菜单在、功能全无」且**不报错**，排障成本极高。此外版本钉死本身就是防封的前置（老 DLL 行为已摸清、风控逻辑未变） |
| **存档救命链** `NetWorkPlayerMgr::CheckCodeLocked` / `OnSaveGuardFailed`（`PatchSaveGuardChain` 已删其 `block_report` 门） | v7.18 丢档教训：这两处若被门挡住，一次校验失败就会走到「覆盖主存档」的路径，**直接丢档**。它与「防封」正交，且属于玩家资产安全底线 ⇒ 必须恒常开 |
| 其它功能补丁（无敌/秒杀/免广告/物品不减/…） | 与防封无关，各自有独立开关 |

## 四、开关状态下的注意点

1. **默认关 ⇒ 首次进入游戏必须在菜单点开「防封」**，否则跑的是官方风控行为（含封号执法）。冷启动开关会被清空，需重新点。
2. 防封关掉时 `ItemUseAnomalyMonitor::CheckAmount`（三变体）与 `ItemAddSourceAnomalyMonitor::CheckAddSource`（hf2/hf3）都会跑 ⇒ **「物品使用反增」在这两个监控下更容易被上报**，两者建议同时开。
3. `LowVersionMgr::OpenUrl` 等版本相关 no-op 仍在下发/拦截列表里（见上表），不要试图把它们挂到开关上。
4. **A 线（12.10701 / vc1644）本轮未改**，其 `block_report` 仍是旧的无条件常开写法；如需同样做成开关需另开一轮（12.x 的 `Program.cs` 是独立文件）。
5. 12.x 早期决定「静默防封不做菜单按钮」的记录（2026-09-23）适用于 A 线；B 线按用户 m02113 改为开关控制，两者口径不同属预期。
