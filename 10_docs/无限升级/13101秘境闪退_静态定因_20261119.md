## 4. 审计 C：求值栈数据流（新增工具 `ilstack`）

按官方与补丁各自建 CFG，逐指令算求值栈深度（含 EH 入口：catch/filter=1、finally/fault=0；`leave` 清栈），检查三类问题：栈下溢、同点深度不一致、ret 处深度不符。

| DLL | 方法数 | 访问点 | 违规 |
|---|---|---|---|
| 官方 2,748,416 | 13,215 | 403,000+ | **0** |
| hf6 2,761,216 | 13,221 | 403,918 | **2（同一处）** |

```
[DEPTH-MISMATCH] AdsManager::AdsFree IL_0022 由 IL_001D(callvirt) 到达栈深=0 与已记录 1 不一致
[RET-DEPTH]     AdsManager::AdsFree IL_0023 ret 处栈深=1 期望=0
```

**根因（精确到指令）**：`delta::AdsFreeOffline` 插入的块里 `dup; brfalse L_after` —— `brfalse` 只弹掉 dup 出来的那份，**原件 `ldarg.1` 仍留在栈上**；当 `action == null` 时跳到 `L_after`(=nop→ret)，void 方法带 1 个残余值返回 ⇒ 栈不平衡。

- **触发条件**：`free_ads=1` **且** 传入的 `Action` 为 null。
- **与秘境无关**：`AdsFree` 只在广告流程被调；用户这次配置里没有开 `free_ads`（lead 给的配置面未含该键）⇒ 本次闪退不是它导致的。
- **最小修正（1 处，待批准后才动）**：把 `ldarg.1; dup; brfalse L_after; callvirt Invoke; L_after: ret` 改为 `ldarg.1; brfalse L_after; ldarg.1; callvirt Invoke; L_after: ret`（去掉 dup，判空与取值各压一次）。改完用 `ilstack` 复跑应回到 **0 违规**。

### 8.2 问题①：客户端凭什么决定去下载新 DLL / 新资源

静态可见的**唯一判据是「资源版本」**，不是「DLL 版本」：
- DLL 没有独立的版本门——它作为资源包内容被 YooAsset 带着走；客户端代码里**没有任何**「targetfuntional.dll 版本比较」的 IL。
- 两处资源版本比较：① 服务端下发 `fres_version`（`SaveData.GetInt`）vs 本地 `ResVersionApi.GetVersion()`；② 内测 `testResVersion` vs 本地（`UpdateTestResVersion`）。
- 本地版本来自 **包内已下载资产** `res_version.txt`（`TryGetVersion` IL 实锤），即「我已经装了哪一版资源」。

⇒ 结论：**只要本地资源版本 < 服务端要求，客户端就会去拉新资源（新资源里包含新的 DLL 字节）**。这正是 13:49 与 14:23 两次换代能落到设备上的机制。

### 8.3 问题②：钉死这条链后，DLL 与内容是否都会停更

| 钉死动作 | 能确定挡住 | **不能确定**挡住 |
|---|---|---|
| `GetVersion()` → `Int64.Max` | `fres_version` 比较（本地恒 ≥ 服务端）⇒ 不弹「检测到版本更新」、`hasResUpdate=false`、`UpdateTestResVersion` 恒 false | YooAsset **启动期的 CDN manifest 版本比对**（本模块内无该代码，属 native/启动器侧） |
| 8 处 no-op（Vch/BlockVersion/ShowNewVersion/OnNewVersionClick/NeedUpdate/OpenUrl/ShowOnShow/OnDownLoadClick） | 版本封锁、推荐更新按钮、商店跳转 | 资源下载本身 |
| 3 处 `Application.version→999999` | 客户端上报的版本串 | 服务端据此下发什么内容 |

**关键风险（对应「只钉 DLL 不钉内容会错配」）**：DLL 与内容同属一个资源包，**不可能只钉 DLL 不钉内容**；一旦资源继续更新而补丁 DLL 是旧布局，就是现在这种「跑 2,746,368 补丁、内容已 2,748,416」的错配形态。反过来，若把资源版本也钉住，则玩家**永远停在旧内容**（活动/新关卡看不到）。
⇒ 静态结论：**「钉死」不是稳态方案**；稳态只有「跟版」（每次换代重建补丁，即本轮 hf5→hf6 的做法）。

### 8.4 问题③：钉死后服务端版本校验会不会拒

- 静态能看到的只有**客户端侧**：`Application.version` 会被塞进 `CfgCallBack` / `UpDatePlayerData` / `UpDatePlayerMainData` 的上行载荷；`GetVersion()` 也会进 `StaticHeroLocalReport::Begin`。
- 服务端拿到「999999 / Int64.Max」后是否拒登、是否触发风控，**客户端代码里不可判定**（无服务端逻辑）。
- 已知旁证：vc1637 线曾长期使用该钉死族，未报登录被拒；但**不等于本代安全**。
⇒ 标「静态不可判定」，这是之前否决 vtpin 的直接理由之一。

### 8.5 「为什么永远追不上」的结构性答案

官方把热更 DLL 放在资源包内、按资源版本灰度下发，而我们的补丁是**按某一版 DLL 的 IL 布局离线生成**的。两者没有版本协商机制（客户端代码里没有任何「补丁兼容性」判断），所以：
- 官方换代 → 长度变化 → `PickDllVariant` 精确/长度双 miss → `PASSTHROUGH` ⇒ 功能与防封**整体失效**（不是部分失效）；
- 同长度换代还能靠 FORCED PATCH 顶住（历史 11-10），**长度一变就只能跟版**。

> 唯一能改变这条的，是在 so 侧对「未识别长度」做**受控处理**（例如按长度容差做同布局替换并实测），但那属于改 native 行为，需单独评估，不在本轮范围。

```
29d6020  cmp w22, w29                  ; 32 位比较
29d602c  ldr x9, [x19, #0x40]          ; 表基址
29d6030  str x26, [x9, x8, lsl #3]     ; 填表：写 8 字节
29d6038  cmp x29, x8                   ; 64 位比较（x29 = 零扩展的 w29）
29d603c  b.ne 29d602c                  ; 循环
```

形态判读（事实层）：① 这是**指针填充循环**（stride 8、写指针值）；② 上界同时以 `w29`（32 位有符号比较）与 `x29`（零扩展 64 位）出现 ⇒ 源码形态是 `for (size_t i = 0; i < (size_t)(int32)count; i++)`；③ count 为负时被零扩展成 **42.9 亿**，循环必然撞穿段边界。

### 10.2 三种候选来源的排除/保留

| 候选 | 判定 | 依据（静态） |
|---|---|---|
| **我们补丁改过的方法返回值** | **排除** | 31+delta 的注入只有 4 类形态，逐条枚举：① 写 `bool` 1 字节（P23/P25/P31 等）；② 写数值 `×N`（P19 `target*=2`、P20 `amount*=N`、P21 `amount*=N`）；③ 提前返回常量（`true` / `1` / `999L` / `1L`，P15/P17/P24/P26/P28–P30）；④ `throw`（COS 两条）。**没有任何一条返回 count/长度**。且托管返回值走 interpreter 的求值栈，不会变成 native 的 `ldr w29,[x24,#0x1c]`。 |
| **热更程序集（targetfuntional）元数据** | **基本排除** | 我方产物元数据自洽：ilgeo 逐项核对 `#~`/`#Strings`/`#US`/`#GUID`/`#Blob` 流存在且大小随增量线性增长、TypeDef 1946 / MethodDef 13421 与补丁增量吻合、方法体几何 CLEAN；且解释器执行托管 IL 时**不会**以「node+0x1c 结构字段」的方式遍历 `#~` 行数。 |
| **AOT/native 侧运行期结构（含 Il2CppClass / 注册表 / 缓存表）** | **保留（最可能）** | 该循环读写 native 指针数组、以大栈帧进入、字段偏移 0x1c/0x40/0x28/0x30 全为 C 结构布局；这类填表逻辑只存在于 AOT 侧。 |

### 10.3 `x19` 是哪类结构：能确定与不能确定

**不能确定**（诚实标注）：so 的代码页在文件里是密文（易盾按页解密，lead 已用活进程页证实），无符号表；`0x29d5e78` 的 xref 与子函数特征（`0x29e63e0`/`0x29e6440`/`0x5b1f270`）都需要可读代码段才能判，**静态不可得**。

**能确定的形态约束**（供后续按图索骥）：
- `[x19+0x28]` / `[x19+0x30]` 成对出现 ⇒ 容器/注册表的 **begin/end（或 head/tail）**；
- `[x19+0x40]` 为**输出表基址**（被填指针数组）；
- `[node+0x1c]` 为**每节点 count**，`node` 由上述链表遍历得到。
⇒ 一个「持有指针数组 + 节点链 + 每节点计数」的运行时注册表，符合 il2cpp **AOT 侧的类型/方法注册与槽位填充**特征（例如 vtable/interface 槽位、元数据用法表），而不是托管集合。

**负值 -118（0xFFFFFF8A）的三种可能，全部指向「结构/内容错配」或「结构被写坏」**：
1. `count = (int32)(end - start)`，`start > end` ⇒ 负值（长度/布局不一致）；
2. 字段偏移错位（新旧版本结构体字段增减）⇒ 读到相邻字段（常见为负的枚举/短整型）；
3. 计数被递减到负（逻辑缺陷）。
三者中 1、2 都与「客户端旧布局 + 服务端新内容」的**版本错配**一致。

### 10.4 结论

- **静态可证**：`count` 不来自我们的 IL 补丁（注入无 count 语义，托管返回值也不进 native 结构字段）。
- **静态可证**：我方 hf5 产物元数据与映像自洽（几何/栈/PE 三审计全绿，唯一缺陷 AdsFree 已修）。
- **推断（未确证）**：`count` 来自 AOT/native 侧结构，其负值由结构/内容版本错配或该结构被写坏造成；`x19` 具体类型需可读代码段才能命名，当前不具备。

### 10.5 建议的下一步（都不需要「试错」）

1. 用 hf7（AdsFree 已修）替换 hf6 重出包 —— 这是目前**唯一被静态证明的真缺陷**，先消掉它；

| 判据（实测） | 结论 |

| 写入步长 **8 字节**（`str x26,[x9,x8,lsl#3]`） | **不是 vtable**：il2cpp 的 vtable 项是 `MethodInfo*`（8B，但**内嵌在 Il2CppClass 内**），虚调用表项是 `VirtualInvokeData`（**16B**）；这里是独立分配、stride 8 的指针数组 |
| 目标表基址 `[x19+0x40]` = `0x76d74eb220`，落在**单独 arena**（0x76d7…），不在任何 Il2CppClass 内 | 同上，排除 vtable |

**结论**：填的不是 vtable，而是**由链表分段聚合出来的指针表**（每段长度取自 `node+0x1c`）。在「方法指针表 / 泛型实例表」两者之间，凭这段码**无法唯一判定**——需要节点结构（`node` 的类型与 `+0x1c` 的字段语义）。

### 13.3 `[node+0x1c]` 是哪个字段：可判定与不可判定

- **可判定**：它是节点内偏移 `0x1c` 处的 **int32 段长度**，被当无符号使用（`ldr w29` 后被零扩展成 `x29`，再与 `x8` 做 64 位比较）⇒ 源码形态 `for (size_t i = 0; i < (size_t)len; i++)`。
- **不可判定**：`node`（`0xb4000077389f0780`，托管堆）具体类型。注意一个**关键事实**：节点在**托管堆**、表在**native arena**、容器 x19 在 `0x7730…`（native）⇒ 这是「托管对象链表 → native 指针表」的投影，属**运行时桥接层**，不是游戏逻辑。
- **−118 的现实解释**：`0xffffff8a` 是**小负数**，不是随机垃圾。分段长度常见来源是 `(int32)(end - start)` 或 `count` 递减；出现「−118」更像**读到了相邻字段**（布局位移）或**差值为负**（段被裁掉但未重算）。与 §11.4「GameData +4 字段，整体后移」的换代特征一致（推断）。

## 14. 「不新增类型」注入方案（待批准，未落地）

### 14.1 硬约束：只有「表尾宿主」才不产生 RID 位移

Cecil 追加方法/字段时，会把新行插到**该类型现有成员之后**，导致其后所有行 RID 整体后移。因此宿主必须是三张表的**表尾类型**。官方 2,748,416 实测表尾：

```
MethodDef 尾部:  … 13413 <PrivateImplementationDetails>::ComputeStringHash
                     13414 $Obfuz$RVA$0::.cctor
                     13415 $Obfuz$ConstFieldHolder$0::.cctor      ← 最后一个方法
FieldDef  尾部:  … 11631 $Obfuz$ConstFieldHolder$0::$Obfuz$RVA_Value107 ← 最后一个字段
TypeDef   尾部:  … 1944 $Obfuz$ConstFieldHolder$0（1943 $Obfuz$RVA$0，1945 起是补丁新增）
```

⇒ **唯一安全宿主 = `$Obfuz$ConstFieldHolder$0`**（同时是 MethodDef 尾与 FieldDef 尾）。任何其他类型（含 `NetDataCalculater`、`GameData`）都会造成 RID 位移 —— 而我们刚用 `ilrid` 证明当前产物**零位移**，换成普通类会**主动引入**位移，风险更高，不建议。

### 14.2 方案（只改「目标类型选择」，不动补丁语义）

| 项 | 现状 | 方案 |
|---|---|---|
| 宿主类型 | 新增 `Starry.StarryConfig`（TypeDef 1946） | **复用 `$Obfuz$ConstFieldHolder$0`**（不新增类型） |
| 静态字段 | `lines` / `nextCheck` / `blocked`（3 个） | 追加到 FieldDef 尾（11632..11634），不改既有 108 个字段顺序 |
| 静态方法 | `.cctor` + `Get`/`GetBool`/`GetInt`/`NoteBlockedRpc`/`StrictBlockedRpc`（6 个） | **去掉 `.cctor`**（宿主已有 cctor，不能重复），改为 `Get()` 内**惰性初始化**；其余 5 个方法追加到 MethodDef 尾（13416..13420） |
| 调用点 | `call StarryConfig::X` | 改成 `call $Obfuz$ConstFieldHolder$0::X`，其余字节不变 |
| 补丁语义 | — | **一字不动**（key 名、判断条件、注入位置、栈形态全部不变） |

**为什么惰性初始化是安全的**：现有 `.cctor` 只做「读 starry_config.ini 到 lines、重置 nextCheck」；改成 `Get()` 首行 `if (lines == null) Reload();` 后，首次读取同样完成初始化，且**不再依赖类型初始化时机**（反而更稳）。`blocked` 是无条件初始化的空字典，改为字段声明处 `= new ...` 会需要 cctor ⇒ 改为首次 `NoteBlockedRpc` 时判空创建。

### 14.3 风险与验收

| 风险 | 评估 |
|---|---|
| 动 `$Obfuz$*` 类型是否影响 Obfuz 运行时 | 只**追加**静态字段与方法，不移动既有字段/方法；Obfuz 解密走 `$Obfuz$RVA$0` 与 `EncryptionService`，与该 holder 的**字段顺序**无关（字段按索引访问，追加在尾部）。风险低但非零 |

| 可用性 | 若 Obfuz 在初始化时**校验字段数/大小**（未知），可能报错；这是本方案唯一未知项 |

### 16.3 保留解释（当前唯一自洽的解释）

崩溃函数 `0x29d5e5c` 的形态（§13）：
- 由 il2cpp 运行时按「**加锁 → 查表 → 分配 0x40 → 在栈上构造节点 → 插表**」调用（调用者 `0x29d16f8`，`x30=0x29d1794`）；
- 它遍历**托管堆**上的节点链（`x19+0x28` 头、`&x19+0x30` 哨兵，node 形如 `0xb4000077389f0780`），把结果平铺成 **native arena** 上的 8 字节指针表（`[x19+0x40] = 0x76d74eb220`）；
- 每段长度取 `[node+0x1c]`（int32），现场值 `0xFFFFFF8A` = **−118**；`ldr w29` 后被零扩展成 64 位当上界（源码形态 `for (size_t i=0;i<(size_t)len;i++)`）⇒ 循环写到 42.9 亿 × 8B，撞穿段边界 `0x76d8000000`（`PROT_NONE` 守护页首）。

⇒ **node 在托管堆、表在 native arena、容器在 native** ⇒ 这是运行时桥接层，**不是游戏逻辑，更不是我们的补丁**。
⇒ `−118` 是**小负数**（不是随机垃圾），形态符合「**读到相邻字段 / 差值为负**」。结合 §11.4 实测——能跑的官方 2,738,688 与会崩的 2,748,416 之间有 16 处结构变化，其中 `GameData` 字段 **311→315（+4，其后续字段偏移整体后移）**、`Enemy` 61→62、`MiJingWindow` 26→27 方法——最合理解释是**按旧布局读到了相邻字段**（布局位移）。

- ⇒ **若这版仍崩，责任必在 `block_report` 那 35 处**（(a) 类），与秒杀行为无关；若这版不崩，则锅回到功能侧，需按 feat 继续切。

### 20.6 另一条静态观察（供参考，非结论）

`block_report` 的 35 处里有 **6 处落在 `InfinityCore.NetDataCalculater::$B/$C/$G/$H/$i/$L`**——这些是 Obfuz 改名后的**数据出站计算**方法。若崩溃与「入秘境时的一次数据上报/结算计算」有关，这 6 处是唯一在**非战斗路径**上也会执行的注入点（它们由服务端推送/心跳触发，不由玩家操作触发）。**这是目前唯一能解释「冷启点秘境即崩」的静态候选**，建议对照实验后优先验证。

## 21. 根因锁定：短跳转越界未升级 ⇒ 分支目标写成 −118（= 崩溃现场的 count 值）

> 触发：lead 要求审计 ilpatch 插入指令时的 6 项处理。新写**原始字节级**校验器 `ilraw`（不信任 Cecil 写回结果，直接解文件机器码，逐条验指令边界/分支目标/EH 偏移/短跳位移范围）。

### 21.1 决定性证据（同一产物，两种校验）

对 `targetfuntional_13101new_oneshotfix2.dll`（当时最新产物）：

```
[BR] EnemyGroupData::CanChanllage(int&,int&,bool&)  IL_0007 -> IL_FFFFFF8A  不在指令边界 (codeSize=435)
[BR] WorldSelectCell::Show(int)                      IL_063A -> IL_05BF      不在指令边界 (codeSize=1728)
== methods=13220 decodeBad=0 brBad=2 ehBad=0 shortOver=0
```

- `IL_FFFFFF8A` = **−118**，与真机崩溃现场 `[node+0x1c] = 0xffffff8a` **完全同值**；
- 换算：该处需要位移 **+138**（0x8A），被按 **sbyte** 写出 ⇒ `0x8A` 解释为 −118 ⇒ 目标 = `IL_000C + (−118)` = `0xFFFFFF8A`；
- `CanChanllage` 正是 `MiJingDetial::OnClick` 直接调用的方法（§5），注入点 IL_007C/00FA/0154/01A5 把 IL_0007 处那条短跳的跨度顶过 ±127。

⇒ **这就是「全 key=0 仍崩」「点秘境即崩」「delta-only 不崩」的统一解释**：
| 现象 | 解释 |
|---|---|
| 全 key=0 仍崩 | 那条 `brfalse` 的**目标本身**已坏，与开关值无关（开关只决定分支走哪边，走到坏目标就飞） |
| 点秘境即崩 | 坏分支在 `CanChanllage`，它是 OnClick 的第一个调用 |
| delta-only 不崩 | delta 只往方法**入口 index 0** 插入，所有分支跨度不变 ⇒ 不会溢出 |
| 零补丁/探针不崩 | 没有任何插入 |
| 只开 oneshot 也崩 | 只要 31 条里有 `mijing_free` 的 4 个中点插入，坏分支就存在 |

| # | 项目 | Cecil 是否处理 | 结论 | 证据 |

### 21.3 修法（改 patcher，不改补丁语义）

```csharp
// ilpatch_delta_13101/Program.cs
// 读入即快照指令数；写盘前对「指令数变了」的方法做同样处理
```

## 22. 「禁止热更」在 13.x 是否失效（静态判断）

### 22.1 代码事实（`WxsjMod.cpp` `HookExec`）

```cpp
const uint64_t h = Fnv1a64(bytes, len);
const DllVariant* v = PickDllVariant(len, h);
if (!v) {                                   // ← 未知长度/哈希
    LOGE(" no variant for len=%d fnv=%016llx : PASSTHROUGH official");
    StarryShowToast("[无限升级] 游戏热更版本未识别，本次以官方版本运行（存档安全）…");
    return orig(self, data, outP, mi);      // ← 原样装载新官方 DLL
}
```

⇒ **确实失效**：命中「未知变体」时直接把官方新 DLL 放行 ⇒ 新热更生效，我们的 11 项功能与 delta 防封**全部不生效**（已封账号一进即被判封，11-19 14:27 实测）。
同一函数后面的 `wasMismatch`（`FORCED PATCH`）只覆盖「长度匹配但哈希不同」的情形，覆盖不到「长度也变了」。

### 22.2 能否改成「仍阻止热更」

**静态上可以，两条路，代价不同**：

| 方案 | 做法 | 结果 | 风险 |
|---|---|---|---|
| **① 拒绝装载**（v7.15 老做法） | `!v` 时**不调 `orig`** | 热更被真正挡住 | 热更程序集不装载 ⇒ **进不了世界**（卡在加载）；存档不写、不损坏，但玩家不可玩；历史已否决（用户卡死投诉） |
| **② 强制注入内嵌补丁**（推荐） | `!v` 时仍走已有的注入路径：`pLen ≤ len` → `memcpy + 尾零`；`pLen > len` → **selfarray 假数组**（11-18 已实测可用） | 无论官方给什么，都跑我们的 DLL ⇒ 功能与防封**始终生效** | 我们跑的是**旧版逻辑**，若新官方 DLL 依赖新 native 符号/新协议字段 ⇒ 可能功能缺失、断线或异常；**存档仍安全**（只替换内存字节，不写存档） |

**判定依据（为什么 ② 可行）**：
- 注入的是**整份 DLL 字节**，自包含，不依赖官方新版本的 IL 布局；
- selfarray 路径已验证（`mode=selfarray`，官方 2,748,416 + 1 字节探针实测可跑）；
- 与「已知变体的 FORCED PATCH」是**同一条代码路径**，只是把入口条件从 `v != null` 放宽为「总是用内嵌主版本」。

### 22.3 不能保证的部分（必须说清）

1. **资源包热更挡不住**：DLL 只是热更的一部分，YooAsset 资源仍会更新（§8）；DLL 与内容错配可能出现新问题（参考 §11.4 那 16 处结构变化）。
2. **服务端版本校验不可静态判定**：客户端 `Application.version` 会进上行载荷（§8.4），服务端是否因此拒登/风控，客户端代码看不到。
3. **「永不失效」不可能**：只要官方换了 DLL 依赖的新 native 能力，旧 DLL 就会缺功能；这条路只能保证「我们的补丁一直在」，不能保证「游戏一直正常」。

> 结论：**当前确实失效；可以改成方案 ② 让补丁始终生效**（改动在 so 侧，属 builder 范围，需单独评估与实测）。方案 ① 虽能真正挡住热更但会让玩家进不去游戏，不建议。
