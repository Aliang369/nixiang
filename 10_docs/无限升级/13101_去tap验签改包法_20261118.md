## 三、脚本与产物

```
# A) 只改 dex（自验模式；默认输出 07_patched/无限升级/13101/tapfix/tapfix.dex）
bash 04_scripts/无限升级/patch_wxsj_tap_unshelled_dex.sh --dex 06_dumped/无限升级/13101/dex_dump/dex_2_77c7fb6ffc_8686144.dex --twice

bash 04_scripts/无限升级/patch_wxsj_tap_unshelled_dex.sh <无壳包.apk> --swap 07_patched/无限升级/13101/tapfix/tapfix.dex --out 08_output/无限升级/无限升级_13.101_unshelled-tapfix-releaseSigned.apk
```

- 实现：`04_scripts/无限升级/dexpatch/PatchWxsjTap.java`（dexlib2 2.5.2，脚本内 javac 即时编译），**只改 3 个类的 4 个方法**，其余类原样透传。
- `--swap`：不重新打补丁，直接把给定 dex 换进包 → 与 dex 产物**逐字节一致**（可复现）。
- APK 模式固定流程：定位含 `TapSignKit` + `GatekeeperRepository` 的唯一 dex → 换入 → 删 META-INF → `zipalign -p 4` → `apksigner sign`（`01_tools/starry_release.jks`）→ `verify --print-certs` → 断言「其余条目 sha256 逐字节透传」。

### 4.1 自验（脚本内置，原文）

```
  回读：10538 -> 10538 文件；新增 0 / 删除 0 / 改动 48

```

**噪声归类规则（复用脚本时必须知道）**——三类差异视为语义等价，逐条单列、不计入目标：

1. 调试项：`.line` / `.local` / `.end local` / `.param` / `.prologue` / `.restart local` 行；
2. **静态字段默认值被省略**：`.field … = false / = 0 / = 0x0 / = 0x0L / = 0x0s / = 0x0f / = 0.0 / = null` → 写回后无值（JVM 默认值，语义相同）；
3. try/catch 区间重编码：`:try_start_N` / `:try_end_N` 标签与 `.catch/.catchall` 行（相邻同 handler 的 try 段会被合并）。

**断言（硬）**：三类之外的任何差异、以及任何新增/删除 smali 文件 ⇒ 直接 FAIL。本次 45 条噪声全部落在第 2 类（实测样例：`.field private static Rv:Z = false` → `.field private static Rv:Z`）。

## 五、风险与待验证

1. **真机三判据（等用户/lead）**：① 无「应用的包名/签名未在 TapTap 开发者中心正确配置」② 登录落内嵌 WebView 而非拉起 TapTap 客户端 ③ 能进主界面。若 ① 出现，先查 ④ 的串大小写与 `getSign` 期望格式（本 dex 期望小写无冒号）。
2. **③ 只改实例化、不改 `instance-of`**：若 SDK 后续版本把 handler 选择改成按数组下标/类型白名单，本补丁会失效（判据：登录页仍拉起客户端）。
3. **`getSign` 单点回灌**：本 dex 里取签名的调用点只有 `GatekeeperRepository$initialize$1$networkData$1` → `TapSignKit.getSign`，若新版新增第二条取签名路径需重查。
4. **native 侧仍可能自己算签名**（`libtapsdkcore.so`）：若日志仍报 1001，说明校验在 native，需要另案处理（本次未观察到，待真机）。
5. **dexlib2 写回会重排整体布局**（size 8,686,144 → 8,809,244，+123 KB）：不影响运行，但意味着「与原 dex 逐字节比对」类校验（如有）会看到全包差异；比对判据应用「目标方法 + 噪声三类」。

## 六、经验（可复用条目）

- **smali 2.5.2 的 `assemble` 非字节确定**：同一 smali 树连跑两次产出不同 md5（实测 `f200f5d7…` / `b3a8e90b…`，而反编译文本 `diff -rq` 完全相同）。原因在于汇编器内部类型/方法 id 分配顺序不稳定。
- **需要可复现就必须走 dexlib2 级手术**：`DexFileFactory.loadDexFile + writeDexFile` 实测确定（两次 `d5508880…`），且只改目标方法、其余类对象原样透传。
- **副作用**：dexlib2 写回会省略静态字段的默认值（`= false` / `= 0` / `= null`），因此「逐文件 md5 比对」必须带语义归一化，否则会误报几十个无关类差异（本作 45 个）。
- **补丁自验的正确形态**：不是「grep 类名/字符串」（dex 字符串池会去重，`ClientLoginHandler;` 在 instance-of 里本就存在），而是「反编译 → 逐文件 md5 + 语义归一化 → 差异集合恰好等于目标文件」＋「目标方法的指令级 diff」。
