## 2. 卡密闸门控制流（反编译定论）

**唯一入口 = `local.privategame.infinity.GateActivity.onCreate`**，仅此一处，无 Java 侧二次校验。

```
AndroidManifest.xml:263  <activity android:exported="true" android:name="local.privategame.infinity.GateActivity"
                             android:theme="@android:style/Theme.Material.NoActionBar">
                           <intent-filter> MAIN + LAUNCHER </intent-filter>
UnityPlayerActivity  :62   android:exported="false"   ← 只能由包内 Activity 拉起

GateActivity.onCreate(Bundle)
  → super.onCreate → new WebView(this)
  → getSettings: setJavaScriptEnabled / setDomStorageEnabled / setAllowFileAccess
  → setWebViewClient(new GateClient(this))
  → setContentView(webView)
  → loadUrl("file:///android_asset/infinity_gate.html")

assets/infinity_gate.js (JS 侧全部校验)
  → 正则 ^{R1}.{issued}.{expires}.{32hex}.{86b64}，要求 expires-issued == 86400
  → crypto.subtle.importKey("spki", PUBLIC_SPKI, ECDSA P-256) + verify(SHA-256)
      payload = "INFINITY-OFFLINE|com.xingzuodaoshi.infinityOffline|R1|<issued>|<expires>|<hex>"
  → 通过后 localStorage["infinity-offline-license-v1"] = 码
  → window.location.href = "infinity-activated://launch"

GateClient.shouldOverrideUrlLoading(webView, url)
  → url == "infinity-activated://launch" 且未 launched 时：startActivity(UnityPlayerActivity) + finish()
  → 其它 url 一律 return true（全部拦掉，页面无法跳外链）

GateClient.shouldOverrideUrlLoading —— 只做 scheme 路由，没有任何验签逻辑。
```

要点：
1. **通过标志没有存在 Java 侧**（无 SharedPreferences / 无静态布尔），只存在 WebView 的 `localStorage`，且每次启动重新验签（复启动时 `checkWindow=false` 只跳过时间窗，不跳过签名）。
2. `GateClient` 不是校验者，只是「看到自定义 scheme 才拉起 Unity」的路由器；把它留着对外部行为无影响。
3. 闸门与游戏本体解耦：Unity 启动只依赖 `UnityPlayerActivity`，不读任何 license 文件。
4. 相关副作用与卡密无关：`com.codex.offline.LocalInitializationProviders`（manifest 中的 provider）在进程启动时把 `assets/offline/*` 解到 `files/offline`，与闸门互不影响。

## 3. 候选方案与选型

| | A) 只改 manifest：launcher 直接指向 UnityPlayerActivity | **B) 只改 classes3.dex 的 GateActivity.onCreate（选用）** |
|---|---|---|
| 改动对象 | 二进制 AXML：`exported=false→true`、新增 MAIN/LAUNCHER intent-filter、组件名换串 | 一个 1.9 KB 第三方 dex 的方法体 |
| 官方件 | manifest 变了（`resources.arsc` 与资源索引存在被牵连风险） | **manifest / classes.dex / resources.arsc / libil2cpp.so 全逐字节透传** |
| 与硬约束 §A#10 | 冲突风险：改 manifest 通常要过 `apktool b`（禁）或手写 AXML 编码器；一旦重编码就会重排字符串池/节点，`resources.arsc` 透传无法保证 | 完全满足：只替换第三方新增的 dex |
| 启动路径 | **该改包上从未验证过**的新路径（系统直接冷启 Unity Activity） | 复现该包**已验证可用**的路径（激活成功后 GateClient 就是这么拉起 Unity 的），只是把触发条件从「点击激活」换成「onCreate」 |
| 易盾壳兼容 | 静态可证不按 launcher 名字拦（plist/nplist 只控制 FLAG_SECURE；InstrumentationProxy 只转发 callActivityOnCreate），但 `libthemis.so` native 完整性校验静态无法证伪，manifest 一动就把不确定性引进来 | 不动 manifest，壳看到的一切声明与底包完全相同 |
| 类解析时机 | 与 B 相同（同进程同 ClassLoader，壳先解出真 dex） | 相同 |
| 攻击面 | UnityPlayerActivity 变 exported=true（外部任意 App 可拉起） | 不变 |

**否决 A 的决定性理由**：A 的收益是「少一个中间 Activity」，但代价是把「官方资源逐字节透传」这条硬约束变成需要额外证明的风险，并引入一条在该改包上从未跑通的启动路径；而 B 的改动面只有 81 条指令级别的方法体，且复现的正是现网已验证的路径。

> 补充事实（支撑「无静态 Unity 类」这一判断）：三个 dex 中只有 classes3.dex 出现 `unity3d`（GateClient 的 type 引用），`classes.dex`/`classes2.dex` 一次都没有 ⇒ Unity 的 Java 类由易盾壳在运行时解密加载，静态包内不存在。这条本身对 A/B 影响相同，但说明「改 manifest 指过去」并不比 B 更"直接"。
