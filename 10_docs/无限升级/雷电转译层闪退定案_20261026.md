# 无限升级 雷电模拟器（x86_64 / libhoudini）启动闪退定案（2026-10-26）

## 结论（一句话）

闪退**不是包结构、签名、dex 注入或易盾壳的问题**，而是包内 `libstarry_magic.so` 的 **libil2cpp inline hook（DobbyHook）在雷电 houdini 转译层下不可用**：
hook 报告安装成功但整轮从不生效，而游戏的 ARM 代码在被 houdini 首次翻译时进程直接 SIGSEGV。

A/B 闭环：**有 so → 4/4 次启动全崩；禁用 so → 存活 22 s+ 无崩溃；恢复 so → 再崩。**

## 现场（实测事实）

- 设备：`emulator-5556`（雷电实例「雷电模拟器-1」；指纹 `XIAOMI/unicorn`、Android 14、`ro.product.cpu.abi=x86_64`、abilist 含 `arm64-v8a`）
- 包：`com.xingzuodaoshi.infinityUpgrade` 12.10701 / vc1644，`base.apk` md5 `d868ba9c68cdfe94ac632147d55e7b83`（122,062,727 B，= 本机 `08_output/无限升级/无限升级_12.10701_surgical-final-releaseSigned.apk`，mtime 2026-10-26 14:45:28），首装 2026-10-26 15:18:45
- 包内 native 只有 `lib/arm64-v8a`（**无 x86_64**）⇒ 全部 native 代码由 `libhoudini.so` 转译执行

## 崩溃签名（4 次启动完全一致）

```
Fatal signal 11 (SIGSEGV), code 1/2 (SEGV_MAPERR/SEGV_ACCERR) in tid (dTi)
rip = /system/vendor/lib64/libhoudini.so + 0x30c02a      ← 恒定
backtrace #00..#07 全部 libhoudini.so，#08/#09 libc 线程启动
rsi/r13 = libil2cpp.so 的 ARM 代码页地址（例 0x40002911f270、0x4000271b6d08）
rdi     = 无效目标（落在 /dev/fastpipe 与 libEGL_adreno 之间的未映射 / PROT_NONE 空洞）
进程 uptime 3 s / 5 s / 6 s / 9 s
```

- 形态＝「从 libil2cpp 取 ARM 代码 → 写入 x86 侧目标地址」的搬运（memcpy 特征），**目标地址无效** ⇒ houdini 在翻译 libil2cpp 代码时内部目标失效。
- tombstone 的 memory map 显示：`libil2cpp.so` 所有段均为 `r--`（代码由 houdini JIT 缓存承载，无 `r-x`），`libstarry_magic.so` 同样 `r--`/`rw-`，无映射坏点。
- 崩溃线程 `dTi` 早于星空层线程创建，**不是** starry 自己的线程。

## 关键反常：hook「装上了」但从未生效

```
I Mod_Menu: [Wxsj] hook installed @base=0x400023600000 +0x2b890d8 orig=0x7d147e0ba000 dual=hf2:2024960B+hf3:2022912B
I Mod_Menu: [Wxsj] config block_report=1 (exists=1)
I StarryMagic: [Wxsj] 初始化成功 / MOD 已就绪 engine=1 cocosGame=0 unityGame=1
I Mod_Menu: [Wxsj] ForceClear (hook kept, features config-driven)
（1.3–4.8 s 后 SIGSEGV）
```

- **整轮没有任何 `Exec call len=` / `patched dll injected` 日志**。真机上这两条必然出现（见 `_state/games/无限升级.md` 各轮真机实锤）。⇒ 游戏调用 `RuntimeAssemblyLoader::ExecuteRuntimeAssembly` 时执行的是 houdini **已缓存的翻译块**，Dobby 写入的跳转从未被执行。
- 推论：hook 既不生效，又改动了 houdini 管理的只读代码页（`r--`）；`orig=0x7d147e0ba000` 这个 trampoline 落在 **x86 用户空间 0x7d14…**，不在 houdini 的 ARM 模块地址空间（`0x4000…`），houdini 无法接管 → 该函数首次被翻译时解析跳转目标失败 → 崩溃。
- 星空层其余部分全部正常：`RegisterNatives 20/20`、菜单初始化、`MenuService overlayVisible=true attached=true`、鉴权链路可达（仅卡密未登录 ⇒ `[验证] grant rejected`，属既有预期态）。

## A/B/A 实验（本轮完成，可逆）

| 步骤 | 操作 | 结果 |
|---|---|---|
| A | 原状启动 ×4 | 4/4 SIGSEGV，3–9 s 内死 |
| B | root 临时 `mv /data/app/~~…/lib/arm64/libstarry_magic.so → …so.off` | 进程存活 22 s+，Unity 持续出帧（60 fps Choreographer），crash buffer 空，仅 Java 侧 `UnsatisfiedLinkError`（原生方法不可用） |
| A' | `mv` 恢复（md5 `b8462be707aa5bba447e195ddab43280`，`cmp` 逐字节一致） | 再次 SIGSEGV（3 s） |

⇒ 闪退与包内 `libstarry_magic.so` 强相关，**与易盾壳 / houdini 本身无关**（无 so 时壳解密、il2cpp、渲染全部正常）。

## 判定分级

- **实测事实**：上述崩溃签名、hook 未触发、A/B/A 结果、设备与包标识。
- **证据支持的推断**：根因＝houdini 转译层下对 libil2cpp 的 inline hook 不可用，且会把进程打死。
- **同类先例**：`d6266683`（2026-10-25 绝区零）已定案「雷电 houdini + 反作弊下 libil2cpp inline hook 不可用」。本作是易盾壳，机制同源。
- **不适用**：真机 arm64 原生（本轮包在真机侧 10-12 已多轮实锤，本结论不外推到真机）。

## 未验证 / 下一步（需 mac 端）

1. **细分 A/B 未做**：「加载 so 但不装 hook」是否稳定（需 mac 端重编 so；本机缺该游戏构建输入 `libs_wxsj` 等，无法在此重编）。
