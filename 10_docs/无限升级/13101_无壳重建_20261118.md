### 7.2 模板与 SPI 的真实关系（2026-11-18 复核，**已纠正一次误判**）

最初我按「字符串池里 `TapLoginForceWeb` 有 1 处命中」推断「基准模板走旧的 `sign.TapLoginForceWeb` 实现、与静态改包法口径不一致」——**这个判断是错的**，经 baksmali 反编译逐条核对后纠正：

| 证据 | 结果 |
|---|---|
| `baksmali d` 包内 `classes5.dex`(md5 `ab10ab27…`) → `com/starry/magic/games/wxsj/GameHookImpl.smali` | 3,406 B |
| `grep -c TapLoginForceWeb GameHookImpl.smali` | **0**（该类零引用旧实现） |
| GameHookImpl 实际调用 | 第 94 行 `invoke-static {p1}, Lcom/starry/magic/o/U0;->j(Landroid/app/Activity;)V`；第 122 行 `->k(...)`；第 134/143 行 `Lcom/starry/magic/o/x;->c/d(...)`（GameHooks 注册） |
| `com/starry/magic/o/U0.smali`（R8 改名后的 `core.TapTapWebLogin`） | `StarryTapLogin` / `TapTapLoginActivity` / `fallbackToWeb` / `com_taptap_sdk_login_request` 命中 **20 处** |

**结论**：模板里的 `GameHookImpl` 走的就是 **R8 改名后的 `core.TapTapWebLogin`**（`o/U0`），与 `_sig` 模板**同源同实现**，只是 `_sig` 版额外插了 `SigReplace`。`TapLoginForceWeb` 那 1 处命中是**源码树里其它游戏仍在用的旧类被一并编进 dex 的残留**，本游戏不经过它。

⇒ 现在的形态是「**静态改包法（dex 侧改 TapTap）+ 同一套新 core SPI 兜底**」，两层同源、不冲突，无需再出「纯基准无 SPI」版。

⇒ 另一个正确的方法论结论（与 §7.1 判据 ② 一致）：**签名/登录类改造不能靠 grep 字符串池判定**（dex 字符串去重，类名本来就在池里，计数不变）；必须 baksmali 看调用点，或用真机行为验。
