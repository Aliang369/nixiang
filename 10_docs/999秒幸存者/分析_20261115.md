## 4. 建议实现形态（总体）

1. **六项全部落在 `libil2cpp.so` 的 AOT 函数上** → 不存在「纯 Java 改判定」路径（Java/dex 里没有游戏逻辑）。
2. 可行形态只有两种：
   - **(a) native hook（推荐）**：菜单开关 → native 侧按 RVA 装 hook（`player.behurt`/`data.bullethurt`/`admanager.showad` 等）。优点：不动 dex、不受存档覆盖、可热切换。
   - **(b) il2cpp API 反射改字段**（`unlockcoupon`/`needcoupon`/`sp`）：用 `dlopen(libil2cpp.so)` + 导出 API（`il2cpp_class_from_name`/`il2cpp_field_set_value`）改实例字段；仍是 native 代码，只是不 patch 代码段。
3. 纯 Java 侧只能做「菜单 UI + 通过 JNI 调 native 开关」，**不能**承担六项功能本体。
4. 待确认：仓库星光框架对「按 RVA 内联 hook libil2cpp 函数」的现成支持程度（是否已有 `hook_rva()` 帮助函数 / 是否走 DOBBY/And64InlineHook）。下一轮查 `mod菜单/` 公共框架（只读）后给 builder 明确接口。

> 方法：Python + capstone 5.0.7 只读 \`libil2cpp.so\`；**RVA→文件偏移不硬编码**，实时解析 ELF64 program header（PT_LOAD 的 p_vaddr/p_offset/p_filesz）换算，例：RVA \`0x1B08748\` → 文件偏移 \`0x1B04748\`（本段 vaddr↔offset 差 \`0x4000\`，且**各段不同**，dump.cs 的 \`Offset\` 列与 RVA 差值不可跨段套用）。
> 工具：\`07_tmp/999秒幸存者/disasm.py\`（\`disasm.py <rva> <n>\`）/ \`fnfind.py <rva> <n> <regex>\`（只打印命中指令，控输出）。
> 符号索引：\`06_dumped/999秒幸存者/symbols.txt\`（79,703 行，\`类<TAB>方法<TAB>RVA\`），后续检索**只 rg 这个文件**。

### 6.1 关键函数逐个验证

#### (a) \`player.behurt\` RVA 0x1B08748 —— ❌ 不是扣血点（推翻第一轮 A1）
\`\`\`
01b0877c  ldr x0,[x20]              ; data 单例
01b08790  ldr x8,[x0,#0xb8]         ; → [x8] 即 data 实例
01b08794  ldr s0,[x8,#0x180]        ; data.playerhurtwhitetime
01b08798  str s0,[x19,#0xcc]        ; player.spritehurttime
01b087a4  ret
\`\`\`
**结论**：整个函数（0x1B08748–0x1B087A4，约 24 条）只把「受击白闪时长」写进 \`player.spritehurttime(+0xCC)\`，**既不写 \`stat.hp\` 也不调 \`basicbase.hurt\`**。它是纯表现层。→ 无敌挂点改为下面 (b)(c)。

#### (b) \`player.hpcheck\` RVA 0x1B06D38 —— ✅ 死亡判定确认
\`\`\`
01b06d74  ldr x8,[x19,#0x130]       ; x8 = player.stat
01b06d7c  ldr d0,[x8,#0x20]         ; d0 = stat.hp (double)
01b06d88  fcmp d0,#0.0
01b06d8c  b.hi #0x1b06f0c           ; hp > 0 → 直接返回（不死亡）
01b06d90  ldrb w8,[x19,#0x154]      ; player.adie
01b06d94  cbnz w8,#0x1b06f0c        ; 已死过 → 返回
01b06da4  bl   #0x194a200           ; ...
\`\`\`
**结论**：\`stat.hp\`=**\`player.stat\` + 0x20（double）**、\`player.stat\`=\`player\`+0x130、\`player.adie\`=+0x154 均实测确认；\`hp<=0 && !adie\` 才走死亡流程。**置信度 ★★★**。

#### (c) \`basicbase.playerhurt\` RVA 0x1A392D4 —— 玩家扣血总入口（置信度 ★★，内部未全展开）
入口 20 条内为 IL2CPP 类初始化样板 + 保存 x19/x21/x22/x23/w20/v8（\`x0=stat\`、\`x2=equipstat\`、\`d0\` 首个 double），\`cbz x21\` 早退。**函数体 > 0x400 字节，本轮窗口未覆盖到 hp 写入指令**。
**取用结论**：作为「玩家受伤」唯一入口候选，hook 入口直接 return 可实现无敌（不依赖内部细节）；但**副作用未验证**（受击表现/无敌帧/吸血/反伤可能一并不触发）。**风险中**。
→ 更稳的组合：\`hpcheck\` 保底 + 每帧把 \`stat.hp\` 回写为 \`stat.maxhp\`（数据型，见 §6.4 建议）。

#### (d) \`player.move\` RVA 0x1B07020 —— ✅ \`stat.sp\` 就是移速
\`\`\`
01b07404  ldr s11,[x8,#0x9c]        ; x8 = [player+0x130] = stat → s11 = stat.sp
\`\`\`
**结论**：\`basicbase.stat.sp\`（\`stat\`+**0x9C**，float）为移动速度系数，在 \`move()\` 内被读取一次参与位移计算。**置信度 ★★★**。
→ 实现：**hook \`player.move\` 入口**，先把 \`stat.sp\` 设为 \`baseSp * k\`（或直接 SafeWrite 该字段），函数体随后读到的即放大后的值；比在 0x1B07404 处内联改指令简单得多。

#### (e) \`data.bullethurt\` RVA 0x1AAC4C4 —— ❌ 不适合做倍率挂点
220 条内 \`bl\` 全部指向 \`0x35f5c6c/0x360219c/0x35ee9a4/0x2380244\`（Unity 引擎侧）与 IL2CPP 样板，**未见 \`enemyhurt\` 类调用**，本体是命中特效/分发。
**结论**：倍率挂点改为 \`basicbase.enemyhurt\`（下条），置信度从 ★★★ 降到 ★。

#### (f) \`basicbase.enemyhurt\` RVA 0x1A3D37C —— ✅ 敌人受伤结算，\`d0\`=伤害值
\`\`\`
01a3d3b0  mov v10.16b, v0.16b        ; 保存 d0 = dem（第二个参数 double）
01a3d3b4  mov x21, x1                ; x1 = stat
01a3d3e0  mov x8, #0x7ff0000000000000 ; +Inf 常量（暴击/上限比较用）
\`\`\`
**结论**：签名 \`enemyhurt(basicbase.stat st, double dem, Transform tf, ...)\` 的首个浮点参数即伤害值，hook 入口改 \`d0\` 即可全乘。**置信度 ★★**（未验证 hp 写入位置）。
→ 兄弟函数 \`enemyhurtnotnac\`(0x1A3D664) 与元素族 \`nmhurt/windhurt/icehurt/electhurt/minehurt/fireehurt/gashurt/soulhurt\`（0x1A3B4DC / 0x1A3BCE4 / 0x1A3C0EC / 0x1A3C4F0 / 0x1A3C77C / 0x1A3CB88 / 0x1A3D04C / 0x1A3B7E4）需一并覆盖，否则只有常规伤害生效。

#### (g) \`admanager.showad\` RVA 0x1ADF4F8 —— ⚠️ **单条 ret 空实现**
\`\`\`
01adf4f8  ret
01adf4fc  mov x1, xzr ; b 0x35fa578 (MonoBehaviour..ctor)   ← 下个函数 .ctor
\`\`\`
**结论**：本版本 \`showad()\` 是空函数，**免广告不能挂在它上面**；真实 SDK 调用在业务函数内部（\`DirichletAdNative adNative(+0x48)\`）。

#### (h) \`admanager.reward\` RVA 0x1ADF120 —— ✅ 唯一发奖分发点（switch on adtype）
\`\`\`
01adf1d0  ldr w8,[x19,#0x50]        ; w8 = admanager.at (adtype)
01adf1d4  cmp w8,#3
01adf1d8  b.hi #0x1adf288           ; at>3 → 跳过

01adf1e8  ldrb w11,[x9,x8]          ; 取表项
01adf1f0  br  x10                   ; → 4 个分支（adtype 0..3）
\`\`\`
**结论**：\`reward()\` 按 \`admanager.at(+0x50)\` 的 4 种取值分派——对应「免广告购买 / 复活 / 经验加成 / 检查」四条业务。它是**发奖的唯一出口**，但**不负责拉起广告**。**置信度 ★★★**。

#### (i) \`admanager.getadcheck\` RVA 0x1ADF094 —— 可用性检查
\`\`\`
01adf0f0  cbz x0,#0x1adf11c
01adf104  bl #0x1acd94c             ; -> func.useeventnotsymbol(...)
01adf108  str wzr,[x19,#0x50]       ; admanager.at = 0
\`\`\`
**结论**：进入即调 \`func.useeventnotsymbol\` 并重置 \`at\`；按钮可用性判定在此。hook 恒返 true 可让「看广告」按钮常亮（**不产生收益**，仅解灰）。

#### (j) \`desachieve.couponunlockachieve\` RVA 0x1B21304 —— ✅ 券的唯一扣减点
\`\`\`
01b2134c  ldr x8,[x0,#0xb8]         ; data 单例
01b21350  ldr x8,[x8,#0x4f0]        ; data.sd  →  data.Savedata 实例（字段名 sd，偏移 0x4F0 已核对）
01b21360  ldr w10,[x8,#0xbc]        ; w10 = sd.unlockcoupon（余额）
01b21364  ldr w9,[x9,#0x54]         ; w9  = achievement.needcoupon（单价）
01b21368  cmp w10,w9
01b2136c  b.lt #0x1b213d0           ; 余额不足 → 跳走（失败分支）

### 6.2 皮肤/解锁真相（第 2 项）

| 结构 | 字段/方法 | 偏移/RVA | 语义（实测） |
|---|---|---|---|
| \`database.onelock\` | \`acname\` / \`count\` / \`haveac()\` | 0x10 / 0x18 / **0x1ABBE1C** | 单条解锁条件：成就名 + 需要计数 |
| \`database.lockmodel\` | \`lv\` / \`demo\` / \`steam\` / \`aclocks\` / \`getallhave()\` | 0x10 / 0x14 / 0x15 / 0x18 / **0x1AB2C08** | 皮肤/人物的锁定模型：条件列表 + 「是否全部达成」 |
| \`database.Achievement\` | \`have\` / \`skinid\` / \`needcoupon\` / \`count\` | **0x3C** / 0x50 / 0x54 / **0x58** | 成就（=解锁条目）：是否已达成、对应皮肤 id、券价、进度 |
| \`database.savedata\` | \`name\` / \`count\` / \`point\` | 0x10 / 0x18 / 0x1C | 存档进度条目（成就/图鉴/人物进度都落这里） |

\`haveac()\` 实测逻辑（**这是「皮肤是否解锁」的判定源**）：
\`\`\`
data.findachievement(acname, null)  → 空 ⇒ return true          ← 找不到条目视为已解锁
否则： if (onelock.count <= 0) return (A.have != 0);
       else                    return (A.count >= onelock.count);
\`\`\`
**挂点结论（置信度 ★★★）**：hook **\`database.onelock.haveac()\` → 返回 1**，即所有基于 lockmodel 的解锁条件全部视为达成（皮肤、人物、图鉴、成就解锁一并生效）。**副作用风险**：成就弹窗/红点/商店「已拥有」状态可能集中出现，且**已付费内容也被判定为已拥有**（本地判定，不影响服务器）。

**更保守的第二选择**：hook \`database.lockmodel.getallhave()\` 返回 1（只影响「所有条件是否满足」的调用点，覆盖面小于 haveac）。
**纯数据替代**：每帧把目标 \`Achievement.have(0x3C)=1\` 且 \`count(0x58)\` 写大 —— 需遍历 database 的 achievement 表，成本高于 hook。

### 6.3 无限解锁券（第 3 项）——「改余额」vs「改 needcoupon」

| 方案 | 做法 | 结论 |
|---|---|---|
| A 改余额 | SafeWrite \`sd+0xBC = 9999\`，Tick 维持 | ❌ 不稳：\`Savedata.savedata()\`(0x1AB113C)/\`loaddata()\`(0x1AB19A0) 会落盘/回读，重启后可能回滚或被校验；且 UI 显示与实际一致性依赖刷新时机 |
| B 改 needcoupon=0 | 每帧遍历把 \`Achievement.needcoupon(0x54)=0\` | ⚠️ 有效但不彻底：\`haveac()\` 的放行不看 needcoupon，只看 \`have\`/\`count\`（见 6.2）；needcoupon=0 只让「消耗=0」，仍需走解锁流程 |
| **C hook 消费函数（推荐）** | hook \`desachieve.couponunlockachieve\`：调 orig 之后把 \`sd.sd->unlockcoupon\` 写回调用前的值 | ✅ **净扣减为 0**，UI/存档/服务端表现全部一致，不依赖余额被读取的时机。置信度 ★★★ |
| D 直接 patch 0x1B213A4 | 把 \`str w9,[x8,#0xbc]\` 改成 \`nop\` | ✅ 同样有效，但属「字节 patch 改函数体」，框架 §铁律默认禁用（E15–E18），不作首选 |

### 6.4 免广告（第 4 项）——三函数调用关系与「一钩全覆」

链路（实测 + 推断）：
\`\`\`
UI 点击 → admanager.getadfreebuy/getadrevive/getadexpmul   ← 业务入口（各自设置 at=adtype）
        → 内部调 DirichletAdNative.adNative(+0x48) 拉起 SDK   ← 广告本体（在业务函数内部，showad 是空壳）
        → SDK 回调 → admanager.reward()                        ← 按 at 分派 4 条发奖分支
\`\`\`
- **只 hook \`reward\` 无法免广告**（它只在看完后触发）。
- **没有单一函数能一次覆盖三业务**（\`showad\` 为空实现，业务函数各自拉起 SDK）。
- **可下手的组合（置信度 ★★）**：hook 三个业务入口 \`getadfreebuy(0x1ADEEAC)\` / \`getadrevive(0x1ADEF58)\` / \`getadexpmul(0x1ADEFE8)\`：
  入口处先按业务语义设好 \`at(+0x50)\` 与 \`nowp/nows(+0x38/+0x40)\`，**直接调 \`reward\`(orig)** 后 return，跳过 orig 业务体（即不拉起 SDK）。
  风险：三个业务函数体内对 \`nowp/nows\` 的赋值细节未展开，若 UI 侧回调依赖业务函数的收尾逻辑，可能出现「奖励到账但界面未刷新」。
- **保底增强**：同时 hook \`getadcheck(0x1ADF094)\` 返回 true + \`canad(+0x28)=1\`，避免按钮变灰导致流程卡住。

### 6.5 框架接口（第 5 项，只读调研）

- **已有脚手架**：\`mod菜单/starry-mod-menu/app/src/main/jni/Games/Mxcz999Mod.h/.cpp\`（527 行，v3.1 模板，**功能全是 TODO 示例，未填实现**）+ \`Android_mxcz999.mk\`。builder 直接填 \`kSlots\` 即可，无需新建四件套。
- **挂点机制**：\`HookSlot{tag, rva, expectInsn, ns, cls, method, argc, hookFn, origPtr}\` + \`HookSlotInstall()\`：**RVA 优先（校验序言第一条指令）→ 失败自动按名查找**；幂等（防同址双钩 SIGSEGV）。
- **实现分层（框架铁律）**：数据型（HP 回写 / 属性 / 资源）→ 偏移 + \`SafeWrite\` + Tick 轮询；行为型（改判定/伤害）→ Dobby hook；字节 patch 默认禁用。
- **Il2Cpp API**：\`Il2Cpp::GetApi()\` 提供 \`il2cpp_class_from_name\`/\`il2cpp_field_get_offset\`/\`il2cpp_field_set_value\` 等（\`Unity/Il2CppApi.h\`），并有「按名查找降级」路径应对 dynsym 被摘。

builder 可直接复用的挂点表（示例，RVA 已实测）：

## 6.8 免广告落地风险（反汇编实测，第四轮）

三个业务函数实测结构（均以 b 尾调用结束，不是 bl）：

| 函数 | RVA | at 写入 | 其他关键写入 | 尾部 |
|---|---|---|---|---|
| admanager.getadfreebuy(perchaseui0 p) | 0x1ADEEAC | mov w8,#1 → **at=1** | str x20,[x19,#0x38]! → **nowp(+0x38)=p** | b 0x1ADED34（LoadRewardAd） |
| admanager.getadexpmul(settlepanel s) | 0x1ADEFE8 | mov w8,#2 → **at=2** | bl 0x194a038（nows 侧辅助） | b 0x1ADED34 |
| admanager.getadrevive() | 0x1ADEF58 | mov w8,#3 → **at=3** | — | b 0x1ADED34 |

逐条回答：

1. **at 的立即数**：freebuy=**1**、expmul=**2**、revive=**3**（与 §6.1(h) 的「at 0..3 四分支」对齐；at=0 是 getadcheck 的复位值）。
2. **是否在拉起 SDK 之前设置 at**：**是**。三者顺序统一为「bl func.useeventnotsymbol → 写 nowp/nows → str at → b LoadRewardAd」，进入广告前上下文已就位。
3. **拉起 SDK 的调用在哪**：**不在这三个函数内**。三者把控制权尾交给 **admanager.LoadRewardAd RVA 0x1ADED34**；SDK 面集中在那里（ldr x20,[x19,#0x48]=adNative，随后 bl 0x1B39804 / 0x1B3980C / 0x1B398A4 / 0x1B398C0 / 0x1B398F8 / 0x1B39888 / 0x1B39964 / 0x1B3A070 / 0x1B3ACB8，均为 Dirichlet 广告类）。
4. **UI 是否依赖返回值**：**不依赖**。三者签名皆 void、末尾为尾跳 b（无 bl 收尾）、序言无 mov w0；因此**入口直接 return 不会破坏调用方逻辑，但也不会发奖**（奖励由 reward() 产生）。

**结论（结构 ★★★ / 运行时 ★★）**
- **最优单点 = hook admanager.LoadRewardAd（RVA 0x1ADED34）**：不调 orig，改用同一 this 调 **admanager.reward（RVA 0x1ADF120）**。此时 at/nowp/nows 已由业务函数写好，reward 的 switch 会落到对应发奖分支 → **一处覆盖免广告购买 + 复活 + 经验加成**。
- 次选（更保守）= 分别 hook 三个业务入口，入口处设好 at 后直接调 reward() 再 return。
- **残余风险**：reward 各分支内部是否还校验 canad/次数/nowp 非空未展开；revive 分支不写 nowp，若其分支体访问 nowp 可能空指针。建议首测只开「免广告购买」，确认后再开另外两项。
- **不建议**只 hook getadcheck：它只解灰按钮，点了仍会走 SDK。
