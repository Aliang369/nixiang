### A.4 结论：点「额外领取」到底执行什么 [实测 + 推断]

```
用户点「额外领取」
  → checkpanel.checkadbutton (0x1B3453C)          [实测：尾跳]
  → admanager.getadcheck     (0x1ADF094)          [实测：尾跳，入口把 at 置 0]
  → admanager.LoadRewardAd   (0x1ADED34)          [实测：0x1ADF118 无条件 b，唯一例外见下]
  → Dirichlet ShowRewardVideoLoadAndShowInternal (0x1B3B604) → LoadRewardVideoAd (0x1B3A320)
  → SDK 回调 → MyRewardVideoAutoAdListener.OnRewardVerify (0x1ADF588) → admanager.reward (0x1ADF120)
```

`getadcheck` 尾部**无条件**尾跳 LoadRewardAd（0x1ADF10C–0x1ADF118：`mov x0,x19; ldp…; b 0x1ADED34`），**唯一不跳的情形**是 0x1ADF0F0 `cbz x0,#0x1ADF11C`（`data.d` 为空 → 抛异常）。

**⇒ 用户实测「getadcheck 被调用但 LoadRewardAd 没被调用」只有一个解释：我们的 hook 命中了 getadcheck 却没有调用 orig**（hook 直接 return / 直接返回 true），于是尾跳链被切断。这不是游戏的问题，是我们 hook 的写法问题。**[推断，置信度 ★★★：因为该函数体内除 cbz 外没有任何 return 分支]**

### A.5 两种可行改法

| 方案 | 做法 | 结果 | 置信度 |
|---|---|---|---|
| A-a 真·免广告 | hook `checkpanel.checkadbutton`(0x1B3453C)：不调 orig，改为**按「额外领取」语义直接发奖**（调 `admanager.reward` 并预设 `at` 为签到分支值）。 | 不弹广告、直接到账；但需知道 at 值（见下） | ★★ |

## B. 无限解锁券

### B.1 data 的静态字段清单 —— 单例字段名是 d，不是 i [实测]

dump.cs:358360

    public static data d; // 0x0

⇒ **`GetDataSingleton` 用 `class_get_field("i")` 必然失败**——字段名是 **`d`**（类型 `data`）。这是数据型方案此前无效的直接原因。[置信度 ★★★]

### B.2 「读 data 单例」的真实取法（3 处一致，[实测]）

| 函数 | 指令 | 说明 |
|---|---|---|
| desachieve.couponunlockachieve | 0x1B21310 `adrp x20,#0x3a64000; ldr x20,[x20,#0xed0]` → 0x1B21338 `ldr x0,[x20]` → 0x1B2134C `ldr x8,[x0,#0xb8]` → 0x1B21350 `ldr x8,[x8,#0x4f0]` | 链：**P=\*[0x3A64ED0] → data=\*[P+0xB8] → sd=\*[data+0x4F0]** |
| checkpanel.checkbutton | 0x1B34228 `ldr x0,[x20]` → 0x1B3422C `ldr x8,[x0,#0xb8]` → 0x1B34230 `ldr x8,[x8,#0x4f0]` | 同上 |
| unlockcoupondisplay.Start | 0x1A4112C / 0x1A41148 `ldr x0,[x0,#0xed0]`（同一 GOT 槽） | 同上，取 0x3A64ED0 |

**注意**：三条链都**用静态 GOT 槽**（0x3A64ED0），**不经过 MonoBehaviour self**。所以「从 checkpanel 实例 + 某偏移拿 data」不成立；任何 MonoBehaviour 都走同一个静态槽。

**确定取法（二选一）**：

```c
// ① IL2CPP API（推荐，版本无关）
Il2CppClass* c = il2cpp_class_from_name(img, "", "data");
FieldInfo*  f = il2cpp_class_get_field_from_name(c, "d");   // 不是 "i"
void* dataInst = nullptr; il2cpp_field_static_get_value(f, &dataInst);
FieldInfo* fsd = il2cpp_class_get_field_from_name(c, "sd");
void* sd = *(void**)((char*)dataInst + il2cpp_field_get_offset(fsd));   // = dataInst+0x4F0
int  coupon = *(int*)((char*)sd + 0xBC);

// ② 纯偏移（不用 API，实测链）
void*  P        = *(void**)(libBase + 0x3A64ED0);
void*  dataInst = *(void**)((char*)P + 0xB8);
void*  sd       = *(void**)((char*)dataInst + 0x4F0);
int*   coupon   =  (int*)((char*)sd + 0xBC);   // *coupon = 9999
```

### B.3 sd + 0xBC 是 int 余额，且无第二余额字段 [实测/推断]
- `data.Savedata.unlockcoupon` 声明为 `int`，偏移 **0xBC**（dump.cs 字段表 + 5 处指令级读写一致）。
- `checkpanel.d1coupon…d7coupon`（0xD0…0xE8）是**每档额度**（加券时 `add w9,w10,w9` 的 w10），**不是余额**；只读它们不会花券。
- 弹窗显示类 `unlockcoupondisplay/unlockcouponsettle` **只读** 0xBC。
- 结论：全库唯一余额字段 = `sd+0xBC`。[置信度 ★★★]

### B.4 「用券解锁」真实路径与 couponunlockachieve 的存疑
- 全库 b/bl 扫描：**没有任何指令**指向 `couponunlockachieve`(0x1B21304)——连尾跳都没有。
- 但「静态 0 引用」≠ 死代码：UnityEvent 由场景数据按**方法名字符串**绑定，代码里不会有引用。是否真被绑定，需解包 scene 才能定（**未确认**，缺 UnityPy）。
- **崩溃地址存疑**：该函数 prologue 的首个解引用是 `ldr x0,[x20]`（若 x20 空则 fault 0x0），第二个是 `ldr w8,[x0,#0xE0]`（fault 0xE0），**第三个才是 `[x0,#0xB8]`**。所以「fault addr 0xB8 且 self=空」**不能**直接归因于本函数被以 null self 调用——它根本不使用 self（x0 入口即被 static 覆盖）。⇒ **崩点很可能在别处**（例如 `desachieve.Update` / `checkpanel.Update` 里 `ldr x8,[x0,#0xb8]` 而静态槽为空），需要 **pc + maps** 才能定位。[置信度：本判断 ★★]
- 真实写余额的指令**只有两处**：`desachieve.couponunlockachieve` @0x1B213A4（扣减）与 `checkpanel.checkbutton` @0x1B34244 等 7 处（增加）。若用户点解锁时余额确实减少，那执行的就是 couponunlockachieve。

### B.5 数据型方案可行性与「为什么之前失败」
**可行**。Tick 里直接写 `sd+0xBC = 9999` 即可；之前失败的原因已定位：**字段名找错（"i" → 实际 "d"）**，导致 `il2cpp_field_static_get_value` 返回 null/抛错，取到空 data，再取 sd 自然失败。
补充风险：`Savedata.loaddata`(0x1AB19A0) 会在读档时覆盖 → Tick 每帧重写即可盖过（Tick 频率 >> 读档频率）。**建议 100ms 一次**。
