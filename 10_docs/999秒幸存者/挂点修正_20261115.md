### 1.4 结论：为什么 LoadRewardAd 的 hook 没触发
**静态上它确实在链上**（4 个入口全部尾跳到它），因此「hook 没触发」只有两种解释：
1. **点击的不是这四个按钮**（例如点的是商店/主界面另一处广告位，onClick 绑的是别的脚本）；
2. **链在更早处断了**：getadfreebuy 在写 nowp/at 之前有 cbz x0,#0x1adef54（data.i 为空即抛）与 bl func.useeventnotsymbol，若当前环境（未登录/未配置广告位/离线）提前返回，就永远到不了 LoadRewardAd。
两者都需真机 logcat 才能定，标**待验证**。

### 1.5 推荐 hook 点（按稳健度排序）

| 优先 | 挂点 | RVA | 说明 |
|---|---|---|---|
| **A（首选）** | checkpanel.checkadbutton / perchaseui0.getfreebuyad / settlepanel.adexpmul / uicontrol0.getrevivead | 0x1B3453C / 0x1A66E2C / 0x1A6FD8C / 0x1A793C8 | 这四个是 UnityEvent 直接被点中的入口，只要用户点到就必然执行；入口处直接发奖最不易漏 |
| B | 四个 admanager 业务入口 | 0x1ADEEAC / 0x1ADEFE8 / 0x1ADEF58 / 0x1ADF094 | 与 A 等价、层次更低；若 A 的实例参数不好处理则选 B |
| C（保底） | admanager.reward | 0x1ADF120 | **只解决「不发奖」，不解决「不看广告」**；单独用无效（实测已证） |
| ❌ 不可用 | admanager.LoadRewardAd | 0x1ADED34 | 实测未触发，且它只「请求广告」不产生奖励 |

**落地建议**：hook A 组四个 UI 入口并在入口 return（不调 orig），再按业务直接调发奖函数：
- 免广告购买 → perchaseui0.freeperchase(0x1A66CF0)
- 双倍经验 → settlepanel.addexpmul(0x1A6FDE8)
- 复活 → 待定（reward at=3 分支目标）
- 广告检查（checkadbutton）→ 把 canad(+0x28) 置 1 或直接 return，让 UI 认为可用

## 2. 券：真实路径是 checkpanel.checkbutton，不是 couponunlockachieve

### 2.1 指令级证据（[reg,#0xBC] 读写点共 98 处，筛出券相关）

| 函数 | RVA | 动作 |
|---|---|---|
| **checkpanel.checkbutton** | **0x1B3419C** | **14 条 ldr w9,[x8,#0xbc] / str w9,[x8,#0xbc] 成对出现（7 个券槽位各读改写一次）** |
| desachieve.couponunlockachieve | 0x1B21304 | 2 读 + 1 写（扣券），但**静态 0 调用者** |
| admanager.reward | 0x1ADF120 | 2 组读写（广告奖励发券） |
| unlockcoupondisplay/settle（Start/Update） | 0x1A410E0 / 0x1A4128C / 0x1A41440 / 0x1A41A18 | 只读（显示） |

证据片段：

    checkpanel.checkbutton  ldr w9, [x8, #0xbc]   @0x1b34238
    checkpanel.checkbutton  str w9, [x8, #0xbc]   @0x1b34244
    ... 同型共 7 组，@0x1b34238 ~ 0x1b34340
    desachieve.couponunlockachieve  str w9, [x8, #0xbc]  @0x1b213a4

### 2.2 为什么 hook couponunlockachieve 从未触发
callers.json 显示它 **bl 调用者=0**；UI 区段尾调用扫描（0x1A60000–0x1B40000）也**没有** b 0x1B21304。⇒ 该函数在本版本**没有静态调用点**，只可能被 UnityEvent 间接调用或已是废弃路径。

### 2.3 结论与推荐
- **推荐 hook：checkpanel.checkbutton（0x1B3419C）** —— 「用券解锁」按钮的真实处理体，7 个槽位各自「读余额 → 判断 → 扣减 → 写回」。
  - 直接入口 return 会「不扣券也不解锁」，不合适；
  - **稳的做法**：hook 后在函数返回前把 sd.unlockcoupon(+0xBC) 写回调用前的值（与原 couponunlockachieve 方案同构，只是换到真实路径）。
- 次选：Tick 写 sd.unlockcoupon 为大值（data.i 静态 0x3A64ED0 +0xB8 → data.sd +0x4F0 → +0xBC），缺点仍会被 Savedata.loaddata 回滚。
- **couponunlockachieve 建议从挂点表移除**（死钩，白占槽位）。

## 3. 伤害语义修正（用户实测已证实）

### 3.1 结论表

| basicbase.enemyhurt | 0x1A3D37C | enemy.collideract(0x1AF55BC) / enemybullet.accalculate(0x1B00920) | **敌人施加伤害（打玩家）** | ★★★（与实测一致） |

| basicbase.hurt / ehurt | 0x19E98F4 / 0x19E96A4 | 元素族 / nmhurte / ehurte / turretbullet / mineeleac | **中立扣血**：写入「传入的第一个 stat 参数」，方向由调用者决定 | ★★★ |

### 3.2 关键证据：hurt 写的是「传入的 stat」

    019e9a60  ldr d0, [x19, #0x20]     ; x19 = 第 1 个参数 st（受害者）
    019e9a68  str d0, [x19, #0x20]     ; 写回 st.hp —— 受害者身份由调用者传入

player.behurt 的调用者只有两个：enemyhurt(0x1A3D54C) 与 enemyhurtnotnac(0x1A3D78C) ⇒ **只有这两个函数代表「玩家被打」**。

### 3.3 伤害倍率的正确挂点
- playerhurt 的第 8 个参数是 **float dimmul**（进 s0/v0，入口 mov v8.16b,v0.16b 保存），并被**原样转发**给 basicbase.nmhurte(0x1A3983C) 的 v3（4 处调用点：0x1A395A4 / 0x1A395FC / 0x1A39660 / 0x1A396C4）。
- **首选**：hook basicbase.nmhurte(0x1A3983C) —— 其**唯一调用者就是 playerhurt**，是纯玩家侧的敌人伤害结算；伤害值在 v0(d0)。
- **次选**：hook basicbase.playerhurt 入口，把 s0(dimmul) 乘 k。
- **不覆盖**：turretbullet.OnTriggerEnter、mineeleac.nmstart、oneframeac.nmstart 直接调 hurt/ehurt（炮台/地雷/持续伤害），绕过 playerhurt ⇒ 这些路径不受倍率影响。

### 3.4 修正后的无敌挂点
1. **basicbase.enemyhurt(0x1A3D37C) 入口 return** —— 怪打人主路径；
2. **basicbase.enemyhurtnotnac(0x1A3D664) 入口 return** —— 第二个会调 player.behurt 的路径；
3. **保留 player.hpcheck(0x1B06D38) 兜底** —— 若元素 DoT 绕过上面两条直写 player.stat.hp，还能不死。
4. **自洽性确认**：player.hpcheck 的**唯一调用者是 player.Update(0x1B0694C)**，player.die 的唯一调用者是 player.hpcheck(0x1B06F08) ⇒ 删掉 playerhurt hook 后「怪物不会变无敌」成立（playerhurt 属玩家打怪路径，与玩家死亡无关）。

### 6.3 重要更正（券）

checkpanel.checkbutton(0x1B3419C) 的 7 组 [x8,#0xBC] 是 **sd.unlockcoupon += dNcoupon（领取）**，不是扣减：

    01b34238  ldr w9, [x8, #0xbc]     ; w9 = sd.unlockcoupon

    01b34240  add w9, w10, w9         ; 相加

⇒ 它是「领取券」按钮。**真实扣券点仍只有 desachieve.couponunlockachieve(0x1B21304)**；它「静态 0 调用者」在 UnityEvent 绑定场景属**正常现象**（onClick 走委托间接调用，静态扫描看不到）。用户 hook 从未触发的最可能原因是**没点到成就面板的「用券解锁」按钮**，而非函数是死的。置信度 ★★（待实测）。
