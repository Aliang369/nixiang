# ACE 过检复盘与通用 SOP（终末地实战复盘，2026-09-03）

> 来源：终末地（com.hypergryph.endfield 1.4.3，腾讯 ACE/TSS：libtersafe2 + libtprt）星空包过检全过程。
> 用途：AI 接手任何 ACE 保护游戏改包"进不去/被杀/卡 Splash"时的完整决策参考。
> 配套：`skill/re-analyze/protection/ace-tss.md`（基础识别与旧案例）、`10_docs/终末地/ACE云端杀_诊断_20260902.md`（原始诊断记录）。

---

## TL;DR

终末地星空包"进不去"的真正根因**不是**签名校验、不是 so 扫描、不是云端 verdict，
而是 **ACE 壳（AceApplication.initialize）校验 AndroidManifest 的 Application 类名——
非预期值即毒丸挂起（libtprt.so 内 `sem_timedwait` 永不返回）或延迟击杀**。

解法：**不替换 Application，改用 ContentProvider（StarryInitProvider）注入初始化**，
manifest 只加 provider/权限条目（已证明不触发）。修复后联网存活 48min+，PROVEN。

排查耗时长的主因是三层误判（残留 → 云端杀 → 数据目录扫描），每层都有"看似自洽"的证据链。
本文档重点记录误判的纠正信号，避免重蹈。

---

## 一、现象与两种死法（先分类，再动手）

| 死法 | 特征 | 指向 |
|------|------|------|
| **卡住**（进程活） | 黑屏+icon Splash 永不前进，进程不退出 | 本地初始化死锁/毒丸挂起 |
| **被杀**（进程死） | ~22s 循环死亡，SIGBUS(7)/SIGSEGV(11)/SIGKILL(9) 混合，无 crash_dump、无 dropbox | ACE 主动击杀（本地校验或外部 kill） |

两者可同时存在（挂起后超时被杀）。**必须先分清当前主现象**，本次排查前半段一直当成"纯被杀"追，绕了远路。

## 二、走错的三层弯路（及纠正信号）⚠️ AI 重点看这里

### 弯路 1：残留引雷（半对，但非死因）
- 现象：`/data/local/tmp/` 堆着 fs-arm64（Frida server）、memdump 产物、APK 本体；清理后进程短暂突破 22s 窗口。
- 纠正信号：**清干净后死亡循环依旧**；且原版联网带着同样的残留也活 → 残留会加重风控但不是根因。
- 结论：残留必须清（规范要求），但别指望清残留解决过检。

### 弯路 2："ACE 云端 verdict 杀"（错误结论，曾写入诊断文档）
- 支持证据：断网 T7 稳定 300s+，联网几分钟内必进循环；原版联网正常。
- 推翻信号：**用户现场观察**——"核心现象是卡 Splash 不是被杀" + "T1~T4 之前都能正常进游戏"。
  重新逐层排查后，provider 版星空包**联网**也稳定 → 云端杀假设不成立。
- 教训：断网存活 ≠ 云端杀实锤。断网可能只是让进程停在触发路径之前（没联网 → 没走到校验/没拉起后续初始化）。**假设必须能同时解释所有现象**，"卡 Splash"和"云端杀"就是矛盾点。

### 弯路 3："ACE 扫 data 目录杀陌生 so 文件"（误判）
- 现象：OTA 目录放 trace so 即死、移走即稳（120s+）。
- 推翻信号：后续发现空壳 so 包（T7）同样进循环且 so 从未加载成功——真正的共同因子是 **Application 替换**，与 so 文件在场与否无关；"移走即稳"是抓错时机（进程恰好刚重启）。
- 教训：单次"在场即死/移走即稳"必须重复验证 ≥2 轮，且配合画面证据。

## 三、真正根因的实锤路径（可复制的方法）

1. **kill -3 抓 ART 全线程堆栈**（`adb shell kill -3 <pid>`，读 `/data/anr/trace_0x`）：
   主线程卡在 `AceApplication.initialize` → libtprt.so `sem_timedwait` → **native 毒丸挂起实锤**。
2. **逐变量排除**（每次只动一个，见下方阶梯）：
   - T8 跳过 SignSpoof → 仍卡同处 → SignSpoof 排除（hidden API 失败非根因；fakes 表本无 endfield，SignSpoof 纯引雷，ACE 游戏默认关闭）
   - T5 = 原包+certs（**保留原 Application**）→ 正常进标题画面 ✅
   - T9a = 原包 + MenuService + 权限 + 惰性 classes7 + certs（**仍保留原 Application**）→ 正常进协议页 ✅
   - 完整星空包（Application→StarryApp）必卡/必死，与 so 是否加载无关
3. **交叉锁定**：唯一区分"活/死"的变量 = Manifest 的 `android:name` 是否被替换 → 根因坐实。

## 四、解法：ContentProvider 注入（ACE 游戏标准姿势）

- 保留原版 Application（终末地为 `com.u8.sdk.U8Application`，壳链 AceApplication）。
- 新增 `StarryInitProvider`，manifest 只加 `<provider>` 条目 + 必要权限 → `onCreate` 里完成 so 加载/菜单启动。
- 外科组装不变项照旧：禁 apktool b、受保护 dex/arsc 字节不动、classes7 新增、zip 对齐重签。
- 效果：provider 版 23:17 安装 → 联网存活 48min+、crash 缓冲 0、starry/ACE so maps 共存、标题画面+星光悬浮窗正常。**PROVEN**。

## 五、ACE 过检通用 SOP（决策树）

```
ACE 游戏改包进不去
├─ 0. 清残留（cleanup_device_re_residue.sh）——排除环境变量
├─ 1. 分类死法
│    ├─ 卡 Splash（进程活）→ kill -3 抓主线程堆栈
│    │    └─ 卡 AceApplication.initialize / sem_timedwait → Application 类名校验毒丸 → 走 Provider 注入方案
│    └─ 被杀（22s 循环）→ 先看有无 tombstone/crash_dump
│         ├─ 无 + 信号随机 + 无 dropbox → ACE 外部杀 → 差分阶梯定位触发变量
│         └─ 有 → 按 backtrace 定位本地校验点
├─ 2. 基线三查：原版联网是否存活（设备无罪）？断网变体？残留清干净没？
├─ 3. 差分阶梯（每步一个变量，从最不可能触发到最可能）：
│      T1 仅重签 → T3 +惰性dex → T4 +so不加载 → T5 +certs/assets
│      → T9a +权限/组件条目（保留原Application）→ 完整包（替换Application）
│      ※ 注意：替换 Application 放最后测，它大概率就是雷
├─ 4. 每步判定 = 截图看画面（过没过 Splash/进没进游戏）> 进程存活
└─ 5. PROVEN 前：联网 ≥30min 连续监测 + crash/events 缓冲零击杀 + 画面证据
```

## 六、硬教训清单（每条都是本次真实踩坑）

1. **"存活"必须核对画面截图**：T1~T7 多次"存活"只是进程没死，画面从未过 Splash。单点 logcat 判断不可靠。
2. **logcat 主缓冲 ~60s 轮转**：事后 grep 全空；要后台常驻抓 `-b main -b system -b crash -b events`。
3. **存活判断要连续监测**：22s 死亡循环里单点检查极易抓到刚重启的进程（本次两次误判存活）。
4. **用户现场观察 > 机器日志**：用户一句"卡的是黑屏画面"和"T1~T4 之前能进"直接推翻了自洽的云端杀证据链。尽早问用户"你看到的画面是什么"。
5. **断网实验结论要克制**：断网存活只能说明"联网路径上有东西"，不能直接定罪云端。
6. **ACE 游戏默认关 SignSpoof**：fakes 表没有该游戏时纯属引雷（替换 PackageInfo.CREATOR 会与 ACE initialize 反制冲突）。
7. **hidden_api_policy**：Android 16 上 SignSpoof 需要 `settings put global hidden_api_policy 1` 才能装上，但装上≠有用。
8. **服务器"版本已更新"弹窗是版本 gate，不是检测**——别混进过检问题。
