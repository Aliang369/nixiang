> 设备：小米 `96f0d883`（M2102K1AC / mars，Android 14，**无 root**）。
> 包：本仓 1.6.4 修戳版，md5 `93ce6635e0ca0539e3b97cf3d0dbc2b9`；包内 so md5 `b1c08263a9eba6e8ab33e3156c896320`、build-id `96ce01c9e61737e8341697727d36a1c738e62bc3`。

## 2. 偏移 → 代码（本地反汇编同一 build-id 的 so，实测）

| 帧 | 偏移 | 本地反汇编结论 |
|---|---|---|
| #07 | `0x12010` | 线程入口；该区段含 `usleep` + `b` 自循环 + `__android_log_print` ⇒ **框架 MOD 线程的 300ms 轮询循环**（`tickIntervalMs=300`） |
| #06/#05 | `0x124f8` / `0x126dc` | `0x12674: bl mutex::lock`、`0x126dc: bl 0x13c00` ⇒ **互斥锁保护的 tick 调用体** |
| #04 | `0x13c38` | 位于 `0x13c00` 起的函数内；该函数随后还调 `0x18a00/0x19ac4/0x19340` ⇒ 多子调用派发 |
| #03 | `0x1829c` | 崩溃指令序列：`18280: ldr x8,[x22,#0x28]` → `1828c: ldr x8,[x0,#0x20]` → **`1829c: blr x8`** ⇒ **两级间接调用进 il2cpp**，随后 il2cpp 内部空指针 |

结合源码（`Games/EndfieldMod.cpp`）：`Endfield_Tick`（:938）**只做**「存 4 个原子开关 + `SyncHooks()`」⇒ **崩溃链就是 `SyncHooks()` 这条路径**。

## 3. 代码定位：`SyncHooks()` 的停止条件有洞（**实测事实 + 代码直读**）

```cpp
static void SyncHooks() {                       // :890
    static std::atomic<bool> done{false};
    if (done.load()) return;                    // :896  稳态早退
    if (!g_libReady.load()) return;
    std::lock_guard<std::mutex> lk(g_hookMtx);
    if (!EnsureApi()) return;
    InstallDmgHooks(); InstallInvHooks(); InstallJumpHooks(); InstallSkillHooks();
    LOGI(... " hooks sync calc=%d apply=%d jump=%d skillCd=%d" ...);
    if ((g_origApplyMod && g_origJump) || g_failApply >= 3)   // :908  ← 落定条件
        done.store(true);
}
```

- **`done` 只在 `apply && jump 都装上` 或 `g_failApply >= 3` 时落定**；`skillCd` 不在条件里（其 miss 属预期）✅。
- 但 `InstallApplyModifier()`（:792）的熔断**只覆盖 `DobbyHook` 失败**：`g_failApply` 仅在 :816 自增；而 **:797「AbilitySystem miss」与 :803「ApplyModifier miss」直接 `return false`，不计数** ⇒
  **若 `Beyond.Gameplay.Core.AbilitySystem.ApplyModifier` 在本机解析不到，`done` 永不落定** ⇒ `SyncHooks()` **每 300ms 重跑一次**（`ResolveClass` → `FindClassNs` → 遍历**全部程序集**调 `api.Assemblies/ImageOf/ClassFromName`）⇒ 高频 il2cpp API 调用**贯穿整个进程生命周期**。
- `HookBool0("jump"/"skillCd", …)` 同理需确认是否也缺熔断（未逐行核完）。

**为什么表现为「第二次打开」**：崩溃那次进程已存活 **7.5 小时**（`Process uptime: 27175s`）⇒ 20:23 是**从后台恢复**时崩的。长时间/恢复/热更阶段都会让 il2cpp 侧状态变化（域重载、程序集重载、更新后重启运行时），此时若 tick 仍在**反复解析**，就会命中失效/空的对象 → **null+0x138 崩在 il2cpp 内**。

## 4. 与「热更」的关系（**推断，未坐实**）

该机外置目录实测：`files/HGGameUpdate` = **2665 MB**、`VFS` = 260 MB（总计 3191 MB；对照 OnePlus 上全量是 29,990 MB）⇒ **资源只下了一部分，崩溃时游戏处在热更更新流程中**。结合 §3，**推断**：更新流程会改变/重载运行时状态，而 tick 的无界重解析正好在那之后继续跑 ⇒ 崩。**待验证**：需要现场 logcat 看崩溃前是否持续出现 `hooks sync … apply=0/jump=0`。

## 5. 修法提案（按优先级，均带落点）

### P0-1 `SyncHooks` 的 `done` 必须有界落定（**根治本崩溃**）
- 问题：解析失败路径无计数 ⇒ 可能无限重试 ⇒ 稳态仍有 il2cpp 调用。
- 方案：加**尝试计数**，N 次（建议 6–10）后无条件 `done.store(true)` 并打一条 `WARN give up`；`InstallApplyModifier` 的 :797/:803 两处 `return false` 也计入失败（或直接依赖外层计数）。
- [落点] `mod菜单/starry-mod-menu/app/src/main/jni/Games/EndfieldMod.cpp:890-910`（`SyncHooks`）+ `:797`/`:803`（解析失败计数）。
- 收益：**稳态 tick 零 il2cpp 调用** ⇒ 从根上消除「长时间/恢复后崩在 il2cpp」这条路。
- 验收：冷启后 `logcat | grep "hooks sync"` **只应出现 1–2 行**；若本机确实解析不到 apply，则出现 6–10 行后停（含 give up 警告），之后不再刷。

### P0-2 给 `HookBool0` 补同样熔断
- [落点] `Games/EndfieldMod.cpp:844-888`（`InstallJumpHooks`/`InstallSkillHooks` 及其 `HookBool0` 实现）。
- 验收：同上，日志不再每 300ms 重复。

### P1-1 运行期自愈（可选，先别做）
- 若后续证明 Unity 在恢复/热更后**重载域**，则应检测 `g_orig*` 失效并重建钩子；但这属于**新机制**，需先有 §4 的现场证据再动，避免凭猜加代码。

## 8. ⚠️ 重大更正（2026-10-16 20:41 装机后真机复测，**推翻 §3/§4 的根因**）

**v14.4（退避 + 有界落定）已出包并装机，但复测证明它止不住这个崩溃** —— 因为崩溃**不是**「长时间/二次打开后」才发生：

- 冷启（`am force-stop` + `monkey`）后 **~3 秒即崩**，帧与旧崩**同一位置**（新 build `2da518c66f0e8e29c22c7ac27ade18a1c0a52f94`：`libstarry_magic.so +0x18564 / +0x13ef4` → `libil2cpp.so +0xc9927f8 / +0xc9be2e8 / +0xc9b14c8`，`fault addr 0x138`、`Cause: null pointer dereference`）。
- **`hooks sync` 一行都没打出来** ⇒ 崩在 `SyncHooks` 的**第一次** Install 调用里（不是重试累积、不是长时间运行）。
- 崩前关键日志（同线程）：
  ```

  20:41:38.866 Mod_Menu: [Il2Cpp] diag il2cpp_class_get_namespace xdl=0x6f99057d60[…] self=0x6f99057d60[…] same
  ```

**两条更正**：

1. **「长时间运行 / 后台恢复才崩」作废**。上一版据此立论，依据是 `Process uptime: 27175s`；而这次**全新进程**（启动 3 秒）报 `Process uptime: 26049s`，与设备开机时长同量级 ⇒ **该字段是系统/设备口径，不是本 App 进程的存活时长**，我读错了。
2. **新主嫌：il2cpp API 地址解析在本设备上不可自证**。`Il2CppApi` 的 stub-shift 锚点**不一致且无法恢复**，却仍打 `api loaded` 继续使用 ⇒ 某些 API 指针可能是错的，**一调就崩在 libil2cpp 内部**。这也解释了「同一份包在 OnePlus 上 L2/L3 全过、而在这台设备上必崩」这一设备相关性。

**下一步（未做，按优先级）**：

- **P0-A（防崩优先）**：`Il2CppApi::Load` 在 `anchors disagree / no recovery` 时必须**降级失败**（`ready=false`，功能整体不启用），或对**每个** API 指针做「落在 libil2cpp 可执行段内 + 序言形态」校验，校验不过**不调用**。宁可功能全关，不可崩。
- **P0-B（定位）**：把 `xdl` 与 `dynsym` 两条解析路径对**全部** il2cpp API 逐条比对（现只对 3 条打了 diag 且都 `same`），找出不一致的那条；崩溃帧 `libil2cpp +0xc9927f8` 与我们调用点 `libstarry_magic.so +0x18564` 可对上号。
- **P1**：本条违反 `hook-rules.md` §31「设备差异一律落运行时判据」——解析失败没有落成运行时判据，而是继续执行。

## 9. v14.5 复测：**我们那条 SIGSEGV 已止住**，但暴露出第二层问题（2026-10-16 20:56）

**已修（v14.5，`Games/EndfieldMod.cpp` 的 `SyncHooks`）**：

- **根因（§8 的延伸，实测坐实）**：`SafeProbe` 的 `siglongjmp` **只在登记过的线程有效** —— `Il2CppApi.h:220/228`：`PushJmp` 失败即 `return false`（**根本不执行 fn**），而**本 MOD 线程从未登记**（只有 `LearnWorker` 登记过）⇒
  ① 所有 SafeProbe 守卫的读取（如 `Api::ImageOf` 的「读首字段」）在本线程直接返回 false ⇒ **按名解析永远失败**；
  ② 未守卫的 il2cpp 调用（如 `Assemblies()` 内的 `domain_assemblies`）一旦命中「运行时未就绪」就是**未捕获 SIGSEGV ⇒ 直接杀进程**（`fault addr 0x138`）。
- **修法**：`SyncHooks` 里先 `Il2Cpp::SetScanThread(pthread_self())`（`thread_local` 只做一次），再把「解析 + 装钩」整段包进 `Il2Cpp::SafeProbe`；故障被 longjmp 捕获 ⇒ 本次判失败返回 + 外层退避重试。
- **实测证据（20:56:31.927）**：
  ```
  W Mod_Menu: [Endfield] hooks try 1 faulted (runtime not ready?) — backoff, will retry
  I Mod_Menu: [Endfield] lib ready (by-name, lazy hooks) dmg=0 inv=0 jump=0 skill=0
  I StarryMagic: [mrfzzmd] 初始化成功
  I MenuService: overlayVisible=true attached=true … show ACTIVITY overlay
  ```
  ⇒ **同一处调用不再杀进程**，模组正常初始化、菜单弹出 ✅。**v14.4 及之前「冷启必崩」的那条路已消除。**

**但仍有第二层问题（新形态：不是我们 so 的 SIGSEGV，而是游戏自己 abort）**：

```
20:56:31.927  [我们] hooks try 1 faulted …                    ← 我们在 Unity 初始化前碰了 il2cpp
20:56:32.321  I Unity : MemoryManager: Using 'Dynamic Heap' Allocator.   ← Unity 才开始初始化
20:56:32.380  W StarryMagic: [验证] grant rejected            ← 授权墙
20:56:32.435  I MenuService: overlayVisible=true …            ← 我们的菜单弹出

              #00 libc.so (abort+168)   ← 游戏/Unity 自己 abort

```

- **关键时序**：**我们在 `20:56:31.9` 调 il2cpp API，而 Unity 到 `20:56:32.32` 才刚起 `MemoryManager`** ⇒ **在 Unity 初始化完成前就触碰了 il2cpp**（fault 虽被捕获，但初始化可能已被扰动）⇒ 0.85 秒后 Unity abort。**判定：推断（未坐实）**。
- **框架侧已排除**：`grep -rn "abort()|_exit(|System.exit|Process.killProcess"` 于 `mod菜单/**` 的 JNI 与 auth 侧**无命中** ⇒ 不是框架在授权失败时杀进程。

**下一步（P0，未做）**：**首次触碰 il2cpp 必须有真正的就绪信号，而不是「早点试 + 捕获异常」**：

- 候选信号：框架授权流程结束（`grant ok`）之后 + 宽限期；或 hook 一个 Unity 侧初始化完成信号（`il2cpp_init` 返回 / UnityPlayer 首帧）；至少也应等 `libunity` 初始化日志出现后再开始解析。
- 保留 v14.5 的「登记线程 + SafeProbe 捕获」作为**最后一层兜底**，以及退避重试。
- **归属验证（决定「abort 是不是我们引起的」）**：在小米上装**官方原包**（`09_test/终末地/base/终末地_1.6.4_base.apk`）跑一次 —— 若官方也 abort，则与本 Mod 无关。⚠️ 需先卸载本包（签名不同），会丢已下的 3GB 资源与登录态 ⇒ **需用户明确授权**。
