## 一、实现路线：为什么不动 native，只打 JS 层补丁

| 项 | 结论 |
|---|---|
| 引擎 | Cocos Creator 3.x + JSB（`lib/arm64-v8a/libcocos.so` 28,798,216 B，md5 `7ad5451d988a57b52e189d4fdc359e83`），**无 IL2CPP / 无加固壳** |
| 逻辑位置 | `assets/assets/**/index.jsc`（**XXTEA 加密**，key 编译进 `libcocos.so`）⇒ **离线解密不可行**，逻辑只能在运行期注入 |
| 注入通道 | native → JNI 反射 `com.starry.magic.cocos.XnbzHooks.pump(String)` → 游戏线程 `evalString`（`com.cocos.lib.CocosHelper.runOnGameThread` + `CocosJavascriptJavaBridge.evalString`）；JS → Java 回传走 `jsb.reflection.callStaticMethod`（`XnbzHooks.logStatus` / `isPatched`） |
| 模块获取 | Cocos 3.x 虚拟模块：`System.get("chunks:///_virtual/{BattleUnit,BattleManager,Network,BattleModule}.ts")`（先例：`Games/BlzzMod.cpp` 同型） |
| 补丁载体 | `Games/XnbzMod.cpp` 内的 `kPatchJs` 原始字符串（`R"JS( … )JS"`），版本守卫 `g.__xnbzPatchVer>=5` + `Tick` 保活重注入（`QueryJsPatched()` 确认后才打「patch confirmed」） |

## 二、功能实现（v5 终版，全部在 JS 层）

| 菜单项 | feat_num | 挂钩点 | 做法 |
|---|---|---|---|
| 无敌 | 1 | `BattleUnit.prototype.updateState`（本地血量账本）＋ `isAlive` / `health` getter | 账本记录我方单位真实血量；开关 ON 时把回放中的我方生命顶住（`isAlive` 恒真、血量不降）⇒ **回放里我不掉血** |
| 伤害倍率 | 2 | `BattleUnit.prototype.applySequentialDamage` ＋ `BattleManager.applyActionEffect` / `applyActionEffectSegmentOnly` 的 `scale(t)` | 我方对敌伤害按倍率放大（1 = 关闭，2..100） |
| 强制胜利（内部） | — | 引擎 `BattleManager.prototype.startBattle` | 读服务端真实 `br.result.winner` 后改 `winner=1`，把回放推进胜利分支（`isWin` 显示侧） |
| 重试判胜 | 3 | `BattleModule.prototype.startBattle`（捕获 `{type,id,extra}`）＋ `Network.requestFightResult` | **结算回包到手之后**才判断：`rawWin!==1 && retry<3` ⇒ 本场**不伪造胜利**、不弹失败礼包、1.5 s 后 `retryNow()` 重开本场，让服务端重算；达上限打 `retry cap hit` |

诊断日志（`StarryTrace`，白名单 tag 看）：

```
xnbz-js replay try#0 win=2 actions=61          ← 服务端判负（win=2），战报动作数
xnbz-js settle: rawWin=2 rewardItems=0 retry=0 ← 结算回包：真实胜负 + changes.items 条数
xnbz-js server judged LOSS -> retry #1/3       ← 触发重开
xnbz-js server judged WIN after retry #N       ← 服务端这一次判胜（真奖励）
xnbz-js retry cap hit (3)                      ← 三次重算结果一致 ⇒ 重试改不了
xnbz-js force win #N (server result.isWin -> true)
```

## 三、实测（真机 `f9a116a2`，OnePlus OPD2404 / KernelSU）

| 轮次 | 用户实测 | 日志证据 | 处置 |
|---|---|---|---|
| v3 | 「无敌生效（不掉血）、伤害倍率只是数字变大、没作用」⇒ 服务端权威处理点改造 | `force win #1` 后胜利页出现 | 加引擎 `startBattle` 强制胜利分支 |
| v4 | 「之前那个胜利是关卡算过了，就是奖励不会发布」 | `replay try#0 win=2 actions=61`（type=1 id=6 主线第 6 关）+ `server judged LOSS, auto-retry #1/3` → **无第二场战报** | **v4 bug**：重试在回放开始 700 ms 就触发 ⇒ 战斗被打断，服务端没产生第二场 |
| v5 | 「奖励还是不下发」⇒ 用户判停 | 离线 harness 5 场景全对；装机后 `retry hook armed` / `patch v5 installed` | 重试改到结算后 1.5 s；本作收案 |

离线验证器 `/tmp/xnbz/harness_retry.js`（node 桩：假服务端按 script 给胜负 + 结算回包 `{data:{result:{isWin,winner},changes:{items}}}`，`setTimeout` 入队手动 drain）：

| 场景 | 服务端序列 | 结果 |
|---|---|---|
| A 概率型 | `[2,2,1]` | 3 次调用后判胜，`rewardItems=1` ✓ |
| B 确定性 | `[2]` | 4 次调用后 `retry cap hit` ✓ |
| C 重试关 | `[2,2,1]` | 1 次调用，只伪造胜利 ✓ |
| D 本来就胜 | `[1]` | 1 次调用，不重试 ✓ |
| E 只开重试（无敌/倍率全关） | `[2,1]` | 2 次调用后胜 ✓ |

## 四、★结论：服务端权威边界（本作判停的技术原因）

1. **战斗在 `game.fightbegin` 时由服务端一次性算完整场**（含 RNG）。请求体 `{type,id,extra}` 的 `extra` 只带**记录号 / 排名**（`PvpLogView.onBtnBattleClick` → `startBattle(t,e,n.toString(),i)`，`n`=recordID），**不含任何我方单位属性** ⇒ 客户端无从影响胜负。
2. **奖励 = `game.fightresult` 回包的 `changes.items`**。`ResponseUtil.checkResponse(e,s,c)` 只把 `messages` 推给 `network.messagesProcess`，**不把 `changes` 写进本地账目**；本地账目来自 `result` 或全量 `playerdata` ⇒ 客户端改 `isWin` 只改**显示**（用户实测已两轮证实）。
3. **380 个 `game.*` 接口全量普查**：战斗相关只有 `game.fightbegin` / `fightresult` / `fightoverwhelming`（碾压）/ `pvesweep`（扫荡）/ `templequickbattle` / `fourduelsweep` / `outertrialsweep` / `activitydrummingquicksettle`；**没有任何接口让客户端上报战斗胜负**（`fightresult` 只发 `{type,battleSn,jump}`）。
4. 客户端权威数据面只有引导（`game.saveclientdata` → `_clientData.guideGroup`）与通用 KV（`game.dataget` / `dataset`）——**都不涉及奖励**。
5. 【重试判胜】是唯一理论上能拿**真**奖励的客户端路子（重开本场让服务端重算）。实测服务端判负后不翻盘 ⇒ 按确定性结算处理。**不做本地假奖励**（伪造 `changes.items` + 本地账目：只本地好看、会被服务端同步覆盖、无法用于任何服务端校验）——用户明确不要。
6. 若将来要真奖励，只剩三条：**真提升服务端战力** / 走服务端本来就发奖的入口（`fightoverwhelming` 碾压、`pvesweep` 扫荡——门槛都在服务端）/ 服务端侧改动（超出客户端 mod 范畴）。
