## 2. 复核结论

### 2.1 旧包的核心缺陷：一条 JS installed 标记把补装链锁死

旧 `HalyMod.cpp` 注入脚本开头执行：

```js
if (g.__starryHalyInstalled) return;
g.__starryHalyInstalled = 1;
```

`Haly_TryInit` 只要 `libcocos.so` 已加载就会返回 ready，并不保证 `System.get("chunks:///_virtual/...")` 中的热更模块已经就绪。若首次 eval 早于热更模块、页面或 GameObject 状态：

1. 标记已经写成 1；
2. 后续 Native 默认每 15s 的补装在 JS 首行直接返回；
3. 免广告、无敌、召唤、雷罚中任何依赖晚到模块的 Hook 都不会再次安装。

这直接解释了同一包“有人有效、有人失效”“重启或热更后偶发失效”的现象。真机当前包的 so 内已确认存在 `__starryHalyInstalled` 和 `hooks installed (auto-buff mode)` 字符串。

### 2.2 免广告存在返回值契约错误

热更源码中真实调用路径为：

```js
const result = await sdk.showRewardAd({ scene, adUnitId });
if (!result.rewarded) { ...失败... }
```

旧补丁在 `SdkRewardAdGuard.showRewardAd` 上返回：

```js
{ success: true, skipped: true }
```

该对象没有 `rewarded` 字段；一旦广告请求绕过 `AdSkipService.tryShowSkipPopup` 或该 Hook 未及时安装，就会被调用方判为“未看完广告”。

### 2.3 雷罚不是概率问题

热更表 `base_skill` 中：

| skill id | name | trigger_type | trigger_param |
|---|---:|---:|---:|
| `100901` | 雷罚打击 | `2` | `6` |
| `100902` | 雷罚打击强化 | `2` | `6` |
| `100903` | 雷罚打击觉醒 | `2` | `6` |

所以官方逻辑是**每 6 次普攻命中计数触发一次**，不是随机概率；`trigger_type=2` 还依赖技能已进入角色 `SkillBookComponent.skillIds`。旧 Mod 想额外每次普攻触发，但补丁未安装时只能留下官方 1/6 节奏，表现正是“时有时无”。

旧实现还把雷罚配置扩成最多 33 段、每段高倍率；在当前热更高频战斗和大量分身场景下增加掉帧/异常风险。

### 2.4 先祖之魂的分身堆积与 runtime 覆盖

官方 `SkillSummonSystem.handleSummonRequest` 会读：

```js
const runtime = source.getComponent(RuneSpecialEffectComponent)?.runtime;
const batches = skill && runtime
  ? runtime.getSummonBatches(skill.skillId, request.effect)
  : [request.effect ...];
```

旧实现固定发送 `skillId: 100203` 并以 100s 持续、12s 间隔反复召唤，理论可堆叠约 27 个分身；某些符文/特殊效果存在时，`getSummonBatches` 还可能覆盖自定义 `effect`。

### 2.5 异常与线程边界

- 旧 JS timer/事件回调缺少逐功能异常隔离；召唤监听器用 `void handleSummonRequest()`，异步异常会变成未处理拒绝。
- 旧 Native 旗标是普通 `volatile bool`，UI 线程与 native Tick 线程并发读写没有统一同步协议。
- 旧 `EvalJs` 未清理 Java 侧 pending exception；虽然 `CocosJsBridge` 自己也有捕获，但 native 边界缺少失败可见性。

## 3. v2 四项功能重写

### 3.1 免广告

覆盖四层：

- `PlayerPrefService.hasAdPrivilege/canSkipAd`
- `AdSkipService.hasAdPrivilege/canSkipAd/tryShowSkipPopup`
- `SdkRewardAdGuard.showRewardAd`（**返回调用方需要的 boolean `true`**）
- `SdkService.showRewardAd`（返回 `{ rewarded: true }`，适配直接检查 SDK 结果的入口）

所有 Hook 仅在 `noAd=true` 时短路；关闭后继续调用原方法。

### 3.2 不羁怒火（自动无敌）

- 保留“主角长时无敌”的行为语义；
- 直接通过官方 `StatusEffectComponent.addEffect(1002, INVINCIBLE, 100, ...)` 维持；
- 已有剩余时间大于 8s 时不重复叠加；
- 关闭时只移除 `id=1002 + INVINCIBLE`，不粗暴清空其它 Buff；
- Native 旗标改为 `std::atomic<bool>`，JS 开关更新后立即 `applyNow`。

### 3.3 先祖之魂（自动召唤）

- 每 12s 触发一次，3 个分身；
- 每个分身持续 20s，最多同时约 6 个，避免旧版长期堆积；
- `inherit_attack=100000000`（官方运行时按 `/10000` 解析为 10000 倍继承）；
- 召唤请求带 `__starryHalyV2` 标记；`SkillSummonSystem.handleSummonRequest` 包装器将转发请求的 `skillId` 改为 `0`，强制走 `request.effect` 分支，避开 `RuneSpecialEffectRuntime.getSummonBatches` 覆盖，同时仍由官方 `spawnCloneEntity` 创建实体；
- 异步异常被包装器捕获并记录，不再形成未处理 Promise rejection。

### 3.4 雷罚打击（每次主角色普攻）

- 包装 `PassiveSkillTriggerSystem.triggerAttackerPassiveSkills`；
- 先保留原调用结果，再单独执行增强触发；
- 只接受 `sourceId == scene.playerEntity.id` 且 `skillId == basicSkillId` 的主角色普攻，避免 DOT、技能伤害、分身或反伤递归触发；
- 每次合格普攻发送 `skill_passive_trigger: { skillId: 100903 }`；
- 热更表增强从旧版的 33 段/高倍率降为固定 11 段、每段 9.9 倍，减少同屏投射物压力；
- `SkillCastSystem.executeSkillEffects` 对 `1009/100903` 加局部异常隔离。

### 3.5 异常兜底与模块重建

- 删除一次性 `__starryHalyInstalled` 锁，改为 `__starryHalyV2` 状态；
- 每个 Hook 独立 `try/catch`，单点失败只影响本功能的 Hook 安装；
- `warnOnce` 限频记录异常，避免每 500ms 刷日志；
- JS 自身每 3s 幂等补装，Native 每 5s 备份补装；
- `mod()` 对每个候选模块路径独立捕获，避免一个缺失路径阻断其它模块；
- `HalyMod.cpp` 的 `EvalJs` 清理 Java exception，避免异常跨 JNI 调用残留；
- 所有功能关闭时不再维持战斗效果，召唤时间戳和无敌效果都会清理。

## 8. 首包闪退定位与 fix2

首版 `combo_fix` 覆盖安装后，用户打开游戏立即闪退。真机 crash buffer 的关键信息：

```text
NoSuchMethodError: no static or non-static method
"Lcom/starry/magic/bridge/ModBridge;.nativeGetPinnedCert()[B"

Failed to register native method
com.starry.magic.bridge.ModBridge.nativeBridgeRegistered()Z

JNI_OnLoad+5568  libstarry_magic.so
Runtime aborting (SIGABRT)
```

根因是首版只替换了 `libstarry_magic.so`，但没有同步替换旧包中的 `classes4.dex`。旧 dex 的 `ModBridge` 缺少当前 Native 源码要求的两项声明：

- `nativeBridgeRegistered()Z`
- `nativeGetPinnedCert()[B`

JNI `RegisterNatives` 找不到方法后进入 ART pending exception 状态，随后抛出新异常时触发 `abort`。

fix2 采用最小 dex 修复：

1. baksmali 旧 `classes4.dex`；
2. 仅给 `com/starry/magic/bridge/ModBridge.smali` 追加两项 native 声明；
3. 重新 assemble `classes4.dex`；
4. 与 v2 so 一起替换进原始星光底包；
5. zipalign + 星光证书重签；
6. 同签名覆盖安装，保留数据。

静态核对结果：旧 dex 缺 2 项，fix2 dex 19 项 JNI 方法齐全；包内 so MD5 仍为 `3851ad78…`。
