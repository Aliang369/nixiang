## ① 结论摘要（三条最关键）

### 结论 1：容器是 **.NET `BinaryFormatter`（MS-NRBF）** 流，**不是** Sirenix Odin Serializer

- `[实测]` 写入器是 **AOT 原生**方法 `Script.Main.Utils.SerializeUtil.BfSerialize(object, out byte[])`
  （dump.cs `745433` 行所在类，VA `0x38F6288`）。其反汇编体内调用：
  - `0x39E892C  public void .ctor()` → `System.Runtime.Serialization.Formatters.Binary.BinaryFormatter..ctor()`
  - `0x39E9554  public void Serialize(Stream serializationStream, object graph)` → `BinaryFormatter.Serialize`
  ⇒ **`Bf` = BinaryFormatter。**
- `[实测]` 读取器 `SerializeUtil.BfDeserialize<T>`；其泛型实例
  `SerializeUtil.BfDeserialize<object>` 的 VA 是 **`0x2633DEC`**，正是加载器
  `HotUpdateDll.<Load>d__9.MoveNext` 在 5 处调用的反序列化函数（见 §⑤）。
- `[实测]` 字节级完全吻合 MS-NRBF：
  - 头 17 字节 `00 01 00 00 00 FF FF FF FF 01 00 00 00 00 00 00 00 00`
    = `SerializedStreamHeader(0)` + `RootId=1` + `HeaderId=-1` + `MajorVersion=1` + `MinorVersion=0`
  - `0x0C` = `BinaryLibrary`，`0x05` = `ClassWithMembersAndTypes`，`0x06` = `BinaryObjectString`，
    `0x0F` = `ArraySinglePrimitive`，`0x0B` = `MessageEnd`
  - 成员类型信息 `BinaryTypeEnum` = `1(String) / 0(Primitive) / 3(SystemClass)`，
    `PrimitiveTypeEnum` = `9(Int64)`，与 dump.cs 中 `_guid:string` / `_version:long` /
    `_assemblies:Dictionary<string,byte[]>` **三者逐一对应**。
- `[实测]` **不存在 `_vm` 字段。** dump.cs `745522`/`745621` 行显示 `AotMetadataDll` 与 `HotUpdateDll`
  的字段只有 `_guid`(string, +0x10) / `_version`(long, +0x18) / `_assemblies`(Dictionary, +0x20)。
  **任务书中的 `_vm` 应更正为 `_version`。**
- `[实测]` Odin 结论的原始依据（`Reflector.cs` 用 `Sirenix.Serialization.Serializer.Get<T>()`）
  指的是**另一路**序列化（资产/对象映射），**与本热更容器无关**。本容器的字节结构由
  `BinaryFormatter` 写入，与 Odin 无关。

### 结论 2：容器**可以重建**，且 LZ4 外层能做到**逐字节复现**（`cmp` 通过）

- `[实测]` 外层 LZ4 frame：magic `04 22 4D 18`，`FLG=0x48`，`BD=0x40`，
  含 8 字节 content size，`HC=0x10`，块依赖（linked blocks，非独立），无块校验、无 content checksum。
- `[实测]` **复现命令（两个文件均 100% 字节相同）**：
  ```
  lz4 -3 -B4 -BD --no-frame-crc --content-size -f <解压后明文> <输出>
  ```
  - `hotupdatedll`：重建 2,868,624 B == 原件 2,868,624 B，`cmp` 通过
  - `aotmetadatadll`：重建 4,115,754 B == 原件 4,115,754 B，`cmp` 通过
  - 压缩等级 **level 3** 与游戏自身 `lz4.Compress(byte[], compressionLevel = 3)`（VA `0x38F4100`）
    **默认值一致**，强烈提示构建管线复用了同一份 LZ4 实现 `[实测·推论]`。
- `[实测]` MS-NRBF **不含任何内容校验和、不含绝对文件偏移、不含总长度字段**
  （内部引用一律用 `ObjectId`，blob 自带 4 字节长度）。⇒ 替换某个程序集只需改
  `ArraySinglePrimitive` 记录的 **4 字节 Length + 载荷**，其余字节**一律不动**。
- ⇒ **重建可执行性：高。** 三档判定标准见 §④。

### 结论 3：运行时会用**服务端下载**的热更 dll **覆盖包内**的 —— 条件成立时成立

`[实测]` `HotUpdateDll.<Load>d__9.MoveNext`（file offset `0x38F3A98`）实际顺序：

1. **总是先读包内 origin**：`_originFilePath`（StreamingAssets 侧）→ 经 `UnityWebRequest.Get` 下载
   → `lz4.Decompress` → `BfDeserialize`（顺序确实是**先 origin 后 cache**）
2. **再读缓存 cache**：`_cacheFilePath`（`persistentDataPath` 侧）→ `File.Exists` + `File.ReadAllBytes`
   → `BfDeserialize`
3. **二选一**（`0x38F7D3C`–`0x38F7D6C`）：
   - cache 对象为空 **或** `cache._guid != origin._guid` → 选 **origin**
   - 否则（`_guid` 相同）→ 选 **cache**
4. **版本比较**（`0x38F7D70`–`0x38F7D88`）：
   `if (version参数 != 0 && 选中对象._version != version参数)` → 调
   `DownloadUtil.DownloadNewest(serverUrl, toVersion=version, fromVersion=选中._version, file=_resource)`
5. **下载成功**（`DownloadCode.Succeed=0`）：把下载体的 `_assemblies` 覆盖进选中对象、
   `_version` 置为请求 version、置"脏"标记 → `BfSerialize` 写回 **cache 文件** → `Assembly.Load` 每个 blob
6. **下载失败**：`DownloadCode` 1/2/4/5/6（WebError/UpdateInfoError/FileVersionError/FileSizeError/
   FileUnzipError）→ 置错误码 → `onResult(错误码)` 返回，**不加载任何程序集**（**不回退包内 origin**）。
   仅 `FileNotFind=3` 被容忍：把 `_version` 顶成请求值后继续用内存里已读到的对象。

⇒ 三选一回答：**②「有缓存/新版本时优先下载」**，且需加一条决定性限定：
**只要服务端 `version` 与包内容器 `_version` 不相等，包内 `OnePercent.dll` 就不会被执行。**

### 推荐出包形态

**A 路（改 `assets/Hybrid/hotupdatedll` 内 `OnePercent.dll`）为主**：
- A 路是唯一能改到**游戏主逻辑（`OnePercent.dll` 有完整 IL）**的路径；
- 容器重建已被证明可逐字节复现，改动面最小（10 字节记录头 + 载荷）；
- 但必须**同步处理 `_version` 对齐**（否则被下载覆盖），或从网络层阻断下载。

**B 路（原生 so 注入 + hook）作为补充**：HybridCLR 解释执行的方法**无原生入口**，因此对热更方法
`methodPointer` hook 命中率可能为 0；但 AOT 侧有大量稳定可用点（`il2cpp_*` 导出 API、
`mini_get_interp_callbacks`、`UnityEngine.Time::set_timeScale` 等），适合做**与具体 IL 无关**的
全局性功能。**C 路（数据层）风险最高**，见 §⑥。

## ③ 容器格式（偏移表 + 复刻规则）

### 3.1 外层：LZ4 frame `[实测]`

| 字段 | 值 |
|---|---|
| magic | `04 22 4D 18` |
| FLG | `0x48` → version=01, B.Indep=**0（块依赖 / linked blocks）**, B.Checksum=0, **C.Size=1**, C.Checksum=0, DictID=0 |
| BD | `0x40` → block max size code 4 = **64 KiB** |
| content size | 8 B 小端 = 解压后长度（`hotupdatedll` = 7,013,189 = `0x6B0345`） |
| HC | `0x10`（由 FLG/BD/content size 派生） |
| 块 | 每块 4 B 小端长度头（bit31=1 表示未压缩直存） |

尺寸：`hotupdatedll` 2,868,624 B → 明文 7,013,189 B；`aotmetadatadll` 4,115,754 B → 明文 9,186,916 B。
`hotupdatescene` 2,877,576 B 是 UnityFS AssetBundle，**不在本报告范围**。

```bash
lz4 -d  <pkg> <dec>                                          # 解压
lz4 -3 -B4 -BD --no-frame-crc --content-size -f <dec> <out>  # 压缩（字节级复现原件）
```

> `[实测]` 不写 `--content-size` 得到 `FLG=0x40`（缺 content size）；不带 `--no-frame-crc`
> 得到 `FLG=0x44`（多 content checksum）。**三者必须齐全**才能得到 `FLG=0x48`。

游戏侧解压由 `lz4.Decompress(byte[])`（VA `0x38F437C`）完成，它调用 Unity 原生
`Unity_LZ4_uncompressSize`（VA `0x38F4484`）/ `Unity_LZ4_decompress`（VA `0x38F4508`）
——**均为 block 级 API**，故 frame 头是 C# 自己解析的 ⇒ **重建时必须保持 FLG/BD/content-size
结构一致**（不能随意改成 `FLG=0x44` 或去掉 content size）。

### 3.5 足以手写 python 复刻读写的规则

**结论：复刻读写几乎不需要真正"重写"整个容器。** 只涉及 4 种 entry：

1. **7-bit 变长长度前缀字符串**（`BinaryObjectString` / `Name` / `MemberNames` / `LibraryName`）：
   ```
   读取: n=0; sh=0
         while True:
             b = data[pos]; pos += 1
             n |= (b & 0x7F) << sh
             if not (b & 0x80): break
             sh += 7
         s = data[pos:pos+n].decode('utf-8'); pos += n
   写入: 逐 7 位输出，低 7 位在前，最高字节清 bit7
   ```
2. **int32（小端）**：`RootId / HeaderId / Major·MinorVersion / LibraryId / ObjectId / MemberCount / Length`
3. **固定单字节枚举**：`RecordType`、`BinaryTypeEnum`、`PrimitiveTypeEnum`
4. **blob entry**（**唯一需要改的地方**）：
   ```
   <0x0F> <ObjectId:int32 LE> <Length:int32 LE> <0x02=Byte> <Length 个原始字节>
   ```

**替换某程序集的完整算法（α 路的全部工作）**：
```python
# 前提：已 lz4 -d 得到明文 dec
rec = 0x730          # hot 的 OnePercent.dll；AOT 侧对应 §3.4 偏移
assert dec[rec] == 0x0F
oid  = int.from_bytes(dec[rec+1:rec+5], 'little')
old  = int.from_bytes(dec[rec+5:rec+9], 'little')
assert dec[rec+9] == 0x02
new_blob = open('patched_OnePercent.dll', 'rb').read()
out = (dec[:rec+5] + len(new_blob).to_bytes(4, 'little') + dec[rec+9:rec+10]
       + new_blob + dec[rec+10+old:])
open('dec.new', 'wb').write(out)
```
然后 `lz4 -3 -B4 -BD --no-frame-crc --content-size -f dec.new hotupdatedll`。
**其余所有字节（含 `_guid`、`LibraryId`、`ObjectId`、成员表、`MessageEnd`）保持不变** —— 因为
MS-NRBF 内部引用全用 `ObjectId`，**没有任何绝对偏移或长度需要联动修正**。

### 3.6 附注 / 未决点（诚实标注）

- `[实测]` **`_version` 值的字节位置**：紧跟 `_guid` 的 `BinaryObjectString` 之后，位于
  **明文 `0x1AD`–`0x1B4`（hot）/ `0x1AF`–`0x1B6`（aot）** 共 8 字节；
  两个文件该 8 字节**完全相同**：`00 00 00 00 8B D0 6D 0C`。
- `[推断·待验证]` 该 8 字节是否就是 `_version`（Int64 小端 = `0x0C6DD08B00000000`）：
  按 `MemberNames` 顺序，`_version` 的值**必然**落在该位置；但按 MS-NRBF 常见实现，
  Primitive 成员值前应出现记录 `8 = MemberPrimitiveTyped`，而此处明文 `0x1AD` 起**并无记录 8**
  （已对 header 区搜索 `08 09` 模式，无命中）。因此存在两种可能：
  (a) 该实现把 Primitive 成员值**内联为纯 8 字节**；(b) 存在一层未识别的包装。
  **修 Mod 不需要碰它，故本报告不据此下结论**；若要改 `_version` 以规避服务端下载，
  **必须运行时验证**（见 §⑦ V1）。
- `[实测]` **VA→file offset 不恒定**：`libil2cpp.so` 有 4 个 `PT_LOAD`：
  `vaddr 0x0 / filesz 0x1CB7664 / off 0x0`（delta `0x0`）、
  `vaddr 0x1CBB664 / filesz 0x29E2E1C / off 0x1CB7664`（delta `0x4000`）、
  `vaddr 0x46A2480 / filesz 0x3B2448 / off 0x469A480`（delta `0x8000`）、
  `vaddr 0x4A588C8 / filesz 0x2936D8 / off 0x4A4C8C8`（delta `0xc000`）。
  本次**全部代码反汇编均落在 delta=0x4000 段**，与 dump.cs 一致；但读 `.rodata`/跳转表/`.got`
  时必须按段换算（本次踩坑并已修正：`HotUpdateDll` 的 `DownloadCode` 跳转表在 VA `0xF7D5D0`，
  属 **delta=0 段**，按 −0x4000 读会得到错误的 `FF FF FF FF 00 00 00 00`）。

## ④ 重建 / 替换方案与风险

### 4.1 路线 α：复刻容器 + 重新 LZ4（**推荐**）

**步骤**
1. `lz4 -d` 解出明文（**不要动 APK**；直接用 `03_decompiled/百分之一/assets/Hybrid/` 下的文件）
2. 用 §3.5 脚本定位目标 `ArraySinglePrimitive`（`hotupdatedll` 的 `OnePercent.dll` 在 `0x730`）
3. 替换 payload、回写 4 字节 `Length`
4. `lz4 -3 -B4 -BD --no-frame-crc --content-size -f dec.new hotupdatedll`
5. 外科 zip 组装

| 风险项 | 结论 | 证据 |
|---|---|---|
| LZ4 外层可逐字节复现 | **是** | `cmp` 通过（hot + aot 两个文件） |
| 内部有无内容校验和 | **无** | MS-NRBF 记录集 + 全文实测无 hash/CRC 字段 |
| 有无绝对偏移需联动修正 | **无** | 引用全部用 `ObjectId`；blob 自带长度 |
| 长度可变（不必等长） | **可以** | 无总长字段；`MessageEnd` 位置自然后移 |
| 剩余风险 | ① `_version` 语义未定（§3.6）② 服务端下载覆盖（§⑤）③ `hotupdatescene`（AssetBundle）另说 | — |

### 4.2 路线 β：等长原位替换

- **硬约束**：新 `OnePercent.dll` 必须**严格等长** 6,697,472 B，即只能做**等长 IL 补丁**
  （改立即数 / 反转分支 / 换调用目标 / 同长度字符串替换）。
- 现实可行性：`OnePercent.dll` 是 6.7 MB 完整 IL，等长改写**约束极强**；
  只有"`ldc.i4.0`→`ldc.i4.1`、`brfalse`→`brtrue`、字段偏移常量对调、等长字符串替换"这类微改可能。
- **关键认识**：β **并不会**因为"原位"而更安全 —— 服务端下载覆盖的判据是容器里的
  `_version` / `_guid` / `_assemblies`，**与 blob 是否等长无关**。
  等长的唯一好处是：明文长度不变 ⇒ 不必重算 `Length`，**但仍需重压缩**
  （`lz4 -3` 输出对内容敏感，等长 ≠ 同压缩字节）。
- 适用：**极小改动 + 无法重打包容器**的应急场景。

### 4.3 推荐与「重建成功」判定标准

**推荐 α**（可改任意 IL、可换 DLL、可改 `_version`/`_guid`），β 仅作应急。

| 级别 | 判据 | 本次可否离线达成 |
|---|---|---|
| **L1 结构** | 重建后的 frame `lz4 -d` 回来 `cmp` 等于修改后明文 | ✅ 可离线自测 |
| **L2 语法** | 明文用 MS-NRBF 解析器**完整走完**（消费到 `len-1`，最后一条 = `MessageEnd`） | ✅ 可离线自测 |
| **L3 字段一致性** | `_guid` / `_version` 8 字节 / `LibraryId` / `ObjectId` / `MemberCount` / `MemberNames` / `BinaryTypeEnum[]` / 汇编名列表 与原件**逐字节相同** | ✅ 可离线自测 |
| **L4 运行时** | 游戏内 `BfDeserialize` 返回 true、`Assembly.Load` 成功（无 `AssemblyLoadError=11` / `CacheWriteError=10` / `LogError`），功能生效 | ⏳ **必须运行时** |

L1–L3 全绿才允许装机；**L4 是"可交付"的唯一证据**。

⇒ **路径模板（结构性结论，100% 实测）**：
```
_cacheFolderPath  = Path.Combine(Application.persistentDataPath,   <A>)
_cacheFilePath    = Path.Combine(_cacheFolderPath,                 <B>)
_originFolderPath = Path.Combine(Application.streamingAssetsPath,  <A>)
_originFilePath   = Path.Combine(_originFolderPath,                <B>)
_resTag           = <E>.ToLower()
_resource         = string.Concat(_resTag, <C>)
```
**即：确实是 `Application.persistentDataPath + …`（cache）与
`Application.streamingAssetsPath + …`（origin）**，两者共用同一组 `<A>` / `<B>`。

`[实测·推论]` **字面量取值**：包内实际文件是 `assets/Hybrid/hotupdatedll`、
`assets/Hybrid/aotmetadatadll`，而 `_originFilePath` 必须指向它们游戏才能跑通 ⇒

| 类 | `<A>` | `<B>` |
|---|---|---|
| `HotUpdateDll` | `Hybrid` | `hotupdatedll` |
| `AotMetadataDll` | `Hybrid` | `aotmetadatadll` |

⇒ 运行时实际路径：
```
cache : {Application.persistentDataPath}/Hybrid/hotupdatedll
        Android: /data/data/<pkg>/files/Hybrid/hotupdatedll
origin: {Application.streamingAssetsPath}/Hybrid/hotupdatedll
        Android: jar:file:///data/app/…/base.apk!/assets/Hybrid/hotupdatedll
```
`<C>` / `<E>`（`_resTag` / `_resource`）取值**未离线确认**，是服务端下载用的文件名/标签（§⑦ V6）。
> 精确取值可用本次同法继续推进：取 `.got` 项（如 `0x4A08878`）的 `R_AARCH64_RELATIVE`
> 重定位 addend 得到 usage slot VA（本次已取得：`0x4A08878 → 78523336` 等），
> 再用 usage slot 索引反查 `global-metadata.dat` 的 `metadataUsagePairs → stringLiteral`。
> 此步**本次未完成**，故标 `待验证`。

### 5.4 三选一结论

**② 有缓存/新版本时优先下载。** 但必须补充两条限定，否则结论会误导：

1. **包内 origin 每次都会被读取**（无条件，先于 cache），它不是"可被跳过"的。
2. **下载只在版本不匹配时发生**；一旦发生且失败，游戏**放弃加载热更程序集**
   （而不是回退到包内那份已读好的 origin）。

### 6.1 外科 zip 组装的校验风险 `[实测]`

- 已知：**无 dex / so 完整性校验**（可外科替换 + 重签名）。
- 但存在 **TapTap 登录** 与 **微信支付签名绑定**：
  - 微信支付的签名基于 **APK 签名证书**；**改包重签名会导致微信支付失效**（服务端校验签名 / 包名）。
  - TapTap 登录同样可能校验签名 / 包名。
  - ⇒ 若 Mod 不需要支付 / 登录，影响可接受；若需要，**A 路改 IL 本身不影响签名**，
    但**重新签名**这一步就会破坏绑定，**务必运行时验证**。
- 建议：优先**覆盖安装 + 保留原签名能力**（若设备已有可用签名方案），否则在 §⑦ 中列入验证项。
