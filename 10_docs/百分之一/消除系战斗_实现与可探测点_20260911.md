# 百分之一 — 消除系战斗：实现机制与可探测点（2026-09-11）

> **范围**：只做**消除系战斗**的探测，其他系统（经济/内购/广告/登录/上报）不在本文。
> **对应玩法**：主线推图、挑战系列、公会挑战、公会 Boss、委托、分数赛、宝藏、大师赛、多重赛、决斗。
> **性质**：纯静态（只读源码，未改文件、未出包、未装机、未启动游戏）。**运行期实测 = 0 项**，所有服务端校验强度均为 **[待验证]**，须抓包定论。
> 源码根 `<SRC>` = `06_dumped/百分之一/hotfix/src`（`OnePercent.dll` 反编译，5,162 个 `.cs`）。

## ① 一句话结论

**消除系战斗里，客户端是一个「只发 6 种操作 + 只播服务端动画」的瘦客户端：**

- **它没有任何战斗数值**（`Logics.GemsBattles/` 里 `Health`/`Hp`/`Damage` **零命中**）——不是"改了会被检测"，而是**客户端根本没有那个数**。
- **它能发给服务端的只有 6 类操作**，全部带服务端下发的步进令牌 `_round`，且受服务端"轮到你了吗"闸门控制 → **无重放/无越回合可能**。
- **唯一可能的缺口**：这 6 类操作里的**实体 ID / 索引 / 坐标是客户端自己填的**（`source`、`target`、`card index`、`handSite`、`teamSite`、`perk Index`）。**胜负无法改，但"用哪个牌/哪个技能/打谁"是客户端说了算的 —— 服务端对这些参数是否做语义校验，就是全部的可探测空间。**

**一句话给结论**：**无损改数值这条路是封死的**；**真正值得探的是"参数语义校验"这 6 个洞**，其中「自选抽牌」和「自选 Perk」静态上最可疑。

## ③ 实现架构：谁是权威

### 3.1 上线流程（[实证]）

```
CharacterBattle.SearchBattleAsync(param)            ← 匹配请求
  → SEARCH_REQUEST(1103) / SEARCH_RESPOND(1104)     → 拿到 BattleServerHost / BattleServerPort / room
  → ConnectAsync(host, port)                        ← 独立战斗服 TCP 连接
  → ENTER_REQUEST(1106)                             ← 带 Helper.Owner.Name + room
  → BE_READY_REQUEST(1108)                          ← 双方就绪
  → START(1110) / ROUND_START(1134)                 ← 服务端开始驱动
```

**关键**：战斗服是**独立连接**（`Router` 基类只有 `ConnectAsync/Send/SendAsync/Close` + `OnMessage/OnLostConnect`）。`GemsBattle.cs:522`、`DuelBattle.cs:497`、`MatchMaster.cs:286`、`MatchMultiple.cs:287` 各自发 `ENTER_REQUEST`。

### 3.2 客户端**没有**任何战斗数值（[实证]，本节最重要）

| 查法 | 结果 |
|---|---|
| `grep -r "Health\|Hp\|Damage" Logics.GemsBattles/` | **0 命中** |
| `elapsing/TROOP_INSTANTLY_PROPERTY.cs` | 单位数值只有 `TIP_LIFE` / `TIP_SHIELD` / `TIP_ATTACK` / `TIP_MAGERY` / `TIP_AMOUNT` —— 命名即**「飘字提示值」**，供伤害飘字/血条显示 |
| `GemsBattle.cs:566,582,1261,1511,1583` | `_troops` 全部由**服务端** `Deserialize` / 服务端命令写入，客户端从不自行计算 |
| `GemsBattle.cs:1616-1641`（`BC_UNIT_FLAT_SHOT`） | 服务端**只下发目标 ID 列表**；客户端拿 ID 去读**自己**的 `TIP_*` 挂飘字 → **连"这一下打多少"都不知道** |
| `GemsBattle.cs:1579`（`BC_UNIT_REMOVE`） | **击杀由服务端下发**，带死因 `TROOP_CAUSE_OF_DROP` |
| `GemsBattle.cs:1455-1459` | `case MID_CHARACTER_BATTLE_FINISHED(1144): message.ReadBool(out value); Post(new BattleFinish(value))` → **胜负 = 服务端消息里的一个 bool** |

**→ 在客户端改 `TIP_*`、`_board`、`BattleFinish`、`_troops`，效果仅限"血条和飘字变好看"，服务端胜负、关卡通过记录（`InstanceLog`）、奖励全不受影响。**

### 3.3 操作门控（[实证]）—— 重放/越回合被堵死

| 机制 | 位置 | 说明 |
|---|---|---|
| **步进令牌 `_round`** | `GemsBattle.cs:1271-1273`（`ROUND_START` → `message.ReadU32(out _round)`） | 回合号由**服务端下发**；客户端的每个操作请求都回抄 `_round`（`:983/:1007/:1029`）→ 服务端可识别过期/重复操作（对应 `PROOF_ID.PID_INVALID_STEP=2`） |

## ⑤ 可探测点（本文核心）— P1~P6 为「参数校验缺口」假设，P7 为零风险增强

> 全部为 **[待验证]**：静态只能确认"参数由客户端提供"，**无法确认服务端是否复核**。
> 每个都给出「若不复核能得到什么」和「怎么验证」。

### P1 ⭐ **自选抽牌**（静态最可疑）

**机制**（[实证]）：
- `DRAW_CARD_INITIAL(1113)` 下发的是 **`tagBattleDrawCardDeck` = 整副牌库**：`genre`、`limit`、`round[]`，每轮 `tagBattleDrawCardRound{sequence, duration, **cardlist[]**, drawcard[], dealcard[]}` —— **`cardlist` 是该轮全部牌**（`GemsBattle.cs:1143-1163`）。
- 客户端**开局即持有所有轮的完整牌表与 `tagBattleDrawCard.index`**。
- 上行 `DrawCard(sequence, card.index)`（`GemsBattle.cs:1052-1058`）。
- 官方 UI 只在「本轮 `cardlist` 中 `taked==0` 的第 `_chose[rid]` 个」里选（`GemsBattleDrawCardRenderer.cs:1458-1478`）—— **这个筛选是纯客户端行为**。

**若服务端不复核 `card` 是否属于本轮可选集合** → 可发**任意 `index`**（含本轮最强/最稀有的牌，甚至其他轮的牌）。

**验证**：抓包对比「官方路径选到的 index」与「手工发一个同轮但非 offered 的 index」的 `DRAW_CARD_RESPOND(1116)`（`succeed` 字段，`GemsBattle.cs:1181-1203`）差异。

### P2 ⭐ **自选 Perk / Booster**（大师赛）

**机制**（[实证]）：`UsePerk(source, target)` → `COST_ITEM_REQUEST(1123)`，其中 **`source` = `MatchMasterPerk.Index`（客户端选哪个 Perk）**、`target` = 落点。UI 调用链：`MatchMasterPerk100x.cs` → `Manager.OnUsePerk(Index, place)` → `MatchMasterManager.cs:1198` → `RouterManager.MatchMaster.UsePerk`。
`UseBooster(target)` → `CAST_SPELL_REQUEST(1121)`。

**若服务端不复核 `source` 是否为该玩家已解锁/已选择的 Perk** → 可**使用任意 Perk**（包括未解锁/未选择的）。

**验证**：抓包发一个**不属于自己 Perk 列表**的 `Index`，看 `COST_ITEM_RESPOND` 与后续 `BC_USE_PERK`。

### P3 ⭐ **任意交换（非邻接）** —— 用户最关心的那条

**机制**（[实证]）：`GemsBattleBoard.Swap(source, target)`（`GemsBattleBoard.cs:38-48`）**只查越界**，**没有邻接校验**：

```csharp
if (_board == null || source >= _board.Count || target >= _board.Count) return false;
// 直接交换任意两格
```

而 `GemsBattle.Swap`（`:976-999`）把它**原样上行**（`SWAP_REQUEST` 带 `_round`/`source`/`target`）。

**若服务端也不复核邻接 / 不复核是否成消除** → **「任意交换」成立**，这是消除系唯一可能质变战斗结果的口子。
**若服务端复核**（更可能，因为服务端持有棋盘并下发 `BC_GEMS_FALL_PHASE`/`BC_GEMS_ABSORB`/`BC_GEMS_EXTRA_ROUND`）→ 无效。

**验证**（最高优先）：抓包发一组合法邻接交换 + 一组**非邻接**交换，比较 `SWAP_RESPOND(1126)` 与后续是否出现 `BC_GEMS_SWAP` / `BC_GEMS_FALL_PHASE` / `BC_GEMS_EXTRA_ROUND`。

### P4 **技能/攻击目标越权**

**机制**：`CastSpell(_round, source, target)` —— **`source` 与 `target` 都是客户端填的 64 位实体 ID**。

**探**：`source` 填**敌方**单位 ID？`target` 填自己/非法 ID？Gems 系带 `source`，MatchMaster 系只带 `target`（服务端定 source，更严）。

**验证**：观察 `CAST_SPELL_RESPOND(1122)` 与 `BC_UNIT_*` 是否体现该动作。

### P5 **决斗放手牌的落点越权**

**机制**：`PutHandCard(handSite, teamSite)` → `DUEL_BATTLE_HAND_CARD_TAKE_CARD_REQUEST`，两个坐标都由客户端填（`DuelHandCardRenderer.cs:576`）。
且 `PutHandCardSynchronizer` 的存在说明**完成需要服务端插入单位确认**（`OnInsert`），即**有服务端参与**。

**探**：`handSite` 指向不存在的手牌、`teamSite` 指向敌方阵位/被禁位（`BC_TROOP_SITE_BAN`）？

**验证**：抓包看是否返回失败，或是否出现 `BC_TROOP_SITE_*`/`BC_UNIT_INSERT`。

### P6 **抽牌序号 `sequence` 越权**

**机制**：`DrawCard(sequence, card)` 的 `sequence` 也由客户端填 → 能否用**其他轮的 sequence** + 该轮的牌？
配合 P1，若两者都不校验，则等于**自由选牌**。

### P7 **客户端侧能做的「合法」增强（无服务端风险）**

#### P7.1 先分清「提示」与「自动操作」—— 官方是**两条互斥路径**（[实证]）

| | 官方「提示」 | 官方「托管」（自动操作） |
|---|---|---|
| 触发 | 服务端每回合推 `ShiftSuggest`（`GemsBattle.cs:1346`） | 服务端每回合推 `TrustOperator`（`GemsBattle.cs:1347`） |
| 接口 | `SUGGEST_REQUEST(1131)` 带 **`(byte)1`** → 服务端返回 **`CGemsBattleBoardEliminateShiftResultArray`**（**全部可行交换及其消除结果**） | **不发任何网络报文**：`OpenTrust()`（`GemsBattle.cs:1127-1133`）只 `Post(new TrustOperator(++_trust))` |
| 本地决策 | `GemsBattleUtil.FindBestShift(shiftArray, absorbs, out source, out target, ...)`（`GemsBattleUtil.cs:59`）→ 本地挑"连击数最大 / 能量最匹配"的那一手 | 读**玩家预设**的行动/技能顺序：`Formation.GetActionOrder(team,…)` / `GetSpellOrder(team,…)` + `_strategy`/`_energy`/`_spell`/`_action`（`GemsBattleTrustRenderer.cs:196-264`） |
| 结果 | **只高亮**建议的宝石（`GemsBoardRenderer.cs:114-200`、`TreasureBoardRenderer.cs:110`、`DuelGemsBoardRenderer.cs:127`），**不自动发 Swap** | **自动替你出牌** |
| ⚠️ 互斥 | `GemsBoardRenderer.cs:95`：**`if (Manager != null && !Manager.IsTrust())`** —— **托管开着时，客户端根本不请求建议** | 反之亦然 |

**→ 官方那个"建议"是纯提示；官方的"自动操作"是托管，而托管走的是玩家预设策略，不是最优解。两者不叠加。**

#### P7.2 托管的解锁门（[实证]）

`GemsBattleTrustRenderer.OnChangeClick()`（`:355-396`）分三态：

| 态 | 条件 | 点击行为 |
|---|---|---|
| `Lock` | `BattleCfg.Value.TrustCfg.IsUnlock() == false` | 只弹提示：「通关第 N 关解锁」（`UnlockLevel` **来自服务端配置** `BattleCfg`） |
| `Close` → `Open` | 已解锁 | 写**本地 DBreeze**`CharacterData.GemsBattleTrust = true` + `Refresh()` + `RouterManager.GemsBattle?.OpenTrust()` |
| `Open` → `Close` | — | 写 `GemsBattleTrust = false` |

宝藏同理用 `HuntCfg.Value.TrustCfg.IsUnlock()` + `CharacterData.TreasureTrust`（`TreasureTrustRenderer.cs:336-350`）。

#### P7.3 「自动最优走法」能做成哪三种形态

| 形态 | 做法 | 价值 / 风险 |
|---|---|---|
| **(a) 纯提示** | 直接调 `GetGemShiftSuggestAsync()` 高亮最优手 | 就是官方现成功能（`GemsBoardRenderer.cs:99`），**价值低** |
| **(b) 全自动最优** ⭐ | mod 自己：调 `GetGemShiftSuggestAsync()` → `FindBestShift` 得最优解 → **自动发 `Swap(source, target)`** | **官方没有这个**（托管不用 suggest、只按预设策略）。每步都是**合法操作、经服务端正常裁决** → 服务端**无法判定为作弊**。这是消除系**最稳妥、收益最接近"无敌"**的功能 |
| **(c) 借官方托管** | 让本地 `GemsBattleTrust = true` 且 `IsTrust()` 为真 | 只绕**本地布尔**那道门；`IsUnlock()`/`UnlockLevel` 在**服务端配置**里，未解锁时 UI 仍是 `Lock` 态 → 且它走**预设策略**不是最优解，**不如 (b)** |

⭐ **支持 (b) 可行的旁证**：服务端自己就允许「托管」= **机器替人出牌、无人类操作节奏**，说明服务端对"非人类点击节奏"没有检测；因此 (b) 的自动出牌在服务端视角与托管玩家无从区分。

> **[待验证]**：`GemsBattleTrustRenderer` 的托管执行体是一个嵌套 async 状态机（`_003C_003CExecute_003Eg__OnExecute_007C0_003Ed`），**ILSpy 未产出该结构体本体**（`GemsBattleTrustRenderer.cs:29-34` 的 DisplayClass 只剩两个字段）→ **托管自己究竟发不发 `SWAP_REQUEST`、还是只自动放技能，无法从反编译文本确认**。但形态 (b) 不依赖这一点，其可行性只取决于 §⑤ P3（服务端是否复核合法性）与 V1。
