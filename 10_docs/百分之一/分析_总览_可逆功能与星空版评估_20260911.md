## 一、一句话结论

**《百分之一》不是单机游戏，但它把战斗拆成了两套完全不同的权威模型 —— 这决定了「哪些功能真能做」。**

| 战斗引擎 | 覆盖玩法 | 权威性 | 常规战斗功能（秒杀/无敌/无限技能…） |
|---|---|---|---|
| **卡牌对战 TCG**（`Script.UI.CardBattle.*`） | 教学、日记剧情、娱乐场 PvE、**排位匹配超时回落的 AI 局** | **客户端本地模拟 → 客户端权威** | ✅ **全部可行** |
| **消除系四战斗**（`GemsBattle` / `DuelBattle` / `MatchMaster` / `MatchMultiple`） | **主线冒险推图**、挑战系列、公会挑战/Boss、委托、分数赛、宝藏狩猎、大师赛/排位、多重赛、决斗 | **独立战斗服务器权威** | ❌ 改本地无收益（只让画面错乱） |
| **巴别塔 BabelTowers** | 巴别塔玩法 | **无任何网络 Router → 纯单机** | ✅ 可行 |

> ⚠️ **最重要的一条纠偏**：**主线冒险推图走的是服务端权威的 `GemsBattle`**，所以「推图秒杀/无敌」在本版本**做不到**——和大多数人的直觉相反。
> 而**卡牌对战（TCG）是真正的本地模拟**，任务里举例的秒杀/无敌/伤害倍率/零CD/无限能量**在这里全部成立**。

**分界线（可操作化）**：看入口有没有调 `Helper.Owner.Battle.SearchBattleAsync(...)`（`Logics.Characters/CharacterBattle.cs`）或 `CardBattleRouter.StartBattleAsync(host, port, room, ...)`。
**调了 = 服务端权威；没调、只用 `AIAgent.Start(...)` 本地开打 = 客户端权威。**

### ⚠️ 对出包定位致命的一条实测

## 三、保护面（实测，结论：**软目标，无壳**）

| 层次 | 结论 |
|---|---|
| 加固壳 | **无**（单个明文 `classes.dex`，无百度/易盾/ACE/爱加密/KwProtect） |
| DEX / so 完整性校验 | **未发现**（Java 层无自研校验；so 无 qkcheck/toolChecker） |
| 反调试 | **未发现**（libil2cpp.so 无 ptrace/frida/xposed 关键字） |
| 反外挂 | 仅 **TapTap Themis-Lite**（`libthemis.so`，导出 4 个 JNI，回吐设备指纹 `tdid`/`gidData`）+ **移动安全联盟 OAID**。**非行为反作弊** |
| 客户端检测 | 全量搜 `cheat/detect/integrity/tamper/root/frida/xposed` **无启用项**（命中的 `DuelChallengeCheatCfg` 是**玩法道具**「作弊收集品」，不是反作弊） |
| 真正的约束 | **服务端对账 + 步进校验**：`PROOF_ID` 里 `PID_INVALID_STEP=2`、`PID_INVALID_SIGN=1039`、`PID_RECONCILIATION_FAILED=1025`、`PID_COMBAT_INVALID_*`、`PID_RECEIPT_*` |

**LZ4/容器/序列化（已更正 —— 先前判断有误）**：热更容器外层 = **LZ4 frame**，内层 = **.NET `BinaryFormatter` / MS-NRBF**（**不是 Sirenix Odin**）。

- **独立复核**（我复读字节 + 与《热更容器与出包链路》结论一致）：解压后头 17 字节 = MS-NRBF `SerializedStreamHeader{RootId=1, HeaderId=-1, Major=1, Minor=0}`；随后 `0C`=BinaryLibrary、`05`=ClassWithMembersAndTypes（根对象 `Script.Main.InitModules.HotUpdateDll`，成员 `_guid`/`_version`/`_assemblies`）、`06`=BinaryObjectString、**`0F`=ArraySinglePrimitive（PrimitiveType `02`=Byte → 即 `byte[]` 程序集载荷）**。
- 字段布局（`dump.cs:745522` / `:745621`）：`_guid` +0x10、`_version` +0x18、`_assemblies` +0x20 —— **不存在 `_vm` 字段**（先前 `_vm` 为误读，实为 `_version`）。
- **要区分两条序列化线**：**Sirenix Odin** 用于**资源/配置**（`Script.AssetManagers.Helpers/Reflector.cs` 的 `Serializer.Get<T>()`），与热更容器**不是同一个东西**。
- **MS-NRBF 无校验和、无绝对偏移、无总长度** → 替换程序集只需改 4 字节 `Length` + 载荷 → **容器可重建**；外层 LZ4 参数已实测字节级复现（`lz4 -3 -B4 -BD --no-frame-crc --content-size`，两个文件 `cmp` 全通过）。

### C 档 —— 全局倍速（跨模式，最实用且风险最低）

全源码 `grep timeScale` 22 处，战斗相关**全部是 `UnityEngine.Time.timeScale` 直接赋值，不存在逻辑帧步进/自定义逻辑时钟**。

| 模式 | 机制 | 位置 |
|---|---|---|
| GemsBattle（含推图/挑战/Boss/合作） | `Time.timeScale = _normalScale`；追赶时固定 `9f` | `GemsBattleSpeedRenderer.cs:304-337`（`:322` = 9f） |
| 宝藏 TreasureHunt | `Time.timeScale = Gears[TreasureSpeedIndex]` | `TreasureSpeedRenderer.cs:56-119` |
| 大师赛 MatchMaster | 只有追赶：`value ? 9f : 1f` | `MatchMasterSpeedRenderer.cs:24-109` |
| 卡牌 TCG PvP | 追赶：硬编码 `1.1/1.25/1.8/2.5/3.5f` | `PvPAgent.cs:81-114` |
| 卡牌 TCG 回放 | `ReplaySpeeds[level-1]` | `ReplayAgent.cs:60-66` |
| 巴别塔 | **无倍速** | — |

**三条关键推论**：
1. `Time.timeScale` **不影响服务端计时**（服务端时间底数是 `Time.realtimeSinceStartup`，`TimerManager.cs:256-273`）→ 倍速只省「看动画」的时间，**不会多给操作时间**，反而压缩真实反应时间。
2. 服务端中继模式的回合计时由**服务端时间**驱动（`elapsing/tagTimeAxis.cs:47-52, 88-97`），本地改不了。
3. AOT 侧唯一「一处生效、覆盖全模式」的原生点 = `UnityEngine.Time::set_timeScale`（RVA `0x43BB170`）。

→ **倍速是最推荐的第一功能**：易做、跨模式、纯表现层、服务端无副作用。

**（1）为什么「本地无敌/秒杀」在这里**不是*改了没用*，而是**根本没有可改的本地数值**（[实证]）：

| 证据 | 内容 |
|---|---|

## 六、星空版落地评估

### 6.1 关键约束

1. 玩法方法在 **HybridCLR 解释执行**的 `OnePercent.dll` 里 → **没有原生函数入口**，星光标准的「按 RVA hook 游戏方法」**对它们无效**；据工作区经验《经验_HybridCLR直写三铁律》，`MethodInfo.methodPointer` 上的 Dobby hook **命中率可能为 0**，且外部线程 `runtime_invoke` 热更方法会使解释器 SIGSEGV（**经验迁移，本目标未实测** → V9）。
2. 但 `libil2cpp.so` **导出 241 个 `il2cpp_*` API**（含 `mini_get_interp_callbacks`）→ **AOT 侧 hook 完全可行**。
3. 战斗挂点只能用 **IL 方法名**定位（`dump.cs` 无游戏代码）。

### 6.2 三条路线

| 路线 | 做法 | 能覆盖 | 成本/风险 |
|---|---|---|---|
| **① Native hook（星光标准）** | 注入 `libstarry_magic.so` + 悬浮菜单，用 `il2cpp_*` API 定位 AOT 方法；必要时 hook 解释器按方法名过滤 | **C 档倍速**（`Time::set_timeScale`，RVA 已有）、B5 帧率、以及所有 AOT 可达点；A/B 档的 IL 逻辑**需解释器级 hook**（进阶） | 低风险、与现有框架一致；**覆盖不到 TCG 战斗内核** |
| **② IL 层改（改 OnePercent.dll）** | 反编译→改 C#/IL→**改 MS-NRBF 里 `ArraySinglePrimitive` 的 `Length` + 载荷**→外层按 `lz4 -3 -B4 -BD --no-frame-crc --content-size` 重压→外科 zip→签名 | **A 档全部（秒杀/无敌/伤害倍率/零CD/无限能量/自动战斗）+ B 档** | ✅ **容器确认可重建**（MS-NRBF 无校验和/无绝对偏移/无总长度）；但有**两个必须先解决的门槛**（见下方「路线②的决定性约束」） |
| **③ 数据层改（DBreeze）** | 改本地解包出的 DBreeze 库（`CharacterData`/`GameUtils` 等） | 倍速档位、托管开关、帧率等**纯本地字段** | 收益有限；服务端下发会覆盖关键配置 |

**推荐路线**：
- **第一阶段（低风险、可快速验证）**：路线 ① + ③ —— 先做 **倍速（C 档）**、**倍速档位解锁**、**跳过引导/教学**、**去公告**、**帧率**。
- **第二阶段（收益最高）**：路线 ② —— 容器已确认可重建，但必须先解决下面的两个门槛；届时可落 **A 档 TCG 全套**（无敌/秒杀/伤害倍率/零CD/无限能量/自动战斗）。
- ③ 不作为主线。

#### ⚠️ 路线②的决定性约束（本目标特有，**不解决就会被官方热更静默覆盖**）

《热更容器与出包链路》用 capstone/IDA 反汇编 `HotUpdateDll.<Load>d__9.MoveNext`（VA `0x38F7A98` / file `0x38F3A98`）得到加载顺序：

1. **无条件先读包内 origin**（StreamingAssets，经 `UnityWebRequest`）；
2. **cache 优先规则**：若 `cache._guid == origin._guid` → **用 cache**；
3. **版本检查**：若服务端下发的 `version ≠ 0` 且 `≠ 选中容器的 _version` → `DownloadNewest(serverUrl, version, 选中._version, _resource)`；
4. 下载成功后**覆盖 `_assemblies`/`_version`、`BfSerialize` 回写 cache**，再 `Assembly.Load`；
5. ⚠️ **下载失败不回退 origin**：`DownloadCode` 跳转表（VA `0xF7D5D0`）里 `1/2/4/5/6` 都直接 `onResult(错误码)` 返回、**不加载任何程序集**（只有 `FileNotFind=3` 容忍）。

**由此得出两条硬约束**：

| 约束 | 后果 | 应对 |
|---|---|---|
| **A. 必须对齐 `_version`** | 若我们改了 `OnePercent.dll` 但容器 `_version` 与服务端版本不符 → 触发下载 → **官方 dll 覆盖我们的改动**，Mod 静默失效 | 把容器 `_version` 设为服务端**当前**热更版本；且**接受"官方一热更就要重出包"的维护成本** |
| **B. 必须改 `_guid`（否则改不动）** | 若保留官方 `_guid`，任何**已存在的官方 cache**（`cache._guid == origin._guid`）都会**优先于 origin** → 我们的修改根本不生效 | 给修改后的容器设一个**新的 `_guid`**，使 cache 不匹配 → 选中 origin |
| **C. 离线风险（Mod 引入的新故障模式）** | 若 `_version` 落后于服务端且**设备离线** → 下载失败 → 按第 5 条**不回退** → **热更程序集完全不加载、游戏起不来** | ⭐ **推荐做法：用路线① 在 AOT 侧 hook `HotUpdateDll.<Load>` / `AotMetadataDll.Load`（VA `0x38F653C`/`0x38F7730`，**AOT 可达**）强制「只读 origin、永不下载」** —— 这样路线② 就变持久且安全，同时消除离线故障模式 |

> 这形成一个**A+B 组合拳**：**B（native hook）负责"守住加载器、锁死 origin"**，**A（IL 层改）负责"注入功能"**。单独用 A 会在官方热更或离线时出问题；单独用 B 够不到解释执行的热更方法。

**另需注意**（[待验证]）：`_version` 8 字节的确切语义、`_cacheFilePath`/`_originFilePath` 的路径字面量取值、`_resTag`/`_resource` 的取值，以及重建后的容器能否被 `BfDeserialize` 正常接受 —— 见《热更容器与出包链路》§⑦ 的 V1–V13。

## 七、红线与边界

- 本作**有真实玩家生态（排位/联赛/公会）**。**A15（TCG 胜负替换）+ 排位 AI 分支刷分**会影响其他玩家与排行，属工作区「影响其他账户」红线，**须先取得明确授权**，且**不建议进入交付菜单**。
- 未取得授权前：不改游戏文件、不出包、不装机、不启动游戏。
- 本地改动只影响本机表现；但**异常回传**（`HandleNativeException`）会把 Mod 引发的异常写进游戏日志 → 实现上必须保证**不抛异常、不刷日志**。
