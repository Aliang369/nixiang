## ③ 登录签名链路

### 3.1 核心结论
[实证] **本版本登录不走 HTTP 签名接口**。`URL.LoginAccount(url, account, time, sign)`（`Protocol.HTTP/URL.cs:24`，形状 `/wooway/login/{channel}/{account}/{time}/{sign}`）在全仓 **0 个调用点**（`grep -rn "URL\.LoginAccount(" --include=*.cs .` 仅命中定义本身）。

[实证] 实际登录协议是 **原始 TCP 长连接 + 自研二进制 `Message`/`MESSAGE_ID` 协议**，四步握手：
| 步 | 方向 | 消息 | 字段 | 证据 |
|---|---|---|---|---|
| 1 | C→S | `MID_VERSION_VERIFY_REQUEST` | `1u, 0u, (byte)0, "wooway"(写死), 1u, 0u, 0u` | `Logics.Routers/GameRouter.cs:405-412` |
| 2 | S→C | `VerVerifyType`（`VR_SUCCEEDED` / `VR_INVALID_VERSION_LOW` / 其他=维护） | — | `GameRouter.cs:371-382` |
| 3 | C→S | `MID_MEMBER_LOGIN_REQUEST` | `account`, `password` | `GameRouter.cs:384-386` |
| 4 | S→C | `PROOF_ID` + `passToken` + `gameServerHost` + `gameServerPort` | 成功后 `ConnectAsync(host,port)` | `GameRouter.cs:492-495, 523-524` |
| 5 | C→S | `MID_ACCOUNT_AUTHORIZE_REQUEST` | `""`, `ChannelManager.NativeChannel`, `""`, `""`, `account`, `passToken` | `GameRouter.cs:428-434` |
| 6 | S→C | `ownerName(u64)` + `FullUpdate 字节流` + 聊天服 host/port | 落地 `LoginAccount/_accountToken` | `GameRouter.cs:458-467, 546-550` |

### 3.2 sign 计算实现（除登录外唯一在用的 sign）
[实证] 全仓 `Md5` 相关签名只有一处与"战斗结果"相关：
```
Script.Config.Script.Card/BattleInitData.cs:58
public string InstanceSign => Convert.ToBase64String($"{InstanceId}{TimeSign}".ToRawMd5());
```
- `ToRawMd5` 定义：`Extensions/StringExtension.cs:125-130` → `MD5.Create().ComputeHash(Encoding.UTF8.GetBytes(content))`（**标准 MD5，无盐、无 key**）
- `InstanceId`：**客户端配置/常量**（如 `DuelCfg.RankInstanceId`，`Script.Config.Script/DuelCfg.cs:69`）
- `TimeSign`：**服务端在 `Launch` 时下发**（`CharacterInstanceLog.LaunchAsync` → `MID_CHARACTER_INSTANCE_LOG_LAUNCH_TUTORIAL_REQUEST(1314)`，响应取 `long`；`Logics.Characters/CharacterInstanceLog.cs:46-67, 386-397`）

### 3.3 改包后能否登录？
[实证] **能，且不需要复现任何签名**。理由：
1. 登录走 TCP `Message` 协议，`account`+`password` 直传，**无 time/sign 参与**（`GameRouter.cs:384-386`）。
2. `URL.LoginAccount`（唯一含 `time`+`sign` 的登录 HTTP 接口）在本版本是死代码。
3. `MID_VERSION_VERIFY_REQUEST` 的渠道字段是**硬编码字符串 `"wooway"`**（`GameRouter.cs:409`），与 APK 签名/包名无关。
4. 无 DEX/so 完整性校验（前提 1），`Base64` 的 `InstanceSign` 亦无包绑定。

[待验证] `MID_ACCOUNT_AUTHORIZE_REQUEST` 中 `ChannelManager.NativeChannel` 是否为可选第三方渠道参数——若为 `taptap` 且服务端校验 TapSDK 会话，则 TapTap 渠道账号可能受影响；但 `"wooway"` 自有账号渠道不受影响。

### 6.4 影响评估

## ⑦ 数值安全线与量级建议

> 定位说明：本节只做**风险识别与影响评估**——说明"服务端能观测到什么、越过哪条线会被看见"，不提供任何绕过/调参手法。

### 7.1 消除系 4 种（服务端权威）→ **明确不建议做数值改动**

**判定依据（[实证]，与《战斗系统_可逆功能清单_20260911.md》§2.3 一致）**
1. 客户端只发**意图**：`SWAP(round,src,dst)`、`CAST_SPELL(round,src,dst)`、`SPEND_ENERGY(round)`、`DRAW_CARD(sequence,card)`、`COST_ITEM`（§4.C 表；证据：`Logics.GemsBattles/GemsBattle.cs:982-1056` 等）
2. 过程与结果由服务端下发：`CBattleCommandArray`（36 种 `BC_*`）+ `MID_CHARACTER_BATTLE_FINISHED(1144)` 只带一个 `bool`
3. `_round` 由客户端回传但**服务端持权威轮次**（`MID_CHARACTER_BATTLE_ROUND_START/ROUND_QUERY` 1134/1135）

**为什么"不建议"**
- 本地改血量/伤害/分数 → 服务端下一帧用 `BC_UNIT_REFRESH` / `BC_SYNC_BOARD` / `BC_STATISTICS` / `BC_SYNC_STATE` 覆盖 → **本地表现立刻错乱，且不改变结算**
- 改 `_round` 或坐标越权 → 服务端可判非法（`PID_COMBAT_INVALID_*` 系列存在于 `NetWorkMessage/PROOF_ID.cs`）
- 唯一"可见即所得"的客户端行为是**认输**（`SURRENDER_REQUEST` 1140）——这是服务端允许的合法输入

**结论**：安全线 = **零变动**。任何数值改动都落在服务端权威覆盖区内。

### 7.2 卡牌 TCG（客户端权威）→ 协议层不可见，风险在统计与结算面

#### 7.2.1 服务端的可观测侧信道（[实证]/[待验证] 混合）
| 侧信道 | 服务端是否持有 | 证据 | 说明 |
|---|---|---|---|
| `InstanceId` + `result` + `sign` | **是**（唯一上报体） | `CharacterInstanceLog.cs:407-409` | sign 不含 result → 无法验伪 |
| `Launch` 与 `Finish` 的到达时刻 | **是**（两次报文时间戳） | `CharacterInstanceLog.cs:46`(1314) / `:406`(1316) | 可算"通关耗时" [待验证] 未见客户端耗时字段，需服务端自行计时 |
| 会话/累计胜负对局数 + `Score` | **是**（字段已定义） | `NetMsg.Card/GetWinProbabilityP.cs:8-18`（`IsNewSession / SessionBattle / SessionWin / TotalBattle / TotalWin / Score`） | 服务端已在做胜率记账 |
| 同一 `InstanceId` 的重复 Finish | **是**（服务端通过 `FullUpdate` 下发通过表，`_passed` 读取在 `CharacterInstanceLog.cs:451-456`） | 客户端也会本地 `_passed.Add`，`CharacterInstanceLog.cs:411-413` | 重复上报可作为异常信号 |
| 奖励发放速率 | **是**（奖励走服务端 `TAKE_REWARD` 1312） | `CharacterInstanceLog.cs` `TakeRewardAsync` | 结算在服务端 |
| 操作流水 / 回合数 / 伤害 | **否**（客户端不上报） | 上报体仅 3 字段 | `NetMsg.Card.OperationRecord` + `BattleEndQ(905)` 全仓 0 调用 → 本版本无战斗日志上行 |
| 联机局的败者指认 | **是（双侧交叉）** | `PvPAgent.cs:165-167` | 双方 `LosterId` 需自洽 |

#### 7.2.2 风险量级
| 场景 | 服务端可观测量 | 风险量级 |
|---|---|---|
| 单次把 AI 局 `result` 由 `-1` 改为 `1` | 协议层无差异；耗时不变 | **低**（协议不可见） |
| 同一 `InstanceId` 反复 Finish 取奖 | 重复实例上报 + 奖励频率 | **中**（结算面异常） |
| 短时间大量通关（对局数陡增、耗时趋近 0） | 耗时分布、日通关量、`SessionBattle/TotalBattle` | **高**（统计面明显偏离） |
| 胜率长期接近 100%（`SessionWin/TotalWin`、`Score`） | 胜率记账 | **高** |
| 任务/教学类关卡（`TutorialAgent`/`DiaryTaskAgent`）被批量完成 | 完成速率 vs 正常节奏 | **中高** |

> 注：`Score` 的语义未在客户端出现（客户端 0 调用 `GetWinProbability*`）→ **无法从客户端推断其阈值口径**，属最大不确定性。

#### 7.2.3 安全线建议
1. **保持"耗时"落在该 `InstanceId` 的正常区间**：服务端同时收到 `Launch(1314)` 与 `Finish(1316)`，零耗时/超短耗时是最容易被抓的单一信号。
2. **控制单位时间的 `Finish` 次数与 `InstanceId` 去重**：避免同一实例重复 Finish、避免单账号在一段时间内通关数远超正常。
3. **胜率保持在正常区间**：`SessionBattle/SessionWin/TotalBattle/TotalWin` 已被服务端记账；`SessionBattle` 很小而 `SessionWin==SessionBattle` 是最典型的异常组合。
4. **优先选择"有正常耗时下限"的玩法**：有交互/动画/回合的关卡天然带耗时，风险低于可瞬间结算的关卡。
5. **不要把"结果上报"与"本地奖励"混淆**：奖励由服务端在 `TAKE_REWARD(1312)` 时发放，绕过上报直接改本地存档不会改变服务端奖励权威（见 §7.4）。

### 7.3 联机 TCG（半服务端）→ 不建议
- `MID_TCG_BATTLE_FINISH_REQUEST(5020)` 的 sign 只覆盖 `GetBeginChoseTime()`，但**服务端同时持有对手的同一局上报**（`PvPAgent.cs:165-167`）。
- 单方面改 `LosterId` → 两份上报矛盾 → 争议/异常判定。
- 技能结算篡改（本地模拟）→ 服务端只中继，**无法验证**，但对手客户端会算出不同结果 → **表现不同步会暴露**（对手侧可见）。
- 安全线：**认输/求和是唯一的合法"改结果"通道**。
