## ① 结论摘要

1. **整体架构是「服务端权威 + 客户端乐观回显」**。所有经济数值（货币、体力、卡牌拥有、箱子、商店、通行证、成就、邮件奖励）都通过 `CharacterPropertyBase.FullUpdate/StepUpdate` 从服务端下发覆盖；客户端只有极少量「乐观预扣 + 失败回滚」的本地写入（全仓仅 3 处）。
2. **真正可改且有效（客户端权威、无服务端副作用）的经济类功能只有一类**：`Script.DataBases.Tables.CharacterData` 这张**纯本地 DBreeze 表**里的 13 个字段 —— 其中真正有玩法收益的是 **`GemsBattleTrust`/`TreasureTrust`（战斗托管）、`GemsBattleSpeedIndex`/`TreasureSpeedIndex`（战斗倍速）、`GemsBattleBkgIndex`（战斗背景）**，以及体力消耗开关 `DuelPowerCost`、提示开关 `ShowPowerCost`、教学标记若干。它们不进网络、服务器不知情、也不会被 `FullUpdate` 覆盖。
3. **"免广告"确实存在，但收益极小且性质特殊**：协议层有完整激励视频三件套（`MESSAGE_ID` 1328–1333），但**客户端没有任何广告 SDK 调用、没有任何播放等待**——token 是客户端用服务端下发数值算 `MD5` 得到的（`ToRawMd5`）。也就是说"广告"在本作里**本来就是纯协议占位、本来就是秒领**，不存在"30 秒可跳过"。唯一相邻功能是绕过每日次数，但由服务端 quota 判定 → **属自欺型**。
4. **内购无法本地伪造发货**：下单只传 `item_name`（商品 key）不含价格；`sign`/`prepayid`/`nonce`/`timestamp` 全由服务端签发；支付 SDK 回调只决定"要不要去轮询服务端回执"；发货的唯一判据是服务端回执里是否出现该 `order_id`。客户端无最终判定权、无本地发货路径。
5. **抽卡/开箱随机数 100% 在服务端**：抽卡走商店交易（`Store.BuyAsync/TradeAsync`，只传 store/goods key），开箱走 `CharacterChests.*`（只传 offset），概率只是配置表里的展示数值。全仓在抽卡/开箱/礼包相关模块内 **`Random` 使用次数为 0**。
6. **拥有关系全部是服务端镜像**：卡牌 `_cards`/`owned`、消耗品 `_consumables`、商店 `_stores`、通行证 `_passport.payer`、成就、图鉴、箱子全部来自 `FullUpdate/StepUpdate`。**实体卡扫码解锁**（`ScanCardAsync` → `MID_CHARACTER_CARDS_BIND_ENTITY_REQUEST`）由服务端判定一次性绑定，客户端只播解锁动画。
7. **兑换码 / 邮件 / 签到 / 任务奖励全部服务端发奖**，客户端只提交一个字符串或一个 id，然后按返回的 `PROOF_ID` 展示。无本地直接发奖路径。
8. **自欺型假象的清单很长**：改内存里的货币/体力、改本地 `_stores` 让商店"显示还有货"、改通行证 `payer`/`flag_paid`、改广告次数缓存、改每日免费抽次数缓存、伪造 `LosterId` 之前的本地胜负判定——都会被服务端重新校验或下一次 `StepUpdate` 覆盖。
9. **唯一值得继续挖的"待验证"点**（均为服务端校验强度问题，客户端代码无法结论）：① PvP/排位 TCG 的 `LosterId` 由客户端上报；② 通行证付费轨 `PASSPORT_TYPE.PT_PAID` 由客户端以参数发送；③ 实体卡扫码 token 由客户端提交；④ 邮件领取只提交 `order` 字符串。

## ④ 内购与广告链路

### 4.1 内购全链路（**客户端无最终判定权，无法伪造已支付**）

```
[UI] RechargePanel / SupplyPacks / SignCard / CardPool.PurchaseDraw
  └ PurchaseManager.Instance.Buy(commodityKey, onOrderSucceed)      ← 只传商品 key
        ├ 本地支付锁检查：Database.ReadPayLockRecord(Name, commodity)
        │   5 分钟内同商品且未 UnLock → 直接拒绝（PurchaseManager.cs:1064-1069）
        ├ 未成年人本地检查：TeenagerGuard.GetAge() < 18 → 只弹提示（:335-338）
        └ 下单（纯透传，无价格、无签名）
             ├ 支付宝 URL.GetAlipayOrder(...)  → /alipay/submit_order?account&item_name&count&comment&pkgname
             ├ 微信   URL.GetWxOrder(...)      → /wxpay/submit_order?...
             ├ 富友   URL.GetFyOrder(...)      → /fpay_v2/submit_order?...
             └ 通用   URL.GetPayOrder(...)     → /order/submit?...
                 (Protocol.HTTP/URL.cs:115-132)
  └ 服务端应答 JSON 解析（PurchaseManager.cs:406-412 / 823-832）
       order_id / sale_off / original_price / actual_price / detail
       微信额外下发：prepayid / nonce / timestamp / sign
  └ 调起客户端 SDK（AndroidJavaClass，不是游戏内发货逻辑）
       ├ 微信 Plugins.WxPay/WxPayHelper.cs:164-173
       │    com.woowaygames.onepercent.Payer.sendReq(activity,"1529124201",prepayId,"Sign=WXPay",nonceStr,timeStamp,sign)
       │    初始化 :259 com.woowaygames.onepercent.Payer.init("wxd13e85837da249a0", listener)
       ├ 支付宝 Plugins.Alipay/AlipayHelper.cs:93-96  com.wooway.alipay.AlipayUtil.payV2(orderInfo, activity, listener)
       └ 富友 Plugins.FyPay/FyPayHelper.cs:14-23    com.wooway.fypay.FyPayUtil.send(scheme, activity)
  └ SDK 回调（只决定"要不要去轮询服务端"）
       微信 WxPayRspCode.Ok / 支付宝 Status=="9000" → 进入轮询
  └ 轮询服务端回执：Helper.Owner.Common.RefreshOrderAsync()
       → MID_CHARACTER_ORDER_REFRESH（CharacterCommon.cs:1573,1963）
       → 判据：receipts.Any(e => e.record.index == orderId)
         （PurchaseManager.cs:532 / 559 / 645）
  └ 命中才 _onOrderSucceed?.Invoke()  ← 该回调只做 UI 刷新
       GoldRechargeWidget.cs:218-227 / MonthCardPackWidget.cs:219-228 实测只调 Refresh()
  └ 另有一路：服务端主动推送 PurchaseResult
       CharacterCommon.TryDequePurchase → GeneralHintBox.CheckAppendPurchaseHint（:92-140）
       ├ PID_SUCCEED            → 提示"购买成功" + 奖励明细
       ├ PID_INSUFFICIENT_SPACE → 提示"成功但背包满"，由服务端后续补发
       └ 同时 Database.UpdatePayLockRecord(Name, token, unlock:true)（:110）解开本地支付锁
```

**结论（[实证]）**：
- 客户端**只做透传**：`item_name` 是商品 key，**不含价格**；`sign` 全部由服务端签发（微信 `sign` 取自服务端 JSON `result.sign`，`PurchaseManager.cs:832`），客户端不参与签名。→ 与前提④一致。
- **客户端对"是否发货"没有任何判定权**：SDK 回调成功只意味着"可以开始轮询"；`RefreshOrderAsync` 命中回执才是成功；真正的奖励入账来自服务端。
- **无法伪造"已支付"获得商品**：本地伪造 `CInnerPurchaseReceipt` 或强制 `_succeed=true` 只能让 UI 弹一次"购买成功"提示并调用一个只做 `Refresh()` 的回调（`GoldRechargeWidget.cs:224`、`MonthCardPackWidget.cs:225`），**不产生任何资源**。`_onOrderSucceed` 全仓实现体均为 UI 刷新。
- 本地 `PayLockRecord_{Name}` 只是**防重复下单的本地节流**，改它最多让你能再发一次下单请求，不改变服务端结算。

### 4.3 广告/激励视频链路 —— **为何"没有 SDK"却"有广告"**

**协议层三件套**（`NetWorkMessage/MESSAGE_ID.cs:335-340`）[实证]：

```
MID_CHARACTER_ADVERTISEMENT_LAUNCH_REQUEST  = 1328
MID_CHARACTER_ADVERTISEMENT_LAUNCH_RESPOND  = 1329
MID_CHARACTER_ADVERTISEMENT_FINISH_REQUEST  = 1330
MID_CHARACTER_ADVERTISEMENT_FINISH_RESPOND  = 1331
MID_CHARACTER_ADVERTISEMENT_REMAIN_REQUEST  = 1332
MID_CHARACTER_ADVERTISEMENT_REMAIN_RESPOND  = 1333
```

**客户端 API**（`Logics.Characters/CharacterCommon.cs`）[实证]：

| API | 发送 | 返回 | 行号 |
|---|---|---|---|
| `GetAdRemainAsync(adTag)` | `REMAIN_REQUEST`（写 `adTag`） | `uint?` 今日剩余次数 | `:1918`；发送 `:290` |
| `LaunchAdAsync(adTag)` | `LAUNCH_REQUEST`（写 `adTag`） | `long?` 服务端下发的数值 | `:1933`；发送 `:1059`；只做 `ReadI64` 后立刻返回 `:1081-1082` |
| `FinishAdAsync(adTag, token)` | `FINISH_REQUEST`（写 `adTag` + `token`） | `bool` 是否发放 | `:1947`；发送 `:186-188` |

**关键：`token` 由客户端从服务端返回值算出，与任何广告 SDK 无关** [实证]：

```csharp
// Script.UI.Chat.FriendsCircle/FriendsCircle.cs:312-318
long? num2 = await common.LaunchAdAsync(cTag);
if (!num2.HasValue) return;
string token = Convert.ToBase64String($"{num2.Value}".ToRawMd5());  // Base64(MD5(str(long)))
if (await common.FinishAdAsync(cTag, token)) { ...发帖... }
```

`ToRawMd5` 实现：`Extensions/StringExtension.cs:125-130`（`MD5.Create().ComputeHash(UTF8(str))`，无盐、无密钥）。

**全部 3 个调用点**（无第四处）[实证]：

| 文件 | 流程 | 行号 |
|---|---|---|
| `Script.UI.Chat.FriendsCircle/FriendsCircle.cs` | 发动态（`OnSendCircleMsg`）：`GetAdRemain`→`LaunchAd`→算 token→`FinishAd`→发帖 | `:241, 312, 317, 318` |
| `Script.UI.Buddy.Circle/BuddyCircleWidget.cs` | 发帖（`OnSendClick`）：同上 | `:97, 129, 130, 190` |
| `Script.UI.Buddy.Circle/BuddyCircleWidget.cs` | 发表情帖（`OnSendEmoji`）：同上 | `:319, 357, 373, 374` |

**没有 SDK、没有播放、没有等待** [实证]：`LaunchAdAsync` 的 `MoveNext`（`:1034-1094`）全程只有一次 `SendAsync` + `ReadI64`，**无 `Delay`、无 Panel、无 VideoPlayer、无 UI 调用**；三个调用点在拿到返回值后立刻算 token、立刻 `FinishAd`，中间无停顿。

**奖励内容**：`ChatCfg.SendCircleRwdBattery`（电量/体力），以 `MsgBoxRwdType.BatteryRwd` 提示（`FriendsCircle.cs:322`、`BuddyCircleWidget.cs:380`）；另外 `PowerWidget` 只读展示 `HomePageCfg.AdBatteryTag` 的剩余次数（`PowerWidget.cs:311`，判空与展示逻辑 `:307-333`），**没有实际的"看广告得体力"按钮**。

**每日次数限制**：`GetAdRemainAsync` 用 `_adTimesCaches`（`AdTimesCache{Times,Timer}`，`CharacterCommon.cs:23-28`）缓存 60 秒（`AdTimesQueryInterval = 60000L`，`:1789`）；返回 0 时客户端直接提示 `CircleTimesLimit`（`FriendsCircle.cs:246-250`）。

> **"免广告"在本作的准确定性（重要）**：
> - **协议层三件套存在** [实证]；
> - **无 SDK、无播放、无等待** [实证] → **"看广告"本来就是秒领，没有可跳过之物**；
> - 故「免广告」在本作**不是一个有用户可感收益的功能**（不存在"跳过 30 秒"）；
> - 唯一相邻的可做项是**绕过每日次数上限**：本地把 `Times` 改大只会让客户端继续发 `LaunchAd`，服务端按自己的 quota 判并会拒绝 → **属自欺型（[仅本地假象]）**；
> - 真实可做而"边际收益"极小的，是 **Hook `LaunchAd/FinishAd` 以实现零延迟连发**（仍需服务端 quota 放行），收益仅为"省下 0 秒"+ 操作自动化。

### 4.4 为何"无广告 SDK"的判定仍然成立（与前提③不矛盾）

- dex 内无穿山甲/优量汇/Unity Ads/TapAD/AdMob，代码内无「广告/激励」中文字样 —— 这两点复核后**仍然成立**。
- 但游戏**确实有激励视频业务语义**，它用纯协议实现（服务端令牌交换 + 客户端 MD5）。因此正确的表述是：
  **"无广告 SDK —— 成立"**，但 **"无广告需求 —— 不成立"**。
- 复现路径：[实证] `grep -rn "ADVERTISEMENT" NetWorkMessage/MESSAGE_ID.cs` → 6 条；`grep -rn "LaunchAdAsync" --include=*.cs .` → 恰好 3 个调用点。

### 5.2 "自欺型假象"的共同特征

所有假象都符合同一模式：**客户端有一个本地门槛函数 → 改它能过门槛 → 但真正动作是一个 `SendAsync` → 服务端重新裁决 → 失败则客户端提示或回滚**。

典型三连：
1. 门槛：`SportPanel.cs:287` `Stamina < PowerCost` → 本地改体力可变 true 分支
2. 动作：`SportPanel.cs:293` `InstanceLog.LaunchAsync(instanceId)` → 服务端扣体力校验
3. 结果：服务端拒绝 → `FlyTip.Show("战斗启动失败")` 或 `PID_*` 错误分支

同类：`AdventureUtil.cs:539/675/787/957`、`CardPoolWidget.cs:306-325`、`CharacterPassport.cs:80-93`、`CharacterChests.cs:760` ↔ `LeagueChestWidget.cs:190`。

**唯一例外**是 §3.1 的 DBreeze 本地表项 —— 它们**没有第 2 步**（不发网络），所以是真有效。

### 5.3 一个需要显式说明的边界

`CharacterCard._cards`（卡牌 `count/owned/grade/cover`）虽是服务端镜像，但 **PvE 人机对战完全在客户端模拟**（`AIAgent.Dispatch` 只 `Execute(_driver)`，`AIAgent.cs:178-181`），所以"改本地卡池 → 在 PvE 里用出来"在**单机过程内**可见。但这**不是**经济挂钩：卡牌入库、成长、分解、卡组保存全部走服务端（`CharacterCard.cs:611,643,657,681,714,726,740`），退出/重登即恢复。故仍归入 §3.2 的 **[仅本地假象]**，并特别标注"PvE 局内可见，无持久收益"。
