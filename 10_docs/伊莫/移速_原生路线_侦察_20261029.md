## 1. 第一道障：`global-metadata.dat` 加密 —— 实际形态与破解

### 1.1 观察

| 来源 | 首 16 字节 | 结论 |
|---|---|---|
| APK `assets/bin/Data/Managed/Metadata/global-metadata.dat` | `48 54 50 58 A4 7B C7 01 12 9B C7 1B …` | 密文（`HTPX` 头） |
| 设备 `files/il2cpp/Metadata/global-metadata.dat`（运行时落盘那份） | 同上 | **同样是密文**（不是解密后的副本） |
| `E:\starry_build\yimo_il2cpp\global-metadata.dat` | 同上 | 同样是密文 |

文件长度恒为 **29,850,532 B**。

### 1.2 关键事实：会在内存里**原地解密**，且只改写头部两个字段

`/proc/self/maps` 里能看到这个文件被 mmap 成一块 rw：
```
7be1f967f000-7be1fb2f7000 rw-p 00000000 08:22 786488 /storage/emulated/0/Android/data/com.x.yimoo.official/files/il2cpp/Metadata/global-metadata.dat
```
把这块（页对齐 29,851,648 B）整体落盘后对比：

| 偏移 | 磁盘文件（密文） | 内存（明文） |
|---|---|---|
| `+0x00` | `48 54 50 58`（`HTPX`） | 同（未加密，是易盾的 tag） |
| `+0x04` | `A4 7B C7 01` | 同 = 0x01C77BA4 = **29,850,532 = 文件大小** |
| `+0x08` 起 | `12 9B C7 1B …`（随机） | `00 01 00 00 28 C6 05 00 …` = **合法 IL2CPP 头部** |

即：**只有 `sanity`（0xFAB11BAF → `"HTPX"`）与 `version`（→文件长度）被改写**，其余原地解密。头部此后是一串完全自洽的 `(offset,size)` 对：

```
+0x08 = 0x00000100 (256)      ← 第一张表紧随 0x100 的头之后
+0x0c = 0x0005c628 (378408)   ← +0x10 = 0x100+0x5c628 = 0x5c728 ✓
…                              （每一对的 offset 都等于上一对 offset+size）
+0xf8 = 0x01c73f70
+0xfc = 0x00003c34 (15412)    → 0x1c73f70+15412 = 0x1c77ba4 = 29,850,532 = 文件末尾 ✓
```

**31 组 (offset,size)**，且各组 size 能被记录大小整除，这正是 v29 头部的形状：

```
methods   7848720/36 = 218020 整    parameters 2646600/12 = 220550 整
fields    2079876/12 = 173323 整    typeDefs   2551824/88 =  28998 整
images       5520/40 =    138 整    assemblies   8832/64 =    138 整
```

### 1.3 产出

```
E:\starry_build\yimo_il2cpp\gm_v29.dat     ← sanity/version 改回 0xFAB11BAF + 29
```
直接喂 `Il2CppDumper` 可以过 metadata 初始化：
```
Initializing metadata...
Metadata Version: 29
Initializing il2cpp file...
Applying relocations...
Il2Cpp Version: 29
Searching...
CodeRegistration : 0
ERROR: No symbol is detected          ← 卡在这里（易盾抹了符号与 codegen 注册特征）
```
⇒ **`Il2CppDumper` 走不通，但不是 metadata 的问题**，是 CodeRegistration 自动搜索失败。已改走自建链路（§4）。

### 1.4 两个额外坑（非常重要，后续任何人复用都别再踩）

1. **这份 metadata 里 `nameIndex` 是「串数据块内的直接偏移」，不是索引**。
   串数据块 = metadata 内 `0x1aa77c` 起、**6,052,452 B，内容 100% 是 ASCII 串**（逐 1 MB 窗口熵均 4~6，全段可读）。
   ⇒ `name = cstr(0x1aa77c + nameIndex)`；`methodIndex = (token & 0xFFFFFF) - 1`（模块内 RID，token 表号恒 `0x06`）。
2. **字符串索引表被从文件里剥掉了**，只在运行时内存（BSS）里存在。
   验证：对整个 metadata 文件做"u32 值是否落在合法串起点"的全局扫描，最长连续段 = 0 条；逐节区扫描，没有任何一节像索引表（合法率最高 59.8%，属于巧合）。
   运行时在 **BSS `0x40002e57f924`** 附近能找到 39 万条连续"合法串偏移"⇒ 索引表在那儿。但因为 `nameIndex` 已是直接偏移，**这张表其实用不上**。

## 2. 采集器改造（`#if MOD_DIAG_LUA` 段内，正式包零代码）

改造目标：把"静默无输出"变成"可知"。逐项：

| 项 | 改法 |
|---|---|
| 入口心跳 | 线程一进来就 `DLOG("meta worker ENTER …")`，成功失败都打 |
| fopen 失败 | `YimoWriteBuf` / maps 打开失败都带 `errno` 落日志，不再静默 `return` |
| 过滤区块统计 | 每轮按原因分类计数：`skip{nonRead=…,small=…,huge=…}`、`eligible=…`、`rw>=8MB=…` |
| 扫描预算 | 魔数扫描每轮上限 256 MB，扫不完打 `skippedBudget=` |
| **命令文件通道** | `meta_cmd.txt`：`dump/maps/findstr/findval/ptrscan/strtab/big/scan` 八个动词，**不用重装就能让进程按需落盘/搜索**（本报告 90% 的取证都靠它） |
| 名字缓冲 | `YimoRegion.name` 80→256（80 会把 `…/lib/arm64/libil2cpp.so` 截断，导致 `strstr(name,"libil2cpp")` 永不命中，实测踩过） |

### 2.1 每轮日志判据原文（改造后第一轮）

```
StarryDiag: meta worker ENTER —— 采集线程已启动（改造版，可观测）
StarryDiag: meta round #1 begin (pid up, tid tick)
StarryDiag: meta round #1: maps=3821 readable=3086/3821 (5292 MB) eligible=478 skip{nonRead=735,small=2606,huge=2} rw>=8MB=25 img=0xffffffffffffffff..0x0
StarryDiag: meta mapsnap -> /sdcard/.../files/meta_maps.txt (315449 B)
StarryDiag: meta round #1 scan: used=256MB regions=1 skippedBudget=479 cand=0
StarryDiag: meta big cand #2 region=0x7be1f967f000..0x7be1fb2f7000 len=29851648 name=/storage/emulated/0/Android/data/com.x.yimoo.official/files/il2cpp/Metadata/glo
StarryDiag: meta cmd: 无 /sdcard/.../meta_cmd.txt（首装正常态）
```
（`img=0xffff…` 就是 §2 第 6 项的 80 字节截断 bug，修好后变成 `img=0x400023800000..0x7be0b0000000`。）

### 2.2 为什么前两版"完全无输出"

- 上一版把尺寸过滤放宽后，`while(…){ regions… }` 里第一个 ≥16 MB 的块是 384 MB 的 dalvik 堆，8 字节步长扫完要很久，且**函数只在结束时打一行日志** ⇒ 表现为"线程没起来"。
- 现在的版本：入口先打、每轮分类统计、扫描有预算、按区打进度，**任何静默 return 都不存在**。

## 3. 设备/环境限制（影响方法论，不是本次任务独有）

1. 模拟器是 **x86_64 + houdini**（ARM64 so 由 houdini 转译执行）。`/system/vendor/lib64/libhoudini.so` 会崩并 dump 寄存器。
2. 进程内 **`pread("/proc/self/mem")` 返回 EACCES（errno=13）**，日志原文：
   `meta reader: pread 不可用（fd=-1 got=0 errno=13）→ 退回直接解引用`
   ⇒ 只能直接解引用。**直接对大范围未映射/已失效页读会 SIGSEGV 打死线程**（实测：`CRASH: Forwarding signal 11`，线程不再打日志，进程被 CrashSight 接住）。
   ⇒ 结论：**重型内存扫描不要放进程内**。改成「定点 `dump` 落盘 + 离线 Python 分析」，稳定且快（pull 80 MB/s）。
3. Dobby 在转译层下可用：三个点 `rc=0`，且 UV 计数真实增长（~30/s）。

## 4. 运行时注册结构定位（绕过 Il2CppDumper）

### 4.1 先否掉两条"想当然"的路

- **libil2cpp 的 `.data` 在内存里也是密文**：把 rw 段（`0x40002e810000`，23.1 MB）整段落盘，熵 **7.215**、`mscorlib`/`.dll` 出现 0 次、3,025,920 个 8 字节槽里指向 so 代码段的只有 **2** 个 ⇒ 静态指针表不在 `.data`。
- 直接以魔数/串搜 metadata 侧：`0x7be1f967f000` 区只有 1 个指针引用它（易盾自己的 bookkeeping），不是 `MetadataRegistration`。

### 4.2 真正的注册数据在 **BSS**

`mscorlib.dll` 串的指针落在 `0x40002df6e5a0`，即 libil2cpp 的 **BSS**（`memsz - filesz` 那段，`0x40002d9d4000..0x40002e750000`）。所以落盘这两段（5.8 MB + 9.5 MB）后离线分析：

- **`Il2CppCodeGenModule` × 137**：结构 `+0 模块名串指针 / +8 methodPointerCount / +16 methodPointers`，例如
  `0x40002db73130 AK.Wwise.Unity.API.WwiseTypes.dll count=107 methodPointers=0x40002e03d350`
- 这些结构的**指针数组**（codeGenModules）在 `0x40002e0205a0`，共 138 项；
- 反查谁指向这个数组 ⇒ 前一个 u32 = **138**：
  ```
  slot=0x40002d9dc160 前一个 u32(count)=138  ==> CodeRegistration ≈ 0x40002d9dc0f0
  ```
- 校验：`CodeRegistration+0x68 = 138`、`+0x70 = 0x40002e0205a0` ✔
  ⇒ **`CodeRegistration` 的 so 内 RVA = `0xa5dc0f0`**（进程基址 `0x400023800000`）。

### 4.3 RVA 解析链路（全部离线，自建）

```
typeDefDef.nameIndex → 串数据块偏移 → 类型名
methodDef: +0 nameIndex / +4 declaringType / +24 token
  RID = (token & 0xFFFFFF) - 1
  image = images[] 中 typeStart ≤ declaringType < typeStart+typeCount 的那一项
  module = image 名（+".dll"）匹配到的 Il2CppCodeGenModule
  RVA = (*(uint64*)module.methodPointers + RID*8) - so_base
```
**自洽性校验**：137 个模块的 `methodPointerCount` 合计 **218,017**，metadata 里 methods 记录数 **218,020** —— 差 3 条（推断为 3 个无方法模块/接口），吻合。
类型名抽样：`<Module>` / `<>f__AnonymousType0\`1` / `EcsElementBase` / `DebugLogHandler`（合法率 976/1000）。

> ★**指纹必须取内存**：`.text` 在文件里是密文。实测同一 RVA 处文件字节是 `a1 00 00 00 a1 00 00 00`（重复填充），内存里才是真指令 ⇒ 一切序言指纹校验都必须在运行时做。

## 5. 移速候选：RVA + 指纹 + 依据

> **★2026-10-29 22:5x 追加的决定性结论（本报告最重要的结论，写在前面）**
>
> `MotionComponent+0xB0` **不是"当前移速"，而是逐帧速度的乘法倍率**。证据：`UpdateVelocity` 内部（rva `0x0435bb8c` 起，运行时代码原文）
> ```
> +0308  ldr  s0, [x19, #0xb0]        ; s0 = this->GmMoveSpeed
> +030c  fcmp s0, #0.0
> +0310  b.le skip                     ; <=0 不生效（默认 -1 = 关闭）
> +0314  ldr  d1, [x20]  / +0318 ldr s2, [x20, #8]   ; 本帧速度向量 xy / z
> +031c  fmul v1.2s, v1.2s, v0.s[0]    ; xy *= 该值
> +0320  fmul s0, s0, s2               ; z  *= 该值
> +0324  str  d1, [x20] / +0328 str s0, [x20, #8]    ; 写回速度
> ```
> ⇒ **写 `6.0` 到该字段 = 6 倍移速；写回 `-1.0` = 完全恢复**。不需要 patch 任何指令。
> 实时速度向量本身在 `+0x1B0..+0x1BC`（`UpdateVelocity` 里 `ldr s2/s3/s4/s12,[x19,#0x1b0..#0x1bc]`），
> 这也解释了早期快照（只扫 `0x60..0x160` 窗口）为什么"角色走了却没有任何字段变化"。

类：`FunPlus.WorldX.Entities.Components.MotionComponent`（235 方法）/
`FunPlus.WorldX.Entities.Components.CharacterControllerComponent`（182 方法），
都在游戏主程序集 `FunPlus.WorldX.Scripts.dll`（**不是** Lua 绑定层 `*Wrap`）。

| 方法 | RVA | 指纹（内存前 4×u32） | 说明 |
|---|---|---|---|
| `GetAttributeSpeedRatio` | `0x0435378c` | `F81F0FFE F9400C08 B4000148 F9405500` | 速度倍率入口【推断】；**实测 0 次命中**，非逐帧 |
| `ChangeMoveStateSpeed` | `0x043533fc` | `FC1C0FE8 A9015FFE A90257F6 A9034FF4` | 按移动状态改速度；只在状态切换命中 |
| `OnSpeedRatioChange` | `0x04353360` | `A9BE57FE A9014FF4 F9400C08 B4000468` | 倍率变化回调 |
| `UpdateVelocity` ★ | `0x0435b884` | `D10443FF 6D083BEF 6D0933ED 6D0A2BEB` | **每帧入口，实测 ~30 次/秒/角色** |
| `set_GmMoveSpeed` | `0x0434fba8` | `A9BF4FFE 1E202008 AA0003F3 F9401800` | 只写 `this+0xB0`（**移速倍率覆盖位**，默认 -1=关闭） |

| `CheckSprint`（CCC） | `0x0430b0d4` | `A9BE57FE A9014FF4 7100503F AA0003F3` | 冲刺判定 |
| `SetVelocity`（CCC） | `0x043089a4` | `F81F0FFE F9400C08 B40000E8 F9406900` | |

### 依据链（不是猜名字）

1. **字段级硬证据**：`set_GmMoveSpeed` 反汇编
   ```
   +0000 stp x30,x19,[sp,#-0x10]!
   +0004 fmov s?,s0
   +0008 mov x19,x0
   +000c ldr x0,[x0,#0x30]
   +0010 str s0,[x19,#0xB0]     ← this+0xB0 是 float 速度字段
   ```
   配套 getter 就是 `ldr s0,[x0,#0xB0]; ret` 两条指令。
2. **调用频率**：`UpdateVelocity(this, arg1, float dt)` 反汇编开头 `sub sp,#0x110 ; fmov s8,s0 ; mov x20,x1 ; mov x19,x0`（第三参是 float dt），实测 `dt=0.0333`（30 fps），命中率 ~30/s ⇒ 逐帧。
3. **命名与归属**：类型/方法名来自真实 metadata；同组件里 `ChangeMoveStateSpeed / OnSpeedRatioChange / GetAttributeSpeedRatio / CheckSprint` 构成"倍率→移动状态→速度"链路，与 Lua 侧 `applyStaticMotionProp` 只下发配置的结论一致。
4. **全部 RVA 处的序言都是真实 ARM64 指令**（不是随机密文），且 RID/模块计数自洽。

### 5.1 实时速度字段的现场证据（站立态快照）

挂 `UpdateVelocity` 后，每 2 s 给每个已知 `this` 打两行 float 快照（`0x60..0xE0` / `0x140..0x1C0`）。
两个同类型单位（`0x400003077a80` / `0x4000030762a0`）的差异点：

```
+0x94 = 6.0   / 6.0
+0xCC = 5.0   / 5.0
+0xD4 = 6.0   / 6.5      ← 两个单位不同，最像"当前移速"
+0xB0 = -1.0  (GM 覆盖，恒定)   +0xB8 = -20.0（像重力） +0xBC = 2.0
```
另有纯默认单位（`0x40000d22a000` / `0x40000d30ca80`）：`+0xD4 = 0`、其余同类字段固定 ⇒ 未初始化/非玩家单位。
**待用户走/冲刺一轮后按三态 diff 定论**（见 §6）。

## 9. 实现（诊断包，`STARRY_DIAG=1`；正式包与 `kYimoPatch` 未动）

### 9.1 方案：写倍率字段，不 patch 指令

```
主角的 MotionComponent  →  *(float*)(this + 0xB0) = mul     (mul>0 生效；-1 关闭)
```
在 `UpdateVelocity` 的 hook 里、**调用原函数之前**写该字段（原函数在 `+0x308` 处读它），
所以每帧都必然生效，且游戏自己把值刷回 `-1` 也抢不过我们（我们每帧先写）。

### 9.2 挂点清单（全部先验序言指纹，不符即拒挂）

| 挂点 | RVA | 指纹 | 用途 |
|---|---|---|---|
| `MotionComponent.UpdateVelocity` | `0x0435b884` | `D10443FF 6D083BEF 6D0933ED 6D0A2BEB` | 写倍率（仅主角） |
| `CCC.CheckSprint` | `0x0430b0d4` | `A9BE57FE A9014FF4 7100503F AA0003F3` | **认主**（冲刺键=真人输入） |
| `CCC.get_InputMove` | `0x04305828` | `A9BE57FE A9014FF4 D00332F5 D00332F4` | 认主备用（实测 0 命中，非玩家路径） |
| `MotionComponent.GetAttributeSpeedRatio` | `0x0435378c` | `F81F0FFE F9400C08 B4000148 F9405500` | 观测量（实测 0 命中，已否掉"每帧入口"假设） |
| `MotionComponent.ChangeMoveStateSpeed` | `0x043533fc` | `FC1C0FE8 A9015FFE A90257F6 A9034FF4` | 观测量 |

### 9.3 认主角的链路

```
CheckSprint 的 this（即 CharacterControllerComponent*）
   +0x18 → entity
   entity +0xD0 → MotionComponent*     ← 只对这个指针写倍率
```
依据：`CCC.SetVelocity` 反汇编 `ldr x8,[x0,#0x18] ; cbz ; ldr x0,[x8,#0xd0] ; b MotionComponent::SetVelocity`。
认主只做一次即锁定；指针做 8 字节对齐与范围合理性检查（`0x10000..0x8000000000`），不合法就**完全不写**。

### 9.4 倍率来源（运行时热读，免重装）

```
/sdcard/Android/data/com.x.yimoo.official/files/spd_mul.txt   ← 内容就是一个整数，如 1 / 6
```
每 1 秒读一次；`mul==1` 自动把主角字段写回 `-1.0`（完全关闭）。
最终要接回菜单 `YM.spd`（正式包），验证阶段先用文件通道做 A/B。

### 9.5 验收日志判据

```

改挂 `CCC.OnHandleMove`（`0x043079e0`）/ `CCC.get_MoveAxis3D`（`0x0430598c`）做认主，链路同上，不需要用户再配合。

## 11. 结论固化（截至停手时的确定项）

1. **`MotionComponent+0xB0` 是逐帧速度的乘法倍率位**（>0 生效，默认 `-1`=关闭），由 `UpdateVelocity` 内部 `+0x308` 处读取后乘到速度向量上。写入可长期保持、不反弹。
2. **`+0x1B0..+0x1BC` 不是速度向量**，是法线/坡度判定输入（`dot` 后 `fabs`→`fmin(…,1)` 与阈值比较）。此前把它当速度的说法**已纠正**。
3. **真正的速度向量是 `UpdateVelocity` 的第二参 `arg1`**（`mov x20,x1`，读 `[x20]/[x20+8]`、写回 `[x20]/[x20+8]`）；游戏自己的 GM 分支就是拿 `+0xB0` 乘它。
4. **认主不能靠 `CheckSprint`**（实测 0 命中）也不能靠 HEUR（命中数最高 ≠ 玩家，可能锁到常驻 NPC）。唯一可靠的判据是 **`MotionComponent+0x18 == 玩家 entity`**（entity 取自 `get_InputMove` 的 `this+0x18`，但该函数整局只触发 1 次，且当时 `entity+0xD0` 为 0）。
5. **`GetAttributeSpeedRatio`（0x0435378c）全程 0 命中**，不是每帧入口（早期假设已否）。
6. **这台模拟器（x86_64 + Houdini 转译）不适合作为 il2cpp 挂点的验证环境**：Dobby 能装上、能命中，但 trampoline 在高频热点上的稳定性无保证；进程内大范围读内存会直接把线程打死（tombstone_28）。**移速这条线的运行验证应放到真机。**

## 13. 2026-10-29 23:53 有效 A/B 结论：**`+0xB0`（GM 倍率位）对玩家移动无效**

这一轮是**第一次真正把倍率打开**的测试（`gm=6.000` 在调用原函数时确认在位），且**认主成功**（entity 指针比对）。

### 13.1 认主证据（真认主，非 HEUR）
```
spd OWNER2(OHM#1) 记录玩家 entity=0x40000545f000（来自 ccc=0x400001b85a00）
spd OWNER 锁定主角 MotionComponent=0x400003053d20（entity=0x40000545f000 指针比对一致） this+0xB0=-1.000
```
链路：`CCC.OnHandleMove` 的 `this`（CCC）+0x18 → entity；再与 `MotionComponent+0x18` 对撞（依据：`UpdateVelocity` 内 `ldr x9,[x19,#0x18]`）。

### 13.2 走 20 秒的数据（关键）
```
spd VEL 主角 this=0x400003053d20 mul=6 pre=(-3.706, 0.110, -2.949) gm=6.000 post=(-3.706, 0.110, -2.949) |pre|=4.738 |post|=4.737 post/pre=1.00
spd VEL 主角 this=0x400003053d20 mul=6 pre=(-4.313,-0.063, -1.759) gm=6.000 post=(-4.330,-0.229, -1.907) |pre|=4.658 |post|=4.737 post/pre=1.02
```
- **`arg1` 确实是实时速度量**：站立全 0；走起来从 0 加速到 **|v| = 4.737（走路速度稳定值）**，冲刺/下落瞬间最高见到 **7.748**。
- **`gm=6.000` 在调用瞬间确实在位**（`gmBefore` 是本 hook 在调用原函数前读的）。
- **`post/pre ≈ 1.00`**：速度没有被放大 6 倍 ⇒ **`+0xB0` 这个 GM 倍率位对玩家移动不生效**。
  （两种可能：(a) `+0x2e4/+0x2f0` 的两个前置门 `tbnz bit0` / `[x0+0x138] > 0` 不满足，GM 分支根本没进；(b) 乘了但随后被 UV 内的**幅值钳位**抹平。日志无法区分，但结论一致：**它不能当移速杠杆**。）
- 这也解释了用户两次"没变化"。

### 13.3 UV 里确实存在一个幅值/位移钳位（静态证据）
```
+0530  fmov  s2, #20.0
+0534  fmul  s3, s8, s2          ; s3 = (第 3 参) × 20
+0538  fcmp  s3, #0.0 / b.lt
+0540  fmul  s2, s3, s3          ; s2 = (20*arg)^2
+0544  fcmp  s12, s2
+0548  b.ls  → 跳过
+0588  fsqrt s0, s12             ; |v|
```
⇒ 想突破速度上限，必须**先搞清 s8（第 3 个浮点参）是什么、以及钳位后的值又写回哪里**，否则任何"乘速度"的做法都会被这一层吃掉。

### 13.4 下一步（按 lead 的第 3 条判据）
换杠杆：**`MotionComponent.SetVelocity`（RVA `0x04351a88`）的 `Vector3` 实参**（`CCC.SetVelocity` 就是 `ldr x8,[x0,#0x18]; ldr x0,[x8,#0xd0]; b MotionComponent::SetVelocity` 的尾巴调用）。这是"游戏这一帧要让角色以多快移动"的**目标速度**，比改结构体字段更接近源头。
验证判据（全机器可判，无需体感）：在 `SetVelocity` 里把实参三轴前后值打出来，缩放 6 倍后看**下一帧 `UpdateVelocity` 的 `arg1` 幅值是否变成 6 倍**（`arg1` 会保留上一帧值，这一点本轮已被证实：`pre` 等于上一帧的 `post`）。

### 14.4 踩坑记录（对后续所有 native 工作通用）
1. **指针合法性上限别写死太小**：本机堆地址形如 `0x4000_xxxx_xxxx`（约 7e13），
   早期上限写 `0x8000000000` 导致**所有 entity 指针被判非法**，认主连续失败数轮。
2. **读 `/proc/self/maps` 的静态缓冲要够大**：实测该进程 maps 约 380 KB，
   96 KB 会截断 ⇒ 内存可读性判断永远失败（表现为"日志一条都不打"）。
3. **不要把 `+0x1B0..+0x1BC` 当速度**：那是法线/坡度判定输入（`dot` 后 `fabs`→`fmin(..,1)`）。
   速度量是 `UpdateVelocity` 的第二参 `arg1`；而**最上游的目标速度**是 `SetVelocity` 的 `Vector3` 实参。
4. **`this+0xB0` 是 GM 调试倍率位**，被两个前置门和 20 单位/秒钳位吃掉，对玩家移动无效（已证伪，勿再试）。
5. 排查期**禁止 `adb logcat -c`**：会把崩溃现场清掉，导致无法回溯。
