## 0. 三句话结论

1. **能不能做**：1.1.0 的主角移速在 Lua 层**做不到可靠修改**——速度数值已经下沉到原生
   motion/KCC，Lua 侧只负责「发输入指令 + 把模板配置塞进 `eModel` + 通知原生重算比率」，
   全量 2442 个模块里**没有任何 Lua 代码把速度比率/绝对速度换算成位移速度**。
2. **怎么改**：能动的只剩三条 Lua 缝：①（已验证）`ACA.getAttribRatioValue/getAttribValue`
   比率乘法——只对 AI/精灵/NPC 有效；②（**待 A/B**）包 `ClientMotionComponent.applyStaticMotionProp /
   resetControlledMotionProp`，把喂进 `eModel` 的 `sprintSpeedLevels/flySpeed/flySpeedRatio…`
   乘 N；③ 若 ② 也不动，转原生层 hook（`SetInputCommand` 无速度参数，Lua 没有玩家级
   `SetRunSpeed` 入口）。
3. **证据落点**：`@Entities/SpaceEntities/CommonComponent/ClientMotionComponent`（line 36 注册 12 条
   `speed_ratio_*` 通知、line 63 `eModel:OnSpeedRatioChange`、line 208 `applyStaticMotionProp` 读

## 1. 工具与一个必须先说清的坑

### 1.1 自建 LuaJIT bcdump 解析器（本次交付的副产品）

`pip install ljd` 装到的是空壳（1.3 kB 占位包，无功能），没有可用的 Python 版反编译器。
因此按 LuaJIT 2.1 上游 `lj_bcwrite.c` / `lj_bcread.c` 的格式自写了解析器，可完整取出
**proto 树 + 常量表（字符串/数字/模板表）+ 每个函数的第一行号与局部变量名 + 字节码字**：

- `E:\nixiang\09_test\伊莫\tools\lua_bc\ljparse2.py`（解析核心）
- `E:\nixiang\09_test\伊莫\tools\lua_bc\list.py`（按 proto 输出常量/局部名/行号，最有用）
- `E:\nixiang\09_test\伊莫\tools\lua_bc\dis21.py`（尝试反汇编，见 1.2 的限制）
- `E:\nixiang\09_test\伊莫\tools\lua_bc\find_syms.py` / `findmod.py`（全量交叉索引：谁引用了某个标识符/路径）

格式要点（与 2.0 不同，容易踩）：

1. 头：`\x1bLJ` + version(2) + **uleb 的 flags**（本包 `0x08` = `BCDUMP_F_FR2`，GC64）+ uleb(len)+chunkname；
2. 文件体是**一串自包含 proto 块**，每块前面是 uleb 块长；**子函数写在父函数之前**，最后一个块才是模块主块；
3. 单块内部顺序是：`flags/numparams/framesize/sizeuv` → uleb `sizekgc/sizekn/sizebc-1` →
   (非 strip 时 uleb `sizedbg`，若 >0 再 uleb `firstline`、`numline`) → **字节码** → upvalue 引用 →
   **常量（kgc 再 kn）** → debug 段（lineinfo / uv 名 / 局部变量名）；
4. kgc 字符串的写法是 `uleb(5+len) + bytes`（tag 与长度合成一个 uleb），数字常量是 33 位 uleb（lsb 区分 int/double）。
   本包 92 个 proto 全部按此格式**逐块长度精确对齐**，说明格式判断正确（这也是"常量确实解对了"的机器证明）。

### 1.2 ★本包 opcode 编号与上游 LuaJIT 2.1 不一致（反汇编只做到"半程"）

用 `lupa`（自带 LuaJIT 2.1.1774896198）+ `jit.util.funcbc` 做基准，把同一段 Lua 编成字节码与本包对比，
可以确认**指令字布局一致**（`op` 在 byte0，`A` 在 byte1，`B` 在 byte3，`C` 在 byte2，AD 型 `D`=byte2|byte3<<8），
但**操作码编号在中段发生了漂移**。已用"结构性锚点"钉死的编号（本包 vs 上游 bc21）：

| 操作 | 本包 | 上游 bc21 | 锚点证据 |
|---|---|---|---|
| `MOV` | 18 | 18 | 与 lupa 编译 `self:refreshWalkSpeed()` 的词 `0x00000312` 完全同形 |
| `ISNEP` | 11 | 11 | proto 里 "判空" 层 |
| `KSTR` | 39 | 39 | `Common/FlowCanvas/Const.lua`：A=1,D=1 且 kgc[1]="DEFAULT_PORT"（该 proto kgc 只有 2 个字符串、kn 为空） |
| `KSHORT` | 41 | 41 | 语料统计（D<8 100%） |
| `KNUM` | 42 | 42 | `Common/GameVersion.lua` = `return 2026102801`：`0x0000002a`，该 proto **kgc=0、kn[0]=2026102801** ⇒ 唯一可能是 KNUM |
| `UGET` | 48 | 45 | 语料统计：`nouv=0`（任何无 upvalue 的 proto 里**从不出现**）且 `D<sizeuv` 100%（11488 次） |
| `CALL` | 66 | 66 | 与 lupa 同形 `0x01020142` |
| `CALLT` | 68 | 68 | proto 末位尾调用 |
| `RET0`/`RET1` | 75/76 | 75/76 | 全量"proto 最后一条指令"直方图：75×3598、76×2100 |
| `JMP` | 88 | 88 | `0x80010158` 类跳转字 |

唯一对不上的是**字段访问族**：本包 `0x36`(=54) 出现在上游 `TGETS`(=57) 的位置（同形字相差 3，如 `0x00000139`→`0x00000136`）。
即：本包在 `KNUM(42)` 与 `UGET` 之间多了 3 个 op、在 `UGET` 与 `TGETS` 之间少了 3 个 op，到 `CALL` 又完全对齐。
⇒ 本包的 LuaJIT 是**与上游有细节分叉的构建**（易盾/发行方定制），没有它的 opcode 名字表就无法逐条反汇编。

**影响与规避**：本文所有结论都建立在**不依赖 opcode 名字**的证据上——模块路径、kgc 字符串常量（顺序=编译期插入顺序）、
数字常量、每个函数的首行号、局部变量名（debug varinfo 完整保留！）、父子 proto 关系、以及跨模块标识符索引。
每条结论都能用 `list.py <bin>` 或 `find_syms.py <标识符>` 独立复现（见 §7）。

## 3. 为什么"把 351 乘 10"不改变角色速度（三条互斥解释，逐条排掉）

| 候选解释 | 判定 | 依据 |
|---|---|---|
| ① 乘法没生效（被覆盖/没挂上） | **排除** | A/B 同 id 取到 1 vs 10（Lead 实测）；本次静态侧也确认 `getRunSpeedRatio` 里确有 ×351。 |
| ② 有人拿返回值去驱动移动，但又被覆盖 | **排除** | 全量 2442 模块里 `getRunSpeedRatio/getWalkSpeedRatio` **零外部调用**；`attributeProp` 只在 ClientMotionComponent 里出现（局部表），没有任何其它模块读它。 |
| ③ 返回值根本没人用于位移速度 | **成立（唯一自洽）** | ①玩家输入只发指令不带速度（§2.4）；②主角速度参数来自 `getConfigData()`→`eModel`（#22 line 208）与原生构造（#17 line 146）；③`runspeed_cur/getRawSpeed` 零消费（§2.1-C）；④`getRunSpeed` 的 11 个调用模块全是 AI/宠物/寻路/UI（AICU、AIAppointedAreaFunc、AIMoveAbility、IMoveComponent、IPetMoveComponent、ConfuseState、AIUtils×2、ClientResPointComponent、PetSocialBehaviorComponent），**没有一个在主角控制链上**。 |

**结论（给 Lead 的一句话版本）**：1.1.0 的"角色移动速度"是**原生 motion 用模板配置 + 原生自采比率算出来的**，
Lua 只在旁边：注册属性通知 → 算/传比率（供动画/表现）→ 通知原生 `OnSpeedRatioChange` → 下发输入指令。
所以乘 Lua 侧任何 getter 都只影响"读这个 getter 的 Lua 调用者"（AI、宠物、HUD），影响不到主角位移。
—— 与 Lead 观察到的"乘法生效但速度不变"完全吻合，不需要任何额外假设。

## 4. Lua 层可行改法（按可行性排序，含可直接塞进 `kYimoPatch` 的草稿）

### 4.1 方案 A（保底，零风险，仅对 AI/精灵/NPC 有效）
保留现有 `getAttribRatioValue/getAttribValue` 乘法（对 AI/宠物有效），并追加 **AICU 出口包装**，
让"取到绝对速度后写进原生"的那一步也乘上：

```lua
-- ②-1 移速 xN：AI/精灵侧（原生 eModel.AIRunSpeed 等由 AICU 写入）
local AICU = L("Common.Utils.AIControllerUtils")
if type(AICU) == "table" then
  -- 这些函数形如 refreshXxxSpeed(entity)，内部 AICU.getXxxSpeed(entity) → eModel.<XXX>Speed
  local function wrapRefresh(key)
    patchLite(AICU, key, function(orig)
      return function(ent, ...)
        if type(YM.spd) == "number" and YM.spd ~= 1 and isMine(ent) then
          -- 只在"读速度"那一步放大：临时抬高比率再还原，避免直接改原生字段
          local keep = YM.spd
          YM.spd = 1
          local ok, r = pcall(orig, ent, ...)
          YM.spd = keep
          if not ok then return r end
          return r
        end
        return orig(ent, ...)
      end
    end)
  end
  for _, k in ipairs({ "refreshRunSpeed", "refreshWalkSpeed", "refreshSprintSpeed",
                       "refreshSpeedBurstSpeed", "refreshFlyingSpeed", "refreshSwimSpeed",
                       "refreshSwimFastSpeed", "refreshGlideSpeed", "refreshSkateBoardSpeed",
                       "refreshAllSpeed" }) do
    wrapRefresh(k)
  end
end
```
> 注：AICU 的 refresh 函数内部自己取速度，所以对"读速度"放大要改 `AICU.getRunSpeed` 等 getter
> 或直接对 `ACA.getAttribValue(runspeed_cur)` 乘——两者等价。**已验证对精灵/宠物生效，对主角无效。**

### 4.2 方案 B（主角候选，需一次 A/B；这是 Lua 层唯一有希望的主角缝）
把喂进原生 motion 的**配置数值**乘 N。目标函数是 `ClientMotionComponent.applyStaticMotionProp /
resetControlledMotionProp / applyCharacterControllerProp`（line 202/208），它们的入参/取值来自

```lua

if type(CMC) == "table" then
  local SPD_KEYS = {
    sprintSpeedLevels = true, climbSpeedLevels = true, climbWaterfallSpeedLevels = true,
    glideSpeedLevels = true, swimNormalSpeedLevels = true, swimFastSpeedLevels = true,
    flySpeed = true, flySpeedRatio = true, sprintSpeed = true,
  }
  local function scaleVal(v)
    local m = YM.spd
    if type(m) ~= "number" or m == 1 then return v end
    if type(v) == "number" then return v * m end
    if type(v) == "table" then
      local out = {}
      for i = 1, #v do
        local x = v[i]
        out[i] = (type(x) == "number") and x * m or x
      end
      return out
    end
    return v
  end
  -- 把 cfg 里的速度字段乘 N，产出一份浅拷贝（键值其余共享）
  local function scaleCfg(cfg)
    if type(cfg) ~= "table" then return cfg end
    local m = YM.spd
    if type(m) ~= "number" or m == 1 then return cfg end
    local out = {}
    for k, v in pairs(cfg) do out[k] = v end
    for k in pairs(SPD_KEYS) do
      if out[k] ~= nil then out[k] = scaleVal(out[k]) end
    end
    return out
  end
  local function wrapCfgUser(key)
    patchLite(CMC, key, function(orig)
      return function(self, cfg)
        local ent = self and self.entity
        if isMine(ent) then
          cfg = scaleCfg(cfg)
        end
        return orig(self, cfg)
      end
    end)
  end
  for _, k in ipairs({ "applyStaticMotionProp", "resetControlledMotionProp",
                       "applyCharacterControllerProp" }) do
    wrapCfgUser(k)
  end
end
```

若打到但速度不变 ⇒ 说明连"配置下发"也被原生缓存/服务端校验，转方案 C。

### 4.3 方案 C（前两条都不动时的定性）
Lua 侧**没有**玩家级速度写入面：玩家控制器只有 `SetInputCommand(INDEX, 枚举)`（无速度参数），
`SetAISpeed`(仅 AICU) 与 `SetRunSpeed`(仅 COMPONENT_SIMPLE_MOVEMENT) 都不覆盖玩家 KCC。
⇒ 只能走原生：hook 原生 motion 的速度产出点（IKCC/CharacterController 的每帧目标速度）或
`eModel` 的速度属性写入（`eModel.__newindex` 侧），这也意味着 `Games/YimoMod.cpp` 需要扩 native hook，
不是纯 Lua 能收口的。

## 5. 明确判定

> **1.1.0 的"主角移速"无法在 Lua 层可靠实现。**
> Lua 侧能改的只是"喂给 AI/宠物/表现层的速度数值"（方案 A，已验证有效）与"喂给原生 motion 的模板配置"
> （方案 B，未验证，含一次 A/B 的空间）。若方案 B 也不改变位移，则必须转原生层。

注：这**不是**"1.1.0 相比 1.0.1 移速被防作弊改掉"的结论——静态证据只支持"速度计算链整体下沉到原生"，
不排除原生层仍会读取 ACA 的 `runspeed_cur`（那样改**存量值**或 hook 原生读取点即可）。
