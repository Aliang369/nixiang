## 3. ★为什么走「xLua 入口 hook + luaL_loadstring 装补丁」而不是照抄斌哥的 chunkname 劫持

斌哥的做法（见 `10_docs/伊莫/斌哥hook锚点_20260930.json` → `injection_mechanism`）：

```
DobbyHook(dlopen) → strstr(path,"libxlua") → 取基址
→ DobbyHook(base + 0x010a41a8 = luaL_loadbuffer, 替换函数 @0x455f0)
→ 替换函数判 chunkname：strlen(x3)==17 && strcmp(x3,"@Core/Common/Time")==0
   相等 → 把 .rodata 里内嵌的 wrapper + IMO MOD 源码整份当 chunk 交给 Lua（即替换掉 Time.lua）
```

**照抄不行的三个理由**：

1. **硬编码偏移 0x010a41a8 / 0x01094430 / 0x009a8ed4 是版本锁死的**。伊莫官方包的 `libxlua.so` 恰好与斌哥包同版本（三个偏移复核通过：`+0x010a41a8 = 0xd103c3ff` = `sub sp,sp,#0xf0`），但一次热更就废。
2. **依赖 `@Core/Common/Time` 这个 chunkname 恰好被加载**，且依赖「Time.lua 是纯工具模块、替换它不破坏游戏」——这是斌哥针对该版本的运气，不是通用机制。
3. 移植到星空版必须**与斌哥源码零耦合**（授权边界），重写比搬运更安全。

**星空版做法**（`Games/YimoMod.cpp`，914 行，xLua 路线、零 il2cpp 依赖）：

```
① dlopen("libxlua.so", RTLD_NOW)（失败退 RTLD_NOLOAD|RTLD_NOW）
   dlsym 九个符号：luaL_loadstring / lua_pcall / lua_tolstring / lua_settop /
                  lua_getglobal / lua_setglobal / lua_pushboolean / lua_type / lua_gettop
② 序言指纹校验（漂移即拒挂，绝不在未知二进制上盲挂）
   kGetTopFp[4] = {0xa9422009, 0xcb090108, 0xd343fd00, 0xd65f03c0}
   kPcallFp[4]  = {0xf81e0ffe, 0xa9014ff4, 0xf9400813, 0x34000143}
③ DobbyHook(lua_pcall) + DobbyHook(lua_gettop)，原函数存 g_origPcall / g_origGettop
④ 每次进 hook：g_inHook.exchange 防重入 → SyncFromLuaEntry(L) → 再调 orig
⑤ 就绪判据：lua_getglobal(L,"pg") 且 lua_type==LUA_TTABLE（游戏环境起来了）
⑥ 装补丁：luaL_loadstring + lua_pcall 跑 kYimoPatch（大段 Lua，守卫幂等）
⑦ 同步：独立 chunk 写 YM.dmg/spd/inv/jump/stam/tp；每 1 s 跑 kYimoTickChunk
```

**关键取舍**：
- **只用 `dlsym` 拿符号，不用任何硬编码偏移** ⇒ libxlua 热更版本漂移时只需指纹复核，不需要重新找偏移。
- **序言指纹是安全阀**：`libxlua.so` 未 strip（有完整 `.dynsym`：`luaL_loadbuffer 0x10a41a8`、`lua_pcall 0x1096dac`、`lua_pushboolean 0x1094430`、`lua_setglobal 0x9a8ed4`、`xluaL_loadbuffer 0x9a9188`），但偏移会变，指纹不会。
- **双 hook 冗余**：`lua_pcall` 是主入口；`lua_gettop` 兜底（游戏若走 `baselib::LuaFuncWrapper::pcall` 或 `luaTimedProtectPcall` 内部调用链，gettop 几乎必然被调到）。任一挂上即 `g_ready=true`。
- **不 hook `luaL_loadbuffer`**：那是斌哥的入口，改用它就得管 chunkname，反而更脆。
- **多 VM 防护**：`SyncFromLuaEntry` 里 `static void* s_states[8]` 记录见过的 `lua_State`，打 `lua state #N = %p`。若游戏有战斗 VM ≠ 加载 VM，会出现「补丁装上了但没效果」，这条日志是唯一的诊断依据。
- **预热 20 次再装补丁**（`if(!g_patched && c>=20) want=true`）：避开游戏启动早期 Lua 环境尚未建全的窗口。

### 3.1 幂等与自愈（★踩过的坑）

`kYimoPatch` 开头 `if _rg(_G,"__YM_V") then return end` 做一次性守卫；但**补丁是每次同步都重跑的**——因为游戏换场景/进战斗时若重建了实体类表，我们的包装会随之丢失，一次性安装会静默失效。

> ☠ **教训（Jjdm 真机踩过）**：补丁 chunk 与「写开关」chunk **必须分开跑**。补丁命中守卫时会提前 `return`，把两者拼在同一个 chunk 里会把写开关整段吃掉，表现为「菜单开关按了没反应」。

### 3.2 装机后实测的 hook 日志（本次成功证据）

```
18:16:17 [Yimo] lua C api ready gettop=0x72c76b0be0 pcall=0x72c76b6dac setglobal=0x72c6fc8ed4
18:16:17 [Yimo] hooked lua_pcall @ 0x72c76b6dac
18:16:17 [Yimo] hooked lua_gettop @ 0x72c76b0be0
18:16:17 [Yimo] init ok（xLua 路线，零 il2cpp 依赖）
```

启动后约 56 s 才拿到符号——**`libxlua.so` 是懒加载的**，所以 `Yimo_Tick` 里做了懒加载重试（`initRetryMax=0` ⇒ 框架不调 `tryInit`，必须 Tick 自己每 ~400 ms 补一次）。

> ☠ **日志 tag 是 `Mod_Menu` 不是 `Yimo`**：`Includes/Logger.h` 里 `#define TAG OBFUSCATE("Mod_Menu")`，`#define YIMO_LOG "[Yimo]"` 只是消息前缀。**抓日志一律 `adb logcat -s Mod_Menu:V`**。

### 3.3 ★★致命坑：伊莫的 Lua 全局表是「白名单式」的，裸读全局拿不到值

**这是本次移植最难查的一个缺陷，必须在所有 xLua 移植里当作默认假设。**

伊莫的 `Core/Framework/Global.lua` 给全局表装了 `__index` / `__newindex`（Global.lua:106 → `__logGlobalError` Global.lua:73 → Global.lua:40）：

- **裸读**一个未声明的全局（如 `YM` / `Yimo`）**不会抛错**，而是走 `__index` → 打一条 Unity 错误日志 → **返回 `nil`**。
- ⇒ 我们最初那句 `if YM then YM.dmg = ... end` **恒为 false**，滑块/开关的值**从来没写进 Lua**。因为默认全 off、行为与「功能未生效」无法区分，所以极其隐蔽。
- 表象是 logcat 里 `Unity` tag 每 200 ms 刷一条：
  ```
  [lua][error][Global]  ...Global.lua:40: Attempt to access an undeclared global variable : YM
      ...Global.lua:73: in function '__logGlobalError'
      ...Global.lua:106: in function '__index'
      [string "if YM then YM.dmg=1 ..."]:1: in main chunk
  ```
  而 `Mod_Menu` 侧**一条错误都没有**（`luaL_loadstring` 成功、`lua_pcall` 也返回 0）——因为 `__index` 只是「记日志 + 返回 nil」，不是 `error()`。

**修法：补丁内所有跨 chunk 通信一律用 `rawget` / `rawset`，彻底绕开 `__index` / `__newindex`。**

| 位置 | 改前（错） | 改后（对） |
|---|---|---|
| `YimoMod.cpp:696` | `Yimo = Yimo or {}` | `local Yimo = _rg(_G,"Yimo")`；`if type(Yimo)~="table" then Yimo={} rawset(_G,"Yimo",Yimo) end` |
| `YimoMod.cpp:747` tick chunk | `if Yimo and Yimo.tick then Yimo.tick() end` | `local G=_G local Y=rawget(G,"Yimo") if type(Y)=="table" and type(Y.tick)=="function" then Y.tick() end` |
| `YimoMod.cpp:780` 同步 chunk | `if YM then YM.dmg=.. end` | `local G=_G local Y=rawget(G,"YM") if type(Y)~="table" then Y={} rawset(G,"YM",Y) end Y.dmg=..`（**自包含：`YM` 不存在时自己建**，且与补丁走同一条 `_G` 路径，两边必然一致） |

复验：修后 `adb logcat -d -s Unity:V | grep -c "undeclared global variable"` = **0**。

### 3.4 ★诊断通道：Lua 侧 `LOG()` 不进 logcat，要直接写文件

游戏的 `Core.Log.LoggerManager:getLogger("YIMO"):warn(...)` **只写游戏自己的日志目录，不进 logcat**（`adb logcat | grep -F "[YM]"` 计数 = 0）。

⇒ `YimoMod.cpp:246` 的 `_dbg(s)` / `_dbgN(s)`（`_dbgN` 用 `_G.__YM_N` 计数、上限 8 条）改走三路：
1. `io.open("/sdcard/Android/data/com.x.yimoo.official/files/ym.log","a")` 直接落文件（**主力通道**）
2. `rawget(_G,"print")`（xLua 的 `print` → `Debug.Log` → logcat tag `Unity`）
3. 兜底才用游戏的 `LoggerManager`

`io` 先 `rawget(_G,"io")`，取不到再 `pcall(function() return io end)`。

**抓日志命令**：
```bash

### 3.5 ★★致命坑：「伤害倍率」对人物（主控角色）无效，只对伊莫精灵有效

**用户提问（2026-09-30）**：「你帮我看看伤害倍率有生效吗？我感觉有效果又没效果，这个伤害倍率是不是对人物没加成，只对伊莫精灵有效果？」——**用户是对的**。

给补丁加了有界诊断追踪（`TRACE` / `RSLOG`，按【来源身份/Packet 名】打点，每键 2 条、总计 400 行）后，实机（伤害倍率＝56）抓到：

```
[YM][tr] ME/RPC_CS_ProjectileHitTarget  #1 mine=true out=true  dmg=56
[YM][rs] RPC_CS_ProjectileHitTarget resend x55 #1     ← 人物：重发发生了
[YM][tr] PET/RPC_CS_DoActOnActorActions #1 mine=true out=true  dmg=56
[YM][rs] RPC_CS_DoActOnActorActions resend x55 #1     ← 精灵：重发发生了
```

人物与精灵各自发出的伤害相关包（去重）：

| 来源 | 发出的包 | 吃重发 |
|---|---|---|
| **人物 ME** | `RPC_CS_ProjectileHitTarget`、`RPC_CS_ProjectileDestroy`、`RPC_CS_AddProjectile`、`RPC_CS_CastAbilityOnTarget`、`RPC_CS_SetCombatActionTimeline` | ❌ |
| **精灵 PET** | `RPC_CS_DoActOnActorActions`、`RPC_CS_ProjectileHitTarget`、`RPC_CS_CastAbilityOnTarget`、`RPC_CS_SetCombatActionTimeline` | ✅ |

**人物从头到尾没发过一次 `RPC_CS_DoActOnActorActions` / `DoActOnSweepTargetsActions` / `OnAbilityCollisionHitTarget`** —— 而只有这三个（+`OnAbilityCollisionHitTarget`）包内无实例身份、重发 N 次服务器真算 N 次。

人物唯一的伤害通道 `RPC_CS_ProjectileHitTarget` 被斌哥实测死在：首参是**投射物实例 id**，命中后紧接 `RPC_CS_ProjectileDestroy`（同 id）⇒ **同颗弹重发只认第一次**。所以人物的 55 次重发 ≈ 白打网络。

**当时的修法（已实现并实机跑通，★但正式包已移除——理由见本小节末）＝移植斌哥的 ①-b「投射物多段命中」（改行为、不改上报）**：

| 开关 | 原值 | 改后 | 源码位置（斌哥文档） |
|---|---|---|---|
| `destroyOnHit` | `true` | `false`（弹穿透，继续命中） | `Projectile.lua:35` |
| `maxHitNum` | `1` | `min(64, 伤害倍率)` | `Projectile.lua:767`，上限 `ProjectileConst.MAX_PROJECTILE_HIT_COUNT_LIMIT=64` |
| `checkCanHitTarget` | `return self.hitTargetSet[hitActorId] == nil` | `return true`（不写 hitTargetSet，重复次数由 maxHitNum 兜） | `Projectile.lua:971` |

要打 **3 个类**（LiteClass 继承是读一次就 rawset 缓存进子类表 ⇒ 少打一个就漏）：`Common.Ability.Projectile.Projectile`、`GameApp.Ability.ClientProjectile`、`GameApp.Ability.EditorProjectile`。

**★实现要点：不做静态猜字段，改成「在命中判定里就地纠正实例」。**
`checkCanHitTarget(self, hitActorId)` 被调用时 `self` **就是真实投射物实例**，于是把 `fixProjInstance(self)` 放在包装函数开头——既拿到实例（无需知道构造器/管理器叫什么），又保证紧接着的那次命中与销毁读到的就是我们改过的值。

装机证据（当时 `[YM][proj]` 日志；`old=function` 证明 `checkCanHitTarget` 确实存在并已包装）：

```
[YM][proj][#1] Common.Ability.Projectile.Projectile dOH=true maxHit=true ccht=true old=function lim=64
[YM][proj][#2] GameApp.Ability.ClientProjectile     dOH=true maxHit=true ccht=true old=function lim=64
[YM][proj][#3] GameApp.Ability.EditorProjectile     dOH=true maxHit=true ccht=true old=function lim=64

#### ☠★为什么 ①-b 没进正式包（2026-09-30 决策）

用户口径：「**人物不用做，精灵就够了**」——精灵那条 `RPC_CS_DoActOnActorActions` 重发通道已实测有效，倍率功能本身不需要 ①-b。但更硬的理由是**副作用**：

- `checkCanHitTarget` 是**类级**方法，`patchProjectileClass` 写的 `vt.destroyOnHit` / `vt.maxHitNum` 也是**类级字段** ⇒ 它作用于该类的**所有**投射物实例，**包括敌方的**。敌方弹从此「命中不销毁 + 可重复命中」，属未估清的玩法副作用。
- 要给人物的弹加伤，正确做法是**按实例判 `owner`**（本次实现的 `fixProjInstance` 已按 `isMyProjectile` 判了），但类级的 `destroyOnHit=false` **无法按实例收窄** ⇒ 要么整个改法重做，要么实测确认敌方弹无影响。本轮不做。

**正式包的处理**：

1. 整段 ①-b 从 `YimoMod.cpp` 移除，原位留一段注释写清「是什么 / 为什么移除 / 重做时要注意什么」（源码搜 `①-b 投射物多段命中 —— ★正式包已移除`）。
2. `RPC_CS_ProjectileHitTarget` **放回** `DMG_OUT` 白名单（＝回到斌哥原始设计）。它对**精灵**的弹幕仍有实际贡献；且 ①-b 移除后不再有「多段命中 × 重发」把 `MAX_RESEND_PER_SEC=500` 挤爆的问题。

### 3.6 ★新能力：`luaL_loadbuffer` 源码转储（把整个游戏 Lua 拿到手）

伊莫的玩法 Lua **全在热更 bundle 里**（`files/cvs`，11.7 GB），APK 内无 `.lua`/`.luac`，磁盘上也没有散文件 ⇒ 核对字段名只能猜。本轮给 `YimoMod.cpp` 加了 `luaL_loadbuffer` 钩子（`Hook_luaL_loadbuffer` / `DumpLuaChunk`）：

```bash
# 装一次跑到「进世界」，然后：
adb pull /sdcard/Android/data/com.x.yimoo.official/files/ym_lua /tmp/yimo_lua
# 实测 2325 个模块
```

- 目录常量 `YIMO_DUMP_DIR`；`mkdir(...,0770)` 在 `InstallLuaHooks()` 里。
- 约束：只写 < 4 MB 的块、最多 3000 个块、文件名消毒（`SanitizeChunkName`，防路径穿越）。
- **天然过滤掉我们自己注入的补丁**：注入发生在 `g_inHook==true` 期间，而游戏跑 Lua 时 `g_inHook` 已置假（`Hook_lua_pcall` 是先 `SyncFromLuaEntry(L)` 再调 `g_origPcall`）。
- ⚠ **转储出来的是 LuaJIT 字节码**（magic `1b 4c 4a 02`＝`\x1bLJ\x02`，内嵌源路径 `E:\dev\jkroot\ws\workspace\XAndPublish\proj\p4dir\client\LuaScripts\...`）⇒ **本作引擎是 LuaJIT（Lua 5.1 语义），不是 Lua 5.3**。要读源码得反编译；但**字符串常量是明文**，`re.findall(rb'[\x20-\x7e]{3,}')` 就能确认字段名/方法名是否存在（本轮就是这样证实 `destroyOnHit` / `maxHitNum` / `checkCanHitTarget` / `hitTargetSet` / `owner` / `srcActorId` 全部存在）。
- ⚠ **正式包已移除该钩子**（2026-09-30 收尾）：`DumpLuaChunk` / `SanitizeChunkName` / `Hook_luaL_loadbuffer` / `YIMO_DUMP_DIR` / `p_luaL_loadbuffer` / `g_origLoadbuffer` / `dlsym("luaL_loadbuffer")` 全部删除，`#include <sys/stat.h>` 一并去掉。移除后不影响任何功能，只是没了「核对字段名」的手段。
- **要再用怎么办**：按下文描述把这几个符号加回 `YimoMod.cpp` 即可。要点复述：只在 `!g_inHook` 时转储（天然滤掉我们自己注入的补丁）、单块 < 4 MB、总数上限 3000、文件名消毒（防路径穿越）、失败只 WARN 不影响功能。
- 设备侧转储目录与 `adb pull` 下来的 2325 个模块已在收尾时删除（约 28 MB，可从 APK + 热更重新转储）。
