## 2. 三条轨（本轮方案）

| 轨 | 做法 | 理由 |
|---|---|---|
| ① 玩法 | xLua 层注入，不变：`dlopen("libxlua.so")` + `dlsym`（**不用硬编码偏移**）+ 指纹后 DobbyHook `lua_pcall`/`lua_gettop` → 跑 24,552 B 的 `kYimoPatch` | 玩法逻辑全在 Lua；1.0.1 已验证 |
| ② 入口 | `ContentProvider = com.starry.magic.StarryInitProvider`（**AXML 里插成 `<application>` 的第一个子元素**，`authorities=<pkg>.starryinit`）+ 菜单 `MenuService`。**不动**易盾 `MyApplication` | Provider 顺序＝平台实例化顺序，必须早于 TapTap 的 `TapTapKitInitProvider`/`TapUpdateFileProvider` |
| ③ 验签 | **运行时签名替换**（2026-10-29 双轨制的签名轨）：注入 MT `bin.mt.signature.KillerApplication193` 作 `classes3.dex`（包名与本底包证书 base64 由脚本现取现改），由 `appComponentFactory` 换成 `com.starry.magic.sign.StarryAppComponentFactory` 在 `instantiateApplication` 里 `Class.forName(...,true)` 触发其 `<clinit>`（换 `PackageInfo.CREATOR` + 清 `PackageManager.sPackageInfoCache`／`Parcel.mCreators`／`sPairedCreators`） | 本作真实 dex 被易盾加密、`classes.dex` 只有 63 KB 壳桩 ⇒ **「改包法」静态改 TapTap 门闩/登录路由无从下手**；签名轨让 TapTap SDK 读到官方证书，SSO/门闩自然通过 |

**为什么没走 TapLoginForceWeb / SignSpoof**：两者已于 2026-10-28/29 按用户指令整体删除（AGENTS.md §3、§7），本包 manifest 与 dex 均不含它们（`framework_entry_audit [B]` ✓、`查12` ✓）。

### 装机三条坑（本轮实测，已写进脚本注释）

1. **`pm install <设备内路径>` 会报 `INSTALL_FAILED_MEDIA_UNAVAILABLE: Failed to restorecon`**（包从 `/data/local/tmp` 复制，context 是 `shell_data_file`）。
   ⇒ 一律用 **`adb install -r -d`（streamed session）**，一次成功。
2. **换签名场景禁止 `pm uninstall -k`**：它会留下带旧签名的 `PackageSetting` 僵尸记录，之后任何 install 都
   `INSTALL_FAILED_UPDATE_INCOMPATIBLE: … signatures do not match`，而 `pm uninstall --user 0` 只回
   `Failure [not installed for 0]`（`rm -rf /data/data/<pkg>` 也救不回）。**标准解（本轮实测有效）**：
   `adb install -r -d 官方原包`（把记录刷成一致）→ `pm uninstall --user 0`（**不带 -k**）→ `adb install 星光包`。
3. **想保住 16 GB 数据要自己做搬迁**（`pm uninstall -k` 是陷阱，见上）：
   ```
   su -c 'am force-stop <pkg>; mv /data/data/<pkg> /data/local/tmp/yimo_data_keep'
   # 官方原包 adb install 刷记录 → pm uninstall → adb install 星光包
   # 新装后：读新 uid/上下文 → rm 新建空目录 → mv 搬回 → chown -R <uid>:<uid> → chcon -R <新上下文>
   ```
   本轮实测：新 uid `10079`（原 `10077`），SELinux 标签 `u:object_r:app_data_file:s0:c79,c256,c512,c768`（原 `c77,…`）。
   搬回后**游戏能正常启动并进入世界**，16,639 MB 热更资源未重下。

### 启动方式（别用显式 `am start SplashActivity`）

`adb shell am start -n …/SplashActivity` 在乐变接管的环境下会「闪一下就回桌面」（Unity 根本不加载）；
**用 LAUNCHER 意图**才正常：
```
am start -a android.intent.action.MAIN -c android.intent.category.LAUNCHER \
         -n com.x.yimoo.official/com.funplus.sdk.fpx.bridge.FpxUnityPlayerActivity
```
另外 `SYSTEM_ALERT_WINDOW` 必须 `appops set com.x.yimoo.official SYSTEM_ALERT_WINDOW allow`，
否则菜单只能打 `NativeMenu: show failed: no activity attach and no overlay permission`（悬浮球起不来）。

1. **人物吃不到「精灵攻击秒杀」**：沿用 1.0.1 的定性（ME 只发 `RPC_CS_ProjectileHitTarget`，同颗弹只认第一次），用户当时裁定「人物不用做，精灵够用」。菜单名已如实写「精灵攻击秒杀」。

3. **乐变（lebian）热更仍是变量**：数据目录被搬动过（uid 10077→10079），当前能正常启动并进世界；若日后乐变判定资源失效会重新下载（16 GB 级）。下次换版本优先考虑「不卸载、只换 dex/so」的路线。

## 9. 2026-10-29 晚 功能修复回合（1.1.0 与 1.0.1 的挂点差异）

首轮装机后用户实测：**移速 / 玩家无敌 / 精灵攻击秒杀三项无效**（菜单显示 ON）。按「不许猜」的口径做了
12 轮机器取证（诊断包同签覆盖、零用户操作），结论如下。

### 9.1 取证手段：Lua 模块转储（新增，可复用）

`Games/YimoMod.cpp` 里加了一条**只在 `STARRY_DIAG=1` 编译期存在**的转储钩子（照 `Games/Match2Mod.cpp` 成熟做法）：
DobbyHook `luaL_loadbuffer` / `luaL_loadbufferx` → 把游戏实际加载的模块落盘到
`/sdcard/Android/data/com.x.yimoo.official/files/starry_lua_dump`（App 自有目录，免存储权限）。
本轮共 **2442 个模块 / 22.6 MB**，含源路径与全部字符串常量：

```
m_xxxx.bin  = \x1bLJ\x02… LuaJIT 字节码（内含 @E:\dev\jkroot\…\LuaScripts\<模块名>.lua 源路径）
m_xxxx.path = 模块路径（哈希→路径对照）
```
> 这是「换版本后功能失效」最快的定位手段：先转储，再按标识符反查模块，比盲试挂点快一个量级。

### 9.2 三项失效的真实根因（都有实测/字节码依据）

| 功能 | 1.0.1 的挂点 | 1.1.0 实测 | 结论 |
|---|---|---|---|
| **精灵攻击秒杀** | 包 `serverMsg`，命中 `DMG_OUT` 名单就重发 | 包住后 `calls=712 / mine=582 / **out=0**`——一封命中包都没命中；字节码显示 `@GameApp/Ability/ClientProjectile` 里命中上报只调 **`serverMsgNoGC`** | **上报入口换了**：`serverMsg` → `serverMsgNoGC` |
| **玩家无敌** | `Utils.checkValidTarget` 返回 false + `dialoguePauseInvincibleEndTs=4e12` + `checkImmuneFallDamage` | `checkValidTarget` 包装装上（`wrap=2`）但**调用次数 0**；`dialoguePauseInvincibleEndTs` 写入后读回仍是 `nil`（被类表 `__newindex` 拒绝）；字节码显示 1.1.0 用 `AbilityUtils.invalidTargetMap / setAbilityInvalidTarget / isAbilityInvalidTarget` | **判定通道换了**：改用 `AbilityUtils.setAbilityInvalidTarget` |
| **移速** | `ActorCombatAttribute:getAttribRatioValue` 乘 `speed_ratio_load_adjustment_v` | 乘法**确实生效**（同一 id A/B 取到 `1` vs `6`；`laMine` 显示真实调用全部判定为「我方」），但游戏内速度不变；`AICU.refreshAllSpeed` 在 1.1.0 不存在；`pg.pawn` 上取不到任何 motion 组件（`motComp=nil`，只有 `rootMotionScales/animSpeed/abilityMotionInfos`），`onMotionAttrChange` 调了也不重算；**连「所有属性比率都乘」都不变** | **未解决**：1.1.0 主角色移动速度不由 Lua 属性 getter 驱动（推断已下沉到原生层），需要原生 hook 才能做 |

### 9.3 顺带查出的**更底层**问题：菜单开关根本不进 Lua（已修）

取证时发现 Lua 里 `YM.inv=false / YM.spd=6`，而菜单显示「无敌 ON / 移速 10」——即
**实时点菜单的值从来没写进 Lua**。原因：写开关只发生在 `SyncOnLua`，而它由 `g_wantSync` 驱动；
实时点菜单走「每 tick 传 `features[]/values[]`」这条路，过去不改 `g_wantSync` ⇒ 只有首次装载写一次。
- 修法：`Yimo_Tick` 里比对上一轮 `features[]/values[]`，有变化就 `BumpSync()`（序号 +1，各 state 补写）。
- 同时把「全局一次性 `g_wantSync`」换成**按 lua_State 记账**（`g_syncSeq`/`g_stateApplied`）：多 VM 时谁先触发 hook 都不会再吃掉别人的同步。

## 11. 原生路线 · 突破记录（2026-10-29 深夜，子代理 il2cpp-track）

### 11.1 metadata 硬障的真相（★可复用到所有易盾 IL2CPP 游戏）

易盾**不是整段加密** `global-metadata.dat`：它在 `mmap` 之后**在内存里原地解密**，只改头部两个字段做反 dump：

| 字段 | 名义值 | 易盾写成的值 |
|---|---|---|
| `sanity` | `0xFAB11BAF` | 字符串 `"HTPX"` |
| `version` | `29` | 文件大小 `29850532` |

把这两处改回 `0xFAB11BAF` + `29`，`Il2CppDumper` 立刻认（输出 `Metadata Version: 29`）。成品落盘：`E:\starry_build\yimo_il2cpp\gm_v29.dat`。
（设备侧 `files/il2cpp/Metadata/global-metadata.dat`、APK 内原件都是密文，头 4 字节为 `HTPX`。）

**但这仍不足以跑 Il2CppDumper 的默认模式**：`Searching...` 阶段报 `CodeRegistration: 0 / No symbol is detected` —— 易盾把符号与 codegen 特征也抹了。manual 模式本可解，但更快的路是下面这条。

### 11.2 绕开 Il2CppDumper 的「运行时全链路」

子代理实测得到的关键事实（对后续所有 native 改动都成立）：

- `libil2cpp.so` 的 **`.data` 段在内存里也是密文**（熵 7.2）；真正的注册数据在 **BSS**（`0x40002d9d4000` 起）：`Il2CppCodeGenModule` × 138、`CodeRegistration` @ RVA `0xa5dc0f0`。
- 这份 metadata 里 **`nameIndex` 是串数据块内的直接偏移**（易盾改了语义）、**字符串索引表被剥掉只在运行时 BSS**（`0x40002e57f924` 附近）。
- `methodIndex = token & 0xFFFFFF - 1`（模块内 RID）。
- 进程内 `pread("/proc/self/mem")` 返回 **EACCES**，只能直接解引用（会踩失效页打死线程，需小步读+日志）。
- **`.text` 在文件里是密文**（同址文件字节实测全是 `a1 00 00 00`）⇒ 指纹只能从**运行时代码**取。

于是「方法名 → RID → methodPointers → RVA」全链路打通，方法数自洽（模块合计 218,017 vs metadata 218,020）。

### 11.3 候选挂点（`FunPlus.WorldX.Scripts.dll`，指纹为运行时内存原文）

## 12. 原生路线 · 倍率位发现与第一次 A/B 阴性（2026-10-29 23:0x）

### 12.1 决定性反汇编（`UpdateVelocity`，RVA `0x0435bb8c` 起，运行时取码）

```
+0308  ldr  s0, [x19, #0xb0]        ; s0 = this->+0xB0
+030c  fcmp s0, #0.0
+0310  b.le skip                    ; <=0 不生效（默认 -1 = 关闭）
+0314  ldr  d1, [x20]      / +0318 ldr s2, [x20, #8]     ; 本帧速度向量 xy / z
+031c  fmul v1.2s, v1.2s, v0.s[0]   ; xy *= 该值
```

⇒ **`MotionComponent + 0xB0` 是"逐帧速度倍率覆盖位"**（>0 生效、`-1` = 关闭）。

### 13.4 踩坑记录（对后续所有 il2cpp 原生改动都适用）

1. **指针合法性上限写成 `0x8000000000`**，而本机堆地址是 `0x4000_xxxx_xxxx`（≈7e13）⇒ 所有 entity 指针被判非法，认主连续多轮失败。**判据要打日志，否则会误判成"机制不成立"**。

### 13.5 正式包第一次失败与根因（★教训：两套实现＝两边都没验证）

正式包第一版（`a4a8fa07…`）装上去**完全没效果**（有 `[Yimo] patch installed`，但没有 `speed native ok` 锚点）。
根因两条，都在「把验证过的诊断实现重写成另一套正式实现」这一步上：

1. **基址算法写错（决定性）**：正式版 `YimoSpdSoBase()` 用 `strstr(p, "libil2cpp.so")` 做**跨行**匹配 ——
   `p` 指向当前行，但 `strstr` 会越过行尾到**后面的行**里命中，于是把**当前行（可能是 APK / houdini 等
   `offset==0` 的映射）的地址**当成 libil2cpp 基址返回 ⇒ 按该基址算出来的 RVA 处指纹必然不符 ⇒ 静默不挂。
   诊断版当时用的是 `fgets` 逐行 + 每行独立匹配，所以没有这个坑。**修法：逐行 `memcmp`，且要求 `offset==0`。**
2. **倍率通路没接上**：正式版那版 `g_spdMult` 恒为 1（菜单值没进到 hook），即便挂上也等于关闭。

**改法（最终形态）**：**只保留一套功能代码**，正式包与诊断包跑同一段逻辑（无 `#if !MOD_DIAG_LUA` 功能分叉），
只有日志受 `DLOG`（`STARRY_DIAG`）控制。教训写进本文件：**验证过的实现不准重写成第二套；要么原地加日志门控，要么先带日志验。**

### 14.5 ★真机两个"像是 bug"的现象，实为运行时状态（判据留档）

| 现象 | 真实原因（日志判据） |
|---|---|
| 装完真机后「移速没效果」 | 新装/重装后菜单值是默认 **`Slider_移速 = 1`**（= 关，按设计完全透传）。日志 `[数值] #2 Slider_移速:1:10:1 = 1`。拉到 10 后立刻出现 `speed native ok (mul=10)` 与 10 倍 SETV。**不是 hook 失效。** |
| 「无敌一直开启、开关无效」 | 上一局运行期残留（无效目标表未清）+ 开局引导/保护期本来不掉血，重装重启后被重置。同代码下健康态为 `INV mapN=0 / clr=N`，菜单 `Toggle_玩家无敌 = OFF`。**不是开关逻辑错。** |

**给用户的固定口径**：**每次重装或重启游戏，菜单值都会回到默认（移速=1、开关全 OFF），需要重新打开**；
移速的"生效证据"就是日志里一条 `[Yimo] speed native ok (mul=N)`（只在 `mul>1` 且真正放大时打一次）。
