## 2. 三条轨（本轮方案）

| 轨 | 做法 | 理由 |
|---|---|---|
| ① 玩法 | xLua 层注入，不变：`dlopen("libxlua.so")` + `dlsym`（**不用硬编码偏移**）+ 指纹后 DobbyHook `lua_pcall`/`lua_gettop` → 跑 24,552 B 的 `kYimoPatch` | 玩法逻辑全在 Lua；1.0.1 已验证 |
| ② 入口 | `ContentProvider = com.starry.magic.StarryInitProvider`（**AXML 里插成 `<application>` 的第一个子元素**，`authorities=<pkg>.starryinit`）+ 菜单 `MenuService`。**不动**易盾 `MyApplication` | Provider 顺序＝平台实例化顺序，必须早于 TapTap 的 `TapTapKitInitProvider`/`TapUpdateFileProvider` |
| ③ 验签 | **运行时签名替换**（2026-10-29 双轨制的签名轨）：注入 MT `bin.mt.signature.KillerApplication193` 作 `classes3.dex`（包名与本底包证书 base64 由脚本现取现改），由 `appComponentFactory` 换成 `com.starry.magic.sign.StarryAppComponentFactory` 在 `instantiateApplication` 里 `Class.forName(...,true)` 触发其 `<clinit>`（换 `PackageInfo.CREATOR` + 清 `PackageManager.sPackageInfoCache`／`Parcel.mCreators`／`sPairedCreators`） | 本作真实 dex 被易盾加密、`classes.dex` 只有 63 KB 壳桩 ⇒ **「改包法」静态改 TapTap 门闩/登录路由无从下手**；签名轨让 TapTap SDK 读到官方证书，SSO/门闩自然通过 |

**为什么没走 TapLoginForceWeb / SignSpoof**：两者已于 2026-10-28/29 按用户指令整体删除（AGENTS.md §3、§7），本包 manifest 与 dex 均不含它们（`framework_entry_audit [B]` ✓、`查12` ✓）。

### 装机三条坑（本轮实测，已写进脚本注释）

1. **`pm install <设备内路径>` 会报 `INSTALL_FAILED_MEDIA_UNAVAILABLE: Failed to restorecon`**（包从 `/data/local/tmp` 复制，context 是 `shell_data_file`）。
   ⇒ 一律用 **`adb install -r -d`（streamed session）**，一次成功。
2. **换签名场景禁止 `pm uninstall -k`**：它会留下带旧签名的 `PackageSetting` 僵尸记录，之后任何 install 都
   `INSTALL_FAILED_UPDATE_INCOMPATIBLE: … signatures do not match`，而 `pm uninstall --user 0` 只回
   `Failure [not installed for 0]`（`rm -rf /data/data/<pkg>` 也救不回）。**标准解（本轮实测有效）**：
   `adb install -r -d 官方原包`（把记录刷成一致）→ `pm uninstall --user 0`（**不带 -k**）→ `adb install 星光包`。
3. **想保住 16 GB 数据要自己做搬迁**（`pm uninstall -k` 是陷阱，见上）：
   ```
   su -c 'am force-stop <pkg>; mv /data/data/<pkg> /data/local/tmp/yimo_data_keep'
   # 官方原包 adb install 刷记录 → pm uninstall → adb install 星光包
   # 新装后：读新 uid/上下文 → rm 新建空目录 → mv 搬回 → chown -R <uid>:<uid> → chcon -R <新上下文>
   ```
   本轮实测：新 uid `10079`（原 `10077`），SELinux 标签 `u:object_r:app_data_file:s0:c79,c256,c512,c768`（原 `c77,…`）。
   搬回后**游戏能正常启动并进入世界**，16,639 MB 热更资源未重下。

### 启动方式（别用显式 `am start SplashActivity`）

`adb shell am start -n …/SplashActivity` 在乐变接管的环境下会「闪一下就回桌面」（Unity 根本不加载）；
**用 LAUNCHER 意图**才正常：
```
am start -a android.intent.action.MAIN -c android.intent.category.LAUNCHER \
         -n com.x.yimoo.official/com.funplus.sdk.fpx.bridge.FpxUnityPlayerActivity
```
另外 `SYSTEM_ALERT_WINDOW` 必须 `appops set com.x.yimoo.official SYSTEM_ALERT_WINDOW allow`，
否则菜单只能打 `NativeMenu: show failed: no activity attach and no overlay permission`（悬浮球起不来）。

## 7. 已知限制 / 未决

1. **人物吃不到「精灵攻击秒杀」**：沿用 1.0.1 的定性（ME 只发 `RPC_CS_ProjectileHitTarget`，同颗弹只认第一次），用户当时裁定「人物不用做，精灵够用」。菜单名已如实写「精灵攻击秒杀」。
2. **未逐项实测**：六项只证到「补丁装上 + 开关值同步进 native + 用户侧菜单可点」。逐项玩法效果属 L3（用户终审）。
3. **乐变（lebian）热更仍是变量**：数据目录被搬动过（uid 10077→10079），当前能正常启动并进世界；若日后乐变判定资源失效会重新下载（16 GB 级）。下次换版本优先考虑「不卸载、只换 dex/so」的路线。
4. **`am start SplashActivity` 会闪退到桌面**（乐变/启动链特性，非崩溃），记录在案避免误判为 mod 故障。
5. 模拟器是 Houdini ARM 翻译环境；真机（arm64 原生）未在本轮验证，理论上更稳（1.0.1 真机通过）。
