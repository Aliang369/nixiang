## 4. 容器格式（已确认，来自 IDA 反编译）
### 4.1 文件头（12 B）
```
0x00 "GDRC"
0x04 u32 1              # 版本
0x08 u32be manifest_len # 必须 ∈ [64, 1048576]；本包 155469
```
→ manifest 明文从 0x0C 开始，长 155469，结束于 0x25F59。

### 4.2 manifest（明文，sub_1596AB8 解析）
```
0x0c u16be 1                          # 版本
     [u16be 14] "pilot-20260920"      # pack_id   -> Container+16
     [u16be 32] "347567f2dd59e39bc9ec5d40c7018bef"  # key_id -> +40
     [u16be 18] "com.example.noname"  # application -> +64
     [u16be 20] "frame-pilot-20260920"# release   -> +88
     [u16be 4]  "main"                # pack      -> +112
0x70 u32 1        # -> +136
0x74 u32 1        # -> +140
0x78 u64be 125546 # -> +176（索引块相对偏移）
0x80 32B digest   # -> +184/+200（索引块摘要）
0xa0 u64be 125518 # -> +216（索引长度）；校验 +176 == +216 + 28
0xa8 u32be 2545   # chunk 数量（<=0x1000）
0xb0 起 chunk 表，每项 61 字节：
     u64be data_offset | u64be data_size | 32B digest | 12B nonce | u8 flags
```
manifeat 有 **签名校验**（`sub_1595390` → 失败 E_SIGNATURE），每个 chunk 有 **32B digest 校验**（`sub_159867C` → E_CHUNK_DIGEST）。

### 4.3 索引块（加密）
解密后格式：magic **"IDX1"**（0x31584449）+ u32be 资源数（≤0x10000）；每资源：
`16B hash(2×u64be) | u16be type | u64be decoded_size | u32be slice_count | slice[20B]{u32 chunk_idx, u64 offset, u64 size}`

### 4.4 数据块（每 chunk 独立 AEAD）
- 数据块前 12 B = nonce，约束：byte[4..7]==0，byte[8..11] = chunk_index 大端；byte[0..3] 全包一致的序列号（否则 E_NONCE）
- 密文 + 16B tag；算法 **AES-GCM**（`sub_1B2CBC4` 分支 128/192/256 + `sub_1B2DC48` + 常量时间 tag 比较）
- AAD = `"godot-resource-data-v1"` + [u16be len]app + [u16be len]release + [u16be len]pack + u32be 1 + u32be 1 + u32be chunk_index
- flags&1 → 解压，解压后长度必须等于 manifest 记录值（E_DECOMPRESSION / E_DECODED_LENGTH）

## 8. 结论与未决
**已确认**：GDRC 容器全格式、加密算法（AES-GCM）、AAD 构造、密钥派生链结构、校验点位置。
**未确认（卡点）**：
1. HKDF 的 salt 具体来源（直接 KDF 路径的 sub_15953D0 第 1 参；已排除空/常量K/keyid 与常见 IKM 组合）
2. chunk 表 61 字节字段的精确对齐（offset 281539 处字节不满足 nonce 约束 → 字段解读有偏差）

## 9. 第二轮：动态取密钥（2026-11-03 晚）

### 9.1 方法：patch so 把中间值写到 .bss
不改控制流、不建 code cave，用**原位 4 条指令替换**（保留 \`stp\` 写 out，额外写 bss，跳过 \`bl memset\` 并保 \`mov w19,#1\` 维持返回值）：

| 地址 | 原指令 | 改为 |
|---|---|---|
| 0x1595488 | mov w19,#1 | adrp x8,#0x438F000 |
| 0x159548c | add x0,sp,#0x10 | str q0,[x8] |
| 0x1595490 | mov w1,#0x20 | str q1,[x8,#0x10] |
| 0x1595494 | bl memset | mov w19,#1 |

写入点选 \`.bss\` 全零页 vaddr **0x438F000**（运行时 \`base+0x438F000\`，落在 \`400024b75000 rw-p\` 段内）。
同法追加两处探针：AAD 数据指针 → bss+0x100（0x1595598/0x159559c），decrypt 实际 key 指针 → bss+0x110（0x159558c/0x1595590）。

### 9.2 结果（实测）
- 包已重签（CN=StarryMagic）并安装为 \`07_patched/梦幻回忆/梦幻回忆_probe.apk\`，**游戏可正常启动运行**
- bss+0x000 = HKDF 输出 32B：\`7b0ff8d7a8d8fafbfcbd9acd078db766e14b4bdab12c9ca20b778b8727764257\`
- bss+0x100 = 运行时 AAD 数据指针；bss+0x110 = decrypt 的 key 指针
- **decrypt 实际 key = 该指针 +6 起的 32 字节 = 上面的 HKDF 输出**（已验证同一性），说明密钥链已完全打通

### 9.3 AAD 精确结构（运行时实测，总长 86 字节）
\`\`\`
"godot-resource-data-v1"   22B   前缀（vector 内含结尾 \0，故 23B）
\x00\x00\x00                     3B   定界
[u16be 18]"com.example.noname"
[u16be 20]"frame-pilot-20260920"
[u16be 4]"main"
u32be 1 | u32be 1 | u32be chunk_index
u8 flags                          由 chunk 描述 +0x38 处读（ldrb）
\`\`\`
关键指令：0x1598a40 \`ldp x28,x8,[sp,#0x40]\`（AAD begin/end）→ 0x1598a48 \`ldrb w21,[x21,#0x38]\`（追加 flags 字节）→ 0x1598a54 \`strb w21,[x28],#1\` → decrypt。

### 9.4 当前卡点
按 9.3 结构复现 AAD + 正确 key 仍 **MAC check failed**（chunk 0/1/1748、index 块全部失败）。
差异只能出在「前缀与长度前缀之间的 3 字节定界」或 flags 取值的具体来源。
下一步需把 AAD 前 96 字节**原样拷入 .bss**（2 条指令余量不足，需借 0x1598a40 之后到 decrypt 之间的指令重排或小型 code cave）。

### 9.5 已验证的辅助事实
- chunk 表 61B/项：\`u32 pad | u32 offset | u64 size | 32B digest | 12B | u8\`，相邻项 offset+size 严格连续（gap=0），nonce 尾 4B = chunk 序号（BE）
- 内存中 chunk 描述数组为 72B/项（\`mov w10,#0x48\`），与 manifest 的 61B 表不同构
- decrypt 实现：AES-256-GCM，nonce=blob[0:12]，ct=blob[12:-16]，tag=blob[-16:]，ct_len=blob_len-28

## 10. 第三轮：全链路打通（2026-11-03 21:10）

### 10.1 关键突破：绕过 GCM 的 AAD
GCM 的明文只依赖 key + nonce，AAD 仅参与 tag。因此用 AES-CTR（nonce 同前 12 字节，initial_value=2）可直接解出明文，无需知道 AAD：
- 2545 个 chunk 全部解出（45.96 MB 明文），765 个本身未压缩
- 类型分布：GPM1 x1、GST2 x835（WebP 纹理）、JSON x333、INCFG x1075（remap/import）、RES x56、bin x245
- 166 个 GDVM 字节码脚本，头部保留源路径（如 res://scripts/ui/battle.gd）

### 10.2 GDVM 格式（自研 GDScript 字节码）
0x00 "GDVM" | 0x04 u32 4(版本) | 0x08 u32 32(头长)
0x0c 16B hash(ASCII hex) | ... | "4.7.2.stable;gdvm4;ptr64;int32;real32"
[u32 len]"res://scripts/ui/battle.gd"  <- 源路径
[u32 len]"Control" ... 标识符表（[u32 ?][u32 len][data]）

战斗逻辑所在的 ui/battle.gd（190 KB）含：damage / heal / attack / max_hp / critical / shield_absorb / shield_cut / defend / dead / attack_buff / _auto_attack。

### 10.3 五处 so 补丁（全部实测生效）
| 地址 | 原 | 改 | 作用 |
|---|---|---|---|
| 0x1595488 | mov w19,#1 | adrp x8,#0x438F000 | 密钥落盘（探针） |
| 0x15955d0 | cset w23,eq | mov w23,#1 | 跳过 GCM tag 校验 |
| 0x1596d40 | tbz w0,#0 | nop | 跳过 manifest 签名校验 |
| 0x1596d50 | tbz w0,#0 | nop | 跳过 manifest digest |
| 0x1598770 | tbz w0,#0 | nop | 跳过 chunk digest |

### 10.4 重打包方法（index 无需改动）
index 记录的是解压后尺寸，与压缩无关 => 改 chunk 内容只需：
1. 用 data key 以 CTR 重新加密（nonce 沿用原 12 字节，tag 可留原值）
2. 从 0x449C3 起重新排列所有 chunk
3. 回写 manifest 末的 chunk 表（+4 u32 offset、+8 u64 size）
4. index 块（0x25F59 起 125546 B）与 manifest 头原样保留

### 10.5 已落地的数值改动（assets_test.pck）
- chunk 1244（战斗属性）：attack 35->9999、defense 20->9999、hit 4760->9999、critical 5->99、default_max_hp 100->99999、default_max_mp 100->9999
- chunk 1131（成长系数）：max_hp 20000->999999、attack 2000->99999、defense 1000->99999

## 12. 第五轮：热更新层与最终死锁（2026-11-03 21:45）

### 12.1 第四层防护：热更新 base_id
- so 内证据：0x400520 附近为热更新模块字符串池（container_sha256 / authenticated_pack / HotUpdate）；0x5e902e = "E_UPDATE_ORIGIN\0godot-hot-update-base-id"（HTTP 头名）；0x3f5438 = "E_UPDATE"
- 启动日志 [HotUpdate] boot 打印 base_id；原包 = 143d142e7cabcef0b34794f2c425bf2f88e2259a2e602b6a2e56e61d386acef9
- 改 pck 后 base_id 变为 a46a5d1b...，客户端据此向 update_origin 请求补丁，服务器返回 404，界面卡在 E_UPDATE_HTTP_404
- 验证：pck 的 sha256 = 8139cc5c... 、md5 = 3ea36ba2... ，均不等于 base_id，说明 base_id 不是整包 hash，而是内部 catalog/container 摘要

### 12.2 完整防护链（四层）
1. GDRC manifest 签名 + chunk 摘要 —— 已用 so 补丁绕过
2. protected_paths（22 条）—— native 强制，改 bootstrap.gdvm 一个字节即 Failed loading resource
3. 12 文件 sha256 完整性清单（display_manifest）—— 清单本身改 1 字符即 Parse JSON failed，已排除长度/偏移/重排因素
4. 热更新 base_id —— 改任何资源即触发补丁请求，服务器无对应补丁返回 404，界面阻塞

### 12.3 战斗链路（服务端权威，实测）
- 进程 TCP 直连 182.106.136.15:29110；服务器列表配置（0530）写 ws://127.0.0.1:29110 / :29111（WebSocket 明文协议，但实际地址被改写为公网）

### 12.4 最终结论
**改资源 → base_id 变化 → 触发热更新 → 404 → 无法进入游戏**，形成死锁；即使突破热更新层，战斗数值仍由服务端计算并下发快照覆盖，客户端改动不会产生真实效果。
