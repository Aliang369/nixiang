## CLAIM

用户要确认：

1. 冲鸭变速器属于分身、虚拟机、插件框架中的哪一类。
2. 游戏添加进去后是怎样运行的。
3. GitHub 上有没有合适源码可以复刻。
4. 是否能作为“root/防御绕过 + 内置菜单”的基础设施。

## VERDICT

冲鸭变速器属于 **Android 应用层虚拟化沙箱**，也就是常说的 **应用分身 / 双开 / 容器 / VirtualApp 一脉**。

它不是：

- QEMU、VirtualBox、云手机那种完整虚拟机。
- 普通 Xposed 插件。
- 单纯的悬浮窗变速工具。
- 已经拿到 root 或内核权限的程序。

它更准确的描述是：

> 宿主 App 在自己的 UID、自己的进程空间和私有数据目录里，用代理组件、虚拟系统服务和自定义 ClassLoader 把 guest APK “假装安装并启动”。

游戏本身没有真正安装进系统，宿主只是把 guest APK 加载进自己的运行时环境。

强证据指向它与 VirtualApp / BlackBox 一脉同源或采用同一类设计，但**不能证明它直接使用了某个公开仓库源码**。它明显包含大量私有改造、壳保护、云端配置和业务层代码。

## 游戏运行原理

### 1. 添加游戏

用户选择游戏 APK 后，宿主读取 guest APK 的 Manifest、Application、Activity、Service、Provider、权限和 ABI 信息，并把 APK 放进宿主的私有目录。guest 并不需要作为独立 App 安装到系统。

### 2. 启动游戏

宿主不会直接把 guest 的 Activity 交给 Android 系统，而是把它转换成宿主已经声明好的代理组件。Manifest 中存在：

- `top.bienvenido.mundo.manifest.MundoActivity$Companion$STUB`
- `MundoActivity$Companion$STUB1` 到 `STUB24`
- `STUB1H`、`STUB1HF` 等横屏/全屏变体
- `MundoService`
- `MundoProvider`
- `MundoReceiver`
- `MundoIntermediary`
- `MundoSplashLauncher`
- `MundoSupervisorProvider`

代理进程是 `:stub1` 到 `:stub24`，任务亲和性为 `top.bienvenido.mundo.task1` 到 `task24`。这说明它不是每个游戏创建一个完整系统虚拟机，而是用有限的代理槽位启动 guest。

### 3. 虚拟系统服务

框架内部存在自己的：

- `IMundoActivityManagerService`
- `IMundoPackageManagerService`
- `IMundoWindowManagerService`
- `IMundoAccountManagerService`
- `IMundoContentService`
- `IApplicationThread`

这些服务在 guest 进程中替换或包装 Android 原本的 PMS、AMS、WMS 等访问路径，使 guest 看到的是：

- 自己的包名和组件。
- 自己的 Activity/Service/Provider。
- 自己的数据目录。
- 自己的 native library 路径。
- 自己的进程身份和任务栈。

实际运行 UID、宿主包名和真实存储路径则属于冲鸭宿主。

### 4. 加载 guest 代码和 native 库

宿主创建 guest 的 Context、Application 和 ClassLoader，再加载 guest dex 与 native `.so`。从先前对“无限升级”的容器诊断看，guest 的运行 UID 与直接安装原版 App 时的 UID 不同，数据目录最终落在宿主私有空间。这符合应用虚拟化的典型行为。

### 5. 内置菜单和插件通道

宿主包含多套悬浮窗类，例如：

- `FloatJisSuLayoutView`
- `FloatNewSpeedLayoutView`
- `FloatingMagnetView`
- `FloatScriptView`
- `FloatSettingLayoutView`

菜单不是改游戏包后塞进去的静态 UI，而是宿主容器提供的悬浮层。菜单操作通过回调、AIDL 或进程内通道送到 guest 侧。

宿主还暴露了：

- `com.modifier.aidl.PluginModifierService`
- action：`com.joke.motifier.plugin`
- action：`com.joke.motifier.ggorjf`
- action：`com.joke.motifier.vaprocessx`
- AIDL：`com.modifier.aidl.IMainAppService`

代码里还引用了内部身份：

- `com.joke.chongya.virtual`
- `com.joke.chongya.blackbox.view.OnePixelActivity`
- `com.joke.chongya.blackbox.view.OnePixelStartUpActivity`

真机上没有单独安装 `com.joke.chongya.virtual`；它更像是宿主内部用于克隆上下文和启动 guest 的身份字符串，不是必须额外安装的独立辅助包。

### 6. 变速功能的位置

变速只是宿主菜单系统的一项业务功能。菜单负责把倍率或功能开关送入 guest 进程，再由宿主注入的 Java/native 层处理。

这里不展开变速算法，但可以确认：

- 菜单和容器是两层。
- 变速后端可以替换。
- 容器本身不依赖某一种变速算法。
- 不能把宿主的变速实现和 guest 游戏自身壳崩溃混为一谈。

## 和斌哥 BUFF 的关系

两者属于同一大类：

- 都是应用虚拟化容器。
- 都能在不真正安装 guest 的情况下启动游戏。
- 都能提供悬浮菜单和注入通道。
- 都会处理包名、路径、组件和系统服务虚拟化。

差别主要在业务层：

- BUFF 更偏通用容器 + 游戏修改生态。
- 冲鸭把变速、菜单、云端配置、VIP、脚本、录屏和上报整合得更深。

所以冲鸭不一定比 BUFF 简单。公开源码通常只能覆盖“容器内核”，而冲鸭的菜单、插件服务、云端配置和兼容层才是大量私有工作量。

## GitHub 可复用源码

没有找到“冲鸭变速器”的公开源码，也没有找到 `top.bienvenido.mundo` 或 `com.zhangkong.virtualbox_core` 的公开上游仓库。

可参考项目：

| 项目 | 类型 | 许可证状态 | 适用性 |
|---|---|---|---|
| `asLody/VirtualApp` | VirtualApp 原始参考 | GitHub API 未识别许可证 | 最接近容器架构，适合理解原理，需自行核许可证 |
| `FBlackBox/BlackBox` | VirtualApp 系容器 | 未识别许可证 | 与冲鸭方向最接近，项目状态和授权需先核验 |
| `ALEX5402/NewBlackbox` | BlackBox 系 | Apache-2.0 | 许可证较清楚，可作为现代化起点调研 |
| `android-hacker/VirtualXposed` | 无 root Xposed 容器 | GPL-3.0 | 研究插件加载和 hook 通道 |
| `LSPosed/LSPatch` | 免 root Xposed 方案 | GPL-3.0，已归档 | 参考，不是通用沙箱底座 |
| `Qihoo360/DroidPlugin` | 插件框架 | LGPL-3.0 | 插件化，不是完整应用虚拟化 |

结论：

- 想理解或复刻“游戏不安装也能跑”，从 VirtualApp/BlackBox 系入手最合理。
- 想直接找一个能复刻冲鸭全部功能的仓库，没有。
- 公开项目基本不覆盖现代游戏壳、Android 16 兼容、云端 mod、VIP、防检测和崩溃兼容。
- VirtualApp 系源码不等于“root 或反作弊绕过”。

## 能不能做内置菜单和防御绕过

### 内置菜单

可行。技术路径是：

1. 用 VirtualApp/BlackBox 系容器启动 guest。
2. 在宿主侧提供悬浮菜单。
3. 菜单通过 AIDL、Binder、EventBus 或自定义通道发送功能开关。
4. 在 guest 进程中用 Java hook 或 native hook 执行功能。
5. 菜单 UI 和游戏本体分离，不必每次重打游戏 APK。

这条路线和冲鸭、BUFF 的核心思路一致。

### root

容器不会自动给 App root。

冲鸭运行在普通应用权限下，没有 `su`、SELinux 放宽或内核权限。它能伪装部分包名、路径和系统 API，但不会把普通 App 变成 root 程序。

### 防御绕过

要分开看：

- Java 层 root 检测、包名检测、路径检测：容器和 hook 有机会改写。
- native 反调试、`/proc/self/maps` 检查、完整性校验、签名校验、ptrace、SELinux、内核检测：容器本身不保证能绕过。
- 服务端校验、行为检测、封包校验、结算对账：客户端沙箱无法解决。

因此：

> 应用虚拟化能提供“承载 guest、注入菜单、改写部分环境”的基础设施，但不保证绕过目标游戏防御。  
> 真正的防御绕过必须针对具体游戏、具体版本、具体保护方案逐项处理。

## NOT PROVEN

- 冲鸭是否直接基于某个公开 VirtualApp/BlackBox 提交，未证实。
- `top.bienvenido.mundo` 的完整上游来源，未找到公开仓库。
- 所有 guest 是否都走同一套进程模型，未逐一实测。
- 云端 mod、脚本、OCR、录屏和上报系统的完整边界，未继续展开。
- 具体游戏在冲鸭内运行时的兼容性和反检测结果，必须逐游戏验证。

## 实际建议

如果目标是做“容器 + 内置菜单”：

- 以 VirtualApp/BlackBox 系为底座做原型。
- 先只实现单游戏、单功能、Java 层菜单和开关。
- 再补 guest native hook 和 64 位支持。
- 最后才处理多游戏兼容、云端配置、签名/环境伪装和崩溃恢复。

如果目标包含“root 绕过、反调试绕过、反作弊对抗”：

- 不要把它当成容器自带能力。
- 要按目标游戏单独做保护分析。
- 服务端校验无法靠客户端容器解决。
- 仅应在本机、自有账号、明确授权测试范围内验证。
