## 二、服务端到底能看到什么（决定安全线）

### 2.1 每场战斗的结算报文（PROVEN，game.js）

```js
// StageMgr.notifyCombatResult
CalcArg: { Range, IsWin, Dps: dpsStat.getDps() }
Stat: {
  MaxHp,                                  // role.Leader.playerChar MHP
  TotalDamage: dpsStat.getTotalDamage(),  // 含溢出（overkill）
  TotalHit:    htsStat.getTotalDamage(),  // 实际掉血（钳在敌人 HP 池）
  KillNpcId: [...], KillNpcAmt: [...]     // 每个怪杀了几个
}
```

两个统计口径不同，这是关键：

- `dpsStat.recordDamage(name, r, …)` 记的是**请求伤害 r**（含溢出，`doDmg` 内 `r` 是过盾后的值，可大于剩余 HP）；
- `htsStat.recordDamage(name, I > 0 ? I : r, …)` 记的是**实际掉血 I**（`C - CUR_HP`）。

⇒ 服务端拿 `TotalDamage / TotalHit` 就是**溢出比**。正常玩家接近 1.0~1.3；一刀 999999 的溢出比会到几十上百。
⇒ 这也是现有「秒杀 = `dmg = CUR_HP + 1`」伪装有效的**原理级依据**：溢出比只多 1 点/次，`TotalDamage≈TotalHit`，与正常击杀无法区分。

### 2.2 时间面（PROVEN，协议成对）

服务端自己有 T0/T1，客户端**伪造不了**。任何「清图变快」的功能都会直接抬高：

- 关卡耗时（服务端侧）
- `Dps = totalDmg / elapseMs * 1000`（客户端算好上传，`addTimeElapse` 用真实帧间隔）

⇒ **Dps 是本质可见面，秒杀/高暴伤都会顶它**；`TotalDamage` 因为只算实际掉血，反而基本不动。

### 2.3 封禁落地方式（PROVEN）

```js
// home.initRpc → S2C_KICK_OUT
ReasonEnum.Forbid   → "该账号已被封禁！"
ReasonEnum.IllegalAcc → "啊哦，连接出现异常，确定后重新登录。"
```

客户端**没有任何本地判定**，只有弹窗。也就是说：封号是服务端单方面决定，客户端侧能做的只有「别给证据」。

### 2.4 运营侧埋点（🟡 可掐，本次新增证据）

`game.js` 共 42 处 `common.sdkStatisticBehavior(...)`，全部走 `com.gravityengine.analyse`（数数科技 ThinkingAnalytics）→ `https://api.gravity-engine.com/event_center/api/v1/...`。战斗相关事件：

| 事件 | 触发点 | 上报内容 | 风险 |
|---|---|---|---|
| `level_time` | 战斗加载时 `{is_time_event:!0}`；关卡结算时 `{level_id}` | TA 侧配成**时长事件** → 关卡耗时分布 | 🔴 推图太快的第一手证据 |
| `level` | 结算：`level_pass` / `level_end` / `level_fail`，100 关额外 `level_clean` | 通关/失败 | 🟡 |
| `Online` | 每 tick 累加在线分钟 | 在线时长 | 🟢 |
| `Frequency` / `Gems` / `Shop` / `Ad_complete` 等 | 各系统 | 行为画像 | 🟢 |

> 注意：这些埋点发给的是**运营方自己**的数仓（不是第三方风控），所以「异常通关时长」在后台是能直接看到的。

### 2.5 原生反篡改（本地，已中和；是否上报 NOT PROVEN）

- `libcocos2djs.so` 内自定义 raw-svc `kill(0,SIGKILL)` 包装器 `0x16ebdf8`，以及 2.2 新增炸弹函数 `0x16d5a08`（`sleep(6)` → `getpid` → libc `kill`）——绕过被中和的包装器，所以必须**两处都补**。
- so 全量字符串扫描（137,602 行）**无任何上报 URL / report 关键字**：只有 V8 引擎符号与 `https://%s/` 模板。
  ⇒ 本地检测链目前的**可证行为只有自杀**；「检出后是否上报服务端」在本样本内 NOT PROVEN（与 20260905 结论一致）。
- Dobby inline hook 会被 watchdog（Adler32 自检）发现——这是**改包存在的可检测痕迹**，当前无解，只能接受（本次也确认 6.03s 炸弹路径已中和，进程 40s+ 存活）。

## 三、降险方案（按性价比排序）

### A. 数值面：把「服务端可见异常」压在正常波动内（🔴 必须做）

1. **秒杀永远用 `HP+1`，禁止 `×999999`**（现状已是）→ 溢出比 ≈1，`TotalDamage` 与正常玩家无差。
2. **回血/回蓝 ×4**：只影响续航，不进结算报文（`Stat` 无回复字段）→ 🟢 安全。
3. **暴击 +60pp / 暴伤 ×2**：只抬 `Dps`，量级约 ×1.5~2 → 🟡 中低。安全线参考 `skill/re-implement/anti-ban-analysis.md`（伤害倍数 ×5 以内）。
4. **闪避 +35pp / 防御 +15pp / 抗性 ×2**：只影响受击，服务端只看到 `IsWin` 与更少的死亡 → 🟢。
5. **别一天推图太快**（官方公告原文）：服务端耗时异常是**跨场次累积**特征，单场看不出来，一天推 50 关必被看到。

### B. 埋点面：掐掉运营侧「时长画像」（🟡 强烈建议，可实现）

- 最小改动：在 splice 里把 `common.sdkStatisticBehavior` 包一层，**丢弃 `level_time`**（或同时丢 `level`、`Online`）。
  - 实现位置：`game.js` 里 `common.sdkStatisticBehavior = function(t){...}` 定义处前置 `if(t==="level_time")return;`。
  - 代价：TA 后台少一个事件（断崖只在一个事件上，比「结算数值异常」隐蔽得多）。
- 不建议：屏蔽结算 RPC、登录、`C2S_REPORT_COMBAT_VAL`——那些是**业务必需**，断了立刻异常。
- 不建议：屏蔽 APMPlus/TapDB/穿山甲——它们不喂运营方的封号判定，收益低、动 dex 风险高。

### C. 节奏面：把「太快」补回来（🟡 可选，影响体验）

- 结算前 `await sleep(N)` 再发 `C2S_END_STAGE_COMBAT`，把服务端看到的关卡耗时拉回正常区间（N 可配 3~10s）。
- 只影响结算弹窗出现时间，不影响战斗本身；对「单场耗时过短」这一特征**直接有效**（因为服务端只能看 T1-T0）。
- 本次**未实现**（用户未要求），需要时再上。

### D. 场景面：高风险副本自动降级（🟡 建议）

- 竞技场/公会裂隙/BOSS/排行（`C2S_START_ARENA_COMBAT` / `START_GUILD_RIFT_COMBAT` / `BOSS_BATTLE_BEGIN` / `START_RIFT_COMBAT`）里，结果会被**其他玩家看到并举报**，是被封的最常见路径。
- 建议：进这些副本自动关 ⑧秒杀/⑨无敌（菜单侧可做 `CombatType` 判断），普通推图随便用。

### E. 环境面（🟢 已做/继续做）

- 反篡改双补丁（kill 包装器 + 炸弹函数）已随本次包生效，日志实证 `neutralized`。
- 不用 frida / ptrace 长挂；KSU 隐藏 root 默认过；避免对局中频繁切开关（每次切换都会走 `get_ret` 桥，本身不敏感，但频繁切容易手滑开高危项）。

## 四、明确不要碰的（会立刻暴露）

| 动作 | 后果 |
|---|---|
| 屏蔽/改 `C2S_END_STAGE_COMBAT`、`C2S_START_STAGE_COMBAT` | 结算失败 / 服务端判定异常 |
| 屏蔽登录、`S2C_SYNC_RESOURCE`、`S2C_UPDATE_VERSION` | 进不去游戏 |
| 改 `S2C_KICK_OUT` 处理逻辑（假称没被封） | 账号状态已在服务端，改客户端无意义，且会反复重连触发风控 |
| 直接把 `Dps` 上报改成固定值 | 与服务端 T1-T0 推导矛盾，属自曝 |
