## 2. 观察、解释与候选经验

- 观察事实：①签名门禁通过后，无 hook 时游戏稳定运行 8 分钟+；②一旦 inline hook（se::evalString/JNI evalString）或 splice 生效，游戏在登录后 8s~数分钟 exit_self SIGKILL；③静态还原：watchdog 线程（sleep(10) 周期）派 5s 检查任务，解析 maps "r-xp" 段 → fopen 模块文件 → **Adler32** 逐字节（A=(A+b)%65521; B=(B+A)%65521）比对，不命中 → log "has been changed!" → 派炸弹线程（sleep(6) → kill(pid,9)）；④该 so 全文仅 2 条 svc：kill(#129) 封装 0x16ebdf8 与 clone(#56) 封装，**7 条自杀路径全部经 kill 封装**；⑤把 kill 封装头 8 字节 patch 为 `mov w0,#0; ret`（带原指令版本守卫、mprotect RWX→写→clear_cache→还原 RX）后，进程跨多个检测周期存活 7.5 分钟+，功能正常。
- 拟提炼经验（带前提）：
  1. **识别**：游戏"过初始门禁后延迟 exit_self SIGKILL、无注入时稳定"的模式 → 优先怀疑周期性完整性校验线程；全文搜 svc 指令枚举 kill/exit 封装调用点，常能找到单点收口。
  2. **动作**：在注入的最早期（挂钩之前）对 kill 封装函数头做"版本守卫 + mprotect 写 `mov w0,#0; ret`"中和；clone/exit 封装不动。
  3. **预期**：之后任何检测命中（含我们自己的 hook 痕迹）都无法执行自杀；检测日志可能周期性出现（无害）。
- 适用范围：本样本已证；"先拔牙再挂钩"的时序要求通用（校验命中到 kill 之间有 sleep(6) 缓冲，但不应依赖它）。
- 不适用/例外：kill 封装与业务逻辑复用（如用 kill 发非致命信号）时不能全 stub；exit/abort 系路径未在本样本出现（无 exit_group svc），其他游戏可能不同。

## 3. 反证、失效与最小区分实验

- 反例：若游戏改用服务端下发封禁（断线+客户端自杀走 Java System.exit）或 exit_group 直调，本中和无效。
- 失效条件：游戏更新改变封装地址/指令（版本守卫会拒绝并打 log，不会误伤）。
- 最小区分实验：中和后仍被杀 → 抓死亡瞬钱 logcat/tombstone 找新的退出路径。
- 停止条件：中和后仍有非 signal-9 的退出 → 分析该退出路径再定。
