## 2. 观察、解释与候选经验

- 观察事实：①功能整体错一格（开无敌→秒杀、开回血→无敌）：菜单 featNum=0 基列表下标（日志 `feature #0..#5`），CWJH 枚举按 1 基定义；②无 Category 占位的列表，0 号位即首个 Toggle，必须 0 基对齐枚举（不能照搬 ZXR 靠 Category 占位的 1 基做法）；③设备实际跑的是热更 0.2.83 game.js，2.1 静态分析的两处锚点（doDmg 签名、暴击掷骰）已不存在，字符串锚点部分仍命中但上下文已变，旧拼接会产生语法错误（⑤号括号 bug 属实现期错误，第一次真正执行才暴露）；④游戏自身热更流程（remote==local 时 `_checkNeedRestart` 首启返回 true → hotUpdate 落 undefined → `cc.game.restart()` 引擎内重启二次求值）是**正常流程**，日志上的 unhandledRejectedPromise + ScriptEngine cleanup + 二次 eval 不应误判为注入故障。
- 拟提炼经验（带前提）：
  1. **featNum**：星光菜单 featNum=菜单字符串列表的 0 基下标（含 Category 占位）。游戏枚举必须按下标对齐；无 Category 的列表从 0 开始。
  2. **锚点**：凡 JS/脚本热更的游戏（启动日志有 MS_PATCH/版本号对比），静态分析得到的锚点只对"分析时那份文件"负责；装机前必须从设备拉取实际运行文件（root: `su -c cat <files-dir>/<热更目录>/…`）重新核对每个锚点唯一性与上下文，拼接产物过 `node --check` 再出厂。
  3. **区分**：热更型游戏日志里"二次求值/引擎重启"先对照热更流程再归因注入。
- 适用范围：Cocos Creator 2.x JSB splice 模式；星光菜单框架。
- 不适用/例外：非热更游戏（锚点跟包走）；Category 占位法在列表确有分类头时仍可用。

## 3. 反证、失效与最小区分实验

- 反例：若菜单框架某版本改为 1 基下发，0 基对齐反而错位——以上线日志 `[开关] #N` 与 `feature #N` 对读即可即时发现（本轮正是靠这两行对出来的）。
- 失效条件：游戏热更改函数签名/重命名；星光菜单框架变更。
- 处置：锚点失效→重拉设备文件重校准（保留旧锚点做回退分支无害）。
- 最小区分实验：单开一个功能看实际效果 vs 菜单语义（本轮用户实测即此实验）。
