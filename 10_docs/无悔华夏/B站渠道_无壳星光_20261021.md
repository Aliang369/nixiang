## 3. 真实 DEX 精确导出（新工具，可复用）

易盾新版把业务 DEX 解密成 ART `InMemoryDexFile`，**盲扫全内存找不到 `dex\n035`**（4399 当年盲扫 0 命中）。
本渠道实测两个额外坑：

1. **不再搜 035**：本包内存态是 **ver 039**（`dex\n039`）。只按 `dex\n035` 搜必 0 命中。
2. **magic 跨 mapping 边界**：真实 DEX 的 mmap 起点比 `dex\n` 晚 4 字节（`+0x...ffc`），
   即 `"dex\n"` 落在**前一段 VMA**。扫描器必须额外读 `region_start-4` 做边界判定，否则整份 DEX 被跳过。

工具：`04_scripts/无悔华夏/whrhx_mem_dex.c`（只读，root 直接读 `/proc/<pid>/mem`，**不 ptrace、不注入**）：

```bash
NDK=~/Library/Android/sdk/ndk/27.0.12077973/toolchains/llvm/prebuilt/darwin-x86_64/bin
# 注意：-static 会被 bionic 以 "TLS segment is underaligned" 拒绝执行；动态链接即可（无 PT_TLS）
$NDK/aarch64-linux-android26-clang -O2 -o /tmp/whrhx_mem_dex 04_scripts/无悔华夏/whrhx_mem_dex.c
adb push /tmp/whrhx_mem_dex /data/local/tmp/ && adb shell "su -c 'chmod 755 /data/local/tmp/whrhx_mem_dex'"
P=$(adb shell pidof com.yhhy.whrhx.bilibili | tr -d '\r')
adb shell "su -c '/data/local/tmp/whrhx_mem_dex $P /data/local/tmp/whrhx_dex5'"
```

- 顺带用第 4 参数做「内存里有没有某个类」的定点检索：
  `whrhx_mem_dex <pid> <outdir> com/tpf/sdk/unity/GameActivity`（先定位承载 DEX 的 region，再回溯）。
- **frida 路线在本包不可用**：`attach` 让进程 `exit(0)`（易盾反调试），
  `frida-dexdump -f` spawn 也超时；本工具不注入，壳无感知。
- 导出后按「类名集合 + 大小 + 是否含 `com/tpf`、`excelliance`、`GameActivity`」认领：
  框架/系统 boot dex（`android.*`、`java.*`，8-10 MB）会被一并扫出，**不要**当成业务 DEX 注入。

## 5. Manifest 两处都要改（本轮踩坑）

乐变 overlay **不读** `android:name`，而是按 `meta-data LEBIAN_APPLICATION` 反射实例化 Application。

- 只改 `android:name` 的结果：主进程**根本没跑 StarryApp**（logcat 只有 `:pushservice`/`:lebian.dns` 两条
  `StarryApp: attachBaseContext skip native`），无 `libstarry_magic` 映射、无菜单。
- 正确做法：
  ```xml
  android:name="com.starry.magic.StarryApp"
  <meta-data android:name="LEBIAN_APPLICATION" android:value="com.starry.magic.StarryApp"/>
  ```
  再补 `MenuService`（`foregroundServiceType=specialUse`）+ `SYSTEM_ALERT_WINDOW` + `FOREGROUND_SERVICE_SPECIAL_USE`。

## 6. 装机后三个必须修的问题（本轮实测，全部已修）

### 6.1 `dlopen failed: cannot locate symbol "__emutls_get_address"`

- 现象：so 文件在包内、`System.load(绝对路径)` 仍失败；菜单“native 未就绪”。
- 根因：`Application.mk` 是 `APP_PLATFORM := android-21`，NDK 对 arm64 也生成 emulated TLS 引用
  （`__emutls_get_address`）；而**本游戏自带的 `libc++_shared.so`（911,696 B）导出的 emutls 符号数 = 0**
  （NDK r27 自带的同名库 = 1）。九游那份能加载是因为加载路径里先有能解析该符号的运行库。
- 修法：`Android_whrhxbili.mk` 加 `-fno-emulated-tls`（只影响本渠道）；构建脚本加反例门禁
  `grep -a "__emutls_get_address"` 命中即失败。新 so md5 `1982d381…`，232,680 B。

### 6.2 乐变 overlay 的 ClassLoader 命名空间里没有 base APK 的 lib 目录

- `ApplicationInfo.nativeLibraryDir` 才是包内 so 的真实目录；乐变换 ClassLoader 后
  `library_path` 指向 `lebian/<pkg>-1/lib/arm64`（负载没落地时该目录不存在）。
- 修法：`StarryNativeLoad` 新增 `loadFromNativeLibraryDir()`，按绝对路径加载，并**先预加载同目录
  `libc++_shared.so`**（本 so 的 DT_NEEDED 含它）。菜单侧登录/刷新都会走幂等加载。

### 6.3 乐变会吞掉 Application 生命周期

- 现象：主进程 `StarryApp.attachBaseContext/onCreate` 的日志整段缺失（logd 在进程启动头几秒会丢日志，
  别把“没日志”当“没执行”）；`MenuService` 却照常起来。
- 修法：新增 `com.starry.magic.boot.StarryInitProvider`（ContentProvider，AMS 在 Application 后、
  首个组件前稳定创建），主进程内做一次幂等 `ensureLoaded` + 4s 后兜底 `MenuService.start`；
  同时把诊断写入 `<pkg>/files/starry_init.log`（logd 丢日志时唯一的取证口）。
- **判定入口**：`adb shell su -c 'cat /data/data/com.yhhy.whrhx.bilibili/files/starry_init.log'`
  → 正常应为 `already done path=…/lib/arm64/libstarry_magic.so`。
