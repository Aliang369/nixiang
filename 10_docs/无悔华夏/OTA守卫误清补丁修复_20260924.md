## 3. 根因

守卫原实现（`PlayOtaManager.invalidateOtaIfApkUpdated`）用 `PackageInfo.lastUpdateTime` 判断「APK 是否比 OTA 新」：

- 设备实测 `dumpsys`：`firstInstallTime == lastUpdateTime == 2026-09-23 20:20:20`（1790166020076）
- 但乐变（免安装 overlay）会把应用可见的 `lastUpdateTime` 抖到 **20:24:54**（1790166294806，= overlay `base.odex.apk` mtime）
- 旧实现的分支：

```java
long stored = Preferences.getOtaApkLastUpdateTime();
if (stored != 0L && nowLu > stored && hasOta) { clearLocalOta(); setOtaApkLastUpdateTime(nowLu); return true; }
if (stored != nowLu) Preferences.setOtaApkLastUpdateTime(nowLu);   // ← 关键
```

`else` 分支把 stored **写回当前进程看到的那个值**。于是一次进程看到 20:24:54（写 1790166294806）、下一次看到
20:20:20（写回 1790166020076），`stored` 在 20:20:20 ⇄ 20:24:54 之间来回抖 ⇒ **每次冷启动都满足 `nowLu > stored`
⇒ 每次下载都被清（死循环）**。这不是「补丁没生效」，而是「补丁记账被清」。

⇒ 功能一直在生效（`/proc/<pid>/maps` 里还映射着已删除的 OTA so inode），坏的只是 OTA 通道的记账。

## 4. 修复（方案 B：so 内烘焙构建戳）

判据从「APK 安装时间」换成「**包内 so 与 OTA so 各自的构建戳**」：只有 `apkStamp > otaStamp` 才清 OTA。
戳是 so `.rodata` 里的 ASCII 字面量 `STARRYSTAMP1:EPOCH=<秒>;`（hidden visibility + strip，dlsym 拿不到，故按字节扫）。

| 文件 | 改动 |
|---|---|
| `app/src/main/jni/Includes/StarryStamp.h`（新） | `STARRY_BUILD_EPOCH` 兜底 + `STARRY_STAMP_MARKER` + 三个符号声明 |
| `app/src/main/jni/Includes/Utils.cpp` | 定义 `kStarryBuildStamp[]` / `starry_build_stamp_marker()` / `starry_build_epoch()`（32/32 个 `Android_*.mk` 都编这个 TU，故不用动 mk） |
| `app/src/main/jni/Application.mk` | `STARRY_BUILD_EPOCH := $(shell git log -1 --format=%ct …)` + `APP_CPPFLAGS += -DSTARRY_BUILD_EPOCH=$(STARRY_BUILD_EPOCH)` |
| `app/src/main/jni/Main.cpp` | `mb_nativeGetBuildStamp` + 注册 `nativeGetBuildStamp ()Ljava/lang/String;`（日志 19/19 → 20/20） |
| `.../bridge/ModBridge.java` | `nativeGetBuildStamp()` + `getBuildStamp()` |
| `.../ota/OtaSoStamp.java`（新） | 扫 so 字节取戳；`of(File)` / `apkStamp(Context)`（nativeLibraryDir ±abi、`sourceDir` 推导的 legacy lib、乐变 `lebian/*/lib/<abi>/`、APK zip 条目兜底，取最大值） |
| `.../ota/PlayOtaManager.java` | `invalidateOtaIfApkUpdated` 重写为戳比对；不再读/写 `lastUpdateTime` 与 `ota_apk_last_update_time` |

判定语义：

- `apkStamp > otaStamp` → 包内更新 ⇒ 清 OTA（覆盖安装后旧 OTA 不再挡新 so）
- `otaStamp == 0`（无戳 = 旧时代产物）→ 视为比包内旧 ⇒ 清
- 相等或 OTA 更新 → 保留（日志 `keep OTA: apkSoStamp=… otaSoStamp=…`）

⚠ `ApplicationInfo.legacyNativeLibraryDir` / `primaryCpuAbi` 是 `@hide`，公开 SDK 编不过 ⇒ 前者用
`new File(ai.sourceDir).getParentFile()/lib` 推导，后者用 `Build.SUPPORTED_ABIS`。

## 8. 教训

- **不要用 `PackageInfo.lastUpdateTime` 判「覆盖安装」**：乐变（免安装 overlay）会把它在真实安装时间与 overlay
  APK mtime 之间来回抖；更糟的是「值不同就回写 stored」这种自愈逻辑会把判据彻底变成随机数。判据必须是**内容自带
  的单调量**（本 so 的构建戳），而不是**环境的时间戳**。
- 修 OTA 守卫这类「记账」问题要同时看三处：服务端 manifest 的 `so_sha256`、包内 so、运行时实际加载的 overlay so
  ——三者一致时，症状一定在记账侧，不在功能侧。
- 菜单 dex 重建后与上一轮做 `baksmali diff`：差异面必须只有本次改动的类（本轮 = ModBridge / OtaSoStamp / PlayOtaManager），
  这是最快发现「顺手改坏了别的类」的手段。

## 10. 第二个根因：乐变 overlay 多 classloader 导致 OTA so 加载被拒（2026-09-24 02:00 定位）

守卫修好、OTA ver=2 下载留存之后，用户报菜单显示「暂无功能列表（native 未就绪）」并质疑「是你的 so 没做好吧」。
**结论：so 没问题，是 Java 侧加载器在多 classloader 下直接 `return false`。**

**机制**：乐变 overlay 会把 Application/Service 二次实例化到**另一个 classloader**（负载 `lebian/<pkg>-1/base.odex.apk`，

Android nativeloader 禁止**同一个 so 文件**被两个 classloader 打开，于是那个 classloader 里 `System.load(OTA 绝对路径)` 抛错，
而 `StarryNativeLoad.ensureLoaded` 的 catch 分支**直接 `return false`**（原注释：有 OTA 文件却 load 失败时不要静默退回 APK）
⇒ 该 classloader 里 native 未注册 ⇒ 功能列表空 + `nativeGetPinnedCert` 失败 = 用户看到的「HTTPS 证书未初始化」。

**为什么以前不暴露**：旧守卫每次启动都清掉 OTA so ⇒ `findOtaSo` 返回 null ⇒ 两个 classloader 各自
`System.loadLibrary("starry_magic")`（各加载自己路径下的副本，**不同路径**不触发该限制）⇒ 都注册成功。
守卫修好、OTA so 存活后，才第一次走到那行 `return false`。

**修复**（`mod菜单/starry-mod-menu/app/src/main/java/com/starry/magic/ota/StarryNativeLoad.java`）：给本 classloader
复制一份**独占副本**再 load，内容仍是 OTA so（不退回包内旧 so，差异探针语义不变）：

- 新增 `COPY_PREFIX = "libstarry_magic_ld_"`、`COPY_SLOT = Long.toHexString(new Random().nextLong() & 0x7fff…L)`（每个 classloader 静态各一份）、
  `copyName()`、`copyForThisClassLoader(File ota)`（清掉同目录 60s 前的旧副本 → 流式复制 → 校验长度）；
- OTA 分支 catch 改为：记 E 日志 → `System.load(copy)`（日志 `loaded OTA so (classloader-private copy): `）→ 再失败
  `System.loadLibrary("starry_magic")`（日志 `OTA so unusable in this classloader; loaded local so via loadLibrary`）→ 仍失败才 `return false`。

## 11. 副作用修复：`install -r` 清空乐变负载 ⇒ 游戏退回包内 il2cpp（RVA 全表失配）

`install -r` 会清空 `lebian/<pkg>-1/`，而**乐变不会自动重下**（4399 先例同样现象）。此时游戏退回映射
APK 内置的 `lib/arm64/libil2cpp.so`（sha256 `d5a977241ab9c485597b1cd6cc2de9574a43ca7d30d8dc45adc1dc60245ce7e3`），
mod 的 RVA 表是按**乐变热更负载**那份校订的（201,381,272B `c04afff4…`），于是日志每 200ms 刷：


## 13. 教训（第二轮追加）

- **乐变（免安装 overlay）游戏里，任何 native so 都不能只按「绝对路径 load 一次」**：overlay 会把 Application/Service
  二次实例化到另一个 classloader，Android 禁止同一 so 文件被两个 classloader 打开。要么每 classloader 复制独占副本，
  要么退到 `loadLibrary`（各加载自己路径下的副本）。
- **`return false` 这类「宁可失败也不降级」的防御分支，会在前置条件被修好后第一次执行**：修守卫时要把所有依赖
  「OTA so 不存在」的隐含假设（这里就是加载器路径）一起过一遍。
- **`install -r` 在乐变游戏上不是无害操作**：它会清空热更负载且乐变不会自动重下，游戏会退回包内 il2cpp（RVA 全表失配）。
  装机后必须复核负载的 `libil2cpp.so` 仍是校订基准；不是就重置 `lebian/resourceInfo.cfg` 的 `currVer` 后拉起两次。
