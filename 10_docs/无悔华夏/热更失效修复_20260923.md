## 4. 「资源不足」的**执行期**门 = `CountryData.CheckRes`

## 12.11 OTA（乐变热更）与 mod so / 菜单 dex 的关系（回答用户提问）

**B. 负载是按「当前安装的 APK」重建的（实证）**：

## 12.13 so / dex 兼容性与分发（回答「别人用这份 so 会不会闪退/无效」）

**一句话：本轮 so 一个字节都没改（`3b754bba…` / md5 `c34f9dc0…`，与 §11 验收那份同一份，工作区 = 包内），
只换了 `classes2.dex`；而 dex↔so 的 JNI 契约是「只增不减」，两个方向都真机验证过 ⇒ 换菜单不会让 so 出问题。**

**JNI 契约实测**（`bash 01_tools/smali/baksmali d <dex>` 双 dex 对比 + `llvm-readelf`/`strings` 看 so）：

```
so  : JNI_OnLoad → ] FindClass ModBridge → ] RegisterNatives 19/19   （静态注册 19 个，so 内日志串实证）
新 dex native 声明 20 条 = ModBridge 19 条 + com.starry.magic.dwdlm.DwdlmApplication.prepareSecureShell()V
旧 dex native 声明 19 条 = 同一批 ModBridge 19 条（一条不多、一条不少，签名完全一致）
```

- 新 dex 比旧 dex 多的**唯一**一条不在 ModBridge，而在**别的游戏**的入口类 `dwdlm.DwdlmApplication`
  （无悔华夏走 `StarryApp`，该分支从不执行）⇒ 不存在「旧 so 缺实现」的路径。
- ⇒ **旧 dex + 新 so 安全**（§11 装机验收就是这一组合，用户实测通过）；
  **新 dex + 新 so 安全**（本轮实测通过）。反向更老的 so 才需谨慎，但对本包不触发。

**三条保险丝 ⇒ 失败一律表现为「无效」，不是「闪退」**：

1. dex 侧三处 `System.loadLibrary("starry_magic")` 都 `.catch Ljava/lang/UnsatisfiedLinkError;`
   （`DexInstaller` / `MainActivity` / `ModBridge`，失败只打 `Failed to load native library` / `loadLibrary starry_magic failed`）。
2. dex 侧还有 OTA so 优先逻辑：`<files>/starry_native/libstarry_magic.so` 存在但加载失败时
   → `OTA so exists but load failed, skip apk loadLibrary`（**宁可歇菜也不混版本**）。
3. so 侧所有钩子都做 RVA + 按名双路校验，落空只打 `[Whrhx] %s paths failed (rva=0x… alt=0x… name=…)` 后跳过，不 abort。

**真正会让这份 so「无效」的四个条件（都与菜单无关，分发前逐条确认）**：

| 条件 | 现象 | 处理 |
| --- | --- | --- |
| 游戏的 `libil2cpp.so` 版本不同（热更级别 ≠ 当前 payload `c04afff4…` / gver242） | 钩子全部落空，logcat `rva miss` 刷屏，功能静默无效 | 重跑 `whrhx_recalibrate_rva.py` → `whrhx_check_kexpect.py` → 重出包 |
| game_id 不是 `whhx`（日志 `auth game_id=whhx`） | 命名空间/开关全不匹配 | 不能跨游戏复用 |
| 渠道 = 好游快爆（KB 分支） | `RVA_KB_*` 本轮未校订（12 条 kExpect 失配，编译期未启用） | 需按 KB 运行时 so 重校 |
| 设备是 32 位（armeabi-v7a） | 包内 `lib/armeabi-v7a/` 只有游戏自己的 `libil2cpp.so`/`libunity.so`，**没有 `libstarry_magic.so`**（底包星空包本来就如此，非本轮引入）⇒ 加载失败被 catch，菜单在、功能全无效 | 需要编 v7a 版 so 才有 32 位支持 |

**分发建议**：dex 与 so **成套发**（= 本轮正式包）；退一步「旧 dex + 这份 so」也可；
**不要**「新 dex + 更老的 so」。若走菜单自带的 OTA so 通道（`starry_native/libstarry_magic.so`），
推错版本只会「无效」不会崩，且**不会回退到包内那份** ⇒ 推送前先在同一游戏版本 + arm64 真机自测。
