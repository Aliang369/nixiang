## 关键证据

### 1. 蒙华科技研发最终调用普通政策执行

`MengHuaTechPolicyData.Research()` RVA `0x762BEB4`：

1. 读取科技研究状态。
2. 已研究、不可研究、研究中分别走提示分支。
3. 可研究分支通过 `MengHuaRecordConfigMgr.GetTechPolicyConfig(TechId)` 取得配置。
4. 取配置中的 `PolicyId`，字段偏移 `MengHuaRecordTechPolicyConfig.PolicyId @ 0x40`。
5. 取当前国家的 `PolicyDataMgr`。
6. 调用 `PolicyDataMgr.ExecutePolicy(PolicyId, 0, true)`，RVA `0x7868DB4`。

因此“科技研发”没有单独的时间字段。它的 `Researching / Researched` 状态由关联政策的执行状态派生。

### 2. 普通政策有明确持续时间

`PolicyConfig.CostTime @ 0xD8`。  
`PolicyConfigMgr.GetPolicyCostTime()` RVA `0x785FB2C` 返回至少 1 的整数时长，并处理特殊资源时长修正。

`PolicyDataMgr.ExecutePolicy()`：

1. 创建一个 `PolicyData`。
2. 以 `GetPolicyCostTime()` 的结果写入 `PolicyData.m_remainTime @ 0x14`。
3. 将政策加入激活/工作列表。
4. 调用 `UpdatePolicyTime(0, true)` 刷新状态。

### 3. 原生加速机制已经存在

`PolicyData`：

- `m_remainTime @ 0x14`
- `m_repeatRemainCd @ 0x18`
- `m_isAccelerating @ 0x1C`
- `PolicyData.SetAccelerate()` RVA `0x78618F4`：写入 `m_isAccelerating = 1`
- `PolicyData.GetRemainTime()` RVA `0x78619E8`：加速时除以 `CommonValue.PolicyAccelerateRate @ 0xA0`

`PolicyDataMgr.UpdatePolicyTime(float passTime, bool needSendMsg)` RVA `0x7863E6C`：

- 遍历激活中的政策。
- 剩余时间大于 0 时扣减。
- 启用 `m_isAccelerating` 时，扣减量再乘 `CommonValue.PolicyAccelerateRate`。
- 剩余时间降到 0 后调用 `HandleExecuteFinish()`。

这证明加速不必伪造显示，直接放大该方法的 `passTime` 即可走原生进度和完成逻辑。

### 4. 立即完成应走原生完成链

`PolicyDataMgr.FinishPolicyTimeAnyway(int)` RVA `0x7865CA8`：

- 找到 `PolicyData`。
- 如果 `0 < m_remainTime < CommonValue.FinishPolicyMaxTime`，把 `m_remainTime` 写成 `0.1f`。
- 下一次时间更新归零后进入正常完成链。

`PolicyDataMgr.HandleExecuteFinish(PolicyData, bool, bool)` RVA `0x786475C` 是归零后的统一完成入口，负责：

- 写入 `LastFinishPolicyId`
- 增加执行次数
- 执行政策效果和联动
- 触发记录、任务、Buff、剧情等
- 调用本地 `SaveData()`

`HandleExecuteFinish()` 的静态调用链中没有 `TimeSaveNetMgr.TryFinishPolicyReq()`，也没有其他网络请求。也就是说，正常倒计时完成本身就是本地结算并落盘。

### 5. 服务端“立即完成”是另一条付费/月卡路径

`TimeSaveNetMgr.TryFinishPolicyReq()` RVA `0x6FDF7A4` 确实存在，调用点为月卡/道具式的 `TryFinishPolicyBtn` 流程。

这表示：

- 游戏官方“立即完成”功能可能要求服务端批准。
- 但政策自然到时完成、`HandleExecuteFinish()` 和本地存档不走该请求。
- 客户端方案会绕过官方请求，可能存在云存档或结算时重算风险，但静态代码中未发现即时拒绝或回滚调用。

## 建议实现

### 方案 A：研发加速滑条

Hook：

- `PolicyDataMgr.UpdatePolicyTime(float, bool)`，RVA `0x7863E6C`

逻辑：

- 功能关闭：原参数调用原函数。
- 功能开启：仅把大于 0 的 `passTime` 乘以倍率，例如 `2 / 3 / 5 / 10`。
- 保持 `needSendMsg` 原值，不直接改政策对象。

优点：改动小，复用游戏原生扣除和完成逻辑。  
注意：这是政策计时总入口，会同时影响正在执行的非科技政策及重复冷却。若只想影响科技关联政策，需要按当前激活政策的 `m_id` 与科技 `PolicyId` 映射过滤，但实现复杂度更高。

### 方案 B：研发立即完成

两种稳定方向：

1. Hook `PolicyDataMgr.UpdatePolicyTime()`，功能开启时把 `passTime` 替换为大值，例如 `86400`，调用原函数完成现有一批激活政策。
2. 只针对新研发：Hook `MengHuaRecordMgr.ResearchTech(int)` 或 `PolicyDataMgr.ExecutePolicy(int, float, bool)`，原函数返回后，对该 `PolicyId` 调用 `UpdatePolicyTime(大值, true)`。

优先方向 1。它直接复用游戏自己的完成函数，后续效果、存档、UI 刷新都按原链执行。

不建议只把 `m_remainTime` 写 0 后等下一帧。实时剧本通常可以，但回合制剧本不一定每帧走 `UpdatePolicyTime()`，且直接改字段不如调用原入口可复现。

## 风险与验证项

1. 回合制剧本：必须分别验证实时流逝剧本和回合推进剧本。`PolicyData.AddTurnBased()` 与 `UpdateAddTurn()` 是另一条扣时链。
2. 云存档/活动结算重算：静态链未发现即时上报，但无法证明服务端在所有结算场景都不会校正。
3. 重复政策与冷却：总入口加速会一起加速 `m_repeatRemainCd`，需要决定是否接受。
4. 主线程：执行和完成 Hook 必须在游戏主线程上下文，避免 UI/存档对象的跨线程调用。
5. 重复完成保护：立即完成开启后，只处理仍在激活列表中的政策，已执行政策不得再次调用完成入口。

## 实现边界

建议把功能作为独立菜单项加入，不修改现有金币、食物、军队、人口、瞬间胜利和游戏加速链路。菜单可拆成：

- `政策/科技研发加速`：滑条 `1..10`
- `政策/科技研发立即完成`：开关

在用户确认采用哪一档前，不改 `WhrhxMod.cpp`，不构建和安装。
