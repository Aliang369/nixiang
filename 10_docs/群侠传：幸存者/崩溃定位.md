# 群侠传：幸存者 0.2.3.9 —— 启动 SIGSEGV 崩溃定位与修复

> 设备 OPD2404 / f9a116a2（root），Godot 4.6.1.stable.official.14d19694e，包名 com.nenlystudio.qunxiasurvivor.cn
> 结论时间 2026-11-12。全部结论均为真机实测（装机 → logcat → 进程存活）。

## 1. 症状

mod 包启动约 3~4 s 后 SIGSEGV，崩在渲染线程：

```
F libc: Fatal signal 11 (SIGSEGV), code 1 (SEGV_MAPERR), fault addr 0x0 in tid (GLThread 56)
F DEBUG: Cause: null pointer dereference
#00 libgodot_android.so ... (Java_org_godotengine_godot_GodotLib_step 路径)
```

崩溃前真正的根因日志（关键就是第一行）：

```
E godot: ERROR: Error decompressing GDScript tokenizer buffer.
E godot:    at: set_code_buffer (modules/gdscript/gdscript_tokenizer_buffer.cpp:154)
E godot: SCRIPT ERROR: Parse Error: Could not parse global class "EconomyStore" from "res://scripts/core/model/economy_store.gd"
E godot: SCRIPT ERROR: Compile Error: Failed to compile depended scripts.
E godot: ERROR: Failed to instantiate an autoload, script 'res://scripts/autoload/run_state.gd' does not inherit from 'Node'.
```

即：**autoload 链（definition_library → run_state）因 .gdc 加载失败而整体编译失败，引擎在缺少 autoload 的状态下继续跑渲染循环 → GLThread 空指针崩溃。** SIGSEGV 只是后果，不是原因。

## 3. 根因

**替换 `assets/**.gdc` 时，新条目的「解压后尺寸」必须与原条目完全一致；尺寸一变，引擎就报
`Error decompressing GDScript tokenizer buffer.`**

- 与「内容」无关：把 economy_store.gdc 换成解压后内容一模一样的重压版（长度 6630→6638）照样报错（C）。
- 与「压缩器」无关：GDRE 自带 zstd 与 zstd CLI 1.5.7 两种输出都报错（A、A2、C）。
- 与「重打包/重签」无关：原包重签、以及逐字节相同的条目替换都干净（D、F）。
- 唯一变量就是**条目长度**：把补丁后的文件用 zstd skippable frame 填到原长度，立刻恢复正常（G、H、I）。
- 证据落点：错误抛在 `gdscript_tokenizer_buffer.cpp:154`，即
  `ERR_FAIL_COND_V_MSG(result != decompressed_size, ...)` —— 引擎拿到的字节数与解压结果对不上。
  条目长度一变，读到的缓冲区就与 zstd 帧错位（截断或越界），解压必然失败。

**未定/待验证**：为什么引擎会按「原长度」读（Godot Android 资源读取层是否有长度缓存、还是 CD/本地头细节所致）
尚未拿到源码级证据。工程上按「等长」这条实测规律处理即可；**不要据此推断其它 Godot 游戏同样如此**。

## 4. 修复配方（可复用）

1. 反编译 → 改 → 回编（命令不变）：
   ```
   "$BIN" --headless --bytecode=4.5.0 --decompile=<gdc> --output=<dir>
   "$BIN" --headless --bytecode=4.5.0 --compile=<gd>  --output=<dir>
   ```
2. **等长填充**（新增步骤，必需）：
   ```bash
   python3 03_decompiled/群侠传：幸存者/pad_gdc.py <回编后的.gdc> <原条目长度> <输出.gdc>
   # 本作三个挂点：economy_store 6630 / health_component 2841 / combat_hit_pipeline 34169
   ```
   脚本把 token 流用 zstd(6/9/12/15/19 逐级尝试) 重压，再用 skippable frame（magic 0x184D2A50）
   补齐到目标长度。**补丁内容的压缩后体积必须 ≤ 原长度-20**，否则要换更小的挂点或提高压缩级别。
3. 原条目长度自查（别手抄数字）：
   ```bash
   unzip -l <原包> | grep -E "health_component.gdc|economy_store.gdc|combat_hit_pipeline.gdc"
   ```
4. 重打包 + 签名 + 装机（沿用既有配方）：zipfile 重写（保留 Stored/Deflate）→ `zipalign -f 4` →
   `apksigner sign --ks 01_tools/starry_release.jks --ks-key-alias starry ...` → `adb install -r`。
5. 验收三条：`adb shell pidof <pkg>` 有值、logcat 无 `Fatal signal`、logcat 出现
   `godot: SessionSentinel: stage=main_menu`（约 20 s 到 opening_cg，约 60~120 s 到 main_menu）。

## 5. 三类功能 + 登录补丁的最终状态

- 无敌：`health_component.gdc` `bind_player_vitals()` 末尾 `invulnerable = true`（只对玩家，敌人走 `bind_row_storage`）。等长填充 2841。
- 伤害 ×10：`combat_hit_pipeline.gdc` 在 `target_damage = hit_event.settle_damage() * damage_multiplier` 之后加 `target_damage *= 10.0`。等长填充 34169。
- 无限银钱：`economy_store.gdc` `set_silver()` 与 `install_draft()` 里 `silver = 999999999`。等长填充 6630。
- 登录：`classes.dex` 4 处 smali（TapSignKit.getSign 固定签名 / isGatekeeperLoadedSuccessfully 恒 true /
  showErrorToast 直接 return / DefaultTapLoginFragmentProvider 强制网页登录）。dex 条目不受等长约束
  （classes.dex 长度变化也能跑，见 H vs I）。
- 仅 dex（B 包）对照：与 I 同源、只换 dex。**该轮装机卡死（adb install 长时间无返回，已 kill），未取得结论**；
  dex「不引入崩溃」由 H（仅 gdc，正常）→ I（H + dex，同样正常）这组对照间接证明，若要严格隔离可补测。

## 6. 装机方式备注（lead 纠正）

§2 矩阵用的是 `adb uninstall` + `adb install --no-incremental`（清数据、最干净的对照，代价是慢）。
**日常迭代不必卸载**：本作所有测试包都是同一把 starry 密钥签名，签名一致，直接 `adb install -r <apk>` 覆盖安装即可
（卸载会清存档且慢；只有从 NenlyStudio 原版换到 starry 签名那一次必须 uninstall）。

最终包已用 `adb install -r` 复验：设备内 base.apk md5 = 8df42d76a4cc0e5c9fcc66c567df034b（与本地产物一致），
启动后 57 s 到 `stage=main_menu`，全程无 `Fatal signal`、无 `Error decompressing`。
