## 4. 「二进制 diff 只落在你改的类」这条：为什么做不到，以及真正的判据

**做不到，且与本次改动无关**——smali 全树重编会重排整个池与调试表。控制实验（零改动往返）：

```
bash 01_tools/smali/smali assemble --api 25 -j 1 -o /tmp/old_rt25.dex 13_scratch/qxzxcz_dexdiff/old
ls -l /tmp/old_rt25.dex                        → 7,964,596 B    # 原 classes.dex 7,887,652 B（+76,944）
cmp -l /tmp/old_rt25.dex classes.dex | wc -l   → 7,551,542      # 占全文件 95.8%
```

按节区看根因（自写 map_list 解析，脚本 /tmp/dexinfo.py）：

| 节区 | 原 | 零改动重编 | 差 |
|---|---|---|---|
| debug_info 条目数 | 20,753 | 32,961 | **+12,208** |
| string_id | 51,154 | 51,153 | −1 |
| encoded_array | 560 | 557 | −3 |
| annotation_set_item | 11,896 | 11,897 | +1 |
| code_item | 39,650 | 39,650 | 0 |
| class_data | 5,843 | 5,843 | 0 |

⇒ 体积增长几乎全是 **debug_info**（D8 对部分方法不写调试信息，smali 补齐），代码本身零变化。
旧版 shipped 的 classes_mod.dex 也是同一形态（+76,588 B、string −3、method −1、debug_info +12,205），**在真机上可用** ⇒ 该噪声有实机先例。

因此本任务的机器判据取「**baksmali 级差异 ⊆ 3 个锚点类**」（§3.3），它比字节级更有意义：字节级对齐下任何一处代码长度变化都会把后续所有 offset 平移，永远无法「只落在某个类」。

## 7. 真机 1001 修复（2026-11-15 16:31 实测后补）

### 7.1 现象与证据链（1001 到底从哪来）

真机日志（lead 反馈，pid 24448，16:31:03 / 16:31:21 各一次）：

```
E godot: WARNING: SteamService: TapSDK 初始化失败（1001）：TapSDK: 包名、签名错误。详见 ErrLog，只做本地对账
E TapSDK-TapSdkCore: [Openlog/src/tapsdk_core.cpp:61] TapSdkCore had already been started! Updating callbacks...
E TapSDK-TapSdkCloudSave: CloudSaveSDK ... client_id wyb6mhuajd4glbws6b, sdk_module_ver 4.11.0
```

逐环定位（全部为本包 0.2.3.10 现取）：

| 环 | 证据 | 命令/位置 |
|---|---|---|
| 1001 = 哪个错误码 | `TapInitErrorCode.CONFIG_ERROR = 0x3e9`（0x3e9 = 1001） | `com/taptap/sdk/initializer/api/TapInitErrorCode.smali:33` |
| 谁产出 0x3e9 | 初始化链路里唯一一处 `const/16 v2, 0x3e9` → `new-instance TapInitState$Failed` → `_initStateFlow.tryEmit` | `GatekeeperRepository$initialize$1.smali:331` |
| 哪个分支 | 只在 `ApiErr$INVALID_CLIENT` 命中时进入；其它异常走 `commitDegradedSuccess()`（= Success） | `GatekeeperRepository$initialize$1.smali:280-311` |
| 文案「包名、签名错误」出自哪 | 不是本地字符串：全 smali 树 `grep 包名/签名错误` **0 命中** ⇒ 是服务端 msg，经 `TapNetworkException.getErr().getMsg()` 塞进 `Failed(0x3e9, msg)` | `grep -rn "签名错误\|包名" 0.2.3.10/smali` |
| 谁把 code/message 送到 Godot | `QxTapTapPlugin$init$1$1.onInitFail(ILjava/lang/String;)V` → `emitSignal("init_finished", [false, code, message])` | 同类 `:63` |
| Godot 侧后果 | `_on_init_finished` 打 warning 并置 `_init_state = FAILED` ⇒ `supports_login()` 恒 false ⇒ 点登录无效 | `gd/taptap_android_backend.gd:230-240` |

结论：**1001 是服务端对「改签包的签名指纹」的拒绝**，与 Java 侧门闩是否放行无关——门闩只决定「谁去读 initState」，改不了「服务端回什么」。
回灌 `getSign` 让它上报官方证书指纹，是消掉 1001 的唯一 dex 侧手段（与 0.2.3.9 旧版同法）。

### 7.2 native 是否自己验签 ⇒ 不需要动 native

```bash
$ strings -a libtapsdkcore.so   | grep -i 'getPackageInfo|GET_SIGNATURES|PackageManager'   # 0 命中
$ strings -a libthemis.so       | grep -i 'getPackageInfo|GET_SIGNATURES|PackageManager'   # 0 命中
$ strings -a libcloudsave_sdk.so| grep -i 'getPackageInfo|GET_SIGNATURES|PackageManager'   # 0 命中
```

- 三个 so 里出现的 `Digital Signature` / `ICC or token signature` / `unable to decrypt CRL's signature` 是 BoringSSL/OpenSSL 的 X.509 常量，不是 APK 签名校验。
- dex 侧 `GET_SIGNATURES` 全包**只有** `TapSignKit` 一处（`grep -rln GET_SIGNATURES` 唯一命中）；`TapSdkCore` 的 start 只在日志里报「already been started」，不参与 1001 判定。
- ⇒ 签名指纹仅由 Java 的 `TapSignKit.getSign` 提供；native 不读 PackageManager，**本次不需要动 .so**。

### 7.3 补丁 D：TapSignKit.getSign 回灌官方证书指纹

文件：`0.2.3.10/smali/com/taptap/sdk/kit/internal/utils/TapSignKit.smali`

```smali
.method public final getSign(Landroid/content/Context;)Ljava/lang/String;   # 原体 83 行
    .locals 3
    const-string v0, "context"
    invoke-static {p1, v0}, Lkotlin/jvm/internal/Intrinsics;->checkNotNullParameter(...)V
    const/4 v0, 0x0
    :try_start_0
    invoke-virtual {p1}, Landroid/content/Context;->getPackageManager()Landroid/content/pm/PackageManager;
    ... getPackageInfo(packageName, 0x40) → signatures → firstOrNull → Signature.toByteArray()
    invoke-static {p1}, Lcom/taptap/sdk/kit/internal/utils/CommonUtils;->getMD5([B)Ljava/lang/String;
    :try_end_40 .catch Ljava/lang/Exception; {...} :catch_41
    return-object p1
.end method
```

替换为（与 0.2.3.9 旧版改法逐字同义）：

```smali
.method public final getSign(Landroid/content/Context;)Ljava/lang/String;
    .locals 3

    const-string v0, "6b013f42541e222db7f2153a138ab301"

    return-object v0
.end method
```

常量来源（命令输出）：

```bash
$ md5 -q 03_decompiled/群侠传：幸存者/cert/cert.der
6b013f42541e222db7f2153a138ab301
```

`Signature.toByteArray()` 的字节 = 证书 DER，故 `getSign()` 的官方返回值就是 `md5(cert.der)`；与旧版硬编码值完全一致（旧版 smali 见 `03_decompiled/群侠传：幸存者/smali/.../TapSignKit.smali:59-65`）。

锚点断言（脚本内两条，缺失即 die）：

1. `.method public final getSign(Landroid/content/Context;)Ljava/lang/String;` 出现 1 次
2. `invoke-virtual {v1, p1, v2}, Landroid/content/pm/PackageManager;->getPackageInfo(Ljava/lang/String;I)Landroid/content/pm/PackageInfo;` 出现 1 次（证明还是原版方法体，不是已改过的）

**是否还有第二个签名入口 ⇒ 没有**：

- `grep -rln GET_SIGNATURES` 全包唯一命中 `TapSignKit`；`grep -rn signature` 其余命中都是 okhttp/kotlin/compliance HMAC（`SecretUtil`/`TapComplianceApiKt`，与 APK 签名无关）。
- `TapTapSdkOptions` 只有 clientId/clientToken/region/language 等，不带签名。
- ⇒ 只改 `getSign` 一处即可覆盖 gatekeeper 请求的 signature。
