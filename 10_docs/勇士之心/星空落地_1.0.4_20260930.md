## 3. 1.0.4 的新加固与破法

1.0.4 与 1.0.3 的结构差异（本轮最大障碍）：`lib/arm64-v8a/` 下**已无 `libcocos2djs.so`**
（只剩 Bugly_Native / secret / secsdk / tapsdkcore / themis）；cocos so 被移到
`assets/apksecuresolib/arm64-v8a/libcocos2djs.so`（加密，15,164,720 B），
由 `libsecret.so`（`SecShell_*` API）**以「签名 + 包名」派生密钥**解密 `assets/apksecurefile`
与该 so，再 `android_dlopen_ext` 明文到 `/data/data/<pkg>/no_backup/mlib/arm64-v8a/libcocos2djs.so`。

破法（三件套，缺一不可）：

- **签名伪造** `java/com/starry/magic/sign/SignSpoof.java`：新增本包条目
  `YSXZ_PKG = com.fightingstars.games.warrior` + `YSXZ_CERT_B64`（官方证书），
  运行期把 `PackageInfo.signatures` 伪装成官方 → 密钥派生通过（日志 `spoof hit … md5=79a6a62f…`）。
- **Application 工厂** `java/com/starry/magic/ysxz/YsxzAppComponentFactory.java`
  （`extends SignSpoofAppComponentFactory`，Manifest `android:appComponentFactory` 指向它）：
  在真实 Application 实例化**之前**装 SignSpoof 并早载 native。
- **壳自检 watchdog** `jni/Games/YsxzSecShell.{h,cpp}`：定位 `libsecret.so` 全局状态词
  （`SecShell_IsDirty` / `FailedMask` 等，RVA 兜底 `0x4e5cc` / `0x4e664`），
  线程 120000 次循环把 dirty/failed 清 0（前 6 s 1 ms 节奏，之后 20 ms），
  保证壳的自检不会因为重签名而拖死启动。

## 4. 启动 5~13 s 干净退出：定位与内核级退出陷阱（本轮核心技术点）

**现象**：启动 5~13 s 后 `Zygote: Process N exited cleanly (0)`，无异常栈、无生命周期回调，root/非 root 都复现。

**定位**（连续排除）：
1. 静态扫保护库内联退出：`/tmp/ysxz_exitscan.py`（capstone 自写 ELF VA→偏移映射，找 `mov w8/x8,#93|94` 后 4 拍内 `svc #0`）
   扫 libsecret/libsecsdk/libtapsdkcore/libthemis/libBugly_Native → **0 个内联退出 syscall**，排除「保护库直发 svc」。
2. Frida 路线放弃：macOS 无 `timeout`、非 root 机不能跑 frida-server、缓冲日志被 `kill` 吃掉 ⇒ 改为在自家 so 里做探针。
3. 自建探针 `jni/Games/YsxzExitTrace.{h,cpp}`：钩 `libc.exit/_exit/_Exit/abort/kill/pthread_exit/syscall` +
   JNI `System.exit/Runtime.exit/exitInternal/Process.killProcess`（Android 14 上后四者**不在** libandroid_runtime.so 导出表，找不到属正常），
   命中打印调用点（`dladdr` → 库名+偏移）+ native/Java 栈，再叠加 seccomp 与致命信号现场探针。
4. 决定性命中：`[YsxzExit] _exit 被调用 code=0 (#68)` —— **保护线程主动 `_exit(0)`**，
   bionic `_exit` 内联 `exit_group(94)`。

**seccomp 三轮实验**（`InstallSyscallTrap()`：`prctl(PR_SET_NO_NEW_PRIVS)` + `SECCOMP_MODE_FILTER`，BPF 只针对 93/94，其余 ALLOW）：

| 轮次 | 策略 | 结果 |
|---|---|---|
| 1 | 93 + 94 → `SECCOMP_RET_TRAP` | 进程 ~270 ms 即 `signal 31 (Bad system call)`，且 SIGSYS 处理器一行没打 |
| 2 | 93 + 94 → `RET_ERRNO\|EPERM` | 变 `signal 4 (Illegal instruction)`：拦 93 让线程从 `svc` 之后继续执行、落进 `udf` ⇒ 整进程陪葬 |
| 3 | **只拦 94 → `RET_TRAP`**，SIGSYS 处理器打印调用点后**只结束该线程**（`syscall(__NR_exit,0)`，不返回） | **进程存活 60 s+**，游戏进入「选择角色」 |

**教训**：① `exit(93)` 是**普通线程退出**的常规路径，绝不能拦；只能拦 `exit_group(94)`。
② `ERRNO` 拦法会让线程继续执行到非法指令/destroyed-mutex 二次崩溃，**必须 TRAP + 处理器内只结束该线程**。
③ 各类退出调用必须**独立计数**（共用一个计数器时 `exit` 首命中会因 `abort` 已计数而不 dump 栈，掩盖调用者）。

  逐项比对「功能名 ↔ 下标 ↔ 控件类型」（开关必须 `getRet`、滑块必须 `getVal`），生成期即拦串号。

  会让 ndk-build 无谓重编，确定性重建产出同一个 so，被 build_so 阶段「有新 .o 而 so 未变=陈旧包」门禁误判。
