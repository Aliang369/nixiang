# 菜单授权「第二次打开未授权」根因与修法（2026-10-04）

> 适用：星光菜单（`com.starry.magic`）任意宿主游戏；本次实证宿主 = 勇士之心（`com.fightingstars.games.warrior`）。
> 关键词：云机 / SSAID 漂移 / device_id / heartbeat / hardKick / 未授权 / 存档被清

---

## §0 一句话结论

菜单界面上的「授权有效 / 未授权」**只读原生进程内存态**（`MainModern.cpp:98 session_live()` 读 `g_rt_ok`），
进程一重启必然为 `false`；能不能救回来，取决于两条恢复路径。原来的实现里：

1. **存了不认** —— 本地已持久化的 `auth_device_id` 只被当成「历史候选」，返回值永远是**当次重算**的 SSAID 派生值；
2. **不上网就判死** —— 存档 grant 里的设备字段与「当次设备号」`strcmp` 不等即拒绝，与网络无关；
3. **失败即毁档** —— 云机指纹漂移导致心跳 401/403，消息里带「设备」二字，被判成权威硬拒 ⇒ `hardKickAuth()` ⇒ **清空存档**。

于是云机上「登录成功 → 关掉 → 再打开 = 未授权」，且**保存的东西真的没了**（被自己清的）；
重新输卡密能立刻恢复，是因为 login 走的是另一条带 `legacy_device_ids` 的迁移路径。

修法三句话：**存了就必须认**、**先自愈再踢**、**清档前先留档**。

## §3 根因：三条断点 + 两层兜底失效

### B1 存了不认（原 `Preferences.java:276-293`）

```
:279  String cached = sharedPreferences.getString(KEY_DEVICE_ID, "");
:283  legacyCandidates(cached, stable)   // cached 只进了历史候选
      return stable;                     // 返回值永远是当次重算值
```

云机（云实例 SSAID 重算 / 换实例 / 重装）下 `stable` 每次不同 ⇒ `auth_device_id` 被无视 ⇒ 路径 A 的
`strcmp(d, device)` 必然不等 ⇒ 存档 grant 当场作废。

### B2 不上网就判死

见 §2 的 `MainModern.cpp:143`。这不是网络问题：**本地就有有效票据，却因为身份对不上被判无效**。

### B3 失败即毁档（最致命）

```
menu/NativeMenuController.java:3356-3370 isHardAuthFailureJson()
   :3361  d.contains("会话") || ... || d.contains("设备") || d.contains("不存在") || d.contains("用尽")
menu/NativeMenuController.java:3203  if (isHardAuthFailureJson(json) || looksLikeAuthFailure(json, data)) {
menu/NativeMenuController.java:3204      boolean coldStart = "cold-start".equals(why);
menu/NativeMenuController.java:3208      if (coldStart && authoritative) {
menu/NativeMenuController.java:3218          mainHandler.post(() -> hardKickAuth(serverMsg));
menu/NativeMenuController.java:3324-3337 hardKickAuth()  → :3327 bridge.clearAuthSession()
menu/Preferences.java:749-760        clearAuthSession() → 逐条 remove auth_token/auth_card/auth_last_ok/auth_expire/auth_bootstrap/auth_grant/auth_card_meta
```

服务端的两种「设备类」拒绝，被客户端一律当成权威致命：

| 服务端 | 含义 | 正确处置 |
|---|---|---|
| 401「会话与设备/游戏不匹配」 | 同一持卡人换了 device_id | **应自愈**（用本地卡密重登，把绑定迁到新 id） |
| 403「设备绑定已变更，请重新登录」 | 同上，语义更重 | **应自愈** |

而真正致命的只有：**封禁 / 卡密过期 / 卡密用尽 / 卡密不存在 / 无权限**。

### 兜底层也失效

`auth/DeviceFingerprint.java`：

- `:56-78` v5 = `dev_` + `sha256("ver=v5|ssaid=" + SSAID)[0:32]` —— **纯 SSAID 派生**，SSAID 一变全变；
- `:161` / `:194` 兜底读旧号依赖 `su`；`:144-156` 依赖外部存储目录（`Android/starry_magic`、`Download/.starry_magic`）与 `/data/local/tmp/starry_magic`；
- 云机**既无 su 也可能无外部存储** ⇒ 兜底全废（MuMu 有 `adb root`，所以这套缺陷在模拟器上从未暴露）；
- 原 `:292` 还会 `throw new IllegalStateException("设备标识不可用：v5/v4 均缺失，需要解绑设备后重新绑定")` —— 在云机上等于整条授权链路直接抛崩。

## §4 修法（F1–F5）

### F1 存了就必须认 —— `Preferences.getOrCreateDeviceId()` 重写

```
:299  public static synchronized String getOrCreateDeviceId() {
:304      if (DeviceFingerprint.isValidDevId(cached)) { markDeviceIdSource("cached", ver); return cached; }   // ← 零 I/O、零 su
:311-317  无缓存才 v5（SSAID）
:320-326  再不行 v4（Build 字段）
:328-333  终局 localFallbackDeviceId()：本机随机号，持久化，**不再抛异常**
```

配套：`markDeviceIdSource()` `:337-347`、`getDeviceIdSource()` `:350-356`、`getStorePath()` `:358-367`、
`localFallbackDeviceId()` `:370-378`、`grantDeviceMatches()` `:381-391`、`hasStoredGrant()` `:393-397`、
`legacyCandidates()` `:399-406`（**把 cached 也并入 legacy 候选**，供服务端迁移识别）、
`DeviceFingerprint.writeSeed(Context, String)`（`:125-141`）把设备号写一份到共享种子文件，供 prefs 被清后找回同一身份。

效果：设备号从此**只在首次定身份时采集一次**，之后永远以存档为准 ⇒ 路径 A 的 `strcmp` 恒等 ⇒
**二次打开可离线直接授权有效**。

### F2 先自愈再踢 —— `NativeMenuController`

```
:3208  if (coldStart && authoritative) {
:3211      if (isSelfHealableFailureJson(json) && trySilentSelfHeal(why, json)) {   // 先静默自愈
:3212          logAuthStoreVerdict("relogin");
:3213          return;
:3214      }
:3216      logAuthStoreVerdict("kick");
:3218      mainHandler.post(() -> hardKickAuth(serverMsg));
```

- `isSelfHealableFailureJson()` `:3397-3418`：命中「设备 / 会话 / 未登录 / 重新登录」**且不命中**
  「封禁 / 用尽 / 不存在 / 过期 / 权限 / 已删除」才为真；
- `trySilentSelfHeal()` `:3420-3437`：要求 `isCardAuthRequired()` 且本地存有卡密，
  `authSelfHealAttempted` 保证每进程只试一次，然后 `authLoginWithCard(card, true)`；
- `handleAuthLoginFailure(err, silent, fatal)` `:3439-3451`：静默模式下非致命只记日志，致命才踢；
- **⚠️ 二次修正（务必照 §7.5/§7.6 实现）**：自愈分支必须**先 `return`**，可自愈类失败**永不** `hardKickAuth`，
  否则「自愈后仍失败」会销毁存档（第 1 轮实测复现，见 §7.5）。
- `maybeRenewGrant()` `:3160+` / `shouldRunGrantBgRenew()` `:3292+`：**token 被上一版误清、但卡密还在时也放行对账**，
  心跳会以「未登录」拒绝，正好走自愈把云机从「未授权死状态」救回来。

### F3 设备不匹配走 legacy 重对齐（服务端）

`auth-server/app/services/auth_service.py`：

```python
def heartbeat(db, token, game_id, device_id, legacy_device_ids: Optional[list[str]] = None) -> dict[str, Any]:
    ...
    device_drift = False
    if session.device_id != device_id:
        requested = _normalize_legacy_device_ids(legacy_device_ids)
        if session.device_id not in requested:
            raise HTTPException(401, "会话与设备/游戏不匹配")
        device_drift = True
    ...
    if card.device_id and card.device_id != device_id:
        known = _load_legacy_device_ids(card)
        migratable = device_drift and (card.device_id == session.device_id or device_id in known)
        if not migratable:
            session.revoked = True; db.commit()
            raise HTTPException(403, "设备绑定已变更，请重新登录")
        old_id = card.device_id
        merged = [old_id] + [x for x in known if x != device_id and x != old_id]
        _store_legacy_device_ids(card, merged)
        card.device_id = device_id
    if device_drift:
        session.device_id = device_id

```

`app/routers/client.py` 透传 `body.legacy_device_ids`。
旧客户端不传（`None`）⇒ 行为与旧版逐字一致，**向下兼容**。

### F5 授权键同步落盘 + 回读校验

`commitChecked(Editor, String verifyKey, Object expect)` `Preferences.java:437-469`：`commit()` 失败重试一次，
再回读比对（`expect == null` 表示「该键应已被移除」）。已用于
`KEY_DEVICE_ID`（`:425`）、`KEY_DEVICE_ID_SOURCE`（`:346`）、`KEY_DEVICE_ID_LOCAL`（`:375`）、
`KEY_LEGACY_DEVICE_IDS`（`:487`）、`KEY_AUTH_TOKEN`（`saveAuthSession` 末尾 `:738`）、`clearAuthSession`（`:752-759`）。
旧的 `apply()` 是异步刷盘 —— 云机/低端机上进程被回收时可能还没落盘，正是「像没存过」的第二个来源。

| `grant_match=true` + `[验证] grant ok` | **B2 已修**：存档 grant 的设备字段与当次设备号相等，离线直接授权通过 |

唯一噪声：进程起来后 ~0.7s 内原生侧先打一次 `[验证] flag=false live=0 / 拒绝 #0（未授权）`，
随后 ~4.9s 由 Java 侧应用存档授权（`grant ok`）——这是「Java 先于 so 应用票据」的启动顺序，窗口约 4s，
菜单显示时（overlay 起于 t+5.9s）授权已经有效。日志：`09_test/_auth_cold_1.txt`、`_auth_cold_2.txt`、`_auth_regression_log.txt`。

### 7.5 设备漂移自愈回归第 1 轮：**发现我方第一版修法自身的缺陷**

复现手法：把 `shared_prefs` 里的 `auth_device_id` 改成一个**新的合法值**
（`dev_a1b2c3d4e5f60718293a4b5c6d7e8f90`，模拟云机换实例/SSAID 重算），
`cat > $PREF` 写回（保 owner `10056:10056` / mode `660`），冷启动 ×2。
脚本：`09_test/_t_auth_drift_regress.sh` + `09_test/_t_drift_prefs.py`。

冷启动 1 的前半段**完全符合预期** —— 自愈确实触发了：

```
W StarryMagic: [验证] grant rejected
W NativeMenu:  [auth] cold-start self-heal: device/session mismatch (cold-start) → relogin with stored card, msg=会话与设备/游戏不匹配
I NativeMenu:  [auth] store verdict=relogin device=dev_a1b2… source=cached has_grant=true grant_match=false token=set card=set backup_at=0
W NativeMenu:  [auth] silent self-heal non-fatal: 卡密已绑定其他设备，请先解绑 (keep archive, retry later)
```

**但约 30s 后**（续票重试循环 `NativeMenuController.java:181 mainHandler.postDelayed(this, GRANT_RENEW_RETRY_DELAY_MS)`）
再次续票 → 仍是设备类失败 → `trySilentSelfHeal()` 被 `authSelfHealAttempted` 守卫拦下返回 `false`
→ **穿透到踢人分支** → `store verdict=kick` → `hardKickAuth()` ⇒ **存档连同卡密一起被清**：

```
终态 prefs 3800 B，仅剩 auth_backup_{at,card,card_meta,device_id,device_source,expire_at,grant,last_ok_at,reason,token}
被 remove 的：auth_token / auth_card_key / auth_grant / auth_last_ok_at / auth_card_meta_json / auth_expire_at
冷启动 2 ⇒ 0 条 store verdict、卡密已丢 ⇒ 永久未授权，直到手动重输卡密
```

**这正是用户抱怨的现象本身，而且是我第一版修法制造出来的。** 根因一句话：

> 第一版把自愈写成合取守卫 `if (isSelfHealableFailureJson(json) && trySilentSelfHeal(why, json))`，
> 于是「自愈失败 / 已经试过一次」会**穿透到 `hardKickAuth`** —— 把「暂时救不回来」升级成「销毁证据」。

### 7.6 二次修正 H1 + H2（已落地）

**H1 —— 可自愈类失败永不踢、永不清档**（`menu/NativeMenuController.java` 冷启动权威分支）：

```java
if (isSelfHealableFailureJson(json)) {
    boolean healed = trySilentSelfHeal(why, json);
    logAuthStoreVerdict(healed ? "relogin" : "heal-deferred");
    if (!healed) {
        Log.w(TAG, "[auth] healable-class failure, heal unavailable -> keep archive, retry next launch: "
                + json.optString("message", ""));
        mainHandler.post(() -> refreshAuthStatus());
    }
    grantRenewCycleDone = true;
    return;                       // ← 永不落到下面
}
grantRenewCycleDone = true;
logAuthStoreVerdict("kick");
mainHandler.post(() -> hardKickAuth(json.optString("message", "")));
```

⇒ 只有**封禁 / 卡密过期 / 卡密用尽 / 卡密不存在 / 无权限**这类真正权威失败才清档；
设备不匹配 / 会话失效这类一律保留卡密，下次冷启动继续尝试自愈。判读靠 `heal-deferred`（救不动但保留）与 `kick`（权威致命）两个不同的 verdict。

**H2 —— grant 里的设备号也进 legacy 候选**（`menu/Preferences.java`）：

云机漂移时，卡密当前绑定仍是**旧设备号**，而旧设备号正躺在存档 grant 的第 2 个字段里
（`1|device|game|exp|menu|card|kid.sig`）。原来它没被当成候选，于是自愈登录走到服务端
`_authorize_device_binding()`（`auth_service.py:94-106`）时 `card.device_id in requested` 为假
⇒ 403「卡密已绑定其他设备，请先解绑」⇒ 自愈必然失败。新增：

```java
public static String grantDeviceId() { /* 解析 auth_grant 第 2 字段，合法 dev_* 才返回 */ }
public static boolean grantDeviceMatches(String deviceId) { return grantDeviceId().equals(deviceId); }

public static List<String> getLegacyDeviceIds() {          // 自愈 login 上报的 legacy_device_ids[]
    ... stored(auth_legacy_device_ids) + grantDeviceId()   // ← 服务端亲自签发过的身份，一定认识
}
private static LinkedHashSet<String> legacyCandidates(String cached, String preferred) {
    ... getLegacyDeviceIds() + cached + grantDeviceId() + DeviceFingerprint.getLegacyIds(appContext) - preferred
}
```

配套说明：`DeviceFingerprint.getLegacyIds()`（种子文件 / su / 外部存储目录）在云机上基本是空的，
所以「服务端见过的旧号」只能靠这条 grant 解析补上；这也是 §3 兜底层失效的补丁。

## §8 未决与已知限制

1. **云机未实测**（用户侧环境不可访问）。已用「伪造 `auth_device_id`」在 MuMu 上复现同一路径并通过；
   云机实测请按 §10 走，日志认 `[auth] store verdict=` 这一行。
2. **`auth_backup_*` 只做诊断不做恢复**：踢档（封禁/过期/用尽/不存在）后不会自动还原旧票据，
   需要用户重输卡密；这是刻意的（避免把已失效的卡密反复复活）。若日后想自动恢复，消费端在 `Preferences.clearAuthSession()` 之后加一步 `restoreAuthSessionFromBackup()` 即可（备份键已齐备）。
3. **4s 授权窗口**：冷启动 t+0.7s 原生侧先判一次未授权（`[验证] flag=false live=0`），t+4.9s Java 侧灌入存档票据 ⇒ 窗口约 4s。菜单 overlay 起于 t+5.9s，用户通常看不到；若要在极快打开菜单时也不闪「未授权」，可把 `ModBridge.syncNativeAuthorized()` 提到 `Application.onCreate`（本轮未做）。
4. **旧版本装过的存档**：`auth_device_id` 可能已被旧版写成漂移值（旧版每次重算）⇒ 首次冷启动会走一次自愈；自愈成功后 grant 与 device_id 都被重写为同一值，此后稳定。
5. 服务端 `_authorize_device_binding()` 接受「**请求带上来的** legacy 列表」中的任一值命中卡密绑定时迁移
   （`auth_service.py:104`）—— 这意味着知道一台设备的 id 就能把卡密迁到新设备；属既有设计（卡密本身即凭证），
   本轮未改动该语义。

## §10 云机实测步骤（交给用户）

```
# 1) 把新包装到云机（保数据）
adb install -r 勇士之心_1.0.3_星光菜单_授权二次打开修复_20261004.apk

# 4) 取日志判定

```

判读表：

| 日志 | 含义 | 结论 |
|---|---|---|
| `verdict=ok … source=cached … grant_match=true` | 存档设备号被直接信任，票据匹配 | ✅ 已修（最常见） |
| `cold-start self-heal … → relogin` + `store verdict=ok` | 设备号漂移过一次，已静默迁移 | ✅ 已修（自愈成功） |
| `verdict=heal-deferred` + `healable-class failure … keep archive` | 暂时救不动，但**卡密与存档保留** | ⚠️ 观察下次冷启动是否转 ok；不要重输卡密 |
| `verdict=kick` + `auth_backup_reason=kick:…` | 权威致命（封禁/过期/用尽/不存在） | ❌ 卡密本身有问题，需换卡 |

> 只要**不出现 `kick`**，存档就不会被清；这是本轮修法的底线保证。
