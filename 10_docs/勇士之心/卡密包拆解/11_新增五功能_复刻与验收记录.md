### 1.1 顺手修掉的一个"静默失效"陷阱

`mod菜单/starry-mod-menu/app/src/main/java/com/starry/magic/cocos/YsxzHooks.java` 的
`RET`/`VAL` 原本是 `new boolean[8]` / `new int[8]`。**数组太小不会崩**——
`getRet(10..13)` 越界只会返回 `false`/`0`，于是 10–13 号开关**点了没反应且没有任何报错**。
已把数组改成 `CAP = 16`，并加了一个可在 dex 里 grep 的构建指纹：

```java
public static final String CAP_MARK = "ysxz_hooks_cap16_20261007";
```

`04_scripts/勇士之心/ysxz_release_103.sh` 现在有两道硬门禁：① so 菜单表必须含
`Toggle_解锁金卡/自动重复挑战/自动出售/自动分解/自动穿戴` 五个串；② dex 必须含
`ysxz_hooks_cap16_20261007`。baksmali 复核新 dex 确认
`.field private static final CAP:I = 0x10` + `const/16 v0, 0x10` + `new-array v1, v0, [Z`。

菜单渲染侧无需改动：`app/src/main/jni/MainModern.cpp` 的
`int count = g_mod ? g_mod->featureCount : 0;` 与 `FeatureListParser.parse(int index, String spec)`

## 4. 改名诊断（本轮新增，防静默失效）

本层依赖的 `fDc / autoBattleFlag / ftA / fvH / bYK / bYJ / efi` **全是逐版本重混淆的短名**。
官方热更改名后钩子挂不上，而**菜单开关照样显示"开"**——这正是上一轮过检测层
（E8）踩过的"一行日志都没有"的静默失效模式。故加：

```js
var MISS = {};
function miss(key, s) { if (MISS[key]) return; MISS[key] = 1; A.warnN++; log("warn: " + s); }
```

落点（每个只打一次）：`gold.data` / `gold.fn`、`rflag`、`panel`、`sd.bag`、`wear.eq` / `wear.ftA`。
`__AUTO_STATE__()` 暴露 `warns` 计数（共 **21** 键）。

诊断本身第一版有两个真缺陷，已在离线验收台抓出并修掉：

1. `repeatFlagSync` 的 `miss("rflag")` 写在 `FEAT(7)` 判断**之外**，且没先判 `$eZ` 是否存在
   ⇒ ①**开关关着**时也打；②**`$eZ` 还没加载**时也打（"还没加载"被误报成"改名了"）。
   修法：`var z = F(); if (!z) return;` + `miss` 只在开关为开时调用。
2. `repeatTick` 的 `miss("panel")` 放在 `panelOpen()` **之后**，而 `panelOpen()`
   在 `fguiMgr` 缺失时只**静默返回 false** ⇒ 该告警**永不可达**，恰好漏掉"面板管理器改名了"
   这个最该诊断的场景。修法：把 `fgm` 判空提到 `panelOpen()` 之前。

## 7. 诚实边界

1. **只在真机 `f9a116a2` 由用户实测通过，未在 MuMu 模拟器验证。** 硬约束 #1 写明目标环境是
   MuMu（已 root），"一切以 MuMu 为准"。本轮**没有** MuMu 侧的实测记录 ⇒ 不得表述为"双端可用"。
2. **全是客户端侧动作，没有任何服务端验证。** 自动重复挑战 / 出售 / 分解 / 穿戴都是发游戏自己的
   联网协议，会不会被服务端从别的观测量（频率、顺序、时长）发现，**无法证明**。
3. **出售/分解需要用户先在游戏背包里勾好品质**（我们只读游戏内勾选，不替用户选）；
   一件都没勾时走兜底 `[1,2,3]`——这个兜底是照抄他的修法，但**属于"猜用户意图"**，请知悉。
4. **自动重复挑战依赖结算面板上的 `efi`**。这条链只有在真的打完一局、结算面板弹出来时才走得到；
