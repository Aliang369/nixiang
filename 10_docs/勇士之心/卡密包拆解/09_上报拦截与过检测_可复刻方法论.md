# 09 上报拦截与过检测 · 可复刻方法论

> 专题文档。素材：卡密包补丁 JS（`03_decompiled/勇士之心_cardkey_20261007/提取_补丁_v66_原始.js`，7229 行）+ 我们自己的仓库普查（`mod菜单/starry-mod-menu/app/src/main/jni/Games/`，129 个 Mod）。
> 结论先行：**他做的不是"绕过检测"，而是"把检测该看到的世界改回正常值"。** 这套思路我们能直接复刻，而且是我们目前最大的短板。

---

## 0. 一句话对照

| | 他的做法（卡密包） | 我们的做法（129 个 Mod 普查） |
|---|---|---|
| 范式 | **补偿式**：上报照常发，值改成自洽 | **阻断式**：白名单插门 / no-op（仅 1 个游戏做了） |
| 载体 | 运行时包装 JS 函数 | 编译期替换热更 DLL（`targetfuntional_dll*.bin`） |
| 覆盖 | 反作弊闸门 + 结算上报 + 伤害字段 | 出站 RPC 白名单 + 执法 RPC no-op + 封号弹窗压制 |
| 隐蔽性 | 高（没有缺失，只有"正常值"） | 低（少一条上报本身就是特征） |

## 1. 他的完整实现（四层，逐层可复刻）

源码位置：`提取_补丁_v66_原始.js`。全部逻辑在 `installAntiDetection()`（L7025）里串起来，入口 `W.__WX_INSTALL_AC__`。

### 1.1 闸门：把"本地反作弊开关"焊死为 false（L6908）

```js
function acGateMod(m, tag) {
  if (!m || typeof m !== 'object' || !('ANTI_CHEAT_ENABLED' in m)) return false;
  Object.defineProperty(m, 'ANTI_CHEAT_ENABLED', {
    get: function () { return false; }, set: function () {}, configurable: true
  });
  ST.acGated = true; if (!ST.acMod) ST.acMod = tag; return true;
}
```

**三个覆盖面（这是精华，不是简单改个变量）：**

1. **出口统一包装**：包 `window.__require`，任何模块一被取出就先过一遍 `acGateMod`（幂等标记 `req.__wxAcLocked`）；
2. **跨版本已知名单**：`['$LZ','$KF','$KM','$KK','$KE','$PZ','$WS','$DOB','$DOC','$DOD','$DOE','$hU','$hV','$hW','$hZ']`（1.1.2.0 旧名单 + 1.1.3.2 实测在读该标志的模块，**名单是会随版本积累的资产**）；
3. **全局扫描兜底**：`for (var g in globalThis)` 逐个试，**5 秒节流**，且只在还没关闸时做。

### 1.2 上报出口挂钩：只挂命名稳定的入口（L7001 / L7015）

```js
function acHookSink(obj, key) {
  var fn = obj && obj[key];
  if (typeof fn !== 'function' || fn.__wxAcSink) return false;
  var of = fn;
  var w = function (proto, payload) {

    return of.apply(this, arguments);

  w.__wxAcSink = true; obj[key] = w; return true;
}
function installReportIntegrity() {
  var ok1 = acHookSink(W.$eZ && W.$eZ.battleServer, 'sendMsg');
  var ok2 = acHookSink(W.$eZ && W.$eZ.gsMgr, 'cQA');
  ...
}
```

**他明确写了为什么这么挂**（L7000 注释原文）：

> 只挂命名的稳定入口（sendMsg / gsMgr.cQA），不碰逐版本重混淆的短名方法

这条原则价值极高：混淆短名每版本都变，挂上去的后果是**静默失效**（`bEP` 在 1.1.3.2 里已经变成"按实体推帧"的热路径函数，照搬包装会挂在热路径上且 `e.frameCheck` 永远取不到）。

### 1.3 结算上报 `useTime` 一致性补偿（L6973 / L6975）

```js
function acFixReport(payload) {
  var cr = payload && payload.completeResult;
  if (!cr || typeof cr.useTime !== 'number') return;
  var st = findBattleState();
  var fk = (st && typeof st.fk === 'number') ? st.fk : 0;   // 逻辑时间（秒）
  var spd = acTimeScale();                                   // 加速倍率 lsGet('wx_gspeed','1')
  var fkMs = Math.floor(fk * 1000);
  var cur = cr.useTime, want;
  if (spd > 1 && ST.riStartWall > 0) {
    var realMs = Date.now() - ST.riStartWall;                // 真实墙钟
    var est = Math.floor(fk / spd * 1000);
    if (realMs < est) realMs = est;
    want = Math.max(1000, Math.min(realMs, fkMs > 0 ? fkMs : realMs));
  } else {
    want = cur;
    if (!isFinite(want) || want < 0) want = fkMs > 0 ? fkMs : 0;
    else if (fkMs > 0 && want > fkMs) want = fkMs;
  }
  want = Math.floor(want);
  if (want !== cur) ST.riFixedUt = (ST.riFixedUt || 0) + 1;
  cr.useTime = want;
  ST.riNote = 'useTime ' + cur + '->' + want + ' fk=' + fkMs + ' spd=' + spd;
}
```

**为什么需要它（L6973 注释原文）：**

> 结算上报的 useTime 一致性补偿：开加速时游戏按【逻辑时长 fk】上报，而服务端能看到的是真实墙钟，两者对不上就是特征。

**真实开战时刻的反推**（L7029，这是配套关键）：

```js
if (BATTLE !== ST.acBattle) {
  ST.acBattle = BATTLE;
  var fk0 = (BATTLE && typeof BATTLE.fk === 'number') ? BATTLE.fk : 0;
  ST.riStartWall = BATTLE ? (Date.now() - Math.floor(fk0 / acTimeScale() * 1000)) : 0;
}
```

⇒ **模式：客户端有一个"逻辑时钟"，服务端有一个"墙钟"，加速会让两者分离。修法是"用逻辑时钟反推墙钟，再让上报值落在两者之间"。**

### 1.4 伤害字段还原：改前记、改后补回"原始值"（L2578）

```js
var originalDamage = Number(damage) || 0;
var atkBefore = null, vicBefore = null;
try {
  atkStat = BattleCore.stat(attacker);
  if (atkStat && typeof atkStat.finalDamage === 'number') atkBefore = atkStat.finalDamage;
  if (vicStat && typeof vicStat.finalHurtValue === 'number') vicBefore = vicStat.finalHurtValue;
} catch (eA) {}

try { DamageFeature.beforeHit(ctx); } catch (e) {}   // ← 这里把 ctx.damage 改成放大值
try { GuardFeature.beforeHit(ctx); } catch (e2) {}

  if (atkBefore !== null && atkStat.finalDamage !== atkBefore)
    atkStat.finalDamage = atkBefore + originalDamage;      // ← 不是清零，是补回原值
  if (vicBefore !== null && vicStat.finalHurtValue !== vicBefore)
    vicStat.finalHurtValue = vicBefore + originalDamage;
  ST.acFixed = (ST.acFixed || 0) + 1;
}
```

**他写明了这两个字段的消费点（L2597 注释原文）：**

> - `battleMgr.bET({damage: hw.finalDamage, takenDamage: hw.finalHurtValue, ...})` 上报
> - 伤害统计面板 `o.cZq` / `c.cZr`

⇒ 所以**必须补回原值而不是清零**：清零会让统计面板归零，同样是异常。这是"**字段有多个消费者**"的典型案例。

### 1.5 「临时视图」技巧：调用期间换值，`finally` 还原（L2650-2700）

```js
/* 1.1.3.2：battleMgr.bEu.ne.jg(event) 直接读取 event.finalDamage */
if (event && typeof event.finalDamage === 'number') {
```

用于"我们希望游戏的某个分支看到 A 值，但事件对象本身不能留痕"的场景。**用完立刻还原**是纪律。

### 1.6 可观测性（L7033）

```js
W.__WX_AC_STATE__ = function () {
  return { gated: !!ST.acGated, mod: ST.acMod || '', baR: !!ST.baR, ri: !!ST.riHooked,
           fixedUt: ST.riFixedUt || 0, dmgFixed: ST.acFixed || 0, note: ST.riNote || '' };
};
```

**过检测必须是可观测的。** 静默失效是这类工作最大的敌人 —— 挂不上、条件不满足、字段名变了，全都不会报错。

### 1.7 反面清单：他明确写了「不做什么 + 为什么」（L6894-6907）

| 不做的事 | 原因（他的原文摘要） |
|---|---|
| `computeCheckNum` 包装 | 1.1.3.2 明文包里这个方法已不存在（出现 0 次） |
| `bEP` / `bEQ` / `gV` / `bDQ` 包装 | 逐版本重新混淆的短名；`bEP` 已变成热路径函数；`e.frameCheck` 永远取不到 → **静默失效** |
| `checkNum` 重算 | 旧公式已不存在；**改写一个自己无法核实的 checkNum 反而更容易被判异常** |
| `exitProgram` 拦截 | 本文件已有 `guardExit()`，不重复挂 |

> **"改写一个自己无法核实的量，比不改更危险"** —— 这句话是整套方法论的底线。

## 2. 可复刻的方法论（7 条）

1. **不禁止，只改值。** 让每条上报照常发出，但值自洽。阻断式留下的"缺失"本身就是特征。
2. **一致性 > 数值大小。** 关键不是把数字改小，而是**两个能互相推出的量不能矛盾**：`useTime` vs 墙钟、`finalDamage` vs 结算伤害 vs 统计面板。
3. **改前记、改后还原。** 任何被我们污染的量，在进入上报/统计字段前必须还原成**原始值**（`before + originalDamage`，不是清零）。
4. **只在稳定命名的出口挂。** 不碰逐版本重混淆的短名 —— 那是静默失效的来源。
5. **多面覆盖 + 幂等 + 节流。** 闸门三个面（`__require` 包装 / 已知名名单 / 全局扫描兜底），幂等标记，扫描 5 秒节流。
6. **可观测。** 暴露 `__WX_AC_STATE__` 式的诊断状态，否则你不知道它有没有生效。
7. **写下"不做什么"和原因。** 防止以后被复制回来（他这段注释直接救了下一版）。

**外加第 8 条（来自我们自己的教训，不是他的）**：**过检测不能依赖玩家开功能开关。**
见 `WxsjMod.cpp:13`：

> ❗失配仍「禁止进入游戏」（v7.15 恢复）：这是**防封号基线**，不是可选项

以及 L308：

> v7.2：屏蔽封号执法为基线功能——无条件武装字节替换（清数据/首装同样生效）。旧逻辑「配置里有功能开启才武装」在清数据后导致原版 dll 运行，封号弹窗+COS上传全链复活。

## 3. 我们现状普查（数据）

### 3.1 129 个 Mod 的上报拦截覆盖

| 关键词 | 命中文件数 |
|---|---|
| `completeResult` | **0** |
| `checkNum` | **0** |
| `ANTI_CHEAT` | **0** |
| `acFix*` | **0** |
| `useTime` | 1（`YsxzPatchJs.h`，且是 `hitPauseTimeScale` 的**子串假命中**，非真处理） |
| `sendMsg` | 1（`BlzzMod.cpp`）+ 1 个二进制 `.a` |

**⇒ 129 个 Mod 里，只有 1 个游戏（无限升级 / `WxsjMod.cpp`）真正做了上报拦截，而且走的是与我们主流一致的思路：编译期替换热更 DLL，把拦截逻辑编进 .NET 程序集。**

### 3.2 我们唯一的那套（WxsjMod）做对了什么

| 点 | 我们的做法 |
|---|---|
| 载体 | hook `RuntimeAssemblyLoader::ExecuteRuntimeAssembly`（`Assembly.Load(byte[])` 的唯一热更装载路径），整包替换成打过补丁的 DLL |
| 拦截层 | DLL 内「δ 层」：**出站 RPC 白名单**（无条件插门）+ 上报拦截 + 执法 RPC no-op + 封号弹窗压制 |
| 防退化 | **FNV-1a 64 整包逐字节校验**底包；失配就 `不调 orig` ⇒ 热更程序集不执行 ⇒ 进不了世界（宁可玩不了，也不能裸奔） |
| 无关性 | 「钩子装上即武装」——触发链 `StarryInitProvider.onCreate → mb_nativeInit → mod_thread → FastRetryThread(100ms×600)`，**与菜单/配置键无关** |
| 配置 | `block_report`（默认开，缺键时自动补 `1`） |

**⇒ 我们有能力做，但只在"重资产游戏"上做了；轻量 Cocos 系（50 个）几乎空白。**

### 3.3 两种范式的取舍

| | 阻断式（我们 Wxsj） | 补偿式（他） |
|---|---|---|
| 实现难度 | 低（白名单 + no-op） | 高（要理解每个字段的语义和消费者） |
| 隐蔽性 | 低（"这条上报没了"可被对账发现） | 高（上报齐全，只是值正常） |
| 失效后果 | 功能缺失 | **算错值反而更明显**（所以必须可观测 + 保守钳制） |
| 适用面 | 有明确"执法 RPC"的强反外挂游戏 | 有"结算/统计"体系的数值游戏 |

**建议：以补偿式为默认，阻断式只用于"执法/封号"这类必须彻底切断的链路。**

## 4. 通用化方案：把"上报拦截"做成框架能力

核心是三张表 —— **每个游戏只需填表，代码复用**。

### 表 A · 出口清单（Egress）

| 出口 | 稳定性 | 语义 | 处置 |
|---|---|---|---|
| `$eZ.battleServer.sendMsg` | 命名稳定 | 战斗消息统一出口 | 装箱 → 补偿 |
| `$eZ.gsMgr.cQA` | 命名稳定 | 结算/全局状态上报 | 装箱 → 补偿 |
| `battleMgr.bET` | 半稳定 | 帧伤害上报（含 `finalDamage`/`finalHurtValue`） | 源头还原（在 hY 层做，不另挂） |
| 出站 HTTP / RPC 白名单 | 按游戏 | 执法/封号链路 | 阻断（唯一该用阻断式的地方） |

> 判据：**命名稳定 = 可以挂**；**逐版本混淆短名 = 不挂**。每个新版本重新确认一次。

### 表 B · 字段账本（Field Ledger）

每行四列，缺一不可：

| 字段 | 谁写（源头） | 谁读（消费者） | 我们是否会污染 | 补偿规则 |
|---|---|---|---|---|
| `completeResult.useTime` | 结算流程（按逻辑时间 `fk`） | 服务端 | 是（加速） | `clamp(真实墙钟, 1000, fk*1000)` |
| `hw.finalDamage` | `proto.hY` 内部累加 | `battleMgr.bET` 上报 + 面板 `cZq` | 是（改伤害） | 写回 `before + 原始伤害` |
| `hw.finalHurtValue` | 同上 | 同上 + 面板 `cZr` | 是 | 同上 |
| `event.finalDamage` | 战斗事件 | `battleMgr.bEu.ne.jg` | 否（临时改写） | `finally` 还原 |

**"谁读"这一列是最容易被漏掉的** —— 漏一个消费者就制造一个新的异常。

### 表 C · 一致性规则（Consistency Rules）

每条规则 = 一个"服务端能观测到的量" vs "客户端上报的量"：

| 规则 | 观测量 | 上报量 | 违反后果 |
|---|---|---|---|
| 战斗时长 | 服务端墙钟 | `useTime` | 加速特征 |
| 伤害账平 | 结算总伤害 | `Σ finalDamage` | 改伤害特征 |
| 收益/时间 | 在线时长 | 金币/经验增量 | 加速 + 挂机特征 |
| 帧数/时长 | `frameId` 递增 | `useTime` | 帧率异常 |

**框架运行时流程：**

```
出口装箱 → 按表 B 还原被污染字段 → 按表 C 校验自洽 → 不自洽则钳制修正
        → 上报 → 记录诊断（fixedUt / dmgFixed / note）→ 暴露 __AC_STATE__
```

### 分层归属

| 层 | 内容 | 现有资产 |
|---|---|---|
| **L0 通用（JS，Cocos 系 50 个游戏复用）** | 出口装箱器 + 字段账本执行器 + 一致性钳制 + `__AC_STATE__` | 无（要新建；可照抄 1.2–1.6 的结构） |
| **L1 通用（Java/dex，所有游戏）** | 诊断页、`__AC_STATE__` 桥接、配置、上报通道本身的可观测 | `com.starry.magic.cocos.*Hooks` 已有桥的形态 |
| **L2 按游戏（DLL / native）** | 出站 RPC 白名单、执法 RPC no-op | `WxsjMod.cpp` 的 δ 层（可抽成通用 C# 组件） |

## 6. 诚实边界

- **这套没有服务端验证。** 他的代码是可用状态，但"能不能扛住服务端对账"没有数据支撑，别当已验收结论。
- **补偿式算错比不改更危险。** 所以第 6 条（可观测）和第 7 条（不碰无法核实的量）是硬约束，不是建议。
- **他是从 `remote.js v33N` 迁移过来的**，上游是按 `res 1.1.2.0` 写的，他按 `1.1.3.2` 裁剪过一半。**这本身就是一个教训：这套东西必须按版本重新核实，不能直接搬。**
