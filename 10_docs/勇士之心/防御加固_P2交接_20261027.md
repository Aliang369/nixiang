## 2. 待办（按价值排序，含已定设计）

### P2-1b `build_id` 绑进票 + build 白名单（防「卡密跨包复用」/防倒卖核心）
- 清单里已有 `build_id`；票升 **v3** 加一字段：`3|device|game|exp|mask|build_id|kid.sig`。
- 客户端 `build_id` 由**已验过的完整性表**派生（对 canonical `SGI1|path=size:sha256|…` 取 sha256 前 16 hex）⇒ 不需要自指、不需要联网。
- 客户端规则：票里带 `build_id` 且与本机不符 ⇒ 拒（静默）。
- 服务端：只对「发过清单的 build_id」发票（清单目录即白名单）；未登记 build ⇒ 不发 v2。
- 收益：**别人拿正版卡密 + 自己重打包的包，票到这个包上不生效**；同时把"改一字节重签"变成"票也不认"。

### P2-2 三层载荷加密（K / build / feature 三层派生）
- 目标：JS 载荷在 so 里不以明文出现；单层被扒还有下一层；破到底拿到的是**诱饵层**。
- 现成能力先查：`skill/starry-mod/` 与 `04_scripts/_common` 里的 js 加解密脚本（禁重造）。
- 铁律：解密密钥由 **build_id + 票派生**，不用固定常量（否则扒一层全通）。

### P2-3 诱饵层（K_fake）
- 已定决策：**静默无效 + 指纹上报**（不做随机衰减，用户已否掉随机衰减方案）。
- 触发条件：清单不符 / 票掩码为 0 / 解密链断在诱饵层。
- 上报内容：设备指纹 + build_id + 失败层号；服务端建"可疑 build/设备"台账。

### P2-4 水印（每张卡密唯一）
- 位置：菜单标题或一处不影响功能的 UI 文本；值 = 卡密 id 的 HMAC（不可逆但可对账）。
- 用途：抓到倒卖包时能定位是哪张卡密流出的。
- 注意：不得因此改变 12 项功能的行为与文案（用户要求「不影响功能」）。

### P2-5 敏感功能迁 OTA
- 把最值钱的 1-2 项（如自动穿戴/自动分解）的判定链搬到服务端签名载荷里，本地只留壳。
- 依赖 P2-1b 的 build_id 与 OTA token 机制（`OTA_SO_REQUIRE_TOKEN` 已存在）。

### P2-6 v1(HMAC) 票退役
- 前置：所有在售包都换成 v2+ 版本。
- 步骤：服务端停发 v1 → 观察一周无老包报障 → 删 `GRANT_HMAC_SECRET` 与客户端 `legacy_pepper`。

## 3. 运维纪律（P1 期间踩出来的，P2 继续适用）

1. **私钥换 = 必须重出包**，否则新包全员 fail-closed（功能静默失效）。
2. 服务器 `auth_service.py` 比仓库 HEAD 旧（少 10-04 云机修复）——**任何后续改动继续按"打在服务器那份上"做**，不要整文件覆盖。
3. 任何构建链路脚本**禁止用 `| tail` 吞构建输出**：失败必须 `exit`。
4. 出包后必跑 `harden_apk.py check`（C1–C4）+ `redteam`（C5），并重新 `publish` 对应 build 的清单。
