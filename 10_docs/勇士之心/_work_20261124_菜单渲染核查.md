### 7.1 先纠正一件事：这份协议**不输出 visibility**

用内嵌属性名表（`meta:__name__` 节点，149 条）逐键比对了 117 个 view 节点：

- 名表里确实声明了 `0x4e = misc:visibility`、`0x4a = misc:selected`；
- 但**每个 view 实际只携带 14 个属性**：`id / meta:__hash__ / meta:__name__ / layout:left|top|right|bottom|width|height / layout:layoutDirection|layoutRtl|hasTransientState|baseline / misc:transformation.alpha / misc:transitionName`；
- **117 个 view 中携带 `misc:visibility` 的有 0 个**（`misc:selected`、text 正文同样不输出）。

⇒ 「直接读三个 e$e 的 VISIBLE/INVISIBLE/GONE」这条路不存在，不能编。本轮改用两条可复现的替代判据（7.2 / 7.3）。

### 7.2 替代判据 A：权重算术 → tab 的三个 visibility（可证）

tab 容器 `LinearLayout L54 T511 R858 B631`（804×120），每个 tab 的 LP = `w=0, h=108(36dp), weight=1`，左右 margin 各 9px。
n 个可见时每个宽度 = (804 − 18n)/n：n=1→786、**n=2→384**、n=3→250。
实测：#113 = 384（L9–R393）、#115 = 384（L411–R795）、#114 = 0×0（L0 T0 R0 B0）。
⇒ **恰好 2 个 tab 参与布局，第 2 个（账号）GONE**。这份 payload 在"水平带权重"的容器里能反推 visibility —— 方法与结论都可复现。

### 7.3 替代判据 B：两次 dump 逐项比对 → 切页是否生效

| 观测 | 功能页 dump(950074c) | 设置页 dump(db33eb4) |
|---|---|---|
| 根 e$b | 1086×907 | 1086×907 |
| e$e #11（功能） | 804×265（L54 T207 R858 B472） | **完全相同** |
| e$e #77（账号） | 0×0 | **完全相同** |
| e$e #100（设置） | 0×0 | **完全相同** |
| tab 栏 top | 511 | **完全相同** |
| 117 个 view 的 (class,L,T,R,B) | — | **逐项比对 0 处差异**（脚本 `13_scratch/menu_render_diag/_diff_two.py`） |

⇒ **切页没有引起任何布局**（若布局跑过，tab 栏 top 或某个 e$e 的尺寸必然变化）。
⇒ 同时 featScroll 仍保留 804×265（GONE 会保留 stale bounds）而用户看不到功能列表 ⇒ **切页确实生效（click 打到了）**，否则用户应当还看见功能列表。

### 7.5 定案

**定案：切换 Tab 只改了 visibility，新显示的页从未进入测量/布局相位（bounds 恒 0,0-0,0），因此渲染阶段没有可画内容 —— 这是"渲染看不出东西"的直接原因，而不是内容高度被压 0、也不是前景九宫格遮挡。**
支撑：§1 静态排除矩阵（12 条）+ §7.2（tab visibility 可证）+ §7.3（两次 dump 117 项 bounds 逐项一致，切页零布局）+ §7.4（排除"uiautomator 看不到=不可见"的误判）+ §5 运行时控件 LP 全在（EditText 720×108、Button 720×102/720×90）。

private void relayoutPanelContentNow() {
    if (panelContent == null) return;
    int w = panelContent.getWidth();
    if (w <= 0) return;
    panelContent.forceLayout();

}
