## 4. 壳与过检测处置

### 4.1 改签能不能起：不能（`_work_20261123_壳可行性.md`）

删 `SignSpoof` 后直接改签，壳按「签名 + 包名」派生密钥解 `assets/apksecuresolib`，签名一变即解不出引擎 ⇒ 起不来。故本代**必须**保留 `YsxzSecShell.cpp`（清 `SecShell_IsDirty/FailedMask`，不装必 NPE 闪退）、`YsxzAppComponentFactory.java`（早载 native）、killer dex（§4.2）。

### 4.2 killer（签名伪装 B 轨，`_work_20261123_killer方案.md`）

- 产物 `ysxz_signature_killer.dex` 13,988 B / md5 `c60b7d03`（构建产物，24 日收尾已入隔离区，可用 `build_killer_dex_ysxz.sh` 重建）；包内挂 `classes3.dex`；
- 13 个参数化 smali 类（`mt/signature/KillerApplication193` 系列）+ 官方证书 DER 烘焙进包；
- 离线校验 `verify_killer_dex_ysxz.py` **17 项全过**；构建 `build_killer_dex_ysxz.sh`（烘焙 + 汇编 + 回读断言）；
- 定位：只做「读到的签名 = 官方签名」这一层，不碰 TapTap 登录判定（TapSDK 弹窗问题本代未处理，不影响功能）。

### 4.3 killguard（壳自杀拦截，`_work_20261123_壳kill二分.md` §7–§8）

现象：注入生效后 10–13 s 被 `dev.mars.secure.ProxyApplication.f()` → `Process.killProcess` 杀（SIGKILL，无栈）。因果二分证明**触发源不是注入的 JS**（空注入包同样被杀），且**非确定性**（同构构建第 4 次运行存活 210 s+）。

处置（`YsxzExitTrace.cpp`，只加判据）：`H_kill` / 新增 `H_tgkill` / 扩展 `H_syscall(__NR_kill 129, __NR_tgkill 131)` —— 仅当 `target ∈ {getpid,gettid,0,-1} && sig==SIGKILL` 时静默丢弃，其余（含 SIGTERM/SIGABRT、非 self）全透传；`BlockShellExit`（exit/_exit 只结束线程）原样保留。

实测：guard 前 3/4 轮被杀 → guard 后 **5 轮全存活**（180 s + 4×45 s）；如实标注：`自杀式 SIGKILL 被拦` 日志一次未出现 ⇒ **拦截动作尚未被真实触发过**（这几轮壳没走到 killProcess）。

### 4.4 过检测层整体移除（含 speed_layer 抽离）

- 过检测**全部是一层 JS**（`ysxz_anticheat/ac_layer.js` 624 行），随 patch JS 编进 so 并内嵌进 `assets/main.js`；native 侧无独立过检测目标。
- **关键坑**：战斗加速（功能第 6 项）的实现体长在 ac_layer 里 ⇒ 直接删文件会让战斗加速整项消失。
- 处置：新建 `ysxz_anticheat/speed_layer.js`（只留 applySpeed / installDeltaScale / startSpeedLoop / tickSeen / dtScaled / speedMul / dtHits / speedPath / schedClock，对外 `window.__starry_speed`）；`build_ac_patch.py` 删 E1–E8 八个 anchor、断言改 `__starry_speed` 并新增反向断言 `__starry_ac` / `ANTI_CHEAT_ENABLED` 计数为 0；`auto_layer.js` 的 battleSignal 次通道由 `__starry_ac` 改读 `__starry_speed`（唯一真实耦合点）。
- 包内复核（本次收官实测）：arm64 so `__starry_ac=0` / `ANTI_CHEAT_ENABLED=0` / `__starry_speed=5`。
- **不动**：`YsxzSecShell`、`YsxzAppComponentFactory`（属壳自检净化，不是检测绕过）。

## 8. 副本自动战斗：定案「服务端裁决，不可实现」（code=7）

1. **不是另一套判定**：全包只有一处自动战斗按钮（battleRender L10461/L10947），点击判定同一句 `(mA.bGA?.d) || monCard.gdk.gdg()`（L10996），副本与普通冒险共用同一开关。
2. **差别在出口**：普通冒险走本地回执（`bHh=r` + `bFS` 入队列，由本地战斗控制逐帧取走 → `battleLogic.gi` → 写成员位起游戏 AI）；副本是**带 connectInfo 的在线局**，走 `battleMgr.bHy` → RPC `reqAutoBattle`。
3. **请求体只有布尔**：sproto `reqAutoBattle {id:7218, request:"boolean", response:null}`（main L32163-32168），**无等级/VIP/特权字段**。
4. **实测**：客户端三处已放行（baseline `gdg` granted、`funcOpen.ckw(MONTH_CARD_OPEN=26)`、fix6 收窄的 buff 族），请求确实发出，**服务端回 code=7**；code 7 = `SystemError.illegalOperation`，命中框架白名单 ⇒ **连 toast 都不弹**，观感就是「点了没反应」。
5. **不做的方案**：本地回执兜底（`bFS`）会被下一次服务端成员同步 `bsI` 覆盖回 false，动作进不了服务端帧序列，且越过硬约束 #11「只放行按钮可点、不接管战斗」⇒ 评估后**不实施**。
6. 结论：**客户端无字段可改**；真要解决只能由服务端授予 AUTO_BATTLE 权益（账户/付费/运营侧），不在客户端范畴。
