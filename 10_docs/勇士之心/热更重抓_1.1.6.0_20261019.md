## 2. 根因：`$eZ.monCard` 那个类的短名【整体顺移】

## 4. 「自动分解一直不会分解」——本轮改成可定案

因为上面四项锚点全在，10-07 那版代码结构上没问题；「不会分解」只能是**运行期事实**问题。
按卡密包作者 `_sdDump` 的思路，加了一次性决定性诊断（每次会话最多几行，热路径不发协议）：

```
[sd] 装备容器@bXk 共 N 件 | 锁定 L | 可取品质失败 F | 可分解 D | 品质分布[1:x 2:y 3:z] | api bYJ=function …
[sd] 判定: 容器里有装备但【没有可分解件】—— EquipTable.decompose 为空(低品质/低等级)或全部 isLock
```

外加：
1. 容器回落 `bXk -> bYn`（卡密包同款回落，防 `bXk` 改名）；
2. 包一层 `bag.pk`(分解协议 `Bag.decompose`) / `bag.pf`(出售协议 `Bag.sellItem`)，把 promise 的 `code` 打出来 ⇒ 区分「协议没发」与「服务端拒」；
3. 第 20 秒先探一次容器（**不发协议**），即使玩家没打一局也能拿到容器事实；
4. `可分解=0` 时不再空发协议，改为日志说明（避免无意义协议刷网络）。

> 已知的强候选根因（卡密包作者原记录）：「分解要 50 级」= `EquipTable.decompose` 为空即不可分解。
> 本轮诊断第一行就能把这条证实/证伪，不需要再猜。

## 8. ④ 自动主线关卡：本轮结论

**可以做，但不建议并进本轮**，理由与证据：

1. 该功能是卡密包 1,600 行状态机（`提取_补丁_v66_原始.js` L5059–L6700 + L4096–5058 的助手层），
   驱动的是**真实协议**（走章节、提交任务、上报 clientEvent）；作者本人为「联网协议撞车」写过多次修（L6228-6232 注释）。
2. 关键按钮方法已漂移：`pickFn(["eff","efe","efk"])` 里 **`efk`/`efe` 在 1.1.6.0 已不存在**（`grep` 计数 0），
   `eeV`（FuncOpenPanel）同样为 0；`eff`/`efd`/`efA` 仍在。⇒ 照抄必挂，需要重新派生。
3. 它读角色/任务数据结构短字段（`role.fBb.fAQ`、`fBm`、`fBe`、`bSq` 等），这些必须逐项在 1.1.6.0 上重新确认；
   而它内部还调 `fDn.fDc`（本次漂移的同一个类）—— 说明这份代码整体是"贴着旧版写的"。
4. 本轮已经同时改了「金卡判定 + 出售/分解 + dex」三处；按「一轮一个变量」纪律，再把 1,600 行状态机塞进同一个包，
   一旦无效就无法归因。

⇒ 建议下一轮单独做，口径先收窄到：**只做「结算面板自动继续（AdventureResultPanel / TurnCardPanel）+ 自动选关」**，
用结构化/行为发现替代 `eff/efe/efk/eeV` 短名，跑通后再扩到整套任务链。

## 10. 追加：用户追问「解锁金卡后，结算翻卡额外获得装备怎么没有？」

### 10.1 机制（`assets/game/index.js` 1.1.6.0 实测行号）

翻卡面板 `AdventureTurnCardPanel` 把结算卡分三组（`$DD`：`c=1` 免费 / `d=2` 特权 / `e=3` 道具）：

| 事实 | 行号 |
|---|---|
| 特权行是否显示 = 该副本 `InstanceRewardTable.cardReward` 里有没有第 2 组 | L49910 `list_privilege.numItems = r.get(b.$DD.d) ? 4 : 0` |
| 一张特权卡能不能翻，只看**服务端下发那张卡对象上的 `hasPrivilege`** | L51761 `this.egP.hasPrivilege \|\| (n = !1)` |
| 没有该字段时的文案 | L51822–51825 `n = "购买月卡后获得"` |
| 特权卡【不消耗道具】，客户端把 `type=2` 改发 `type=1`（免费） | L51893 `if (this.egR == a.d) e = a.c` |
| 翻卡走服务端协议 `FightInstance.selectCard` | L180808 `bFh` → `gsMgr.cQA(SprotocolMap.FightInstance.selectCard, …)` |

`hasPrivilege` 在**整个 bundle 里只有 3 处读、0 处写**（`grep -rn hasPrivilege` 仅 L51761/51797/51822）
⇒ 它不是客户端按 `$eZ.monCard.fDf("gold")` 现算的，而是随卡数据由服务端下发（推断，依据：无客户端写入点）。

**结论**：我们「解锁金卡」改的是客户端本地 buff 查询（`fDf("gold")`），
而特权翻卡的准入字段是另一条链路（服务端 `hasPrivilege`）⇒ **本地解锁不会让那 4 张牌变成可翻**
（它们会停在「购买月卡后获得」）。这就是「怎么没有」的直接原因。

### 10.3 顺带发现（很重要，直接解释「自动分解一直不会分解」）

结算面板 `AdventureFinishPanel` 里**游戏自带**自动出售/自动分解，整块被金卡判定门控：

```js
if (… && $eZ.monCard.fDq.fDf("gold")) {
  $eZ.localMgr.cnn($NV.b) && (btn_again.visible || btn_toNext.visible) && …;   // 自动重复挑战
  var Z = [COMMON, SENIOR, RARE], x = Z.filter(t => $eZ.localMgr.cnp(t));
  x.length > 0 && $eZ.bag.bYK(x);      // 自动出售
  var N = Z.filter(t => $eZ.localMgr.cnq(t));
  N.length > 0 && $eZ.bag.bYJ(N);      // 自动分解
}
```
（L48851–48868）

⇒ 以前金卡判定恒 false，这段**整块不执行**，所以「自动出售/自动分解」从根上就不会动。
本轮金卡修好之后，这条路才真正打开（我们那层回城触发是第二重保险）。这与 §9 的「当前装备可分解=0」并不矛盾：
两者叠加才是用户看到的「一直不分解」。
