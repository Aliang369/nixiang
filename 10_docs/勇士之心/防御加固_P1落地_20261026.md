## 1. 一个必须先说的技术偏离（用户可否决）

**非对称算法由计划里的 Ed25519 改成 RSA-2048 PKCS#1 v1.5（SHA-256）。**

| 原因 | 证据 |
|---|---|
| 出包环境**无网络** | `web_fetch https://tweetnacl.cr.yp.to/...` → `fetch failed`；仓内 0 个 curve25519/ed25519 实现 |
| 本机**无 Windows C 编译器** | `where cl/gcc/clang` 全部无输出，只有 NDK clang（只能编 Android 目标） |
| 手写 curve25519 字段运算风险高 | 需要 fe/ge 群运算 + modL 规约约 600 行，任一细错 ⇒ 全员授权异常 |
| RSA 验签实现面小且**可被 JDK 完整对拍** | `sg_rsa_pkcs1.py` 签出的签名与 JDK `SHA256withRSA` **逐字节相同** ⇒ C 实现正确性可被机器证明 |

**安全性质完全等价**：两者都是「只有私钥能签，客户端只有公钥」——破解者剥包剥不出私钥，签不出票，二次加卡密倒卖这条路被同样掐断。
**代价**：票长 559 B（vs 约 100 B），验签约 20 ms 一次（只在登录/续票时），包内多约 6.5 KB 代码。

> 若你坚持 Ed25519：需要先解决「有网取一份可审计实现」或「接受我手写 + 只能靠 JDK 做的黑盒对拍」，建议不要。

## 4. 本轮踩到并修掉的两个真 bug（记教训）

1. `uint8_t chk[8]` 接 `sha256()` 的 32 字节输出 → **栈溢出，设备上 SIGSEGV**（`apply` 成功但 `live()` 崩）
2. `sg_derive_key` 里同样把 32 B 写进 8 B `canary` → canary 恒错 ⇒ `live()` 恒 false

两个都是「看着对、跑起来崩/静默失效」，靠**真机跑向量**才发现 —— 印证了「静态看过不算数」。

另有一处工程坑：pwsh 调 `bash -c` 传中文路径会被吃字符（命令静默不执行）；改用 ASCII 路径的 runner 脚本（`09_test/ysxz/run_*.sh`）。

## 5.5 已知限制（写清楚，别当已解决）

1. **so 自身不在完整性清单里**（自指不可能）。改 so 的破解者必须重写整个门禁与功能载荷 —— 成本极高，但理论上不是"被检测到"。
   下一步（P2）可用「服务端签名的 build 清单」补：票里带 `build_id`，服务端只认自己发过的 build。
2. **完整性依赖 Java 传 `getPackageCodePath()`**：若某些渠道用 overlay/免安装装载，路径不同会判 `g=0` ⇒ 功能全灭（fail-closed）。酋士之心 1.0.3 是直装线，不受影响；将来上渠道包要先验这条。
3. **dex 明文**（`-dontobfuscate`）：本轮没做类名重写（P1 未含），破解者仍能读懂逻辑，只是改不动（一改完整性就炸）。
4. **v1(HMAC) 票还在**：过渡期必须留，一版后连同服务端 `grant_hmac_secret` 一起退役 —— 否则密钥泄露仍有铸币权。

## 9. 兼容性口径（重要，别踩）

1. **新包 + 旧服务器 = 能用**：旧服务器只发 v1 `grant`，客户端 `pickGrant` 缺失 grant2 时回落 v1，native 仍支持 v1 解析 ⇒ 功能照旧。用户没部署新服务端之前，本包只是"带着新防御但没启用 v2"。
2. **旧包 + 新服务器 = 能用**：新服务器同时发 v1（`grant`）与 v2（`grant2`），旧客户端只读 `grant`。
3. **新包 + 新服务器 = 全加固生效**：客户端优先 grant2，native RSA 验签。
4. 客户端**故意不做 v1 回退兜底**：v2 验不过就失败（fail-closed）。若现场出现"登录成功但功能不开"，先查公钥指纹（`gen_pubkey_header.py --check`）与 `grant_rsa_key_path` 是否配对。
