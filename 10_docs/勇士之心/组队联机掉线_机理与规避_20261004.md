# 组队/联机「掉线」机理与规避方案（2026-10-04）

> 对象：勇士之心（`com.fightingstars.games.warrior`）星光版；证据来自解密后的运行时 bundle
> `09_test/_plain2/assets__game__index.js`（1.1.4.0 明文）与 `assets__battleLogic__index.js`。
> 结论适用范围：所有「改战斗逻辑」类 MOD 功能在**联机副本**中的行为；不限于本游戏。

---

## §0 一句话结论

联机副本用的是**帧同步（lockstep）+ 服务端权威帧**：所有客户端跑同一份 `randomSeed` 的确定性战斗逻辑，
本地帧序列要能和服务端下发的 `frameList` **逐个 id 对齐**。
改本地战斗逻辑（秒杀 / 无敌 / 无限技能 / 改时间缩放）⇒ 本地状态与权威帧分叉 ⇒ 补帧永远对不上 ⇒
重试 3 次后主动断线 —— **这就是「组队掉线」，它不是网络问题，客户端修不了**。

可行的只有策略层规避：**检测到联机上下文时自动停用改战斗逻辑的功能**（判据已在 §5 给出，是现成的）。

---

## §1 现象

- 用户原始诉求（m00001 第 ④ 项）：组队 / 联机组队掉线或网络冲突；「不能修 / 影响大就放弃」。
- 服务器公告侧也自认这是灰区：「游戏检测加强，打团队、多人匹配副本、刷塔、联机副本存在封号的风险，请谨慎使用。」

## §2 证据：联机 = 帧同步 + 服务端权威帧 + 结算上报

### 2.1 randomSeed 来源即可区分「本地战斗」与「联机战斗」

```js
// assets__game__index.js:179957  （战斗初始化）
this.bDH && $eZ.battleServer.room.cWc
  ? this.bDC.randomSeed = $eZ.battleServer.room.cWc.randomSeed     // ← 联机：服务端下发
  : this.bDC.randomSeed || (this.bDC.randomSeed = Date.now());     // ← 本地：本地生成

// assets__game__index.js:222525-222527（渲染侧取 seed）
var c = i.bDC.randomSeed;
if (this.ctrl.mA) { c = $eZ.battleServer.room.cWc.randomSeed; }     // ← ctrl.mA = 联机标志
```

`ctrl.mA` 就是「联机实例」标志；联机时 `randomSeed` **必须**来自 `room.cWc`，否则本地与服务端不是同一局。

### 2.2 权威帧序列由服务端下发，补不上就断

```js

```

`AUTO_FILL_FRAME_ERROR` 就是玩家看到的「掉线/重连失败」。
注意：**帧序列的权威在服务端**（`grep 'syncFrame'` 命中 `M_Protocol.FightInstance.syncFrame`，
`:221333` / `:246617` 注册与发送），客户端只是补齐并执行。

`result` / `useTime` / `hpRemain` / `score` 都是裸的上报值 —— 也就是说
「秒杀 + 满血通关 + 时间极短」在联机副本里是**同时**触发掉线和服务端异常判定的组合。

### 2.4 帧序列可整段回放

```js
// assets__game__index.js:226569+  （回放解析）

  case i.SprotocolMap.FightInstance.onCreate.id:  b.b = m.message; break;

```

`onCreate` + `syncFrame` + `onSettle` 三类包可离线回放 ⇒ 服务端/对手侧持有完整replay，
本地逻辑改动的痕迹**不会消失**。

## §3 机理

```
服务端下发 randomSeed ──► 所有客户端跑同一份确定性战斗逻辑 ──► 每帧计算结果必须一致
        ▲                                                        │
        │                                                        ▼
   权威 frameList ◄──── 客户端上报帧/状态 ────────────────► 本地状态（被 MOD 改过）
                                                               │
                        帧号接不上 / 状态不一致 ────────────────┘
                                    │
                       retryReqSyncFrame ×3 → AUTO_FILL_FRAME_ERROR → 掉线
```

1. 帧同步的**前提**是「同输入 + 同逻辑 = 同状态」。MOD 改的是逻辑或状态（HP 直置 0、伤害倍率、
   技能门恒真、时间缩放），任何一条都会让本地状态与权威帧产生**不可逆**分叉。
2. 分叉一旦发生，本地帧号与服务端 `frameList[0].id` 就再也接不上（§2.2 的严格相等判断），
   重试 3 次后直接判错断线 —— 表现为「进副本秒掉线」「打一会儿突然掉」。
3. 「移速 / 时间缩放」类功能虽然不改血量，但改了**帧推进节奏**（`worldTimeScale` / `hTimeScale`），
   同样会让本地帧的产生时机与权威帧错位，危害与改血量同级。
4. 单人/本地副本（`randomSeed = Date.now()`）没有权威帧对齐，所以本地改逻辑**不触发**这条链 ——
   这就是「单人刷图没事、组队就掉」的全部原因。

## §4 能不能修？

**客户端修不了**，理由是逻辑性的，不是工作量问题：

| 想让联机不掉线 | 需要做的事 | 与 MOD 目的的关系 |
|---|---|---|
| 让本地帧与权威帧一致 | 不许改任何影响状态或帧节奏的逻辑 | 与「秒杀/无敌/无限技能/移速」直接冲突 |
| 让服务端接受被改过的帧 | 伪造/篡改帧序列或结算上报 | 属于服务端对抗，必然触发检测（公告已明说封号风险） |
| 只在本地表现层改 | 只改渲染（特效/UI），不改逻辑与帧 | 可行，但那已经不是「功能」类 MOD |

结论：**放弃「在联机副本里修好掉线」这个方向**，改为下面的规避。

## §5 可做的规避：联机自动停用（推荐，判据现成）

### 5.1 判据（任一条成立即视为联机上下文）

```js
// 1) 服务端下发了 seed —— 最干净、最权威
const room = globalThis.$eZ && $eZ.battleServer && $eZ.battleServer.room;
const online = !!(room && room.cWc);                       // room.cWc.randomSeed 来自服务端

// 2) 渲染控制器联机标志
const online2 = !!($eZ.battleMgr && $eZ.battleMgr.bDC && $eZ.battleMgr.ctrl && $eZ.battleMgr.ctrl.mA);

// 3) seed 不是本地生成（本地 = Date.now()）
const seed = $eZ.battleMgr && $eZ.battleMgr.bDC && $eZ.battleMgr.bDC.randomSeed;
const online3 = !!(room && room.cWc && seed === room.cWc.randomSeed);
```

### 5.2 停用清单（改状态 / 改帧节奏 ⇒ 必停）

| 功能 | 是否改动战斗状态或帧节奏 | 联机处置 |
|---|---|---|
| 秒杀（f1，改伤害/直置 HP） | 是 | **停用** |
| 无敌（f2，拦截死亡/受伤落点） | 是 | **停用** |
| 无限技能（f3，门恒真 + 清 CD） | 是 | **停用** |
| 移速 / 时间缩放（f4） | 是（帧节奏） | **停用** |
| 自动战斗（f5） | 是（代打输入） | **停用** |
| 纯界面/纯本地表现 | 否 | 可保留 |

### 5.3 落点

- 补丁侧：在 `_ysxz_patchjs.js` 的 `MOD_boot` 内加 `online()` 探测，命中即对 f1–f5 的挂钩**全部旁路**
  （挂钩仍在，但函数体直接走原逻辑），并在菜单/日志打一条 `[MOD] online instance → combat mods suspended`。
- 菜单侧：加一个「联机自动停用（默认开）」开关；关闭时给出显式警告文案。
- 本文件对应的排查结论：**不要把「组队掉线」当成 bug 去修**，把它作为「设计约束」写进规约。

## §6 风险提示（须随包公告）

- 联机副本（团队 / 多人匹配 / 刷塔 / 世界BOSS组队）中，即使功能被自动停用，
  客户端存在 MOD 环境本身仍可能被判定为异常环境 ⇒ 仍建议不使用。
- 服务端公告原文：「游戏检测加强，打团队、多人匹配副本、刷塔、联机副本存在封号的风险，请谨慎使用。」
