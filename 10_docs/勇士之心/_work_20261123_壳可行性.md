# 勇士之心 1.0.6 壳可行性判定（去掉 SignSpoof 后改签还能不能起）

> 生成：2026-11-23 只读分析（壳可行性判定子代理）。**未改任何代码与既有文档、未重签、未装/卸包、未动游戏数据、未截图**；唯一写入＝本文件。
> 输入底包：`02_apks/勇士之心_1.0.6_official.apk`（65,531,496 B / md5 `c06a1c1e3cc4f57e4d9ab29ecd9becfa`）。
> 证据分级（AGENTS §5）：本结论＝**静态证据支持的推断（高置信）**，未做装机实测（本轮禁止装机），标「未实测」。

---

## 0. 结论：不能

**改签（CN=StarryMagic）后、没有签名源时，1.0.6 起不来。**

一句话机制：引擎解密密钥 ＝「内嵌常量 ⊕ f(运行时签名, 包名)」，运行时签名取自 Java `PackageManager`。改签后取到的是星空证书 ⇒ 密钥错 ⇒ `key unwrap failed (sig/package mismatch?)` ⇒ 明文 `libcocos2djs.so` 不落盘 ⇒ `refuse empty mlib` ⇒ 引擎不加载。

- `SignSpoof` 当年干的事就是把 `PackageManager` 查到的签名换回官方证书（日志 `spoof hit md5=79a6a62f…`），所以 10-24 那版能起。**签名源一撤，这条路就断。**
- 壳的 root / 模拟器检测**不是**阻断点（官方包在本机 root 雷电上正常启动、引擎已解密落盘，见 §3）。
- `YsxzSecShell`（清 `dirty/FailedMask`）救不了：它能清**状态字**，清不掉**密钥**。

## 2. 机制链路（按 libsecret 内部顺序）

1. `JNI_OnLoad` 装壳 → 413~483 ms 自检（签名 / 完整性 / root / 反调试…），结果写 `CheckedMask/FailedMask`，任一项失败置 `dirty=1`。
2. 取「运行时签名」（Java `PackageManager.getPackageInfo(..., GET_SIGNING_CERTIFICATES / GET_SIGNATURES)`）。
3. 与 `.data` 0x66aed 的官方 SHA-256 比对；不一致 ⇒ `signature check failed, possible repack/theft` + 置 check-signature 位（**只置位**）。
4. 密钥派生（VA 0x4f188）：`key = const48 ⊕ digest(运行时签名 ……)`，结果缓存。
5. 用该 key 解 `assets/apksecurefile` 与 `assets/apksecuresolib/<abi>/libcocos2djs.so` ⇒ 密钥错就 `key unwrap failed (sig/package mismatch?)` ⇒ `refuse empty mlib`。
6. 即使 `dirty=1`，`Games/YsxzSecShell.cpp` 的 watchdog 只清状态字（让真实 `Application.onCreate` 被调），**不参与密钥** ⇒ 结论不变。

## 4. 若"不能"——四条替代路线

| 路线 | 做法 | 工作量 | 风险 |
|---|---|---|---|
| **R1 窄口径签名源（推荐）** | 只在本包、只在 Application 之前，把 `PackageManager` 对「本包签名」的查询返回**官方证书 DER**（DER 可从官方 APK 的 v2 签名块提取，等同当年 SignSpoof 的 `YSXZ_CERT_B64`）。**不要**恢复旧 SignSpoof 的 50 包白名单 / `killPm` / 隐藏 API 豁免那一套 | 编码 2–3 h ＋ 1 轮装机 30 min | 中高。① 政策门：SignSpoof 系列 2026-10-28 整体删除，**恢复须用户当轮指令**（AGENTS §3.3、规范变更日志 2026-10-28 18:4x）；② 雷电 userdebug 可过，Android 14+ 真机对私 API 豁免历史上有失败记录，需以本机实测为准；③ 只改 dex，不碰 libsecret ⇒ 13 条必保条目不受影响 |
| **R2 动 libsecret 的取签名函数** | 让其（VA 0x4efd0）返回官方 DER 构成的 `std::string`：静态改字节，或自家 so 里 inline hook | 4–8 h（含三 ABI、C++ 返回约定） | 高。撞壳 `.text self-check`、APK 完整性 bit9、`surgical_ysxz_1.0.6.sh` 的 13 条必保条目与 `protected entry tampered`；状态位可清，改指令的副作用必须真机验证 |
| **R3 绕壳加载明文引擎 so** | 用已落盘的明文 so（35,844,552 B，现设备可取）旁路 `apksecuresolib`，把加载路径改到明文（同族先例：`04_scripts/动物大联盟/patch_secret_jnipath_dwdlm.py`、`patch_engine_keyref_dwdlm.py`） | 6–10 h | 最高。三 ABI 都要明文 so；逐 ABI 验证；包体 +20~100 MB |
| **R4 换回 1.0.3 线** | 走现成 `ysxz_build_so_103.sh` → `ysxz_assemble_103.py`；该代是 `fancy/` 加固、引擎 so 明文、无签名派生密钥 | 0.5–1 轮（脚本齐、历史 L3 通过） | 低。代价＝版本退回 vc3、热更需重抓；与「本轮用 1.0.6」口径冲突（`硬约束.md` B-13 原本写的就是 1.0.3 为交付线） |

**推荐顺序**：先请用户拍板 R1（放行窄口径签名源）；不放行就落 R4，**不要**先动 libsecret（R2/R3 会把一个未验证变量叠到"移除过检测层"上）。

## 5. 对「用户要求移除战斗过检测层」的影响

1. **无耦合**：过检测层是 JS（`04_scripts/勇士之心/ysxz_anticheat/ac_layer.js` 624 行，随 patch 编进 `libstarry_magic.so` 并内嵌 `assets/main.js`）；壳是 `libsecret.so` 的 native 解密与自检。删 AC 层**不会**让包起得来，也**不会**让它更起不来。
2. **边际成本很小**：R1 只改 dex，而本轮本来就要重跑 `ysxz_build_menu_dex.sh`（`surgical_ysxz_1.0.6.sh` L100-104 硬查 6 个 smali 类）⇒ 签名源与 AC 拆分可同轮做完，不额外增加装机轮次。
3. **若走 R2/R3**：会撞 13 条必保条目与壳完整性，出包链要改校验表并留对照；且会把"壳问题"和"AC 拆分"混进同一轮，违反"一轮一个变量"。建议壳先单独打通，AC 移除另起一轮。
4. **验收前提被前置**：功能层 13 项、`battle-speed` 日志、`[AC]` 0 条 —— 这些验收**全都要求包能启动**。所以壳问题是本轮**前置阻断项**，不是可并行项。
5. **登录不受影响（也不变好）**：R1 落地后 TapTap 仍报「包名、签名未正确配置」（TapSDK 自己解析 APK，历史实测打印星空指纹 `161fca32…`）⇒ 仍按短信登录，与过检测层无关。

## 7. 未取证 / 口径限制

1. **没有一次「改签 + 无签名源」的实机实测**（本轮禁装机）⇒ 本判定属"静态证据充分"，不是"实测"。若要升级为实测结论，最小实验＝R1 之外的对照包（改签、不装签名源）装一次看 `key unwrap` 日志，需用户授权装机。
2. `.data` 0x66b0d = 0x01 是**静态读值**；"该字节=0 就不混签名"是由控制流（0x4f220 `cbz → 0x4f294`）推断的，**0 路径能否解出正确密钥未验证** —— 别把它当现成方案。
3. logcat 里没有 `[secure]` 失败行，可能是日志级别或一次性打印导致静默；"root/模拟器不阻断解密"另有正面证据（进程存活 ＋ 引擎 so 已在 maps 中）。
4. 反汇编为线性扫描＋调用点上下文判读，函数边界靠导出符号（`SecShell_*`）序言推断；未做完整 CFG 重建（结论只依赖"运行时签名进入 KDF"这一条调用链，够用）。
5. 本轮**未**核对 10-24 那版成品包（`08_output/` 已不在仓）⇒ "当时 spoof 命中"引用的是文档与 evidence 日志，不是本机复跑。
