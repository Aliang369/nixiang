### 1.2 evalString 定位的三条独立证据（同一结论）

1. **调用关系**：JNI 桥（dynsym 0x2C1264）在 `0x2C12F0` `bl 0x31418C`，寄存器实参 `x1=script, x2=-1, x3=0, x4=0` ⇒ 命中 `evalString(const char*, long, Value*, const char*)`。
2. **序言同构**：0x31418C = `sub sp,sp,#0x150` + `stp x28,x27,[sp,#0xf0]`…，与 1.0.3 的 0x3138E4 同一套帧（这也是它成为稳定指纹的原因）。
3. **字符串旁证**：函数体内 0x314584 / 0x3145C4 引用 `ScriptEngine::evalString catch exception:` 与 `… script %s, failed!`。

### 1.3 新增的自动锚点（跨版本止血）

`ResolveEvalViaBridgeBl()`：先 `getSymAddress(JNI 桥)`，再扫其前 64 条指令里的 `BL`，凡是目标序言 == `0xD10543FF` 的就认作 evalString。
⇒ 下次再重编/换包，即使候选表没跟上，也能自动命中（1.0.6 实测命中 0x31418C；桥内另 3 个 BL 目标序言都不是该形态，不会误认）。

## 6. 新阻塞（本轮发现，未修，需 lead 决策）

**现象**：注入生效后进程在 10–13s 被**壳自己 kill**（不是崩溃）。

```
W System.err: java.lang.Exception: call killProcess callstack! pid=20597
W System.err:   at android.os.Process.killProcess(Process.java:1318)
W System.err:   at dev.mars.secure.ProxyApplication.f(EXCEPTIONCLASS:1)
W System.err:   at dev.mars.secure.ProxyApplication.d(EXCEPTIONCLASS:1)
W System.err:   at dev.mars.secure.ProxyApplication$d.run(EXCEPTIONCLASS:4)
W System.err:   at android.os.Handler.handleCallback(Handler.java:958)
I Process : Sending signal. PID: 20597 SIG: 9
```

**因果对照**：上一轮同壳同 ExitTrace、**splice 未命中**的包存活 200s（`install_20261123/RESULT_boot4.md` 判据①）；本轮 splice 一命中，10–13s 必死（两轮复现）。⇒ 触发点在「注入完成后」。

**已知缺口**：ExitTrace 想钩 `Java_android_os_Process_killProcess__I` 但 `dlsym` 失败（RegisterNatives，不在 `libandroid_runtime.so` 导出表）⇒ 壳走 Java 层 kill，拦不到。

**下一步候选（按成本排序，均未执行）**：
1. **因果二分**（最省）：把 `GetPatchJs()` 临时置空（`patch js empty -> passthrough`）出一个包 —— 活 ⇒ 触发者是注入的 JS；仍死 ⇒ 触发者是 Dobby 改写引擎代码页（壳自己在解密的 .so 上做校验）。
2. 若为 JS：查 `LshLog checkDebugMode`（kill 前 5.5s 打印过该行）与壳的 `ProxyApplication.d/f` 判定条件（需解 dex，`03_decompiled` 里没有该游戏）。
3. 若为 native：在 `YsxzExitTrace.cpp` 补 hook libc `kill/tgkill`（只丢 `pid==getpid() && sig==SIGKILL`，其余透传），或在壳层把 kill 决策的上游标志清掉。

> 在这条修好之前，用户进战斗仍会断线/退出 ⇒ 战斗内效果无法验证。
