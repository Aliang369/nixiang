# 勇士之心 · 卡在「正在为您加载游戏资源」根因（卸载重装后必现，2026-10-27）

状态：**根因已定位并有实机日志铁证；修法未施工（等用户确认）**

## 1. 用户现象

> 加了最新的防御（P2-2 载荷加密 + P2-3 诱饵）后，**卸载重装、重新下数据**，就一直卡在
> 「正在为您加载游戏资源」页面。

设备：雷电 `emulator-5554`（x86_64 + Houdini，root），包
`com.fightingstars.games.warrior.tt1`，设备内 `base.apk` md5 `fee4b2c7492e3975bc54f6874976f588`
（= 当前 P2-2 成品包，index 行一致的 `fee4b2c7`）。

## 2. 结论（一行）

**诱饵层不是「合法可执行」的：它没有定义 `window.__starry_capture`，而原生 splice 把
`assets/main/index.js` 改成了 `}(window.__starry_capture({…}))`。拿不到 K_build 的路径
（无票 ⇒ 诱饵）会在主 bundle 载入瞬间抛 `TypeError` ⇒ `evalString … failed` ⇒
`Failed to invoke require` ⇒ 引擎永远停在加载页。**

卸载重装只是**把「有票」变成「无票」**的触发器，不是游戏/服务端的问题。

## 3. 根因链（每步都有实测行）

| # | 事实 | 证据（`09_test/勇士之心/hang_20261026/decisive_lines.txt`） |

所以**不是加固/授权/签名问题，是诱饵层的 JS 契约破了**。

## 4. 为什么之前 L3 能过

P2-2 出包那台设备 prefs 里有 `auth_grant = 3\|dev_32c3fda…`（走过授权墙），启动时能解出真载荷
⇒ 12 项功能正常。**「无钥→诱饵」那条路径当时只跑了预检（进程存活 + 菜单弹出）就判 PASS**，
没有把「游戏能不能进场景」当判据 —— 这是本轮真正漏掉的验收口径（见 §6）。

## 5. 修法（待用户拍板，二选一或都做）

**A. 诱饵补透传（保留「看起来注入过」的假象，最小改动）**
- `YsxzDecoyJs.h` 里除了 noop 层，必须补
  `window.__starry_capture = function (reg) { try{…noop…}catch(e){} return reg; };`
- 自检：`node --check` 通过 + 断言含 `__starry_capture` 且 `return reg`（否则门禁拦包）。

**B. 解不开就完全不 splice（最保险，但改包者能看出没注入）**
- `GetPatchJs()` 返回空时，`HookedEvalString` 直接 `return g_origSeEval(...)`，不改写 bundle。

**共同前提（设计层）**：**「无票」只能让功能静默无效，绝不能影响游戏本体启动**。现在等于是
「要票才能进游戏、要进游戏才能输卡密」的闭环，任何新装机（含正版用户换机/清数据）都会撞上。

## 6. 顺带要补的两个门禁

1. **预检判据**：logcat 里出现 `ScriptEngine::evalString script … failed!` / `Uncaught`
   ⇒ 判 FAIL（现在只看「进程存活 / 菜单弹出 / 空转不崩」，会放过这种「活着但游戏死了」）。
2. **出包门禁**：诱饵必须自包含（定义 `__starry_capture` 并 `return reg`）；
   可加进 `harden_apk.py check` 作为 C10。
3. 已有事实（原样保留作为教训）：`harden_apk.py` 七项与「C7 载荷层已编译」都只证明
   **代码进了包**，不证明**诱饵路径可用**，与 P2-2 §5 三条坑同源。

## 7. 复现与证据

- 复现：卸载重装（或清数据）→ 冷启动 → logcat 过滤 `payload key absent|__starry_capture`。
- 原始日志：`09_test/勇士之心/hang_20261026/start_fresh.txt`（全量，2.8 MB）
- 决定性行：`09_test/勇士之心/hang_20261026/decisive_lines.txt`
- 采集方式：`adb logcat -c` → `am force-stop` → `am start` → 录 100 s（无任何界面点按）
