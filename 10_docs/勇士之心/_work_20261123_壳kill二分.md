# 勇士之心 1.0.6 · 壳 kill 因果二分（2026-11-23，agent-9）

> lead 定：先出「patch JS 置空」诊断包，判定壳 `Process.killProcess` 是不是注入的 JS 触发。
> 方法：**splice 机制照旧**（Dobby 钩 evalString、代码页照改），只把注入的 JS 置空
> ⇒ `HookedEvalString` 走 `patch js empty -> passthrough`，一行 JS 都不进 bundle。
> 这样「改代码页」与「JS 内容」两变量被拆开。

## 0. 结论（一句话）

**触发源不是注入的 JS。** 空注入包照样被杀：`patch js empty -> passthrough`（main+game 双双放行）→ 3.2s 后壳 `_exit(0)`（被 ExitTrace 拦）→ **172ms 后 Java 侧 `Process.killProcess` 补刀**。
同时发现该 kill **不是确定性**：同构的「hook + 正常注入」构建第 4 次运行存活 **210s+**（无 kill），所以它是壳自检失败后的一次**竞态**，不是「一 hook 就必死」。

## 3. 但「改代码页必死」也不成立（关键修正）

| 运行 | 构建 | 注入 | 结果 |
|---|---|---|---|
| #1 anchor-hit | 295,368 so | main+game 注入 | 17s 被 kill |
| #2 anchor-hit | 同上 | 同上 | 10s 被 kill |
| #3 diag-empty | 200,088 so | **无注入** | 11.3s 被 kill |
| #4 恢复包 | 295,416 so（= #1 源码 + 诊断开关本体） | main+game 注入 | **存活 210s+，无 kill** |

共同点（4 轮全有）：`[YsxzSec] normalized failedMask=0x8/0x200/…`（壳自检有多项失败，看门狗清零）；**每轮都发生过一次`_exit(0)` 被拦截**。

⇒ 真实机制更像是：**壳自检失败 → 壳先 `_exit(0)`（ExitTrace 只结束该线程）→ Java 侧 delayed handler 视时序补一记 `killProcess`**；补不补刀取决于竞态（#4 没补）。所以「注入行为」只是**提高了壳自检失败的触发概率**，不是唯一致死开关。

已知缺口：`[YsxzExit] 符号未找到(dlsym) libandroid_runtime.so!Java_android_os_Process_killProcess__I`（RegisterNatives，不在导出表）⇒ Java kill 路径当前完全没拦。

## 7. A 方案（拦自杀 SIGKILL）落地

改动文件：`mod菜单/starry-mod-menu/app/src/main/jni/Games/YsxzExitTrace.cpp`（只加判据，不动 exit_group(94) 陷阱）

### 9.3 位 → 检测：目前能确定的部分

1. **0x8 / 0x200 不是 kill 触发位**：这二位在**全部 5 次运行**（含 210s 存活那轮）都被 `normalized` 清掉过 ⇒ 属环境类常驻检测（root/模拟器一族），与是否被杀无关。
2. **退出路径已定位**：libsecret 里唯一的 `_exit` veneer 是 `0x5A5EC`（`b _exit@plt`），全库只有 4 个调用点：`0x3F044`、`0x453D4`、`0x45518`、`0x540E4`。
   实机日志里命中的是 **`0x45518`**，它属于 `0x45510` 这个两指令函数（`bl log; bl _exit`）⇒ 壳的「die」入口。
3. **位→检测名尚未 1:1 打通**：failedMask 的写点不是直接 `str w,[x,#0xd8]`（全库仅访问器一处读），写入走间接基址/指针，静态反汇编里没有可枚举的写点。
   下一步（未做）：① 动态——在 `n > 0` 的瞬间用 Frida/断点在写点抓调用栈；② 静态——找 `0x45510` 的调用者（当前无反汇编直调，说明经函数指针表）；③ 逐位实验——把 failedMask 固定写成单个位，看壳在哪一位走 die。
4. **最可疑的一族**：`libc inline-hook suspected` / `.text segment tampered` —— 我们 Dobby 钩了 libc 的 6 个函数 + 引擎 evalString，形状正好落在这两条检测的靶心。但「存活轮也钩了同样多」说明它不是充分条件（可能是扫描节拍/竞态）。

### 9.4 对 A 的处置建议

保留 A（成本 0、只在 self+SIGKILL 时静默丢弃，不影响正常退出）；把 C 的第 3 条（位↔检测打通）作为下一轮，打通后再决定是否撤 A。
