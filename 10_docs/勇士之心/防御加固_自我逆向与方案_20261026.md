## 0. 结论（先回答「我的要求能不能做」）

| # | 要求 | 判定 | 一句话理由 |
|---|---|---|---|
| 1 | 删掉卡密系统/屏蔽账号页 ⇒ 直接打包玩 | **能做**（当前做不到，正是最脆的一环） | 现在门禁是**一个全局 bool**（`g_rt_ok`）+ **可读 dex**；门禁下沉到功能执行点 + 自完整性校验 + 非对称票后，删掉任何一层都只是「功能静默失效」，不是「游戏照玩」 |
| 2 | 层套层加密 + 最外层是假的 + 许可 root 绕过、禁二次加卡密倒卖 | **大部分能做，有一处必须说清楚的物理边界** | 非对称签名（破解者无法自签票）+ 票派生密钥的载荷分层加密 + 诱饵层 + 水印溯源 + 服务端黑名单，可以把「删我卡密→挂自己的卡密卖」这条路从**几小时**抬到**不可行**；但**客户端不可信**是原理性事实：拿到包的人在本地一定有最终解释权，能做的是「成本极高 + 可追溯 + 可远程吊销」，不是数学意义上的「禁止」 |
| 3 | 每次打包自动带加固，不用我手动做 | **能做** | 出包走的是 `ysxz_assemble_103.py`（单点组装）→ 在里面加一个 `harden` 阶段 + 交付门禁断言即可；断言不通过就不出包 |

**一句话**：这三条都在可做范围，而且第 1 条的「一个点断全部」确实是当前真实存在的漏洞（下面 §2 有证据和定位）。但「完全防住」不存在，方案的目标是把攻击者从「删个 bool」抬到「重写整套授权+载荷解密+逐版本跟新」，同时让他做的每一步都可追溯到具体卡密。

## 2. 六个真弱点（按被利用的容易度排序）

> 下面每条都是「实测事实 + 推断利用路径」，推断部分标了【推断】。

### W1 ★★★ `session_live()` 是单点总闸（正是用户直觉里的"一个点断卡密"）
事实：整个授权只落到 `g_rt_ok` 一个 static bool，9 个调用点全读它。
【推断】利用：IDA 里用 `[验证] grant ok exp=%lld` 交叉引用 → 20 分钟内落到 `apply_grant_utf8` 与其调用者；把 `session_live` 改成 `mov w0,#1 ; ret`（2 条指令）⇒ 9 个门全开，连票都不用伪造。
⇒ 破解成本：**一次性 1~3 小时，之后所有版本通用**。

### W2 ★★★ 对称密钥可提取 ⇒ 破解者能「自签票」= 天然支持二次加卡密
事实：`GRANT_HMAC_SECRET` 与 so 内 pepper 是**同一串**，且**跨游戏共用默认值**（`GRANT_AUTH.md`「默认密钥已经和 APK 对上了，不改密钥就不用动 native」）。
【推断】利用：`OBFUSCATE()` 是编译期变换（`jni/Includes/obfuscate.h`），静态剥或运行时 dump 都能拿到 24 字节明文 → 用 python 20 行 `hmac_sha256` 就能给任意 device/game 签票 → **他的卡密系统只要调一次 `nativeApplyGrant` 就正版放行**。这不是"绕过"，这是"拿到铸币权"。

### W3 ★★★ 没有自完整性校验 ⇒ 整个授权层可以整块替换
事实：包内 `classes1..4.dex` / `libstarry_magic.so` / `assets/main.js` 都没有任何哈希或签名互验。
⇒ 删掉我的 dex、换成自己的菜单+卡密，运行时没有任何一方会拒绝。

### W4 ★★☆ Java 侧明文可读 ⇒ 账号页/门禁逻辑白送
事实：`-dontobfuscate` + `-keep class com.starry.magic.** { *; }`。
⇒ 「屏蔽账号页」在 UI 层是几行 smali 的事；`requireAuthForFeature` 一个 `return true`。虽然 native 还挡着（W1 才是真闸），但**UI+Java 层完全没有防御价值**，等于把地图免费送人。

### W5 ★★☆ 明文日志 = 逆向路标
事实：交付包里 `[验证] grant ok` / `grant rejected` / `boot self-heal` 都在（`STARRY_DIAG` 只管诊断行，证据行无条件保留）。
⇒ 攻击者不用读懂任何逻辑，按串 xref 就能定位门禁。这是"自己给自己指路"。

### W6 ★☆☆ 无溯源 ⇒ 倒卖无法追责
事实：票据里有 device/game，**没有 per-buyer 水印**；服务端也没有"哪个 build 在流通"的概念。
⇒ 包被倒卖后，无法判断是哪张卡/哪台机器泄的，只能全量换密钥重发（成本全落在你身上）。

## 3. 目标架构：L0–L7（每层都写清"落到哪个文件、怎么验收"）

```
L0 打包期（每次出包自动）  ── 生成 build_id / 密钥材料 / 签名清单 / 断言不过不许出包
L1 反分析                 ── 去路标 + dex 串加密（+ 可选：per-build 类名重写）
L2 自完整性               ── 清单签名 + JNI_OnLoad 校验 + 随机间隔复验 + 失败静默降级
L3 授权（非对称）          ── Ed25519 票 + per-feature 位掩码 + 票派生会话密钥 K
L4 载荷分层加密            ── 功能块 = K ⊕ build_key ⊕ feature_key 三层；无钥即垃圾
L5 诱饵层（"最后是个假的"）── 显眼的假成功通道 + 真路径另用 K' + 静默上报
L6 水印溯源               ── 每卡 16B 水印，进请求头/本地状态/日志分量
L7 服务端 = 唯一不可破的一层 ── 短票 + build 白名单/黑名单 + 敏感功能只走 OTA
```

### L0 打包期（**这条直接满足要求③**）

- 新脚本 `04_scripts/_common/harden_apk.py`（跨游戏共用），由各游戏 assemble 脚本调用：
  `04_scripts/勇士之心/ysxz_assemble_103.py` 末尾加 `harden` 阶段；`pipeline.json` 增加 stage `harden`，`pipeline.sh next` 自然带上。
- 每次出包固定产出（写进 `08_output/<游戏>/build_meta_<date>.json`，入库）：
  `build_id`（随机 8B）、`key_epoch`、`seed`、受保护条目清单与哈希、水印规则、`harden_ver`。
- **门禁断言（不合格直接 fail，不出包）**：
  1. 包内无明文路标串（`[验证]`/`grant ok`/`grant rejected`/`session_live` 等词表）
  2. 清单签名可被包内公钥验证通过
  3. `libstarry_magic.so` 内含 `build_id`
  4. 无票启动自检：`harden_apk.py --redteam` 三条攻击路径（改 bool / 换 dex / 自签票）必须全部失败或落进诱饵
- 交付门禁：`check_release_clean.sh` 增加「加固产物齐套」一项。

### L1 反分析（解决 W4/W5）

1. **去路标（必做，低风险）**：交付构建把证据行改成 `SDIAG` 或换成 8 字节 hash 短码（`[验证]` → `[V:1a2b]`），保留「能自证装上/被调用」的能力，但不再指向门禁函数。判据：`strings` 词表 0 命中 + 现有实测判读脚本仍可读。
2. **dex 字符串加密（必做，中风险）**：构建期把敏感串（URL、字段名、`nativeApplyGrant`…）替换成 `SgS.d(id)` 查表 + XOR/RC4，解表密钥来自 L3 会话密钥（无票时解不出 ⇒ 天然联动）。
3. **per-build 类名重写（可选，高风险，建议 P3）**：在现有 smali 轮（`ysxz_build_menu_dex.sh` 已经在做 apktool→smali→dex）里把 `com.starry/**` 改名为每版随机包名，同时 ① 生成 `SgNames.h` 给 native 用（仓库已有生成头先例：`gen_ysxz_patch_header.py`）② Manifest 里引用的组件名同步改名（`ysxz_assemble_103.py` 本来就在改 Manifest）。收益：所有网上流传的破解教程**每版作废**；风险：改名残缺 ⇒ ClassNotFound 闪退，必须 L1/L2 全量回归。

### L2 自完整性（解决 W3）

- `harden_apk.py` 生成 `manifest = {path: sha256}`，用 **Ed25519 私钥签名**（见 L3 密钥托管），签名块嵌入 so 的只读段（或 `assets/sg/manifest.bin`，两处互验）。
- native `JNI_OnLoad` 校验一次 + 独立线程以**随机间隔（30–120 s）**复验；读文件走 `openat/read` 直接读 APK 字节（不依赖 Java 层，防 hook Java 校验器）。
- **失败行为 = 静默降级，不是闪退**：功能改为 no-op、菜单显示正常、不弹任何窗（闪退等于告诉破解者"你被发现了"，也会误伤正常玩家）。同时静默上报 `{build_id, 水印, 失败条目}`。
- 反 hook：校验结果不存成 bool，而是作为**解密密钥的一段**（见 L4）——hook 掉校验器只会让密钥错，功能失效，攻击者拿不到"成功"信号。

### L3 授权改非对称（**这条是要求②的地基**）

- 票改 **Ed25519**：`payload = {v, device, game, exp, feat_mask, key_epoch, build_channel}` + 64B 签名；so 内只有公钥。
- 私钥**只在服务端**（`GRANT_HMAC_SECRET` 退役为过渡期双验：先验 Ed25519，再兼容旧 HMAC 一个版本）。
- **per-feature 位掩码**：不再只有「游戏开/关」，每个功能一位；门禁从 `if (session_live())` 改为 `if (feat_ok(i))`，且 `feat_ok` 的实现分散在 3 个不同函数（Tick/SetValue/JS 注入各一处，实现不同、结果参与不同运算）。
- 票验过后派生 `K = HKDF(ticket_sig, device, build_secret)`，K 不进任何 Java 对象、不留日志。
- 兼容性：离线宽限沿用现在的「进程内会话永不过期、冷启动对账一次」，玩家体验不变（这条是硬要求，不能为了安全让玩家反复登录）。

### L4 载荷分层加密（"一层之后还有一层"的落地）

| 层 | 密钥来源 | 缺了会怎样 |
|---|---|---|
| 外：服务器信封 | 服务器私钥签名 + 票 | 没票 ⇒ 拿不到 envelope |
| 中：build 层 | so 内 `build_secret`（随包 baked，`key_epoch` 轮换） | 换包/重签 ⇒ build_secret 变 ⇒ 旧密文全废 |
| 内：feature 层 | `K ⊕ feat_index`（每功能独立） | 有票但没买该功能 ⇒ 该功能块解出垃圾 ⇒ 静默 no-op |
| 芯：诱饵层 | 无（明文可见） | 见 L5 |

- 落地：`YsxzPatchJs.h`（113 KB）/ `YsxzBootBlob.h`（274 KB）现在是**编译进 so 的明文补丁**；改为「构建期加密 + 运行时按 feature 解密到临时页、用完 mprotect 保护并在秒级内清零」。
- 性能：单次解密 <5 ms（AES-CTR/RC4 级别），只在开功能/进战斗时做，不影响帧率。

### L5 诱饵层（"破解到最后还是个假的"）

设计要点：**留一个看起来"就是门禁"的显眼通道**，并让走这条通道的包"看起来能玩"：

1. `g_authorized` 这条**保持现状**（本来就是诱饵，`Main.cpp:255` 注释已写明），但补上：单独翻它 ⇒ 菜单显示"已解锁"、`nativeGetFeature` 返回 true、日志打"grant ok"（假）。
2. 真正的功能写入路径依赖 `K'`（只有真票能派生）：诱饵通道给的是 `K_fake`，解出的功能块 = **参数被缩放到无效**（例如伤害倍率×1、秒杀不命中）。
3. 诱饵通道被触发时立刻静默上报 `{build_id, 水印, device}` → 服务端把该 build 标为「在破解者手里」⇒ 之后的 OTA 载荷、新版本授权对它一律不给。
4. 断点检测（可选）：诱饵包在 20–40 分钟随机时刻把某一项功能回落到原值，制造"闪一下就没了"的反馈，进一步消耗破解者信任。

> 诚实说明：诱饵层不是"防住"，是"让破解者以为自己成功了、并在服务端留下指纹"。它有效的前提是**静默**——一旦闪退/弹窗，破解者立刻知道被骗。

### L6 水印溯源（解决 W6，也是「禁二次倒卖」唯一可执行的抓手）

- 发卡时服务端生成 `watermark = HMAC(server_key, card_id)[:16]`，随票下发。
- 客户端把它编进 ① 每个 API 请求头 `X-Sg-Wm` ② `Preferences` 里某个 hash 分量 ③ native 内存里的菜单渲染串（只进日志/上报，不显示给玩家）。
- 倒卖发生后：买家机器一上报就指向原始卡 → 你能精确吊销那张卡 + 该 build。
- 注意隐私与合规：水印只用于你自己发卡体系内部对账，不采集其他个人信息。

### L7 服务端（唯一"数学上不可破"的一层）

- 票短、可吊销；`key_epoch` 支持轮换（换钥后旧包仍能验旧票、新票只给新包）。
- build 白名单：只给自己发过的 `build_id` 发票；未知 build 一律拒绝（破解者自建的包无法获得票）。
- **敏感功能只走 OTA**（`ota.py` 已有 manifest/file + 会话校验）：把最值钱的功能实现放 OTA 载荷，本地只有解密器。这条是抬升成本最狠的一招，代价是需要联网。

## 4. 「允许 root 绕过，但不允许二次加卡密倒卖」怎么同时成立

这两条不矛盾，但要看懂它们各自能保证什么：

| 说法 | 技术真相 | 我们的做法 |
|---|---|---|
| 允许 root 绕过 | root/调试环境里，攻击者一定能改内存和 so。**不跟它对抗**（对抗 = 误伤正常 root 玩家 + 无谓维护） | 不做反 root/反调试强杀；检测到只做**遥测**，不阻断 |
| 不允许二次加卡密倒卖 | 「阻止他改包」不可能；「让改包卖不出钱 + 卖出去能被抓」可行 | ① 非对称票 ⇒ 他签不出有效票（除非重写整套授权）② 每版随机类名 ⇒ 教程失效、他得每版重做 ③ 载荷分层加密 ⇒ 他解不开功能块 ④ 水印 + build 黑名单 ⇒ 卖出去的包一联网就暴露，买家拿不到后续 OTA/更新 ⑤ 服务端只认自己的 `build_id` |

**换句话说**：他想卖，就必须自己重新实现"功能 + 授权 + 解密 + 更新"，等于重做一遍产品；他能拿到的顶多是「当前这一版的静态功能」，且一联网就掉 OTA、一溯源就封卡。

## 5. 分阶段落地（每阶段都保证"功能不受影响"）

| 阶段 | 内容 | 风险 | 验收（缺一不可） |
|---|---|---|---|

## 7. 反对意见 / 风险自陈

- 这个方案会让**出包变重**（多两步：签名、加密载荷），出包失败面变大 → 建议 `harden_apk.py` 自带 `--dry` 与「跳过要显式写理由」，但**门禁断言不许跳过**。
- **私钥丢失 = 全体玩家授权链断裂**（需 `key_epoch` 双钥并存过渡，方案里已预留）。
- **客户端不可信**是原理：只要攻击者愿意投入远超收益的成本（逆向整条链 + 每版跟新），理论上仍能破。本方案的目标是让"投入 > 收益"，而不是"不可能"。
- 现网存量（已发出去的 1.0.3 包）无法回补这些防御，只能靠新版本生效 + 服务端对旧 build 逐步收口。
