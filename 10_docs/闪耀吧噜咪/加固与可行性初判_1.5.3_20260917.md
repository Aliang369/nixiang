## 一、结论摘要

- **确认有加固，但不是传统“DEX 壳”。** Java/DEX 层可完整反编译；核心保护落在 Unity IL2CPP 元数据、IL2CPP 加载链和联网校验。
- **IL2CPP 元数据不是明文。** `global-metadata.dat` 首 4 字节为 `HTPX`，全文熵约 7.9063，未找到标准 `0xFAB11BAF` 头，也没有 `mscorlib`、`Assembly-CSharp` 等明文字符串。当前不能直接用 Il2CppDumper 产出 `dump.cs`。
- **实际保护/风控组件：**
  - 网易 HTProtect：`libNetHTProtect.so`、`libhtpcrash*`、`HTPX` 元数据；`libunity.so` 中存在一组 `HTP*` 动态符号解析失败提示，证明它介入 IL2CPP 加载链。
  - TapTap Themis Lite：`libthemis.so`，通过 Manifest 中的 `ThemisProvider` 自动初始化。
  - Bilibili GSC SDK：请求签名、原生 `custom_rules` 规则、云存档。
  - Bilibili 加固存储/签名：`libblkv.so`、`libbili.so`、`libtapsdkcore.so` 等。
- **未发现腾讯 ACE/TSS 主组件。** 无 `libtersafe2.so`、`libtprt.so`；Java 侧虽有 `Class.forName("com.gsc.lib.ace.AceWrapper")` 的可选入口，但 APK 内不存在该类，属于未打包/未启用的可选通路。
- **玩法不是纯单机。** 资产类名与协议模块包含 `BattleServerInvoker`、`ClientGatewayProtocol`、`ProtoBattle`、`ProtoMessageBattle`、`UnityWebSocket`、`Google.Protobuf`；`level0` 内写有正式服域名列表：
  `https://l1-prod-cn-ob-vs-lumigo.bilibiligame.net;https://l3-prod-cn-ob-vs-lumigo.bilibiligame.net;https://lumigo-cn-prod-vs.bilibiligame.net`
- **四项功能的静态可行性：**
  - 攻击倍率：有客户端战斗类候选，可做性中高；但 PvP/GVG/排行结算存在服务端复核风险。
  - 上帝模式：有客户端战斗实体/结算链候选，可做性中；服务端结算仍可能拒绝或回滚。
  - 无限技能：客户端技能状态类明确，通常是四者中相对最容易的一项。
  - 百分百捕捉：已有 `AdventureCatchRate`，同时存在 `AdventureEventCatchLumiServer2` / `ServerModel`，捕捉结果明显走服务端模型；**客户端强改不可靠，风险最高**。
- **防封号不能由客户端保证。** 可以降低客户端特征和异常量级，但不能消除服务端判定。HTProtect 的 token/角色信息、Themis 设备指纹、GSC 请求签名和云存档共同构成风控面。
- **屏蔽上报与阻止存档上传“技术上可研究”，但不等于安全。** HTProtect/Themis 的 native 上报链不适合用简单 Java Hook 粗暴拦截；单纯阻止云存档会造成服务端与客户端状态不一致。服务端写操作和绕过服务端裁决不在本轮范围。

## 三、保护与校验面

### 1. IL2CPP/HTP 加载链

- `assets/bin/Data/Managed/Metadata/global-metadata.dat`：
  - 文件大小：11,635,420 B
  - 首 4 字节：`48 54 50 58`（`HTPX`）
  - 熵：全文件约 7.9063；标准 metadata 头、常见明文字符串均未出现。
- `libNetHTProtect.so`：
  - 导出 `JNI_OnLoad`。
  - 包含 `com/netease/htprotect/factory/JNIFactory` 和初始化签名
    `(Context, String, HTPCallback, HTProtectConfig)V`。
  - 引用 `libil2cpp.so`、`libart.so`、`ptrace`。
- `libunity.so`：
  - 包含多条 `il2cpp: function HTP... not found` 字符串，说明 HTP 组件参与 IL2CPP 符号/加载链初始化。
- 影响：静态 Il2CppDumper 不能直接得到 C# 类型与方法；要拿到精确挂点，需要运行态明文 metadata 或等价运行时枚举。

### 2. TapTap Themis Lite

- `libthemis.so` 导出：
  - `Java_com_taptap_sdk_themis_lite_ThemisLite_Z8f7JxQk`
  - `Java_com_taptap_sdk_themis_lite_ThemisLite_vQe8bYsT`
  - `Java_com_taptap_sdk_themis_lite_ThemisLite_xJ3kLm9Q`
  - `Java_com_taptap_sdk_themis_lite_ThemisLite_zXq3tVwP`
- Manifest 注册：
  - provider `com.taptap.sdk.themis.lite.ThemisProvider`
  - authority `com.bilibili.lumi.cn.themisLite`
- `ThemisProvider.onCreate()` 调用 `ThemisLite.Register(context)`，初始化时机早于普通 Activity。
- 日志缓冲确认安装/启动期出现 Themis provider 注册记录；设备上 `com.taptap` 自身也加载了 Themis，但本包同样内置并注册了自己的 Themis 组件。

### 3. 签名和请求签名

- TapTap：
  - `TapSignKit.getSign()` 读取 `PackageManager.GET_SIGNATURES`。
  - `GatekeeperRepository` 会携带 APK 签名请求 gatekeeper。
  - 改签后可能需要官方证书回灌，否则登录初始化/风控可能异常。
- GSC：
  - `ParamsSignInterceptors` 为 GET/POST 统一添加 `timestamp`、`domain`、`fingerprint`、`sign`。
  - 登录路径额外使用 RSA 签名。
  - `CustomRules` 通过 native `libcustom_rules.so` 生成 token/header。
  - 这意味着单纯 Hook 请求体而不处理签名头，容易产生 4xx/风控事件。

### 4. 云存档

- `ArchiveManager` 实现上传、下载、列表、删除、注册。
- 关键请求：
  - 上传：`/storage/mult/upload`
  - 下载：`/storage/downloadStorage`
  - 列表：`/storage/mult/list`
  - 删除：`/storage/deleteStorage`
- 上传参数包含：
  `gameId`、`userId`、`accessToken`、`channelId`、`archiveSlot`、`archiveMd5`、`gameVersion`、ZIP 文件。
- 云存档 Host 常量：`https://api.biligame.net/cloud-storage`
- 存档操作会额外上报 `gs-cloud-storage` 事件（start/success/failure/error/finish）。
- 结论：这是标准的服务端存档接口，不是“客户端偷偷上传文件”。阻止上传会影响跨端/恢复能力，并可能产生异常行为画像。

### 5. 游戏侧候选校验/上报类

从 `globalgamemanagers.assets.split0` 读取到的序列化类名包括：

- `CheatChecker`

- `LogReporter`
- `SDKLogPlatformReporter`

## 四、四项功能可行性

| 功能 | 静态候选 | 可行性判断 | 主要风险 |
|---|---|---|---|
| 攻击倍率 | `BattleClientExecer`、`BattleDamageNumManager`、`ProtoMessageBattle` | 中高 | 伤害/结算可能由服务端重算；PvP、GVG、排行风险高 |
| 上帝模式 | `BattleEntityManager`、`BattleHero`、`BattleServerInvoker` | 中 | 只能改客户端表现不能改服务端判定；异常血量/承伤统计 |
| 无限技能 | `BattlePlayerSkillState`、`SkillValueChange`、`ActiveSkill` | 中高 | 技能次数/能量可能被服务端对账；频繁瞬间释放会形成异常行为 |
| 百分百捕捉 | `AdventureCatchRate`、`AdventureEventCatchLumiServer2(Model)`、`AdventureCatchGroupRate` | 低到中，客户端单改不可靠 | 捕捉结果走服务端模型，存在结果回滚/拒绝/风控 |

### 判定口径

- “可实现”仅表示存在客户端挂点候选，**不等于安全、稳定，也不等于服务端接受**。
- 四项功能都必须在拿到运行态 metadata 后确定具体类、方法、字段、调用时机，再做单功能、低量级、可回滚验证。
- 在没有动态证据前，不应把任何一项标为“已经可实现”或“可交付”。

## 五、防封号、屏蔽上报与反检测

### 1. 防封号

- 客户端无法保证防封。HTProtect/Themis/GSC 只增加了检测面，最终裁决仍可能在服务端。
- 可控风险因素：
  - 不注入/不 ptrace 受保护 native 库。
  - 不在对局中频繁切开关。
  - 不进入 PvP、GVG、排行、结算奖励等强校验场景。
  - 低倍率、短时、单功能试验。
- 不可控因素：
  - 服务端战斗回放、伤害统计、技能释放时序、捕捉概率分布。
  - 设备/环境画像与“异常后立刻断网/关服”的行为特征。

### 2. 屏蔽上报

- Java 侧可以找到 Bugly、Sentry、云存档 Track、TapTap 统计等调用点，理论上可逐项停用。
- HTProtect/Themis 的 native 上报不能当作普通 Java 日志处理；粗暴 Hook 其初始化或 native 函数会同时破坏 IL2CPP 加载链和完整性假设。
- “全局屏蔽上报”会：
  - 让云存档/登录/崩溃恢复出现非正常状态；
  - 让服务端缺失正常心跳/统计；
  - 增加而不是降低风控关注度。
- 结论：可做局部、白名单式研究，但不建议把“屏蔽所有上报”当作反封手段。

### 3. 存档上传

- 可以定位到客户端上传入口和请求构造点，但存档是服务端资产。
- 阻止上传只解决“本轮存档不落到云”，不能阻止战斗结果、角色数据、风控事件继续经游戏协议上报。
- 恢复旧存档、伪造 MD5、重放 accessToken 都属于服务端写操作/绕过服务端裁决，需独立授权并单独评估，不属于本轮静态实现。

### 4. 反检测

- 当前设备已有 KernelSU root；从现有日志看，原版启动/安装过程未显示直接拒绝。
- 但 HTProtect/Themis 的检测不只依赖 `su` 文件：还会组合设备信息、进程/内存特征、签名、调用链和运行时行为。
- Frida、ptrace、Xposed、Zygisk、inline Hook 受保护 so 都是高风险路线。若后续仅做分析，应优先使用只读运行时枚举/内存导出，不注入 hook。
- 结论：反检测“可降低已知客户端特征”，但不能宣称“防检测/防封”。

## 九、加固与校验面能否通过（分层判断）

| 检查面 | 判断 | 依据与边界 |
|---|---|---|
| DEX / Java 层 | **有机会通过** | 没有传统 DEX 壳；但必须保留官方 DEX、resources.arsc、既有 so 字节，新增文件也要重新做安装/启动 A/B |
| APK 重签 / TapTap 签名 | **有机会通过** | `TapSignKit` 走 PM 签名查询，可研究 SignSpoof / 官方证书回灌；未实测前只能标候选 |
| HTProtect / HTPX 加载链 | **不确定，硬 patch 风险高** | `libNetHTProtect.so` 含 `ptrace`、`/proc/self/maps`、SHA/CRC、证书、可疑安装包信息等能力；`libunity` 依赖 HTP 符号链。patch 校验结论可能触发自旋/毒丸或多重自校验 |
| IL2CPP metadata 保护 | **静态过不了，运行态可绕层** | 当前 metadata 不能直接 dump；正路是运行时在解密后取明文，不是逐点 patch HTP 校验 |
| GSC 请求签名 | **可随原链路通过，不等于业务通过** | 不改网络层、让原签名代码继续签名时，传输层有机会过；服务端业务校验仍独立存在 |
| Themis Lite | **通常不挡启动，但会留下风控画像** | Provider 自动初始化，主要采集设备指纹；root 原版当前可启动不代表改包/Frida 不会被记录 |
| 战斗结算 / 捕捉 / 排行 | **不能仅靠客户端保证通过** | `BattleServerInvoker`、`ProtoMessageBattle`、`AdventureCatchLumiServer2` 表明结果可能服务端权威 |
| 屏蔽原生上报 / 全面反检测 | **不建议视为可行交付项** | native 上报链不适合粗暴 Hook；屏蔽后仍无法消除服务端风控，且可能增加异常特征 |

### 最可能的可行路线

1. **只新增，不替换**：保留 `libil2cpp.so`、`libunity.so`、`libNetHTProtect.so`、`libthemis.so`、官方 DEX、resources.arsc 与 metadata 原始字节。
2. **绕层打功能**：功能不碰 HTP/校验函数，只在业务层落点做运行时读写或少量跳转；原请求签名和登录链继续保持工作。
3. **先做 A/B 存活**：先测零改动重签、只加 asset、只加 dex、只加 so、只 hook 单点，区分启动校验、签名校验和业务崩溃。
4. **服务端验收单列**：客户端能跑、登录能进、功能能触发、结算能接受、账号无异常是五个不同等级，不能合并成“过了”。

### 直接结论

- **“改包能启动并登录”**：有希望，但需实测，不能提前保证。
- **“强行 patch HTProtect/HTPX 后稳定运行”**：不建议，风险高，失败形态可能是黑屏、静默退出或延迟自杀。
- **“四项功能都生效且服务端接受”**：远未证明，尤其是百分百捕捉。
- **“全面防封、反检测”**：客户端无法保证，不应按可实现项立项。
