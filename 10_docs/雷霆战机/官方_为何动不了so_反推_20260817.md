# 官方 1.25.31：为何 ADD/改 so 必死（反推，2026-08-17）

> 不再围着 libsdk 四点转。从 **A0/Bn/disk4c 现象** 反推「谁在拦 so」。

---

## 1. 已知现象（已有真机，不重复猜）

| 实验 | 改动 | 结果 |
|------|------|------|
| resign-only | 不改 so | 活 |
| A0 | **ADD** 新 `lib/arm64-v8a/*.so`（不 load） | ~15s SIGBUS |
| Bn | **REPLACE** `libn.so` 翻 1 字节 | ~15s SIGBUS |
| B0d | 同内容 DEFLATE 重打 | 活 |
| disk4c | 改 `tersafe` 1 NOP + 同步 MD5/段摘要 | 2–7s 死 |

含义：查的是 **so 解压后内容 / 其 CRC 类指纹**，不是 zip 包装方式；**多一个 lib 文件名也不行**。

---

## 2. 新发现（本轮静态，可复核）

`libtprt.so` **`.data` 内嵌原生库库存表**：

| 项 | 值 |
|----|-----|
| 文件偏移 | **`0x19bc10`** 起 |
| 步长 | **16 字节** / 条 |
| 字段 | `u32 size` \| `u32 zip_crc32` \| `u64 tail`（算法未解） |
| 条数 | **25** |
| 覆盖 | 官方 arm64 的 **27** 个 so 里除 **`libcocos.so` / `libtprt.so`** 外全部 |

同区还有版本串 **`1.25.31`** @ `0x19bba8`。

示例（与 APK `ZipEntry` 一致）：

| so | size | CRC（APK） | 表内偏移 |
|----|------|------------|----------|
| `libn.so` | 6160 | `dec9e2e1` | `0x19bc80` |
| `libtersafe2.so` | 5979312 | `9192ff85` | `0x19bd10` |
| `libBugly_Native.so` | … | `6cee49e7` | `0x19bd60` |

### 2.1 直接打脸 disk4/disk4b/disk4c

disk4c 改完后：

| | |
|--|--|
| 新 `libtersafe2.so` zip CRC | **`32189801`** |
| 表内仍写的期望 CRC | **`9192ff85`**（未改） |
| 此前只同步的 | `0x16956c` MD5 等 |

→ **MD5 槽改了、库存 CRC 没改 = 必杀。**  
这就是「动 so 死」的硬机制之一，不是四点语义问题。

### 2.2 和「加不了 so」的关系

- **改已有 so**：库存表 CRC（+ 可能 tail）对不上 → 杀（Bn / disk4c）。  
- **ADD 新 so**：库存表仍只有 25 条；A0 证明还有 **「多文件」面**（目录枚举 / 中央目录 / AnoStamp / 未入库名单等）——⚠ 具体调度函数尚未 xref 钉死，但现象闭合。  
- 斌哥 `libsdk`/`libSDKloading` 的 CRC **不在** 斌哥 tprt 同款库存里 → 斌哥不是靠「登记新 so」，而是 **旧 ACE + 运行时刀检查**（另线）。

### 2.3 `AnoStamp`（Manifest）

```
AnoStamp = SKuFlKioqKmoqKipp1lE+adZRPg=
→ 20 bytes: 48ab8594 a8a8a8a9 a8a8a8a9 a75944f9 a75944f8
```

与库存表 MD5 无直接相等；⚠ 待验证是否包级水印，本轮不当唯一解。

## 3. 可验证下一步（单变量）

1. **disk5-inv**：只翻 `libn.so` 1 字节（Bn 死法）+ **只改** 表内 `libn` 的 `size/crc`（tail 先原样）→ 若仍死，再动 tail / 找校验函数。  
2. **disk5-ts**：tersafe 1 NOP + 同步 **库存 CRC** + 原 MD5/段摘要 → 对照 disk4c。  
3. **ADD 面**：在钉死「枚举 lib 目录」xref 前，不盲目往表里塞第 26 行。

验收门：≥60s + cocos；失败停，不叠刀。

## 4. disk5 真机（Bn + 同步库存 CRC，2026-08-17 23:33）

包：`雷霆战机_1.25.31_disk5-invCRC-libn-releaseSigned.apk`  
改动：`libn` 末字节翻 1 + 表内 `0x19bc84` CRC 与 zip CRC 对齐（`a9ced277`）；**tail 未改**；顺带改了 `libtprt`（写表）。

| 项 | |
|----|--|
| 结论 | **FAIL** |
| 寿命 | ~5–7s 轮转（sig 7/11） |
| cocos | 未 load |

含义：

1. **只改库存 CRC 不够** —— 至少还要过 `tail(8)`，和/或  
2. 改 `tprt` 写表触发了 **tprt 自检**（`.data` 段摘要等），和/或  
3. 运行时不算 zip CRC，而是算 **内容另一套指纹**（与 tail 同源）。

下一刀（仍单变量，不叠盲刀）：**解开 tail 算法**，或 xref 读 `0x19bc10` 表的比较函数再决定是改期望值还是废比较。

### 4.1 disk5-pad（进行中）

单变量：只改 `libtprt` `.data` 填充区 `0x19bb40` 四字节 `00000000→11223344`，**不动**任何 so 业务内容、不动库存 CRC。

| 目的 | 区分「库存表逻辑」vs「tprt `.data` 任一改动即死（段完整性）」 |
| 包 | `雷霆战机_1.25.31_disk5-tprtDataPad-releaseSigned.apk` |

- 若 **活**：可继续在 `.data` 里改库存表 / 做毒化 CRC 对照。  
- 若 **死**：改库存表本身就会触发 tprt 自检；零 Root 改表路线要先过 **tprt 段完整性**（或废比较），不能只同步 CRC。

### 4.2 disk5-pad 真机（2026-08-17 23:41）

| 项 | |
|----|--|
| 结论 | **FAIL** |
| 寿命 | ~2–6s 轮转（sig 7/11） |
| cocos | 未 load |

**关键结论：`libtprt.so` 的 `.data` 任一字节改动都会死。**

因此：

1. disk5「改库存 CRC」失败，**首先**就死在「写表必须改 tprt `.data`」，不必先怪 tail。  
2. 零 Root **不能**靠「改期望 CRC/MD5 槽」闭环——改槽本身要动 tprt/tersafe，而两者都有自检。  
3. 可行方向转向：  
   - **废比较 / 废自杀点**（等长 patch 指令，且还要过「改 `.text`」的自检——同样难，除非 patch 落在未校验区或运行时写）；或  
   - **运行时晚改内存**（Root 一次 / 已有晚载路径）；或  
   - 找到 **不被校验的载具**（历史：assets 可 ADD，lib/dex 不可）。

---

## 5. 一句话

**动不了 / 加不了 so，核心嫌疑是 `libtprt@0x19bc10` 的 size+CRC(+tail) 库存表（+ ADD 面），不是 libsdk 四点。**  
disk4 系列败在没改这张表；**disk5 证明只改 CRC 仍不够**，必须把 **tail / 读表比较点** 钉死。
