## 三、静态机器解码（2026-09-05 新解，坐标+expected 字节）

### 3.1 通用 syscall stub 农场（tersafe2 0x3f8360–0x3f9200）

- 33 个等长 stub（0x70 步距），形态 = `mov x8,x0; mov x0,x1 …; svc #0; cmn x0,#1,lsl#12; cneg; b.hi <err@0x3b9f14>; ret`，带垃圾指令混淆；
- 即 **`syscall(nr, …)` 通用实现**：任何系统调用（含 kill/tgkill/rt_sigaction）可经它发出，与 8 月抓到的运行时匿名 svc 跳板同构（匿名副本=此处模板的运行时拷贝，工厂调用点 `0x3b950c` nr=222 mmap）；
- 8 月过滤 tramp 的 kill/ptrace 无效的原因：**编号可变量传入，按站点过滤天然失效**。

### 3.2 自杀机器簇1（编排已完整解码，反汇编见 `cluster1_disasm.txt`）

```
0x124940 编排器（无直接调用方，函数指针表 0x38c10/0x570258 注册）:
  1. snprintf("/proc/%d/task") → opendir/readdir/atoi 枚举目标进程全部 TID（≤255）
  2. bl 0x124a5c: signal(SIGILL/ABRT/BUS/FPE/SEGV/PIPE/SIGUSR1, SIG_DFL)×7 + SIGCHLD/SIGHUP 处置
  3. bl 0x124b14: 逐 TID → worker-A 0x124e50（PTRACE_ATTACH/GETREGSET/SETREGSET 0x4200 族, ptrace@plt 0xa9520）
  4. 兜底 mov w0,#0x7f; bl _exit@plt 0xa8e20   ← _exit(127)
```

- 与运行时观测完全对齐：SIG_DFL 置位 → 自 raise sig=11 无 handler → 组杀；
- 8 月「PC 落 libc/libart、LR/x8 污染」= worker ptrace SETREGSET 改寄存器的指纹；
- kill@plt（0xa8d10）仅 2 处调用（SIGSTOP/SIGCONT @0x125384/0x1253b8），非致命投递点（8 月已证，本轮复认）。

### 3.3 中和点表（CaveBoot stage-0 用，全部带版本守卫）

| 点 | 地址 | expected 前16字节 | 建议动作 | 理由 |
|---|---|---|---|---|
| N1 | tersafe2 `0x124940` | `f403002a e0330091 …` | `mov x0,#0; ret`（`000000d2 c0035fd6`） | 拆编排器（枚举→重置→ptrace→exit 链头） |
| N2 | tersafe2 `0x124a5c` | `ff0301d1 f31300f9 …` | `ret` | 拆 SIG_DFL 重置（即使有残余 kill 也回到可 handler 面貌；对健康业务无影响——它只在自杀链上被调） |
| N3 | tersafe2 `0x124e50` / `0x125058` / `0x1251a8` | 见 §3.3 顶部 hex | `mov x0,#0; ret` | 拆 ptrace 投毒 worker |
| N4 | tersafe2 `0x1252a0`(C2-1) + 簇2 各入口 | 见 hex | `ret` | 簇2 备用旁路（8 月 ace8/9 曾整簇 early-ret，磁盘必死；**内存 patch 无磁盘完整性问题**） |
| N5 | tersafe2 `_exit@plt 0xa8e20` / `exit@plt 0xa9270` | 见 hex | `mov w0,#0; ret` | 拆兜底 exit（kill@plt 0xa8d10 保留——它只承载 STOP/CONT 正常节流） |
| N6 | tprt farm `0x3f8360-0x3f9200` 33 个 stub | 逐 stub | **暂不动**（正常 syscall 依赖它） | 若 N1–N5 后仍死，再按 nr 过滤组杀路径 |

- **注入时机**：cave 在 libcocos 加载时执行（实测 load +0.03s），此时 tersafe2/tprt 已映射；距行刑 ~9.5s，窗口充裕；
- **风险控制**：每点 patch 前 memcmp expected 16 字节，不符即跳过并打日志（版本守卫，防误伤；超维进化模板）；
- **为何这次可能成功而 8 月 disk4/H5h 失败**：不打磁盘（无完整性问题）、不打 PLT 之外的调度 BLR（那些是 Java 触发口）、直接拆**自杀编排器本体**——正是本次运行时观测到的死亡执行体。

## 四、未竟与下一步

> **2026-09-05 深夜追加：E5/E8 迭代与死亡模型修正**

| 实验 | 改动 | 结果 | 结论 |
|---|---|---|---|
| E5 | 内存 patch N1（簇1编排器 0x124940→ret，守卫过） | 仍 +10~15s 死 | 簇1 不是（唯一）执行体 |
| E5-F | raw_syscalls 全系统过滤 93/94/129/130/131（+138/240/424 复核=0） | **全程 0 条 kill 族 syscall**；死亡=全线程 sig=9 deliver（无 generate、无 tombstone） | 杀器不经任何 kill 类 syscall；sig=9 风暴=内核组拆除合成信号（某线程 default-fatal 死亡后 zap 兄弟线程的指纹） |
| E8 | 内存中和直连 read 包装器（0x315710→永远返回 0 字节，守卫过） | 仍 +5~10s 死 | 期望摘要为**预存常量**（非运行时同源计算）；空读=失配=死 |

**修正后的死亡模型**：checker 线程在 verdict 锁存后 ~10s，**故意触发自身内存故障**（run-2 的 sig=11 code=1=SEGV_MAPERR 为真实缺页，处置已被重置 SIG_DFL）→ 线程死亡 → 内核组拆除（其余线程合成 sig=9 deliver）。杀的原语 =「触发缺页」，**不存在可过滤/可中和的通用收口**（signal@plt 全部 8 个调用方都在簇1，但 N1 中和无效说明杀机不依赖簇1）。

**checker 引擎结构（静态）**：文件读取助手 0x3141e8（open+read+close 直连 svc）← 7 个调用方；其中孪生哈希驱动 0x36cdac/0x36f1d8（各 ~0x2400B，8 种哈希原语×7）；主引擎 **0x35aa60**（0x11738B、17870 指令、哈希原语×102、24 回边），入口经 **vtable 间接派发**（上游 bl 链断于 0x345f64）；JNI 调度簇 0x37a4c4-0x37d1d8（8月 H5h patch 过的三 BLR 在此，patch 后仍死 → 判定通道 ≥4 条）。`libcocos` 字符串在两 so 中均不存在 → checker 经 /proc/self/maps 枚举模块再逐个哈希（与 1Hz 读解压文件吻合）。

**对交付路线的含义**：
1. 任何 lib/ 磁盘篡改（含 CaveBoot 方案必须的 libcocos .text patch）→ init 期判定锁存（早于 cocos load+0.4s，早读点在 load+0.024s）→ 必死，除非中和整个多通道判定引擎（obfuscated+vtable，需 IDA 函数级恢复，1–3 天量级且不保证成）。
2. CaveBoot 时序上比早读点晚 ~24ms（DT_INIT vs load 后读），竞态窗口极窄。
3. **已验证可活的交付面**：纯 assets 注入（C1/C2 存活）+ Root 一次落 so（`abhw`/晚载，8-16 已验收出菜单）。8 月的「注入被杀」主因是磁盘篡改线与 sticky 污染，而非 assets 注入本身。
