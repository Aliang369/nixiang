## 1. 关于 apktool（答用户）

**apktool 不是签名工具。**

| 工具 | 实际用途 |
|------|----------|
| **apktool** | 解包 / 改 smali·资源·Manifest / **整包重建**（`apktool b`） |
| **uber-apk-signer / apksigner / MT 签名** | 只做 **签名 + 对齐** |

本机正式链路一直是：改包 → **uber** 重签 → root `pm install`。  
以后签名换成 MT 可以，**解决不了今晚的卡启动**——杀手是 **apktool 全量重建（以及若干 zip 改动形态）触发 ACE**，不是「谁来签名」。

MT 适合：静态分析、试改、手机侧重打包实验。正式星光交付仍建议脚本化 zip 注入 + 电脑签名（或 MT 只签最后一步）。

---

## 2. 卡启动真正原因（本轮）

用户看到的「黑屏 + 中间游戏 icon」= **系统启动窗口未撤**，进程在隐私页附近被 ACE 弄死或卡死。

两条已复现的死法：

1. **nop `AceApplication.attachBaseContextShell`** → 能活到 `AppActivity`，但卡在 `System.loadLibrary("cocos")` → `libtprt` `sem_wait`（假活黑屏）。  
2. **保留 ACE initialize + 现行 `inject_ltzj_1.25.31.sh`（apktool 重建）** → 隐私页约十几秒 **SIGBUS/SIGSEGV** 循环。

干净机对照（§14）：**仅 uber 重签原包可玩**。因此不是「重签必杀」，而是 **改包方式** 触发 ACE。

## 3. 存活矩阵（干净机、无 Frida）

| 探针 | 做法 | 结果 |
|------|------|------|
| resign-only | 原 APK + uber | **SURVIVES** → AppActivity / cocos |
| apktool roundtrip | 无任何业务改动，仅 `d→b` + uber | **SIGBUS ~3s** |
| 星光 inject（apktool） | keep ACE / 有无 SignSpoof | **SIGBUS** 隐私页 |
| Z1 zip marker | `assets/` 加小文件 | **SURVIVES** |
| Z2 zip so→`lib/arm64-v8a/` | 新增 `libstarry`（± libc++） | **SIGBUS ~9s** |
| Z3 zip so→`assets/starry_native/` | so 不进 `lib/` | **SURVIVES** → AppActivity |
| Z4 + `classes6.dex` | 新增星光 dex | **SIGBUS/SEGV 循环** |
| Z5 原样重写已有 dex | 同字节 `zip -u classes*.dex` | **SURVIVES** → AppActivity |
| Z6 改已有 dex 内容 | privacy skip + assets so | **SIGBUS/SEGV 循环** |

摘要文件：

- `08_output/雷霆战机/ltzj_zip_probe_z3z4_summary.txt`
- 日志/包：`ltzj_zip_probe_*` · `雷霆战机_1.25.31_zipProbe-*.apk`

**结论（给明天）：**

- 禁止对雷霆官方包做 **apktool 全量重建** 出正式包。  
- **不要**往 `lib/arm64-v8a/` 塞新 so。  
- **不要**新增 `classesN.dex`。  
- **不要**改已有 dex 字节（ACE 像在校验 dex 内容；同字节重写可活，改内容即杀）。  
- **可以**：原包 + uber；zip 改 `assets/`（含把 so 放 `assets/starry_native/`）。

|------|------|
| APK 内改任意 `lib/*.so` / 新 so / 改 dex / apktool | **杀** |
