## 2. 纯 APK「自动出菜单」在机制上缺什么

星光要的是：某次 **已由 Java `loadLibrary` 触发的 `JNI_OnLoad`** 里拿到 `JavaVM*`，再跑自己的 DexInstaller / MenuService。

本包**已经具备**多条会走 `JNI_OnLoad` 的正规加载口（上表 1–5）。  
缺的不是「再发明一条 JS System.load」，而是：

> **在不破坏 Ace/引擎的前提下，把星光挂进「已经被 loadLibrary 的那一次 JNI_OnLoad」里。**

`assets/` 里的 so **不会**被系统自动 `JNI_OnLoad`；必须进入 `lib/` 加载路径，或被某个已加载 so 显式 `dlopen` + 手调 `JNI_OnLoad`。

补充：仅给某 so 加 `DT_NEEDED → libstarry` **不够**——依赖库被 linker 拉起时，**不会**自动调 `JNI_OnLoad`；仍须在宿主 `JNI_OnLoad` / `.init_array` 里手调。

## 3. 候选挂载面（按「改动面」排序，待实验，不断言死活）

### A. Manifest `lib_name` 改指向「薄加载器」（优先假说）

- **改动**：`AndroidManifest` meta `android.app.lib_name`：`cocos` → 例如 `cocos_ldr`  
- **新增**：`lib/arm64-v8a/libcocos_ldr.so`  
- **行为**（`JNI_OnLoad`）：
  1. `dlopen("libcocos.so")` → 调其 `JNI_OnLoad`（保住 GameActivity/Cocos JNI）
  2. `dlopen("libstarry_magic.so")` → 调其 `JNI_OnLoad`
- **不改**任何 classes*.dex  
- **时机**：与现网 `libcocos` 同点（AppActivity/`CocosActivity.onCreate`），隐私同意之后  

风险未知（待测）：`AnoStamp` / ACE 是否校验 lib 目录文件集合、是否校验 `lib_name` 字符串、是否校验 cocos 必须被「直接」loadLibrary。

### B. 替换「非 Ace 核心」且已会 load 的 so 的 `JNI_OnLoad` 入口

冷启已证实会 load 的非 tersafe 候选：

| so | 体量 | 备注 |
|----|------|------|
| `libBugly_Native.so` | ~220KB | AppActivity 后几乎立刻；导出符号多，需 `.orig` 转发或只劫持 `JNI_OnLoad` 再 `dlopen` 原体制 |
| `libtapsdkcore.so` | ~6MB | 同批；体积大、渠道相关，风险面更大 |

薄包装思路：`libBugly_Native.so` → shim；原文件改名 `libBugly_Native.so.orig` 同目录；shim `JNI_OnLoad` 里 `dlopen(orig)` + `dlopen(starry)` + 两个 `JNI_OnLoad`。

### C. 极小 so（`libn.so` / `libpangleflipped.so`）

导出极少，适合做 shim；但 **本冷启 maps 前 12s 未见映射**——若玩法路径不 load，则挂了也不会自启。需先用长窗口 `nativeloader` 确认触发条件，再谈替换。

### D. 不优先

- 动 `tersafe2` / `tprt`：与 `AceApplication.initialize` 同命运，分析未完成前不做  
- 只把星光丢进 `assets/`：无 Java/`JNI_OnLoad` 调用方则永不会起

### 6.1 现网对 `lib/` 的约束（当次证据）

1. **禁止新增** `lib/arm64-v8a` 文件名（A0）。假说 A（`lib_name` 薄加载器）在 A0 已否。  
2. **禁止改** 已有 so 的**解压后字节**（B1 / Bn）；连未加载的 `libn` 也查。  
3. **允许** 同内容 DEFLATE 重打包该条目（B0d）；完整性看的是 so 内容，不是 zip store/deflate 包装差异（在同 CRC 前提下）。  
4. 实验间若混入 A0/B1 死法，resign-only 也会假死 → **每轮前 cleanup**。

### 6.2 纯 APK 自启：下一刀方向（lib 内容锁死后）

`lib/*.so` 内容与清单文件名均不可动时，自启只能落在：

- **仅 Manifest / assets**（zip-assets-menu 曾可开机）上找「已有 PathCL `loadLibrary` 之外」的入口；或  
- 证明某条 **不改 lib、不改 dex** 的系统/引擎加载路径（待搜）；或  
- **等长之外**已证伪；改 dex 需单独新开最小实验（不沿用旧标签，须 cleanup 后重测）。

假说 B（改 Bugly 内容做 shim）**已否**。

### 6.5 `SDKWrapper` / `service.json`（本包静态）

- `AppActivity.onCreate` → `SDKWrapper.shared().init(this)` → 读 **`assets/service.json`** → `serviceClasses[]` → `Class.forName().newInstance()` 当 `SDKInterface`。
- **官方 APK 内无 `assets/service.json`**（缺文件时 `getJson` 空串，异常吞掉，等价空插件列表）。
- 这是理想的「只 ADD assets + 已有 PathCL 类」挂载面；但插件类必须已在 PathCL。  
  → 自写加载器 ⇒ 要 `classes6` ⇒ **D0 已否**。  
  → 本包 **无** 现成 `SDKInterface` 实现可挂星光。

附带：`SafelyLibraryLoader.loadLibrary(ctx,name)` 会 `System.loadLibrary` 失败后再从 APK **`lib/$ABI/`** 解压到 `files/libso` 再 `System.load`——仍依赖 **lib 目录条目**（A0/B 已否），且 JSB 侧难以传入 `Context`。

- PathCL 上 `System.load(String)` 调用方：`SafelyLibraryLoader`（要 Context）、`NativeCrashHandler.tryLoadSo`（**实例**）、`abqd.dl`（要 Frankie）、lz4 `Native.load()`（固定库名）。

- 无参/`String` 且内部 `getFilesDir+System.load` 的公开静态方法：仅 `abqd.dl`（要 Frankie）与 lz4 `Native.load`。

### 6.10 三扫 + `abqf.A`/`abqf.g` 实锤（2026-08-16 22:30+）

#### System.load 调用方穷尽（extract/classes*.dex）

| 类.方法 | 签名 | JSB 可直调？ |
|---------|------|--------------|
| `SafelyLibraryLoader.loadLibrary` | `(Context,String)Z` | 否（要 Context） |
| `NativeCrashHandler.tryLoadSo` | 实例 `(String,z)Z` | 否 |
| `abqd.dl` | `()Z` | 要 Frankie；且只加载固定 emulator so |
| `com.tds/tapadn.util.Native.load` | `()V` | 固定 lz4 |
| `Marc.b` | `(Flat)I` | 要 Flat 对象 |
| **`abqf.g`** | **`(String,z)Z`** | **是** |

另：`abqf.A(File)` 仅被 `abqf.g` 调用；`abqg.a(CL,File)` 仅被 `A` 调用。

- **`file2 = dir + "/" + str`** → 入参必须是 **`libstarry_magic.so`**，不是 `starry_magic`

## 7. 问题重框 · 非 JSB 展开（2026-08-16 23:35，重启后）

### 7.1 真正要解的问题（不是「让 JSB 调通 abqf.g」）

在 **ACE 生存矩阵** 下，把 `libstarry_magic` 送进 **PathCL 的 `System.load` / `loadLibrary`**，从而 `JNI_OnLoad` → DexInstaller → MenuService。

| 已证实可活 | 已证实必杀 |
|---|---|
| resign-only；**ADD** 新 assets；Manifest **ADD** MenuService | **ADD** `lib/*.so` 文件名；**REPLACE** so 内容；**ADD/REPLACE** `classes*.dex`；**REPLACE** Cocos `manifest.json` 已登记资源（`main.js` / `realMain.js` / …） |
| 同内容 so 仅改 zip 压缩（B0d） | **REPLACE** 未进 Cocos manifest 的 `gbsdk.plugin.*.apk`（E0，ACE 另册） |

鸡生蛋：

```text
菜单类在 assets/starry_dex → 要先挂 PathCL
挂 PathCL / abs-load 要先有 so 的 JNI 或已有 PathCL 跳板
跳板在游戏 dex 里改 = ACE 死
so 放进 lib/ = ACE 死
so 只在 assets = 没人自动 JNI_OnLoad
```

### 7.2 为何 JSB 线会把思路变窄

JSB 只能：`void` / 数值 / `String`。  
全包扫下来，**公共静态 + 能 PathCL abs-load/hook+loadLibrary** 的，实质只剩 `abqf.g(String,z)`，而它要 `Frankie.getApplication()`。

本包 `CloverApplication.onCreate`：

```java
if (CloverEnv.getInstance().isOSDK()) {
    GBCommonSDK.onCreate(this);  // → prepare → FrankieDelegate.init + loadLocalPatch
}
// Tap 渠道：整段不走 → mContext 永 null（进主界面亦然）
```

`CloverEnv` 读的是 **`assets/cloverEnv.js`（当文本配 channel，不是当 JS 执行）**。  
当前 `channel: "android-tap"` → 不是 OSDK → Frankie 冷启永不 init。  
所以「纯 JSB + abqf.g」在 **Tap 官方包** 上先天缺 Application，不是晚一点就有。

另：`System.load(abs)` 从 JSB 调会绑错 ClassLoader（历史 NPE/`expected occurred`）；要 PathCL 栈上的跳板。

### 7.3 非 JSB / 旁路候选（本轮静态）

| 候选 | 机制 | 现状 |
|---|---|---|
| A. 改已有 so 的 `JNI_OnLoad` / DT_NEEDED 挂星光 | 不经 JS | **REPLACE so → DEAD**（Bn/B1） |
| B. Manifest 换成自有 Application/Provider | 冷启 Java | 类必须在 PathCL → **ADD dex DEAD** |
| C. `AceApplication.handleLoad` 内存 dex | ACE 自用 | 仅 GP6/7 / attachBase 调用；JSB 无法传 `byte[]` |
| D. `SafelyLibraryLoader` / `abqd.dl` | Java abs-load | 要 Context/Frankie；且 dl 固定 emulator so 名 |
| E. 资产里 `libfrankie_sh_util_emulator.so` 掉包 | 被 dl 加载 | 要 Frankie；且 REPLACE assets 二进制大概率死 |
| F. 改 `cloverEnv.js` → `android-osdk` | **非 JSB**：让 Java 走 GBCommonSDK→Frankie.init | **未做单变量复验**；文件 **不在** Cocos `manifest.json`，但历史与 `main.js` 一并标过 DEAD；E0 证明「未进 Cocos manifest ≠ ACE 不管」 |
| G. 纯 APK 自种子 `files/hot-assets-*` | `main.js` 已支持 hot-assets | 首次只能跑 **APK 内已登记** `realMain.js`；要改它才 `require(boot)` → **DEAD**；无 Root 时安装后也写不进别的应用 `files/` |
| H. 渠道换包（官方 OSDK 包） | 产品层 | Frankie 可能自 init；仍要解决「谁调 abqf.g / 谁落 hotfix_so」 |
| I. Root 落 libdir + abhw（现行过渡） | 非零 Root | **已通**；重启后 pid@15s 稳定 |

启动链补强（本轮 jadx）：

- `AceApplication.<clinit>`：`tersafe2` / `tprt`
- `CloverApplication`：Tap **跳过** OSDK；OSDK 才会 `FrankieDelegate.init` + `loadLocalPatch`
- 全 dex「字符串像 assets + 同方法 `System.load`」：**仅 `abqd.dl`**
- 不存在 `getCurrApplication()` 与 `System.load*` 组在同一可 JSB 静态方法里

`assets/manifest.json`：约 33493 条；**未登记**含 `cloverEnv.js`、`gbsdk.plugin.*.apk`、`libfrankie_sh_util_emulator.so` 等（258 个）。未登记仍可能被 ACE/其它校验盯（E0）。

### 7.4 可替代方案排序（面向「零 Root 纯 APK」）

2. **产品换 OSDK/会 init Frankie 的官方渠道包** 再做 zipAssets + 可活 JS 入口（若有不改登记文件的热更下发）。

3. **维持 Root 一次种植**（libdir + abhw / 或设备端晚载脚本）——唯一已闭环交付。

4. **不要再试**：REPLACE dex（含 Frankie 微改）、ADD lib、改 `main.js`/`realMain.js`。
