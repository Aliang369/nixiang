# 雷霆战机零Root纯APK — 旧版官方包执行方案

> 日期：2026-08-17
> 基础：旧官方 1.20.13（版本号 12013，签名 CN=clover O=5agame，确认正版）
> 目标：零 Root、纯 APK 安装即用，星光菜单 + 玩法功能

---

## 背景

### 三包 ACE 对比

| 组件 | 旧官方 1.20.13 | 新官方 1.25.31 | 斌哥 999999 |
|------|---------------|---------------|-------------|
| libtersafe2.so MD5 | 0e9f1de1… | ba597b32… | 823fef52… |
| libtprt.so MD5 | 71790caa… (1692296B) | 3ae6724e… (1692296B) | 5f4e0734… (1682312B) |
| GCLOUD_VERSION | TP_7.6.015.26314 | TP_7.6.015.26314 | TP_7.6.015.26314 |
| libsdk.so | 无 | 无 | 有 (2.94MB) |
| libSDKloading.so | 无 | 无 | 有 (3.88MB) |

三个包的 ACE 组件各不相同。斌哥的 ACE 既不是旧官方也不是新官方，是自建/定制的。

### 旧官方 1.20.13 关键信息

| 项 | 值 |
|----|-----|
| 版本号 | 1.20.13 (versionCode 12013) |
| 包大小 | 635MB |
| 签名 | CN=clover, O=5agame（官方证书） |
| compileSdkVersion | 34 (Android 14) |
| Application | com.cocos.game.CloverApplication → com.ace.gshell.AceApplication |
| lib_name | cocos |
| dex | classes.dex~classes5.dex |
| libcocos.so | 28766192 bytes（新官方 29272344 bytes，差 500KB） |
| classes dex 大小 | 均不同于新官方（版本差异） |

### 核心假设

旧版 ACE（1.20.13）的检测机制可能比新版（1.25.31）更弱：
- 可能没有匿名 svc trampoline 扫 maps 机制
- 可能没有 Dobby hook 检测
- 校验范围可能更窄（不扫 lib 新增、不校验 dex 修改等）
- 大版本跨度（1.20→1.25 差了 5 个小版本），ACE 在这期间升级了多次

## 执行方案

### 阶段 0：旧官方包基线验证

**目的**：确认旧官方 1.20.13 在干净机上能正常跑

**步骤**：
1. 清理设备（`cleanup_device_re_residue.sh`）
2. 卸载当前雷霆战机（1.25.31 需先卸载，1.20.13 versionCode 不同不允许覆盖）
3. 安装旧官方 1.20.13 APK（uber 重签后直装）
4. 冷启进游戏，观察 ≥60s 存活
5. 记录冷启 nativeloader 日志，确认 so 加载顺序

**预期**：存活，可正常进游戏
**产物**：基线日志

---

### 阶段 1：旧包 ACE 检测面探测（最小外科实验）

**目的**：摸清旧 ACE 校验范围，逐项测试能改什么不能改什么

每个实验单独打一个包，覆盖安装，冷启观察 ≥60s，记录存活/死亡/存活时间。

#### 实验 1-A：ADD lib 新 so

| 项 | 内容 |
|----|------|
| 改动 | 外科 zip ADD `lib/arm64-v8a/libstarry_magic.so`（空壳，仅日志 JNI_OnLoad） |
| 目的 | 旧 ACE 是否禁止新增 lib 文件 |
| 预期 | 如果旧 ACE 不扫 lib 清单 → 存活；如果扫 → 死 |

#### 实验 1-B：ADD classes6.dex

| 项 | 内容 |
|----|------|
| 改动 | 外科 zip ADD `classes6.dex`（最小 Probe 类，仅日志） |
| 目的 | 旧 ACE 是否禁止新增 dex |
| 预期 | 如果旧 ACE 不校验 dex 清单 → 存活；如果校验 → 死 |

#### 实验 1-C：改已有 so 1 字节

| 项 | 内容 |
|----|------|
| 改动 | 外科 REPLACE `libn.so`（翻最后 1 字节，libn 几乎不加载） |
| 目的 | 旧 ACE 是否校验已有 so 内容 |
| 预期 | 如果旧 ACE 不做 so 内容 MD5 → 存活；如果做 → 死 |

#### 实验 1-D：改已有 dex

| 项 | 内容 |
|----|------|
| 改动 | baksmali classes4 → 改一个无关方法加空方法体 → smali → 外科 REPLACE classes4.dex |
| 目的 | 旧 ACE 是否校验已有 dex 内容 |
| 预期 | 如果旧 ACE 不校验 dex 内容 → 存活；如果校验 → 死 |

#### 实验 1-E：ADD assets + Manifest

| 项 | 内容 |
|----|------|
| 改动 | 外科 zip ADD `assets/starry_native/` + `assets/starry_dex/` + Manifest 声明 MenuService（同 1.25.31 的 zipAssets-menu 方案） |
| 目的 | 确认旧 ACE 放行 assets + Manifest 改动（已知 1.25.31 放行） |
| 预期 | 大概率存活（旧 ACE 检测面通常 ≤ 新 ACE） |

#### 实验决策表

| 结果 | 含义 | 下一步 |
|------|------|--------|
| 1-A 存活 | 旧 ACE 不扫 lib 清单 | 直接走阶段 3（星光 so 放 lib + Manifest 出菜单） |
| 1-A 死、1-B 存活 | 禁 lib 不禁 dex | 走阶段 2（dex 跳板加载 so） |
| 1-A/1-B 都死 | 旧 ACE 也校验 lib+dex | 走阶段 4（加斌哥过检体） |
| 1-C 存活 | 旧 ACE 不校验 so 内容 | 可改已有 so 做 shim |
| 1-C 死 | 旧 ACE 校验 so 内容 | 不能改已有 so |
| 1-D 存活 | 旧 ACE 不校验 dex 内容 | 可改已有 dex 加跳板 |
| 1-D 死 | 旧 ACE 校验 dex 内容 | 不能改已有 dex |
| 1-E 存活 | 旧 ACE 放行 assets | 基础载体可用 |

**关键**：每个实验前必须清理设备 + 重装基线，避免 ACE sticky 污染。

---

### 阶段 2：dex 跳板加载星光 so（若 1-B 存活）

**前提**：旧 ACE 不校验新增 dex

**思路**：
1. ADD `classes6.dex`，内含 `StarryLoader` 类
2. `StarryLoader.<clinit>` 或 `.attachBaseContext` 中 `System.load` assets 里的星光 so
3. 触发时机：通过 Manifest `Application` 继承链或 `ContentProvider` 初始化

**步骤**：
1. 编写 `StarryLoader.java`（compile → dex → classes6.dex）
2. 外科组装：旧官方底 + ADD classes6.dex + ADD assets/starry_native/ + Manifest 改 Application 继承
3. 签名装机
4. 验证：冷启 → `StarryLoader` 执行 → so 加载 → JNI_OnLoad → 菜单出

**风险**：
- Manifest 改 Application 可能触发 ACE（需 1-D 配合验证）
- 旧 ACE 可能校验 Application 类名

---

### 阶段 3：lib 直装 + Manifest 出菜单（若 1-A 存活）

**前提**：旧 ACE 不禁止新增 lib 文件

**思路**：
1. ADD `lib/arm64-v8a/libstarry_magic.so` + `lib/arm64-v8a/libc++_shared.so`
2. ADD `assets/starry_dex/starry.dex`
3. Manifest 声明 MenuService + 继承链
4. so 的 JNI_OnLoad → DexInstaller → MenuService → 菜单出

**步骤**：
1. 外科组装：旧官方底 + ADD 上述文件 + Manifest 改动
2. uber-apk-signer 签名
3. 覆盖安装（或卸载重装，versionCode 不同需卸载）
4. 验证：冷启 → 菜单自出 → 登录 → 功能可用

**这是最理想的情况——零 Root 纯 APK 自启菜单。**

---

### 阶段 4：加斌哥过检体（若旧 ACE 也校验 lib/dex）

**前提**：旧 ACE 和新 ACE 一样禁止新增 lib/dex

**思路**：
把斌哥的 `libsdk.so` + `libSDKloading.so` 放进旧官方 1.20.13，让斌哥的过检体处理旧 ACE。

但斌哥的 ACE 和旧官方 ACE 不是同一套（MD5 不同），需要验证兼容性：

#### 4-1：斌哥组件兼容性测试

1. 外科组装：旧官方底 + REPLACE `libtersafe2.so` → 斌哥版 + REPLACE `libtprt.so` → 斌哥版 + ADD `libsdk.so` + ADD `libSDKloading.so`
2. 签名装机
3. 验证：能否冷启存活、菜单壳是否出现

**风险**：斌哥的 libsdk 可能依赖斌哥版 libcocos.so（1.20.13 的 libcocos 和斌哥的可能不同版本），不兼容 → 崩。

#### 4-2：整包斌哥组件替换

如果 4-1 不兼容，全量替换：

1. 外科组装：旧官方底 + REPLACE 全部 ACE 组件为斌哥版（tersafe2 + tprt + libcocos + libsdk + libSDKloading）
2. 但旧官方的 jsc 可能依赖新版 libcocos 接口 → 需验证

**这条路本质上是"用斌哥的底层 + 旧官方的业务"组装一个混合包，和直接用斌哥包差不多了。**

---

### 阶段 5：玩法功能适配

**前提**：菜单已在旧官方包上跑起来

#### 5-1：XXTEA 密钥验证

1.20.13 的 XXTEA 密钥可能和 1.25.31 不同：
1. 从旧包 `libcocos.so` 提取 XXTEA 密钥（`strings` + 搜 `jsb_set_xxtea_key` 调用点）
2. 解密旧包 jsc
3. 定位玩法挂点（`XPlane.hurt()` / `EnemyPlane.hurt()` 等）

#### 5-2：LtzjMod.cpp 适配

1. 切 GameConfig.h 到 LTZJ
2. 确认旧包的 `se::ScriptEngine::evalString` 符号地址（dlsym 查）
3. BSS 旗标偏移可能和 1.25.31 不同，需重新 dump
4. 编译 `libstarry_magic.so`

#### 5-3：EvalJs 玩法注入

1. 用旧包正确的模块名/类名
2. 百倍伤害：`EnemyPlane.prototype.hurt` ×100
3. 无敌：`XPlane.prototype.hurt` → `return false`
4. 免广告：hook `showAd` → `fakeRewardShow`

## 执行顺序

```
阶段 0（基线）→ 阶段 1（探测，1-A~1-E 逐个实验）
  ├─ 1-A 存活 → 阶段 3（lib 直装）→ 阶段 5（玩法适配）→ 交付
  ├─ 1-B 存活 → 阶段 2（dex 跳板）→ 阶段 5（玩法适配）→ 交付
  └─ 全死 → 阶段 4（斌哥过检体）→ 阶段 5（玩法适配）→ 交付
```

## 注意事项

1. **每次实验前必须**：`cleanup_device_re_residue.sh` + 卸载旧包 + 重装基线
2. **ACE sticky**：如果某包实验后即使卸载重装基线也死 → 重启手机
3. **versionCode 不同**：1.20.13 (12013) 和 1.25.31 (12531) 不同 → 必须卸载才能装，不能覆盖安装
4. **旧包资源少**：635M vs 952M，旧包没有一些新活动资源 → 功能可能不受影响但需验证
5. **热更风险**：旧版首次启动可能触发游戏热更（下载新资源），热更后行为可能变化
6. **每步记录**：实验产物 → `08_output/雷霆战队/`，日志 → `09_test/雷霆战机/old_pkg_experiments/`，结论 → `10_docs/雷霆战机/`

## 成功标准

✅ **完全成功**：零 Root、纯 APK 覆盖安装、冷启菜单自出、三功能（百倍伤害/无敌/免广告）可用、≥5 分钟稳定不崩
