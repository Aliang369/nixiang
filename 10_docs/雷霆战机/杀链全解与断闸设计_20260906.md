## 二、修正后的架构认知（消息级联）

```
子检查器（6个，ctx 步长0x48，摘要比对 [sp+8] vs [x8+0x1C8]，备用比对 +0x1B8）
  失败 → b.ne 0xB33FC 跳过成功标记（str wzr,[x8+0x128]）→ 比对 fallback → 聚合
  → 【0xB2648 直接调用消息总线 0xB1980（w6=0），绕过投诉标志！】
  → 消息节点 0x410B（链+两个0x200载荷），入队点：0xB20DC（∈handler-A）/0xB61B4(队列合并)
  → worker 0xB1C8C 路由（0x3AC32C 注册表按名查找）
  → handler-A 0xB1E34（再入队→消息级联）/ handler-B 0x3D4B44（memcpy+0x3A7330 加密）
  → 级联终端 → libc syscall@plt(0xA9960，nr=变量，22 调用点) 或缺页

投诉标志 +0x72（0x12E62C 置位）是平行的次级通道：
  ReportComplaint 处理 → 标志=1 → 走廊 B1B18 → 时间检查 → 0xB1980 发送
  E15 断掉它后杀仍发生 → 主通道 = 检查器直接上总线
```

## 九、E16/E17 实验结果（2026-09-06 深夜，真机）

- **E16 总线断闸（0xB1980 入口→mov w0,#0;ret，+1.5s 应用，两次复现）**：原进程**活过 10s 杀窗**（t+10s 存活），死于 ~12-14s；重生进程（无补丁）精确死在自己的 +10s → **杀计时器按进程启动计算、杀消息确认走总线**。
- E17 janitor（清 +0x72）：单例在走廊前不存在（懒创建），扑空——本地篡改杀不经过投诉标志，E15 后假说（检查器直发总线）成立。
- 第二通道：~12-14s 死因未定位（走廊 flag→B1C8C 直调？或 tprt/终端原语独立通道）。下一轮：**真·双闸**（总线 0xB1980 + 路由 0xB1C8C 同时 patch；本轮第二闸脚本插入失败未测）。
- 脚本教训：占位符必须端到端程序化生成（本轮 awk 偏移占位符漏替换导致 E16 三次空跑、E15 字节错误一次）。
- 设备状态：libcocos 官方 md5 已验证还原。

## 十、E18 双闸结果与结论（本轮收束）

- E18：总线 0xB1980 + 路由 0xB1C8C **同时**断闸（双 PATCHED 确认）→ 仍 ~10s 死。
- 与 E16（单总线闸，活过 10s 死于 12-14s）对比：消息层断闸只能推迟/扰动，**存在绕过消息总线的直接杀路径**。
- 嫌疑收敛：①终端原语直调（syscall@plt 变量 nr 站点 0x351xxx×7 / 0x362xxx×10，消息可能只是携带参数而非必经路径）；②tprt 侧独立执行（濒死反序列化线程）；③mem_trap2（堆陷阱）机制。
- 方法论教训：消息层推论的「唯一性」在平坦化+自改写+多通道架构下不可靠；必须以**终端原语**为锚点做反向数据流，而不是正向门控。
