# 斌哥 libsdk.so 脱壳分析 — RC4 壳机制（2026-08-17）

> 日期：2026-08-17
> 对象：`雷霆战机_集结_999999_mod.apk` 内 `lib/arm64-v8a/libsdk.so`（2935288 字节）
> 目标：脱壳还原 hook 表与过检逻辑，评估「整包代换」可移植性
> 结论：**壳机制已完全破解**（双层：RC4 流密码 + 自定义分组密码），入口/算法/配置/加密目标全部定位；仅剩第二层分组密码未静态还原，建议转真机动态 dump。

---

## 1. 一句话结论

`libsdk.so` 是**双层保护的自定义壳**：

```
.so 加载 → .init_array 触发自解密
    ├─ 第一层：查表混淆（0x15638）生成 32 字节中间 key
    ├─ 第二层：自定义分组密码（0x157c0，NEON + 256B 自定义 S-box）→ 16 字节 RC4 key
    └─ RC4 流密码（0x25c10 KSA + 0x25e70 PRGA）就地解密 .main 段
```

加密目标是 **`.main` 段**（含 `JNI_OnLoad` 与核心过检/hook 逻辑），不是全 so。

## 2. 静态事实

### 2.1 段布局与熵

| 段 | file offset | 大小 | 熵 | 性质 |
|----|-------------|------|-----|------|
| `.text` | 0x14a60 | 0x4583c (285KB) | 6.836 | 明文（含壳入口 + RC4/分组密码代码） |
| `.main` | 0x5a29c | 0x267c (9.8KB) | **7.980** | **加密（含 JNI_OnLoad @ 0x5b900）** |
| `.rodata` | 0x5c920 | 0x221670 (2.2MB) | 6.336 | 数据 + 查找表 + 压缩 payload |
| `.data` | 0x28d000 | 0x3c058 | **7.779** | 加密数据 |
| `.ced` | 0x2c9058 | 0x20 (32B) | — | **解密配置表** |
| LOAD6 | 0x2ca000 | 0x29f4 | 4.846 | 明文附加段 |

### 2.2 解密配置表 `.ced`（32 字节）

```
hex: 9ca205007c260000 090a000000000000 0000000000000000 0000000000000000
[0] = 0x0000267c0005a29c  → 高32位 0x267c=大小，低32位 0x5a29c=.main 段起始 VMA
[1] = 0x0000000000000a09  → 第二层分组密码参数
```

### 2.3 解密入口链（已实锤）

```
.init_array[0]  （文件内为 0，靠 RELATIVE 重定位运行时填 0x14a6c）
  → 0x14a6c    壳入口（引用 .ced，调用 0x25a78）
  → 0x25a78    解密调度
       ├─ dladdr 拿 so 基址 → base + 0x5a29c = .main 运行时地址
       ├─ mprotect 改 .main 为 RWX
       ├─ 0x15638  查表混淆 → 32 字节中间 key
       ├─ 0x15698/0x157c0  自定义分组密码 → 16 字节 RC4 key
       ├─ 0x25c10  RC4 KSA（用 16 字节 key 打乱 S-box）
       ├─ 0x25e70  RC4 PRGA（就地解密 .main 段）
       └─ __clear_cache + dsb/isb（刷新指令缓存）
```

### 2.4 RC4 算法已还原（0x25c10 + 0x25e70）

`0x25e70` 是标准 RC4 PRGA：
```
i = (i + 1) & 0xff
j = (j + S[i]) & 0xff
swap(S[i], S[j])
明文 = 密文 XOR S[(S[i] + S[j]) & 0xff]
```

`0x25c10` 是标准 RC4 KSA：
```
S = [0..255]
for i in 0..255:
    j = (j + S[i] + key[i % keylen]) & 0xff
    swap(S[i], S[j])
```

### 2.5 第一层 key 生成已还原（0x15638）

从 `.rodata` 4 张查找表生成 32 字节：
```
table1 @ 0x5caa0（512B）   table2 @ 0x5ccc0（512B）
table3 @ 0x5cca0（32B）     table4 @ 0x5ca80（32B）

for i in 0..31:
    key[i] = (table1[(i<<4) + table3[i]] << 4) | table2[(i<<4) + table4[i]]
```

实测生成 32 字节中间 key：`df5d72490c45b00ecb3d314b1706b533a2e0d71c54379f3fbeddb69d88d941f8`

### 2.6 第二层（未还原，卡点）

`0x157c0` 是自定义分组密码（非标准 AES）：
- 256 字节自定义 S-box @ `0x29d210`（前 16 字节 `6ebbe79329e028f62a687803bf546ea5` ≠ 标准 AES `637c777bf26b6fc53001672bfed7ab76`）
- 16 轮（`cmp x24, #0x10`）
- 大量 NEON SIMD（d8-d15）
- 把 32 字节中间 key → 16 字节 RC4 key

## 3. 其他壳特征

| 项 | 结论 |
|----|------|
| 符号混淆 | C++ 导出符号名混淆成 `Y00000xxx` / `M00000xxx` 等（OLLVM 类）；`uncompress`/`__cxa_*` 等标准符号未混淆 |

## 4. 脱壳剩余路线

**静态还原第二层（0x157c0）成本高**（魔改分组密码 + 自定义 S-box + NEON），**建议转真机动态 dump**：

### 方案 A（推荐）：真机 dump 明文 .main 段

斌哥包冷启后 `.init_array` 已跑完，`.main` 段在内存中是明文：
```
1. 真机跑斌哥包
2. 找 libsdk.so 基址：adb shell su -c 'cat /proc/<pid>/maps | grep libsdk'
3. dump：base+0x5a29c ~ base+0x5a29c+0x267c（含 JNI_OnLoad 明文）
```
无需还原第二层算法，直接拿明文代码。

### 方案 B：Unicorn 模拟执行

模拟执行 0x14a6c，hook dladdr/mprotect/malloc，让壳自解密后 dump。无需真机，但要模拟环境。

### 方案 C：Frida hook 0x25e70 返回点

Florida 魔改 server，attach 后 hook RC4 解密函数 0x25e70 返回，dump .main 段。

## 5. 对「整包代换」的意义

静态分析已足以证明：
- 斌哥过检 = **自带 RC4 壳的 `libsdk`（native 过检体）+ Killer（签回灌）+ 配套旧代 tersafe/tprt**，不是「旧 ACE 更弱」。
- 三个官方/斌哥包的 tersafe2 是**同一引擎**（字符串/检测关键词完全一致，见 `旧ACE与新ACE同引擎_静态对比_20260817.md`）。
- 要真正移植过检能力，必须先拿到 libsdk 脱壳后的明文 hook 表（它 hook 了哪些 ACE 导出、怎么改 maps/签名），才能评估能否迁到别的 tersafe 代。

## 8. 脱壳结果与过检机制（2026-08-17 晚真机 dump 实锤）

### 8.1 脱壳成功

真机冷启斌哥包后，`.main` 段已在内存解密，dump `base+0x5a29c`（0x267c 字节）即得明文：

- dump 段熵 **7.98 → 6.88**，前 64 字节为标准 ARM64 序言（`sub sp,#0x430` + `stp`）
- 反汇编 `JNI_OnLoad`（0x5b900）已可读，无 `<unknown>` 乱码
- 重建 `libsdk_decrypted.so`，`.main` 段全明文

### 8.2 JNI_OnLoad 明文逻辑

```
JNI_OnLoad:
  GetJavaVM（JNIEnv->functions[6]）
  prctl(PR_SET_DUMPABLE=4, 1)        // 设可 dump（反反调试/放行 maps 读）
  dladdr → 拿 libsdk 自身基址
  0x5a2e4(基址)                       // 遍历结构体表（292B/项）+ mprotect RWX
  0x5b5f4 / 0x5b82c                    // 初始化两个对象
  0x5bc48(obj1, obj2) → bool           // 核心过检逻辑
  成功则调 GOT 函数指针 [0x29c000+0xf40]
```

### 8.3 过检机制（导入函数实锤）

libsdk 导入的关键函数揭示其过检方式：

| 导入函数 | 用途 |
|---------|------|
| `dl_iterate_phdr` + `/proc/self/maps` | **定位 tersafe2/tprt 基址**（不是 dlsym 符号名） |
| `mprotect` / `mmap` / `munmap` | 改 ACE 代码段权限为 RWX |
| `uncompress`(zlib) | 解压 `.rodata` 里预置的 patch 数据（9 个高熵 4KB blob） |
| `open` / `read` / `lseek` / `strstr` | 读并解析 `/proc/self/maps` |
| `dlopen` / `dlsym` | 加载依赖 / 查部分符号 |
| `prctl` | PR_SET_DUMPABLE 等进程控制 |

**关键结论**：`.rodata` 里**没有** `tersafe` / `tss_sdk_init` / `tss_sdk_ioctl` 等符号名字符串 → libsdk **不靠 dlsym 符号名 hook，而是基于「特定 tersafe2 版本的硬编码 file offset/RVA」直接 patch 代码**。

### 8.4 可移植性结论（回答整包代换）

1. libsdk 过检 = `dl_iterate_phdr` 定位 tersafe2/tprt → `mprotect` → **按硬编码偏移 patch 代码** → 解压 zlib patch blob 覆盖检测点。
2. **不依赖符号名，只认特定 tersafe2 代码布局**（斌哥 823fef52 那代）。
3. 这解释了历史现象：抄 libsdk 到新官方 1.25.31（tersafe2 `ba597b32`）→ **代码布局不同，硬编码偏移对不上 → 反复重启**。
4. 要移植过检能力，需对新目标 tersafe2 重新定位每个 patch 点（不能直接复用 libsdk）。

## 9. libsdk 完整 hook 表（2026-08-17 真机 dump 对比实锤）

真机冷启斌哥包后，dump tersafe2/tprt 被 patch 后的内存，对比原始文件，得到 libsdk 的**全部 4 处 patch**：

| so | file offset | 原始指令 | patch 后 | 语义 |
|----|-------------|---------|---------|------|
| tersafe2 | `0x3ad0b4` | `97f3f10f` `bl gettimeofday` | `d503201f` NOP | 禁用时间戳函数（返回恒 0），绕过耗时/性能检测 |
| tprt | `0x041258` | `ffc301d1` `sub sp,#0x70`（函数序言） | `c0035fd6` ret | **整个函数直接返回**（`REL_HOOK_7` 内的 hook 检测） |
| tprt | `0x0d9444` | `c83b0094` `bl 0xe8364` | `e0031f2a` b（跳过） | 跳过 `unwind_xx_ioctl` 里的一个调用 |
| tprt | `0x1356f0` | `fd7bbca9` `stp x29,x30,[sp,#-0x40]!`（函数序言） | `c0035fd6` ret | **整个函数直接返回**（`unwind_xx_ioctl` 内的检测） |

### 9.1 patch 特征

- **全部是「禁用型」patch**：NOP / ret / b 跳过，**没有注入任何代码**，只是把检测函数变成空操作。
- **4 处 patch 全是硬编码 file offset**，绑定斌哥那代 tersafe2/tprt（`823fef52`/`5f4e0734`）的代码布局。
- **ter safe2 只 patch 1 处**（gettimeofday → NOP），**tprt patch 3 处**（两个函数序言 ret + 一个调用跳过）——过检主体在 tprt。

### 9.2 可移植性最终结论

1. 要移植到新官方 1.25.31，需在新 tersafe2（`ba597b32`）/tprt（`3ae6724e`）里**重新定位这 4 个等价检测点**：
   - tersafe2 的 gettimeofday 时间戳函数
   - tprt 的 `REL_HOOK` hook 检测函数（约 0x41258）
   - tprt 的 `unwind_xx_ioctl` 里两个检测点（约 0xd9444 / 0x1356f0）
2. 硬编码偏移对不上 → 历史「抄 libsdk 到 1.25.31 反复重启」的根因。
3. 但因为 patch 是**简单的禁用型**（不是复杂 hook），只要在新 tersafe2/tprt 里找到「同样的检测函数」，替换成同样的 NOP/ret 即可，**移植可行性存在**，只是要逐点重定位。
