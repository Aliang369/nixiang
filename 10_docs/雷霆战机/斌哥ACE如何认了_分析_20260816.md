# 斌哥 ACE「认了」到底是什么（2026-08-16）

> 约束：本篇只分析，**不改包**。改之前的验收标准见文末。  
> 对照包：官方 `雷霆战机_原版.apk`（1.25.31 / 2026-07-10）↔ 斌哥 `雷霆战机_集结_999999_mod.apk`  
> 相关：`雷霆战机_星光移植_20260810.md` §2–4 · `雷霆战机_加固与校验分析.md` §3 · 冷启时序 §7

---

## 1. 一句话

斌哥不是在**当前官方 1.25.31 ACE** 上打补丁让它放行星光；  
而是整包换成 **更旧一代的游戏/ACE 二进制**，再叠 **Killer（Java 签）+ `libsdk`（native 过检体）+ `libSDKloading`（菜单壳）**，让「改签 + 多出来的 lib so」落在**他们那一套已配套**的过检面里。

官方 zip 晚载星光仍被 `SI_USER` 杀，是因为我们站在 **新 ACE** 上，少了整套配套，还多了 **清单外的 so 映射**——这正是目前没挡住的检测。

## 2. 静态对照（已核）

### 2.1 Application / 加载链

| | 官方 1.25.31 | 斌哥 999999 |
|--|-------------|-------------|
| `AceApplication` 父类 | `android.app.Application` | **`KillerApplication193`** |
| `<clinit>` loadLibrary | `tersafe2` → `tprt` | `tersafe2` → `tprt` → **`sdk`** |
| Killer | 无 | `classes6`：`killPM(包名, 原厂 clover 证书 B64)` + `killOpen(...)`（本包参数多为空串） |
| 菜单 | 无 | `classes7` + `libSDKloading`；`Main.StartWithoutPermission` |

冷启 `nativeloader`（已抓）：`tersafe2` → `tprt` → **`libsdk`**（~15ms）→ ~0.7s `SDKloading` → `cocos`。

### 2.2 核心 so：**不是同版 ACE**

| so | 官方 md5 / 日期 | 斌哥 md5 / 日期 | 结论 |
|----|-----------------|-----------------|------|
| `libtersafe2.so` | `ba597b32…` / **2026-07-10** / 5979312 B | `823fef52…` / **2025-11-19** / 同尺寸 | **不同代 ACE**（同长度异哈希） |
| `libtprt.so` | `3ae6724e…` / 1692296 B | `5f4e0734…` / **1682312 B** | 不同文件；官方内嵌 tersafe MD5 @ `0x16956c` = `ba597b32…`，斌哥该偏移已非同布局 |
| `libcocos.so` | `d39e4551…` / 29.3MB | `06d8a9c5…` / 28.6MB | **整引擎也是旧包** |
| `libsdk.so` | **无** | `1c6576e9…` / 2.94MB | 斌哥专用；高熵壳，明文极少 |
| `libSDKloading.so` | **无** | `1fa3fba6…` / 3.88MB | 菜单壳；在 `lib/` 合法条目里 |

额外 so（仅斌哥 `lib/arm64-v8a`）：`libsdk.so`、`libSDKloading.so`。

### 2.3 `libsdk` 能看出什么（静态上限）

- ELF 可加载；可见 `JNI_OnLoad`、`dlopen`、`mprotect`、`/proc/self/maps`、`base.apk`。  
- **几乎无**明文 `ptrace` / `TracerPid` / `frida` / `tersafe` / `Dobby`（壳加密或运行时拼）。  
- 整文件熵 ~6.7，尾部更高 → **打包壳**，未脱壳前不能当「已看清内部 hook 表」。  
- 运行时：冷启后立刻有 `NativeUI: DobbyHook`（疑似 sdk 起 hook），与菜单壳分工：sdk≈过检，SDKloading≈UI/玩法。

### 2.4 Killer 挡的是哪一层

- `killPM`：Java `PackageInfo` / 签名回灌为 **原厂 clover**（重签后 ACE/业务读签仍像官签）。  
- **不够单独保活**：官方底 + 仅 Killer、不配 `libsdk`、或 MT Killer643 **无 sdk** → 历史已死在 native（见移植笔记 E/F/I/J）。  
- 结论：Killer = **签层面**；**native 过检靠同代 `libsdk` + 同代 tersafe/tprt**。

## 3. 「认了」拆成三层

```
① 换代底包：旧 cocos + 旧 tersafe2/tprt（2025-11 代，非整改 2026-07 官方 ACE）
② Java：Killer193 让重签仍像 clover
③ Native：Ace <clinit> 同批 load libsdk → 在 ACE 初始化窗口内改/喂过检态
④ 菜单 so：SDKloading 进 APK lib/，对「那一套」ACE 是预期模块，不是晚塞的异常映射
```

所以别人能 `lib/` 早挂菜单，是因为 **过检面已按他们的包裁好**；不是官方 ACE「突然不查 so 清单」。

## 4. 我们官方星光 **没挡住** 的检测（对照作战表）

| 检测 / 现象 | 斌哥侧 | 官方星光现状 | 状态 |
|-------------|--------|--------------|------|
| **so / 模块异常**（清单外、非 apk lib 路径映射） | `sdk`/`SDKloading` 在 `lib/`，且 ACE 为配套旧代 | 星光在 `assets`/`files/`，Florida 晚载后进 maps → ~1–2min **`SI_USER`** | **未挡（当前杀因）** |
| **APK 签名** | Killer 回灌 clover | resign-only 可玩；无 Killer 时靠不改业务字节 | 基线可玩；**挡不住**上面模块杀 |
| **tprt↔tersafe MD5** | 旧对旧自洽 | 官方对官方自洽；磁盘改 ACE **已败** | 勿再盲补丁 |
| **改/增 dex、apktool** | 斌哥自带 classes6/7（其 ACE 代允许） | 官方增改 dex 杀 | 硬禁官方路径 |
| **登记资源 MD5** | 未作主线对比 | 改已登记 assets 杀 | 硬禁 |
| **ptrace / Frida 残留** | 交付不靠长挂 | 晚载用 Florida 后必清；残留放大误判 | 前置 |
| **抄 binge `libsdk` 到 1.25.31** | — | 与新 tersafe **不匹配** → 反复重启（移植 E） | **已证伪** |

挂机/晚载后 tombstone 共性：`SIGSEGV` + **`SI_USER`**（外送杀），不是菜单空指针。  
→ 没挡住的是 **「进程里出现非预期 so / 注入痕迹」** 一类 ACE 行为，不是「60s 倒计时文案」。

## 5. 尚未完全清楚（改之前仍缺）

1. **`libsdk` 脱壳后的真实 hook 表**（对哪几个 ACE 导出 / maps 读法 / 签名 blob）。  
2. 旧代 ACE 的 **so MD5 清单** 是否明文可抽（`probeSoMd5Record` 类），以及是否显式收录 `libsdk`/`SDKloading`。  
3. 官方 1.25.31 上是否存在 **同代可迁的过检体**（不是抄 2025-11 的 sdk）。  
4. 星光是否可做成 **ACE 扫不到的形态**（非 `files/` 长驻、非 Frida 载入）——当前无解。

## 6. 改之前的门槛（你说的「完全清楚后再改」）

满足再动手改官方过检/早载：

- [ ] 说得清：斌哥 = **换代 ACE 底 + Killer + 配套 sdk**，不是「补丁当前官方 ACE」  
- [ ] 说得清：我们被杀主因 = **清单外 starry 映射 / 注入面**（`SI_USER`），不是菜单 UI  
- [ ] 有一条 **可验证** 的官方路径假说（同代过检体 / 或证明某检测点可关），且不靠「再抄一遍异代 libsdk」  
- [ ] 假说失败标准写死（几秒内何种信号 / 是否进 cocos）

**当前结论：分析到「机制分层」已清楚；`libsdk` 内部指令级未脱壳清楚 → 还不到改官方 ACE 的时候。**

权宜（非本篇目标）：继续用斌哥整包底做玩法，或官方 zip 只保证开机、不晚载星光。
