# 雷霆战机零Root纯APK方案 — 思路分析

> 日期：2026-08-16

## 核心思路：旧版官方包 + 斌哥过检方案

### 原理

斌哥的包能过 ACE，不是因为他在官方 ACE 上打补丁，而是**整套换了旧代 ACE 底包**：

| 组件 | 官方 1.25.31 | 斌哥 999999 |
|------|-------------|-------------|
| libtersafe2.so | 2026-07 版（新） | 2025-11 版（旧） |
| libtprt.so | 2026-07 版（新） | 2025-11 版（旧） |
| libsdk.so | 无 | 有（与旧 ACE 配套的过检体） |
| libcocos.so | 2026-07 版 | 2025-11 版 |
| 过检机制 | 无 | Killer193（Java 签）+ libsdk（native 过检） |

斌哥的链路自洽：旧 ACE 认 libsdk 是合法模块 → 60s 倒计时后功能可用。

### 为什么官方包上做不到

1. ACE 校验自己的 MD5（libtprt 内嵌 libtersafe2 的期望 MD5 @ 0x16956c）
2. 改 lib 内容 → 15s SIGBUS
3. 换 tersafe2 + 同步 tprt MD5 → 卡隐私页 / PID 轮转（ace13/ace14 已证死）
4. 抄斌哥 libsdk 进官方 → 与新 tersafe 不匹配 → LMKD 重启循环

### 突破方向：找一个和斌哥同代 ACE 的官方旧版 APK

如果有 2025-11 左右的官方旧版 APK：

- 旧版 ACE（libtersafe2 + libtprt）和旧版 libcocos.so 是配套的 → 不会有版本不兼容
- 旧版 jsc 和旧版 cocos 是配套的 → 不会崩
- 拿斌哥的 libsdk.so + Killer193 放进去 → 旧 ACE 认 → 过检
- 再塞星光菜单 → 零 Root 纯 APK

**整条链自洽，不需要 Root。**

## 需要确认的事项

### 1. 斌哥包的具体版本号
- 斌哥包版本是 999999（伪装版本），需要确认它基于哪个官方版本改的
- 如果斌哥包的 libcocos.so MD5 = 某个官方版本的 libcocos.so MD5 → 那个官方版本就是目标

### 2. 旧版官方 APK 是否存在
- 雷霆战机 1.25.31 是 2026-07 的版本
- 需要找 2025-11 左右的官方版本（版本号可能是 1.2x.xx）
- 来源：豌豆荚、apkmirror、taptap 历史版本、用户本地备份

### 3. 旧版业务逻辑兼容性
- 如果旧版官方包和斌哥包的 libcocos.so MD5 一致 → 完全兼容，直接组装
- 如果不一致但版本接近 → 大概率兼容，需测试
- 如果差很远 → 可能 jsc 接口不兼容

## 组装方案（确认旧版包后）

```
旧版官方 APK（业务 dex + assets + jsc + libcocos.so）
  + 斌哥 libsdk.so（过检体）
  + Killer193（Java 签名伪装）
  + 星光菜单（libstarry_magic.so + starry.dex + Manifest）
  + uber-apk-signer 签名
```

### 预期 ACE 检测链路
1. 旧 ACE 初始化 → libsdk 在同批 load（过检 hook 挂上）
2. 旧 ACE 扫 lib/ → 星光 so 在 lib/ 合法条目里（对旧 ACE 是预期模块）
3. 60s 倒计时 → 过检完成 → 功能可用
4. 星光菜单正常出（Dobby hook evalString 不被新 ACE 打，因为根本没有新 ACE）

### 与当前方案的对比

| 维度 | 当前方案（官方 1.25.31） | 旧版方案 |
|------|------------------------|---------|
| ACE 版本 | 2026-07 新版 | 2025-11 旧版 |
| so 加载 | 需要 Root 落 so | lib/ 合法条目，零 Root |
| ACE 驻留检测 | 60-126s 杀进程 | 旧 ACE 认 libsdk，不杀 |
| Dobby hook | 被 ACE 打 | 旧 ACE 不打 Dobby |
| Root 需求 | 需要一次 Root | 零 Root |
| 风险 | 已知死路 | 需验证版本兼容性 |
