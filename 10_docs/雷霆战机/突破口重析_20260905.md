## 一、结论摘要

1. **零 Root 卡点已收窄为单一杀因**：改 `libcocos` 内容（含末 1 字节）或 ADD `lib/*.so` 文件名 → **~10–15s 延迟 SIGBUS/SEGV**。菜单本身已打通（H5f/g：cocos cave + CaveBoot + xDL，用户肉眼确认菜单、auth 通、悬浮窗出）。
2. **H5i 系列全灭的统一解释**：kill/exit/sigaction GOT 劫持无效 + SIGBUS handler 从未进入 + PC 落 libc/libart 且 LR/x8 污染 → ACE 走 **raw svc 系统调用**（先 raw svc 解除信号处理器，再投毒/杀），不走 PLT。tersafe 里早就定位过同形证据：ptrace 簇1 含 `signal(SIGBUS,…,SIG_DFL)` + `_exit(127)`（`官方原包…md` §10.2）。
3. **H5h 三刀无效的解释**：patch 的是 tersafe `sectionhash/filecrc/HashBySyscall` 的 **JNI 调度簇 BLR**——那是 Java 侧触发口，不是周期检查路径；周期检查器大概率直调 vtable 实现函数，或根本跑在 **`:core`/GP6 服务进程**（主进程死时 `:core` 同死，从查过）。
4. **新突破口=把超维进化已 PROVEN 的方法论搬过来**：「延迟自杀」模式 → 枚举 svc 找单点收口 → 最早注入期 mprotect 内存中和（版本守卫）。雷霆的 H5g 已提供 ~11s 的**进程内先手窗**，正好够做 stage-0 拔牙。
5. **资产警告**：LTZJ 全部二进制/脚本资产已在 09 月初清理中丢失（见 §二），任何实验前必须先重取原包。

## 三、杀因取证现状（散点拼图）

### 3.1 钉死的改法→死法矩阵（干净机、单变量）

| 改法 | 死法 | 出处 |
|---|---|---|
| resign-only | 活 ≥70s（可玩） | 纯APK自启 §6 |
| REPLACE 任意 so 1 字节（含未加载 libn） | ~15s SIGBUS | 同上 Bn |
| ADD `lib/*.so` 文件名（不 load） | ~15s SIGBUS | 同上 A0 |
| 同内容 DEFLATE 重打包 | 活 | 同上 B0d |
| ADD/REPLACE `classes*.dex` | ~10–15s pid churn | 同上 D0/F0 |
| REPLACE 已登记 assets（jsc/cloverEnv/gbsdk 插件） | 死 | E0/§7.6 |
| ADD assets / Manifest ADD 组件 | 活 | C0/C1/C2 |
| 改 libcocos `.dynamic`/DT_NEEDED | 毫秒级 | 路线3 H3/H3c |
| 改 libcocos `.text`（1 字节或 cave） | **~10–11s** SIGBUS | H1/H5g |
| stock cocos + ADD boot so（无 DT_NEEDED） | **~10.6s** | H3d |

→ 杀因在「**解压后 native lib 目录的内容+文件集合**」面上，与 zip 包装/签名无关；且 **libcocos 不在 tprt 库存表（25 条）里**，它的检查器**至今未定位**——这是主线缺口。

### 3.2 死亡瞬间的取证积累

- 信号：SIGBUS(7) 为主、偶发 SIGSEGV(11)；tombstone 常缺；非 SIGKILL（≠超维进化的 signal 9 模式）。
- 故障 PC：libc 内**非对齐**（滑动 +4）或 libart 内对齐，**LR/x8 垃圾未映射**（`官方原包…md` §7.2/§10.4）→ 返回址/寄存器被污染，不是普通空指针。
- In-process handler（SA_SIGINFO, PC+4 skip）**从未进入**（H5i4）→ 处理器在投递前已被解除（raw svc `rt_sigaction`）或信号外部投递。
- GOT 级 kill/_exit/exit_group/abort/sigaction/signal stub：**全部无效、无拦截日志**（H5i~H5i6）。
- anon svc trampoline：ACE 正常 syscall 走它；全阻会秒死；9s 窗内未见 kill/tgkill（残留期数据，且**只看了主进程**）。
- `:core` 子进程与主进程**同时消失**；Manifest 还有 GP6/GP7 Service（ACE 相关）——**从未作为杀源排查**。
- tprt `.data` 库存表 `0x19bc10`（size+crc+tail×25）只覆盖除 cocos/tprt 外全部 so；tprt `.data` 任一字节改动即死（disk5-pad）。

## 五、突破口清单（按信息增益/成本排序）

> **2026-09-05 执行结果**：P0-1/P0-2 已完成，杀因实锤——执行者在主进程内、杀器 SIGKILL 组杀、checker=1Hz 线程读解压 so；中和点表已出（含 expected 字节）。详见 **`杀因取证与中和点_20260905.md`**（本文档 P0/P1 描述作废，以该文档为准）。P1-3 的前提（CaveBoot 重写）待启动。

### P0-1 零修改取证：钉死「谁在 ~10s 读什么、谁发信号」（Root，1 次装机）

- **问题**：致命 SIGBUS 的 sender 是主进程 raw svc 还是 `:core`/GP6/GP7？checker 何时读哪些文件（nativeLibraryDir? base.apk? libcocos?）？
- **已有证据**：`:core` 与主进程同死（§7.1）；外送杀 SI_USER 先例（晚载面）；tramp openat/read 密集但只见主进程。
- **方法**（全部零注入/零改 so）：重建 H1 复现包（仅 libcocos 末字节）→ Root 侧 ①ftrace `signal_generate`（直接打印 sender pid+target pid，一锤定音）；②ftrace syscalls openat 按 pid 过滤（看 checker 读文件节奏与清单）；③t≈8s `kill -3` 抓 `/data/anr` 全线程栈（认 watchdog 线程）；④`ps -A`+`/proc/*/task` 连续快照。对照 resign-only 基线各跑一遍。
- **预期新增信息**：sender 进程、被读文件集、watchdog 线程清单与栈。**这一步直接决定中和点选在哪**。
- **成本/停止**：重建 1 个包 + 1 次设备会话；拿到 sender+文件集即停，**不打任何补丁**。

### P0-2 静态收口点枚举（零设备，与 P0-1 并行）

- **方法**：对新取原包解出 `libtersafe2.so`/`libtprt.so`（MD5 门禁 `ba597b32…`/`3ae6724e…`）→ capstone 全量枚举 `svc` 并按 x8 系统调用号分类：kill(129)/tkill(130)/tgkill(131)/exit(93)/exit_group(94)/rt_sigaction(134)/rt_sigprocmask(135)/ptrace(117)/process_vm_readv(270)/writev(271) → 找「封装函数」（少量 svc、多调用点）vs 直散 svc；xref 三个 ACE 线程入口与 ptrace 簇；解析 filecrc/sectionhash 的 vtable 实现函数并列出其全部调用方（区分 JNI 触发 vs 内部周期触发）；与 tramp 1Hz openat/read 循环对齐。
- **产出**：候选中和点表（每点：地址、expected 字节、patch 指令、风险评估、版本守卫条件）。
- **停止条件**：≥1 个高置信收口（或证明收口不存在→转 P1-4 外部杀分支）。

### P1-3 CaveBoot stage-0 单点中和（P0-1/P0-2 汇合后）

- **改动**：仅 H5g 同款包 + CaveBoot 最前段加一个中和函数（超维进化模板：版本守卫+mprotect 写+清 cache），**单变量、一次一刀**。
- **判据（终末地协议）**：冷启菜单后存活 **≥10min**（跨过 60s 检测窗与历史 1–2min SI_USER 窗）+ 连续 logcat 驻留抓取 + 截图差分可操作 + crash 缓冲零击杀。失败即停，报现象不叠刀。
- **前置**：CaveBoot 源码重写（小体量；行为按 H5f/g 文档记载；xDL 在菜单工程内已有先例）。

### P1-4 `:core`/GP6 进程面（仅当 P0-1 证实外部杀）
