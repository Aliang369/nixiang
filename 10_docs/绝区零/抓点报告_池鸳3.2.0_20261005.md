## 0. 一句话结论

池鸳改包走的是**非斌哥路线**：不改磁盘 `libil2cpp.so`，而是启动时先校验 4 条 `(RVA,16字节原始字节)`
指纹闸门，全部 MATCH 后用 Dobby 风格 12 字节跳转桩（`adrp/add/br`）在**运行时内存代码页**上改写
3 个函数入口，跳到 `libcymod.so` 内的 3 个 handler；handler 通过预存的「原函数指针」回调原函数。
磁盘文件在 4 个候选点全部是原始字节 ⇒ 文件完整性/校验和类检查看不到任何改动。

菜单共 **13 项功能**（全部抓到，见 §2）。防御面初步结论见 §4（保护类 so 运行时一个都没加载，
`libtersafe2.so` 时间戳异常，**待官方原版对照确认**）。

## 3. 新路线：运行时内存 Hook（与斌哥路线对照）

### 3.1 机制总览

1. **指纹闸门**：`libcymod.so` 文件偏移 `0xe7798` 起是一条 4 项表，每项 = 8 字节 RVA + 16 字节原始指令。
   安装前逐条比对**当前内存字节**（代码 `0x4d880–0x4d8fc`，编译器把比对内联成 XOR 常量），
   任一条不符 → 打日志 `3.2 fingerprint mismatch at RVA 0x%lx`（串 `0xe75b1`）并放弃安装。
2. **12 字节跳转桩**：命中后改写函数入口前 12 字节为
   `adrp x17, #page; add x17, x17, #imm; br x17`，直接跳到 `libcymod` 内 handler。
3. **handler + 原函数 trampoline 指针槽**：`libcymod` 一条 3 项描述表（文件偏移 `0x10f5e0` 区）登记
   `站点RVA / handler偏移 / 指针槽偏移 / 名称串偏移`；指针槽在 `libcymod` 运行期 anon `.bss`
   （RVA `0x130f70/78/80`，本次 dump 偏移 `0x1af70` 起），运行期被写入 Dobby 风格 **trampoline 指针**
   （实测 `0x75a9600000 / 0x75a9600020 / 0x75a960004c`），handler 靠它回调原函数。
4. 改完恢复代码页权限（`libcymod` 内有 `restore code-page permissions failed errno=%d` 与
   `外部修改冲突/已写入/已恢复/已保持/写入失败/状态变化/旧对象已丢弃/等待数据初始化` 状态机串）。
5. 日志串自述：`three independent JNI hooks installed; attack-writeback version=20260918-v1;
   multi/invincible unchanged; no external payload used`（`0xe7479`）。

### 3.2 指纹闸门 4 条（全部 MATCH 磁盘 `libil2cpp.so`）

`find_patch_sites.py` 实测输出（RVA / 文件偏移 / 16 字节原始）：

| # | RVA | 文件偏移 | 16 字节原始 | 本轮是否被 hook |
|---|---|---|---|---|
| 1 | `0xae001a0` | `0xadfc1a0` | `ffc303d1 fd7b09a9 fc6f0aa9 fa670ba9` | ✅ 是（multi attack） |
| 2 | `0x10a05354` | `0x10a01354` | `ffc301d1 e82300fd fe5705a9 f44f06a9` | ❌ 否（运行时=SAME） |
| 3 | `0x11521138` | `0x1151d138` | `fe57bea9 f44f01a9 880306d0 f503022a` | ✅ 是（invincible upstream） |
| 4 | `0x16631314` | `0x1662d314` | `ff4303d1 eb2b056d e923066d fd7b07a9` | ❌ 否（运行时=SAME） |

第 2/4 条不是 hook 站点但也在闸门里（必须保持原始字节）⇒ 语义待确认，倾向「版本探针/防篡改哨兵」。
第 3 个 hook 站点 `0xc02a9f0` **不在**这条 4 项闸门表内，其指纹/写入走另一条路径
（`libcymod` 内有 `Nap32Extra` 串）——**部分推断，待验证**。

### 3.3 实际落地 3 个 Hook（PID 2441 会话实测）

跳转桩目标已用真实映射基址反汇编确认（`libcymod` ELF 装载基址 `0x746cc93000` 口径：VA = 基址 + RVA）：

| # | 名称（mod 自述串） | 站点 RVA | 文件偏移 | 运行时桩（本次会话） | 跳到 handler | 原函数指针槽 |
|---|---|---|---|---|---|---|
| 1 | `multi attack` | `0xae001a0` | `0xadfc1a0` | VA `0x737b61a1a0` → `0x746cce0e78` | `libcymod+0x4de78` | `0x130f70` |
| 2 | `attack writeback update` | `0xc02a9f0` | `0xc0269f0` | VA `0x737c8449f0` → `0x746cce145c` | `libcymod+0x4e45c` | `0x130f80` |
| 3 | `invincible upstream` | `0x11521138` | `0x1151d138` | VA `0x7381d3b138` → `0x746cce12c8` | `libcymod+0x4e2c8` | `0x130f78` |

（运行时 VA 是该次进程 ASLR 结果，只作本次证据；跨启动稳定的是 **RVA + 指纹**。）

> 复核修正：此前轮次把 `0x11521138` 记作「攻击倍率/写回」、把 `0x10a05354` 记作「无敌」，均不对。
> 以运行时跳转桩目标 + mod 自述描述表为准（上表）。

### 3.4 handler 行为（反汇编确认）

- `0x4de78`（multi attack）：入口 `ldr x26,[0x130f70]`（原函数指针），为空直接收尾；
  之后解析参数并按次数循环回调原函数（`0x4e250–0x4e28c`：`w20` 从 0 到 `w27`，`blr x29`，
  `x29` 即取回的原函数指针）⇒ 「多次攻击」= 同一调用重复 N 次。
- `0x4e2c8`（invincible upstream）：`ldr x24,[0x130f78]`；解析事件字段与 `0x85`（=133，
  即伤害事件位）比较；命中分支打日志
  `invincible blocked: currentActor=%u eventType=133`（串 `0xe75d7`），未命中 `blr x24` 调原函数；
  另有 `ldarb [0x130f38]` 开关 + `[0x130f3c]` 原子计数（防刷屏/限流，用途待确认）。
- `0x4e45c`（attack writeback update）：`ldr x8,[0x130f80]`，非空先 `blr x8` 调原函数，
  之后从 `0x4e494` 起走自己的写回逻辑（配套串
  `attack multiplier state: enabled=%d value=%d currentActor=%u …` `0xe7500`）。

### 3.5 与斌哥路线差异（为什么不能按斌哥路径）

| 维度 | 斌哥包 | 池鸳改包（本样本） |
|---|---|---|
| 特征 so | `libSDKloading.so`/`libtoolChecker.so`/伪装 so | `libChiy.so`/`libcymod.so`/`libmain.so`/`libxhook.so` |
| 菜单来源 | 远程 HTML（myqcloud）+ `com.android.support.*` Java 桥 | 运行期生成（本轮从 `.bss` dump 抓取），JNI 桥 `Java_com_chiyuan_support_Main2_bdbb` |
| 玩法实现 | 壳内自带开关 + memdiff 提取 | 磁盘不改，运行时指纹闸门 + 12B 跳转桩 + handler 回调原函数 |
| 提取方法 | 磁盘 vs 内存 diff / JS 注入 | **指纹表 + 运行时页 dump + handler 反汇编**（本轮路线） |

## 4. 防御/加固与校验点（初步，待官方原版对照）

### 4.1 已实测事实

1. 改包为**第三方重签名**且 `debuggable=true`、`extractNativeLibs=true`（aapt 实测）。
2. APK 内带一整套保护/风控 so：`libtersafe2.so`(5,609,568 B)、`libtoyger.so`、`libthemis.so`、
   `libaliyunaf.so`、`libmsaoaidsec.so`、`libfacedevice.so`、`libzkfv_tj.so`、`libAPSE*.so`、
   `libtapsdkcore.so` 等；**本进程 maps 里一个都没加载**（`rg` 0 命中）；
   实际加载的只有 `libil2cpp/libunity/libChiy/libcymod/libmain/libAkSoundEngine/libcri_*` 等。
3. `libtersafe2.so` 在 APK 内的时间戳是 **2026-09-10 11:41:16**，其余官方库是 2026-08-22 批次
   ⇒ 疑似池鸳替换过（TP2 导出齐全：`tp2_sdk_init_ex` 等；`tp2_sdk_init` 是薄壳）。
4. Java 侧 `classes7/com/tencent/tp/TssSdk.smali:194` 用 `System.loadLibrary` 加载的库名
   经 `np/protect/*->n(I)` native 解密；`classes4/com/tencent/tersafe2/TP2Sdk.smali` 是转发桩。
5. `libil2cpp.so` 磁盘字节在 4 个候选点全部保持原始（逐字节比对过）⇒ 改包在**文件完整性面**干净；
   3 处 hook 全在运行时内存页（页权限改完还恢复）。
6. `libcymod.so` 导入表只有 `dlopen/dlsym/dl_iterate_phdr/mmap/mprotect/pread64/pthread` 等，
   **无 ptrace、无 signal 反调试陷阱**；反调试能力串（`debugger=%s`、`is_root=%d`、`emulator_name=`）
   都在**未加载**的 `libtersafe2.so` 里。
7. `libChiy.so`（JNI_OnLoad `0x3b064`）控制流平坦化，本轮未解；是签名校验绕过/注入的疑似主逻辑。

### 4.2 推断与未证实项（NOT PROVEN）

- **保护 so 为什么没加载**：是池鸳拦掉了初始化，还是 3.2.0 在这台设备/这条流程本来就不加载，
  需要官方原版同机冷启动日志对照才能定案。
- **签名校验怎么过的**：可能在 `libChiy.so`/`np/protect`，也可能因为 TP2 没加载而没有校验在跑；
  本轮没有拿到直接证据。
- **`libtersafe2.so` 是否被替换/阉割**：时间戳是线索，必须官方包对比（大小/md5/exports/关键函数）。
- 第 2/4 条闸门站点（`0x10a05354`、`0x16631314`）的实际用途未确认。
- `libil2cpp.so`/`global-metadata.dat` 是否与官方一致：待官方包对比（改包 metadata 为 `MHY` 加密）。
