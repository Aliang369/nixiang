## 0. 本轮最重要的两条修正（会推翻/收窄既有口径，先看）

### 0.1 FDE 函数边界表解析有 bug（必须修，否则函数归属全错）

`04_scripts/绝区零/version_relocate/ehtool.py`（及 `xref.py`）把 `.eh_frame_hdr` 的二分查找表条目
当作**绝对地址**使用，但该表实际编码是 **`tbl_enc = 0x3B` = `DW_EH_PE_datarel|sdata4`**，
`datarel` 基址 = `.eh_frame_hdr` 段自身 VA = **`0xbd82a8`**。正确公式：

```
func_start = 0xbd82a8 + raw_entry      # 旧实现直接用 raw_entry
```

【实测佐证】表头首 32B `011b033b ccb0cd00 e3b51900 b806d203 ...`：
`ver=1, ehptr_enc=0x1b, fde_cnt_enc=0x03, tbl_enc=0x3b`，`fde_cnt=1684963`；
第 0 条 `raw=0x3d206b8` → `0x3d206b8+0xbd82a8 = 0x48f8960` = 可执行段首地址（分毫不差）。
修正后表范围 `0x48f8960 … 0x1bfa4820`，共 1,684,963 条。

【实测佐证】修正后抽样 20 个 start，绝大多数是标准序言（`sub sp,sp,#..` / `str x30,[sp,#-..]!` /
`stp x30,x19,[sp,#-0x10]!`）；且已知锚点**精确落在函数首**：

| 锚点 RVA | 是否 = FDE 起点 | 下一条 FDE 起点 | 首指令 |
|---|---|---|---|
| `0xa04a370` | ✅ | `0xa04a3c0` | `stp x30, x19, [sp, #-0x10]!` |
| `0xa04a3c0` | ✅ | `0xa04a410` | `stp x30, x19, [sp, #-0x10]!` |
| `0xa04a410` | ✅ | `0xa04a418` | `ldrb w0, [x0, #0xb8]` |
| `0x12118318` | ✅ | `0x1211849c` | `stp x30, x21, [sp, #-0x20]!` |

⇒ **凡是历史上用 ehtool 直接吐出的「函数起点 / 长度」都要重算**；用 `disasm_so.py` 逐字节核对过
的站点 RVA（如 0x12118318、0xa04a370）本身没问题，不用动。
修正后的实现见本文 §7 `fde.py`（11 行），本轮所有函数归属都用它。

### 0.2 `str w,[x,#0xA0]` / `+0xA4` 的写点绝大部分不是实体字段，而是 `List<T>` 内部布局

【实测】`RVA 0x5497a88`（List.Add 型函数）完整语义：

```
0x5497af4  ldr  w8, [x26, #0xa0]          ; _size
0x5497b00  ldr  w9, [x26, #0xa4]          ; _version (或 capacity)
0x5497b0c  cmp  w8, w9
0x5497b10  b.hs -> 0x5497b3c              ; 满则 EnsureCapacity(0x51eda5c)
0x5497b14  ldr  x9, [x26, #0x98]          ; _items 数组
0x5497b24  stp  x20, x24, [x8]            ; 写 16B 元素
0x5497b2c  add  w8, w8, #1
0x5497b30  str  w8, [x26, #0xa0]          ; _size++
```

即 **`+0x98 = items 指针`、`+0xA0 = _size`、`+0xA4 = _version`** 是 il2cpp `List<T>`/`Dictionary` 的
标准三件套。本轮全 so 命中：

| 扫描 | 数量 | 说明 |
|---|---|---|
| `str w?,[x?,#0xA0]` 站点 | **1,826** | 与上一轮统计完全一致（交叉验证通过） |
| 含该站点的 FDE 函数 | **1,286**（修正前误报 1,359） | |
| `str w?,[x?,#0xA4]` 站点 | 1,004 | |
| 同时写 0xA0 与 0xA4 的函数 | **132** | 修正前（错表）算得 87；修正后 132，**大多数是 List.Add/Insert/Capacity 族** |
| 其中 base 寄存器是 `sp`（栈槽，非对象） | 大量 | 例：`str x30,[sp,#0xa0]`、`str w8,[sp,#0xa0]`；**必须按寄存器名过滤** |

⇒ 上一轮「`str w,[x,#0xA0]` 1826 处/332 函数太泛」的判断成立且原因已定：
**0xA0/0xA4 在 3.3.0 里没有区分度**，把它当「HP/ATK 字段签名」做筛子是错的。
（这**不**否定实体确实有 `+0xA0`/`+0xA4`，只说明不能用它做全局筛。）

## 2. 目标 1：id → 实体解析链

### 2.1 主候选：`0x16de0acc`（置信度：中高）【实测 + 推断】

函数边界 `0x16de0acc … 0x16de0cfc`（长 0x230，140 指令）。签名与语义：

```
; x0 = manager(this)，w1 = id
0x16de0ae4  ldr  x8, [x0, #0x10]          ; A = this->+0x10
0x16de0af4  ldr  w9, [x20, #0x48]         ; this->+0x48  (版本/缓存计数)
0x16de0af8  ldr  w8, [x8, #0x18]          ; A->count
0x16de0afc  cmp  w9, w8 ; b.eq -> 0x16de0b0c
0x16de0b04  ldr  x8, [x20, #0x20] ; cbz -> 0x16de0b18
0x16de0b0c  ldr  x8, [x20, #0x40] ; cbnz -> 0x16de0b28
0x16de0b18  bl   #0x16ddfdf8              ; 懒初始化 / 重建索引
0x16de0b28  ldr  x0, [x20, #0x38]         ; this->+0x38  (主查表容器)
0x16de0b30  mov  w1, w19  (id)
0x16de0b38  bl   #0x1016a3b4              ; TryGetValue(id, out) / ContainsKey
0x16de0b40  tbnz w0, #0 -> 0x16de0b94     ; 命中即返回
0x16de0b44  ldr  x21, [x20, #0x40]
0x16de0b54  bl   #0x13fe8a5c              ; GetIndex/IndexOf(id) -> w0
0x16de0b58  tbnz w0, #0x1f -> 0x16de0bac  ; <0 走慢路径（哈希探测 0x1759e488）
0x16de0b64  ldr  w9, [x8, #0x18] ; cmp w0,w9 ; b.hs -> 越界抛
0x16de0b78  add  x8, x8, w0, uxtw #4          ; 条目 = base + idx*16
0x16de0b80  ldrsw x8, [x8, #0x2c]             ; 取到内部索引
0x16de0b8c  add  x8, x9, x8, lsl #3
0x16de0b90  ldr  x21, [x8, #0x20]             ; **返回对象**
0x16de0ba8  ret
```

**判据**：`w1=id` 入参 → 容器 `+0x38` 上 `TryGetValue` + `IndexOf` 双路 → 条目数组 `base+idx*16`
→ `ldrsw [..+0x2c]` 二级索引 → `ldr x21,[base+idx*8+0x20]` → 返回对象；全程带版本检查
（`+0x48` vs `+0x10->+0x18`）与越界检查。这是标准的 **`容器.Get(int id) → object`** 形状。

**调用规模**【实测】：全 so `bl` 到 `0x16de0acc` 的站点 **728 处**（含 veneer 解析）；
其中紧邻前面是 `ldr w1,[x?,#0x3C]`（把 id 塞进 arg1 的惯用法）的有 **92 处**，
调用方散布在 `0x804…`、`0xa6b…`、`0xd38…`、`0xedc…`、`0x11d…` 等**十几个互不相关的模块**
——符合「全局实体查表」的分布，不像某个类的私有方法。

**保留意见**：在该函数的 728 个调用方里做特征统计，**没有一处在同函数内读 `+0xA4`**
（`ldr_a4 = 0`，见 §3.2）。如果 `0x16de0acc` 真是 actor 表，那么「伤害扣血」的函数应当
既查表又读攻击——目前没看到。可能原因：① 攻击值通过另一个属性系统（属性快照）取，
不落在实体 `+0xA4`；② `0x16de0acc` 是另一类 id 表（如 buff/关卡对象）。
⇒ 标 **中高**置信「id→对象解析」，**中低**置信「就是伤害路径用的 actor 解析」。

## 3. 目标 2 / 3：HP 写入函数

### 3.1 方法（可复现）

1. numpy 全 so 扫 `str w?,[x?,#0xA0]`（编码 `0xB9000000 | imm12=0x28<<10`）与 `+0xA4`（imm12=0x29）；
2. 用**修正后**的 FDE 把站点归到函数；
3. 三重过滤：**剔除 base=sp**、剔除 `List<T>` 三件套（同函数同时出现 `+0x98/+0xA0/+0xA4` 且带
   `cmp`+`b.hs`+`EnsureCapacity` 调用）、要求「同一 base 既读又写 0xA0」（read-modify-write）；
4. 对站点前 9 条指令做「值是否被计算」判定（`sub/subs/csel/bic/fmul/fsub/fcvt/sdiv` 且目标寄存器
   = 被存寄存器），再人工读窗口。

结果：1826 个写点 → 1,286 函数 → **RMW+异 base 读 ATK 的只剩 20 条**（剔除 sp 后）；
「计算型」写点 **123** 条。逐条读过之后**没有一条能被证实是实体扣血**，理由见下。

```
0x5a5a45c  str  w11, [x0, #0xa4]
0x5a5a474  ldr  w8, [x19, #0x18] ; cmp w8,#1
0x5a5a480  csel x8, x22(0x50), x21(0x58), eq

```

⇒ 入参语义（A）：**实体/组件指针 = x0**，**数值 = w1**（不是「伤害值」，而是「目标值/百分比」，
因为先与上限 `+0x9c` 取大）；**被写字段 = +0xA4（当前值）、+0x98（护盾层）**；
伤害 delta 由 `(目标-上限) * [[x0+8]+0]` 得到。

### 3.3 交叉验证（目标 3）结论

- 「附近有 fmul/伤害运算」的写点：123 条，人工读前 12 条**全部**落到非伤害用途
  （星级夹逼、物理向量、计数器自减、属性拷贝）。
- 「调用链能连回 0x12118318」：入口的 6 个 callee 已全部解析并逐个读反汇编
  （`0x12bfec70` / `0x144d9e84` / `0x144d3e10` / `0x4c5aa38` / `0x6106acc` / `0x60f3c70`），
  **没有一个**包含 `+0xA0` 写入（`0x6106acc` 是哈希/校验型运算，`0x60f3c70` 是异常收尾）。
  ⇒ 从 0x12118318 出发到 HP 写入之间，**在静态上断了**（中间必然隔着委托体/接口派发，
  委托目标是运行期注册的，静态不可解析）。
- 唯一没断的是 `0x16de0acc`（id→对象）——但它与 HP 写入之间同样缺一环。

## 4. 未闭环项（必须动态验证才能定案）

1. **`0x12118318` 到底是不是伤害事件入口**：其 6 个 callee 全是簿记/日志/校验形状，
   HP 写入不在其中。「伤害事件」这个定性依赖上一轮的实测观察，本轮静态无法复现。
2. **`0x16de0acc` 的 `this` 是什么类型**：728 个调用点里 `x0` 都不是直接从全局槽装入
   （10 指令内 `adrp+ldr x0` 命中 0/728），说明 manager 来自更深的字段链。找到它才能确认
   「实体表」并枚举该 manager 的全部方法（HP 写入很可能就在其中）。
3. **`0x1E725000`**：本轮未能在可执行段里找到稳定的实体表形状（不是 `Dictionary`/数组），
   暂不使用，建议后续单独做一次「该全局 → 引用点 → 容器初始化」的定点分析。
4. **HP 字段到底是不是 `+0xA0`**：§0.2 证明 `+0xA0/+0xA4` 在全局无区分度；getter 族的
   `+0xA0`（默认 1）/`+0xA4`（默认 999）也可能是「配表默认值」而非实战 HP。
   建议先用动态手段确认 get_hp 返回的确切字段值变化（见 §6 步骤 2）。
5. 入口里 `0x1E5D4208` 单例的具体类型与 `+0xCB` 语义未定名。

### 10.1 HPW-B `0x1aa964b0`（0x2b8 / 174 条）

签名（实测寄存器映射）：`f(x0=容器宿主, x1=记录A, x2=记录B)`；序言即 `mov x21,x0 / mov x20,x1 / mov x19,x2`。

**关键：`+0xA0` 在这条链上是「数组下标」，不是 HP。** 判据链：

```
0x1aa964d8  ldr   x8,  [x21, #0x18]      ; 容器 C = *(x0+0x18)
0x1aa964e0  ldrsw x9,  [x20, #0xA0]      ; x9 = A->+0xA0   ← 有符号下标
0x1aa964e4  ldr   w10, [x8, #0x18]       ; w10 = C->count
0x1aa964e8  cmp   w10, w9
0x1aa964ec  b.ls  #0x1aa96764            ; 越界 → 抛 IndexOutOfRange(0x1a9fcd4c)
0x1aa964f4  ldrsw x11, [x19, #0xA0]      ; x11 = B->+0xA0（同一下标语义）
0x1aa96500  ldr   x8,  [x8, #0x10]       ; items 数组
0x1aa96504  add   x9,  x8, x9,  lsl #3   ; &items[A->idx]
0x1aa96508  add   x8,  x8, x11, lsl #3   ; &items[B->idx]
0x1aa9650c  ldr   x22, [x9, #0x20]       ; 条目对象（数组头 0x20）
0x1aa96510  ldr   x23, [x8, #0x20]
```

`0x1aa96518–0x1aa96694` 全是**双向链表摘除/拼接**的手工展开（反复 `ldp/stp` 搬 `+0x10` 前驱、
`+0x18` 后继、`+0x20` 挂载，并 `str xzr,[+0x28]` 清零）。

写 `+0xA0` 的指令（全部是「把下标标成 -1 ＝ 空闲」）：

| RVA | 原始字节 | 指令 | 语义 |
|---|---|---|---|
| `0x1aa966ac` | `8ca200b9` | `str w12,[x20,#0xA0]` | w12 = `mov w12,#-1` |
| `0x1aa966b0` | `6ca200b9` | `str w12,[x19,#0xA0]` | 同上 |
| `0x1aa966e4` | `49211429` | `stp w9,w8,[x10,#0xA0]` | 回填 (A 原下标, B 原下标) |

**判定**：**槽位/链表管理**（分配 → 摘链 → 两条记录下标标 -1 → 必要时把旧下标还回另一宿主）。
`+0xA4` 在本函数只出现 `ldr w8,[x20,#0xA4]` / `ldr w13,[x19,#0xA4]` + `cmp w13,#1`，是**状态字**，
不是攻击力。**无算术、无 fmul、无伤害值。**

### 10.2 HPW-C `0x1aa95b14`（0x554 / 341 条）

签名：`f(x0=宿主, x1=记录A, x2=记录B, x3=上下文, x4=上下文)`；
序言 `cbz x1 / mov x19,x2 / cbz x2 / mov x21,x4 / mov x22,x3 / mov x20,x1 / mov x23,x0`。

```
0x1aa95b44  ldr w24, [x19, #0xA0]     ; B->+0xA0
0x1aa95b48  ldr w10, [x1,  #0x48]     ; A 的状态/所有权
0x1aa95b4c  ldr w12, [x19, #0x48]     ; B 的状态/所有权
0x1aa95b54  ldr w8,  [x20, #0x54]     ; 组号
0x1aa95b58  ldr w9,  [x19, #0x54]
0x1aa95b60  cmp w8, w9 ; b.ne 0x1aa95c08   ; 组不同 ⇒ 走镜像块
```

写 `+0xA0` 的指令（三处置 -1 + 一处 8 字节整体交换）：

|---|---|---|---|
