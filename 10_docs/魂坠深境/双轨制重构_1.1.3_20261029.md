# 魂坠深境 1.1.3「双轨制」重构（2026-10-29，Windows / 雷电）

> 会话：win 端，设备＝雷电模拟器 `emulator-5554`（`ro.serialno=00cd89da`，Android 14 / x86_64 / `ro.build.type=user` / `ro.debuggable=1` / 有 su）。
> 用户口令：「我在雷电模拟器上面安装了原版，你直接拉去改成正式包吧，**用新方法改**」；装机前二次确认选「直接卸载重装，不备份」。
> 前置问答：用户先问「雷电上装的魂坠深境是不是旧版签名伪装过的 TapTap 校验、为什么有人用还会提示【tapsdk 包名】」，本轮的动机就是把这套旧法换掉。

## 1. 为什么必须重做（旧包取证）

对雷电里**旧星空包**（md5 `3c219aaec75b83ea7b7d00dbd3450abf`，即 mac 端 2026-10-28 出的 1.1.3）做 dex 级实测：

| 项 | 实测 | 判读 |
|---|---|---|
| `manifest@appComponentFactory` | `com.starry.magic.sign.SignSpoofAppComponentFactory` | 旧法挂载点（该类已于 2026-10-28 删除） |
| `classes5.dex` | 含 `Lcom/starry/magic/sign/SignSpoof;` / `SignSpoofAppComponentFactory` / `TapLoginForceWeb` / `PKG_WHITELIST` / `HZSJ_CERT_B64` / `exemptHiddenApis`(×8) / `setHiddenApiExemptions` / `VMRuntime` / `sPackageInfoCache` | 旧法＝隐藏 API 豁免 + 换 `PackageInfo.CREATOR` + 按包名回灌证书 |
| 新法特征 | `SignatureKiller` / `KillerApplication193` / `bin.mt.signature` / `mCreators` / `sPairedCreators` 全 0 | 新法完全没用 |
| 缺什么 | 未复位 `Parcel.mCreators` / `sPairedCreators` | 只换 CREATOR 的已知缺口（= 二启失败的根因，见 SF3 2026-10-29 实测） |

「有人用还提示 tapsdk 包名/签名」的机制（对应用户口中的【tapsdk 包名】）：
报错文案是 `TapInitializer: 应用的包名、签名（certificate fingerprint）未在 TapTap 开发者中心正确配置` → `JuHeSDK CONFIG_ERROR`；**包名是官方原包名，坏的是签名一项**。四条成因：
① `SignSpoof` 依赖隐藏 API 豁免（`exemptHiddenApis`），Android 14 **user 版**真机必失败（蛋壳战机 1.2.1 先例、小米实测 `failed`），只有雷电这类 `ro.debuggable=1` 实例能过 ⇒ 别人的手机上伪装根本没装上；
② 只换 CREATOR、不复位 `Parcel.mCreators`/`sPairedCreators` ⇒ 二次启动仍读到改签证书（正中靶心2 / 无限升级同症状）；
③ 证书表按包名 hardcode（`HZSJ_CERT_B64` 只对 `com.chillyroom.containerofsoul.yw`）⇒ 多开/分身/改包名版取不到表项；
④ 时序/跨进程（推断）。

## 2. 本轮方案（双轨制，2026-10-29 口径）

| 轨 | 内容 | 落地 |
|---|---|---|
| **B 签名/完整性** | 运行时签名替换：MT `bin.mt.signature.KillerApplication193`（`<clinit>` 内换 `PackageInfo.CREATOR` + 清 `PackageManager.sPackageInfoCache` + `Parcel.mCreators` + `Parcel.sPairedCreators`） | 新增 `classes6.dex`（13,720 B）；由 `StarryAppComponentFactory.instantiateApplication` 里 `Class.forName(KILLER_CLASS, true, cl)` 触发 |
| **A 登录方式** | 静态改包：TapSDK client-SSO 的 action 常量等长就地替换 `com.taptap.sdk.action` → `com.taptap.sdk.act1on` | `classes3.dex` 里 `com/taptap/sdk/login/impl/data/model/Actions$CN.getAction()`；dex 头 `signature`/`checksum` 已重算，尺寸不变（10,429,708 B） |

**与暗影格斗3 1.45.3 的差别（有意偏离，已在本轮验证）**：SF3 用「改 `androidx/multidex/MultiDexApplication.super` 挂 killer」，本轮改为 **appComponentFactory 触发类加载**。理由：① killer 的安装动作全在 `<clinit>`，`Class.forName(...,true)` 等价且**更早**（`instantiateApplication` 早于 Application `attachBaseContext/onCreate` 与一切 Provider）；② **官方 dex 一个字节都不用动**（SF3 那条要 baksmali/smali 整份 classes5.dex）。实测 3/3 冷启通过，见 §5。
killer 内 `killOpen(...,"","","")` 三参为空串 ⇒ 立即 `goto` 返回，属无害空操作。

| killer dex | `classes6.dex` 13,720 B（`07_patched/魂坠深境/surgical/killer_smali`，父类已改 `android.app.Application`） |
| so | `libstarry_magic.so` **199,096 B** md5 `14c4161e46e125177eaaf8bb88632314`（Windows NDK 27 现编；`STARRY_BUILD_EPOCH=1793213570`） |
| 正式包 | `08_output/魂坠深境/魂坠深境_1.1.3_starry-newmenu-releaseSigned.apk`（939,258,753 B，md5 **`114217f57bb514ea8df6eedfa97bc7fe`**，`CN=StarryMagic`） |
| 包内回执 | `orig=2455 copied=2450 replaced=2(manifest,classes3) added=4(classes5,classes6,libc++_shared,libstarry_magic) dropped_sig=3`；passthrough CRC 2450 条全过 |

**so 体积差异（必须记账）**：mac 端 1.1.3 的 so 是 2,224,328 B，本轮 Windows 现编只有 199,096 B。`llvm-readelf` 对比：`.text` 0x20fa4 vs 0x20fb4、`.rodata` 0x4088 两者**相同**，差异全在 `.data`（旧 so 0x1EEC28≈2.0 MB，内含 `-----BEGIN CERTIFICATE-----` + `MZ` + `BSJB`，即 无限升级 `WxsjPatchedDll.a` 的 patched .dll 载荷）。根因＝`Android_hzsj.mk` 复制粘贴带进来的 `wxsj_dll` 预编译库（该 `.a` 未被 git 跟踪，只在跑过 wxsj 构建的机器上存在）。本轮已加 wildcard 守卫（有文件时行为完全一致），Windows 侧因此少链了这 2 MB 与 hzsj 无关的载荷；链接成功且 3/3 冷启菜单/授权/功能链正常，判定为死重量（若后续出现 so 侧异常，第一嫌疑点回查此处）。

## 7. 未做 / 风险 / 下一步

- **L3 已通过（2026-10-29，用户原话「都没问题了」）**：登录与六项功能（秒杀/无敌/无限卡牌/无限金币/无限魂晶/自动胜利）用户实测正常；机器层 3 次冷启另证「不弹签名错、菜单出、不崩」。
- **硬约束 #1 的真机回归未做**：小米 `96f0d883` 在线但本轮未装（异签仍要卸载重装，且 1.1.3 官方包在那台机器上是否有存档未核）。雷电 + 真机同包同签直装，按 #1 应补一次真机回归。
- **`10_docs/魂坠深境/路线锁定.md` 缺口**：挂点五步门禁第 5 步要求该文件填满才准装机，本游戏一直没有该文件；本轮 native 挂点/功能链与 1.1.3 基线逐字未变（so 由同一 `Games/HzsjMod.cpp` + `HzsjEntry.cpp` 现编，六条菜单串与 `[Hzsj] ready` 均已实测），属结构性缺口而非行为偏离，建议下轮补齐。
- **待观察**：so 的 2 MB `.data` 载荷差异（§3）；若某台设备出现 so 侧异常先回查。
- **框架层遗留（勿在本轮扩散）**：`wxsj_dll` 残留散落在 ~40 个 `Android_*.mk` 里，其它游戏在 Windows 上仍会因缺 `.a` 而构建失败；`framework_entry_audit` 的 [D] 看不到 per-game mk。两条都已登记候选经验。
