## 4. 本轮核心：两轮重构（用户实测反馈驱动）

### 4.1 货币：直写 999999 会被判作弊 ⇒ 值域锁 999 + 不足才回填

**静态结论（IL 证据，`Assembly-CSharp.dll` 反编译）**

- 局内金币/魂晶的**合法上限就是 999（0x3E7）**，四处独立钳制：`ChangeCoinAction::Update` `Mathf.Clamp(coin+Δ, lb, 999)`（IL 45917-45940）、`ChangeCrystalAction::Update`（46031-46059）、`SetCoinAction::Update` `Mathf.Min(value,999)`（54004-54040）、`SetCrystalAction::Update`（54076-54110）。全 IL **不存在 999999 这个整数常量**。
- 作弊判定**在服务端**：结算 `GameRecord::TriggerResolve → GameOverRequest/GameOverResult → ApplyServerSettlementRewards`，客户端只弹 `GameOverSettlementError::IsBlocked` 的两个码：**106001=作弊**、106007=频率。
- 旧写法必然出事的机制：任何一次货币动作都把余额 `Clamp(旧+Δ, …999)` 并把 delta **重算**为 `999−999999=−999000`，经 `GameEventManager::TriggerCoinChange(value, delta, notCountAsGain)`（IL 505039-505066）进事件链随结算上报 ⇒ 服务端 106001。这与用户「金币增加 999000/999999、结算有问题」的现象一一对应。

**改法（`HzsjMod.cpp` 两处）**：`CURRENCY_VAL` 999999 → **999**；`WriteCurrencyAt()` 先 `ReadProtectedInt` 读现值，**coin / crystal 各自独立、仅 `cur < 999` 才回填**（并发日志 `cap=%d`、`CURR_REFILL# coin a->b cry a->b`）；回读失败按旧行为兜底打 `rdfail`；顺带堵掉「偏移=0 时往对象头写三元组」。

### 4.2 无敌：999999 会污染承伤统计 ⇒ 写 `health = maxHealth`

- 血量域**没有常量上限**（所有写入点是 `Min(值, maxHealth)`/`Clamp(值,0,maxHealth)`，`0x3e7` 只出现在货币四件套），合法域 `CombatValueLimit.Max=10,000,000` ⇒ 999999 不会被切。
- 但受击时游戏算 `clamped=Min(health+Δ, maxHealth)` 并把 `V=Max(clamped,0)−旧health ≈ maxHealth−999999 ≈ −99.9万` 记进 `InGameRecorderManager::RecordPlayerRealHealthDamage`（塔模式 `RecordAppliedDamage`）⇒ 统计/成就/回放被污染，同样进结算数据。
- **改法**：先读 `g_offBftMaxHp` 并解码，守卫 `0 < maxHp ≤ 10,000,000`（异常打 `INV_SKIP`），再读 `health`，**仅 `health < maxHp` 时写 `health = maxHp`**（每 tick 200ms 执行，无额外节流），日志 `INV#… health=<maxHp> maxHp=<maxHp>` 与 `INV_REFILL#… health a->b (maxHealth)`。`DMG_CAP`、秒杀、卡牌、自动胜利、货币逻辑零改动。
