## 2. 时间的坑（为什么拖了 15 小时）

### 2.1 方法 hook 是死路，但发现了太晚（最大浪费）
- 1.0.5 的成功模板是「hook 公共 invoke 跳板改参数」。1.1.0 沿用 → 10 版循环。
- **真相**：1.1.0 签名桥只在 AOT↔热更边界走；`DamageAction.Update` 是虚调用，另有派发入口；Execute hook 拦 200 万次调用也看不到目标方法。**方法 hook 对该版本结构性失效**。
- **触发器失效**：规则说「2 次验证不收敛必须换路线」，实际 v5 零命中时就该停，却修到 v13（修观测代码而不是质疑路线）。

### 2.2 黑盒观测替代不了源码
- 探针/Execute 采样都是黑盒猜：猜方法名、猜参数槽、猜签名。每个假设一轮装机（5–40 分钟）。
- **热更 DLL 反编译 30 分钟给出全部答案**（字段名、偏移语义、调用链、CD 判定是哪个字段），且零装机成本。

### 2.3 按名解析的连环坑
- `FindClassExact("Item")` 撞杂类（type/data 两字段的同名类）
- `il2cpp_class_get_field_from_name` 对部分热更类返回 0
- `ClassFromName` + image 名匹配：AOT 与热更程序集**同名**（Assembly-CSharp.dll），`strstr` 会误中 firstpass
- **解法（v19 自学习）**：从活对象反查类 → 类上迭代字段拿偏移。实例驱动 > 名字驱动。

### 2.4 工程杂音（每个 5–20 分钟，累计 ~1.5h）
- heredoc `$(...)` 展开、mk 切换脚本两次修正、`:=` 清掉 += 追加、磁盘写满中断两次（build base 882MB × N 份拷贝）、日志大写十六进制正则、`g_clsItem.store()`（void* 无 store）。

### 2.5 语义确认靠人肉循环
- 秒杀 health=0 引发「有动作就死」（CheckDeath 事件连动），v15 才修正为 1——**游戏机制问题应在出包前问用户/读源码确认**（源码里 `IsDeathPendingEnemy`/`CheckDeath` 本可提前看出）。

## 3. 下次版本更新（1.1.0 → 1.1.x）的标准动作（预估 1–2h）

1. 拉原包 + `files/Asset/hotfix` → UnityPy 解 DLL → ilspy 反编译（**第一步就做，30min**）
2. diff 热更 DLL（ilspy 输出 diff 或 C# 源码 diff）：字段名/偏移语义/判定方法是否变化
3. 无变化 → 改 OTA patch.json 字段偏移（甚至零代码，只改 json）
4. 有变化 → 按 `对齐1.1.0_探针抓桥_20260903.md` §8.3 的链路表更新 HzsjMod.cpp 直写段
5. 换 so 重签装机（手机现装包 pull 回来当 base，5 分钟）
6. 实机四功能验证 + 归档
