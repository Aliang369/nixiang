## 0. 一句话结论

**客户端绕不过支付。** 物品发放 100% 在服务端：客户端所有支付回调只驱动 UI 与防沉迷计数，收到 SC2201 也只是把 Promise 置成功；客户端没有任何一条 addItem/发奖代码。唯一能改的客户端变量是"付多少钱"（amount 由本地配置表算出），最多做到「0.01 元买全档」，做不到 0 元。

---

## 1. 支付 SDK 是谁

**喜扑 XiPuSDK（com.xipu.msdk），H5 收银台，不是 TapTap 支付、也不是支付宝/微信 SDK 直连。**

证据链（smali）：

| 位置 | 证据 |
|---|---|
| smali_classes6/com/wbxxm/qoxmcc/AppActivity.smali:289 callXiPuRechange | XiPuSDK.getInstance() → XiPuSDK.pay(Activity, RoleModel, HashMap) |
| smali_classes3/com/xipu/msdk/BXiPuSDK.smali pay(Activity,RoleModel,HashMap) | 读 "amount"，补 app_id/accesstoken/server_id/role_id/timestamp，算 sign = Md5("accesstoken=…&amount=…&app_id=…&timestamp=…\|\|\|appsecret=…")，再 NetworkUtil.makePayOrder |
| smali_classes3/com/xipu/msdk/util/NetworkUtil.smali makePayOrder | GET XiPuConfigInfo.MAKE_ORDER_URL |
| smali_classes3/com/xipu/msdk/config/XiPuConfigInfo.smali | 路径常量 "h5pay/make_order"、"h5pay/query_order"、"h5pay/query_pay_report"、"pay/trades" |
| smali_classes3/com/xipu/msdk/util/NetworkUtil$11.smali onSuccess | 解析 out_trade_no，随后 new NetworkUtil$11$1(...) 拉起支付页 |
| smali_classes3/com/xipu/msdk/ui/PayDialog.smali | WebView 对话框（xp_NavigateDialog），关闭/返回时 NetworkUtil.queryPayOrder(out_trade_no) → payDone() |

**结论**：用户看到的"支付页面"＝喜扑 PayDialog 的 H5 收银台（支付宝/微信在 H5 内部，SDK 不直接调起原生支付）。支付结果由**喜扑服务端** h5pay/query_order 轮询确认后才回调成功 —— 本地伪造"已支付"没有意义。

## 2. 完整支付链路（客户端每一步做了什么）

### 2.1 JS 侧入口：PayDataHelper.sendRecharge
index.js 行 **873** / 偏移 **2043456**（模块 chunks:///_virtual/PayDataHelper.ts）

原文（缩写但保留判据）：

~~~js
e.sendRecharge=function(e){
  return "XI_PU"==d.player.platform ?  /* ①真支付 */
         ( m ? /* ②GM模拟充值 */ : /* ③报错 平台不支持充值 */ )
}
~~~

**分支顺序是硬编码的 if/else 链**：只要 player.platform === "XI_PU"，**永远走①**，m（=IsGmLogin）这个条件**根本不会被求值**。这是 GM 开关"看起来没生效"的第一层原因。

### 2.2 ① 真支付分支

1. w(e) 防沉迷校验 —— AntiAddiction.rechangeCheck（行 101 / 偏移 261316 附近），按身份证年龄判 50/200、100/400 限额；不通过直接 reject。
2. $() 注册两个事件监听：RechargeSdkPaid → D、RechargeFinished → R。
3. **CS2200 下单**：{rechargeId: shopPriceId} → NetEnum.GetRechargeOrderId(2200) → 服务端返回 orderId（10s 超时，超时即"没有拿到订单号"结束）。
4. T(shopPriceId, orderId, ()=>callXiPuRechangeG(shopPriceId, orderId))：启 **90s SDK 超时**（pay_sdk_<orderId>）后调 callXiPuRechangeG 拉起喜扑。

### 2.3 拉起喜扑：NativeAPIMgr.callXiPuRechangeG
index.js 行 **783** / 偏移 **1822461**（模块 NativeAPIMgr.ts）原文：

~~~js
static callXiPuRechangeG(t,e){                    // t=shopPriceId  e=orderId
  if("XI_PU"!==s.player.platform) return !1;
  const n = `${a.getShopPrice(t).price}00`,          // 金额：本地配置表算出来的
        f = `com.iiuyeg.wbxxm.${n}`;                // product_id 也是本地拼的
  p = JSON.stringify({product_id:f, amount:n, callback:e+"#"+t, notify_url:g,
                      role_id:.., role_name:.., role_level:..});
  r.reflection.callStaticMethod("com/wbxxm/qoxmcc/AppActivity","callXiPuRechange","(Ljava/lang/String;)V",p)
}
~~~

- amount 与 product_id **100% 由客户端决定**（XlsMgr.getShopPrice 读本地 shop_price 表，行 **1167** / 偏移 **2599468**）。
- callback = "<orderId>#<shopPriceId>" 一并交给喜扑；notify_url 是自家服务端 https://api.ginkgogames.fun:15003/api/auth/account/xi/pu/pay（VersionConfig.ts 行 1133 附近 XipuNotifyUrl）。

### 2.4 Java/smali 侧

AppActivity.callXiPuRechange(json) → parseJsonToMap → RoleModel.setRoleid/Rolename/Rolelevel → XiPuSDK.pay(ctx, role, params) → 签名 → h5pay/make_order → PayDialog(H5) → 用户支付 → h5pay/query_order 轮询 → payDone() → AppActivity$j.smali：

~~~smali
const-string v0, "NativeAPIMgr.onXIPURechangeSuccessG()"
invoke-static {v0}, Lcom/cocos/lib/CocosJavascriptJavaBridge;->evalString(Ljava/lang/String;)I
~~~

（失败走 AppActivity$k → NativeAPIMgr.onXIPURechangeFailedG()）

### 2.5 回到 JS：成功之后**不会发奖**

- NativeAPIMgr.onXIPURechangeSuccessG（行 783 / 偏移 1823251）：o.emit(c.Type.RechargeSdkPaid)。
- PayDataHelper.D()（偏移 2041144）：只 delete sdkTimer → setStage("等待2201") → 启 **30s 到账超时**（pay_deliver_<orderId>）。**没有加物品。**
- 到账靠服务端推送 SC2201：ConnectMgr 行 **231** / 偏移 **522178**：
  V.setResponeHandler(u.code.NoticeRechargeFinished, ...) → m.emit(y.Type.RechargeFinished, !0, orderId)
- PayDataHelper.R()（偏移 2041797）收到后 → N(order, true, "delivered")（偏移 2042821）：

~~~js
function N(e,t,n){ ... t&&i.updatePlayerDataAfterRecharge(e.shopPriceId), ...
                   t?e.resolve(!0):e.reject(!1) }
~~~

- i 不是物品管理器，而是 **AntiAddiction**（PayDataHelper 的 setter 第 9 个参数 = AntiAddiction）。updatePlayerDataAfterRecharge（行 101 / 偏移 261316）：

~~~js
updatePlayerDataAfterRecharge = function(t){
  const n = XlsMgr.getShopPrice(t)?.price;
  o.player.totalRecharge += n;  o.player.totalRechargeTime = now();   // 只改防沉迷计数
}
~~~

- 各业务弹窗的 .then(...) 也只是：D.setData(本地配置的奖励列表); D.openUI()、sendGetShopInfo(...) 重新拉商店、checkActivityDataChange、close。
  **物品真正的来源**：服务端在发 SC2201 之前就已把物品写进玩家数据，靠常规数据同步落到客户端（与"免广告"CS1602 完全同一套机制）。

> 佐证：全仓搜 RechargeFinished / RechargeSdkPaid 监听者，只有 PayDataHelper + ConnectMgr(协议分发) + NativeAPIMgr(emit)，**无任何模块在支付成功后本地加道具**。

## 3. 为什么 GM 探针没生效（第二层原因）

### 3.1 IsGmLogin 根本不管支付分支，它管**登录方式**

GameStartMgr 行 **375** / 偏移 **885928**：

~~~js
(native) && ( H ? this.showGMLogin() : I.onXIPULogin() )   // H = IsGmLogin
~~~

showGMLogin()（同处）＝ 把登录页换成"账号输入框 + 当前服务器 + 跳过引导开关"，点确定走 ConnectMgr.onLocalLogin(nickName)（行 **231** / 偏移 **509241**）：

~~~js
e.onLocalLogin=async function(e){
  M.player.platform="TEST";                     // 关键：GM 登录把 platform 设成 TEST
  fetch(LoginUrl,{body:JSON.stringify({platform:"TEST",channel:"TEST",account:e,token:"YourToken",...})})
}
~~~

而正常登录 onXIPULoginSuccess → M.player.platform="XI_PU"（ConnectMgr 行 231）。

**player.platform 全仓只有 3 个赋值点**（都在 ConnectMgr）："XI_PU"（喜扑登录）/ "TEST"（GM 本地登录）/ "WEI_XIN"（微信）。

### 3.2 所以「改 IsGmLogin 无效」的准确解释

| 观察 | 解释 |
|---|---|
| 只把 IsGmLogin:!0 打开，但**仍用喜扑账号进游戏**（或登录界面没变） | platform 仍是 "XI_PU" → sendRecharge 走①，**GM 分支是 else-if，永远不可达** ⇒ 点击支付必然 CS2200 + 跳 H5 支付页 |
| 打开后**登录页变成账号输入框**并这样进了游戏 | platform="TEST" → 应弹"模拟充值弹窗"（走 CS1302）。若此时仍跳支付页 ⇒ 说明**改的 jsc 根本没被加载** |
| 只改了 IsGmMenu | 该开关只控制调试窗：initDebugWin() 里 if(!V) return; 之后才给 account_label 绑 open(M.Debug)；与支付无关 |

### 3.3 改动可能根本没生效的头号嫌疑：热更遮蔽

assets/main/index.jsc **在热更清单 build-in.project.manifest 内**（md5 bb5eef90d88063c6333e230abaf412c4），而 main.js 注入了 setSearchPaths(热更目录优先)。若设备上已落过热更，**包内被改的 jsc 会被 writable 目录同名文件遮蔽**，表现正是"改了没反应、游戏一切正常"。

判定方法（下次装机必做）：
1. 看登录页是否出现 GM 账号输入框（出现=改到了）；
2. adb shell ls /data/user/0/com.wbxxm.wbxxm/files/gg-hot-update/assets/assets/main/ 有 index.jsc 即被遮蔽；
3. logcat 看 gg-hot-update / GGHotUpdateInstance 的搜索路径日志。

## 4. 五条绕过路径逐条评估

| # | 路径 | 证据（模块/函数/行号） | 可行性 |
|---|---|---|---|
| **a** | **支付成功回调伪造** | AppActivity$j → evalString("NativeAPIMgr.onXIPURechangeSuccessG()")；JS 侧 D() 偏移 2041144 只启 30s 等待 | ❌ **不可行**。伪造后只会进入"等待 2201"，30s 后 deliver_timeout → 失败提示，**不加任何物品** |
| **b** | **下单金额改写** | callXiPuRechangeG 行 783：amount = getShopPrice(t).price + "00"、product_id = com.iiuyeg.wbxxm.<amount> | ⚠️ **可做，需真机验证**。amount/product_id 全由本地表算，改 XlsMgr.getShopPrice（行 1167）即可让喜扑 H5 收银台显示 ¥0.01；SDK 的 sign 用新 amount 重算，**签名不会失败**。风险：服务端收到喜扑 notify 时若比对金额/**product_id**（product_id 里也含金额）→ 直接判失败。**这是唯一还活着的客户端口子，但只能"少付"，不能"不付"** |
| **c** | **到账 SC2201 伪造** | ConnectMgr 行 231 handler → R() → N() → updatePlayerDataAfterRecharge（AntiAddiction，只改 player.totalRecharge） | ❌ **不可行**。本地 emit RechargeFinished,true 的后果 = 关支付 loading + 本地 totalRecharge 自增 + 弹一个**内容来自本地配置**的奖励弹窗；背包/道具不变，重登即回滚 |
| **d** | **GM recharge 正确触发路径** | PayDataHelper 偏移 2043456 第 2 分支：m(IsGmLogin) → 弹"模拟充值弹窗" → CS1302_PlayerGm {cmd:"recharge",params:[id]} | ⚠️ **可触发但需服务端受理**。正确入口＝IsGmLogin:!0 **且** 用 GM 本地登录（platform="TEST"）。即便走到，发奖仍靠服务端受理 CS1302（_home_debug 里 addItem/clearAllItems 走同一协议，若普通号可用，游戏早被刷爆）⇒ 基本等于服务端 GM 白名单；且 GM 分支订单号 gm_<档>_<时间戳> 之后**仍要等 SC2201** |
| **e** | **其它免费口子** | 礼包码 ExchangeCodePopup→服务端；首充/月卡/免广告卡→commons+sendGetShopInfo；player.recharge 只读（仅 ConnectMgr 赋值，无客户端判定） | ❌ **未发现**。没有客户端首充判定、没有本地购买标记、没有本地月卡到期时间可写（MonthCardShop.buy 成功后只 updateTimeLabel()） |

补充说明（为什么"看起来"客户端有奖励弹窗）：多个弹窗在 sendRecharge(id).then(()=>{ D.setData(本地奖励配置); D.openUI(); }) —— **奖励弹窗是本地渲染的**，但那些道具是服务端已经发到账的东西；伪造成功只会看到"假弹窗"。

## 5. 最短路径建议

1. **先做一次"改动到底有没有生效"的验证**（比任何支付研究都重要）：用 IsGmLogin:!0 改包后，看登录页是否出现账号输入框。没出现 ⇒ 先解决热更遮蔽（删 /data/user/0/com.wbxxm.wbxxm/files/gg-hot-update 或改走 main.js 注入），否则后面所有结论都是"改不到"。
2. **若只想降成本**：改 XlsMgr.getShopPrice 让 amount=1，**真花 ¥0.01 下一单**（挑最小档），看 SC2201 是否到账、到账物品是否对应高价档。一单即可判定服务端是否校验金额/product_id。**这是客户端唯一可能生效的路径。**
3. **若要零元**：客户端无解，只能走服务端（GM 账号 / 服务端金额校验漏洞），不建议在本项目投人力。
4. 建议把结论回写 功能挂点分析.md 的内购节（原"IsGmLogin+CS1302 探针"结论需修正为：**IsGmLogin 只切登录方式**，且在 XI_PU 平台下 GM 支付分支不可达）。
