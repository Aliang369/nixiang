## (a) 签名校验落在 dex 还是 native —— 判定与证据

### a.1 判定

**TapTap 侧 = dex 层取身份、服务端裁决；dex 补丁能改"喂给服务端的是什么"，但改不了"服务端认为包被改过"。**

调用链（全部 `classes2.dex`，**[实测]** 逐行读过）：

```
TapTapSdk.init → TapTapSdkInitializer → GatekeeperManager.setupGateKeeperFlow
  → GatekeeperRepository.initialize()            ← 网络拉 gatekeeper 配置
      └─ GatekeeperRepository$initialize$1$networkData$result$1  (L93~L94)
           new GateKeeperRequest("android", context.getPackageName(),
                                 TapSignKit.INSTANCE.getSign(context))   ← 签名 MD5 在这里产生
           → GatekeeperApiService.fetchGatekeeper(...)                  ← 服务端比对
      ├─ 成功 → access$setLoadGatekeeperSuccess$p(true)   (initialize$1 L351)
      └─ 失败 → setLoadGatekeeperSuccess(false) + setGatekeeperError(...) (L309/L314)
                 └─ 后续任一业务接口 → showGatekeeperError() → showErrorToast() → Toast + banner(tag=TapInitializer)
```

- 唯一读签名的 TapSDK 类：`com/taptap/sdk/kit/internal/utils/TapSignKit.smali` **[实测]**
  （全 `com/taptap` 包内 `grep -l 'Landroid/content/pm/Signature;'` 仅此 1 个文件）
  `getSign(Context)` = `pm.getPackageInfo(pkg, 0x40).signatures[0].toByteArray()` → `CommonUtils.getMD5([B)`；
  `CommonUtils.getMD5` 走 `MessageDigest("MD5")` + `getHashString`（逐 nibble `toHexString`）⇒ 返回**32 位小写无分隔**的证书 DER MD5 ＝ `e5112fc602832f25b0956c9fa263f839` **[实测]**
- `GateKeeperRequest` 字段仅 3 个：`platform / packageName / packageSign` **[实测]**（`initializer/data/request/GateKeeperRequest.smali` L81–86）
  ⇒ 服务端就是拿 `packageSign` 跟开发者中心登记的证书指纹比。

### a.2 native 层无校验（反证）

| 检查 | 结果 |
|---|---|
| `libtapsdkcore.so` 里 `TapInitializer` 常量 | **0 命中** [实测]（`strings -a`） |
| `libtapsdkcore.so` 里中文 `包名`/`签名` | **0 命中** [实测]（命中的 signature 串全是 BoringSSL/OpenSSL 证书语义） |
| 26 个 `lib/arm64-v8a/*.so` 全扫 `TapInitializer|getPackageInfo|packageSign` | 仅 `libentryexpro.so`、`libluster.so` 各 1 处 `getPackageInfo`（穿山甲/优量汇广告 SDK 自查，与 TapTap 无关）[实测] |
| `libcocos.so`/`libtapsdkcore.so`/`libthemis.so` 含官方指纹 `e5112fc6` 或 `E5:11:2F` | 全 **0** [实测] |
| 全包硬编码官方指纹常量 | 只有 1 处，在 **dex**（见 a.3）[实测] |

⇒ **与爆裂防线 1.02.01 的关键差别**：那款是 `libtapsdkcore.so` 自己弹"包名、签名错误"（dex 补丁拦不住）；
本作 native 无痕迹，弹窗文案（`getDescription()`）是**服务端下发**的字符串，本地只在 `showErrorToast` 里有一个兜底默认串
（`"当前应用初始化信息错误, 请在 TapTap 开发者中心检查[当前应用包名]与[调用初始化接口设置的 clientId、clientToken]是否匹配"`，注意**不是**"签名错误"文案）。

### a.3 本作独有的第二消费者：喜扑 `SOPackageUtil.MarketP`（决定性证据）

```smali
# smali_classes3/com/xipu/startobj/util/check/SOPackageUtil.smali  L340~L392
.method public final MarketP(Landroid/content/Context;)Ljava/lang/String;
    const-string v0, "MD5"
    invoke-virtual {p0, p1, v0}, ...->getSignInfo(Landroid/content/Context;Ljava/lang/String;)Ljava/util/ArrayList;  # 取签名 MD5
    ...（取第 0 个）
    const-string v0, "E5:11:2F:C6:02:83:2F:25:B0:95:6C:9F:A2:63:F8:39"   # ← 官方证书 MD5（带冒号大写）
    invoke-virtual {p1, v0}, Ljava/lang/String;->equals(Ljava/lang/Object;)Z
    if-nez p1, :cond_23
    const-string p1, "1"      # 不匹配 → "1"
    return-object p1
    :cond_23
    const-string p1, "0"      # 匹配 → "0"
    return-object p1
.end method
```

调用点唯一：`smali_classes3/com/xipu/msdk/util/ParamUtil.smali` L1225 → 写进公共参数 `market` **[实测]**
（`mCommonParams.put("market", MarketP(ctx))`），随每次请求上报喜扑服务端。

**判定影响**：
- 改签后如果只打 TapTap 侧补丁，喜扑这边 `market` 会从 `"0"` 变 `"1"` —— 这是**服务端可见的身份变化**，属于 `skill/re-analyze/login/server-rejection-triage.md` 要追的那类问题，不能当"顺手"忽略。
- ⇒ **签名轨必须用 B（killer）**：`PackageInfo.CREATOR` 一换，`TapSignKit` 和 `SOPackageUtil` 同时读到官方证书，两个消费者一起归零，且**不需要**再改 `TapSignKit`/`MarketP`（避免双修、避免归因困难）。

### a.4 TapAD 宿主指纹（本任务范围外，登记为风险）

`assets/dirichlet/compatibility/android-host.json` 的 `host_source_fingerprint`（recon §3.1）**不含**本证书指纹（该文件里只有自哈希）[实测]，但 `com/tapsdk/tapad` 下有 40 个 smali 读 `Signature` **[实测 grep 计数]**。
⇒ 若 killer 生效则这些消费者同样看到官方证书，理论上安全；**仍按 recon 待验证项 #4 做最小改包冒烟**。

## (b) 门闩补丁的精确 smali 锚点（TapSDK 4.10.4，全部位于 `classes2.dex`）

> 4.10.4 与 4.8.2 的差异（**不要照抄模板旧锚点**）：
> `InitializerServiceImpl` 现在在 `com/taptap/sdk/initializer/**service**/`（旧：`initializer/`）；
> `login/internal/LoginActivityImpl`、`login/internal/handlers/**` **整包不存在**，改成 `login/impl/ui/activity/TapTapLoginActivity` + `login/impl/ui/fragment/TapLoginFragmentProvider`。

### b.1 主锚点：`GatekeeperRepository.isGatekeeperLoadedSuccessfully()Z`

`smali_classes2/com/taptap/sdk/initializer/repository/GatekeeperRepository.smali` **L482**，原形（`.registers 2`，读 `loadGatekeeperSuccess` 字段）：

```smali
.method public final isGatekeeperLoadedSuccessfully()Z
    .registers 2

    const/4 v0, 0x1

    return v0
.end method
```
（原体 `iget-boolean v0, p0, ...->loadGatekeeperSuccess:Z` + `return v0` 两行整体替换；`.registers 2` 不动）

### b.2 弹窗锚点：`GatekeeperRepository.showErrorToast(TapNetworkException)V`

**L363**，`private final`，`.registers 5`。方法体首行插 `return-void`，**保留原 `.registers 5` 与原方法体**（改成小值会 smali 报 `requires at least 3 registers`）：

```smali
.method private final showErrorToast(Lcom/taptap/sdk/common/network/throwable/TapNetworkException;)V
    .registers 5

    return-void
    # ↓ 原方法体全部保留（不可达）
```

### b.3 建议一起打的第二弹窗口：`GatekeeperRepository.showGatekeeperError()V`

**L491**，`public final`，`.registers 5`。这是 `checkInitialize` 失败时真正被调到的出口（内部两条分支：`gatekeeperError==null` 弹"当前应用还未初始化"，否则转 `showErrorToast`）。
同样首行插 `return-void`（保留 `.registers 5`）。**b.2 与 b.3 选一个也行，两个都打更保险**（二者互不冲突，均只影响 toast）。

### b.4 统一入口（可选加强）：`InitializerServiceImpl.checkInitialize(Z)Z`

`smali_classes2/com/taptap/sdk/initializer/service/InitializerServiceImpl.smali` **L81**，`.registers 6`（p1=`v5`）。
在**首行**插两条指令，其余原样保留：

```smali
    const/4 v1, 0x1

    return v1
```

### b.5 为什么必须打门闩（静默失败的证据）

`smali_classes2/com/taptap/sdk/login/TapTapLogin.smali` L109 `loginWithScopes(...)`：

```smali
    invoke-static {v0, v1, v2, v3}, Lcom/taptap/sdk/initializer/api/check/TapSdkChecker;->checkInitialize$default(...)Z
    move-result v0
    if-nez v0, :cond_1b
    return-void          ← 门闩不过 = 直接 return，无 toast、无回调 ⇒ "点了没反应"
```
（`LoginServiceImpl` L159/L351、`TapTapFirstPartyLogin` L157 同样先过 `TapSdkChecker.checkInitialize`）[实测]

### b.6 轨道纪律

按模板定案：**签名链条只用 B（killer）**，本节的 b.1–b.4 **仅在 killer 已挂但验收仍见门闩时**作为第二道加进来（一轮一变量，便于归因）。
若 killer 生效、验签不弹，b.1–b.4 可以全部不打。

## (c) 强制网页登录的精确锚点

### c.1 首选：`ClientLoginUtils.isClientLogin(Activity, Actions)Z` 恒 false

```smali
# smali_classes2/com/taptap/sdk/login/impl/utils/ClientLoginUtils.smali  L64（.registers 4，p1=Activity, p2=Actions）
.method public final isClientLogin(Landroid/app/Activity;Lcom/taptap/sdk/login/impl/data/model/Actions;)Z
    .registers 4

    const/4 p1, 0x0

    return p1
.end method
```

**为什么它是唯一正确的点**（[实测] 调用链已走通）：

```
TapTapLogin.loginWithScopes → LoginManager.login → LoginCoordinator.auth (L275)
   → LoginTypes$Companion.from(activity, Actions$Companion.from(regionType))       ← 全链路只此一处决定 loginType
        └─ ClientLoginUtils.isClientLogin(activity, action)  (L48)
             ├─ true  → LoginTypes.CLIENT
             └─ false → CloudGameUtils.isCloudGame(activity)? CLOUD_GAME : **WEB**
```
改 false 后 `LoginTypes` 在**最上游**就是 `WEB`，连带 `buildInfo` 的 `&tapsdk_login_type=web`、trackInfo 也一致 ⇒ 服务端/埋点口径自洽。
`WebLoginFragment.generateWebUrl()` 的基址来自 `WebViewUriProvider` **硬编码常量**（CN：`https://accounts.taptap.cn/authorize`，RND：`https://accounts.xdrnd.cn/authorize`），**不依赖 gatekeeper 下发**，所以门闩挂了也不至于取不到 URL [实测]。

`Actions$CN` 的 action 常量确认为 `com.taptap.sdk.action`（`login/impl/data/model/Actions$CN.smali` L67）[实测]；
**不需要**改这个常量（改它只是让"是否装了客户端"探测失效，属于旧版打法，语义不如改 isClientLogin 干净）。

### c.2 备选（c.1 若被 4.10.4 其它路径绕过再用）：`DefaultTapLoginFragmentProvider.provide`

`smali_classes2/com/taptap/sdk/login/impl/ui/fragment/DefaultTapLoginFragmentProvider.smali`
**L197** 的 `aget v2, v3, v2` 之后插一行 `const/4 v2, 0x3`：

```smali
    aget v2, v3, v2

    const/4 v2, 0x3          # ← 新增：强制落到 WhenMappings 的 WEB 分支(3)

    const/4 v3, 0x1
    if-eq v2, v3, :cond_6f   # 1=CLIENT
    ...
    :cond_5e                  # 3=WEB → WebLoginFragment
```
分支语义（[实测] 读 `:cond_5e/:cond_64/:cond_6f`）：1→`ClientLoginFragment`、2→`CloudGameFragment`、3→`WebLoginFragment`、其它→`NoWhenBranchMatchedException`。
**不要**动 `instance-of`/`$WhenMappings`（不是这套结构），也别把 3 写成 0/4（会抛异常）。

### c.3 不要用的点

`TapTapLoginActivity.fallbackToWeb(LoginRequest)` 只在 `fragmentProvider$1.executeFallbackStrategy` 里由 `CloudGameException` 触发，靠它兜底等于赌客户端登录失败时的路径，语义是"失败回退"不是"强制网页"。

## (d) killer dex：挂载点与证书

### d.1 底包形态判定 → 模板表格第 ② 种

| 判据 | 实测值 |
|---|---|
| `<application android:name>` | `com.xipu.msdk.XiPuSDKApplication`（`aapt2 dump xmltree`，line=103） |
| `<application appComponentFactory>` | `androidx.core.app.CoreComponentFactory`（系统默认，无自定义工厂） |

### d.2 两行补丁（`smali_classes2/com/xipu/msdk/XiPuSDKApplication.smali`）

```smali
# L2
.super Lbin/mt/signature/KillerApplication193;      # 原：.super Landroid/app/Application;

# L21（构造体内）
    invoke-direct {p0}, Lbin/mt/signature/KillerApplication193;-><init>()V   # 原：...Landroid/app/Application;-><init>()V
```
- `onCreate()` 里的 `invoke-super ...->onCreate()V` **不用改**（`Application` 仍在继承链上，`invoke-super` 沿链解析成立）。
- 时序保障：JVM/ART 初始化规则「先父类后子类」⇒ `KillerApplication193.<clinit>`（装钩子）**早于** `XiPuSDKApplication.<clinit>/<init>`，也早于 `attachBaseContext/onCreate` 与任何 ContentProvider。
- killer 类本身：`04_scripts/我在神界刷装备/assets/sjzz_killer_smali/mt/signature/KillerApplication193.smali`（893 行，`.super Landroid/app/Application;`，含 `$a…$l` 12 个内部类）——**现成可复用的参数化模板**，占位符 `@@CERT_B64_WRAPPED@@` / `"@@PKG@@"`，配套 `build_killer_dex_sjzz.sh` 已实现「从底包 v2 签名块取 DER → base64 → 64 字符折行 → 烘进 smali → smali assemble → 回读断言」全流程 [实测读过脚本]

### 红线与注意

- **不得替换证书后当交付**：本方案所有重签都用我方 keystore（`01_tools/starry_release.jks` 或项目约定），**官方证书只以 killer 运行期伪装的形式存在**，绝不允许把官方证书塞进重签包（v2 签名者必须换，签名者 `CN=gemjycn` 由 killer 在 `PackageInfo.CREATOR` 层伪装）。
- **不要改 `TapSignKit`/`SOPackageUtil.MarketP`**（同一链条双修 ⇒ 失败无法归因；killer 已覆盖两者）。
- **不要塞 `classes.dex`**（余量 1,821）；killer 走 `classes8.dex`。
- 热更风险：`assets/main.js` 的 `gg-hot-update` 会把热更目录挂在搜索路径首位、可覆盖包内 `main.js`/`index.jsc`——**本方案只动 dex，不受热更影响**（dex 不在热更范围）。
- 待验证项：① TapAD `host_source_fingerprint` 是否影响广告链路；② 喜扑服务端对 `market` 的处置；③ 若改签后仍出现验签弹窗，**先查 killer 是否 `mounted`**（killer 运行期不打日志，不能用"没日志"判未生效）。
