### 2.3 `tsc` 与 APK 条目的对应

对 `tsc` 的 105 条逐条按 `size + CRC32` 匹配 APK 原始条目：

- 匹配成功：**105 / 105**
- 未匹配：**0**
- 受保护条目去重后：**103**
- APK 总条目：**1,403**
- 未列入 `tsc` 的条目：**1,300**

受保护范围包括：

- `classes.dex`、`classes2.dex`、`classes3.dex`、`classes4.dex`
- 四个 ABI 的核心 so，含 `libtersafe2.so`、`libtprt.so`、`libcocos.so`、`libEncryptorP.so`
- `resources.arsc`
- `assets/main.js`、`assets/hortor/env.js`、`assets/hortor/load-manifest.js`、`assets/hortor/sdk.js`
- `assets/application.5fb03.js`
- `assets/src/chunks/bundle.d7717.js`
- `assets/src/cocos-js/cc.727dc.js`
- 多个 `res/*.webp`、`res/*.wav`、`res/*.mp4`
- `DebugProbesKt.bin`、Kotlin builtins、部分 `publicsuffixes.gz`

不在 `tsc` 中（示例）：

- `AndroidManifest.xml`
- `assets/config.json`
- `assets/supplierconfig.json`
- `assets/settings.ca18a.json`
- `assets/import-map.2248b.json`
- 若干 internal 配置
- 大量非核心 SDK 资源

`tsc` 对 `com/taptap/sdk/okhttp3/internal/publicsuffix/publicsuffixes.gz` 出现 3 条记录；APK 中没有重复 ZIP 名称。因此 `tsc` 不是简单的“按文件名去重白名单”，而是按保护对象实例记录。

### 2.4 `tsd`

- 51 条记录
- 51 个 SHA-256 全部唯一
- 这些 SHA-256 与本轮测试的条目路径、条目路径 + NUL、basename、包名、版本号等字符串都不匹配
- `tsd` 的语义仍为 **待验证**；它更像另一套对象/区段摘要，不是 APK 条目路径的直接 SHA-256

补充核对（2026-09-20 第二轮）：`tsd` 每条记录的 `tag` 可精确解释为 `CRC32(basename)`。
- `0xe521f41b = CRC32("libumeng-spy.so")`，对应 3 个 ABI 条目
- `0xc36a1892 = CRC32("libEncryptorP.so")`，对应 4 个 ABI 条目
- `0xd5d95c3a = CRC32("libtprt.so")`，对应 4 个 ABI 条目
- 其余 tag 同样逐项命中 basename CRC32；51 条记录对应 15 类核心库、按 ABI 展开后的 51 个受保护 so

但记录里的 64 字符摘要不是这些 APK 条目的普通 SHA-256（原始条目、压缩数据、路径字符串均不匹配），说明它是 ACE 自己的对象摘要格式，或摘要对象不是单个 ZIP 条目。`tsd` 的最终语义仍需实机或 native 还原验证。

### 2.5 清单结构对“新增条目”的含义

`tsc` 的 105 条记录只包含 `field0 + size + crc32`；`tsd` 的 51 条只包含 `basename CRC32 + 对象摘要`。两份清单都**没有**：APK 总条目数、中央目录摘要、EOCD 摘要或全 ZIP 摘要字段。

因此从清单结构本身不能推出“新增条目必然被拒”。更符合现有数据的假设是：ACE 至少对受保护对象做逐项核验；是否额外枚举 ZIP 并拒绝新增条目，取决于 VM 化校验分支或 Java 壳层，尚未静态证明。

## 3. Native 分析结果

### 3.1 `sub_319DF4` 是命令分发器，不是校验实现

`libtersafe2.so` 中：

- `sub_319DF4` 为 `TssJavaMethod` 命令分发器
- case 773 `sectionhash` -> 接口表 `+0x20`
- case 782 `gamerescrc` -> `+0x68`
- case 783 `filecrc` -> `+0x70`
- case 784 `newgamerescrc` -> `+0x78`
- case 786 `hash` -> `+0x88`
- case 854 `HashBySyscall` -> `+0x2A8`

这些分支只打印命令名并调用间接函数指针，不是校验本体。

### 3.2 `TssJavaMethod_SendCmd` 的真实路径

- `TssJavaMethod_SendCmd @ 0x2BFF14` -> `sub_2BFF68` -> `sub_2C0290`
- `sub_2C0290` 及其调用链在关键分支被 VM 化控制流保护，F5 只能看到 `BR` 跳转桩
- `sub_2DAB24` 唯一引用 `UnzipSignatureData`，但反编译只得到日志调用后 `return 0`，不是实际解包实现

### 3.3 JNI 注册表

`JNI_OnLoad @ 0x1C656C` 使用两张 `JNINativeMethod` 表：

- `0x51FAB8`，3 项：`init()I`、`onPause()I`、`onResume()I`
- `0x5615A8`，11 项：运行时由 `sub_1C6CC0` 填充

`sub_1C6CC0` 注册的 11 项实现对应 TSS SDK Java 接口：

- `sub_1C50E4`
- `sub_1C52A0`
- `sub_1C5638`
- `sub_1C5AA8`
- `sub_1C5B88`
- `sub_1C5E58`
- `sub_1C5F2C`
- `sub_1C5FE4`
- `sub_1C61A0`
- `sub_1C636C`
- `sub_1C6424`

这些不是 `AceApplication.initialize` 的实现；ACE 壳初始化位于另一条运行时注册/分发路径，本轮未在静态层解出可判定的“新增条目枚举”分支。

## 4. Java/服务端签名链

### 4.1 服务端 `signPrint`

`SignCheck.getCertificateSHA1Fingerprint()`：

- 读取 `PackageManager.getPackageInfo(pkg, 64)`
- 取 `PackageInfo.signatures[0]`
- 用 X.509 解析后计算证书 DER 的 SHA-1
- `RequestServerManager.getCommonParams()` 与 `Utils.getCommonParams()` 都写入 `signPrint`

0.1.57 实测：仅重签能启动并到登录，但服务端提示“指纹签名无效”。这说明 **仅重签不可交付**；即使 ACE 放行，也必须做运行时证书回灌。

### 4.2 当前包里的 `file_md5`

`Utils.getFileMD5()` 当前只写：

- `fileMessage = file.length()`
- `file_md5 = ""`

因此这条字段当前不构成新的阻断。

**适用范围**：0.1.57、旧 ACE 版本、MuMu 环境。不能直接外推到 0.1.65。

## 6. 标准外科路线的可行条件

若 ACE 只核验 `tsc` 白名单中的条目，则标准外科路线成立，形态应为：

1. 保留官方 `GameApplication` 类名与 `appComponentFactory`，不替换 Application。
2. 通过 Manifest 新增 Provider 完成注入，新增 `classes5.dex` 与 `lib/arm64-v8a/libstarry_magic.so`。
3. `tsc` 中的 105 条受保护条目逐字节不变（不是“重新压缩后 CRC 相同”，而是原始条目内容不变）。
4. 在 Provider 内执行 `SignSpoof`，回灌官方 `CN=hortor` 证书，覆盖服务端 `signPrint` 读取。
5. 在 native/JS 层实现《遗弃之地》战斗功能 Hook；旧 `YqzdMod.cpp` 的四锚点可作为 0.1.65 的初始候选，但需要按 0.1.65 的 JS/热更内容重新确认。

若 ACE 仍枚举 ZIP 中央目录并拒绝任何新增条目，则标准外科 APK 没有出口，当前包只能放弃。

## 7. 关键未决问题

**唯一决定性问题**：当前 0.1.65 的 ACE 是“按 `tsc` 白名单逐条核验”，还是“枚举整个 APK 并拒绝新增条目”？

第二轮独立核对（2026-09-20）补充：

- `tsd` 的 tag 已确定为 `CRC32(basename)`，51 条对应 15 类核心 so 按 ABI 展开的 51 个条目
- `tsc`/`tsd` 均不含总条目数、EOCD、中央目录或全 ZIP 摘要
- `libtersafe2.so` 的 `filecrc`、`gamerescrc`、`sectionhash` 是命令名，实际分支仍 VM 化
- `libtprt.so` 是运行时保护/执法层，含 13 组 ELF hook 桩与 `ptrace/fork/execv/kill/mprotect` 等导入
- 当前库内没有第二款同版本 ACE 原包可做对照，无法用横向证据替代实机探针

因此静态层的上限是：**支持“逐项白名单核验”假设，但不能排除“全 ZIP 枚举”**。最终判定只能由新增条目存活探针给出。

现有静态证据只能说明：

- `tsc` 确实是一份完整的受保护条目清单，105 条全部匹配
- `tsc` 不包含 `AndroidManifest.xml` 和若干 assets 配置
- 当前 native 的校验实现被 VM 化，未解出“新增条目枚举”分支
- 旧版 0.1.57 的毒丸现象不能直接证明 0.1.65 的机制

因此：

- “ACE 会拒绝新增条目” = **待验证**
- “ACE 只按白名单核验” = **待验证**
- “标准外科路线可行” = **NOT PROVEN**
- “标准外科路线不可行” = **也未被 0.1.65 证据证明**

## 8. 建议的最小验证实验

### 实验 A：最小启动存活探针

目的：区分“新增条目被拒绝”与“新增条目被放行”。

构造最小外科候选包：

- 官方 `classes.dex` ~ `classes4.dex`、`resources.arsc`、所有 `tsc` 条目字节不变
- 保留官方 `GameApplication`
- 仅新增：
  - `classes5.dex`：最小 Provider + 一条启动日志
  - `lib/arm64-v8a/libstarry_magic.so`：只做 `JNI_OnLoad` 日志和最小初始化
- Manifest 只新增 Provider 与必要权限
- 不实现任何游戏功能，先观察是否触发 ACE 击杀

成功标志：

- 冷启动能到登录界面
- `logcat` 出现 Provider/native 启动标记
- 无 `SIGSEGV`、`SIGBUS`、ACE 毒丸、FATAL、ANR

失败标志：

- 启动阶段或登录后固定窗口内出现 ACE 击杀
- 此时应判定“新增条目被拒绝”，停止标准外科路线

### 实验 B：单变量差分

在实验 A 基础上分别测试：

- 只新增 `classes5.dex`
- 只新增 `lib/arm64-v8a/libstarry_magic.so`
- 只新增 assets 配置

目的：确认是“所有新增条目”被拒，还是某类路径/后缀被拒。

### 实验 C：签名回灌闭环

在实验 A 通过后：

- 加入 `SignSpoof`
- 验证服务端登录不再提示“指纹签名无效”
- 再进入功能实现与验收

### 装机前置

实验 A 需要：

- 异签安装预计必须卸载官方包
- 卸载会清本地数据
- 当前没有安装/卸载/清数据授权

因此本轮不执行装机；需要用户明确授权后才能继续。

## 10. 结论

对 0.1.65：

- 包身份、签名、ACE 组件和 `tsc` 白名单已核清
- `tsc` 105 条全部匹配，白名单范围明确
- 旧版 0.1.57 的“全包校验”结论不能直接套用
- 当前决定性问题只剩“ACE 是否拒绝新增条目”
- 标准外科 APK **尚未宣告死亡，也尚未证明可行**
- 下一个有信息增益的动作是最小启动存活探针；该动作需要安装/卸载授权

在获得授权前，不能把标准外科称为已死路线，也不能把当前包称为可交付星空包。
