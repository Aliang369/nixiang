## 2. EnterFrameFromInterpreter 重定位（本次核心）

### 2.1 方法

旧 0.9.10 so 已不在盘上，无法子串指纹匹配。改按 HybridCLR 源码语义在 1.0.1 上直接识别：

1. `04_scripts/_common/find_hybridclr_interp_entries.py` 扫 prologue + BL 引用图
2. 发现 `0x265cec0`(VA) 被 **51582 个** BL 引用，来源遍布 .text 开头的 thunk 区
   → 这是 `Interpreter::Execute`（native→C# 独桩共享入口）。旧版已证「钩 Execute 看不见扣血」，排除。
3. 列出 Execute 函数体（[0x265cec0, +0xd5f8]）内部 BL 的全部低地址目标，共 5 个候选
4. llvm-objdump 逐个反汇编，按源码特征锁定

### 2.2 实锤（llvm-objdump，VA 域）

`0x265b084` 起函数，ABI 与 0.9.9/0.9.10 完全一致（`x0=this, x1=MethodInfo, x2=argBase`）：

```
265b0a4: ldr  x8, [x20, #0x58]     ; mi 扩展
265b0ac: ldr  w9, [x8, #0x2c]      ; maxStack
265b0b0: ldr  w8, [x8, #0x20]      ; argStackObjectSize
265b0b8: sub  w1, w9, w8           ; ★ maxStack - argStackObjectSize
265b0bc: bl   0x265b0f8            ; ★ AllocStackSlot（含扩容分支 0x265b138）
265b0d4: stp  x20, x19, [x0]       ; ★ 帧压入 {MethodInfo, argBase}（不拷参数）
```

被 Execute 内部 16 处 BL 引用。与旧注释「AllocStackSlot(maxStack - argStackObjectSize)，不拷参数」逐条吻合。

### 2.3 结论

| 符号 | 0.9.10 (file) | 1.0.1 |
|------|---------------|-------|
| EnterFrameFromInterpreter | 0x2656920 | **file 0x2657084**（VA 0x265b084） |
| Interpreter::Execute（不钩） | 0x265875C | VA 0x265cec0（51582 thunk refs） |
| text PT_LOAD delta | — | va = file + 0x4000 |

`CstjjsMod.cpp` 仅改 `FILE_ENTER_INTERP = 0x2657084`，hook/过滤/补参逻辑零改动。
运行时 `FileOffToVa` 自行解析 maps，无 base+RVA 依赖。

## 5. 服务生命周期三修复（20260908，共享层 MenuService.java / Manifest）

> 现象：MuMu 上滑关闭游戏后，菜单悬浮球"重新加载一次"仍挂在屏幕上；真机（小米 SwipeUpClean
> force-stop）无此现象。首版修复（stopWithTask + onTaskRemoved stopSelf）未生效。

### 5.1 根因（logcat 实锤，15:59 时序）

```
15:59:52.376 W/ActivityManager: Scheduling restart of crashed service …for start-requested
15:59:53.395 I/ActivityManager: Start proc 9143:com.netkuu.changsheng.tjjs … for service {MenuService}
15:59:53.612 I/MenuService: startService (plain, no-FGS)   ← Application.onCreate 注入点重新执行
15:59:53.649 I/NativeMenu: attached OVERLAY                 ← 菜单挂上僵尸进程
15:59:53.661 I/MenuService: task removed → stopSelf         ← stopSelf 后仍被重新 onStartCommand
15:59:53.740 … attached OVERLAY → 菜单稳定存活
```

MuMu 上滑走**直接杀进程**路径（非"移除任务"），onTaskRemoved/stopWithTask 均不触发；
AMS 按 start-requested 自动重启服务；新僵尸进程里 Application.onCreate 注入点再次调
`MenuService.start()`（进程级标志判定因此失效）；模拟器已授悬浮窗权限 → OVERLAY 模式
无需游戏 Activity 即可挂悬浮球。

### 5.2 修复（活宿主判定 + 看门狗自杀）

- Manifest：`stopWithTask="false"` → `"true"`（工程模板 + cstjjs/zhmr 两装配脚本同步）
- `onTaskRemoved`：`stopSelf()` 兜底（覆盖"移除任务"路径，MuMu 杀进程路径由下条兜底）
- `onStartCommand`：`startedActivityCount>0 || resumedActivityCount>0` 才立即挂菜单；
  否则延迟挂载 + **25s 看门狗**——超时仍无宿主则 `stopSelf()`（僵尸进程静默消失，
  屏幕上不会出现没有游戏的菜单）。`onActivityStarted` 时取消看门狗。
- 注意：不能用进程级/Application 级标志判僵尸——AMS 重启进程会重跑 Application.onCreate
  注入点；Activity 生命周期计数在进程死亡时自然重置，是最可靠的判据。

### 5.3 验收

修复版上滑后悬浮球一次都不出现；AMS 重启的僵尸进程 25s 内自杀（日志
`no host within 25s → zombie service, stopSelf`）。
