## 0. 一句话结论

这个包**不是我们做的、也不是斌哥做的**，是第三方「**卡密平台**」壳：APK 里塞了 **3 个文件**（加密引导 dex + 原生 mod so + 外壳 dex），开机后外壳解密引导 dex → 引导 dex 去**云端拉取悬浮面板 dex** → 面板要求输入**卡密**（走第三方平台 `wy.llua.cn`），验证通过后由面板把开关值推给原生 so，原生 so 用 il2cpp 内联钩子改游戏（伤害/锁血/免广告/全屏吸取/加速/一键胜利）。

**出厂是「全关」**：云端 `dshk.cfg` 里所有功能都是 0 ⇒ 没有卡密的人拿到的是**原版游戏**。

### 1.1 注入识别：零 mtime 分组

2722 个 zip 条目里，**2716 条** mtime = `1981-01-01 01:01:02`（原始打包时间），**只有 6 条** mtime = `2024-01-01 00:00:00` ⇒ 这 6 条是注入/重签名产物：

| 条目 | 大小 | 角色 |
|---|---|---|
| `classes5.dex` | 10,792 B | **外壳**（`com.unity.plugin.*`，仅 4 个类） |
| `assets/dshk_payload.bin` | 19,776 B（stored 未压缩） | **加密的引导 dex** |
| `lib/arm64-v8a/libunityhelper.so` | 13,440 B（stored） | **原生 mod**（il2cpp 钩子） |
| `META-INF/ANDROIDD.SF` / `.RSA` / `MANIFEST.MF` | — | 重签名（`ANDROIDD` = 签名别名） |

**官方部分未被修改**：官方 `classes.dex`~`classes4.dex`、`libil2cpp.so`、`libunity.so`、`libmain.so` 内 grep `unityhelper`/`LoaderEntry`/`unity/plugin`/`dshk` **全为 0**；21 个 so 的 `DT_NEEDED` 无一处引用 `libunityhelper`（故它只能由 dex 里 `System.loadLibrary` 加载）。manifest **无注入组件**（`<application>` 无 `android:name`，组件全是官方/广告 SDK）⇒ 触发点就是「Android 多 dex 自动加载 `classes5.dex`」＋该类静态初始化里的 `System.loadLibrary("unityhelper")`。

对比：斌哥 1.1.5 外壳是自加两个 so（`libSDKloading.so` + `libtoolChecker.so`，dex 到 `classes8.dex`）；本包走「**dex 外壳 + 加密载荷 + 单个原生 so**」路线，**不是同一家的壳**。

## 2. 加载链

```
Android 加载 classes5.dex
  └ com.unity.plugin.FileProviderImpl (ContentProvider 子类，静态块 loadLibrary("unityhelper"))
        ├ nativeGetKey()  ← libunityhelper.so 返回 32 B 密钥
        ├ 读 assets/dshk_payload.bin  (19,776 B, salt16‖nonce12‖ct)
        ├ AES-GCM 解密 → 19,732 B dex（v1 方案）
        ├ InMemoryDexClassLoader.loadClass("com.unity.plugin.LoaderEntry")
        └ LoaderEntry.start(ctx)
              ├ GET http://js.sheng15.site/dshk.cfg          (774 B 明文配置)
              ├ 把配置值原样推给 native（pushToNative/applyAll）
              ├ GET http://js.sheng15.site/dshk_helper.bin   (54,588 B 密文)
```

真机日志（`/sdcard/Android/data/com.survivor.acecn/files/dshk_boot.log`，pid 14003，13:48:06→13:48:10）逐行印证了上面每一步，包括 `payload decrypted: 19732 bytes`、`payload decrypted v2: 54588 -> 54540 bytes`、`helper dex ok: com.unity.plugin.CloudPanel (54540 bytes)`、`cloud panel shown`。

### 2.1 密钥与两套解密方案（已完整还原，可离线复现）

**密钥**（`Java_com_unity_plugin_FileProviderImpl_nativeGetKey`，`0x69a4`）：

```asm
ldr q0, [x8, #0x1f0]   ; = .rodata[0x11f0:0x1200]
ldr q1, [x9, #0x1e0]   ; = .rodata[0x11e0:0x11f0]
stp q0, q1, [sp]       ; 拼成 32 B 后 NewByteArray/SetByteArrayRegion
```

⇒ **IKM = `7c147cf1dd58d7be623a4ba2c9d03728a057ca9ddda9770bcdf46c95ba31148b`**（前 16 B 来自 0x11f0，后 16 B 来自 0x11e0）。

**v1（本地 `assets/dshk_payload.bin`）**：`salt=asset[0:16]`、`nonce=asset[16:28]`、`ct=asset[28:]`；
`K = HMAC-SHA256(key = HMAC-SHA256(key=salt, msg=IKM), msg = "dshk-payload-v1"‖0x01)[:32]`；`AES-256-GCM(K, nonce, ct)`。

**v2（云端 `dshk_helper.bin`）**：`salt=[0:16]`、`nonce=[16:28]`、`expectedLen=BE32([28:32])`、`body=[32:]`；
`prk = HMAC-SHA256(passphrase(), salt)`（`passphrase()` = 硬编码两个 4×8 字节表逐字节异或，值 = `630d6127fc2095b787eff611070d7ed0128242b2918fb69f85d9d331144c9db1`）；
`kEnc = HKDF-Expand(prk, "dshk-enc-v2", 32)`、`kPerm = HKDF-Expand(prk, "dshk-perm-v2", 32)`；
`body = undoPerm(body, kPerm)`（Fisher-Yates 置换，随机流 = `SHA-256(kPerm‖BE32(ctr))` 串接）；再 `AES-256-GCM(kEnc, nonce, body)`，要求结果是 dex 且长度 == `expectedLen`。

（v1/v2 的实现细节与其 Java 源码落在 `/tmp/dkzj/boot_jadx/sources/com/unity/plugin/LoaderEntry.java:286-440`。）

## 6. 诚实边界

1. **全是客户端侧结论**。卡密验证的真假最终由 `wy.llua.cn` 判定，我们没有、也不该去动它；文档只描述它**怎么被调用**。
2. **「功能有没有生效」只从静态代码 + 日志推断**。真机上 `dshk_panel.log` 记录 `canOverlay=true added=false onScreen=false`（悬浮窗权限有、当时那一瞬还没挂到窗口），我们**没有**操作屏幕去点面板（m01772），所以各开关的实际游戏内效果**未经我验证**。
3. `assets/na.czl`、`assets/hnlhol.dat` 两个可疑资源**未判定归属**（无官方 1.1.7 副本可比对）；目前证据（时间戳属原始群、dex/so 无引用）倾向官方/广告 SDK 自带。
4. 本包与斌哥壳、我们的星空包**没有任何代码/密钥/签名重合**。

## 7. 反作弊 / 上报拦截勘察（对照问题：「这游戏没有过检测或者拦截上报吗？」）

结论一句话：**游戏侧有——而且是「战斗录像上传 + 客户端重放校验 + 服务端下发重算对账」这条比勇士之心更重的链路；卡密包侧完全没有**（零过检测、零拦截上报）。

### 7.1 游戏侧：三层可证据化的面（源：`assets/bin/Data/Managed/Metadata/global-metadata.dat`，27,620,056 B）

**① 客户端本地战斗校验器**
`HotFix.BattleVerifyServices.BattleVerifier` + `BattleVerifyResultStatus` + `IBattleVerifierInput`，
各战斗类型各有一个解析器：`BattleServer.Verify.Parser|{MainCombatParser, GoldDungeonCombatParser, CrossArenaCombatParser, TowerCombatParser, UnionBossCombatParser, WorldBossCombatParser}`（接口 `ICombatRequestParser`），
重放引擎 `HotFix|BattleRecSegmentReplayController` / `BattleRecReplayParser` / `BattleRecReplaySegment` / `BattleRecSegmentInput`。
判定结果枚举（= 已知的失败面）：`UnKnow, DecompressedError, WorldInitInfoFail, FrameDataReadFail, RunFrameError, NotEnd, ServerStartUpFail, OtherException`。
对应的错误码枚举 `BattleServerError` 里另有一组：`BsVerifyServerStartUpError, BsVerifyByteArrayTooLarge, BsVerifyVersionNotMatch, BsVerifyFrameDataReadError, BsVerifyRunFrameError, BsVerifyRunFrameLogicError, BsVerifyDecompressDataError, BsVerifyReadWorldInitInfoError, BsVerifyNotBattleEndError, BsVerifyUnknowError`。

**② 上报/上传链路（= 真正值得「拦截上报」的对象）**

**③ 服务端下发重算 + 作弊错误码**

**④ 包内安全组件（都在 1.1.7 卡密包里，卡密包照样跑得起来）**
`libsecsdk.so`(442 KB)、`libsgcore.so`(88 KB)、`libpanglearmor.so`(265 KB)、`libti-monitor.so`、`libtobEmbedEncrypt.so`、`libBugly_Native.so`。
`AndroidEmulatorDetector` / `AndroidProxyDetector` 等**来自 BestHTTP/广告 SDK（噪声，不作为游戏反作弊证据）**；元数据里**没有** `frida` / `Xposed` / `magisk` / `ptrace` / `SafetyNet` / `PlayIntegrity` 任何标识。

### 7.2 卡密包侧：零过检测、零拦截上报

- 注入物只有 `classes5.dex`(10,792 B)、`assets/dshk_payload.bin`(19,776 B)、`libunityhelper.so`(13,440 B) 三个自造体 + 3 个签名文件；`strings` 全关键词扫（`anti|cheat|detect|report|upload|verity|sign|integrity|root|frida|xposed|检测|上报|封`）：
  - `libunityhelper.so` 全是**功能面**（`damage -> 0x%llx ; 已打开=%d%s`、`hplock/adskip/pick/speed/switch`、`CTRL armed: …`、`framebuffer`、`il2cpp api: get_class/get_method/invoke/domain/asm/class`、`found libil2cpp.so base=`）与 il2cpp 运行时管道，**没有任何反检测或上报拦截**。
  - 面板 dex 唯一带"反检测"色彩的东西是 **root 静默提权**：`overlay appop missing -> root grant (silent)`、`root appops grant exit=`、`root appops grant failed:`（拿不到悬浮窗权限时自己 `appops` 授权）。
  - 三个 dex 都没有 sink hook、没有 useTime 补偿、没有伤害字段还原、没有上报出口拦截 —— 与勇士之心卡密包（四层 compensating 过检测）形成鲜明对照。
- 它改的恰好是**会被上报的字段所依赖的量**（伤害/攻速/时间倍率），却把「英雄攻击」上限压在 **10x**（我方星空包 100x）——可能是作者规避对账异常的自觉取舍。**属推测，不是证据。**

### 7.2.1 全量穷尽扫描（证明「没有」而不是「没看到」）

**由导入表得出的硬结论**：该 so **没有 `mprotect` / `mmap` / `ptrace` / `syscall` / `socket` / `open` / `read` / `write` / `fopen`** ⇒ 它**改不了代码页、读不了文件、联不了网、也反不了调试**；它只会 `dlopen(libil2cpp.so)` + `dlsym(il2cpp_class_from_name / il2cpp_class_get_method_from_name / il2cpp_runtime_invoke / il2cpp_thread_attach …)` 后**反射调方法/改字段**（日志 `found libil2cpp.so base=0x%lx`、`il2cpp api: …`、`damage -> 0x%llx`）。这是「用官方 API 改值」，**与「挂上报出口」在机制上就是两条路**。

**它唯一接近「隐蔽」的三件事（都不是过检测）**：

2. **Java Activity 生命周期 hook**（面板侧，为挂悬浮窗）。
3. **root 静默 `appops` 授悬浮窗权限**（`overlay appop missing -> root grant (silent)`）⇒ 权限绕过。
另外它会调 `runInBackground -> true`（`runInBackground: setter=%p (ticks=%d)`）= 让游戏后台继续跑，也是功能项。
