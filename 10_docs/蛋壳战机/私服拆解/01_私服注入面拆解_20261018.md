### 2.2 账号（Unity PlayerPrefs 注入 + 悬浮徽标 + 触摸闸门）— dex5

- **`AccountStore`**（1770 行，dex5）：直接读写 Unity 的 SharedPreferences 文件 `<pkg>.v2.playerprefs`（`AccountStore.smali:522`、`:539`），维护本体的账号键：`ACCOUNT_Key` / `ACCOUNT2_Key` / `DEVICEID_Key` / `ACCOUNT_LIST_Key` / `ACCOUNT_PENDING_SELECTION_Key` / `ACCOUNT_AUTO_START_Key` / `ACCOUNT_REMOVED_ACTIVE_Key` / `ServerUrlOverrideKey` / `ServerUrl` / `ACCOUNT_NoDefault_Build_Key`（`:88-142`）。

- **`AccountBadge`**（1507 行）：`attach(activity)` 把徽标**塞进宿主 activity 的 `android.R.id.content` FrameLayout**（`AccountBadge.smali:29-49`），不是独立 WindowManager 窗口；点击弹 PopupWindow 账号菜单（切换/移除账号，`:476/506/521`），移除走 `AlertDialog`（`:127`）。
- **`AccountLifecycle`**（1534 行）：`DxxUnityActivity.onCreate` 里 new（`AccountLifecycle.smali:73`），构造里调 `LoginBridge.install`（`:98`）。接管宿主 `dispatchTouchEvent`：

### 2.3 防沉迷 — Java 侧为空壳，真身在本体 C#

- Java 侧只有 `LoginInjector` 的**字符串名单**（`LoginInjector.smali:31-43`，`:453` 用于匹配）：
  `com.xcsp.sdk.activity.AntiAddictionActivity`、`com.xcsp.sdk.activity.LoginActivity`、`com.cw.platform.core.activity.{Login,Register,BindPhone,Authenticate,VerifyId}Activity`。
  这 7 个类在包内**一个都不存在**（§0 修正 2）→ 名单是给「另一种宿主」预留的替换表，本包不生效。
- 真正的实名/防沉迷在本体 C#：`global-metadata.dat` 含 `Gorilla.AntiAddictionManager` / `AntiAddictionPolicy` / `AntiAddictionClock` / `AntiAddictionEntryEvaluator` / `AntiAddictionLoginPromptHandler` / `AntiAddictionConfig`（metadata strings 165440–166016）、`Gorilla.ID` 的 `RealNameAge`、`Gorilla.Audit.AccountStore` / `AuditIdentityValidator`（226813–226890）。
- 结论：**防沉迷＝本体 Gorilla ID SDK，落在 dex 注入面之外**；它不校验客户端完整性，只影响「账号是否实名/是否被限时」，服务端判。

### 2.4 礼包码（服务端发奖通道）— dex7 + liblgsgift.so

- **入口类**：`com.dkzj.accountauth.GiftCodeReward`（543 行）：

  - `start(Activity)`（`:505`）起守护线程 `lgs-giftcode-reward`，`GiftCodeReward$1.smali:52` 每 **2500 ms**（`0x9c4`）轮询一次。

  - `eventId` 变了才 `runOnUiThread` → native `showReward(json)`（`:502` native 声明；`GiftCodeReward$1.smali:57-63`）。

## 5. 星空入口落位建议

### 5.1 Provider 插在哪

- **实例化顺序 ≠ XML 顺序**：Android 按 `initOrder` **降序**实例化 provider，同值才按 XML 顺序。本包 20 个 provider 里有 3 个非 0：

  | 次序 | provider | manifest（dump 行 / 原始 line） | initOrder |
  |---|---|---|---|
  | ① | `com.gorilla.base.InitializeProvider` | dump:330 / line=134 | **1000** |
  | ② | `com.sigmob.sdk.SigmobFileProvider` | dump:1174 / line=313 | **200** |
  | ③ | `com.gorilla.channel.core.ChannelInitializer` | dump:230 / line=105 | **100** |
  | ④…⑳ | 其余 17 个（`GorillaShareFileProvider` dump:335/line=135、快手/uniwebview/百度/byazt/字节/GDT、`androidx.startup` dump:1314/line=346） | 按 XML 顺序 | 0 |

- **建议落位**：`<provider>` 写为 `<application>` 的第一个子元素（在 `ChannelInitializer`，raw line=105 之前），并 **`android:initOrder="2000"`**（> 1000）。
  - 只写 `initOrder=100`（上一版国服脚本的取值）在本包会排到 **第 3**（InitializeProvider 1000 → Sigmob 200 → Starry 100）。`InitializeProvider` 只把签名写日志（E18），`SigmobFileProvider` 是空实现的 FileProvider（`outA0/com/sigmob/sdk/SigmobFileProvider.smali` 仅构造函数），二者不会因签名被换而拒绝启动；但「先于其它 Provider/SDK 回灌签名」的设计意图会落空，故仍建议提值。
  - XML 位置用于「同 initOrder 时」兜底，真正决定次序的是 `initOrder`，两者都要给。
- **authority**：`com.wxdmxga.dkzj.starryinit`。已逐一比对现有 20 个 authority（全部 `com.wxdmxga.dkzj.*`），无冲突。
- 组件类型声明：`android:exported="false"`、`android:enabled="true"`，与既有脚本一致（`surgical_dkzj_1.1.8.sh:146-153`）。
- 注意：上一版脚本是把 provider **append 在 `</application>` 前**（`surgical_dkzj_1.1.8.sh:150`，靠 `initOrder=100` 抢先；在国服里其余 provider 都是 0 时有效）。私服有 1000/200 两个高值，**必须同步把 initOrder 提到 2000**，否则次序会变。

### 5.2 宿主真实 Application 类名

- manifest `<application>` **没有 `android:name`**（dump:157-171 逐条：theme/label/icon/debuggable=false/allowBackup=false/hardwareAccelerated/supportsRtl/extractNativeLibs/usesCleartextTraffic=true/networkSecurityConfig/roundIcon/**appComponentFactory**/requestLegacyExternalStorage/enableOnBackInvokedCallback，无 name）。
- 因此宿主 Application = **`android.app.Application`（默认）**；`appComponentFactory` = **`androidx.core.app.CoreComponentFactory`**（dump:169，原值）。
- 组件工厂只负责实例化组件，**不是 Application**；`CoreComponentFactory` 会先尝试组件的 `mComponentFactory` 静态字段（AppCompat 之类），私服没有自定义工厂。
- → 星空**不要**新增/替换 `android:name`（本仓 `StarryInitProvider` 的设计即「无 Application 替换注入」，见 `mod菜单/starry-mod-menu/app/src/main/java/com/starry/magic/StarryInitProvider.java` 头注释）。

### 7.1 红线（必须原样保留）

### 7.2 隐患（按危险度排序）

| # | 隐患 | 机理与证据 | 处置建议 |

## 9. 未闭环项

1. **服务端是否校验签名/包名**：本地无签名门（E18），但 `dzpxldn.cn` 的 `/game`、`/gateway`、`/api/giftcode/reward` 是否比对签名或包名，静态无法确认（需真机抓包，本任务不做真机）。
2. **`LoginProvider` 未注册是否刻意**：manifest 里确实没有它（E16）；若有人误补注册，`autoLaunch=false` 仍不会自动弹登录，但会多一个空 provider。
3. **防沉迷的实际拦截点**：`AntiAddictionEntryEvaluator` / `LoginPromptHandler` 何时拦（进游戏/进战斗/时长），需 dump 本体 C# 才能定，不属于 dex 注入面。
4. **私服是否给本体加了额外反作弊**：metadata 有 `BattleCheat`/`is_cheat` 字段，libil2cpp 无调参痕迹；是否新增客户端判据需 `dump.cs` 对照国服 1.1.8 才能定。
5. **`/gateway` 账号体系与 WebView 账号体系是否互通**：两套入口（`AccountAuthActivity` vs `LoginActivity`）是否写同一个 `AccountStore` 键，代码上是（都写 `ACCOUNT_Key/ACCOUNT2_Key`），但服务端账号是否同一库无法静态确认。
